## 1. 为什么 B1 是核心闭环

产品的可用性由一条最短链路决定：用户在会话里发起一个任务，任务在后台执行，产出一个文件，文件能在会话里被看到、被打开展示、被下载，工作台能看到这次交付的汇总。这条链路上任何一段断掉，用户都拿不到可用的结果：任务只是接口、文件只是数据库行、工作台只是空页面。B1 选的就是这条链路，而不是按域铺功能。

B1 的四个 PRD 组各自守着链路的一段：`PRD-TASK-001/002` 让任务从发起到完成有可读的状态与进度；`PRD-TASK-003` 让长任务不阻塞会话并在会话里留下开始与结束两条消息；`PRD-TASK-006` 让中断、失败、取消都有出口；`PRD-FILE-001/003/004` 让产物从会话与工作台两侧都能被列出、打开、下载。`PRD-WORK-004` 是工作台的汇总面，三条链路的出口都在这里收口。

## 2. 这次改什么

产品层补证的产出是本变更包与两份产品 spec 的 AC 改写，不改代码、不改测试、不改状态。

- P2-TASK：6 个 PRD 的泛化 AC 改写为 30 条可判定判据，重点补齐 `PRD-TASK-003`（异步开始/结束消息、重启不重复写）、`PRD-TASK-004`（复杂度分级与确认门禁）、`PRD-TASK-005`（子会话归属）、`PRD-TASK-006`（取消幂等、重试递增、预算触顶、重启恢复）。
- P4-FILE：6 个 PRD 的泛化 AC 改写为 31 条可判定判据，重点补齐文件页入口与列表、预览与下载的分类型验收、目录隔离与四条越界负用例。
- 新增本变更包：proposal / spec / tasks / test-plan / evidence，出口判据写清"发起任务 → 执行 → 产出文件 → 工作台汇总"一条链。

## 3. 不改什么

## 4. 现状差异（关键 6 条）

- 单任务的开始/结束消息未实现：`backend/internal/modules/tasks/workflow.go:447-450` 对 `task.WorkflowID == ""` 直接返回。
- 预算未接真实用量：`backend/internal/modules/chat/runtime.go:305` 固定返回 `taskTokenBudget:200000、used:0`。
- 跨会话读任务无归属校验：`GET /api/tasks/{id}` 只按 id 查。
- 前端没有文件页：会话侧只有任务组与交付物卡片，`frontend/src/app.tsx:813-814` 用 `window.open(previewUrl)` 整页打开。
- 上传没有扩展名白名单：只有文件名规约与落点校验（`attachments.go:280`）。
- 文件分类型渲染与下载文件名安全未验收。

## 5. 已裁决（8 条，2026-11-22）

- 任务消息角色与分类：开始消息取 `role=agent`、`category=progress`，带 `task_id`；历史 `messages` 数据不迁移（`P2 Q-01`）。
- 复杂度分级与确认事件类型固定为 `complexity_classified`、`task_confirmed`；不设自动执行超时，30 分钟未确认由前端提示、12 小时未确认在概览标「待确认超时」，只标记不执行（`P2 Q-02`）。
- 父会话概览只统计本会话任务，子会话任务不在父层计数，父层提供「含 N 个子会话」入口（`P2 Q-03`）。
- 进度刷新走 WS `task.progress` 加 5 秒兜底轮询，AC 只约束 5 秒内可见（`P2 Q-04`）。
- 0 字节文件返回 HTTP 400、`error.code="empty_file"`（`P4 Q-01`）。
- 预览在会话右栏「文件」标签内抽屉渲染，PDF 走新标签页，所有类型始终提供下载（`P4 Q-02`）。
- 同名重复生成新增产物并依次追加 `-2`、`-3`，不覆盖原产物（`P4 Q-03`）。
- 文件页入口固定在会话右栏「文件」标签，条数与 `GET /api/sessions/{id}/files` 一致（`P4 Q-04`）。
