# 43 F5 治理与安全补强 —— 多租户 / 权限隔离 / 合规

> **这份文件回答一个问题**：多租户、权限隔离、合规这些"Agent 系统特性"，有没有必要放进本框架？
> **一句话结论**：**已经放进来了，但放得深浅不一**——三样都在 `33 v1.3` 的 F5 治理与安全域里有条目，也都在 `31 v1.3`（边界/决策权/权限模型三值）与 `34 v1.3`（高合规六判据/记录三性）里有声明位；真正的缺口不是"要不要放"，而是三处**"判得出来、落不到控件"**：租户只有一行、权限没有合并公式、合规判据没驱动字段。
> **本文件只出增量，不重写 v1.3 三件套**：作为 `33 v1.4` / `34 v1.4` 的输入。判定依据是 122 型次验证暴露的同类机制缺口（42 §5），不是先验偏好。
> **不新增第十要素**（P9 属性化原则不变）：三样都落在已有九要素的子属性 + F5 的执行机制上。

## 2. 逐项评估

### 2.1 多租户

**现状**：`33:381` F5.3 只有一行——"数据+运行隔离；组合隔离不替代租户隔离"，验收判据"跨租户不可见/不可调"，P1。`26 §8.5`/`29:120` 明确把多租户列在 MVP 之外、按业务量阈值触发；`28:268` 列为 P1/P2 不做。

**已够的部分**：
- 方向对：租户是**部署单元级**隔离，不是类型级概念——不与九要素冲突；
- F5.7 组合隔离与 F5.3 租户隔离的关系已经写清（组合隔离不替代租户隔离）；
- F6.1 已有租户级并发上限。

**缺口（4 个，全部是"声明了但没定义单元"）**：

| # | 缺口 | 具体表现 | 后果 |
|---|---|---|---|
| N1 | **没定义"租户边界单元"的内容** | 只有"数据+运行"，没写租户边界由哪几件构成 | 实现时每人理解不同：有人只做查询过滤，有人做 schema 隔离 |
| N2 | **类型归属租户没有字段** | 类型可被哪个租户用、能否跨租户共享，无处声明 | 跨租户复用类型只能靠约定；42 的 T221 已暴露"组合跨租户声明只能写正文备注"（S08） |
| N3 | **实例的租户上下文不入 I 表** | I 表 12 字段里没有"租户 id" | 审计问"这次运行属于哪个租户"答不出来（只能从输入绑定反推） |
| N4 | **知识分区的租户维度没接** | 读集"驻留范围"是数据驻留（境内/境外/本地），不是租户分区 | 租户级知识隔离无处声明，只能落到"范围"里当子情形 |

**补强（F5.3 升格为"租户边界四件"）**：

租户边界 = **数据分区 + 运行上下文 + 配额 + 凭据** 四件，缺一件就不算隔离：

1. **数据分区**：知识条目、实例记录、审计日志、凭据池都带租户 id；跨分区读必须显式声明（F5.3 判"跨租户声明"存在与否）。
2. **运行上下文**：每次实例运行携带租户上下文（租户 id + 租户级配置版本），运行时的每一次读写都校验租户上下文与资源分区一致——不一致即拒绝并记审计（同 F5.5）。
3. **配额**：并发（接 F6.1）、预算、存储按租户计量；超限排队而非抢占（接 F6.5 反压）。
4. **凭据**：租户级凭据池，租户间凭据不共享；凭据注入时带租户 id（接 F5.4）。

**单机阶段的诚实边界**：当前架构是单机 SQLite 单写者、本地 Web 无鉴权（26 §8.5、29:120）。此阶段"租户"只能是**逻辑隔离**（同一进程内按租户 id 分区），不是物理隔离。写清这一点，避免把"逻辑隔离"当"安全隔离"卖——这是合规审计会直接问的问题。

**最小必要补充**：类型归属租户（N2）与实例租户上下文（N3）**不必等 P1**，可以随 v1.4 以 T 表/I 表各加一项的形式先落（低成本、高审计价值），租户边界四件整体仍 P1。

### 2.2 权限隔离

**现状**：机制最全的一块——F5.1 权限上界（P0，"类型上界→实例权限只收窄"）、F5.2 审批（P0，含分级授权与决策权联动）、F5.4 凭据（P1）、F5.7 组合隔离（P1）；类型层有权限模型三值、读集六项、写域三项、边界判定方式、决策权默认档+条件→档位；实例层越权入 F5.5 审计。

**已够的部分**：
- "只收窄"原则已成立（实例不能超类型上界）；
- 权限模型三值（并集/独占/签发等级）已能表达并发与授权关系；
- 越权已入审计、可回放。

**缺口（3 个，都属于"规则分散、没有单一公式"）**：

| # | 缺口 | 具体表现 | 后果 |
|---|---|---|---|
| P1 | **没有"有效权限"的合并公式** | 能力上界、读集、写域、工具白名单分散在四个要素里 | 实现时各自校验，边界处会漏（"能力允许调工具 A，但读集不含工具 A 所需的数据源"这种矛盾没人查） |
| P2 | **没有"越权检测"的可执行定义** | F5.5 说"越权入审计"，但没定义越权=什么比什么 | 审计只能看到"调用了什么"，无法回答"这个调用超出声明了吗" |
| P3 | **最小权限没有落点** | 边界有"必须审批/不可碰"，但没有"默认拒绝"的总体原则 | 权限只能靠枚举禁区，漏一个就放行 |

**补强（新增 F5.9 有效权限计算与越权检测）**：

**有效权限 = 能力上界 ∩ 读集 ∩ 写域 ∩ 工具白名单**（四个集合求交，不并）。这一条把四要素从"各自校验"收成"一次计算、一处校验"：

- 能力上界：类型声明的五维能力（含权限模型三值）；
- 读集：六项（范围含可见粒度/版本/时效/权威级别/驻留范围/准入）；
- 写域：三项（可写/只追加/禁止写）；
- 工具白名单：该类型允许调用的工具集合（F4 注册表 + 能力包）。

**越权检测三步**（每次动作前）：

1. **算**：按上式算本次动作的有效权限；
2. **比**：动作要求的资源、工具、读写模式是否在有效权限内；
3. **记**：不在则拒绝 + 写审计（越权类型、动作、请求方、缺的维度），并可 fail-closed 上报（接 F5.2 无审批者 fail-closed）。

**最小权限落点**：在八步创建法步 6（边界）加一句——**默认拒绝**：未在能力/读集/写域/工具白名单中显式允许的，一律拒绝；"禁止写"与"允许读"同等重要（对应 40-金融验证 S1 的"读集准入"缺口）。这不需要新要素，只需把"默认拒绝"写成 F1.5 的一条校验（C17）与 F5.9 的默认行为。

### 2.3 合规

**现状**：v1.3 刚补强过——F5.8 六判据（H1 人身安全/H2 法定对外义务/H3 许可证依赖/H4 监管报送/H5 记录留存义务/H6 第三方审计权）+ 判定规则 + 高合规三后果（强制新建/审批上调一档/成员变更加合规负责人）；类型层有记录三性+留存期限+依据留痕；34 R14 校验六判据全落值；F5.5 审计满足记录三性；F7.7 对外义务与回执。

**已够的部分**：
- 判据可操作（六项三值+理由），判定规则明确（H1/H2 直判，H3–H6 ≥3）；
- 后果已联动三处（派生/审批/组合成员变更）；
- 记录义务有落点（记录三性+留存期限）。

**缺口（2 个，都属于"判定与控件之间缺一张表"）**：

| # | 缺口 | 具体表现 | 后果 |
|---|---|---|---|
| C1 | **判据不驱动控件** | 判"命中 H3 许可证依赖"后，没有任何机制要求"必须有许可证编号字段" | 判出高合规，但该填的字段仍可空；合规判定变成"标签"，不产生义务 |
| C2 | **没有"合规义务清单"这个中间产物** | 六判据 → 三后果，中间没有"必须做哪些事"的清单 | 审计只能逐条问，无法"按清单验" |

**补强（新增 F5.10 合规判据→控件映射与义务清单）**：

判据 → 必填控件（每项至少一条，映射表进 34 附录）：

| 判据 | 必填控件（落在哪） | 校验点 |
|---|---|---|
| H1 人身安全 | 物理域环境三项（隔离物/许可票面/监护在场）非空；误判方向=保守（误拦>误放） | 缺失即类型不可保存（C18） |
| H2 法定对外义务 | 接口组·对外义务（对象/时限/格式/回执）+ 记录三性开启 | 义务项空置即高合规不可判定 |
| H3 许可证依赖 | 能力组·资质四件（证照/编号/有效期/责任主体）+ 许可证编号必填 | 资质缺件即阻断 |
| H4 监管报送 | 生命周期·硬时限（起算点+期限+逾期后果）+ 义务回执 | 硬时限缺失即阻断 |
| H5 记录留存义务 | 记录要求（三性+留存期限）非默认值 | 留存期限未填即阻断 |
| H6 第三方审计权 | 审计记录监管可直读 + 依据留痕开启 + 证据等级 | 直读开关关闭即阻断 |

**判定即生成清单**：F5.8 出判定结果时，同时生成"合规义务清单"（命中判据 × 必填控件 × 当前取值 × 是否满足），作为类型版本的附件冻结；任何一项未满足，高合规结论不得成立（C16 的加强版）。这样"高合规"从标签变成**可逐条验的义务**——外部审计来的时候，清单就是举证材料。

**不做**：不做合规认证、不出法律意见；六判据不设权重（避免算分式黑箱，33:390 已定）。义务清单只表达"命中判据对应哪些必填控件"，不判断"是否达到某个标准"。

## 5. 对 31 的影响（不动，说明理由）

| 问题 | 结论 |
|---|---|
| 要不要加"租户"到九要素？ | **不加**。租户是**归属/部署维度**，不是 Agent 的定义要素——加到类型里会让"同一类型在不同租户下变成不同类型"，破坏类型系统的复用。落 F1.1 的"归属"字段 + T 表第 25 行。 |
| 要不要加"权限"到能力？ | **已有**。权限模型三值是能力组的子属性；有效权限四交集是执行期计算，不是声明项——声明只有"上界"，运行时只能收窄（F5.1 原则不变）。 |
| 要不要加"合规"到接口？ | **已有**。记录三性+留存期限在接口组，六判据在 F5.8，义务清单是判定的产物。 |
| 会不会破坏 P9 属性化？ | 不破坏。三样补强全部落在"已有要素的子属性 + F5 执行机制 + T/I 表字段"，没有新增定义项。 |

**一句话**：31 v1.3 的九要素不动；43 的增量是 F5 域与 34 模板的补深，不是范式改动。

## 6. 优先级判断（自行拍板，只报结论）

| 项 | 优先级 | 理由 |
|---|---|---|
| F5.9 有效权限计算与越权检测 | **P0** | 安全底线：任何"agent 能调工具、能读写知识"的系统都躲不开；越权检测是审计的前提。且成本低（四集合求交 + 三步校验），不需要新基础设施 |
| F5.10 合规判据→控件映射与义务清单 | **P0** | 高合规三后果已是 P0，义务清单是它的落地；没有清单，"高合规"只是标签，审计时答不出"你凭什么说合规" |
| F5.3 租户边界四件 | **P1**（类型归属/实例上下文两小项 P0 随 v1.4 先落） | 单机单租户阶段不阻塞；但"租户 id 进 T/I 表"成本极低、审计价值高，先落不留债 |
| 多租户物理隔离（schema/进程/机器级） | **P2** | 依赖部署形态变化（多机/云），28:268、29:627 已列非目标；只在"出现第二台机器或第二个租户"时触发（26 §8.5 阈值） |

## 7. 业界对照（简短，只作定位，不作论据）

- **K8s / SaaS**：多租户是 namespace/部署单元级隔离，不是应用内类型概念——与本框架"租户是归属维度、不是九要素"一致；
- **主流 agent 框架（LangGraph / Letta 等）**：权限与租户都在"运行时/宿主"层，类型层只声明可访问范围——与本框架 C5/F5 的定位一致；
- **合规**：业界普遍是"控制框架（如 SOC2 控制项）× 证据清单"的方式，判定与证据分离——本框架的"六判据→义务清单"是同一结构的小型化。
- **诚实边界**：以上是公开文档层面的定位对照，不是本框架的验证依据；本框架的判据来自 122 型次验证（42 §3 的 U8/U25/U27/U28 等）与物理域/金融域的实测卡点。

## 8. 仍未解（与 42 §9 的 4 条不重复）

1. **租户与组合的交叉**：组合跨租户时，成员实例的租户上下文如何传递、移交契约里的"跨租户读声明"由谁签——当前只能落 F5.3 声明，运行时无可校验形态（42 的 S08 同源）。
2. **有效权限与"投影"的关系**：F3.7 遮蔽投影决定"能看见什么"，F5.9 决定"能做什么"；两者在"读但只读投影"的场合需要一次合并判定，当前设计里两处分别校验，未定义优先级（建议：投影先于权限，投影减少可见再算可做）。
3. **合规义务清单的变更管理**：判据命中变化（如新增许可证要求）时，已冻结的义务清单如何触发类型升版复核——接 F1.4 版本管理，但触发条件未写。
4. **默认拒绝的迁移代价**：v1.3 已有类型可能"未显式允许"却实际在用某项能力；默认拒绝上线需要对存量类型做一次"允许清单补录"，这是迁移工作，不是设计缺口。
