**v1.4 的四条变化**：

4. **行 20 六子项、H4 执行方口径与组合件租户归属落地**：交付物归档写全对外公开范围、留存期限、脱敏责任人、撤回方式、销毁或归档、读取审批六子项；H4 监管报送以"报送动作由本类型执行"为命中口径，执行方是必填控件；组合件租户归属由组合登记承载，成员继承。

## 0. 总述与 v1.4 核心变化

**总述**：智能体类型是设计产物，它用九个要素回答"这个 agent 是谁、为什么存在、能做什么、知道什么、怎么干、不能干什么、怎么交互、怎么活、和谁协作"。每个要素带子属性，把"答得出来"升级为"答得可判定"；关键子属性用复合取值结构，把"可判定"升级为"可表达真实需要"；类型定义只装永远不变的约束，本次的数据装进独立的实例运行记录。v1.4 在这条分界上补了两个实例侧字段，并把协作与租户两处容易混层的取值拆开。

**v1.4 的四条变化**（先看这四条就够）：

1. **运行事件流单独占 I 表一行（D19）**：拒绝、重放、接管、审批、失败、异常是一次运行内的事件，不是完成时的证据。I 表第 14 行只追加，允许运行中分次追加；第 8 行执行证据只管完成时证据集合。两者按事件 id 与证据 id 互指，事件流补上"被拒动作没有完成时证据"的时序缺口。
2. **义务清单引用单独占 I 表一行（D20）**：高合规类型的合规义务清单随类型版本冻结，I 表第 15 行只写 `obligation_list@版本`，版本须可解析且与类型版本冻结一致。清单本体不复制进 I 表，引用是外部制度与本次运行之间的绑定；高合规必填，非高合规可空。
3. **行 22 拆 22a 依赖与 22b 上交（D21）**：依赖是"缺了它任务干不了"的阻塞调用，失败按跳过、转人工、阻塞、降级为只读四值处理，可以指向外部持证主体；上交是"把事报上去"的上报式转交，不阻塞当前任务、不调用接收方，只通知接收方并移交产物。33 A8 禁止声明跨类型依赖，上交不受这条限制。
4. **行 25 拆 25a 类型级语义与 25b 部署取值（D22、D26）**：25a 写是否允许跨租户、依据三要素与审批角色，随类型版本冻结；25b 的租户 id、部署形态、具体接收方租户 id 与配置版本由部署配置生成，不写进类型定义。R17 只查 25a 三要素是否完整可解析，部署形态一致性由 R19 检查，R19 是 P1，依赖部署配置登记表 DP-1。

## 1. 原则：类型是设计产物，实例是运行产物

- **类型**：跨实例不变的 agent 定义；可评审、可版本化、可复用、可枚举。
- **实例**：类型的一次具体化；带输入、快照、私有草稿、租约、产出；可丢弃、可重建。
- **分界判据**：问"换个任务，它变不变？"不变的是类型，变的是实例。
- **推论**：设计一个 agent，本质是设计一个类型，而不是"写一段提示词"或"配一个工具集"。

**v1.1 的三条原则（保留）**：

- **P9 属性化而非扩张**：九要素是骨架，不够的地方用子属性补。新增顶层要素的代价是每份类型定义都要多填一栏、每个组件都要多承载一层，收益却只有局部；加属性的边际成本远低于加要素。唯一例外是"授权上下文"，它不是类型的本体属性，而是创建前置（见步 0）。
- **P10 可判定分级**：任何"边界可判定 / 验收可判定"的声明都必须标注判定方式与误判方向。写成"程序高可信"就必须有检测点；是近似判定就明说会漏放还是误拦、代价多大。假装严格比承认近似更危险。
- **P11 类型 ≠ 角色/流程节点**：一个类型承担一个角色；互斥角色（既评审又实现）、流程节点（人机双签）不能塞进一个类型，用组合（阶段状态机 + 多个类型 + 人）解决。可判据：有独立交付物 + 独立边界 + 可被单独委派 = 类型；只签署/排序/转发 = 流程节点。

**v1.2 的一条原则（保留）**：

- **P12 单值不足时用复合取值，不新增要素**：当一个子属性的取值结构装不下真实需要（验收双段、决策权分级、环境阶段化、档位实例覆盖），保留属性位置、扩展取值结构，用"主值 + 附加"（验收）、"默认档 + 条件档位"（决策权）、"序列"（环境）、"默认 + 覆盖"（档位）表达。扩展时必须写清"何时取主值、何时取附加/覆盖"，否则复合值不可校验。

**v1.3 新增的一条原则（保留）**：

- **P13 类型定义与实例运行记录分层**：类型定义（T 表）只装"永远不变、可被评审、可被复用"的约束；实例运行记录（I 表）装"本次的"数据，包括输入绑定、租约（holder+epoch+到期）、幂等键值、单次运行起止、上轮结果引用、执行证据、审批记录、产出引用、生命周期状态、运行事件流、义务清单引用。判据：把这一栏删掉，另一个实例是否完全不受影响？是，它是实例数据，不该进 T 表；否，它才可能进 T 表。
  - 为什么必须分层：第三轮发现 34 的 20 行模板要求类型定义写"幂等键"，但幂等键只有在实例运行时才有值；结果"写了也无处校验"，T205 只能靠文字约定阻断重跑。层次错配不能靠加属性解决，只能靠分层。
  - T 表与 I 表的衔接共六处：幂等要求 + 幂等键来源（T 声明，I 取值）、记录要求（T 声明，I 落盘）、依据留痕（T 声明，I 记录本次判断时点与依据版本）、租户归属 25a（T 声明，I13 落值）、高合规义务清单（类型版本附件，I15 引值）、多段时限的时钟源与各段到期时刻（T 行 19 声明，I 表第 6 项落值）。运行事件流只在 I 表，T 表不声明事件，事件类型由运行时按动作结果生成。第五处衔接是高合规义务清单引用，T 表侧是随类型版本冻结、按合规强度六判据逐条判定的清单附件，I 表侧是第 15 行 `obligation_list@版本`；运行事件流不构成第六处。第六处是多段时限的时钟源与各段到期时刻，把 T 行 19 与 I 表第 6 项连起来，34 v1.6 §4.4 已按六处定稿。

## 2. 一个智能体类型包含什么（九要素 + 子属性）

> 每个要素给：定义 / 设计时要回答的问题 / 子属性 / 判定标准 / 常见反例。
> 子属性不是必填全部：标"必填"的必须填；标"条件必填"的按条件填；标"可选"的允许留空但要在检查时说明理由。
> **v1.4 术语**（与 33 v1.5、34 v1.5 逐字一致）：九要素；读集六项（范围含可见粒度/版本/时效/权威级别/驻留范围/准入）；能力五维（影响面/可逆性/成本/作用域/环境，环境含三段）；环境三段（部署环境/可回放性/人身风险）；权限模型三值（并集/独占/签发等级）；幂等要求三值（必须/不需要/条件）；否决权四值（无/单方否决/双方否决/需一致）；移交契约五要素（交付物 id@版本/验收判据引用/拒收退回规则/责任方签字/跨阶段追溯 id）；记录三性（不可篡改/只追加/监管直读）；依据留痕（判断时点/依据版本）；合规强度六判据（人身安全/法定对外义务/许可证依赖/监管报送/记录留存义务/第三方审计权）；有效权限四交集（能力上界/读集/写域/工具白名单）；租户边界四件（数据分区/运行上下文/配额/凭据）；合规义务清单；运行事件流；义务清单引用；T 表 = 类型定义，I 表 = 实例运行记录（类型定义与实例运行记录分层，P13）。

### 2.1 身份（Identity）

- **定义**：这个 agent 是谁，包括角色名、人格、语气、立场。
- **要回答**：它以什么姿态工作？遇到冲突时站在哪边？它"像谁"？
- **子属性**：
  | 子属性 | 必填性 | 说明 |
  |---|---|---|
  | 角色名 | 必填 | 一个名词短语，如"后端代码审查者" |
  | 人格/语气 | 必填 | 3 句话内能约束行为 |
  | 立场 | 必填 | 冲突时倾向哪一方（保守/激进/中立；成本优先/质量优先） |
  | 价值取舍顺序 | 可选 | 多个目标冲突时的排序，如"正确性 > 交付速度 > 成本"。价值观并入身份，不单设要素（D1） |
- **判定**：能用 3 句话说清"它是谁"，且这三句话能约束行为，而不是形容词堆砌；立场能推出至少 2 个具体决策。
- **反例**："你是一个专业的助手"，没有约束力。

### 2.2 职责（Purpose）

- **定义**：它为什么存在，负责哪类任务、边界内交付什么、什么叫"做好了"。
- **要回答**：它只做什么？不做什么？成功标准是什么？它的结论在什么范围内成立？
- **子属性**：
  | 子属性 | 必填性 | 取值 | 说明 |
  |---|---|---|---|
  | 任务类 | 必填 | 一句话 | "一类任务 + 一种交付物"，窄到可枚举 |
  | 交付物 | 必填 | 名词 | 可验收的产物（补丁/报告/结论/清单） |
  | **验收口径** | 必填 | 一个结构 | 代理指标（交付时可测）/ 真实指标（最终目标，可空）/ 参数与给定方（阈值、权重、容忍度；由类型所有者还是实例委托人给） |
  | **决策权** | 必填 | 默认档 + 条件档位 | 三档：建议 / 共决 / 执行；允许"额度内执行、超限共决"这类分级表达 |
  | **适用域** | 条件必填 | 地区/期间/主体/交易结构/前置条件 | 结论只在某个范围内成立；写"全域"必须给理由。以职责处为准，接口处引用（D13/U21） |
- **判定**：职责能用"负责 X，交付 Y，以 Z（代理指标）验收，决策权=W（含条件），适用域=V"表述；Y 可验收；决策权与能力、边界一致，决策权=执行却无副作用能力是矛盾，决策权=建议却有写权限是越权。
- **反例**："负责后端开发"，太宽。决策权缺失的反例：红队类型不写"建议"，读者会以为它可以自主打穿系统。

### 2.3 能力（Capabilities）

- **定义**：它完成任务所需的工具、技能、资源，这是能力的上界，不是清单。
- **要回答**：最少需要哪些工具？这些工具能造成多大影响、能不能撤销、花多少钱、作用在哪个范围、在哪个环境执行？这个动作法定或合规上由谁做、agent 只能做到哪一步？同一时刻谁持有这个能力、谁能签发、谁能否决？
- **子属性**（每个工具/能力都要标：读写性质 + 能力五维 + 权限模型三值 + 责任主体）：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | 读写性质 | 只读 / 副作用 / 审批 | v1.1 原有 |
  | **影响面** | 无副作用 / 局部（单资源）/ 广泛（跨系统/对外） | 决定审批级别与隔离 |
  | **可逆性** | 可回滚 / 可补偿 / 不可逆 / **公开但可更正** | "不可逆 = 必须审批"是硬规则；"公开但可更正"（公开言论类）默认按不可逆处理（D14） |
  | **成本** | 低 / 中 / 高（或具体量级） | 决定配额、熔断、并发；度量单位仍未决（§7.3 遗留项） |
  | **作用域** | 实例内 / 项目内 / 全局 | 能作用到哪一层 |
  | **环境** | 环境三段：部署环境（只读样本/沙箱/预发/生产）+ 可回放性（可回放/部分可回放/不可回放）+ 人身风险（无/有） | v1.3 补"部分可回放"第三态；阶段化（沙箱、灰度、生产逐级）用序列表达；物理域展开三项见下 |
  | **权限模型**（v1.3 新增） | 并集 / 独占 / 签发等级 | 并集=多人同时有效（"任何人可急停"）；独占=同一时刻一个持有者（"唯一指挥"）；签发等级=分级签发，签发人须有对应等级 |
  | **责任主体与资质** | 主体（持证电工/注册结构工程师/总监等）+ 证照四件（类型/等级/有效期/责任险）+ agent 角色（**仅辅助不担责** / 可执行） | v1.3 补第三值"仅辅助不担责"；"谁签"与"谁担"是两件事 |
- **物理域"环境"三项展开（v1.3，条件必填）**：
  | 项 | 取值 | 说明 |
  |---|---|---|
  | 隔离物 | 编号 + 上锁状态（围挡/闭锁/接地） | 可声明，是否上锁要能校验（一级物证 vs 照片） |
  | 许可 | 票面五要素：票种 / 编号 / 有效期 / 签发人 / 作业范围 | 与边界·环境级的"许可"成对 |
  | 监护 | 在场确认方式：现场 / 远程 + 见证 + 签字 | 监护人"在场性"不能再只写在身份里 |
- **判定**：能力集能覆盖职责；说清"少了哪个就干不了"；每个能力五维填满（环境三段按需）；不可逆能力有对应审批路径；涉及法定资质的能力标出责任主体、证照与 agent 权限上限；权限模型的"独占/签发等级"与边界、协作一致。
- **执行期收窄**：声明层只给能力上界，运行时按有效权限四交集计算本次能做什么。有效权限 = 能力上界 ∩ 读集 ∩ 写域 ∩ 工具白名单，四个集合求交不求并，交集只会变窄；声明里给了某一项，不等于运行时有效。
- **反例**：把"所有工具"都给它，能力越界。只标"副作用"不标可逆性，无法决定审批强度。把"法定只能由持证电工做的动作"写成 agent 可执行，责任主体缺失。把"可辅助但不可担责"写成"可执行"，问责链断裂。

### 2.4 知识（Knowledge）

- **定义**：它需要读哪些共享知识、往哪里写回，这是读集与写域，不是知识本体。
- **要回答**：读哪些领域、项目、历史？读的是哪一版、会不会过期、多大权威、能存多久、能不能读、能读多细？写回哪一层、谁可读、哪些禁止写？
- **子属性**（每个读集项都要标，读集六项）：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | 范围（含**可见粒度**） | 领域/项目/历史/外部源；粒度：全量/脱敏/仅标志/仅分数 | 读什么、读多细（反欺诈名单只能看命中标志） |
  | **版本** | 固定版本号 / 最新 / 任务开始时快照 | 决定可复现性 |
  | **时效** | 永久 / 30 天 / 本任务周期 / 显式过期时间 | 过期后处理（重新取/标记失效） |
  | **权威级别** | 权威（以此为准）/ 参考（可被覆盖）/ 候选（未确认） | 权威项冲突时必须上报，不得自动裁决（24 Q3） |
  | **驻留范围** | 本实例 / 同类型实例 / 全局 | 读到的内容能存到哪、谁能再读 |
  | **准入** | 可读 / 需授权读 / 禁读 / 仅命中标志 | 知识来源的准入，不是动作禁区 |
- **写域子属性**：层级（任务/领域/全局）、驻留范围、是否禁止写（只读类型：写域=禁止写）。
- **判定**：读集/写域能对应到共享层具体范围；越界可判定；权威级别为"权威"的项与现有知识冲突时必须走争议路径（disputed，不自动裁决）；"禁读"项有检测点（在读取入口拦）。
- **反例**：把知识写进提示词，会过期、会膨胀。只写"读规则库"不写版本，改版后同一任务结果不可复现。把"不得读取未公开重大信息"写成动作禁区，语义错位，这是知识准入。

### 2.5 行为（Behavior）

- **定义**：它怎么想、怎么做，包括决策风格、规划方式、歧义处理、失败处理、停止条件。
- **要回答**：先规划还是边做边看？不确定时问还是猜？失败了重试还是上报？什么时候停？
- **子属性**（每组至少 1 条，写成"遇到 X 做 Y"）：
  | 组 | 示例 |
  |---|---|
  | 规划 | 先出计划再执行；计划变更需记录 |
  | 歧义 | 歧义影响验收时先问；不影响时按最保守假设并标记 |
  | 失败 | 失败先看日志/证据再重试（≤N 次）；连续失败上报 |
  | 停止 | 满足验收条件即停；不追超出职责的"更好" |
  | 越界 | 读到"禁读"或超出授权范围的数据时停止并上报（与读集·准入联动）；越界事项走上交 22b，写清接收方与移交产物 |
- **判定**：每条行为规则能对应一个可观察的动作或决策点。失败策略留在行为里，不单设要素（D2）。
- **反例**："要聪明地工作"，不可观察。

### 2.6 边界（Boundaries）

- **定义**：它不能做什么，包括禁区、必须经人的动作、不可越过的范围，这是上界。
- **要回答**：绝对禁区是什么？哪些动作必须审批？哪些数据不能碰？这条边界靠什么判、判错了会怎样、偏哪边、谁批阈值？
- **子属性**（每条边界都要标）：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | **判定方式** | 程序高可信 / 近似判定 / 人工 / 环境化 | 见下表 |
  | **粒度** | 动作级 / 环境级 | 动作级=禁某个动作；环境级=整体隔离。物理域的环境级展开为"隔离物（围挡/闭锁）+ 许可（工作票/作业许可）+ 监护（人）" |
  | **误判方向与代价** | 漏放（该拦未拦）/ 误拦（不该拦拦了）+ 代价 | 判定方式不是"程序高可信"时必填 |
  | **取向与阈值审批人** | 偏漏放 / 偏误拦；阈值调整由谁批准 | 代价不对称时（反欺诈偏误拦、风控偏漏放）必须写取向与审批人；v1.3 补"误拦的经济代价与补偿通道" |
  | 触发条件 | 动作 / 资源 / 数据范围 / 条件 | 与 v1 的"写成不+动作/资源/条件"一致 |
- **判定方式分级**：
  | 判定方式 | 定义 | 要求 | 典型场景 |
  |---|---|---|---|
  | 程序高可信 | 规则/检测能直接判，几乎不误判 | 写明检测点（在哪拦、拦什么） | 禁写生产库、禁发外部邮件 |
  | 近似判定 | 有检测但会误判 | 写误判方向 + 代价 + 缓解 | 语义不变检测、GMV 承诺、关键词密度 |
  | 人工 | 判定标准需人判断 | 写判定人 + 时效 | 法务结论、医疗建议 |
  | 环境化 | 动作空间开放，无法事前判 | 隔离/配额/审批/审计四件套至少三件 | 红队、开放探索、高危运维 |

**租户边界的两层判定（v1.4）**

租户归属属于边界的环境级，类型层与部署层分开写。类型层写 25a 类型级跨租户语义：是否允许跨租户取"是/否/仅特定场景"三值；允许时写依据三要素（数据流向、接收方角色、法域或合同依据）与审批角色（角色+审批档，不得与类型所有者同人）。这一层随类型版本冻结，R17 只查这一层三要素是否完整可解析。部署层写 25b 部署取值：本次租户 id、部署形态（单机/多租户）、具体接收方租户 id、租户配置版本；这一层由部署配置生成，不随类型版本冻结，部署形态一致性由 R19 检查。R19 是 P1，依赖部署配置登记表 DP-1。

"类型定义不装部署数据"是 P13 的直接推论。把租户 id、部署形态写进类型定义，同一类型版本就无法同时服务单机与多租户，每次部署变化都会逼类型升版。判据仍是"删掉它，另一个实例是否完全不受影响"：部署取值删掉后另一个部署不受影响，所以它不进 T 表。

租户边界四件是数据分区、运行上下文、配额、凭据，四件缺一不算隔离（43 §2.1）。单机阶段只有逻辑隔离，没有物理隔离，类型层只能声明"不允许跨租户"。执行期的有效权限四交集（能力上界、读集、写域、工具白名单）决定这次动作能做什么，租户上下文决定这次动作作用在哪个分区；两者都在运行时校验，声明层只给上界。

- **判定**：每条边界必须标一种判定方式；"程序高可信"是首选，但不得把近似判定写成程序高可信；环境化边界必须落四件套；能力中的"不可逆"动作必须出现在边界里（成对约束）；物理域的环境级边界必须写"判定不了时取什么二级证据"（照片/打卡），并声明交付时证据等级。涉及跨租户的类型，25a 三值与依据三要素齐全，25b 不写进类型；单机部署只能写"否"。
- **反例**：只写"注意安全"，必须具体到动作/资源/条件。"不推断受保护特征"写成程序高可信，实际是概率防护，必须标近似。

### 2.7 接口（Interface）

- **定义**：它接收什么形态的任务、产出什么形态的交付物、证据是什么、验收在什么时候做、有没有法定对外义务、记录要求是什么。
- **要回答**：输入是消息、工作项、事件还是文件？输出是文本、补丁、报告还是文件？验收证据是什么？交付时就能验，还是过一段时间才知道对错，还是两段都要？效果怎么归因到本类型？有没有必须按格式送达的外部接收方？这条记录要不要不可篡改、能不能监管直读？
- **子属性**：
  | 子属性 | 必填性 | 取值 | 说明 |
  |---|---|---|---|
  | 输入形态 | 必填 | 消息/工作项/事件/文件 | 与实例绑定方式对齐 |
  | 输出形态（含**成熟度**） | 必填 | 文本/补丁/数据集/报告/文件/动作；成熟度=事实/假设/建议/决定 | 下游可消费；读者能从类型层判断交付物是"可执行结论"还是"待验证假设" |
  | 证据（含**强度/置信度**） | 必填 | 证据清单 + 证据在哪 + 等级；强度=一级（可复现物证）/二级（影像/打卡）/三级（自述）+ 置信度 + 证据有效期 | 事实核查、物理域类必须有强度；v1.3 补证据有效期（气体检测单 30 分钟就过期） |
  | **验收类型** | 必填 | 主验收时点（交付时/效果后/过程型）+ 附加回访 | 双段验收用"主 + 附加"表达 |
  | **归因设计** | 条件必填 | 无对照-仅观察 / 基线期对比 / 同期对照 / 随机化 / 声明不可归因 | 效果后验收必填 |
  | 回访时点与判定人 | 条件必填 | 效果后/附加回访必填 | 什么时候看、谁看 |
  | **对外义务** | 条件必填 | 对象 / 时限 / 格式 / 回执要求 | 法定上报、监管报送、对外公告类必填；高合规类型另附合规义务清单（随类型版本冻结），本次运行在 I 表第 15 行引其 `obligation_list@版本` |
  | **记录要求**（v1.3 新增） | 条件必填 | 记录三性布尔：不可篡改 / 只追加 / 监管直读 + 留存期限 | 法定记录类必填；物理域强制全真；拒绝、重放、接管、审批、失败、异常等过程事件另进 I 表第 14 行运行事件流，不挤进本行的证据集合 |
  | **依据留痕**（v1.3 新增） | 条件必填 | 判断时点 + 依据版本（引用记忆条目 id@版本） | 问责类必填；"当时依据哪一版"无从查起就不可问责 |
  | **适用域** | 条件必填 | 引用职责处的适用域 | 不重复定义（D13） |
- **验收分型**：
  | 验收类型 | 定义 | 证据要求 | 典型场景 |
  |---|---|---|---|
  | 交付时 | 交付即可验 | 证据在交付物内（测试报告/对比表/引用） | 代码补丁、翻译、数据清洗 |
  | 效果后 | 交付后一段时间才能验 | 交付物 + 回访时点 + 判定人 + 判定指标 + 归因设计 | 营销文案、投放、招聘、培训 |
  | 过程型 | 结果不可完全验，验过程 | 结构完整 + 来源可追 + 预算未超 + 动作序 | 创意、探索、红队、开放调研、消防检测 |

**记录要求与运行事件流的分工（v1.4）**：记录要求声明本次运行要落哪些证据、三性与留存期限；运行事件流记录一次运行内发生的过程事件，只追加，允许运行中分次追加。被拒绝的动作不产生完成时证据，只能以事件形式留下时序，因此事件流是执行证据的前置层，执行证据是完成时的证据集合。两者按事件 id 与证据 id 互指，事件流不替代证据，证据也不承担时序。

- **判定**：验收类型必须选主值；效果后必须写时点、判定人、归因设计；过程型不得声称"结果可验"，且必须写动作序列是否要求对应条款；双段验收必须写清"主值是哪段、附加回访验什么、两段判定人是否相同"；有法定对外义务的必须写对象/时限/格式/回执；有记录要求的必须写三性与留存期限；高合规必须附合规义务清单并在 I 表第 15 行引用。
- **反例**：输入输出不定，无法匹配、无法验收。创意类硬写"点击率提升 20%"作为交付时验收，验不了。施工类只写"交付时验合规"、不写事故率效果后，漏了真实目标。法定记录只写"留档"不写不可篡改与监管直读，审计时对不上。被拒动作只写进执行证据，重放几次、何时被拒都答不出。

### 2.8 生命周期策略（Lifecycle Policy）

- **定义**：它怎么活，包括档位、状态怎么存、什么时候交接、什么时候退休。
- **要回答**：处理完就销毁？活一个任务周期？反复领任务？按周期重算？它必须记住的东西放在哪、活多久、谁能读？档位会不会随配置变？有没有硬性时限？重跑会不会重复副作用？
- **子属性**：
  | 子属性 | 必填性 | 取值 | 说明 |
  |---|---|---|---|
  | **档位** | 必填 | 一次性 / 短驻 / 长驻 / 周期批处理 + 默认档可实例覆盖 | 同一类型可随项目配置切换（单版本 vs release train）；覆盖时义务集联动（v1.3：覆盖为长驻则自动加交接/续期） |
  | 有效期 | 条件必填 | 发布窗口结束/截止日 | 有界长驻用它表达 |
  | **硬时限**（v1.3 改多段，v1.4 加第六件） | 条件必填 | 多段五件：起算点（谁的事件触发计时）+ 期限 + 逾期后果 + 是否可延 + 延批人；第六件为各段到期时刻与时钟源（段序号、到期时刻、起算事件序号、时钟源、与授时源的偏差） | 原来单值装不下"每轮时限 + 月结截止 + 监管报送截止"；起算点归属必须写（困人时限从上游接报起算）。第六件是类型层声明与实例层落值的分工面：类型层声明段数与每段时限，运行期在 I 表第 6 项落各段到期时刻；起算事件迟到按 34 R22 的迟到判定处理，到期时刻按实际起算事件时间顺延并在 I 表第 14 项追加异常事件；跨节点时钟不同源时该段标"不可判"，以该段时限为门禁的验收不得通过 |
  | **触发节奏** | 条件必填 | 基础节奏（每日/每周/事件驱动）+ 复合事件（且/或） | 周期批处理必填 |
  | **单次运行边界** | 条件必填 | 一次跑多少（时间/条数/范围） | 周期批处理必填；长驻也要写（v1.3：长驻无"单次运行"概念时，改写成"单次处理的上界"） |
  | **幂等要求三值**（v1.3 新增，T 表侧） | 条件必填 | 必须 / 不需要 / 条件（写条件）+ 幂等键来源（事件 id / 周期 id / 调用方传入） | 周期批处理强制"必须"；键值本身进 I 表，不进这里（P13） |
  | **状态外化** | 条件必填 | 两个对象：实例私有状态（位置/保留期/读权限）/ 交付物归档六子项（对外公开范围/留存期限/脱敏责任人/撤回方式/销毁或归档/读取审批） | 长驻、周期批处理必填；v1.4 把归档六子项写全，与实例私有状态三项分栏 |
  | **交接条件** | 条件必填 | 交给谁、交什么状态、上轮结果如何被下轮读到 | 长驻替代"停止条件"；v1.3 补上轮结果外化（否则交接等于重跑） |
  | 续期/退休 | 条件必填 | 续期审批人、退休时状态归档 | 长驻必填 |
  | **实例寿命**（v1.3 拆三项） | 必填 | 租约期限 / 单次运行边界 / 业务有效期，三项分开写 | 原来"实例寿命 vs 业务周期"两值混了三种语义（第三轮 S10） |

**状态外化的两个对象（v1.4）**

状态外化分两个对象。实例私有状态写位置、保留期、读权限，回答"这次运行的草稿存在哪、活多久、谁能读"。交付物归档写六子项：对外公开范围、留存期限、脱敏责任人、撤回方式、销毁或归档、读取审批，回答"交付物能不能公开、留多久、谁负责脱敏、怎么撤回、到期怎么处置、谁批准读取"。34 模板已在行 20 把两个对象分开，归档六子项与实例私有状态三项各占一栏，不再把归档位置塞进私有状态。

- **档位定义**：
  | 档位 | 定义 | 状态要求 | 典型场景 |
  |---|---|---|---|
  | 一次性 | 一任务一实例，完成即销毁 | 实例状态无需外化；交付物按归档要求 | 咨询、单次分析、翻译 |
  | 短驻 | 一个工作周期内复用（多轮/多任务） | 私有草稿可存于实例，跨实例需外化 | 修代码、评审、跟单 |
  | 长驻 | 跨周期持续存在（值班/监控/陪伴） | 必须状态外化 + 交接 + 续期 + 上轮结果外化 | 值班响应、舆情监控、日程助理 |
  | 周期批处理 | 按固定周期唤起、跑完即退 | 必须幂等要求=必须 + 幂等键来源 + 触发节奏 + 单次运行边界 + 上轮结果外化 | 每日库存重算、周报生成、定时巡检 |
- **判定**：档位有理由；长驻必须写状态外化/交接/续期；周期批处理必须写周期、触发节奏、幂等要求与来源、单次运行边界；有界长驻用"有效期"表达；有硬时限的写清起算点与逾期后果；三类时间（租约/单次/业务）分开写；交付物归档六子项逐项有值。
- **反例**：所有类型都默认长驻，资源浪费。长驻实例把"经验"留在内存，实例一回收就没了。周期批处理不写幂等，重跑重复下单。归档只写"保留 3 年"不写脱敏责任人与撤回方式，撤回时找不到人。

### 2.9 协作关系（Collaboration，可选）

- **定义**：它和谁一起工作，包括可委派给谁、向谁汇报、是否必须有人参与、明确不和谁协作、依赖哪些其他类型、把什么事上交、共决时谁能否决。
- **要回答**：哪些子任务可委派？向谁交付？谁可以委派？哪些动作必须人确认或人机双签？缺了哪个类型就干不了？越界和异常报给谁？共决时一方的否决算不算数？
- **子属性**：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | 可委派 | 类型 id 列表 | 把子任务交给谁 |
  | 被委派 | 类型 id 列表 | 谁可以把子任务交给它 |
  | 汇报 | 类型 id / 角色 | 结果交给谁 |
  | **人** | 需人确认 / 人机双签 / 人只被告知 | 关键动作的人介入方式 |
  | **禁止协作** | 类型 id / 角色 / **席位对** 或"无" | 明确不协作对象；组合内部必须按席位对声明（"实现席位 A 不得调用评审席位 B"，不只按类型） |
  | **依赖 22a**（v1.4 由行 22 拆出） | 类型 id@版本 + 方向 + 缺失时降级（跳过/转人工/阻塞/降级为只读）+ 是否阻塞启动 + 是否指向外部持证主体（是则写主体与证照有效期） | 缺了它任务无法完成；阻塞调用，失败按降级枚举处理；可指向外部持证主体 |
  | **上交 22b**（v1.4 新设） | 接收方（类型 id@版本 或外部角色）+ 移交产物 + 通知方式 + 回执 + "不阻塞、不调用"的声明 | 上报式转交：不阻塞当前任务、不调用接收方，只通知接收方并移交产物；用于越界、异常、超出决策权的事项 |
  | **否决权四值**（v1.3 新增） | 无 / 单方否决 / 双方否决 / 需一致 | 共决不是对称的；"一方能否决、另一方的否决无效"要表达得出 |

**依赖与上交的区别（v1.4）**

依赖与上交的区别有三处。依赖缺了任务干不了，调用是阻塞的，失败要按跳过、转人工、阻塞、降级为只读四值处理；上交不阻塞当前任务，不调用接收方，只通知并把产物移交给接收方，回执用于证明送达。依赖用于完成任务所必需的能力或主体，上交用于跨类型上报，典型场景是越界、异常和超出决策权的事项。依赖可指向外部持证主体，必须带证照与有效期；上交的接收方是类型或外部角色，不要求持证。

上交流程与移交契约五要素的衔接要写清。移交契约五要素（交付物 id@版本、验收判据引用、拒收退回规则、责任方签字、跨阶段追溯 id）用于组合内阶段交接，双方是同一组合的相邻阶段，交接要过验收。上交用于跨类型上报，接收方不在同一组合内，移交的是产物与责任，不要求五要素齐全，只要求接收方、移交产物、通知方式、回执四项可查。两者分工不同，不能互相替代。

- **判定**：协作关系显式声明；不声明 = 不协作（默认隔离）；"人"档必填；有强依赖的必须写依赖与缺失降级；组合件内部也要声明"禁止协作"（写者不得自评）；共决必须写否决权四值之一；外部持证主体作依赖时必须带证照与有效期（不能只写公司名）；越界上报必须写上交 22b 的接收方与移交产物。
- **反例**：隐式协作（"它知道该找谁"），不可治理。红队类型不写"人机双签"，风险不可控。共决双方都写"能否决"，实际执行时互相锁死。把越界上报写成依赖，接收方不回就卡死。

### 2.10 要素之间的约束

- **必须成对定义的**：
  | 成对 | 缺了会怎样 |
  |---|---|
  | 职责 与 接口 | 无法验收 |
  | 能力 与 边界 | 能力无约束（有写权限却没写边界 = 越权） |
  | 知识读集 与 写域 | 只读不写 / 只写不读 |
  | **验收类型 与 交付物形态 与 归因设计** | 效果后验收却只给"交付即验"的证据 = 没有验收 |
  | **状态外化 与 生命周期档位** | 长驻却无状态外化 = 状态随实例蒸发 |
  | **交付物归档 与 输出形态** | 一次性类型不写归档 = 交付物丢失 |
  | **能力不可逆 与 边界必须审批** | 不可逆动作无审批 = 高危裸奔 |
  | **能力环境段 与 边界环境级** | 物理生产环境却只写软件式审计 |
  | **读集准入 与 行为越界处理** | 写了"禁读"却没有越界停止规则 = 准入不可执行 |
  | **幂等要求 与 档位**（v1.3） | 周期批处理写"不需要幂等" = 重跑重复副作用 |
  | **记录要求 与 高合规/法定记录**（v1.3） | 法定记录未声明三性 = 审计对不上 |
  | **移交契约 与 组合件**（v1.3） | 有组合没契约 = 阶段之间"交什么"没人定义 |
  | **权限模型 与 决策权 与 否决权**（v1.3） | 独占能力 + 共决 + 无否决权 = 谁都能改谁都不能拦 |
  | **租户 25a 与 I13**（v1.4） | 声明允许跨租户却没有租户上下文 = 越权检测无从比对 |
  | **义务清单 与 高合规**（v1.4） | 判了高合规却没有 I15 引用 = 合规不可举证 |
  | **依赖/上交 与 行为·越界**（v1.4） | 写了越界上报却没有上交路径 = 上报无处落地 |
- **互斥/冲突的**：职责越宽，身份/行为越难具体；能力越多，边界越难判定；决策权=执行与影响面=广泛+不可逆同时出现时，必须有分级授权或人工双签。宁可窄，不要宽。
- **可选的**：协作关系（不声明即不协作）；适用域（无则写"全域"并给理由）；价值排序。
- **证据链约束**：任何"做好了"的声明都必须有证据位。交付时验收的证据在接口里，效果后验收的证据是回访指标 + 归因设计，过程型验收的证据是过程记录。没有证据位的验收标准等于没有标准。

## 3. 怎么创建一个智能体类型（创建流程）

### 3.1 什么时候需要新类型

先判断"能不能复用现有类型"：

1. 现有类型的职责能覆盖，复用（实例化，不建新类型）；
2. 职责相近、边界不同（判定方式/权限/合规要求，即"换维"），新建（不是派生）；
3. 职责相近、边界只是收紧、能力可扩但每个新能力带五维与新边界，派生（见 §4.2，需满足优先级判据）；
4. 需要互斥角色或多个能力组合，组合（多个类型 + 人 + 状态机，不建"万能类型"）；
5. 只出现一次，不建类型，用通用类型 + 一次性配置。

**判据**：新类型必须是"会反复实例化的稳定职责"；一次性的东西不配拥有类型；身份/职责/边界任一不同就新建；高合规域（金融/医疗/物理作业/涉及资质的领域）边界差异几乎必然换维，优先新建（D11）。高合规判定用合规强度六判据（D15）：人身安全 / 法定对外义务 / 许可证依赖 / 监管报送 / 记录留存义务 / 第三方审计权；命中前两项任一，或满足 ≥3 条，即高合规。监管报送（H4）的命中口径按 D23：报送动作由本类型执行才计命中，执行方是 H4 的必填控件，签发与执行分离，审批方签发不改变命中判定；外部持证主体执行报送时，引用外部回执，不计本类型命中。

### 3.2 创建流程："八步创建法 v1.4"

> 名称保留"八步"以免断链；实际动作 = 步 0 前提、1 职责、1.5 证据与验收形态、2 身份、3 能力、4 知识、5 行为、6 边界、7 接口、8 生命周期与协作，依次执行。其中 3 与 6 可迭代、1.5 与 7 可回退、生命周期与职责同步。

| 步 | 动作 | 产出（概念层） | 完成判据 |
|---|---|---|---|
| **0 确认前提** | 确认授权上下文（谁授权、范围、有效期）、预算、隔离环境、是否组合、是否有法定资质主体、是否高合规（合规强度六判据） | 前提清单 | 无授权不许创建；无预算上限不许写职责；资质主体不明不许写相关能力；高合规须标注 |
| **1 定职责** | 写"负责 X，交付 Y，以 Z 验收"，加决策权（含条件）、适用域、验收口径（代理/真实指标、参数给定方） | 一句话职责 + 决策权 + 适用域 + 验收口径 | Y 可验收、Z 可判定；决策权与能力/边界一致 |
| **1.5 定证据与验收形态** | 定主验收时点、附加回访、证据强度、证据有效期、归因设计 | 验收形态 + 证据清单 + 归因设计 | 证据能在对应时点获得；效果后有归因设计 |
| **2 定身份** | 写 3 句"它是谁" + 立场 + 价值取舍顺序 | 身份三句 | 能从身份推出至少 3 条具体行为 |
| **3 定能力** | 列最少必要能力，每项标读写性质 + 能力五维（环境三段）+ 权限模型三值 + 责任主体与资质（证照四件/agent 上限三值） | 能力上界清单 | 少一个就干不了；不可逆有审批；资质主体明确；独占/签发等级与边界一致 |
| **4 定知识** | 写读集（每项六项）+ 写域 | 读集/写域 | 能对应到共享层范围；越界可判；禁读有检测点 |
| **5 定行为** | 写"遇到 X 做 Y"：规划/歧义/失败/停止/越界；越界注明上交 22b 的接收方 | 行为规则集 | 每条可观察、可执行 |
| **6 定边界** | 写禁区 + 审批动作 + 不可碰数据；每条标判定方式 + 粒度 + 误判方向与代价 + 取向/阈值审批人；跨租户类型写 25a | 边界清单 | 每条有判定方式；不可逆动作有审批；物理域环境级展开隔离物/许可/监护；25a 三值与依据三要素齐全 |
| **7 定接口** | 写输入/输出形态（含成熟度）+ 证据（含强度/有效期）+ 主验收时点 + 附加回访 + 归因设计 + 对外义务 + 记录要求 + 依据留痕 + 适用域（引用）；高合规附合规义务清单 | 输入/输出契约 | 对齐职责验收；下游可消费；有法定对外义务的写了对象/时限/格式/回执；有记录要求的写了三性与留存；高合规有清单 |
| **8 定生命周期与协作** | 选档位（默认+可覆盖）+ 多段硬时限 + 触发节奏 + 单次运行边界 + 幂等要求三值/来源 + 状态外化（私有/归档两对象，归档六子项）+ 交接/续期 + 三类时间分离 + 协作（含"人"、"禁止协作"、依赖 22a、上交 22b、否决权四值） | 生命周期 + 协作 | 与职责匹配；长驻有状态外化与交接；周期批处理有幂等三件；依赖显式；上交有接收方与回执；共决有否决权 |

**五条流程调整（v1.2 的 H2 结论，v1.3 保留）**：

1. 步 0 不能省：三轮共 122 型里，边界案例全部需要；无授权不成立、无资源上限无法写职责；涉及法定资质的，步 0 必须确认资质主体。
2. 证据形态前置到 1.5 步：软目标类型必须先回答"怎么验"才能定"交付什么"。
3. 3 与 6 允许迭代：加能力立刻产生边界义务，回头补。迭代不是失败。
4. 1.5 与 7 允许回退：创意/效果后类型常出现"先定了证据形态，到接口时发现验不了，要回去改验收定义/归因设计"，允许回退，不视为返工。
5. 生命周期与职责同步：职责（连续性）决定档位；第 1 步定职责时就先定档位候选，第 8 步细化。

**v1.3 新增、v1.4 保留的一条流程动作**：步 8 之后做一次"T/I 分拣"，把刚写下的每个字段过一遍 P13 判据（"删掉它，另一个实例受不受影响？"）。该进 I 表的字段（幂等键值、租约、单次运行记录、上轮结果、执行证据、运行事件流、义务清单引用）从类型定义里移出；租户 25a 留在 T 表，25b 的部署取值移出类型定义。

### 3.3 创建后的动作

1. **注册**：进入类型注册表（可枚举、可发现）；
2. **版本化**：`typeId@version`；改类型 = 新版本，旧版本保留；
3. **评审**：按 §6 检查清单过一遍（设计者不能自签，需独立评审；D4）；
4. **试实例化**：用一个真实任务实例化一次，看"类型定义是否够用"。第二轮/第三轮的教训是：试实例化必须真的产生一次 I 表记录，记录里能看到第 14 行运行事件流与第 15 行的取值（非高合填写 `—`），否则幂等等运行时字段永远验不到；
5. **观察与迭代**：用实例的成功率/成本/质量反推类型是否需要调整（调整 = 新版本）。

### 3.4 反模式（创建类型时最容易犯的错）

| 反模式 | 表现 | 后果 | 替代 |
|---|---|---|---|
| **万能类型** | 一个类型什么都能干 | 边界失效、无法评测 | 拆窄类型 + 组合 |
| **类型即提示词** | 类型 = 一段 system prompt | 知识/能力/边界都没定义 | 九要素 + 子属性齐全 |
| **类型即工具集** | 类型 = 工具列表 | 身份/职责/边界缺失 | 工具是"能力"的一部分 |
| **知识塞进类型** | 把领域知识写进类型 | 知识过期、类型膨胀 | 知识放共享层，类型只声明读集 |
| **边界缺失** | 只写"要安全" | 权限无法判定 | 边界具体到动作/资源/条件 |
| **一次一类型** | 每任务建一个类型 | 类型爆炸 | 一次性用通用类型 + 配置 |
| **派生滥用** | 共享风格/输出结构就标"派生" | 语义漂移 | §4.2 优先级判据 |
| **假边界** | 开放动作空间写"可程序判定" | 评审误放行 | 标"环境化"+ 四件套 |
| **假验收** | 效果类硬写"点击率提升 20%" | 验收永不通过 | 效果后/过程型 + 归因设计 |
| **单值硬填** | 双段验收硬塞"交付时"、分级决策权硬写"执行" | 定义与真实不一致 | P12：用"主+附加""条件+档位" |
| **代理冒充真实** | 交付时验代理指标，却当成真实目标已验 | 效果不达标也判合格 | 验收口径拆代理/真实 |
| **责任主体缺失** | 法定资质动作写成 agent 可执行 | 责任无人承担 | 能力标责任主体与 agent 上限 |
| **类型定义装实例数据**（v1.3） | 类型定义里写"幂等键""本次租约" | 写了也无处校验，运行时可绕过 | P13：T 表只声明要求与来源，I 表装值 |
| **声明不校验**（v1.3） | 物理域只写"需隔离/监护"，不写编号、上锁状态、在场方式 | 交付时只有二级证据，事故后无法问责 | 环境三项展开 + 证据等级 |
| **共决无否决**（v1.3） | 双方共决都不写谁能否决 | 实际执行时互相锁死或一方单干 | 协作·否决权四值 |
| **事件挤进证据**（v1.4） | 拒绝、重放、接管都写进 I8 执行证据 | 时序与重放次数丢失，审计答不出 | I 表第 14 行运行事件流 |
| **依赖当上交**（v1.4） | 把越界上报写成阻塞依赖 | 接收方不回就卡死，越界无法上报 | 22a 与 22b 分开写 |
| **部署数据装类型**（v1.4） | 把租户 id、部署形态写进 T25 | 同一类型版本无法同时服务单机与多租户 | 25a 留类型，25b 交部署配置 |
| **高合规无清单**（v1.4） | 判了高合规，不附义务清单，I15 写"—" | 高合规不成立，审计无举证材料 | 附清单并在 I15 引用 |

## 4. 类型生命周期、派生与组合

### 4.1 类型自身的生命周期

| 阶段 | 动作 | 规则 |
|---|---|---|
| **设计** | 走 §3 流程 | 产出类型定义草案 |
| **注册** | 进类型注册表 | 类型 id 唯一、可枚举 |
| **版本化** | `typeId@version` | 不可变；改=新版本 |
| **使用** | 实例化 | 实例绑定创建时版本 |
| **弃用** | 标记弃用，停止新实例化 | 不删除；旧实例可继续 |
| **归档** | 类型定义 + 历史版本保留 | 可复现、可审计 |

### 4.2 派生规则（有优先级的判定顺序）

**先记住一条事实**：三轮共 122 型样本里，没有一条最终判定为"应当派生"（所有原以为的派生候选都改判新建）。派生规则更多是防误判闸门，不是创建类型的主路径（R45）。不要把"看起来像"当"应当派生"。

**判定按顺序执行，命中即停**：

1. **职责不共享（含职责换向）判为新建**。职责换向（评审代码改为评审架构、写稿改为检稿、诊断改为编排）属于新建，不属于派生。
2. **职责共享，但边界"换维"，判为新建**。"换维"指判定方式/权限/合规要求/资质主体不同（成人 vs 未成年人、内部 vs 外部、持牌 vs 非持牌）；这是不同型，应当走新建，不能按收紧处理。
3. **职责共享，边界同型且只收紧或放宽在允许范围内，判为派生**。派生时：
   - 能力可扩（用户拍板），但每个新能力必须带完整五维（含环境三段），新增不可逆/广泛影响能力必须同步新增审批边界，并说明"新能力为什么不能由父类型覆盖"；
   - 既有边界不得放宽，不得删禁区；
   - 派生链 ≤ 2 层。
4. **高合规域优先新建**：高合规（合规强度六判据命中）的类型，派生默认不可用。强合规域的边界差异几乎必然落在"权限/合规/判定方式"上，走派生会继承不该继承的边界。

**派生 vs 新建的升级判据表**：

| 关系 | 判据 | 结论 |
|---|---|---|
| 复用 | 身份/职责/边界/能力都覆盖 | 实例化，不建类型 |
| 派生 | 共享身份+职责，边界同型只收紧，能力可扩但每个新能力带五维+新边界声明，非高合规域 | 派生（≤2 层） |
| 新建 | 身份/职责/边界任一不同（含职责换向、边界换维、资质主体不同） | 新建 |
| 组合 | 需要互斥角色或多能力组合 | 多个类型 + 人 + 状态机（见 §4.3） |
| 依赖 | 缺了某个类型就干不了、但不是父子/包含关系 | 写进协作·依赖 22a（不建新类型） |
| 上交 | 越界、异常、超出决策权，需要报给另一个类型或角色 | 写进协作·上交 22b（不建新类型） |

### 4.3 组合优先与组合登记

互斥角色（既评审又实现）、流程节点（人机双签）、多能力协同（调研+写作+校对）一律用组合：

- **组合件** = 多个类型实例 + 人 + 阶段状态机（谁在什么阶段做什么、交接条件是什么）；
- 组合件本身不是类型（不进类型库、不参与实例化路由），但必须单独登记进类型注册表的"组合条目"类，不是类型条目。组合形态的四项（成员列表、状态机、依赖声明、移交契约）由组合登记条目承载，字段定义以 34 §4.8 的组合条目为准；成员类型只写所属组合的 id 与版本，不重复写四项内容。依赖声明落在字段 3，每条依赖成对写上游成员引用与下游成员引用，并挂降级枚举与是否阻塞；字段 3 的边集必须等于成员行 22a 指向本组合成员的边集；状态机的回退边不进依赖图，前驱指阶段序列里位置更早的阶段，回退目标必须在前驱集合内；依赖图按 34 R21 做环检测，检出环时拒绝登记并回写环路径。
- 成员行 22 的引用格式为"组合成员声明见组合条目 `<组合id>@<版本>`"，成员被多个组合复用时每个组合写一条；引用解析不到组合条目时按 34 的校验规则判为不通过。
- **组合内部也要"禁止协作"，且按席位对声明**：写者席位不得自评、审核实例不得与评分实例共享分数，组合不是"什么都共享"；
- **组合件租户归属（v1.4，D24）**：由组合登记承载，登记字段为"租户归属"：是否允许跨租户（是/否/仅特定场景）+ 依据三要素（数据流向、接收方角色、法域或合同依据）+ 审批角色（角色+审批档，不得与类型所有者同人）；具体租户 id 由部署配置给出，组合登记不写死。成员继承组合声明，成员的 25a 写"继承组合登记"，不再各自写一套；成员同时属于多个组合且租户声明不一致时，由组合所有者与类型所有者共同复核，复核不通过则阻断。
- **典型**：T075 双重身份 = 实现者实例 + 评审者实例 + 阶段状态机；T078 人机双签 = 签署类型 + 人 + 双签状态机。

**新增两行的性质（v1.4）**：

运行事件流是过程记录。它记录一次运行内发生什么、何时发生、凭什么判、怎么处置，只追加，允许运行中分次追加，回答被拒、重放、接管这类没有完成时证据的动作。执行证据是完成时证据集合，回答交付凭什么成立。两者按事件 id 与证据 id 互指，事件流不替代证据，证据也不承担时序。I 表第 9 行审批记录与第 12 行生命周期状态仍记结论，第 14 行记事件本身，事件条目用引用指向第 9 行或第 12 行，不重复正文。运行结束后的重放、接管与审批补充事件允许追加；追加时第 8 项封链证明生成新版本并引用前一版本，旧版本保留，记录整体仍满足只追加。I 表行 14 的追加以 D27 为准。

义务清单引用是外部制度绑定。清单本体在类型层，按合规强度六判据逐条列命中、不命中、不适用，附必填控件、义务条目与验收证据，随类型版本冻结；I 表第 15 行只存 `obligation_list@版本`，版本须可解析且与类型版本冻结一致。它回答这次运行依据哪一版义务清单。清单变更要触发类型升版，I 表不复制清单正文，非高合规可空。

**为什么必须分**：第三轮验证里，把 I 表内容写进 T 表的类型，全部出现"填了也无处校验"，幂等键写成"必须有"，模板里没有值，运行时也就没有去重依据。v1.4 再补两类：事件挤进执行证据会丢时序，义务清单只留在类型层会让审计无法把"这次运行"与"那版义务"对上。分层之后，类型层能表达"这类任务必须幂等、这类类型必须留证"，运行时能按来源生成键、按事件落时序、按清单查义务。

> **字段模板以 34 类型库模板为准**：T 表 25 行；I 表由 13 行增至 15 行，新增第 14 行运行事件流与第 15 行义务清单引用。T 表行号不变，行 20 在说明栏内拆归档六子项，行 22 拆 22a/22b，行 25 拆 25a/25b。功能树侧的分工与校验见 [33 v1.5](33-智能体框架-产品功能树-v1.5.md) §8.2.2 与 F1.5。

## 5. 示例：创建一个"后端代码 agent"类型（走八步 v1.4）

| 步 | 内容 |
|---|---|
| **0 前提** | 授权：项目仓库写权限（有效期=工作项周期）；预算：单任务 ≤ 200k token / 2 小时；环境：沙箱（代码）+ 预发（部署验证，需审批）；组合：否；法定资质：无；高合规：否（无监管报送/法定记录，合规强度六判据逐条为不命中） |
| **1 职责** | 负责"修复/实现后端代码变更"，交付"补丁 + 测试证据"；验收口径：代理指标=测试通过率/变更范围可控/无回归，真实指标=上线后 7 天错误率不升（效果后），参数=阈值由类型所有者给；决策权=默认执行，条件档位=合并主干需人确认（共决）；适用域=本仓库当前分支，不含架构级重构 |
| **1.5 证据与验收** | 主验收时点=交付时；附加回访=上线后 7 天错误率（判定人=值班工程师）；证据强度=一级；证据有效期=不适用（代码态可复现）；归因设计=无对照-仅观察（错误率受其他变更影响，声明不可强归因） |
| **2 身份** | 后端工程师；严谨，先复现后修改；不确定时先问；价值顺序：正确性 > 可维护 > 速度 |
| **3 能力** | 读代码（只读/影响面局部/全局作用域/环境=沙箱/权限模型=并集）；跑测试（局部/可回滚/低成本/沙箱/并集）；git 提交（局部/可回滚/中/项目内/沙箱+预发/独占：同一分支同一时刻一个实例）；部署（广泛/不可逆/高/生产/部署环境=生产、可回放=部分可回放、人身风险=无/需审批/权限模型=签发等级：合并需项目负责人等级）；责任主体=项目维护者，agent 角色=可执行但合并需人确认 |
| **4 知识** | 读：代码库记忆（快照/本任务周期/参考/项目内/可读/全量）、团队规范（最新/永久/权威/全局/可读/全量）、历史决策（最新/30 天/参考/项目内/可读/全量）；写：任务结论（任务层/项目内/可写）、可复用经验（领域层/全局/候选制，需评审） |
| **5 行为** | 先复现、定位、最小改动、测试、提交；歧义影响验收先问；失败先看日志再重试（≤2 次）；测试不全不停；读到越权数据停止并上交 22b（接收方=项目负责人，移交证据包，要回执） |
| **6 边界** | 不碰生产配置（程序高可信：预发隔离）；不碰敏感数据（程序高可信：白名单）；改公共接口需审批（程序高可信：CI 门禁）；不直接合并主干（程序高可信：合并权限）；不可逆部署需人工审批（环境化：预发先行，隔离/配额/审批/审计四件套）；取向=偏误拦，阈值审批人=项目负责人；25a=不允许跨租户（依据：数据流向仅本仓库、接收方=无、法域=本地） |
| **7 接口** | 输入：工作项；输出：补丁 + 测试报告 + 影响范围（成熟度=事实/建议混合）；证据：测试通过记录、diff、回归对比（强度=一级）；主验收时点=交付时 + 附加回访=7 天错误率；对外义务=无；记录要求=无（非法定记录）；依据留痕=判断时点+依据版本（引用代码快照）；适用域=引用职责；合规义务清单=不适用（非高合规） |
| **8 生命周期与协作** | 档位=短驻（可被实例配置覆盖为周期批处理）；幂等要求三值=条件（同一分支重复部署需检测），来源=调用方传入；硬时限=单段（24h 内无进展则上报）；状态外化：实例私有草稿存任务层/30 天/同类型可读；交付物归档六子项=对外公开范围：不公开、留存期限：仓库历史、脱敏责任人：无（不含敏感数据）、撤回方式：关闭 PR 并标记、销毁或归档：归档、读取审批：项目内可读；三类时间：租约=2h/单次运行=≤1 次部署/业务有效期=工作项周期；协作：可委派"测试编写"，向项目负责人汇报，人=改公共接口/合并时需确认，禁止协作=无，依赖 22a=无，上交 22b=安全事件与越界（接收方=项目负责人、移交证据包、通知方式=工作项评论并抄送、回执=需回执、不阻塞不调用），否决权四值=需一致（合并）；25a=不允许跨租户，25b=部署配置给出（租户 `local`、单机），不写进类型 |

**两次实例化**：任务 A"修复订单创建失败"、任务 B"给订单接口加幂等"，类型相同，输入/快照/产出不同；I 表不同、T 表相同。

**v1.4 的 I 表落值**：第 14 行运行事件流记一条拒绝事件（事件序号=1、事件时间=部署前、事件类型=拒绝、判定依据=边界·不可逆部署需审批、引用对象=审批记录 id、判定人角色=部署审批人）；第 15 行写 `—`（非高合规，不引用义务清单）。25a 的类型级语义与 25b 的部署取值分列，前者随类型版本冻结，后者由部署配置给出。

**与 v1.3 的差异**：v1.4 的示例补齐了运行事件流、义务清单引用、归档六子项、依赖与上交分离、25a 与 25b 分离；每一格都能回答"运行时靠什么校验"。

## 6. 创建检查清单（v1.4）

### 6.1 通用（所有类型，31 条）

**前提与职责**
- [ ] 步 0 前提是否齐（授权/预算/隔离环境/是否组合/法定资质主体/高合规判定）？
- [ ] 能一句话说清"负责什么、交付什么、怎么验收"？
- [ ] 职责窄到"一类任务 + 一种交付物"？
- [ ] **决策权**填了（含条件档位）？与能力、边界一致？
- [ ] **适用域**填了（或写"全域"+理由）？接口处是引用而非重写？租户 25a 写了类型级语义、25b 部署取值没写进类型？
- [ ] **验收口径**拆了代理指标/真实指标？参数给定方写了？

### 7.3 仍未决（4 条，不阻塞 v1.4）

1. **部署配置登记表 DP-1 未建**：25b 的租户 id、部署形态、具体接收方租户 id 与配置版本还没有登记载体，R19 只能停在 P1 人工核对，I13 的配置版本也无处解析。
2. **覆盖率算法版本与重放次数语义**：一次审计查询答不出"覆盖率按哪版算法算"与"这一轮被投递几次"；前者缺算法版本字段，后者缺重放计数、聚合口径与返回体形态。
3. **事件流保留期限与归档策略**：运行事件流只追加，保留多久、何时归档、归档后审计是否仍可直读都未定；定之前按对应记录要求的留存期限从长处理。
4. **跨租户审批人不得与所有者同人在小组织不可填**：小组织里类型所有者往往就是合规负责人，规则要求审批人与所有者不同人，实际只能外聘合规顾问或走 A3；外聘顾问的资质、责任边界与审批档映射还没有定义。
