# 本项目试验规则（v0）

本文件是本工作区正在试用的规则全集，先在工作区内生效，积累到足够证据后再向上提议进入 `E:\dsh_home\rules\` 与全局 `AGENTS.md`。工作区 `AGENTS.md` 只保留精简版与一条指向本文件的索引。

试验期从 2026-11-22 开始。每条规则带状态：观察中表示刚启用还没有反例或正例，已验证表示至少在一轮真实任务里产生了可对比的效果，稳定表示跨多轮反复成立、可以提议升级。状态与迭代记录在文末表里，改动规则先改本文件再改工作区 `AGENTS.md` 的精简版。

## 一、汇报可读性

1. 汇报先讲事件，再放细节。第一段回答四件事，这一轮在做什么、为什么要做、结果怎样、下一步是什么。中间段落按先发生什么、然后发生什么的顺序写，每个改动先说它解决什么问题，再说改了什么，最后说数字。

2. 代号第一次出现时用自然语言说一遍。规则编号、任务代号、文件编号、状态码在第一次出现的位置写出它是什么，后文再用编号。只在内部使用的代号不进汇报。

来源是 2026-11-22 的一次真实反馈，用户读完任务汇报后说可读性不强、不知道发生了什么。对照样例见 `harness-design/writing-example-2026-11-22.md`。状态：观察中。

## 二、子智能体编排

3. 同一份文件的连续修订归属一个子智能体。判据是同文件加同验收标准，换主题或上下文过门槛才新开。

4. 验收与修复合成一个循环。修复交回原实现子智能体，复核由同一个验收者做，连续两轮不过才换人。最终签字仍由独立子智能体完成。

5. 修订回补丁清单，不回整篇。五列是文件、行号、原文、新文、理由。整篇重写只在结构变更时做。

6. 派单内嵌五到十个关键片段与行号区间，并写明禁读清单。不写"参考之前的讨论"。

7. 压测按覆盖一次到位，同类样本一次二十到三十个，按能力维度分层，不逐个样本派单。

8. 极短任务走扇出。单问单答、批量核对、多文件同构替换写成一次脚本扇出，不逐个起子智能体。

9. 同一验证连续两次取不到证据就停，记未验证并报升级。单次验证超过十分钟拿不到证据同样落盘，不原地重试。

来源是 2026-11-21 到 11-22 这次会话的实测复盘，二十二点九小时里开出六十个子智能体，其中约一半由重复劳动产生。状态：观察中。

## 三、任务粒度

10. 派单单元是一个功能分类，不是单个功能点或单个文件改动。判断标准是一个子智能体能不能连续把它做完，能就不要再拆，拿不准时往粗里合一档。

这条与工作区 `AGENTS.md` 的"任务拆分与 Agent 派发"一节同口径，以那一节为准，本文件只留索引。

## 四、沉淀与迭代

11. 每轮结束在文末迭代记录里加一行，写清这轮用了哪条规则、效果如何、是否要改。不写进记录的经验不算沉淀。

12. 规则升级要三个条件同时满足，状态为稳定、跨三轮以上任务成立、在别的会话里复现过。三条齐了才把内容移到全局规则文件，移到全局后本文件只留索引与差异说明。

13. 规则改动只改本文件与工作区 `AGENTS.md` 的精简版。全局文件（`E:\dsh_home\rules\`、`E:\dsh_home\AGENTS.md`）在本项目试验期内不动。
