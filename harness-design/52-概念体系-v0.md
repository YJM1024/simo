# 概念体系与编号收口（v0）

本文档收敛 harness-design 目录里已经流通的概念与编号，建立一张唯一的索引表，处置已经确认的编号冲突。文档不修改任何既有文件，不写实现代码，不新增设计，只把已有概念归位、把冲突列清、把未解项留下。改动一处概念的成本主要落在引用上，索引表的作用是让每一处引用都能落到一个定义位置。本版把 26、29、45、46、49、50 与 51 里已定义但未登记的概念补入 §2，登记条数从 37 条增至 55 条，新增 EP 编号，§6 第 5 条改为已解并追加两条未解。

## §0 这份文档解决什么问题

本设计线从 26 到 51 已经积累了九套编号与数十个概念，这些概念分布在不同文档、由不同轮次验证产生，彼此之间只靠正文引用维持联系。随着 49 的回填裁决与 51 的分层把新概念引入目录，同一个词在不同文档里指不同物、同一件物在不同文档里叫不同名、被反复引用的概念找不到定义位置这三种情况同时出现。本文档把已有概念按层归位、给每个概念一个定义位置、把编号冲突列出并选定一种处置方式，输出物是一张总表、一张编号表和一份检查流程。判定一条概念能否收进本文档的标准是它能否在既有文档里找到定义位置，找不到的写入 §6，不在这里补定义。

三类失真在目录里都有真实例子，下表列出已经确认的六条，处置位置指向本文档的对应章节。这些例子不是孤立的笔误，它们来自不同轮次的验证与回填，每一轮只关心自己引入的概念，缺少一次跨轮次的收敛。本文档的第一件事就是把这类例子固定下来，作为后续检查的样本。

| 失真类型 | 真实例子 | 处置位置 |
|---|---|---|
| 同词不同义 | K1 至 K8 在 51 指元框架原语，在 39、41、42 指类型库验证卡点 | §4 改名并登记映射表 |
| 同词不同义 | P1 同时是设计原则与产品优先级，P0 至 P2 与 P1 至 P13 并存于 31 | §4 引用时加限定词 |
| 同义不同词 | 记录三性与记录要求三性，指同一组不可篡改、只追加、监管直读 | §2 统一为记录三性 |
| 同义不同词 | 依据三要素与 25a 三要素，指同一组数据流向、接收方与法域依据 | §2 归并到归属租户一行 |
| 概念悬空 | U 码在 31 与 34 被反复引用，U7 的定义只在 41 | §5 记为悬空，不补定义 |
| 概念悬空 | 组织轴在 51 承担分类作用但此前没有定义 | §1 补层并在 §2 登记 |

同词不同义最重的一例是 K 前缀。51 用 K1 至 K8 指元框架的八件原语，39、41、42 用 K1 至 K10 指类型库验证中暴露的卡点，两套含义都在目录内流通。31 与 33 的依据列写“K3 状态无外化位”，而 51 的分层写状态与存储由 K3 原语提供，读者在同一份目录里读到这两句时无法判断 K3 指哪一件物。同类问题还有 P 前缀，31 用 P0 至 P2 标产品优先级，同时用 P1 至 P13 标设计原则，P1 在两种用法里都出现。

同义不同词出现在术语的口语化改写上。T 表行 12 与 34 的 R10 一处写记录三性、一处写记录要求三性，指的是不可篡改、只追加、监管直读这三项。49 的 D22 把跨租户依据写成依据三要素，33 的 C20 与 34 的 R17 又把同一组取值写成 25a 三要素，读者要读完三处才能确认是同一组数据流向、接收方与法域依据。验收门与主验收时点、双段验收的混用也属于这一类，31 的 D6 与 34 的 R7 各自用了一套叫法。

概念悬空的典型是 U 码。34 的 R1 在依据列写 U7、U13、U21、U30，31 的 D 表也多次引用 U 码，而 U7 的正文只出现在 41，31 里没有任何一句定义 U7 指什么。组织轴在 51 的分层里承担分类作用，但此前没有文档说明它包含哪几种组织方式，本文档 §1 只能按任务书给出的四种组织方式登记。能力上限来源在 51 的分层里被引用多次，51 给出了能力上限来源表，本文档把它作为 CT2 的一条登记项收入 §2，表本身由 51 维护。

三类失真的处理方式不同。同词不同义要改其中一套编号或加限定词，同义不同词要择一并登记，概念悬空要补定义位置或明确标为未定义。本文档对每一类都给出可执行的检查动作与一份收口流程，检查动作放在 §5，编号处置放在 §4，概念定义放在 §2。历史引用按 §4 的规则保留原样，本文档给出的改名只作用于新写下的文字。

本文档的边界有三条。第一条是不修改既有文档，检查发现的问题只登记不代改；第二条是不新造概念与编号，表中出现的名称都能追到一个定义位置；第三条是不做实现，字段怎样落到代码由 34 的模板与校验规则负责。三条边界同时约束写法，凡是要补定义才能说清的地方一律写入 §6。

阅读顺序按问题走。要知道一条概念属于哪一层看 §1，要知道它的定义与稳定性看 §2，要知道它与谁相连看 §3，要知道某个编号能不能用看 §4，要检查目录有没有新的失真看 §5。五节之间用编号互相指，不重复定义，读到不认识的编号先回 §4 查前缀。

## §1 概念分层

概念层使用 CT0 至 CT3 四个编号，CT 是概念层号（Concept Tier），与 51 使用的架构层号 L0 至 L2 分开命名。CT0 原语层对应 51 的元框架内核，CT1 组织轴层对应 51 的 L1 框架层，CT2 规范层与 CT3 裁决层都落在 51 的 L1 框架层之内。51 的 L2 产品层概念不进入 CT 表，跨文档引用时见到 L 指架构层、见到 CT 指概念层。

概念分四层，分层依据是一件概念回答的问题属于哪一类问题。层次从下往上依次是原语、组织轴、规范与裁决，下层的机制被上层引用，上层的规则不反过来改写下层。分层的目的在于给每个概念一个唯一归属，使同一个词只在一个层里承担一个义项。四层占用的编号不同，CT0 只占 K，CT2 占 A、R、C 与表行号，CT3 占 P、J、D，CT1 不占编号。系统层的调度对象与运行记录也登记在 CT2，不另占编号。

CT0 原语层由八件原语构成，分别是单元与生命周期、能力与工具、沙盒与边界、状态与存储、调度与资源、观测与验收、租户与隔离、宿主与扩展接口。扩展点契约版本、命名空间与分区隔离分别是 K8、K4 与 K7 的属性，也登记在这一层，不另立原语。这一层回答的问题是任何框架都必须具备哪些不可再拆的机制，换掉其中一件之后元框架是否还成立。不出现在这一层的是具体类型的字段、验收参数、审批档与组织形态，这些内容属于 CT2 与 CT3。对内契约也归在这一层，它承诺的是原语与扩展点的行为，只在换宿主、移植与查上限时打开。

CT1 组织轴层由四种组织方式构成，分别是类型化框架、协作框架、编排框架与单体配置。这一层回答的问题是一套 harness 用哪种方式组织单元与单元之间的关系，换一种组织方式之后元框架是否仍然成立。类型化框架的内核是类型定义与校验、实例化与运行记录、创建准入、派生与组合、调度租约与验收语义五个部件，这五个部件在换成协作框架或编排框架之后不再成立，因此它们属于类型化框架的内核，不进入元框架内核。不出现在这一层的是字段级取值与校验条款，也不出现 P、J、D 这类裁决编号。对外契约归在这一层，它承诺类型注册、实例运行与产出验收三组接口。45 的七件核心机制与框架准入自检也归在这一层，前者是类型化框架内核的另一种切分，后者是框架接入元框架前的自检。

| 组织轴 | 组织对象 | 内核来源 | 定义状态 |
|---|---|---|---|
| 类型化框架 | 类型及其运行实例 | 五个内核部件，见 §2 类型化框架条 | 已定义 |
| 协作框架 | 两个以上类型之间的分工与交接 | 席位与共同目标，51 | 待定义 |
| 编排框架 | 流程节点与阶段顺序 | 阶段与回退边，51 | 待定义 |
| 单体配置 | 单个类型及其运行参数 | 无独立内核 | 待定义 |

CT2 规范层由九要素、T 表、I 表、A1 至 A8、R1 至 R20、C1 至 C20 与八步创建法构成。这一层回答的问题是一个类型或一个实例要满足哪些可检查的字段与条件，检查不通过时停在创建还是停在运行。不出现在这一层的是原语的实现方式与跨文档的裁量结论，这两类内容分别归 CT0 与 CT3。能力上限来源也登记在这一层，它以表格形式写清类型化框架的每项能力由哪件原语提供、上限在哪里，表本身是登记件，不引入新机制。系统层的调度对象与运行记录也登记在这一层，包括工作项、候选、预算、分片单写者与事件溯源。26 与 29 把这组对象放在系统层，架构上归元框架，概念层按三问归 CT2，因为它们的字段直接约束实例。

CT3 裁决层由 J1 至 J5、D1 至 D27 与 P1 至 P13 构成。这一层回答的问题是两条规则冲突时按什么顺序裁、为什么这样裁、裁完的结果落在哪一层。不出现在这一层的是字段取值与表结构，裁决一旦落到字段就移入 CT2 登记，D19 至 D27 的多数条目已经按这个方式落到 T 表与 I 表。J 与 D 的分工是 J 判边界与必要性，D 判具体取舍，P 是贯穿全线的原则，三者都不直接定义字段。

给一个概念定层时按三个问题顺序判断。第一个问题是换掉它之后元框架是否还成立，答案为否则归 CT0；第二个问题是它是否只在某一种组织方式下成立，答案为是则归 CT1；第三个问题是它是否以字段、条款或编号的形式约束类型与实例，答案为是则归 CT2，剩下承担裁量作用的归 CT3。三个问题都答不出来的概念记入 §6，不强行归层。

层与层之间的引用方向是单向的。CT2 的条款可以引用 CT0 的原语与 CT1 的内核部件，CT3 的裁决可以改写 CT2 的条款，反过来 CT2 不改写 CT3 的编号。一旦 CT2 的条款直接写某项能力由 K3 提供，说明封装漏到了规范层，要回到能力上限来源表登记。这条规则同时解释了为什么 34 与 33 的条款里出现了原语编号时需要通过能力上限来源表过渡，而不宜直接写进类型字段。

## §2 概念总表

概念总表按 §1 的分层收录 55 条概念，每条给出定义、回答的问题、归属层、首次定义文档与行号、稳定性。本版新增 18 条，来自 26、29、45、46、49、50 与 51，其中系统层 5 条、边界裁定 6 条、P0 实践 3 条、51 定稿 4 条。与既有条目同义的九组说法，包括运行实例、at-least-once 与幂等键来源、租约 fencing、组合登记与租户归属、验收门证据契约、义务清单冻结语义、运行事件流与封链、移交契约五要素与拒收退回、否决席位对，改为在既有条目的定义里补别名，不另占一行。稳定性的判法是换掉它之后元框架是否仍然成立，仍成立再看类型化框架是否仍然成立；换掉后元框架不成立的记稳定，元框架成立而类型化框架不成立的记可换，两者都成立的记易变。概念层号用 CT0 至 CT3，与 51 的架构层号 L0 至 L2 分开，对照见 §1 与 §6 第 4 条。

## §3 概念关系

概念之间有四类关系，分别是层级、依赖、替换与相对、持有。层级说明谁包含谁，依赖说明谁离开谁不成立，替换与相对说明同一件机制在不同层的身份差异，持有说明一条记录归谁。四类关系都只取 §2 已登记的概念，不引入新词。四类关系合起来回答一个问题，即改一处会牵动哪些概念。

层级关系由包含关系构成，共 8 条。判断一条包含关系是否成立，看被包含的一方能否独立于包含方存在。不能独立存在的归入包含关系，能独立存在的归入依赖关系。

1. 元框架包含八件原语，第八件是宿主与扩展接口。
2. 元框架包含类型化框架，类型化框架是元框架上的一种组织轴。
3. 类型化框架包含五个内核部件，即类型定义与校验、实例化与运行记录、创建准入、派生与组合、调度租约与验收语义。
4. 类型化框架包含对外契约，对外契约包含类型注册、实例运行与产出验收三组接口。
5. CT2 规范层包含九要素与 T、I 两表，A、R、C 三套条款是这些字段的检查规则。
6. CT3 裁决层包含 P、J、D 三套编号，D19 至 D27 是 49 回填产生的裁决。
7. 组合包含成员类型与阶段，成员按 id@版本 引用，阶段之间用移交契约连接。
8. CT1 组织轴层包含类型化框架与其余三种组织方式，组织轴是这四种方式的集合。

依赖关系说明一个概念离开另一个概念就不成立，共 8 条。判断依赖的方向看两点，改动上游是否必改下游，上游缺失时下游是否无法判定。两点都成立才写成依赖，只有一点成立的写成引用。

1. 类型化框架依赖元框架的五个扩展点实现类型定义与校验。
2. 创建准入依赖有效权限可算与合规强度判定，对应 C17 与 R14。
3. 运行事件流依赖封链证明的版本化，R20 的版本序列依赖 D27 的追加规则。
4. 验收门依赖证据强度、归因设计与代理真实分栏三项取值，缺一项则双段验收不成立。
5. 义务清单依赖合规强度六条判据的命中结果，判为高合规才生成清单。
6. 幂等键依赖调度原语提供的键生成与去重存储，T 表只写来源不写键值。
7. 能力上限来源表依赖八件原语的分工，每项能力对应一件主责原语。
8. 对外契约依赖类型注册、实例运行与产出验收三条链路，缺一条则契约不完整。

替换与相对说明同一件机制在不同层的身份不同，共 7 条。判断是否属于同一件机制，看两处的定义对象是否同一、换掉之后的后果是否落在不同层。同名的机制在两层分别记为内核与模式，不合并成一个概念。

1. 状态与存储在 CT0 是内核，换掉它实例无法运行；在 CT2 它是状态外化的两个对象，换掉只改字段。
2. 租约在 CT0 是调度原语的内核，在 CT2 是实例寿命三类时间中的一类。
3. 观测与验收在 CT0 是内核，在 CT2 表现为验收门、证据强度与归因设计三组字段。
4. 类型化框架在元框架视角是模式，在类型库视角是内核，这是相对内核的直接体现。
5. 租户与隔离在 CT0 是内核，在 CT2 表现为归属租户与类型级、部署级两段拆分。
6. 扩展点在 CT0 是内核接口，在类型化框架里是五个具体挂点，换组织轴后挂点集合可以不同。
7. 验收在 CT0 是观测与验收原语，在 CT2 拆成验收门与双段回访，在 CT1 表现为对外契约的产出验收接口。

持有关系说明一条记录归谁，共 8 条。判断持有看记录的所有者与生命周期，记录随持有方销毁时才记为持有。一处记录被两方引用时，只把写入方记为持有方。

1. 类型持有实例，一个类型版本可以对应多条 I 表记录。
2. 组合持有成员类型，组合条目按阶段引用成员类型 id@版本。
3. 实例持有租约，I 表第 4 项记录 holder、epoch、到期与续租次数。
4. 类型持有九要素，每个要素持有自己的取值结构。
5. 义务清单持有控件、义务条目与验收证据三件，缺一件则高合规不成立。
6. 封链证明持有版本序列，新版本持有前一版本的最后事件序号与哈希。
7. 组合持有阶段顺序与回退边，回退边必须显式枚举。
8. 类型持有创建准入记录，A1 至 A8 的判定结果随类型版本冻结。

契约关系单列两条，用来防止封装泄漏。对外契约只依赖类型化框架的领域内核，不直接引用元框架原语。对外契约里一旦出现某项能力由 K3 提供这样的写法，说明封装漏到了接口层，要回到能力上限来源表登记并改为对内契约的引用。对内契约只在换宿主、移植与查上限时打开，日常创建与校验不读它。

关系表随概念增删同步维护。新增一条概念时先看它在 §3 能挂到哪一类关系上，挂不上说明它与既有概念没有可判定的联系，登记价值也不高。删掉一条概念时把与它相连的条目一并删掉，不留下指向空名的引用。四类关系的条数不设上限，每类至少保留五条可用实例。

改动前按四类关系各走一遍，可以避免只改一处而留下断开的引用。层级关系给出影响范围，依赖关系给出阻塞顺序，替换与相对关系给出同一机制换层后的身份变化，持有关系给出一条记录散落在哪几张表。能力上限来源表是这四类关系的交汇点，它同时记录层级归属、依赖方向与上限取值。

本轮新增的 18 条按四类关系挂接。层级上工作项包含实例与候选，核心机制包含七件机制与两个边界接口。依赖上候选与晋升依赖分片单写者与幂等键，事件溯源与投影依赖运行事件流与封链证明。替换与相对上预算在 CT2 是工作项与实例的上限字段，在 CT0 是 K5 调度与资源的配额机制，命名空间在 CT0 是 K4 的隔离手段，在 CT2 是 T 表与 I 表占用的容器。持有上工作项持有租约、尝试与预算，框架准入自检持有声明文件。

| K | 元框架八件原语 K1 至 K8 | 51 | 只指原语，验证卡点一律改用 V 码 |
| EP | 扩展点契约版本，EP-1 至 EP-5 对应五个扩展点，后接 v 版本号 | 51 | 写 EP 号与契约版本；按声明版本调用，未登记版本拒绝，旧版本删除前仍接受；升版写迁移说明 |
| U 与 S | 验证卡点 U1 至 U31 与各验证文件的临时 S 码 | 41、42、39 | U 码写编号与文档号；S 码只在各自文件内有效，跨文件引用换成 U 码 |
| 对外契约 | 类型化框架的对外接口承诺 | 51、§2 对外契约条 | 不占编号，只登记在概念总表 |
| 对内契约 | 元框架对类型化框架的承诺 | 51、§2 对内契约条 | 不占编号，只登记在概念总表 |
| DP-1 | 部署配置登记表，待建件 | 33、34 的 R19 | 只登记部署形态与租户清单，不进 T 表 |

K 前缀有两个义项，39、41、42 用它标类型库验证卡点，51 用它标元框架原语。两种处置方式都能消掉歧义，代价不同。第一种把验证卡点改名为 V1 至 V10，第二种把原语改名为 M1 至 M8。本文档选第一种。

改验证卡点的代价落在三份验证文件的读法上。39、41、42 的正文不改写，引用时写 V 码并在括号里保留原码，检索 K 时需要按原语与卡点两个限定词分流。31 与 33 的依据列已经写了 K1 至 K10，这些位置按映射表追读，不重编。映射关系列在下表。

| 原 K 码 | 新 V 码 | 卡点名 |
|---|---|---|
| K1 | V1 | 验收时态单一 |
| K2 | V2 | 决策权无位 |
| K3 | V3 | 状态无外化位 |
| K4 | V4 | 生命周期档位不足 |
| K5 | V5 | 判定方式未分级 |
| K6 | V6 | 能力维度太粗 |
| K7 | V7 | 知识读集缺属性 |
| K8 | V8 | 适用域无位 |
| K9 | V9 | 派生判据过松 |
| K10 | V10 | 协作表达不完整 |

改原语的代价更大，51 已定稿，原语编号已经进入本文档的 §1、§2 与 §3，改名要同步改这三处的引用，还要重画 45 的七件核心与原语的对照。验证卡点只出现在三份验证文件与若干依据列里，改动面小，且卡点本身是历史诊断结论，不承担结构角色。原语集合固定为八件，编号与件数一一对应，改名会让 K1 至 K8 这种整体指代失去锚点，所以选改验证卡点。

引用规则共七条，从本文档起执行。七条规则同时约束新写的文字与旧文档的追读方式，旧文档不改写但按新规则追读。规则的例外情况写入 §6，不在正文开口子。

1. 跨文档引用同一规则必须同时写编号与文档号，只写编号视为不可定位。
2. 历史文档的编号不复用、不重编，改名以映射表登记，旧文不改写。
3. 新编号必须先在本表登记再使用，未登记的编号不进正文。
4. 编号不作句子成分，定位信息放在句末或表内单独一列。
5. 同一前缀只保留一个义项，K 冲突按本节处置，V 码不得再用于其他含义。
6. 契约不编号，只登记在概念总表，引用契约时写名称与 §2 的行号。
7. 扩展点契约版本写 EP 号与版本号，按声明版本调用，未登记版本拒绝，旧版本删除前仍接受，升级时写迁移说明。

编号表本身也要维护。新增一套编号时先在前缀列登记用途与出现位置，再在 §2 补定义格；一套编号停用时保留行并把状态改为停用，不复用前缀。每次升版核对前缀列与 §2 的行号，行号变动只改 §2，不改编号表。

两条契约不进编号表的前缀列，原因在于契约描述的是承诺，承诺只能整段引用，规则条目可以单独引用。契约改名不影响编号，契约内容变化要发新版本并在 §2 更新定义格。这条安排也避免了契约与 K 原语之间出现第三种编号。

## §5 三种失真的检查方法

三类失真各有可执行的检查动作，检查工具是文本检索与术语表反查，不依赖人工通读。检查在每次概念或编号变更后执行一遍，结果写进变更记录。三项检查可以并行，交集部分在收口流程第 4 步统一处置。

三项检查的执行时机有三处。概念或编号变更时做一次全量检索，版本升级时做一次交叉核对，51 定稿后做一次专项复核，本轮已完成。每次检查只记录命中行与判定结论，不在这里改文档，改动统一走这一节的五步流程。检查结果按版本存档，便于下一版对比。

| 失真类型 | 检查动作 | 判定标准 |
|---|---|---|
| 同词不同义 | 检索同一前缀的全部命中行，分定义、引用、举例三类 | 两处定义句式不同即记为冲突 |
| 同义不同词 | 从 §2 取概念名，检索常见改写与口语化说法 | 两处以上指同一物即记为一组 |
| 概念悬空 | 核对 §2 六列与首次定义文档和行号 | 只有引用没有定义即记为悬空 |

同词不同义用同一词在各文件的定义处比对。做法是对每个前缀与关键词在各文档里检索，列出命中行，再逐行判断该行是在定义、引用还是举例。同一个词在两处出现不同的定义句式，即记为冲突。已经确认的冲突有 K、P 与 S 三组，K 按 §4 处置，P 在引用时加限定词，S 只在本文件内使用。检查可以对全部前缀执行一遍，重点看 P0 至 P2、K1 至 K10 与 S1 至 S34。

同义不同词用术语表反查。做法是从 §2 取出每条概念名，在目录内检索它的常见改写，命中两处以上且指同一件物时记为一组。已经确认的有记录三性与记录要求三性、依据三要素与 25a 三要素、验收门与主验收时点三组。处置方式是择一并写进 §2 的定义格，其他写法在首次出现处标见 §2。反查要连表格一起检索，这三组混用都发生在表格单元格里。

概念悬空用定义位置核对。做法是逐条检查 §2 的六列是否填全，首次定义文档与行号是否存在，该文档里是否有一句能独立读懂的定义。只有引用没有定义的概念记为悬空，标为未定义并写入 §6。已经确认的悬空有 U 码与组织轴两项，其中 U 码在本文档里只登记不补定义，组织轴按任务书给出的四种登记。检查时要区分从未定义与定义只在别处两种情况，51 已定稿，其条目的行号已在本轮补齐。

收口流程分五步，每一步有明确的产出。五步的顺序按依赖排，前一步的产出是后一步的输入。流程可以在局部执行，但产出物要按五步的格式留档。

1. 抽词。从 26、29、31、33、34、39、41、42、45、46、49、50 与 51 抽出候选概念与编号，形成候选清单，产出是带出处的清单文件。
2. 定层。按 §1 给每个候选定层，定不了层的记入 §6，产出是带层号的清单。
3. 找定义。按 §2 六列填表，找不到首次定义位置的标悬空，产出是概念总表初稿。
4. 消歧。同词不同义改名或加限定词，同义不同词择一登记，产出是改名映射表与术语归并记录。
5. 回写索引。更新 §2 与 §4，未解项写入 §6，下一版复核，产出是本文档的新版本。

五步的顺序不能颠倒，因为定层依赖抽词的完整度，找定义依赖层号，消歧依赖定义位置。流程可以只做局部，例如只处理 K 冲突时走第 3 步到第 5 步。每次收口后要重跑三项检查，确认没有引入新的同形编号。

## §6 未解与已解对照

以下八条按影响面排序，其中六条在本版没有结论，第 4 条与第 5 条已解决。每条写明现状与卡点，不在这里给方案，也不替 51 预设结论。未解项与 §2 的悬空登记互相引用，读一条能追到另一条。

1. 概念稳定性如何随版本变化。§2 的稳定、可换、易变三档按当前分层判定，31 从 v1.3 升到 v1.4 时新增了 T、I 分层的判据，若下一版再拆层，已登记的稳定性需要重判，重判规则尚未定。
2. 编号跨文档引用是否需要全局唯一 id。现在靠前缀加文档号定位，51 定稿后架构层号 L0 至 L2 的引用会从个位数增加到十余处，前缀冲突已经出现一次，是否引入全局 id 与现有九套编号并存，尚未定。
3. 协作框架与类型化框架并用时的概念归属。一个协作件既可能按组合登记，也可能按编排描述，两种归属对应不同的字段与校验，判定规则未定。
4. 层号已分开命名，本条已解决。概念层号已改为 CT0 至 CT3，与 51 的架构层号分离，51 仍用 L0 元框架、L1 框架层、L2 产品层三层。跨文档引用时见到 L 指架构层、见到 CT 指概念层，不再需要靠文档号区分。
5. 51 定稿后的行号与术语复核，本条已解决。51 已定稿为 357 行，本轮按定稿行号登记了元框架、类型化框架、相对内核、扩展点、组织轴、对外契约、对内契约与能力上限来源八条，术语按 51 的表述统一。独立验收仍建议做一次，但行号与术语不再列为未解。
6. S 前缀的两个义项。33 用 S1 至 S3 标创建准入的结构前提，39、41、42 用 S 码标各批验证的临时卡点，两者同名不同义，本文档按“S 码只在各自文件内有效”处理，未给结构前提另设前缀。是否把结构前提改为 P 前缀或并入 A 表，需要一次跨文档确认。
7. 系统层对象与类型层记录的对应关系未定。26 与 29 的工作项、实例、候选、预算与 31、34 的 T 表、I 表是两套登记，工作项与 I 表记录、候选与组合条目之间怎样互指，一个工作项允许对应几条 I 表记录，本轮只登记概念，没有给出映射规则。
8. 45 的七件核心机制与 51 的八件原语不是一一对应。45 的七件是类型化框架视角的切分，51 的八件是元框架视角的切分，两者在类型系统、实例运行时与宿主接口上的归位不同；跨文档引用时按哪套计数，本轮没有定。

其余六条的共同点是都需要等 51 定稿或下一轮验证，不靠本文档的单方面约定就能解决。在结论出来之前，引用 CT0 概念时保留件名与文档号，不做进一步缩写。下一版收口时先核这六条，并确认第 4 条的层号用法已落到全部引用，再决定是否扩表。
