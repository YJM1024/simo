# 51 元框架分层 v0

本文是定稿候选，编号仍记 v0，与讨论稿的区别在于上一轮留下的四条未决项已经结清。四条各自写成裁定、论证、代价与被否决的做法，放在 §7，互相之间的依赖在每条末尾注明。仍未决的部分只剩运行证据与一个保留窗口，即混编演练、跨版本契约试装、容器复用试验、第五种组织轴试装、旧契约版本的保留时长，五项列在 §7.5。文档的边界与前几版一致，不改变任何既有文件，不新增第十要素。

本文回答用户提出的一个抽象如何实施：通用架构里运行、沙盒、工具、租户这些与具体 agent 形态无关的部分，应当抽成一个单独的框架，类型与实例的设计是在这个框架之上做具体化。本文把这个单独的框架命名为元框架（Meta-Framework），把类型与实例的具体化命名为类型化框架（Typed Framework），并把整个结构写成 L0 元框架、L1 框架层、L2 产品层三层；元框架由八件原语构成，框架层通过五个扩展点接入元框架。全文的术语按这一套使用，元框架指内核，类型化框架指内核之上的一种组织轴框架，二者不再混用别的叫法。

这个裁定与 45 的边界结论不冲突，45 用 J1 至 J5 把 13 个候选裁定成 7 件核心机制加 2 个边界接口，回答的是哪些机制该进框架；本文在同一个框架内部再分一层，回答进框架的机制放在元框架还是放在类型化框架。分完之后，45 的 7 件里有 1 件成为类型化框架独有的内核部件，5 件在元框架里是原语或其组合，1 件由元框架的原语加类型化框架的运行记录语义组成，2 个边界接口合并成元框架的第 8 件原语，这个算术在 §4 逐件展开。45 的判据没有被替换，本文只是在它下面补了一层归属判断。

本文的边界写在四处：不改变任何既有文件，不新增第十要素，不把元框架写成产品功能清单，不写实现代码。文中对 31、33、34 的引用只用于定位机制，不改变这些文件的内容；对 45 与 49 的裁定只做归位，不重新裁定。分层结论是否成立，最终要看一次新增组织轴能否在不改元框架的前提下接入，本文给出的是判据与待验证项。

## §0 问题与裁定

用户提出的抽象是：把通用架构里与具体 agent 形态无关的部分抽出来，成为一个单独的框架，运行、沙盒、工具、租户都在其中；类型与实例的设计放在这个框架之上，作为它的一种具体化。这个提法把此前混在一起的两类东西分开了，一类是所有 agent 都要用的机制，另一类是某一类 agent 才需要的组织规则。抽象要落地，必须先确定类型与实例整体位于这个单独框架的内部还是上方。落地之后还有四个实施问题要回答：多个框架共存时调度与验收归谁，扩展点契约怎么版本化，通用版本容器的边界在哪，新增一种框架怎么准入。

本文的裁定是：那个单独的框架叫元框架，它不含任何一种具体组织方式，只提供把智能体跑起来所必需的原语与扩展点；类型与实例的整体叫类型化框架，它是元框架上的一种应用，也是元框架的一种扩展。类型化框架把 agent 长什么样编码成类型，把这一次在做什么编码成实例，再用创建准入、派生、组合、调度租约与验收门把两者接起来。它不新增元框架的原语，只在五个扩展点上挂实现，然后增加一条类型组织轴。这个裁定在本文里写成三层、八件原语与五个扩展点三部分。

裁定类型化框架位于元框架之上，第一条依据来自元框架的启动前提。如果元框架在创建单元时要求先有类型定义与版本号，那么单体 agent 的一次会话、流程编排里的一个阶段、团队里的一个临时成员都无法启动，因为这些单元本来就没有跨实例重复使用的定义。要让它们运行起来，只能给每个单元临时造一个类型，类型于是从一种组织方式变成所有方式的必经步骤。31 的 P11 已经写明类型不等于角色与流程节点，组合件本身也不是类型；元框架若把类型设为入口，这三种单元会被挡在启动之前。

第二条依据来自实例的时间边界。类型是设计产物，实例是运行产物，这条分界写在 31 的第一节；实例带租约与单次运行起止，运行结束即可丢弃，而类型的定义、注册、版本、派生与校验发生在任何一次运行之前，并且要跨许多次运行存在。把类型化框架整体记作一个实例，等于把注册表、版本不可变、派生链与校验规则放进一次运行，运行结束它们随之消失，下一次运行无法重复使用，其他组织轴也无法引用。即使把实例做成长期存活，它仍然是一个运行体，不能被多个产品当作规则集选择与替换。

这两条依据合起来给出一条判据：一种框架若要被多种产品选择、并且在被选择之前就已经存在，它只能位于元框架之上，身份是元框架上的一种组织模式。L1 因此设四种并列的组织轴，类型化框架只是其中之一；另外三种是以团队为轴的协作框架、以流程为轴的编排框架与单体 agent 配置。四种组织轴使用同一套元框架原语，差别只在声明的细度与语义，这条性质是 §5 判据二的来源。

这里要区分框架与实例两个词。类型化框架是一套关于单元如何被定义、如何被跨运行重复使用、如何被执行的规则，它在任何一次运行之前就存在，可以被多个产品选择、替换与组合。实例在本文里专指运行中的 agent 实例，即 I 表 15 行描述的那一个运行体；用实例指称类型化框架，会让框架层的规则与一次运行的产物共用同一个词，也会把设计期的注册与版本误读成运行期状态。这个区分在 §1.2 用定义表固定下来，后文不再混用。

这个抽象的实际后果是把 45 的七件机制重新排一次位置。类型系统从元框架里移出，成为类型化框架独有的内核；共享状态、能力与工具、边界与治理、调度与资源、观测与验收五件在元框架里是原语或其组合，在类型化框架里获得类型语义；实例运行时由元框架的单元与生命周期原语加类型化框架的运行记录语义组成。31、33、34 随之从框架规范重新定位为类型化框架的规范，26 与 29 的系统层对应元框架。

这四个实施问题在 §7 各有裁定，结论分别落在调度与验收的归属、准入自检与容器边界上。调度与验收的执行点分别由 K5 与 K6 持有，框架只声明并发量级、租约形式与验收判据的内容，四种组织轴并存时按租户与类型分区隔离，不共享实例与租约，跨框架依赖走 22b 上交。新增组织轴要过准入自检，声明用到哪几件原语、实现哪一版扩展点契约、能力上限来自哪件原语、在 K4 占用哪个命名空间，缺一条不予准入。K4 只提供命名空间隔离、版本单调递增与只追加日志，不提供字段语义与校验，T 表与 I 表是类型化框架在 K4 里占用的命名空间，元框架的字段数因此不随组织轴的数量增长。

## §1 三层模型

三层按 L0 元框架、L1 框架层、L2 产品层记。L0 只提供机制，不提供语义；L1 放置以不同组织轴建立的框架，类型化框架是其中一种；L2 把框架组合成产品能力，包括界面、模板、行业包、计费与协作面板。三层之间的调用只有两条通道：L1 到 L0 走五个扩展点，L2 到 L1 走框架登记与查询接口，任何一条通道之外的调用都视为越层。

三层里 L2 不可省。用户的提法只有元框架与具体化两段，如果不设产品层，33 的 F1 至 F10 会被整段压进 L1，框架层就要承担界面、模板、市场这些产品内容，框架与产品的边界重新混在一起。L2 的职责只有一条：把框架选择、参数与交互组合成可交付的产品，不新增机制。这条职责也解释了为什么 A1 至 A8 的阶段值由 L2 给，而条件内容留在类型化框架。

| 层 | 职责 | 不含什么 | 对上层暴露什么 |
|---|---|---|---|
| L0 元框架 | 八件原语的机制与五个扩展点 | 类型、角色、阶段、职责、验收口径、组织形态 | 五个扩展点、执行结果、事件流 |
| L1 框架层 | 以不同组织轴建立的框架，类型化框架是其中一种 | 界面、模板、计费、市场、宿主形态 | 框架登记、声明与校验结果、框架事件 |
| L2 产品层 | 把框架组合成产品功能与交互 | 隔离、租约、存储、调度的执行 | 产品功能与交互，供最终用户使用 |

三层对照表里的“不含什么”一列是分层的可检验条件。任何一层出现右列的内容，就说明上一层的职责被下移，或者下一层的机制被上提；评审时先查这一列，比讨论分层是否清晰更容易得出结论。跨层接口只有表中“对上层暴露什么”一列列出的那些，新增接口要同时改两层，代价会在 §5 第一条里出现。

### 1.1 元框架

元框架是不含任何一种具体组织方式的内核，只提供把智能体跑起来所必需的原语与扩展点。它管一个单元从创建到回收的存续，管工具调用的注册、执行与收据，管文件、网络、进程的隔离与资源上限，管键值与对象存储、版本与只追加日志，管队列、配额与租约，管 trace、指标、事件与验收门的执行点，管租户分区与上下文注入，管宿主输入归一化与插件装载。它不知道这些机制被用来表达类型、角色、阶段还是职责，同一套机制被四种组织轴以不同语义使用。它自己不产生 agent，只产生能产生 agent 的框架，这句话是元框架与产品、与具体框架的分界。

元框架的边界由三条禁止构成：不反向依赖框架层的任何语义，不内置任何一种组织方式的字段，不允许框架层直接持有底层句柄。第三条最容易被忽略，因为存储句柄与隔离开关一旦交到框架层，租户分区与审计就可以被绕过，K6 与 K7 的保证随之失效。元框架只发能力句柄，能力句柄带上作用域、有效期与调用记录，框架层拿不到句柄背后的资源。这三条禁止同时是 §6 第三条反模式的判据，万能钩子之所以危险，就是因为它能绕开第三条。

元框架的八件原语按执行职责划分，每件都满足三条性质：四种组织轴共用，语义可由框架层注入，执行点唯一。八件之间没有一件是某种组织轴专属的，这条性质让元框架可以在不知道组织轴的情况下启动。八件原语之间的依赖只指向执行顺序，不指向语义，因此新增一种组织轴时不需要改原语的划分。

### 1.2 类型化框架

类型化框架是以类型与实例为组织轴的框架，也叫面向类型框架，它把 agent 长什么样编码成类型，把这一次在做什么编码成实例。类型侧由 T 表 25 行描述，实例侧由 I 表 15 行描述，两者之间用创建准入、派生、组合、调度租约与验收门接起来。它的内核由五个部件构成：类型定义与校验、实例化与运行记录、创建准入、派生与组合、调度租约与验收语义。这五个部件合起来回答三个问题：一个单元是什么，这一次它做什么，做完之后由谁验收。

| 概念 | 回答什么问题 | 包含什么 | 不含什么 |
|---|---|---|---|
| 元框架 | 把 agent 跑起来至少需要哪些机制 | K1 至 K8、五个扩展点、执行点 | 类型、角色、阶段、职责、验收口径、任何组织轴 |
| 类型化框架 | agent 长什么样，这一次在做什么，两者怎么接起来 | 类型系统五个部件、T 表 25 行、I 表 15 行、A1 至 A8、R1 至 R20 | 隔离、租约、分区、事件流的执行 |

两个概念的关系可以写成一条式子：类型化框架 = 元框架 + 类型组织轴的具体化。这条式子里的加号表示在元框架之上挂实现，不表示把元框架的原语复制一份；类型化框架仍然使用 K1 至 K8，只是给其中的取值与时机加上类型语义。具体化的动作落在五个扩展点上，声明式配置写 T 表与 I 表的 schema，校验器写 R1 至 R20 与 A1 至 A8，生命周期钩子写八步创建法，租户上下文注入写 25a 与组合登记，事件订阅写 I 表第 14 行。五个扩展点之外没有第六种接入方式，这一点在 §3 展开。

不用“实例”指称框架的具体化，原因是这个词在本文里有固定所指。实例专指运行中的 agent 实例，即 I 表的一行，带租约、带单次运行起止、运行结束即丢弃；类型化框架在任何一次运行之前就存在，并且要跨许多次运行被引用。两者共用“实例”一词，会让读者把注册表、版本不可变与派生链当成一次运行的状态，也会让 I 表的 15 行与框架层的规则混在同一层讨论。本文因此只用“框架”指类型化框架，只用“实例”指 I 表描述的运行体。

与类型化框架并列的还有三种组织轴。以团队为轴的协作框架把多个执行体按委派与合议规则组织起来，团队本身不注册为类型；以流程为轴的编排框架把阶段状态机与交接条件作为组织方式，阶段是单元，流程不是类型；单体 agent 配置把一份配置当作定义，一个执行体跑完一类任务。三种组织轴都不需要 T 表与 I 表，也都只使用八件原语中的一部分。

| 框架 | 一句定位 | 主要使用的原语 | 自己声明什么 |
|---|---|---|---|
| 类型化框架 | 设计期定义可重复使用的类型，运行期按版本实例化 | K1、K4、K6；K2 与 K3 由类型声明收窄 | 九要素、T 表 25 行、I 表 15 行、A1 至 A8、R1 至 R20 |
| 以团队为轴的协作框架 | 多个执行体按委派与合议规则协作，团队不注册为类型 | K1、K5、K6、K7 | 席位、委派规则、合议与否决、团队级归因 |
| 以流程为轴的编排框架 | 阶段状态机加交接条件，阶段是单元，流程不是类型 | K1、K5、K8；K4 存阶段状态 | 阶段、进入退出条件、回退边、移交契约五要素 |
| 单体 agent 配置 | 一个执行体带一份配置跑完一类任务，配置即定义 | K1、K2、K8 | 配置结构、能力清单、边界与验收口径 |

四种组织轴对八件原语的使用没有排他性。类型化框架把 K2 与 K3 的取值写进能力五维与边界清单，协作框架把 K5 的配额按席位分配，编排框架把 K1 的单元按阶段创建，单体配置只写一份配置。同一件原语在不同组织轴下声明不同，执行点仍然是同一个，这是“机制共用、语义分层”的具体含义。

以 K1 为例，四种组织轴绑定的声明各不相同：类型实例绑定 typeId@version，单体会话绑定配置哈希，团队成员绑定席位与委派关系，流程阶段绑定阶段 id 与进入条件。元框架只认单元 id、输入、租户上下文与租约，四类绑定都存在框架层的声明里。如果元框架为其中一类绑定加字段，另外三类就要为空值或伪值，这正是 §6 第二条反模式描述的膨胀路径。

### 1.3 相对内核与嵌套分层

相对内核的判据只有一句：把一件机制换掉之后，它所在的那个框架还成不成立。判据不问这件机制重不重要，只问它是不是那个框架的身份条件；换掉之后框架仍成立，它就是那个框架的外层模式，换掉之后框架不成立，它就是那个框架的内核。同一件机制可以在内层是内核、在外层是模式，这个性质叫相对内核。

用这条判据量类型系统，结果分成两半。把类型系统从元框架里换掉，元框架仍然成立，它还可以支撑协作框架、编排框架与单体配置，所以类型系统不是元框架的内核。把类型系统从类型化框架里换掉，类型化框架不再成立，因为 T 表、I 表、A1 至 A8、派生三规则与组合四件都以它为前提，所以它是类型化框架的内核。同一个类型系统，在元框架这一层是模式，在类型化框架这一层是内核，这就是相对内核的意思。

相对内核让分层变成嵌套的，本文只展开三层。第一层是元框架的内核，即 K1 至 K8 八件原语，不可替换性来自“换掉任何一件就不再是通用地基”；第二层是类型化框架的内核，即类型系统五个部件，不可替换性来自“换掉任何一个部件就不再是类型化框架”；第三层是产品层的固定选择，即产品选定的框架、配置与行业包，不可替换性来自“换掉之后不再是这个产品”。八件原语在类型化框架这一层不叫模式，叫宿主与基础设施，因为类型化框架把它们当作既定条件使用，不对它们再做组织轴层面的选择。

| 层 | 内核是什么 | 不可替换性的来源 |
|---|---|---|
| 元框架 | K1 至 K8 八件原语 | 换掉任何一件，它就不再是通用地基 |
| 类型化框架 | 类型系统五个部件 | 换掉任何一个部件，它就不再是类型化框架 |
| 产品 | 产品选定的框架、配置与行业包 | 换掉之后不再是这个产品 |

类型化框架因此有两层内核。宿主内核是 K1 至 K8，它在类型化框架里固化，不允许替换；领域内核是类型系统五个部件，它决定类型化框架与另外三种组织轴的区别。相对内核判据对两层同时适用，观察点不同：对宿主内核问换掉之后元框架是否还成立，对领域内核问换掉之后类型化框架是否还成立。把两层混为一谈，会让类型系统的改动被当成元框架版本变更，也会让宿主替换被当成类型化框架的破坏性变更。

### 1.4 外部视图与封装

从外部看，类型化框架是元框架上的一个应用，也是元框架的一种扩展。它不改变任何原语，只在五个扩展点上挂实现，然后增加一条类型组织轴；元框架的八件原语、执行点与不变量在类型化框架里原样保留。全文用“应用”与“扩展”描述这层关系，因为类型化框架不改变元框架的内部结构。这条措辞约束对应一条可检验的事实：类型化框架的每次新增都应当能在五个扩展点里找到对应位置。

封装的第一条承诺是对外只承诺类型化框架契约。类型注册、实例运行与产出验收是三个对外动作，调用方只需要知道这三个动作的输入、输出与失败语义，不需要知道元框架的租约、分区与事件流如何实现。元框架是对内契约，它约束类型化框架的实现，不约束类型化框架的调用方。这条承诺让类型化框架可以在元框架实现变化时保持对外稳定，也让调用方不必跟着元框架版本升级。

第二条承诺是元框架整体可替换。单机部署换成云托管，或者换一套宿主与扩展接口的实现，类型化框架的对外契约不变；替换的边界是 K1 至 K8 的整体，替换之后类型化框架仍然按原来的三个对外动作工作。这条承诺成立的前提是类型化框架没有直接持有元框架的底层句柄，也没有把某一件原语的私有字段写进对外契约。只要有一处直接依赖，整体替换就会退化成逐点适配。

第三条承诺是元框架只在三种场合打开：换宿主、移植、查能力上限。日常的类型注册、实例运行与验收不需要读元框架的文档，只有这三类工作才需要下探到 K1 至 K8。这条承诺减少了类型化框架使用者的学习面，也把元框架的变更影响限制在少数场合。打开的场合越少，元框架的版本节奏越容易与类型化框架解耦。

封装的代价是能力上限由元框架决定。类型化框架对外宣传的并发、租约、幂等、事件流与租户隔离，全部来自元框架的原语，元框架弱，类型化框架的上限就低，换一套更弱的宿主实现就会暴露这个上限。类型化框架不能在自己的层里补出这些能力，因为补出来的第二套判定会绕开元框架的执行点。为了让上限可见，类型化框架需要维护一张能力上限来源表，逐项写清能力由哪件原语提供、该原语的上限在哪里、上限被什么约束。

| 能力名 | 由哪件原语提供 | 该原语的上限 | 上限被什么约束 |
|---|---|---|---|
| 并发 | K5 调度与资源 | 单实例并发数、队列深度、租户配额 | 宿主 CPU 与内存、反压策略 |
| 租约与 fencing | K1 单元与生命周期、K5 | 租约时长精度、epoch 单调性、到期判定 | 时钟一致性、存储读写延迟 |
| 幂等键 | K1、K5 | 去重窗口长度、键空间大小 | 去重存储容量与保留期 |
| 事件流与封链 | K6 观测与验收、K4 | 追加吞吐、封链算法、版本保留数 | 存储吞吐、审计保留要求 |
| 租户隔离 | K7 租户与隔离 | 分区粒度、跨租户检查点密度 | 部署形态，单机或多租户 |
| 验收门 | K6 | 可挂载校验器数量、证据回放范围 | 校验器执行预算、证据可得性 |
| 状态外化 | K1、K4 | 快照频率、单对象大小、恢复点间隔 | 存储配额、恢复时限 |
| 扩展点版本化 | K8 宿主与扩展接口 | 同时支持的契约版本数、兼容窗口 | 契约版本策略，见 §7.2 |

这张表是类型化框架对外的能力说明，也是选型时的核对单。读者问这套框架能撑多少并发时，答案不在类型化框架的声明里，而在 K5 的配额与宿主资源里；问租约能精确到什么程度时，答案在 K1 的时钟与存储延迟里。表里任何一行写不出上限来源，就说明该能力目前只是宣传语，还没有实现依据。

合格与否按三件逐行核：能力名能在 §2 的八件原语里找到归属；上限列至少一个可测参数；约束列指向一个外部量。三件齐的行可以当核对单用，缺一件的行标为未实现，不能当能力宣传。数值本身要宿主压测才能填，结构合格不等于上限已知。

## §2 元框架的八件原语

八件原语按执行职责划分，每件都满足三条性质：四种组织轴共用，语义可由框架层注入，执行点唯一。下面每件给一个三栏表，分别写它提供什么机制、明确不预设什么、对框架层暴露什么扩展点，随后一段说明它与 31、33、34 的对应关系以及哪些部分留在元框架、哪些由类型化框架声明。八件之间没有一件是某种组织轴专属的，这条性质让元框架可以在不知道组织轴的情况下启动。

第 1 件原语是单元与生命周期。元框架在这一件上管单元的创建、启动、挂起、恢复、结束与回收，管单元 id 与七值状态机，管租约的 holder、epoch、到期与续租次数，管单次运行起止与幂等键的生成和去重窗口。它不预设单元代表什么，也不预设生命周期四档的语义，因此同一套状态机可以用于类型实例、单体会话、团队成员与流程阶段。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 单元创建、启动、挂起、恢复、结束、回收；单元 id 与状态机（运行中/成功/失败/超时/取消/已交接/已退休）；租约（holder+epoch+到期+续租次数）；单次运行起止；幂等键生成与去重窗口 | 单元代表什么；一次性、短驻、长驻、周期批处理四档的判别口径；状态外化的对象结构；交接与续期的业务规则 | 生命周期钩子（创建前、启动后、结束前、退休时）；声明式配置（档位、时限、幂等要求） |

它在 31 对应生命周期策略与 I 表的第 4、6、12 行，在 32 对应 C2 的实例化与生命周期，在 33 对应 F2 与 F6。留在元框架的是状态机、租约与幂等去重的执行位；由类型化框架声明的是四档的判别口径、状态外化的私有与归档两对象、交接与续期退休规则。49 的 D19 把运行事件流放进 I 表第 14 行，这一行由 K1 的事件通道追加，元框架不知道事件类型叫拒绝还是接管。

第 2 件原语是能力与工具。元框架管工具与能力的注册、查找、调用、超时、取消与结果收据，管未注册不可调用的拒绝，管调用前的准入检查点与执行环境的选择，管调用记录写入事件流。它不预设能力的五维取值，也不预设责任主体与审批档，这些都由类型化框架写在声明里，元框架只按声明执行。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 注册、查找、调用、超时、取消、结果收据；未注册不可调用；调用前准入检查点；执行环境选择（进程、容器、网络出口）；调用记录 | 能力五维的取值与判定；权限模型三值；责任主体、证照与 agent 角色上限；审批档与审批人；工具属于哪个类型 | 声明式配置（工具清单、作用域、超时）；校验器（调用前准入）；事件订阅（调用结果与收据） |

它在 31 对应能力五维与权限模型三值，在 33 对应 F4，在 34 对应 R3 与 C8。留在元框架的是注册、执行、收据与越界拒绝；由类型化框架声明的是五维取值、资质与审批动作。有效权限四交集的计算在类型化框架，执行点落在 K2 与 K3，两个原语共用同一个准入检查点，以免出现两套判定。

第 3 件原语是沙盒与边界。元框架管文件系统、网络与进程的隔离，管 CPU、内存与时长的上限，管权限判定的执行点，管判定不通过时的 fail-closed，管需要审批时的挂起与恢复，管审计写入。它不预设什么算越界，也不预设合规强度与审批人，边界的条数与判定方式由类型化框架声明，元框架只保证判定发生在一个不可绕过的位置上。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 文件系统、网络、进程隔离；CPU、内存、时长上限；权限判定执行点；不通过时 fail-closed；审批挂起与恢复；审计写入 | 什么算越界（读集、写域、工具白名单的内容）；边界条数与判定方式；合规强度六判据；审批角色与档位；哪些动作不可逆 | 校验器（准入与越界判定）；生命周期钩子（挂起等审批）；租户上下文注入（隔离域） |

它在 31 对应边界要素与有效权限四交集，在 33 对应 F5，在 34 对应 R2、R14、R17 与 R18，43 的租户边界四件也落在这一件与 K7 上。留在元框架的是隔离与 fail-closed 的执行点；由类型化框架声明的是四交集的具体集合、六判据、义务清单与审批档。执行点唯一这条性质在越权拦截上最不能让步，因为第二套判定一旦存在，绕过路径就随之出现。

第 4 件原语是状态与存储。元框架管键值与对象存储、命名空间、版本号、不可变快照、只追加日志、事务边界与快照读，管写入事件的发布。它不预设知识本体的结构，也不预设 T 表与 I 表的分表方式，存储只保证版本可追溯、快照可复现、日志只追加。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 键值与对象存储；命名空间；版本号；不可变快照；只追加日志；事务边界与快照读；写入事件发布 | 知识本体结构；读集六项与写域三项的语义；T 表与 I 表的分表；记忆合并与投影策略；保留期限 | 声明式配置（命名空间、schema、保留期）；校验器（写前 schema 与权限）；事件订阅（写入与版本变更） |

它在 31 对应知识要素、读集六项、写域三项与 P13 的分层，在 32 对应 C3，在 33 对应 F3，在 29 对应 M1 记忆读写闭环。留在元框架的是版本、快照与只追加；由类型化框架声明的是 T 表 25 行、I 表 15 行、读集与写域的语义、候选写回与冲突处理。26 的并发 harness 是这一件与 K1、K5 组合出来的一种实现形态，不是新的原语。

第 5 件原语是调度与资源。元框架管队列、并发上限、配额、优先级、租约发放、依赖就绪检查、反压与重试，并与 K1 的幂等去重协同。它不预设触发节奏与档位，也不预设团队席位与阶段顺序，这些语义由类型化框架声明，元框架只按声明分配与排队。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 队列；并发上限；配额；优先级；租约发放；依赖就绪检查；反压与重试；与 K1 的幂等去重协同 | 触发节奏与档位；任务优先级语义；团队角色分工；阶段顺序；预算归属 | 声明式配置（配额、优先级、并发上限）；生命周期钩子（就绪、抢占、降级）；事件订阅（排队、开始、抢占、失败） |

它在 31 对应触发节奏、硬时限与幂等要求三值，在 33 对应 F6，在 32 对应 C6，在 29 对应 M2 与 M3。留在元框架的是队列、租约与配额执行；由类型化框架声明的是档位语义、22a 依赖的阻塞与降级、团队席位的优先级。45 把调度与资源整件留在框架内，本分层维持这个判断，因为四种组织轴对租约与配额的需求在语义上一致。

第 6 件原语是观测与验收。元框架管 trace、指标、日志与事件流，管验收门的执行点与三级结果，管双段状态的容器，管归因字段与证据引用，管只追加日志上的封链与版本号。它不预设验收口径，也不预设证据强度与 A1 至 A8 的条件，门的执行点固定，门里判什么由类型化框架给。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| trace、指标、日志、事件流；验收门执行点与三级结果（通过、阻断、警告）；双段状态容器；归因字段；证据引用；封链与版本号 | 验收口径（代理指标、真实指标、阈值、给定方）；证据强度分级；A1 至 A8 的具体条件；双段验收的业务含义；误拦补偿规则 | 校验器（验收判定与门禁）；事件订阅（产出、证据、回访）；声明式配置（指标、保留期、采样） |

它在 31 对应验收口径、接口要素与证据要求，在 33 对应 F7，在 34 对应 R7、R8 与 R9，在 29 对应 M4 与 M6，46 的双段状态落在这一件上。留在元框架的是门执行点、事件流与归因字段；由类型化框架声明的是验收口径、证据强度、A1 至 A8 与误拦补偿。D27 的封链版本化也按这条线拆开：元框架给只追加日志与版本号，类型化框架给“新版本引用前一版本”的规则与 R20 的判定。

第 7 件原语是租户与隔离。元框架管租户 id 与配置版本、数据分区键、运行上下文注入、按租户的配额与凭据作用域、跨租户访问的检查点，以及隔离失败时的 fail-closed。它不预设是否允许跨租户，也不预设依据三要素与审批角色，租户语义由类型化框架声明，元框架只保证声明被执行。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 租户 id 与配置版本；数据分区键；运行上下文注入；按租户的配额与凭据作用域；跨租户访问检查点；隔离失败时 fail-closed | 是否允许跨租户（25a 的三值）；依据三要素；审批角色；组合件的租户归属；合规义务 | 租户上下文注入；校验器（跨租户判定）；声明式配置（租户清单与配置版本） |

它在 31 对应 25a 与 25b 以及 I 表第 13 行，在 33 对应 F5.3，在 34 对应 R17 与 R19，43 的租户边界四件与 49 的 D22、D24 都落在这一件上。留在元框架的是分区、注入与检查点；由类型化框架声明的是 25a 的三值、R17 与 R19 的分工、组合登记与成员继承。DP-1 部署配置登记表是产品层的登记件，元框架不建这张表，只在上下文里接收租户 id 与配置版本。

第 8 件原语是宿主与扩展接口。元框架管输入归一化、输出通道、人机交互原语、插件加载与版本约束、协议适配。它不预设宿主形态，也不预设交互流程与展示方式，K8 只保证外部输入被归一化成元框架能处理的任务、消息或事件，外部扩展被装载进受约束的位置。

| 提供什么机制 | 明确不预设什么 | 对框架层暴露什么扩展点 |
|---|---|---|
| 输入归一化（任务、消息、事件）；输出通道与渲染接口；人机交互原语（审批、接管、确认）；插件加载、版本约束与依赖检查；协议适配 | 宿主形态（CLI、Web、API）；交互流程与展示；场景包内容；市场与计费；启用哪种组织轴 | 声明式配置（插件清单、启用开关）；生命周期钩子（装载、卸载）；事件订阅（外部事件进入、产出送出） |

它在 31 对应接口要素，在 32 对应 C8 与 C9，在 33 对应 F8 与 F9，在 45 对应 B1 宿主接口与 B2 扩展接口。留在元框架的是装载、版本约束与审批接管原语；由类型化框架声明的是接口形态与成熟度；由产品层承接的是展示与市场。45 把宿主与扩展判为两个边界接口，本分层把它们合并成一件原语，因为两者的共同点是与外部交换，而不是与内部执行。

按调用关系，八件原语之间有四处直接依赖：K1 向 K5 要租约，K2 与 K3 共用准入检查点，K4 用 K7 的分区键，K6 订阅 K1 与 K5 的事件。四处依赖都指向执行顺序，不指向语义，所以元框架可以在不知道组织轴的情况下启动，组织轴可以在不知道其他组织轴的情况下接入。八件原语没有一件是某种组织轴专属的，这条性质是 §5 判据二的来源，也是 §0 第一条依据在元框架侧的具体形态。

## §3 类型化框架的落位

类型化框架是四种组织轴中被写得最细的一种，31、33、34 三份文档合计约三千三百行都在描述它。它在分层后的用法可以按设计期与运行期分开：设计期用 K4 存声明、用 K8 接评审与注册，运行期用 K1 起单元、用 K2 与 K3 执行、用 K6 验收、用 K7 分区。这种用法没有一处需要元框架认识“类型”这个词，全部经五个扩展点接入。

| 扩展点 | 元框架给什么 | 类型化框架声明什么 |
|---|---|---|
| 声明式配置 | 命名空间、schema 注册、版本、生效时点、回滚 | T 表 25 行的 schema；生命周期四档；能力清单；I 表 15 行的记录格式 |
| 校验器 | 注册、排序、三级结果（通过、阻断、警告）、执行记录 | R1 至 R20 与 C1 至 C20 的判定内容；A1 至 A8 的准入条件 |
| 生命周期钩子 | 创建前、启动后、结束前、退休时四个挂点，含上下文快照与失败语义 | 八步创建法的步骤编排；T/I 分拣；状态外化与交接 |
| 租户上下文注入 | 租户 id 与配置版本、分区键、凭据作用域 | 25a 的声明；R17 与 R19 的分工；组合登记的成员继承 |
| 事件订阅 | 事件类型、序号、只追加、封链版本 | I 表第 14 行的事件类型映射；验收门订阅产出事件；误拦补偿 |

五个扩展点覆盖声明、校验、时机、上下文与事件五类接入需求，类型化框架的全部差异都能归到这五类之一。如果某种组织轴需要第六类接入，按本文的判据应当先检查元框架是否缺一件原语，而不是先加一个钩子。这条判断是一个假设，四种组织轴里只有类型化框架被三份文档反复验证过，另外三种还没有试装记录，见 §7.5。

八步创建法属于类型化框架的人机流程，元框架只提供四个钩子。步 0 的授权上下文、步 1.5 的证据形态、步 6 的边界判定方式与步 8 的档位选择都是语义判断，元框架无法预置；如果元框架内置步骤顺序，单体配置与编排框架会被迫走同一套步骤，而它们本来没有类型定义这一步。钩子与步骤的对应关系是：创建前负责步 0 与 T/I 分拣，启动后负责 I 表第 6 行与第 14 行，结束前负责状态外化与交接，退休时负责第 12 行与归档。

T 表 25 行与 I 表 15 行是类型化框架的规范，不是元框架的数据结构。49 的 D19 与 D20 给 I 表加了第 14、15 行，34 同步加了 R20，元框架一行未改；如果这两行是元框架字段，加行就要发元框架版本，四种组织轴都要跟着升级，而实际上受影响的只有类型化框架这一种。元框架提供的是带版本的声明命名空间与只追加的运行记录，行号、字段名与必填性由类型化框架的 schema 决定，T 表存进 K4，I 表追加到 K4 与 K6 的事件流。

准入与校验同样属于类型化框架，元框架只提供校验器接口。A1 至 A8 是 P0 阶段的准入条件，P0 这个阶段值由产品层给，条件内容留在类型化框架；R1 至 R20 是类型化框架校验器的判定内容，其中 R19 与 R20 自带 P1 未验证标记，说明校验器可以携带自己的成熟度而不影响元框架。C1 至 C20 是产品侧的类型校验表，与 R 表同层，元框架给校验器的只有注册、排序、三级结果与执行记录。

| 类型化框架的构件 | 层属 | 元框架对应 | 是否改元框架 |
|---|---|---|---|
| 九要素 | 类型化框架 | K4 声明命名空间与 K8 评审接口 | 否 |
| T 表 25 行 | 类型化框架 | K4 版本化声明 | 否 |
| I 表 15 行 | 类型化框架 | K1 生命周期、K4 只追加、K6 事件流 | 否 |
| 八步创建法 | 类型化框架 | K1 的四个钩子 | 否 |
| A1 至 A8 | 类型化框架，阶段值由产品层给 | K6 校验器接口 | 否 |
| R1 至 R20 与 C1 至 C20 | 类型化框架 | K6 校验器接口 | 否 |
| 78 型类型库 | 类型化框架的数据资产 | K4 存储 | 否 |

这张表最右一列全部为“否”，它表达的是分层是否成立的可检验条件：只要新增一条类型化框架的规则需要改元框架，就说明这条规则的机制被放错了层。78 型类型库作为数据资产放在 K4，不进入元框架代码，也不改变原语的划分。这条条件可以直接用于评审未来的改动，比讨论分层是否清晰更容易核对。

## §4 与现有文档的关系

45 的七件核心机制在新分层下逐件归位。归位的结果可以用一个算术核对：七件减去成为类型化框架独有内核的类型系统，剩六件；边界与治理拆成 K3 沙盒与边界、K7 租户与隔离两件，变成七件；再由 B1 宿主接口与 B2 扩展接口合并成 K8，正好八件。这个算术把八件原语与 45 的裁定接上了：它们由 45 的裁定加一次移动与一次拆分得到，不需要另行划分。拆分的依据是 45 的判据在本分层下多了一层：J1 至 J5 判断要不要进框架，§5 的四条判据判断进元框架还是进类型化框架。

31 在新分层下是类型化框架的原则规范。九要素、P1 至 P13、八步创建法、D1 至 D27 全部留在类型化框架，元框架不引用其中任何一条；P13 的 T 表与 I 表分层是类型化框架的 schema 分层，元框架只提供版本化容器与只追加日志。把 31 读成框架规范会让人以为元框架要实现九要素，按新分层，元框架只需要能存下任意 schema 的声明。

33 在新分层下有双重位置，机制描述部分属于类型化框架，产品呈现部分属于 L2。F1 类型工厂落在类型化框架与 K4、K8，F2 实例运行落在 K1、K4、K5、K6，F3 知识中心落在 K4，F4 能力与工具落在 K2，F5 治理与安全落在 K3 与 K7，F6 调度与资源落在 K5，F7 观测与评测落在 K6，F8 扩展与生态与 F9 宿主与交互落在 K8，F10 协作与编排落在协作框架与编排框架上。C1 至 C20 与 A1 至 A8 是类型化框架的校验与准入内容，十域因此不再是元框架的功能清单。

32 是最接近本文的一份旧文档，它把类型系统 C1 与实例运行时 C2 并列为元框架组件。本分层把 C1 整体移出元框架，把 C2 拆成 K1 的机制与类型化框架的声明；C3 至 C7 分别对应 K4、K2、K3 与 K7、K5、K6，C8 与 C9 合并为 K8。这次移动的依据就是 §0 的两条：元框架不能以类型为入口，实例装不下设计期的注册与版本。

49 的 D19 至 D27 在新分层下仍然成立，而且提供了一条现成的证据。D19 与 D20 给 I 表加第 14、15 行，D26 拆 R17 与 R19，D27 给封链证明加版本，这些改动全部落在类型化框架，元框架的八件原语没有一件需要新增字段。如果按把类型焊进元框架的做法，这九条裁定每一条都会变成一次元框架版本变更，四种组织轴都要跟着适配。

## §5 判据与代价

45 的 J1 至 J5 回答要不要进框架，本分层需要第二层判断，回答进元框架还是进类型化框架。四条判据按顺序使用，前三条判机制属于哪一层，第四条判它在那一层是不是内核；任何一条判为外层，就不再往下判，四条都通过，机制才进元框架。判据用于给下一次新增机制一个可重复使用的判断顺序。

| 判据 | 问法 | 判为内核的条件 | 判为外层的条件 |
|---|---|---|---|
| 删词 | 把候选机制定义里的类型、角色、阶段、职责、验收口径删掉，句子是否还成立 | 仍能完整描述并执行 | 删掉后无法描述 |
| 共用 | 四种组织轴是否都需要同一语义 | 四种都需要且语义一致 | 只有一种需要，或各组织轴语义不同 |
| 执行点 | 是否必须在元框架唯一执行点拦截或记录 | 是，外层自建会留下绕过路径 | 否，外层可自建并按事件回传 |
| 相对内核 | 把候选机制换掉之后，所在框架是否仍成立 | 换掉后所在框架不成立 | 换掉后所在框架仍成立，只是失去一种组织轴 |

用前三条量四件有争议的机制，结果各不相同。租约三条全过，留在元框架；T 表 25 行在第一条就失败，因为它删掉“类型”就无法描述，整体归类型化框架；验收门在执行点这一条通过、在删词这一条不通过，于是拆成元框架的门执行点与类型化框架的验收口径；审计三条全过，留在元框架并从 K6 的事件流读取。四种结果覆盖了整体留、整体移、拆开三种处置，说明三条判据能区分不同情况。

第四条判据补的是框架身份这一维。把类型系统从元框架里换掉，元框架仍能支撑协作框架、编排框架与单体配置，所以它不是元框架的内核；把类型系统从类型化框架里换掉，T 表、I 表、A1 至 A8、派生三规则与组合四件失去前提，类型化框架不再成立，所以它是类型化框架的内核。把 K1 换掉，元框架立刻不成立，因为单元存续没有替身，所以 K1 是元框架的内核；在类型化框架这一层，K1 属于宿主内核，同样的判据换一个观察点得到同样的结论。

代价一在扩展点契约的稳定性。五个扩展点被四种组织轴与产品层共同依赖，签名、调用时机与失败语义一旦发布，任何破坏性变更都要四种组织轴同步适配，并重跑 78 型的回归；元框架版本节奏因此受最保守的使用方限制。缓解办法是每个扩展点各自带版本号，兼容变更递增小版本，不兼容变更新开大版本并保留旧版本，规则见 §7.2。

代价二在框架层绕过元框架的风险。框架层若直接持有存储句柄、隔离开关或调度队列，就能绕开租户分区与审计；防线是元框架只发能力句柄、不发底层句柄，并用事件流对账。代价是每次读写多一层转换，性能与实现复杂度都上升，转换层的缺陷还会同时影响四种组织轴。

代价三在不同组织轴混用时的语义冲突。同一单元同时被两种组织轴声明时，生命周期归属、验收归属与租户归属会冲突；裁决顺序写死为元框架不变量优先、其次创建者、再次框架登记的优先级，三者都判不了时按组合登记的成员继承处理，仍判不了则阻断启动。框架登记因此是一个新的人工维护面，维护不当会让冲突从两层之间转到登记处内部。按 §7.1 的分区隔离，一个实例只归一个框架，生命周期与验收归属的冲突因此减少。剩下的是跨框架依赖的登记，它在 22b 上交时由创建者与框架登记两级判定，判定顺序沿用同一条链。

代价四在文档迁移。45 的七件要重新归位，31、33、34 的定位从框架规范改为类型化框架的规范，读者要同时持有两套编号；78 型的回填表不因分层失效，但 R17 与 R19 的层属要补一行说明。这条代价是一次性的，迁移完成后消失；代价一至三是长期的，决定架构能不能维持，代价五随组织轴数量增长。

代价五在新增两份登记面。准入自检要求每个框架维护一份声明文件，写明用到的原语清单、扩展点契约版本、能力上限来源与 K4 命名空间，框架每升一版就要同步一次。容器边界要求框架层自己维护命名空间里的 schema 与解析规则，跨框架复用同一份配置时要额外写一层换算。两份登记的维护量随组织轴数量线性增长，登记写错的后果是准入被拒或命名空间冲突，两者都能在准入时发现。

| 做法 | 否决理由 | 反证 |
|---|---|---|
| 把类型焊进元框架 | 元框架以 typeId@version 为创建入口 | 单体会话与流程阶段没有类型，只能造假类型；49 的 D19 与 D20 加两行 I 表就会变成元框架版本变更 |
| 把类型与实例整体降为一个实例 | 设计期能力被放进一次运行 | 注册表、版本不可变与派生链要跨运行存在；其他组织轴无法引用这套规则 |
| 照搬 DSH preset 的 bundle 机制当架构 | 把装载单位当成组织轴 | preset 解决装什么，不解决单元如何定义与组合；没有 T/I 分层、租户语义与验收门 |

三种做法的共同点是把一种组织轴的位置放错：第一种把它放进元框架，第二种把它压进运行体，第三种把它换成一个产品装载单位。三种做法都能让类型化框架运行起来，代价是另外三种组织轴运行不上，或者元框架与产品被绑死。四条判据可以逐条否掉它们：类型不是四种组织轴共用的语义，实例装不下设计期规则，preset 不是单元的定义方式。

## §6 反模式

反模式按出现频率排列，每条给识别方法与后果，替代做法沿用前面各节的结论。四条都曾在 45 与 49 的评审里出现过雏形，写下来是为了下一次评审时能直接对照。每条都配一个可以当场核对的问题，避免靠印象判断。

1. 把产品能力当原语。模板市场、行业包、协作面板、计费这些能力一旦写进 L0，元框架就随产品需求膨胀；识别方法是检查删掉它之后四种组织轴是否都无法运行，答案为否就留在 L2。45 的 J5 已经给出同一条判断，本分层只是把它从框内框外延伸到元框架与产品。

这条反模式的代价是元框架与产品发布节奏绑死。产品功能每加一次，元框架就要发一次版本，四种组织轴都要跟着适配，而它们本来与这个功能无关。把产品能力留在 L2，元框架的版本只随原语与扩展点变化，产品的迭代可以独立进行。

2. 用框架层的复杂度倒逼元框架。类型化框架需要 T 表 25 行，就要求元框架开 25 个槽位；协作框架需要角色表，再开一轮；几轮之后元框架成为所有组织轴的并集。识别方法是检查新字段是否只服务一种组织轴，答案为是就留在框架层的 schema 里，用 K4 的命名空间存。

这条反模式的根源是把声明写得细当成内核要认识得多。类型化框架的声明越细，越说明它需要的是可配置的容器，而不是更多内置字段；K4 的命名空间与版本号已经能装下任意 schema，元框架不需要知道 schema 里叫 typeId 还是 stageId。把这两件事分开，元框架的字段数就不会随组织轴的细度增长。

3. 扩展点做成万能钩子。一个钩子传一个任意上下文对象，框架层想改租约、审计、隔离都能改，元框架不变量随之一条条失效；识别方法是检查钩子能否改变元框架不变量，答案必须是不能。每个扩展点要声明可读字段、可写字段与失败语义，越权写入直接拒绝，拒绝本身记进事件流。

万能钩子的诱惑来自短期便利：加一个字段就能让一种组织轴跑通，不必想清楚它属于哪件原语。代价是元框架的不变量变成可协商的，四种组织轴各自依赖不同的协商结果，最后没有一条不变量是共同的。把钩子的可写范围写死，短期会多几次设计讨论，长期省掉的是跨组织轴的兼容问题。

4. 分层写完后两边互相甩锅。元框架说语义在框架层，框架层说机制在元框架，缺口无人补；待建件最容易在两层之间反复登记。识别方法是检查每个跨层契约是否有唯一责任方与验收证据，没有则视为未完成；49 的未验证清单给出了可用的登记格式，每一行写缺口、为什么没验证、要什么才能验证。

这条反模式的实质是分层只分了描述，没有分责任。每一条跨层契约要写明谁提供机制、谁声明语义、谁验收结果，三者的名字落在文档里，缺口才不会在两层之间来回移动。分层越细，这份责任表越重要，因为细的分层给了更多可以推诿的边界。

## §7 已结与未决

上一轮列出的四条未决项已经结清，四条裁定各自带论证、代价与被否决的做法，互相之间的依赖在每条末尾注明。调度与验收的归属依赖准入自检里的调度需求声明，容器的边界依赖声明式配置这个扩展点的契约版本。四条都还缺运行证据，缺哪一类写在 §7.5。

### 7.1 跨框架共存的调度与验收归属

这一条的裁定是调度与验收各归一件原语。并发上限由 K5 调度与资源原语统一持有，框架只声明自己需要的并发量级与租约形式，实际分配由 K5 的租约池裁决，框架不得自建调度器。验收门由 K6 观测与验收原语统一持有，框架只声明验收判据的类型与断言内容，判据怎么判、什么时候判、判不过怎么处置都由 K6 决定。多个框架共存时按租户与类型分区隔离，不共享实例与租约，跨框架的依赖走 22b 上交，22a 依赖只用于框架内部。

论证落在实例记录与证据链的唯一性上。并发上限只有 K5 一个来源时，配额扣减、排队与反压记在同一个事件流里，跨框架复盘可以按事件逐条核对。验收门只有 K6 一个执行点时，同一次产出的判据类型、断言内容与三级结果落在同一份证据引用上，判据版本与判定人也查得到。31 的触发节奏、硬时限与幂等要求三值属于声明，K5 只按声明分配与排队，这条分工在 §2 第 5 件原语里已经写明。验收侧同样分成两半，A1 至 A8 的条件内容留在类型化框架，判定规则与证据格式由 K6 给。

代价落在资源利用率与链路长度上。分区隔离的代价是资源不能共享，同一租户下两种框架各自占一份配额，峰值叠加时租约池会比共享实例时更早达到上限。跨框架依赖改走 22b 上交之后，链路比 22a 依赖更长，一次跨框架交付要经过两层登记与一次人工确认。分配依据从单元改成框架声明的量级，K5 要维护一份框架量级表，表里的数字估低了会被反压，估高了会挤占其他框架的配额。

被否决的做法是每个框架自带调度器与验收门。两个调度器处理同一实例时，配额从两处扣减，实际可用并发取两者中较小的一个，而事件流只记录其中一处。两个门并存时同一次产出会被判两次，结论不一致就取较严的一次，较严的那次不写明理由，证据链里只剩一个阻断结果。实例记录与证据链因此无法统一，跨框架的复盘也就没有共同的事实基础。本条与 §7.4 相连，准入自检第一条里的调度需求声明正是 K5 分配配额的输入。

### 7.2 扩展点契约的版本化

这一条的裁定是五个扩展点各自带独立版本号。编号由扩展点序号与版本两段组成，形如 EP-3 v2.1，前一段标识是哪一个扩展点，后一段标识契约版本。框架在声明文件里写清自己实现的是哪一版契约，元框架按这一版调用，调用记录里带上契约版本。元框架升级扩展点契约时，兼容变更在同版本号上递增小版本，不兼容变更新开大版本并保留旧版本。框架自行选择升级时机，元框架不因为契约升级而拒绝旧版本的声明，只有旧版本被删除之后才不再接受。

论证落在变更节奏与一条判据上。判据是删词测试，把旧框架换到新契约上，如果它的声明与行为不需要改就能跑，这次变更就是兼容的。这条判据把兼容性从一句承诺变成一次可执行的检查，评审时拿旧框架的声明文件对照新契约的签名、调用时机与失败语义即可得出结论。版本号按扩展点分开记，原因是五个扩展点的变更节奏不一致，声明式配置与校验器可能连续两个大版本不变，事件订阅可能在一个版本周期里改两次。合在一起记时，任何一处无关变更都会迫使全部扩展点升级，框架的声明文件随之全部重写。

代价落在组合数量与适配层上。独立版本号的代价是组合变多，一个元框架版本对应一组契约版本，框架声明的合法性要按这组版本逐项核对。旧版本的保留期内，元框架要同时支持多套签名，实现里多出一层适配，适配的缺陷会同时影响已升级与未升级的框架。旧版本的保留窗口从"未定"改为待裁决，另给三条约束作为裁决依据：最小保留期取两个发布周期与九十天中的较长者，这条沿用元框架版本节奏受最保守使用方限制的口径；删除前必须列出一份仍声明旧版本的框架清单，契约版本本来就在框架声明文件里，清单可以按声明直接生成；删除动作要批准人为元框架维护者并有批准记录，沿用框架登记的登记面。三条齐了即可裁决，不需要任何运行样本。

被否决的做法是扩展点契约跟着元框架版本整体走。元框架换宿主时扩展点可能一行不用改，两者的变更节奏不同步，整体走版本号会让一次宿主适配把五个扩展点全部标成新版本。所有框架因此被迫重新声明，而它们对应的契约内容没有任何变化。整份契约共用一个版本号时，兼容性问题无法按扩展点定位，评审只能对整份契约做回归。本条与 §7.3 相连，K4 的命名空间与日志格式经声明式配置这个扩展点传递，它的版本号要与容器规则一起核对。

### 7.3 通用版本容器的边界

这一条的裁定是 K4 只提供三件事。元框架的 K4 状态与存储提供命名空间隔离、版本单调递增与只追加不可改的日志，不提供字段语义，不给 schema，不做校验，也不认识 T 表与 I 表这两个名字。T 表与 I 表是类型化框架在 K4 里占的一个命名空间，字段名、必填性、行号由类型化框架的 schema 决定。容器不知道命名空间里装的是类型声明、阶段状态还是协作事件。

论证落在换框架测试上。把类型化框架换成一个以协作事件为组织轴的框架，K4 仍然可用，只是命名空间里装的东西不同。命名空间回答对象存在哪里，版本单调回答哪一份更新，只追加日志回答发生过什么，三件都与内容无关。四种组织轴共用同一套容器时，容器的实现只随这三件的语义变化，不随组织轴的增加而扩展。本文的 K4 与 §2 第 4 件原语是同一件，本节只补它的边界，不改它提供的机制。

代价落在 schema 的维护责任上。只给三件事的代价是 schema 与校验由框架层自己维护，两套框架的 schema 不兼容时容器不做拦截，冲突要到读取阶段才暴露。版本单调递增不保证语义兼容，框架换了 schema 之后旧对象仍按旧结构存放，读取方要么按版本分支处理，要么做一次迁移。迁移工具不在元框架的范围内，由框架层自备，跨框架复用同一份配置时还要再写一层换算。

被否决的做法是元框架内置版本化 schema 引擎。schema 引擎要理解每种组织轴的数据模型，等于把类型化框架的逻辑下沉到内核，元框架从此要知道 typeId 与 stageId 的区别。删词测试在这一条上失败，schema 引擎的描述里删掉类型就无法说明它在做什么。第五种组织轴进来时引擎还要再扩字段，元框架的字段数随组织轴数量增长，这条路径通到 §6 第二条反模式。本条与 §7.2 相连，容器接受的声明格式由声明式配置这个扩展点的契约版本决定。

### 7.4 框架准入自检

这一条的裁定是四条自检，缺一不予准入。任何声称跑在元框架上的框架，要声明用到的原语清单，即八件里用了哪几件；要声明实现的扩展点与契约版本；要声明各项能力的上限并说明来自哪件原语，逐项按 §1.4 表的四列对齐，能力名、原语归属、上限参数、外部约束都要落在同一行里，缺列视为未声明；要声明在 K4 里占用的命名空间。四条都写清才准予准入，自检结果写成一份声明文件，随框架版本一起变更。

论证落在声明与实现的可核对性上。原语清单检验框架有没有把框架层需要的东西当成元框架缺的机制，扩展点与契约版本检验它的接入方式是否在五个扩展点之内。能力上限来源对应 §1.4 的能力上限来源表，核对写法是拿框架声明里的每项能力去对表：能力名能在八件原语里找到归属，上限列有至少一个可测参数，约束列指向一个外部量，三项齐才算这条声明可核对，缺项要求补声明而不是补解释。命名空间声明对应 §7.3 的容器边界，四条都过之后，新增组织轴不改元框架才有可核对的依据。自检只核对声明与实现是否一致，不评价框架的好坏。

代价落在声明文件的维护上。每次框架升版都要同步一次声明，声明与实现不一致时准入被拒，补救要等下一次发布。四条自检不覆盖语义正确性，一个框架可以四条全过而验收判据写错，错误要到运行期才暴露。维护声明文件要同时读懂八件原语与五个扩展点，这个门槛比填一份问卷高。

被否决的做法是用一套问卷打分。打分把四条自检压成一个总分，总分不说明缺的是哪一条，复核时找不到对应的实现位置。声明的每一条都能对照实现与文件位置，准入决定因此可以逐条追到依据。本条与 §7.1 相连，自检第一条的原语清单要写明调度需求的量级与租约形式，K5 按这份声明分配配额。

### 7.5 仍待验证的部分

上面四条结清的是归属与规则，运行证据仍然没有。下表六项还没有答案。前四项各对应一次可执行的试装或演练，判据与所需样本在表里写明；旧契约版本的保留窗口已改为裁决项，不需要样本；能力上限来源表的结构层已通过、数值层要宿主压测。四条裁定都依赖真实运行或第二种组织轴的试装，文档无法替代，做完之前本文只能用于评审新增机制的归属。
