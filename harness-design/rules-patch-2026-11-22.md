## 二、team-mode.md 末尾追加第 10 节

锚点：文件末行是 `判断是否超预算的信号：某次派单的 prompt 里出现了整段规格原文，或某次回报里出现了 200 行以上日志。`，在它之后空一行接下面的全文。

```markdown
## 10. 子智能体编排与复用

本节规定子智能体的开法与复用方式。判据来自一次运行二十二点九小时、开出六十个子智能体的真实会话，其中约一半的子智能体由重复劳动产生。重复劳动集中在三处：同一份文档连改五轮，每轮新开一个子智能体并从零重读一千四百行规范；验收与修复分成两个子智能体，修完再开第三个验收；十四个单问单答的短任务逐个派单，每个都单独走一次启动与收尾。

1. **文档生命周期归属一个子智能体**：同一份文件从起草到定稿的连续修订由同一个子智能体续做，不按版本换人。换主题、换验收标准、或上下文已无法压缩时才新开。

2. **查修验合成一个循环**：验收发现的问题交回原实现子智能体修，修完由同一个验收子智能体复核。连续两轮不过才换人或拆分，换人前先让它把已完成部分写回文件。最终签字仍由独立子智能体完成，实现者不得自签。

3. **极短任务走扇出**：单问单答、批量核对、多文件同构替换这类任务，写成一次 workflow 脚本扇出，不逐个起子智能体。判据是任务之间没有依赖且每个任务只需一次工具调用。

4. **压测批次按覆盖一次到位**：同类样本一次压二十到三十个，按能力维度分层覆盖，不按单个样本逐个派单。

5. **固定角色可以续用**：同一会话内的固定角色（文档 owner、验收者）在上下文未跨过门槛时可续做下一张卡。跨过门槛、换文件主题、或用户要求全新判断时新开。

6. **同主题短文档合并交付**：同一轮要写的多份同类短文档合并给一个子智能体，交付时按文件分段。

7. **验收按核对与裁决分级**：核对型验收（条款是否落位、数字是否一致）用 low，裁决型验收（口径是否有缺陷、结构是否闭合）用 high 或 max，整线最终验收用 max。

8. **重试限额**：同一验证连续两次取不到证据就停下，记未验证并报升级。任何单次验证超过十分钟拿不到证据同样记未取到并落盘，不许原地重试。

9. **裁决台账**：每次裁决记进文件（问题、选项、选择、理由、代价），不靠对话记忆。换人或跨会话时先读台账。

10. **复用判据**：续用与换人只看三件事，上下文是否跨过 `rules/cost-efficiency.md` 的门槛、是否换文件主题、是否要求独立判断。三条都否就续用。
```

## 三、cost-efficiency.md 在第 78 行之后插入新节

锚点：第 78 行是 `## 观测与回滚` 之前的位置，插入下面的节。

```markdown
## 子智能体编排成本

成本的来源是请求数与旧上下文重读，不是单请求大小。实际运行里出现过同一份规范被五个连续子智能体各重读一次（每次约十万 token），也出现过同一件事拆成修、验、再修、再验四个子智能体。本节给编排侧的硬判据。

硬判据一：同一份文件的连续修订归属一个子智能体。判据是"同文件加同验收标准"。跨过门槛续做时先压成不超过八千 token 的交接摘要。

硬判据二：验收与修复合成一个循环。修复交回原实现者，复核由同一验收者做，连续两轮不过才换人。最终签字独立。

硬判据三：补丁式修订。修订回补丁清单五列（文件、行号、原文、新文、理由），不回整篇。整篇重写只在结构变更时做。

硬判据四：预读包加禁读清单。派单内嵌五到十个关键片段与行号区间，并写明"不要读哪些文件或区间"。

硬判据五：压测按覆盖一次到位。同类样本一次二十到三十个，按能力维度分层，不逐个样本派单。

硬判据六：极短任务走 workflow 扇出。单问单答、批量核对、多文件同构替换一次脚本扇出。

不能省的：独立验收的独立性、P0 级发现的完整报出、跨文件口径一致性、未验证项完整列、裁决不降档。这五项省掉的后果是返工，返工成本高于原本要省的请求数。
```

## 五、writing.md 追加汇报可读性两条

锚点：`E:\dsh_home\rules\writing.md` 的"交付与汇报"一节，在该节第一条之前插入，或作为该节末尾的补充条款。

来源是 2026-11-22 的一次用户反馈：主会话交付任务 C 之后写了一份汇报，用户读完说"可读性不是特别强，不知道到底发生了什么事情"。问题出在两处，一是汇报从代号开始，任务 C、五十七报告、R21、25a 这些编号在第一句就出现，读者不知道它们指什么；二是汇报只列改动，没有说这些改动解决什么问题，读起来像清单而不像事件。

```
汇报先讲事件，再放细节。第一段回答四件事：这一轮在做什么、为什么要做、结果怎样、下一步是什么。中间段落按"先发生什么、然后发生什么"的顺序写，每个改动先说它解决什么问题，再说改了什么，最后说数字。数字与代号放在句末或括注，不放在第一句。

代号第一次出现时用自然语言说一遍。规则编号、任务代号、文件编号、状态码在第一次出现的位置写出它是什么，例如"新增组合依赖图无环规则（编号 R21）"，后文再用编号。只在内部使用的代号不进汇报。
```
