## 0. 一分钟读法

**三个判断，先看这三个：**

1. **1 万需求 ≠ 1 万实例同时跑。** 逻辑并发（工作项数）、物理并发（同时活跃实例）、写入并发（候选提交）、冲突面（同一事实/同一文件）是四个不同的量，瓶颈各不相同。harness 的核心不是"能起多少实例"，而是**准入、配额、租约、合并、反压**五件事。
2. **实例是记忆的临时视图，不是记忆的容器。** 实例 = 记忆快照 + 私有草稿 + 租约 + 预算；可以随时杀、随时重建；身份与连续性在记忆里，不在进程里。〔用户已定，12 §0.1 第 1 条〕
3. **有效并发由"可并行写域"和"资源配额"共同决定，不由需求数决定。** 1 万个需求都改同一个文件时，并发度是 1；1 万个需求分属 200 个互不相干的模块时，并发度才可能上去。

**MVP 目标**：单机、单代码库、1 种后端 agent、100 个工作项 / 8–16 物理并发，先证明"记忆中心 + 并发 + 候选合并 + 恢复"的语义闭环，再谈 1 万。

## 1. 我的理解（供你纠正）

### 1.1 你的设计 vs 一般 harness

| | 一般 harness（业界常见） | 你的 harness |
|---|---|---|
| 核心 | **模型**：上下文、工具、循环都围着一次模型调用转 | **记忆**：项目代码库 + 任务描述 + 进展 + 看法，是长期主体 |
| agent 实例 | 会话的拥有者，状态在实例里 | 记忆的**临时视图 + 一次性执行体**，可丢弃 |
| 派生 | 子代理/团队，实例间对话、分工 | **spawn/fork 实例**：并行读同一套记忆，各自写私有 + 提交候选，**彼此不对话** |
| 并发 | 通常是个位数到几十 | 目标形态是**万级逻辑并发** |
| 扩展方式 | 加工具、加提示词 | 加**工作项**、加**实例**、加**写域** |

### 1.2 一条关键澄清：这不是"多 Agent 协作"

这是最容易抄错的地方。多 agent 协作（Agent Team / Router-Worker）解决的是"**一个任务内部**怎么拆、怎么分工、谁跟谁说话"；你的模型解决的是"**很多任务之间**怎么并行、归属、授权、恢复、合并"。

两者的判据：

- 协作：实例之间**有消息流**，需要通信协议、角色、汇报链；
- 你的模型：实例之间**没有消息流**，只有"同一记忆的并发读 + 候选写"，协调靠**记忆本身 + 合并规则**，不靠对话。

所以本设计**不引入实例间对话**：没有 team 通信、没有 lead/worker 对话、没有任务认领对话。需要的是并发控制（租约、版本、合并、反压），不是协作协议。

**但必须区分两件事，否则会和 19/14 的已拍板结论打架**：

1. **实例之间不对话**——这是对的，协调靠记忆 + 合并规则；
2. **用户出口仍是"秘书投影"**——19 Q1=A 已拍板"主 Loop 只读 + 沟通 + 派发 + 候选，写操作交专家"（19:1164-1169, 676-680）；14 已确认"用户只跟秘书说话，专家不直接对用户输出"（14:140）。本文的 `Instance` 对应 19 的**专家实例**（depth=1 的 worker），H0 的**秘书投影**负责汇总/确认/汇报，是唯一对用户说话的角色。

一句话：**记忆是协调者，秘书是出口，实例是执行体**——三者不矛盾。角色映射：

| 角色 | 落在本文哪层 | 职责 | 不做什么 |
|---|---|---|---|
| **secretary（秘书投影）** | H0 | 唯一用户出口；读全局记忆；把用户需求转成 WorkItem；汇总结果、发起确认 | 不直接执行写操作（19 Q1=A） |
| **expert（工作项实例）** | H3/H4 | 读任务作用域 + 领域只读；写私有 + 候选；调工具/改代码 | 不直接对用户说话；不写公共记忆 |
| **reviewer / adjudicator** | H2/H5 的人审队列 | 处理 `disputed`、验收门、高风险合并 | 不替实例重做任务 |

**19 的 DELEGATE 六决策之一**：映射为"H2 派发子 WorkItem"；子实例 `depth=1`，不递归（沿用 19 §8 的 depth=1、并发≤2）。本文不新增"实例间委派对话"。

### 1.3 派生语义：spawn 与 fork 的区别（沿用 12 §4.1 的默认语义；Q9 未拍板）

| 动作 | 含义 | 复制什么 | 典型场景 |
|---|---|---|---|
| **spawn** | 在某作用域上新建实例，私有工作集为空 | 只复制"视图"（快照 + 检索结果） | 1 万个需求各起一个实例 |
| **fork** | 从进行中的实例/任务分叉 | 视图 + **当前私有工作集 + 任务上下文** | 同一问题试两条路；失败重试保留试错记录 |

两者共同点：**都不复制记忆本体**。复制的是"读到哪一版 + 自己的草稿"。

> **证据等级**：12 §4.1 自标"推断，需你确认，见 Q9"；Q9 在 12 §10.2"可边做边定"表。本文按该默认值设计，**不把它当已定结论**；若要改（例如 fork 语义变化），改动点在 §4.2 与 §5.6。

### 1.4 规模诉求的正确读法

"产品经理给 1 万个需求，派生 1 万个 agent"——这句话在工程上要拆成：

```
1 万个需求
  → 1 万个工作项（WorkItem，落库、有依赖、有验收条件）
  → 调度器按"可并行写域 + 资源配额"发放租约
  → 同时活跃 N 个实例（N 由容量决定，不是 10000）
  → 每个实例：读快照 → 执行 → 提交候选
  → 合并器单写者按分片合并 → 冲突升级
  → 验收门 → 归档
```

**1 万是"在系统里的工作项数"，不是"同时运行的进程数"。** 这个区分决定了整个架构：如果是前者，核心是持久化的工作图 + 调度 + 合并；如果是后者，核心是资源池 + 限流——而后者在单机上根本做不到 1 万，也不需要。

**一个必须显式选择的变体**：实例是**短生命周期**（spawn → 执行一个工作项 → 结束）还是**长驻**（一个实例活着、反复领任务）？本文默认**短生命周期**，因为它让"实例可丢弃 + 快照隔离 + 幂等恢复"三条不变式同时成立；长驻实例会引入"实例自己缓存了旧记忆/旧假设"的问题，需要额外的失效与重载机制。若你更倾向长驻（更像"常驻员工"），这是 D-H1 的一个前置选择，见 §10。

### 1.5 业界先例：三个可借样板与一个强反证

> 外部证据的完整出处见 `.tmp/harness-design/industry-research.md`（548 行，167 个 URL）；这里只列会改变设计判断的部分。

| 先例 | 做法 | 与本文的关系 |
|---|---|---|
| **Letta shared memory**〔文档〕 | 组织级 **git 仓库**作为多 agent 共享记忆；每个 agent clone 到本地 checkout，用普通文件 + git 工具读写，**必须 commit/push**，别人再 pull；早期"shared memory blocks"仍受支持但建议迁移到仓库（https://docs.letta.com/concepts/shared-memory）。**限定**：原文写明 shared memory repositories **require cloud-hosted agents**，本地 agent 用各自的 MemFS | **最接近用户设想**："记忆是共享仓库、实例是本地 checkout"。差异：Letta 仍以 agent 为身份主体；本文选**记忆为身份主体**（12 I1）。落地建议：记忆仓库用 git 语义，**但高频运行时写入改用事件日志/DB**，不要所有的写都走 commit；MVP 是单机本地部署，因此要**自建本地等价物**（本地 git 仓 + 本地 checkout），不能把 Letta 的 cloud-hosted 前提照搬 |
| **SQS lease + Temporal Event History + LangGraph at-least-once + K8s desired state**〔文档〕 | 四家**各自的原句**成立：SQS 的可见性超时/`ChangeMessageVisibility` 续约/DLQ；Temporal 的 Event History 恢复；LangGraph 的"幂等键必须来自已持久化状态""缺 ack 视为未知""graceful drain"；K8s 控制器只比较 desired/current、控制器本身可失败 | **本文的归纳**〔推断〕：这四家共同指向"至少一次 + 幂等 + 可恢复"，可映射为本文 §5.2 的租约语义。**注意**：四家的机制/粒度/失败语义并不相同（SQS 是队列，Temporal 是工作流，LangGraph 是图执行，K8s 是控制循环），"完全对齐"是本文的归纳，不是原文表述；"控制器不信任自报完成"也是本文推论，K8s 原文只说不终止地比较 desired/current |
| **Anthropic 多 agent 研究系统**〔文档〕 | 早期为简单 query 派生 50 个子 agent；同步等待子 agent 会堵塞全局；agent ≈ **4×** chat token，多 agent ≈ **15×**；在 BrowseComp 上 token 用量解释 **80%** 性能方差（三因素合计 95%）（https://www.anthropic.com/research/multi-agent-research-system） | 成本必须先于技术成为约束：**1 万需求不能默认按"多 agent 15×"跑**；初版应分级（小需求单实例、低频轮询；大需求才 fan-out）。"按需求规模分级调度"是本文推论〔推断〕，原文只有 prompt 层的 scale-effort 启发式 |
| **Cognition 的反证**〔文档〕 | "Actions carry implicit decisions, and conflicting decisions carry bad results"；主张共享完整 trace、默认排除多 agent 并行（https://cognition.com/blog/dont-build-multi-agents） | **原文论域是"单任务内多 agent 分治"**（Flappy Bird 例），并未讨论"任务间并行"。把它外推到"1 万任务并行"是本文推断〔推断〕：任务间虽无消息流，但会经共享记忆互相污染。应对不是无视它，而是把**隐式决策显式化**：每个实例的假设/取舍必须落成记忆条目（belief/decision），合并按条目而非按最终产物 |
| **git worktree 的官方边界**〔文档〕 | "Multiple checkout in general is still experimental, and the support for submodules is incomplete. **It is NOT recommended to make multiple checkouts of a superproject.**"（https://man7.org/linux/man-pages/man1/git-worktree.1.html，Git 2.55 BUGS 节） | 单仓库可用 worktree；**monorepo/superproject 不建议多 checkout**——这是 §5.4 写域隔离的硬边界，必须写进 MVP 范围。"改独立 clone + 共享对象库或虚拟 FS"是本文推断〔推断〕，原文未给替代方案 |

**一条术语提醒**：**未找到**"harness as OS"的一手来源（不是"业界没有"这种强断言），它只是类比（K8s 控制循环 + Fowler 的控制论类比 + 微软/OpenHands 的 provider 分层；"三分"是本文的映射〔推断〕，各家实际是五层/四包）。本文不用"OS"做承诺，只借用"控制循环 + 端口 + 资源治理"的形状。

## 2. 问题定义：1 万并发的四个维度

把"1 万"拆成四个独立的量，每个量有自己的瓶颈。这是本设计最重要的一张表：

| 维度 | 1 万意味着什么 | 直接瓶颈 | 本设计的应对 |
|---|---|---|---|
| **逻辑并发** | 1 万个工作项同时在系统里（待办/进行/待审/失败） | 工作图存储、状态查询、调度公平性 | 持久化 WorkItem 表 + 索引；状态机收敛；分页/聚合查询 |
| **物理并发** | 同一时刻真正在调模型/跑工具的实例数 | 模型 RPM/TPM、CPU、沙箱槽位、磁盘 I/O | 令牌桶配额 + 租约 + 队列；**物理并发是受控变量，不是目标** |
| **写入并发** | 每秒/每分钟有多少候选提交到单写者 | 合并器吞吐、事务争用、版本冲突检测 | 合并按 scope 分片；提交批量化；纯规则合并（不调模型）〔12 §5.1〕 |
| **冲突面** | 多少实例在改同一个事实/同一个文件 | 三方合并成本、人审带宽 | 写域划分 + 租约互斥；冲突显式化 + 升级队列；冲突率作为反压信号 |

**推论：** 一个 harness 的容量上限近似为：

```
有效并发 N ≈ min(
    模型配额可支撑的并发,        # Q_model / (tokens_per_step / step_latency)
    沙箱/CPU 可支撑的并发,       # C_sandbox / cpu_per_instance
    合并器可支撑的提交速率,      # Q_merge × avg_time_per_work
    可并行写域数,                # W_parallel（同一写域内必须串行）
    人审队列可承受的产出速率      # Q_review × avg_time_per_work
)
```

〔推断〕这个公式的价值不在于精确，而在于**让"加机器"和"改架构"分开**：如果 N 被 W_parallel 卡住，加机器没用，要拆写域；如果被 Q_model 卡住，要谈配额或换更便宜的模型；如果被 Q_merge 卡住，要分片或批处理。

**单位口径**（否则公式不可算）：`Q_model` 用 token/秒；`tokens_per_step` 用 token/步；`step_latency` 用 秒/步；`Q_merge` 用 提交/秒；`avg_time_per_work` 用 秒/项（合并吞吐项按 Little 定律 `L = λW` 换算）；`W_parallel` 用"可并行写域数"。

### 3.2 一次执行的数据流（文字时序）

```
需求导入
  → H1：拆成 WorkItem（或先由 Planner 拆，见 23），写依赖图，状态 pending
  → H2：deps 就绪 + 写域空闲 + 有配额令牌 → 状态 ready → 发放 Lease
  → H3：spawn 实例（instanceId、memorySnapshot、privateScope、budget）
  → H4：实例循环（读视图 → 调模型 → 调工具 → 写私有草稿）
        工具执行有独立超时/配额；写操作先落私有/事件日志
  → 结束时：生成 Handoff（候选批次）→ 提交
  → H5：单写者校验 → 合并/冲突/拒绝 → 发版本 → 回执
  → H2：收到回执 → WorkItem 状态 `candidate_merged` / `disputed` / `rejected`
  → H5/H6：代码/产物合并进主干 → `integrated`
  → H7：验收门（自动证据检查）→ 通过则 `accepted → closed`，否则退回 `running`（补证据）
  → 归档：episode 保留，私有工作集冻结 7 天〔12 §4.4〕
```

## 4. 核心对象

> 只列**本文新增或需要强调**的字段；记忆条目 schema 以 12 §2 为准，不重复。

### 4.1 WorkItem（工作项，H1 的一等公民）

**先定关系（否则就是第二套任务模型）**：`WorkItem` 不是新造的任务本体，而是 **18 SDD 的 Task / 23 的 Plan 子项在 harness 侧的"调度视图"**——字段权威归 18 v0.3（`planRevision/dependsOn/acceptanceKeys/boundary`）；本文只加调度必需字段（lease/attempt/priority/budget/writeDomains），`WorkGraphStore` **不持久化第二份 Task 状态**，只存"调度态投影 + 索引"，状态变化仍回写 18 的权威表。若要把 WorkItem 升级为独立对象，列为 D-H14（默认不）。

| 字段 | 说明 |
|---|---|
| `id` / `parentId` | 工作项 id；支持树/图（1 万需求 → 可拆子项）；建议直接用 18 的 Task id 派生 |
| `projectId` / `scopeRef` | 所属项目；绑定记忆作用域（`domain:后端` / `task:<id>`） |
| `goal` | 目标（自然语言，给模型） |
| `acceptance[]` | **验收条件（结构化）**：测试命令、期望输出、静态检查、变更范围；缺它不许进 review（验收门的权威定义在 18 SDD 的 acceptance_keys/evidence，本文只做强制执行） |
| `deps[]` | 依赖的工作项 id（DAG） |
| `writeDomains[]` | **代码可写域**：文件/模块/服务路径；同一域同一时刻只允许一个活跃租约（与 24 的"记忆写域"是不同概念，见附录 C） |
| `priority` / `createdAt` / `deadline` | 调度用 |
| `budget` | `{tokens, wallClockSec, toolCalls, costUsd}`；**默认软上限 + 可配置硬熔断**（见 §4.5） |
| `policy` | `{model, tools, approvalMode, maxAttempts}` |
| `state` | 见下方唯一状态机 |
| `attempts` / `leaseId` / `instanceId` / `epoch` | 执行追踪（epoch 见 §4.3） |

**唯一状态机**（旧稿 `merged/closed/working` 混用，这里统一）：

```
pending → ready → leased → running → submitted
  → candidate_merged      # 候选已合并进记忆（12 §5）
  → integrated            # 代码/产物已合并进主干（§5.4 merge 语义）
  → accepted              # 验收门通过（证据齐全 + 自动检查过）
  → closed                # 归档（完成 = closed）

disputed（等裁决）→ running（补证据/重做）| adjudicated → accepted | rejected
failed（attempt 用尽）| blocked（等人/依赖/资源）| canceled（取消传播）
```

**状态约束**：

- `submitted` 只表示"候选已提交"，**不表示完成**；`candidate_merged` 是记忆合并，`integrated` 是代码合并，`accepted/closed` 是验收通过——三者不能混用一个词；
- `disputed` 不是失败，是"等裁决"（冲突也是记忆，12 §6.1 第 5 条）；裁决后回 `running` 或进 `accepted/rejected`；
- `failed` 可重试（`attempts < maxAttempts`），但**重试是重新 spawn，不是复活旧实例**；`attempts` 用尽后 `failed` 是**终态**，进异常队列（DLQ 语义），不静默消失；
- `blocked` 显式区分"等人/等依赖/等资源"，可查询、可排序（对齐 Super-agent 的 `person/*` 状态）；
- `canceled` 必须做**取消传播**：释放租约、回收 worktree、取消子 WorkItem。

### 4.2 Instance（实例，一次性执行体）

| 字段 | 说明 |
|---|---|
| `instanceId` | 一次性 id |
| `workItemId` / `leaseId` / `leaseEpoch` | 绑定；`leaseEpoch` 用于 fencing（§4.3） |
| `agentRef` | **主体**：`{agentId, personaVersion, memoryDomain, readScopes[]}`，由 InstanceManager 从 24 §6 解析；没有它就无法执行人格防混乱、敏感例外、读集校验 |
| `memorySnapshot` | `{scopeId: rev}` 版本向量——spawn 时钉住 |
| `privateScopeId` | 私有工作集（`scope=instance:<id>`） |
| `model` / `tools[]` | 本次算力与能力（换模型 = 新实例，记忆不受影响）〔12 §4.5〕 |
| `budgetLeft` | 实时剩余预算 |
| `startedAt` / `heartbeatAt` / `expiresAt` | 租约与回收 |
| `state` | `spawning → running → submitting → ended | crashed | killed` |

**"实例无状态"的准确含义**：实例**可以**有自己的私有草稿、内存里的对话、临时文件；但**任何需要跨越崩溃的东西必须已落日志/记忆**。所以"无状态"= **可替换**，不是"没有内存状态"。

**新增不变量**：实例的读/写不得超出 `agentRef.readScopes` / `memoryDomain`；跨域只读必须显式 `refs`（24 §6.2/§6.5）。

### 4.3 Lease（租约）

| 字段 | 说明 |
|---|---|
| `leaseId` / `workItemId` / `instanceId` | 绑定 |
| `epoch` | **单调递增的 fencing token**；每次发放租约 +1 |
| `ttl` / `heartbeatAt` | 默认 60s TTL，15s 心跳（数字待压测校准） |
| `attempt` | 执行尝试序号（只在"重新开始一次完整执行"时 +1；崩溃重试复用同一 attempt） |
| `state` | `active → expired | released` |

规则：

1. **同一 WorkItem 同一时刻最多一个 active 租约**（否则两个实例同时改同一写域）；发放用**原子 CAS**（`UPDATE ... WHERE state='ready'` 或唯一部分索引），不是"先查后写"；
2. 心跳丢失超过 TTL → 租约过期 → 实例标 `crashed` → 工作项回 `ready`；
3. **fencing**：所有提交/写工具必须带 `epoch` 并校验 `epoch == current`；旧 epoch 的写入**一律拒绝**并记 `outcome_unknown`（防"过期实例还活着、写出幽灵结果"）；
4. **租约不等于锁**：它保护"谁在执行"，不保护"谁都别读"；读永远允许（快照隔离）。

### 4.4 Candidate / Handoff（候选提交）

沿用 12 §5 的候选制，这里只强调并发相关字段：

| 字段 | 说明 |
|---|---|
| `candidateId` | **全局唯一** = `workItemId + attempt + candidateSeq`（同一 attempt 内允许多次提交：progress/final） |
| `idempotencyKey` | = `candidateId`；重复提交返回同一结果（不是 `workItemId+attempt`，避免吞掉同 attempt 的多次提交） |
| `baseVersion` | 实例 spawn 时钉住的版本向量（用于三方合并） |
| `operations[]` | 新增/修改条目、progress、decision、experience（**只写私有层/候选**） |
| `sources[]` | episode 引用（无来源只能 `agent_inferred`，不得占高权威位）〔12 §5.8〕 |
| `evidence[]` | 验收证据（测试输出、命令、diff 哈希） |
| `state` | `pending → validating → merged | rejected | disputed` |

### 4.5 Budget（预算）

**默认软上限 + 可配置硬熔断**（对齐 19 Q3=A 已拍板：软上限允许最后响应/子代理尾巴完成并计入，报告写清可能超支；23 §Q3 同）。四类预算：

- **token 预算**：每实例、每工作项、每项目三层；
- **时间预算**：wall-clock（防长尾卡死）；
- **工具调用预算**：防"无限重试/无限搜索"；
- **成本预算**：按模型单价折算，用于熔断。

到限动作：软上限下**先产出中间结果 + 标记 `budget_exceeded`**，允许最后一次响应完成；**硬熔断是可配项**（万级场景可开启"到限即停"），开启时同样先落中间结果，不静默失败。由 H1 决定"降级续跑 / 拆小 / 失败"。

## 5. 五个机制（本设计的核心）

### 5.1 准入与配额：调度器到底在调度什么

调度器不是"给每个需求起一个实例"，而是**在四类约束下发放租约**：

| 约束 | 检查 | 不满足时 |
|---|---|---|
| 依赖就绪 | `deps` 全部 `integrated/closed` | 留在 `pending`，不占资源 |
| 写域空闲 | `writeDomains` 无活跃租约 | 排队；**这是并发度的硬上限** |
| 资源令牌 | 模型 RPM/TPM、沙箱槽位、磁盘配额 | 排队；高优先级可插队 |
| 人审容量 | 待验收队列未超阈值 | **暂停发放**（做完没人验 = 假吞吐） |

**优先级策略**（MVP 可先用简单版，P1 再优化）：

1. 显式优先级（人给的）> 截止时间近的 > 依赖下游多的（解锁更多）> 先来先服务；
2. 防饥饿：低优先级等待超过阈值 → 临时提权；
3. **同类合并**：1 万需求里大量是模板化的（改配置、加字段、跑迁移），调度器可把它们合并成"批处理工作项"，用一个实例按清单执行——这是 1 万规模下最有效的成本优化〔推断〕。

**反压信号**（任一触发就降速，不是等崩）：

- 候选积压 > 阈值（合并器吃不下）；
- 冲突率 > 阈值（并行写域重叠太多，再加并发只会制造更多冲突）；
- 人审队列 > 阈值（产出速度超过人的验收速度）；
- 模型 429/限流比例 > 阈值；
- 单实例平均 token 超预算比例上升（模型跑偏）。

### 5.2 租约与恢复：崩溃是常态，不是异常

**语义选择：at-least-once + 幂等提交**（不用 exactly-once，代价过高）〔推断〕。

崩溃恢复流程（固定顺序，可测）：

1. 心跳停止 → TTL 过期 → 租约 `expired`；
2. 实例标 `crashed`；私有工作集**保留**（冻结，供审计/接手）；
3. 工作项回 `ready`；
4. 重新 spawn：新实例、新 `instanceId`、**新 epoch**；`attempt` 只在"重新开始一次完整执行"时 +1（崩溃重试复用同一 attempt，避免幂等键漂移）；
5. 合并器若已处理过该 `candidateId` → 直接返回旧结果，不重复写；旧 epoch 的迟到提交一律拒绝（`outcome_unknown`）。

**必须能回答的问题**（恢复的可测断言）：

- 杀进程后，重启能否在 X 秒内继续？
- 同一工作项被两个实例先后执行，会不会写两份记忆？（幂等键回答）
- 崩溃时正在执行的外部副作用（写文件、发请求）会不会重复？（工具层需要"先落日志再执行 + 幂等收据"，对齐 12 §5 / 19 §7）

**一条容易漏的语义**（LangGraph 口径）：**缺 ack 视为未知**——外部动作可能已提交但回执丢失，本地无记录 ≠ 没发生；恢复时必须先查外部状态再补偿，不能默认"没做过"直接重放。

**三个外部参照的边界**（避免照搬错）：① SQS 可见性超时**最长 12h**（延长不重置该上限），因此长任务必须拆小或改用工作流引擎——本文租约 TTL 远小于此，但"长任务"要显式拆；② SQS 标准队列 in-flight 上限约 **12 万**，说明"队列层可容纳万级逻辑并发，但活跃 worker 必须自有上限"；③ Temporal 的 "exactly once" 是**工作流内部**语义，外部副作用仍需幂等（LangGraph 明确指出 at-least-once 不保证外部副作用只发生一次），本文按后者设计。

### 5.3 快照隔离与候选合并：规模化后的真正瓶颈

继承 12 §6.1 的五条规则（快照隔离、只写私有、乐观并发 + 三方合并、禁止 last-write-wins、冲突也是记忆），本文补充**规模化后的三个工程点**：

**(a) `baseVersion` 过期是常态，合并器是热点。**
10 并发时冲突是"偶发"；1 万并发时，同一 `domain` 作用域的所有实例都在提交候选，`baseVersion` 几乎必然过期。应对：

- 合并器**纯规则、不调模型**（12 §5.1 的分工是"推断"，需压测验证；见 §13）；
- 按 `scopeId` 分片：`shard = hash(scopeId) % K`，每片一个串行队列，**片内单写者**、片间并行。**这是本文对 12 I2 的修订**：单写者粒度从"全局一个进程"变为"每个 scope 一个写者"；每个 scope 仍只有一个写者，不存在两个写者同时写同一 scope；
- **跨 scope 候选禁止同批**：12 §5.6"批次原子"是硬要求；跨片批次要么拆批，要么走两阶段提交（本文默认拆批，D-H8 确认）；
- 合并结果只记"结论 + 来源 + 决定者"，不把推理过程写进公共层。

> **H-INV（新增不变量）**：任何写路径必须经过**所属 scope 的单写者**，禁止实例/后台整理者直写 DB 或记忆文件；分片只改变"哪个单写者"，不改变"单写者"这条性质。

**(b) 冲突要分"结构冲突"和"语义冲突"，且以 24 v0.3.1 Q3 为准**：

- 结构冲突（同 key 不同值、同文件不同改法）：**fact 类一律 `disputed`**（24 v0.3.1 Q3=A 已定，不允许按权威自动裁决）；只有 progress/experience 等低风险 kind 允许规则自动合并，且**任何自动裁决都必须保留败者为 `disputed`/证据，不静默丢弃**（12 I3/I6）；12 §5.4 与 24 Q3 冲突时**以 24 为准**（待 12 回写）；
- 语义冲突（不同 key 但话对着干）：必须 LLM/人判 → 进裁决队列，**不自动合并**。

**(c) 冲突率是调度信号，不是纯故障。**
冲突率高说明"写域划分太粗"或"并发太高"。正确反应是**调低并发/拆细写域**，而不是加大重试。

### 5.4 写域与隔离：并发度到底由什么决定

这是"1 万并发"最容易被忽略的一层。**并发度 ≈ min(资源配额, 可并行写域数)**。

| 场景 | 写域粒度 | 隔离方式 | 有效并发 |
|---|---|---|---|
| 后端代码库（MVP） | 文件级 | git worktree / 分支；补丁提交 | 受同一文件冲突限制 |
| 后端代码库（P1） | 模块/服务级 | 每实例独立 worktree + merge queue | 可到"模块数"量级 |
| 知识/文档类 | 条目级 | 记忆作用域 + 候选制 | 可很高（冲突只在同一条目） |
| 纯只读分析类 | 无写域 | 无隔离 | 只受资源配额限制 |

**代码库场景的关键设计**：

- 实例在**独立 worktree** 工作，不直接改主干；
- 提交候选 = **补丁 + 测试证据 + 变更范围**；
- **合并队列**按写域串行 apply（"merge queue" 是本文借用的业界实践名称，未取到官方行为细节，按〔推断〕使用）；apply 失败 → 退回实例或升级人审；
- **"本地改完"不算完成**，合并进主干 + 验收通过才算——否则 1 万个"完成"没有意义〔推断；验收门的权威定义见 18 SDD 的 acceptance_keys/evidence〕。

### 5.5 人类注意力与验收：1 万实例怎么不淹没人

**核心原则：实例不直接对人说话**（对齐 14:140 与 19:50 的"单出口/只见秘书"，**不是** 12 I5；I5 讲的是私有工作集不外溢）。

只有三类东西上浮到人：

| 类型 | 触发 | 呈现 |
|---|---|---|
| **需决策** | `disputed` / `open_question` / 高风险合并 | 聚合列表，按影响面排序 |
| **需验收** | `submitted` 且证据齐全、自动检查通过 | 按项目/写域分组的验收队列 |
| **异常** | 失败超重试、成本超限、租约反复过期 | 告警 + 聚合，不逐条报 |

**验收门必须自动化**（否则 1 万规模下人被淹没）：

- 缺验收条件 → 不许进 review；
- 证据不全 → 退回 `running` 并列出缺什么；
- 自动检查（测试/静态检查/变更范围）不过 → 不打扰人；
- 人只看"自动通过 + 证据齐全"的。

**指标**（对齐 14 §8 与 [17](../design/17-评测设计-v0.md) 的指标纪律；具体口径待定）：人均日打扰次数、`ready` 后被推翻的返工率、人 stop 率、静默弃单率。

**H7 指标最小集（定义 + 采集点 + 分账）**——只有名字的指标等于没有：

| 指标 | 定义 | 采集点 | 分账维度 |
|---|---|---|---|
| 吞吐 | `closed` / 小时 | WorkItem 状态迁移 | 项目 |
| 时延 | time-to-close p50/p95 | 状态迁移时间戳 | 项目/写域 |
| 并发 | 活跃实例数、队列深度 | InstanceManager / Scheduler | 全局 |
| 租约健康 | 租约过期率、心跳丢失率 | Lease | 全局/写域 |
| 合并 | 合并 p95、候选积压 | MemoryCore | scope |
| 质量 | 冲突率、revert 率、验收通过率 | 合并/验收 | 项目 |
| 成本 | tokens/项、cost/项、cost/closed | Meter | 实例/工作项/项目 |
| 人 | 验收队列深度、人均打扰次数 | ApprovalService | 人 |

### 5.6 视图装配：实例启动时到底看到什么

spawn/fork 的差异最终落在"视图装配"上。沿用 [12 §4.3](../design/12-记忆模型-候选稿.md) 的五步（不重新定义算法），harness 侧只负责三个接口：

| 接口 | 语义 | 约束 |
|---|---|---|
| `snapshot(scopes) → {scope: rev}` | 实例启动时钉住版本向量 | 之后所有读都基于这个版本；写入不改变它 |
| `assemble(instance) → {blocks[], entries[], snapshotVersion, budgetReport}` | 常驻块 + 检索条目 + 私有草稿（fork 时有） | 确定性可重放；有 token 预算；超预算按 12 §4.3 顺序降级（先裁检索、再裁低分，**绝不裁红线块**） |
| `refresh(instance) → 过期提示` | live 订阅的条目变更 | 只追加"某条已更新"的提示，**不悄悄改上下文**〔12 §6.6〕 |

三条工程约束：

1. **装配必须确定性**：同 snapshot + 同私有草稿 → 同视图；否则崩溃恢复后实例"看到的"变了，行为不可解释；
2. **fork 复制的是"私有工作集 + 视图起点"**，不是记忆本体；代码场景下 = 复制 worktree 快照 + 任务上下文；
3. **`budgetReport` 必须可查**：让人能回答"这条记忆为什么没生效"（被预算裁掉 / 没检索到 / 被权限过滤）。

### 5.7 工具执行在并发下的三条规则

引用 [19 §6](../design/19-AgentLoop设计-v0.md) 的工具管线（五段、权限六步、三态取消），这里只补"多实例共享机器"的三条：

1. **每个写工具必须绑定写域**：写域不匹配 → 直接拒绝（不是排队），防止实例越界改别人的文件；
2. **外部副作用先落日志再执行 + 幂等收据**：崩溃重放时按收据去重（对齐 12 §5 / 19 §7）；
3. **工具资源池化**：编译/测试/浏览器等重工具按槽位限流，避免 100 个实例同时编译把机器打满。

## 6. 一次"1 万需求"的端到端流程与数量级

> 下面的数字全部是〔估算〕，用来说明"1 万在物理上意味着什么"，不是承诺。

### 6.1 流程

```
[PM 导入 10000 条需求]
  → H1 去重/聚类/拆解 → 假设 8000 个工作项（20% 可合并）
  → H2 调度：受"模型配额 + 写域数 + 人审容量"约束，物理并发 N
  → 每项平均 15 步、每步输入 8k / 输出 1k token → 每项 ≈ 135k token
  → 总 token ≈ 8000 × 135k ≈ 10.8 亿 token
  → 合并：8000 份候选 → 冲突率 5% → 400 个 disputed → 人审
  → 验收：自动检查通过率 90% → 800 个需要人看
```

> **导入幂等（评审补充）**：1 万需求导入必须有**幂等键（外部需求 id）+ 去重规则（同标题/同目标聚类）+ 重复需求的合并策略**；否则"10000 → 8000"只是估算，真实系统会重复执行。这是 MVP 第一天就要的工程件。

### 6.2 现实约束（关键）

| 约束 | 估算 | 含义 |
|---|---|---|
| 模型 TPM | 假设 200 万 token/分钟（企业配额，需核实） | 10.8 亿 token ÷ 200 万/分钟 ≈ **540 分钟 ≈ 9 小时**纯模型时间 |
| 单步时延 | 假设 20–30s（含工具） | 8000 项 × 15 步 × 25s ≈ 833 小时串行；N≈90 并发 ≈ 9.3 小时 |
| 物理并发上限 | 由 TPM 反推：200 万/分钟 = 33,333 token/s；每实例 9k token/25s = 360 token/s → 33,333/360 ≈ **93 个实例** | 单实例不是瓶颈，**配额才是**；想跑 100 并发就要 ~216 万 TPM |
| 人审 | 400 冲突 + 800 验收 | 若人均每天看 50 条 → **24 人天**；不聚合就会压垮人 |
| 成本 | 按 10.8 亿 token 与单价估算 | 这是项目预算问题，不是技术问题 |

### 6.3 三个反直觉结论

1. **1 万需求的主要瓶颈通常不是"起实例"，是模型配额、写域冲突、人审带宽**——三者在架构里都要有明确的"闸"。
2. **合并不是"后处理"，是吞吐的一部分**：合并器慢，前面跑得再快也会堵住。
3. **1 万规模下，"完成"的定义比"速度"重要**：没有验收门，8000 个"完成"里有多少是真的？（验收门见 18/17，本文只做强制执行）

## 7. 不变量（可测，违反即作废）

在 12 §1.1 的 I1–I6 之上，本文补并发层的不变量。**注意：其中 I2 经 §5.3(a) 修订**——单写者粒度从"全局一个进程"变为"每个 scope 一个写者"；其余 I1/I3/I4/I5/I6 原样继承，不做修改。

| # | 不变量 | 怎么测 |

## 8. MVP POC 设计

### 8.1 目标与范围

**目标**：证明"记忆中心 + 多实例并发 + 候选合并 + 崩溃恢复"的语义闭环，而不是证明 1 万吞吐。

| 做 | 不做（明确留到后面） |
|---|---|
| 单机、单代码库、1 种后端 agent | 分布式、多机、多租户 |
| 100 个工作项，8–16 物理并发 | 1 万真并发 |
| WorkItem DAG（简单依赖） | 复杂调度优化、抢占式调度 |
| 租约 + 心跳 + 崩溃恢复 | 跨机故障转移 |
| 候选合并（规则）+ 冲突升级 | 自动语义合并 |
| 写域 = 文件级 + git worktree | 模块级/服务级写域 |
| 验收门（测试证据） | 完整评测体系（见 17） |
| 事件日志 + 指标面板 | 完整可观测性栈 |

### 8.2 最小技术形态（建议，待拍板）

- **存储**：SQLite（WAL）+ 事件表 append-only；或 JSONL 事件日志 + SQLite 索引（对齐 [14 §7.2](../design/14-总体设计-v1.md) 的单写者入口 + 12 I2；**不是**引用 00 的待定项）；
- **执行**：单进程内 worker pool（goroutine/线程），每实例一个上下文；先不做独立进程（P1 再拆）；
- **模型**：单一 provider + 熔断；实例级 token 计量；
- **工具**：复用既有工具运行时（read/write/edit/pwsh 等），加"每实例沙箱目录/worktree"；
- **记忆**：复用 12/24 的 schema 与合并语义；MVP 可先不做向量检索（FTS 即可）；
- **事件流**：SSE/WS 单出口；实例状态变化 → 聚合视图。

### 8.3 验收标准（可执行）

1. **功能**：100 个工作项，8 并发，2 小时内 `closed` ≥ 90%；每个 closed 项都有验收证据；
2. **幂等**：同一 `candidateId` 重复提交 3 次，记忆版本只增加 1；`progress` 与 `final` 两次提交各自生效、互不吞；
3. **恢复**：随机 kill -9 一次（记录 kill 时点），重启后在 **≤2×TTL** 内继续，已提交候选不丢、不重；**旧 epoch 实例的迟到提交必须被拒**并记 `outcome_unknown`；
4. **冲突**：构造两个实例改同一事实 → 产生 `disputed` + `open_question`，无静默覆盖；
5. **预算**：构造超 token 预算任务 → 软上限下允许最后一次响应并计入，标 `budget_exceeded`；开启硬熔断时停在预算上限，产出中间结果 + 原因；
6. **反压**：注入高冲突负载 → 租约发放速率 ≤ 注入前的 X%（给出 X 与测量方法，而不是"下降"）；
7. **视图确定性**：同 `snapshot` + 同私有草稿 → 装配结果哈希一致（可重放）；
8. **写域越界**：实例写非 `writeDomains` 路径 → 工具层拒绝；
9. **隔离**：两实例同写域 → 串行（租约互斥）；不同写域 → 并行（worktree 各自独立）；
10. **成本**：记录每工作项 token/成本，给出基线（不是目标值）。

### 8.4 MVP 的"1 万预演"

即使 MVP 只跑 100 项，也要**用 1 万的假设做容量设计**：

- 所有队列、租约、事件表都按"可持久化、可恢复"设计，不依赖内存状态；
- 合并器从第一天就按 scope 分片（哪怕 K=4）；
- 指标从第一天就记（吞吐、冲突率、合并延迟、租约过期率、成本/项）；
- 压测用"100 项 × 多轮"模拟负载，而不是等真 1 万。

### 8.5 与既有单机假设的冲突与迁移阈值

> 本地盘点确认：现有工程默认是"单机 Web + Go 单体 + SQLite + 单写者 + 单实例文件锁"（[14 §7.2](../design/14-总体设计-v1.md)；15 的工程默认），且 12 自陈"10 并发还行，**100 客服会紧**"（[12:1075](../design/12-记忆模型-候选稿.md)）。这些结论**对司墨 V1 有效**；本文的万级目标是另一档，不能默认沿用。
>
> **下表阈值全部是〔估算/待基线〕**，不是实测；触发后按决策程序走（D-H12），**确认前不改变 V1 形态**。阈值纪律沿用 15 §6.5：以实测为准，不预写未定数字。

| 既有假设 | 现有结论/出处 | 万级下的问题 | 迁移阈值（触发才改） | 迁移后形态 |
|---|---|---|---|---|
| 存储 | SQLite + 单写者（14 §7.2） | 单写者合并吞吐；100 并发即"紧"（12:1075） | 合并队列 p95 > 2s，或写冲突率 > 5% | 按 scope 分片 → 服务化存储（Postgres/对象存储） |
| 进程 | 单进程、单实例文件锁（15 M1） | 1 万实例不可能；故障域过大 | 物理并发 > 64，或需要故障隔离 | 多 worker 进程 → 多机（P1/P2） |
| 部署 | 本机 `127.0.0.1`、无鉴权（README） | 多租户/远程必须鉴权、配额、计费 | 出现第二台机器或第二个租户 | 网关 + 鉴权 + 配额 |
| 事件流 | 会话级 SSE（19 §10） | 1 万实例扇出、断线续接、快照重置成本 | 活跃流 > 1k | 聚合视图 + 采样 + 分层推送 |
| 隔离 | 工作区目录 + 审批（M9/M10） | 并发写同一仓库冲突；monorepo worktree 边界 | 并发写同一仓库 > 16 | worktree 池 / 独立 clone + merge queue |
| 一致性 | 单机强一致（SQLite） | 分布式下只能 at-least-once + 幂等 | 跨机部署 | 事件溯源 + 幂等 + 补偿 |

**结论**：不要把"万级"当成"把单机参数调大"，它是一次**架构档位切换**。本文的 MVP（P0）刻意停在单机档，但每个端口都按"可替换、可分布"设计，避免以后重写。

## 9. 演进路径（P0–P3）

| 阶段 | 形态 | 物理并发 | 触发升级的条件 | 主要代价 |
|---|---|---|---|---|
| **P0 MVP** | 单进程、SQLite、进程内 worker | 8–16 | 语义闭环验证完成 | 单点；无跨机恢复 |
| **P1 多进程** | 同机多 worker 进程 + 共享 DB + 租约 | 32–128 | 单进程 CPU/内存饱和；需要隔离故障 | 进程间协调、DB 争用 |
| **P2 分布式** | 远程 worker + 分片调度 + 对象存储 | 256–2k | 单机资源上限；需要弹性 | 分布式一致性、网络分区、运维 |
| **P3 万级** | 多项目/多租户 + 专用模型池 + 批处理 | 1 万+ 逻辑 | 业务量真实到达；成本模型跑通 | 多租户隔离、配额计费、SLA |

**每一步的判据**（不要提前优化）：

- 队列深度持续 > 阈值 × 2 小时 → 加并发/加 worker；
- 租约过期率 > 1% → 查崩溃/心跳/超时；
- 合并延迟 p95 > 阈值 → 分片或批处理；
- 冲突率 > 10% → 拆写域/降并发，**不是**加实例；
- 成本/项持续上升 → 检查模型选择、上下文膨胀、重试。

## 11. 风险与反直觉

1. **先做 1 万并发会失败。** 语义（租约、幂等、合并、冲突）没闭环时，规模只会放大 bug；先 100 项跑通，再谈扩容。
2. **单写者可能成为瓶颈。** 12 §5.1 已警告"管理器若调模型立刻变瓶颈"；本文加的"分片 + 纯规则 + 批处理"是缓解，不是消除。观察指标：合并 p95、分片倾斜。
3. **冲突率随并发非线性上升。** 写域划分是并发度的分母；不拆写域只加实例，等于制造冲突。
4. **成本可能比预期高一个量级。** 1 万需求 × 135k token 是估算；真实上下文膨胀、重试、工具输出会放大。必须从第一天计量。
5. **记忆不是智能。** 记忆解决"知道什么/做到哪"，不解决"会不会做"；模型能力仍是上限。不要把"记忆中心"当成"能力中心"。
6. **1 万条"完成"可能是假吞吐。** 没有验收门，agent 的"完成"无法验证；验收门必须在 MVP 就有，不能后补。
7. **"实例无状态"不等于"没有私有状态"。** 私有草稿必须保留（崩溃审计/接手），否则恢复时无法解释"它当时为什么这么做"。
8. **人审是隐藏的串行瓶颈。** 400 冲突 + 800 验收，可能是整个系统最慢的一环；必须聚合、分级、自动化。
9. **并行的最强反证是"隐式决策冲突"**（Cognition）：两个实例各自做假设、产物风格不一致，合成者收拾残局。**限定**：原文论域是"单任务内多 agent 分治"，把它外推到"1 万任务并行"是本文推断〔推断〕——任务间虽无消息流，但会经共享记忆互相污染。缓解不是"提高同步频率"，而是**把假设/取舍落成记忆条目**（belief/decision），合并按条目而非按产物；仍不够时，**先并行只读侦察、再串行写**。
10. **成本可能先于技术成为瓶颈**：agent ≈ 4× chat token、多 agent ≈ 15×（Anthropic 口径）；1 万个"多 agent"任务先撞预算，不是先撞并发。初版必须分级：小需求单实例低频轮询，大需求才 fan-out。
11. **monorepo 的 worktree 边界**：git 官方 BUGS 节明确"不推荐对 superproject 做多 checkout"；monorepo 必须独立 clone/虚拟 FS。MVP 选单仓库可绕开，但要在范围里写明。

## 13. 这个初版最可能错的地方（我的不确定性）

1. **写域粒度**：文件级可能太细（冲突多）也可能太粗（并发低），需要真实代码库数据校准；
2. **合并器吞吐**：我假设"纯规则合并毫秒级"，但真实候选的校验（来源检查、敏感检查、结构冲突）可能更重；
3. **人审容量**：400 冲突 + 800 验收的数字是拍脑袋的，真实比例取决于需求质量和验收自动化程度；
4. **模型配额**：200 万 TPM 是假设，实际配额决定物理并发上限；
5. **"1 万"是否真是目标**：如果实际是 1000，架构可以简化一半；
6. **fork 的语义**：fork 私有工作集在代码场景=复制 worktree，磁盘和合并成本可能被低估。

**下一步建议**：先拍 D-H12（本文服务谁）、D-H1（短生命周期还是长驻 + 执行形态）、D-H3（交付语义）、D-H4（写域）、D-H9（实例间是否允许通信）五条，它们决定 MVP 骨架；其余可边做边定。

| 术语 | 定义 |
|---|---|
| **工作项（WorkItem）** | 可调度的最小单元；一个需求可拆成多个工作项 |
| **逻辑并发** | 系统中同时存在的工作项数（可 1 万） |
| **物理并发** | 同一时刻真正在执行（调模型/跑工具）的实例数（受资源约束） |
| **写域（Write Domain）** | 可并行修改的最小范围；同一写域同一时刻只允许一个活跃租约 |
| **租约（Lease）** | "谁在执行这个工作项"的有时限凭证；过期即回收 |
| **候选（Candidate）** | 实例结束时的提交包；只有经单写者合并后才进公共记忆 |
| **反压（Backpressure）** | 下游吃不下时主动降低上游发放速率（不是等崩溃） |
| **验收门（Acceptance Gate）** | 进人审前必须满足的证据契约；缺证据退回 |
| **写域互斥** | 同一写域同一时刻只有一个活跃实例；不同写域可并行 |
