# 45 框架边界裁定 —— 这个 Agent 框架到底该有什么

> **背景**：用户指出"协作树只是举例/参考，不是补了这些就行、也不是做这些就必须补；框架要包含哪些产品功能或特性，要自己决定"。
> **本文的作用**：把"框架该有什么"的判断标准写下来，并用它把 33 的十域、43 的补强、44 的吸收清单**重新裁一遍**——该收的收，该砍的砍，而不是跟着别人给的清单长。
> **一句话结论**：框架只包含**"删掉它，实例就无法正确/安全/可验证地运行"**的机制。按这条判，框架的核心是 **7 件**，加 **2 个边界接口**；协作、生态、商业化、体验**都不是框架**。
> **与 43/44 的关系**：43 站得住（补的是 F5 内部机制缺口，不是加功能）；44 的"吸收清单"**收回大半**——只保留它暴露的两处机制缺口（打扰预算、团队级归因），其余不作为待办。

---

## 0. 判断标准（先定尺子，再量东西）

一条能力要不要进框架，只问四个问题，**任一"否"就不进**：

| # | 判据 | 问法 | 反例 |
|---|---|---|---|
| J1 | **必要性** | 删掉它，实例还能不能正确运行？ | "汇报风格"删掉，实例照样跑 → 不进 |
| J2 | **一致性** | 不在框架里统一，会不会同一条规则各有各的实现？ | "边界判定"不统一，每个类型自己判 → 进 |
| J3 | **可验证性** | 框架能不能对它做校验/取证？（不能校验的，放进来也只是标签） | "agent 是否合规"无法校验 → 只能做义务清单，不做认证 |
| J4 | **不重复** | 是不是某件已有机制的另一种说法？ | "自主等级"= 决策权三值的产品侧说法 → 不新增机制 |

**补充一条反向判据（J5）**：**凡是"建在框架之上"比"放进框架"更合适的能力，都不进。** 行业包、市场、客户成功、体验一致性，都是建在上面的东西。

---

## 1. 逐项裁定（13 个候选，全表）

标记：**核心**（必须有）｜**边界**（框架给接口与最小机制，不做产品）｜**不进**（框架外）

| 候选 | 裁定 | 依据 | 说明 |
|---|---|---|---|
| 类型系统（定义/校验/注册/版本/派生） | **核心** | J1/J2 | 没有它，每个实例各写各的定义，无法复用、无法校验 |
| 实例运行时（实例化/执行循环/生命周期/归因） | **核心** | J1 | 没有它，类型只是文档 |
| 共享状态（知识/记忆：读写/版本/冲突/隔离/投影） | **核心** | J1/J2 | 多实例并发读写的唯一真相，必须一处管 |
| 能力与工具（注册/执行/越界拒绝/环境） | **核心** | J1/J2 | 工具权限与执行必须在框架层统一，否则越权无处拦 |
| 边界与治理（权限上界/审批/审计/合规强度/记录） | **核心** | J1/J2 | 安全与合规的承重墙；用户与外部审计会直接问 |
| 调度与资源（并发/租约/幂等/配额/队列/依赖就绪） | **核心** | J1 | 多实例并行正确性（at-least-once + 幂等）全靠它 |
| 观测与验收（trace/指标/验收门/双段状态） | **核心** | J1/J3 | 没有验收，agent 产出无法判定对错；没有 trace，事故无法复盘 |
| 宿主与交互（CLI/Web/API/人机交互） | **边界** | J5 | 框架给接口与最小交互（审批/接管/确认），产品形态由宿主决定 |
| 扩展与生态（注册/插件/市场/行业包） | **边界** | J5 | 框架给扩展点（工具、连接器、场景包格式），市场是生态 |
| 多智能体协作（角色/团队/派工/会话/冲突调解） | **边界（P2）** | J4/J5 | 框架必须保证的只是"多实例并行时的一致性与隔离"（已在调度/边界里）；协作编排是上层用法，不是框架机制 |
| 自主性（自主等级/主动发起/请示停手） | **边界（P2）** | J4 | 决策权三值已在类型层表达；产品侧要的"开关"只是实例级覆盖字段 |
| 人机分寸（打扰预算/汇报风格/人格语气） | **边界（部分核心）** | J1 | **打扰预算是核心**（人被打扰成瓶颈会破坏运行）；风格/语气/人格不是框架 |
| 商业化（计费/定价/ROI/分成） | **不进** | J5 | 建在框架之上的商业系统 |
| 体验一致性（跨端/国际化/可访问性/离线） | **不进** | J5 | 宿主与产品体验层 |

## 2. 收敛后的框架结构（7 核心 + 2 边界）

```
框架 = 7 件核心机制 + 2 个边界接口
├─ [1] 类型系统（T 表：定义/校验/注册/版本/派生/组合登记）
├─ [2] 实例运行时（I 表：实例化/执行循环/生命周期/归因/运行记录）
├─ [3] 共享状态层（知识/记忆：读集六项/写域三项/冲突/隔离/投影）
├─ [4] 能力与工具（注册/执行/越界拒绝/环境三段/权限模型三值）
├─ [5] 边界与治理（F5：有效权限四交集/审批/审计/记录三性/合规强度与义务清单）
├─ [6] 调度与资源（并发/租约/epoch fencing/幂等/配额/队列/依赖就绪）
├─ [7] 观测与验收（trace/指标/验收门/双段状态/误拦补偿）
├─ [B1] 宿主接口（CLI/Web/API 的最小契约；审批与接管是核心，展示是产品）
└─ [B2] 扩展接口（工具/连接器/场景包的格式；市场是生态）
```

**与 33 十域的关系**：33 的 F1–F10 是**产品视角的功能组织**，不是框架边界。用 §0 的尺子量：
- F1–F7 = 核心（对应上面 1–7）；
- F8 扩展、F9 宿主、F10 协作 = 边界层（框架只出接口与最小机制）；
- 所以**十域不砍，但优先级要说清：F8/F9/F10 不可能是 P0**，它们永远不会阻塞"定义→实例化→跑完→验收→审计"闭环。

**这正是"协作不必现在展开"的依据**：F10 在 P0 闭环里一个功能都不需要；协作树的 A4 再完整，也不是框架的承重墙。

## 3. 对 43 / 44 的自裁

| 文件 | 裁定 | 理由 |
|---|---|---|
| 43（F5 补强：租户边界/有效权限/合规义务清单） | **保留**，且是本次唯一该做的增量 | 三样都过 §0 四条：删掉它越权拦不住、合规审不出、租户说不清（J1/J2/J3）；它们不是"新功能"，是 F5 内部机制补缺口 |
| 44（协作树对齐） | **收回大半** | §3 的"吸收清单 30–35 点"降级为参考，**不作为待办**；只保留两条机制缺口（打扰预算=J1；团队级归因=J2/J3，P2）；§5 的编号规则与 §6 的"自主等级=决策权"仍有价值，保留 |

**一句话**：43 是"框架缺了承重墙的一段钢筋"，44 是"别人家的户型图"——前者该补，后者只当参考，不当施工图。

## 4. 我对协作树这类材料的正确用法

1. **当检验清单，不当需求清单**：拿它问"它提到的这件事，我们的框架有没有机制能承接？"——能承接就过，不能就看是否过 §0 四条。
2. **当反例来源**：它暴露的"打扰预算""团队级归因"是真缺口（J1/J2 过），别的多是产品层展开。
3. **当边界压力测试**：它让你看到"产品会长到多大"——恰好证明框架必须**收窄**，否则框架会被产品需求拖着膨胀。

---

## 5. 反模式（写下来防自己再犯）

1. **按例补**：别人给了 135 个功能点，就去对齐吸收——框架会从 100 点长到 200 点，P0 失焦。
2. **把产品能力当框架机制**：多租户、协作、自主等级、市场，听起来都像"系统特性"，但多数是建在框架之上的产品能力。
3. **用清单代替判断**：清单只能提示"可能漏了"，不能决定"必须有"。判据永远是 §0 四条。
4. **版本膨胀**：每来一份外部材料就升一版。版本应该跟着**机制缺口**走（如 43），不跟着材料走。
5. **把"能描述"当"已具备"**：F10 有 18 个功能点描述 ≠ 框架支持多 agent 协作；框架支持的是并行一致性与隔离。

## 6. 结论

- **框架必须有的**：类型系统、实例运行时、共享状态、能力工具、边界治理、调度资源、观测验收（7 件）。
- **框架只给接口的**：宿主、扩展、协作/自主/人机分寸中的产品部分（2 个边界 + P2）。
- **框架不该有的**：商业化、体验一致性、行业包、市场、组织管理。
- **当前唯一该做的增量**：43 的 F5 补强（有效权限公式、合规义务清单、租户边界单元）。
- **判断标准落盘**：以后任何"要不要加"的问题，先过 §0 四条，再过 §5 五条反模式。

**下一步**：出 v1.4 只做两件事——把 43 的 F5 补强落进 33/34；把 44 的两条机制缺口（打扰预算、团队级归因，均为 P2，且后者只占位）作为待办记入 §9，不展开。31 九要素不动。
