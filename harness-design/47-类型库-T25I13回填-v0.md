# 47 类型库 T25/I13 回填建议 v0

## 0 口径与诚实声明

### 0.1 本表性质

本表是 T001–T037 的 T 表第 25 行与 I 表第 13 行取值建议草案（v0），供 34 v1.4 模板评审与后续回填使用。全部取值未经评审，不构成已审定的类型定义，也不表示任何一型已经支持多租户。本表只新建 47 这一个文件，35、36 与 34 原文件保持不动；表中类型名称与编号逐字取自 35、36，没有新增或改写类型。

### 0.2 默认口径

默认按单机/本地部署给出建议值：租户 id 写 `local`，是否允许跨租户写 `否`，理由写“单机单租户，只有逻辑隔离，无跨租户场景”，审批人写 `—`，I13 写 `local@<部署配置版本>`。`<部署配置版本>` 是占位，原因是 34 §6.4 与 §7.0 都已承认部署配置版本表尚未建立，当前没有可解析的版本号。单机阶段只有逻辑隔离，没有物理隔离；租户边界四件的落地程度以 43 F5.3 为准，本表不把逻辑隔离当成安全隔离。

### 0.3 判定规则

逐型只依据 35、36 中该型真实写明的读集、写域、对外接口与运行形态判断，不按域外推，不按名称联想。只有操作本身会把一个租户的数据、产出或影响带到另一个租户的类型，才在“是否允许跨租户”列写 `是`；写 `是` 的行同时给数据流向、接收方、法域或合同依据的草案，以及角色加审批档的审批人建议。其余行写 `否`，理由用“单机单租户，只有逻辑隔离”或“该类型不涉及跨组织数据”两种，并说明读集与写域的边界。多租户部署下可能改判的类型放入 §2 重判清单，不在 §1 里直接写成 `是`。

### 0.4 合规强度

34 §3 是决策权、验收类型、适用域三列总览，不含逐型合规强度；合规强度实际在 34 §2.1，按域给六判据统计。本批 37 型落在 A 至 E 五个域，域级合规强度为低或中，没有 H 域，因此 §1 没有一行标“高合规：需附合规义务清单（附录 D）”。T018、T029、T034、T036、T037 在型级 R14 六判据上可能命中法定对外义务、监管报送或记录留存义务，命中后应按高合规处理并附合规义务清单；本表只把这些型列为重判候选，没有代替型级 R14 判定。

### 0.5 术语

本表沿用 31 v1.3 与 43 的术语。租户边界四件指数据分区、运行上下文、配额、凭据，缺一件不算隔离。有效权限四交集指能力上界、读集、写域、工具白名单求交，不求并。合规义务清单指六判据命中项、必填控件、义务条目、验收证据四者的组合，随类型版本冻结。读集六项指范围（含可见粒度）、版本、时效、权威级别、驻留范围、准入。写域三项指层级、驻留范围、是否禁止写。能力五维指影响面、可逆性、成本、作用域、环境，环境含部署环境、可回放性、人身风险三段。记录三性指不可篡改、只追加、监管直读，另加留存期限。

### 0.6 覆盖核对

§1 共 37 行，T001 至 T037 连续无缺号。A 域 10 型（T001–T010），B 域 8 型（T011–T018），C 域 5 型（T019–T023），D 域 8 型（T024–T031），E 域 6 型（T032–T037），合计 37。

### 2.3 无法判定的边界

37 型都能给出建议值，无法判定的是“最终应判是还是否”的边界，缺的是部署侧输入。下面五组列出缺什么信息，以及缺了会影响哪一列。

|---|---|---|
| T006 | 共享库的租户分区方式（schema 级还是行级），平台运维是否登记为独立租户 | 租户 id、接收方租户 |

### 2.4 统计

37 型由判是 2 型、判否但需重判 21 型、不需重判 14 型组成。重判 21 型中第一档 14 型、第二档 7 型。涉及判是或重判的型共 23 型，按域分布为 A 域 2 型（T006、T009）、B 域 7 型（T011、T012、T013、T015、T016、T017、T018）、C 域 2 型（T022、T023）、D 域 8 型（T024–T031）、E 域 4 型（T034、T035、T036、T037）。


## 3 与 34 R17 的一致性检查

### 3.1 逐项检查

| R17 检查项 | 本表结果 | 证据与限制 |
|---|---|---|
| T25 四项齐全 | 37/37 形式齐全 | 每行都有租户 id、是否、理由、审批人；否行审批人为 `—`，符合“不允许时写 —” |
| 是否与部署形态一致 | 35 行通过，2 行条件通过 | T006、T018 写是，仅多租户成立；放入单机 T 表必须先改否 |
| 单机不得声明跨租户 | T006、T018 不通过（若按单机插入） | 这两行是条件值，不能直接落单机表 |
| 是行理由与审批人必填 | 2/2 形式齐全 | 理由含三要素草案；接收方是角色不是登记 id；审批人是角色加档位 |
| 审批人不得是类型所有者 | 无法核 | 35、36 没有类型所有者字段 |
| 多租户实例必有 I13 | 类型层有格式，实例层无记录 | 34 §7.0 记 0 条 I 记录；本表不能证明实例 I13 存在 |
| I13 租户 id 与 T25 一致 | 单机口径一致（`local`） | 多租户需换登记 id，当前表未给 |
| I13 配置版本可解析 | 不通过 | `<部署配置版本>` 是占位；部署配置版本表不存在 |
| 跨租户时 I13 引用 T25 与审批记录 id | 2 行给了引用格式，无实际 id | 审批记录 id 在实例层产生，类型层给不出 |

结论：本表在字段齐全、格式正确层面可以通过 R17 的形式检查；在单机不声明跨租户、配置版本可解析、实例 I13 存在、审批人非所有者四条实质检查上不能宣称通过。T006、T018 是条件值，插入当前单机 T 表会触发 R17 阻断。

### 3.2 T001 推演

T001 后端代码 Agent，A 域。T25 建议：租户 id `local`，是否 `否`，理由“单机单租户，只有逻辑隔离，无跨租户场景”，审批人 `—`。I13 建议：`local@<部署配置版本>`，跨租户声明引用 `—`。

单机部署推演：T25 四项齐全，否与单机一致，R17 的四项齐全、单机不声明跨租户两项通过。多租户部署推演：该型仍判否，因为它只读写单租户代码仓库与测试目录，读集六项都限定在一个租户内，写域三项也只落在该租户的补丁与说明；若部署为多租户，T25 租户 id 要换成使用方租户的登记 id，I13 写该租户 id@配置版本，跨租户引用 `—`。R17 的“多租户实例必有 I13”要求实例层真的写这条记录，本表只给格式。风险点：若把 T001 放进共享代码平台，让一个实例同时服务多个租户的仓库，读集就跨分区，T25 需重判，当前否不成立。

### 3.3 T018 推演

T018 报表生成 Agent，B 域。T25 建议：租户 id `local`（多租户部署登记为集团母公司租户 id），是否 `是`，理由“各法人租户的财务与经营数据汇总进集团合并报表；接收方为集团母公司租户；依据为合并报表法定义务或集团管理协议加对外披露审批”，审批人“合规负责人 + 财务负责人 + 审批档 A/B”。I13 建议：`租户id@配置版本 + T25 声明引用`。

单机部署推演：T25 写是，违反“单机不得声明跨租户”，R17 阻断；必须在单机表里写否，理由改为“单机单租户，只有逻辑隔离”，I13 写 `local@<版本>`，跨租户引用 `—`。多租户部署推演：T25 四项齐全；理由是数据流向加接收方加依据的草案，但接收方写的是“集团母公司租户”这个角色，不是部署登记里的具体租户 id，R17 的“接收方租户 id”还差一步；审批人有角色和档位，是否与类型所有者同一人无法核，因为 35、36 没有所有者字段；I13 要写集团母公司租户 id@配置版本，并在本次跨租户时引用 T25 声明与审批记录 id。结论：T018 的是值只在多租户集团部署下成立，且要把接收方角色换成登记 id、补齐审批记录 id，才能过 R17。

### 3.4 T037 推演

T037 投放优化 Agent，E 域。T25 建议：租户 id `local`，是否 `否`，理由“单机单租户，只有逻辑隔离，无跨租户场景”，审批人 `—`。I13 建议：`local@<部署配置版本>`。

单机部署推演：T25 四项齐全，否与单机一致，R17 形式通过。多租户代投推演：一个代运营租户管理多个广告主租户的账户，读集是各广告主账户数据与人群包，写域是各账户的出价、预算、定向，数据流向从广告主租户到代运营租户再回到广告主账户，接收方是代运营租户；法域或合同依据是委托投放合同与广告主授权书；审批人建议合规负责人加投放负责人加审批档 A。此时 T25 应改判是，I13 写代运营租户 id@配置版本并引用 T25 与审批记录 id。当前写否只对单广告主、单租户部署成立；多租户代投下继续写否，R17 会因未声明跨租户而阻断。结论：T037 是本批最典型的“否但多租户必重判”型，回填时应把触发条件写进备注，不能只留一个否。

### 3.5 总体结论

本表可以作为 34 §7.3 期 1 的输入草案，不能作为 R17 已通过的证据。可直接落单机 T 表的是 35 行否值；T006、T018 两行要先按部署形态改写；I13 列全部是格式建议值，实例层记录与配置版本解析都缺证据。下一步需要部署配置登记租户清单与配置版本，补类型所有者字段，并对 21 个重判候选逐型确认多租户触发条件。

### 4.2 修订建议分级

P0 是不修则 R17 无法判定的三项：先建部署配置登记，给 T25 加部署形态条件，把接收方拆成类型层角色与部署层 id。P1 是不修则 R17 只能人审、容易漏项的五项：逐型合规值、跨租户审批定档、理由结构化、类型层与实例层分开验收、型级 R14 补判。P2 是可维护性两项：判定依据枚举、类型所有者字段。

### 4.3 回填方法

逐型读 35、36 的职责、读集、写域、对外接口与运行形态，按“数据是否离开本租户分区”和“产出是否送达另一租户”两个问题判是或否。判否时再问一句“多租户 SaaS 或代运营模式下，这个型的正常用法会不会让一个实例服务多个租户”，会则进 §2 重判清单，不会则标不需重判。判是时只给理由草案与审批角色，不写具体租户 id，因为部署配置还没有租户登记。全部 37 型的名称、编号、域与 35、36 逐字核对，没有新增类型，没有改原文件。
