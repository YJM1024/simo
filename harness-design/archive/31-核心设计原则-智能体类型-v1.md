# 核心设计原则方案 v1 —— 智能体类型：要素与创建

> **定位**：Agent 框架的**第一条核心设计原则**。回答两个问题：**一个智能体类型应该包含哪些元素？想创建一个智能体类型，应该怎么做？**
> **不是**实现方案、技术选型、接口设计；是"设计一个 agent 时该想清楚什么、按什么顺序想、怎么判断想清楚了"。
> **与既有文档的关系**：[30-类型与实例](30-Agent框架-类型与实例-v0.md) 是讨论稿，本文是整理后的方案；[29-系统设计方案](29-系统设计方案-v1.md) 的"记忆中心"降级为"知识层的实现策略"。
> **与方案二的关系**：本文是"怎么设计一个 agent"（类型视角）；[32-通用 Agent 框架](32-通用Agent框架-v0.md) 是"框架由哪些组件构成"（系统视角）。两份方案互补，不重复。

---

## 0. 一句话与阅读指南

**一句话**：智能体类型是**设计产物**，它用九个要素回答"这个 agent 是谁、为什么存在、能做什么、知道什么、怎么干、不能干什么、怎么交互、怎么活、和谁协作"；创建类型就是**按顺序把这九个问题答完，并接受一组检查**。

阅读顺序：§1 原则 → §2 九要素 → §3 创建流程（本文重点）→ §4 生命周期 → §5 示例 → §6 检查清单与待确认。

---

## 1. 原则：类型是设计产物，实例是运行产物

- **类型**：跨实例不变的 agent 定义；可评审、可版本化、可复用、可枚举。
- **实例**：类型的一次具体化；带输入、快照、私有草稿、租约、产出；可丢弃、可重建。
- **分界判据**：问"换个任务，它变不变？"——不变的是类型，变的是实例。
- **推论**：设计一个 agent，本质是**设计一个类型**，而不是"写一段提示词"或"配一个工具集"。

---

## 2. 一个智能体类型包含什么（九要素）

> 每个要素给：**定义 / 设计时要回答的问题 / 判定标准（怎样算定义清楚） / 常见反例**。

### 2.1 身份（Identity）

- **定义**：这个 agent 是谁——角色名、人格、语气、立场。
- **要回答**：它以什么姿态工作？遇到冲突时站在哪边？它"像谁"？
- **判定**：能用 3 句话说清"它是谁"，且这三句话能约束行为（不是形容词堆砌）。
- **反例**："你是一个专业的助手"——没有约束力；身份必须能推出具体行为。

### 2.2 职责（Purpose）

- **定义**：它为什么存在——负责哪类任务、边界内交付什么、什么叫"做好了"。
- **要回答**：它只做什么？不做什么？成功标准是什么？
- **判定**：职责能用"负责 X，交付 Y，以 Z 为验收"表述；Y 可被验收。
- **反例**："负责后端开发"——太宽；职责必须窄到"一类任务 + 一种交付物"。

### 2.3 能力（Capabilities）

- **定义**：它完成任务所需的工具、技能、资源（**上界**，不是清单）。
- **要回答**：最少需要哪些工具？哪些是只读？哪些有副作用？哪些需要审批？
- **判定**：能力集能覆盖职责；且能说清"少了哪个就干不了"。
- **反例**：把"所有工具"都给它——能力越界，治理失效；能力应按职责最小化。

### 2.4 知识（Knowledge）

- **定义**：它需要读哪些共享知识、往哪里写回（**读集/写域，不是知识本体**）。
- **要回答**：读哪些领域/项目/历史？写回哪一层（任务/领域/全局）？哪些不能读？
- **判定**：读集/写域能对应到共享层的具体范围；越界可判定。
- **反例**：把知识写进提示词——知识会过期、会膨胀；知识必须在共享层，类型只声明范围。

### 2.5 行为（Behavior）

- **定义**：它怎么想、怎么做——决策风格、规划方式、歧义处理、失败处理、停止条件。
- **要回答**：先规划还是边做边看？不确定时问还是猜？失败了重试还是上报？什么时候停？
- **判定**：每条行为规则能对应一个可观察的动作或决策点。
- **反例**："要聪明地工作"——不可观察；行为必须落到"遇到 X 时做 Y"。

### 2.6 边界（Boundaries）

- **定义**：它不能做什么——禁区、必须经人的动作、不可越过的范围（**上界**）。
- **要回答**：绝对禁区是什么？哪些动作必须审批？哪些数据不能碰？
- **判定**：每条边界都能被程序判定（不是"尽量别"）。
- **反例**：只写"注意安全"——边界必须具体到动作/资源/条件。

### 2.7 接口（Interface）

- **定义**：它接收什么形态的任务、产出什么形态的交付物。
- **要回答**：输入是消息/工作项/事件？输出是文本/补丁/报告/文件？验收证据是什么？
- **判定**：输入输出能对齐"职责"的验收标准；交付物可被下游消费。
- **反例**：输入输出不定——实例化时无法匹配、无法验收。

### 2.8 生命周期策略（Lifecycle Policy）

- **定义**：它怎么活——一次性 / 短驻 / 长驻；回收规则。
- **要回答**：处理完就销毁？活一个任务周期？反复领任务？
- **判定**：策略与职责匹配（一次性任务不该长驻；需要经验积累的角色不该一次性）。
- **反例**：所有类型都默认长驻——资源浪费、状态腐坏。

### 2.9 协作关系（Collaboration，可选）

- **定义**：它能找谁——可委派给谁、向谁汇报。
- **要回答**：哪些子任务可委派？向谁交付？谁可以向它委派？
- **判定**：协作关系显式声明；不声明 = 不协作（默认隔离）。
- **反例**：隐式协作（"它知道该找谁"）——不可治理；协作必须显式。

### 2.10 要素之间的约束

- **必须成对定义的**：职责 ↔ 接口（否则无法验收）；能力 ↔ 边界（否则能力无约束）；知识读集 ↔ 写域（否则只读不写/只写不读）。
- **互斥/冲突的**：职责越宽，身份/行为越难具体；能力越多，边界越难判定。**宁可窄，不要宽**。
- **可选的**：协作关系（不声明即不协作）；生命周期（默认短驻）。

## 3. 怎么创建一个智能体类型（创建流程）

### 3.1 什么时候需要新类型

先判断"能不能复用现有类型"：

1. 现有类型的职责能覆盖 → **复用**（实例化，不建新类型）；
2. 职责相近但交付物/边界不同 → **派生**（特化现有类型，见 §4）；
3. 职责是新的、且会反复出现 → **新建类型**；
4. 只出现一次 → **不建类型**，用通用类型 + 一次性配置（避免类型爆炸）。

**判据**：新类型必须是"会反复实例化的稳定职责"；一次性的东西不配拥有类型。

### 3.2 八步创建法

> 顺序不能乱：先"为什么存在"，再"是谁"，最后"怎么活"。反过来会先想工具/提示词，导致类型没有边界。

| 步 | 动作 | 产出（概念层） | 完成判据 |
|---|---|---|---|
| **1 定职责** | 写"负责 X，交付 Y，以 Z 验收" | 一句话职责 + 验收标准 | Y 可验收、Z 可判定 |
| **2 定身份** | 写 3 句"它是谁" + 它能推出的行为 | 身份三句 | 能从身份推出至少 3 条具体行为 |
| **3 定能力** | 列"完成职责最少需要的工具/资源"，标只读/副作用/审批 | 能力上界清单 | 少一个就干不了；多一个就是越界 |
| **4 定知识** | 写读集（领域/项目/历史）+ 写域（任务/领域/全局） | 读集/写域 | 能对应到共享层范围；越界可判 |
| **5 定行为** | 写"遇到 X 做 Y"的规则：规划/歧义/失败/停止 | 行为规则集 | 每条可观察、可执行 |
| **6 定边界** | 写禁区 + 必须审批的动作 + 不可碰的数据 | 边界清单 | 每条可程序判定 |
| **7 定接口** | 写输入形态 + 交付物 + 证据 | 输入/输出契约 | 对齐职责验收；下游可消费 |
| **8 定生命周期与协作** | 选一次性/短驻/长驻；声明可委派/汇报关系 | 生命周期 + 协作（可空） | 与职责匹配；协作显式 |

### 3.3 创建后的动作

1. **注册**：进入类型注册表（可枚举、可发现）；
2. **版本化**：`typeId@version`；改类型 = 新版本，旧版本保留；
3. **评审**：按 §6 的检查清单过一遍（设计者不能自己签字，需独立评审）；
4. **试实例化**：用一个真实任务实例化一次，看"类型定义是否够用"；
5. **观察与迭代**：用实例的成功率/成本/质量反推类型是否需要调整（调整 = 新版本）。

### 3.4 反模式（创建类型时最容易犯的错）

| 反模式 | 表现 | 后果 | 替代 |
|---|---|---|---|
| **万能类型** | 一个类型什么都能干 | 边界失效、无法评测、无法治理 | 拆成多个窄类型 + 组合 |
| **类型即提示词** | 类型 = 一段 system prompt | 知识/能力/边界都没定义 | 九要素齐全，提示词只是"行为"的一部分 |
| **类型即工具集** | 类型 = 工具列表 | 身份/职责/边界缺失 | 工具是"能力"的一种，不是全部 |
| **知识塞进类型** | 把领域知识写进类型定义 | 知识过期、类型膨胀 | 知识放共享层，类型只声明读集 |
| **边界缺失** | 只写"要安全"，没有禁区 | 权限无法判定 | 边界具体到动作/资源/条件 |
| **一次一类型** | 每个任务建一个类型 | 类型爆炸、无法复用 | 一次性的用通用类型 + 配置 |

## 4. 类型创建后的生命周期

| 阶段 | 动作 | 规则 |
|---|---|---|
| **设计** | 走 §3 八步 | 产出类型定义草案 |
| **注册** | 进类型注册表 | 类型 id 唯一、可枚举 |
| **版本化** | `typeId@version` | 不可变；改=新版本 |
| **派生** | 组合优先（has-a），继承克制（is-a，≤2 层） | 子类型不得放宽父类型边界；派生显式可查 |
| **使用** | 实例化 | 实例绑定创建时版本 |
| **弃用** | 标记弃用，停止新实例化 | 不删除；旧实例可继续 |
| **归档** | 类型定义 + 历史版本保留 | 可复现、可审计 |

**派生 vs 新建的判据**：如果新类型与旧类型共享"身份/职责"、只是能力/知识/行为不同 → 派生；如果连"是谁、为什么存在"都不同 → 新建。

## 5. 示例：创建一个"后端代码 agent"类型（走八步）

| 步 | 内容 |
|---|---|
| 1 职责 | 负责"修复/实现后端代码变更"，交付"补丁 + 测试证据"，以"测试通过 + 变更范围可控 + 无回归"验收 |
| 2 身份 | 后端工程师；严谨，先复现后修改；不确定时先问而不是猜 |
| 3 能力 | 读写代码、跑测试、git、查文档（只读/副作用/审批已标）；不含部署、不含生产配置 |
| 4 知识 | 读：代码库记忆、团队规范、历史决策；写：任务结论、可复用经验（候选制） |
| 5 行为 | 先复现→定位→最小改动→测试→提交；歧义先问；失败先看日志再重试（≤2 次）；证据不全不停 |
| 6 边界 | 不碰生产配置/敏感数据；改公共接口需审批；不直接合并主干 |
| 7 接口 | 收工作项（目标+验收条件）；产出补丁 + 测试输出 + 影响范围 |
| 8 生命周期 | 短驻（一个工作项）；可委派"测试编写"给测试 agent |

**两次实例化**：任务 A"修复订单创建失败"、任务 B"给订单接口加幂等"——类型相同，输入/快照/草稿/产出不同；类型不因实例改变。

## 6. 创建检查清单（15 条，评审用）

**职责与身份**
- [ ] 能一句话说清"负责什么、交付什么、怎么验收"？
- [ ] 职责窄到"一类任务 + 一种交付物"？
- [ ] 身份能推出至少 3 条具体行为（不是形容词）？

**能力与知识**
- [ ] 能力是"最少必要集"，不是"所有工具"？
- [ ] 能力标了只读/副作用/审批？
- [ ] 知识是"读集/写域"，不是知识本体？
- [ ] 越界读/写可判定？

**行为与边界**
- [ ] 行为规则都是"遇到 X 做 Y"，可观察？
- [ ] 边界每条可程序判定（不是"尽量"）？
- [ ] 高风险动作有"必须经人"的路径？

**接口与生命周期**
- [ ] 输入输出对齐职责的验收标准？
- [ ] 交付物能被下游消费（有证据）？
- [ ] 生命周期与职责匹配（不是默认长驻）？
- [ ] 协作关系显式（或明确不协作）？
- [ ] 会反复实例化（不是一次性的）？

## 7. 与其他原则的接口与待确认

**与其他原则的接口**：

- **多智能体自主协作**（另一会话主题）：本文只留"协作关系"要素；协作协议不在本文；
- **通用框架组件**：见 [32](32-通用Agent框架-v0.md)——类型系统、实例运行时、共享层、调度、安全等组件如何承载九要素；
- **知识/记忆**：类型只声明读集/写域；知识本体由共享层承载（29 的参考实现）。

**待确认**（不阻塞下一步）：

1. 九要素是否要加"价值观/偏好"（我倾向并入"身份"）与"成本画像"（我倾向并入"能力/资源"）？
2. "失败策略"留在"行为"里，还是独立成要素？（我倾向留在行为，避免要素膨胀）
3. 生命周期三策略是否 MVP 全保留？（我倾向先只留"短驻"，另两种作为策略扩展）
4. 创建流程的"评审"由谁做？（设计者/独立评审/用户——取决于组织形态）
