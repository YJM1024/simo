# Agent 框架设计 v0.1 —— 类型与实例

> **定位**：这是 Agent 框架的**第一条核心设计原则：类型与实例**。不是完整框架、不是实现方案、不是技术选型；后续会叠加其他核心原则（多智能体自主协作、安全访问、并发、租户等）。
> **与前序文档的关系**：[29-系统设计方案](29-系统设计方案-v1.md) 的"以记忆为核心"在本稿中**降级为"共享知识层的一种实现策略"**——记忆是状态策略，类型/实例才是骨架。29 不废弃，作为"知识层 + 运行时"的参考实现之一。
> **一句话**：Agent 框架 = **类型系统**（可枚举的 agent 定义）+ **实例运行时**（这一次的执行体）+ **共享层**（知识/工具/边界/租户）+ **调度**（并发与资源）。第一条原则：**类型定义"可能是什么"，实例定义"这一次是什么"**。

---

## 0. 为什么是"类型与实例"，而不是"会话/进程/记忆"

| 若以它为核心 | 会发生什么 |
|---|---|
| **会话** | 会话一删，身份与状态就丢；跨任务/跨渠道无法复用；会话是交互视图，不是 agent 本体 |
| **进程** | 进程是执行体，不可枚举、不可治理；"有哪些 agent"无法回答；扩展只能堆进程 |
| **记忆** | 记忆是"状态怎么存"的策略；它回答"知道什么"，不回答"是什么、能做什么、谁允许"；换场景就要换记忆模型 |
| **类型/实例** | 能回答：**有哪些 agent（可枚举）**、**每个能做什么（能力/边界）**、**这一次是谁在做什么（实例与归因）**、**怎么复用与派生（类型关系）** |

**结论**：类型/实例是"agent 系统的构成论"，记忆/会话/进程是"运行时的实现论"。前者换不掉，后者可以换。

---

## 1. Agent 类型（模板）：一个类型定义什么

一个类型是**设计期产物**，是一套跨实例不变的 agent 定义。九要素：

| # | 要素 | 回答的问题 | 设计时的追问 | 例子（后端代码 agent） |
|---|---|---|---|---|
| 1 | **身份** | 它是谁 | 角色名、人格、语气、立场？ | 后端工程师；严谨，先复现后修改 |
| 2 | **职责** | 它为什么存在 | 负责哪类任务？什么叫"做好了"？ | 修复/实现代码变更，交付可验收补丁 |
| 3 | **能力** | 它能做什么 | 最少需要哪些工具/技能/资源？ | 读写代码、跑测试、git、查文档 |
| 4 | **知识** | 它知道什么 | 读哪些共享知识？写回哪里？ | 代码库记忆、团队规范、历史决策 |
| 5 | **行为** | 它怎么想/做 | 怎么规划？歧义怎么办？失败怎么办？何时停？ | 小步提交；歧义先问；失败先复现 |
| 6 | **边界** | 它不能做什么 | 绝对禁区？哪些动作必须经人？ | 不碰生产配置、不改敏感数据、高风险审批 |
| 7 | **接口** | 它接收/产出什么 | 任务形态？交付物形态？ | 收工作项；产出补丁 + 测试证据 |
| 8 | **生命周期策略** | 它怎么活 | 一任务一实例，还是常驻？ | 短驻：一个工作项一生 |
| 9 | **协作关系**（可选） | 它能找谁 | 可委派给谁？向谁汇报？ | 可委派测试 agent；向秘书汇报 |

**前七条是"设计一个 agent 时真正要回答的问题"**；第 8 条是运行策略；第 9 条留给多智能体协作（另一个会话的主题）。

### 1.1 类型的三个"上界"

类型不是"建议"，是**上界**：

- **能力上界**：实例可用的工具/技能，不能超出类型声明的集合；
- **权限上界**：实例的权限是类型权限的子集，只能收窄，不能放宽；
- **知识读集上界**：实例能读的共享知识范围由类型声明，不能越界。

**为什么是上界而不是"清单"**：上界让"实例按任务裁剪"成为可能（灵活），同时让"越权"有明确的判定依据（可治理）。

### 1.2 类型是可枚举的治理锚点

- 存在**类型注册表**：系统能回答"有哪些 agent 存在"；
- 权限、审计、评测、配额都挂在**类型**上（不是挂在某个实例上）——否则治理无法穷举；
- 没有"野生 agent"：任何实例都必须来自一个已注册类型。

### 1.3 类型是设计产物，改类型 = 新版本

- 类型不可变；修改类型产生**新版本**（`typeId@version`）；
- 旧版本保留（已创建的实例仍引用旧版本，可复现）；
- 弃用是"标记 + 停止新实例化"，不是删除。

## 2. Agent 实例：一个实例是什么

实例是**运行期产物**：类型的一次具体化。

**实例的六个组成**（概念层）：

1. **输入**：这一次的任务/消息/事件；
2. **知识快照**：实例启动时读到的共享知识版本（不是知识本体）；
3. **私有草稿**：这一次的中间状态、试错、未提交结论；
4. **租约与预算**：谁在执行、时限、资源上限；
5. **产出**：交付物、结论、证据；
6. **过程记录**：这次做了什么、为什么（可归因）。

### 2.1 实例的四个"只能"

- **只能收窄**：权限/能力/知识读集只能在类型上界内裁剪；
- **只能读快照**：执行期读的是启动时钉住的知识版本，不被别人写入影响；
- **只能写私有**：公共知识只能通过"提交候选"写回，不能直写；
- **只能被类型创建**：没有"绕过类型直接造实例"的路径。

### 2.2 实例可丢弃

- 实例是消耗品：可以杀、可以重建；
- 任何需要跨实例/跨崩溃保留的东西，必须已在外置层（知识层/事件记录）；
- **"可丢弃"不等于"没有私有状态"**：私有草稿可以存在，但要能解释、能归档、能审计。

### 2.3 实例的归因

每个实例的产出都能回答：**哪个类型、哪个版本、哪个实例、基于什么输入、用了什么能力、留下了什么证据**。这是"类型是可治理锚点"的落地。

## 3. 核心关系：派生（类型→类型）与创建（类型→实例）

这是本稿的核心。两个动词必须分开：

### 3.1 派生：类型 → 类型

**为什么需要派生**：真实场景里 agent 类型有共性——"后端 agent"和"前端 agent"都是"工程师 agent"的特化；"客服 agent"和"售后 agent"共享"服务 agent"的边界。

两种派生方式，**组合优先，继承克制**：

| 方式 | 含义 | 适用 | 代价 |
|---|---|---|---|
| **组合（has-a）** | 类型 = 身份/职责 + 若干**能力包/知识包/边界包** | 大多数情况；能力可复用、可拼装 | 需要维护"包"的目录与兼容性 |
| **继承/特化（is-a）** | 子类型继承父类型，覆盖/收窄/扩展 | 身份与职责确有"是一种"关系时 | 深继承难治理；父类型改动影响面大 |

**派生的硬规则**：

1. 子类型**不得放宽**父类型的权限上界（收窄可以）；
2. 子类型**可以扩展**知识读集与能力集（在租户/场景允许范围内）；
3. 子类型**可以特化**行为（更严格的策略），不得弱化父类型的边界；
4. 派生关系**必须显式、可查**（类型注册表里能看到"谁从谁派生"）；
5. 派生**层级建议 ≤2 层**（父类型 → 特化类型），再深就改用组合。

### 3.2 创建：类型 → 实例

**实例化协议（概念，不是接口）**：

```text
输入到达
  → 匹配：这条输入该由哪个类型处理？（显式指定 / 按职责语义匹配 / 按输入类型路由）
  → 绑定：类型 + 输入 + 知识快照 + 租约/预算
  → 运行：实例按类型定义的行为工作（能力/边界/知识读集约束内）
  → 结束：产出 + 证据；提交候选写回共享层；归档过程记录
  → 归因：typeId@version + instanceId + trace
```

**实例化的三条硬约束**：

1. **必须轻**：实例化只做"绑输入 + 钉快照 + 发租约"，**不复制类型定义、不复制知识本体**——否则"动态快速产生实例"不成立；
2. **必须过类型**：没有类型就没有实例；实例化是类型系统的一部分；
3. **必须可归因**：实例的创建、运行、产出、销毁都留痕。

**实例化失败的语义**：匹配失败（没有类型能处理）→ 拒绝并说明；绑定失败（资源/租约）→ 排队或拒绝；运行失败 → 实例失败，但类型不受影响（类型的"健康度"用实例成功率度量）。

### 3.3 状态归属：三层，不能混

| 层 | 归属 | 内容 | 可变性 | 谁写 |
|---|---|---|---|---|
| **类型层** | 类型定义 | 身份/职责/能力/行为/边界/接口/生命周期策略 | 不可变（改=新版本） | 设计者 |
| **共享层** | 系统/租户/领域 | 知识、工具、边界策略、租户配置 | 可变（有版本/审计） | 知识写者/管理员（实例只能提交候选） |
| **实例层** | 这一次 | 输入、快照、私有草稿、产出、过程记录 | 可变（随实例生灭） | 实例自己 |

**关键**：**知识/记忆属于共享层，不属于类型，也不属于实例**。类型只声明"读集/写域"；实例只持有"快照/草稿"。这是"记忆中心"降级后的正确位置。

### 3.4 生命周期与版本

**类型生命周期**：设计 → 注册 → 版本化 → 使用中 → 弃用（停止新实例化）→ 归档。旧版本永久可查（可复现）。

**实例生命周期**（三种策略，由类型声明 + 场景选择）：

| 策略 | 含义 | 适用 |
|---|---|---|
| **一次性** | 处理完即销毁 | 消息/事件处理；纯任务型 |
| **短驻** | 活一个任务周期 | 有中间状态的任务（默认） |
| **长驻** | 反复领任务，状态延续 | 需要"经验积累/身份连续"的角色 |

**版本绑定**：实例绑定**创建时**的类型版本（可复现）；类型升级不自动影响运行中实例；新实例用新版本。

### 3.5 多实例关系

- **同类型多实例**：并行、独立、共享同一知识层；**彼此不直接对话**（协调靠共享层与合并规则）；
- **父子实例**：父实例可委派子任务给子实例（可选能力，由类型的"协作关系"声明）；
- **跨类型实例**：不直接通信；通过共享层或"协作协议"（留给多智能体会话）。

## 4. 通用元素在类型/实例模型里的位置

Agent 框架肯定要有工具、知识、边界、安全、并发、租户。它们不是并列的"模块"，而是**分布在这三层里**：

| 通用元素 | 类型层 | 共享层 | 实例层 |
|---|---|---|---|
| **工具** | 声明能力包（上界） | 工具注册表/实现 | 按任务选子集，越界拒绝 |
| **知识/记忆** | 声明读集/写域 | 知识库/记忆（有版本/审计） | 快照 + 私有草稿 |
| **边界** | 声明禁区/审批要求 | 租户/场景的边界策略 | 运行时只能收窄 |
| **安全访问** | 权限上界 | 租户隔离、凭据、审计 | 审批、实际访问 |
| **并发** | 资源画像（可选） | 调度器、配额 | 租约/预算 |
| **租户** | 类型归属哪个租户/命名空间 | 租户级知识/工具/配额 | 实例在租户边界内运行 |

**推论**：框架的"通用元素"不是各自独立设计，而是**先定类型/实例骨架，再把每个元素放到对应的层**。这样不会出现"工具单独一套权限、知识单独一套租户"的割裂。

## 5. 核心设计原则（8 条，每条给判定）

| # | 原则 | 判定标准（可检查） |
|---|---|---|
| **P1** | **类型是设计产物，实例是运行产物** | 类型可评审/版本化；实例可创建/销毁；两者不混在同一个对象里 |
| **P2** | **类型定义上界，实例只能收窄** | 任何实例的权限/能力/读集 ⊆ 其类型声明的上界；越界可判定 |
| **P3** | **知识是第三层，不属于类型也不属于实例** | 类型只声明读集/写域；实例只持快照/草稿；知识本体在共享层 |
| **P4** | **实例化必须轻** | 实例化不复制类型定义/知识本体；只绑输入+快照+租约 |
| **P5** | **实例可丢弃，状态必须外置** | 杀实例不丢关键信息；重建可继续；过程可审计 |
| **P6** | **类型可派生/组合，但派生克制** | 派生显式可查；层级 ≤2；组合优先；子类型不放宽父边界 |
| **P7** | **类型是可枚举的治理锚点** | 权限/审计/评测/配额挂类型；无"野生 agent" |
| **P8** | **实例归因到类型版本** | 任何产出可回答"哪个类型版本、哪个实例、基于什么" |

## 6. 四个设计取舍（现在不拍板，先摆代价）

| 问题 | 选项 A | 选项 B | 我的倾向 |
|---|---|---|---|
| **类型该专还是通** | 专：一类任务一类型（好治理、好评测） | 通：一个大类型覆盖多类（好复用、边界模糊） | **专**为主，通用能力用组合包解决 |
| **派生方式** | 继承（is-a） | 组合（has-a） | **组合优先**，继承仅用于身份/职责确有特化 |
| **实例能否临时长能力** | 不能（必须改类型） | 能（实例内扩展，类型不变） | **默认不能**；在类型上界内"选子集"可以 |
| **输入怎么找到类型** | 显式指定 | 语义匹配（按职责描述） | **显式为主 + 语义兜底**；匹配失败要可解释 |

**共同判据**：任何取舍都问一句"坏了能不能查、越界能不能判、换场景要不要改骨架"。答不上来就选更保守的那个。

## 7. 走查：一个类型 + 两次实例化

**类型定义（后端代码 agent）**：

- 身份：后端工程师；严谨、先复现后修改；
- 职责：修复/实现代码变更，交付可验收补丁；
- 能力：读写代码、跑测试、git、查文档（上界）；
- 知识：读"代码库记忆/团队规范/历史决策"（读集）；写回"任务结论/经验"（写域，候选制）；
- 行为：小步提交；歧义先问；失败先复现；
- 边界：不碰生产配置、不改敏感数据、高风险审批；
- 接口：收工作项；产出补丁 + 测试证据；
- 生命周期：短驻（一个工作项）；
- 协作：可委派测试 agent。

**实例 1**：输入"修复订单创建失败"；快照=代码库记忆 v42 + 规范 v7；私有草稿=排查记录；产出=补丁 + 测试证据；结束归档。

**实例 2**：输入"给订单接口加幂等"；快照=代码库记忆 v45（已更新）；私有草稿=方案对比；产出=补丁 + 证据；结束归档。

**观察**：类型完全相同，两次实例的输入、快照、草稿、产出都不同；类型没有因为实例而改变。这就是"类型/实例"要保证的：**类型稳定、实例自由**。

## 8. 与其他核心原则的接口（留白）

- **多智能体自主协作**（另一会话主题）：实例之间的协作、委派、协商、团队——本稿只留"协作关系"要素与"父子实例"接口，不设计协议；
- **安全访问**：类型权限上界 + 共享层租户隔离 + 实例审批；具体机制另立；
- **并发/租户**：调度与隔离在"实例运行时"层；类型层只声明资源画像与归属；
- **评测**：以类型为锚点做"类型级评测"（这个类型的实例成功率/成本/质量），实例级做回归。
