# 核心设计原则方案 v1.1 —— 智能体类型：要素与创建

> **定位**：Agent 框架的**第一条核心设计原则**。回答两个问题：**一个智能体类型应该包含哪些元素？想创建一个智能体类型，应该怎么做？**
> **不是**实现方案、技术选型、接口设计；是"设计一个 agent 时该想清楚什么、按什么顺序想、怎么判断想清楚了"。
> **v1.1（2026-11-21）**：依据 [39-类型库-验证结论](39-类型库-验证结论-v1.md) 的 R1–R12 修订。78 个真实类型的验证结论是：**九要素骨架成立，但表达力不足**——不新增第十要素，全部缺口用"要素内子属性 + 创建前置"解决。v1 保留不动。
> **与既有文档的关系**：[30-类型与实例](30-Agent框架-类型与实例-v0.md) 是讨论稿；[31 v1](31-核心设计原则-智能体类型-v1.md) 是本方案的上一版；[29-系统设计方案](29-系统设计方案-v1.md) 的"记忆中心"降级为"知识层的实现策略"；[32-通用 Agent 框架](32-通用Agent框架-v0.md) 是系统视角（组件），本文是类型视角（怎么设计一个 agent）。

## 0. 一句话与阅读指南

**一句话**：智能体类型是**设计产物**，它用九个要素回答"这个 agent 是谁、为什么存在、能做什么、知道什么、怎么干、不能干什么、怎么交互、怎么活、和谁协作"；**每个要素再带若干子属性**，把"答得出来"升级为"答得可判定"；创建类型就是按顺序把这九个问题答完、子属性填满，并接受一组检查。

**v1.1 的核心变化**（先看这四条就够）：

1. **要素不变，属性补齐**：九要素一个不加；补 6 组子属性（决策权、能力五维、读集四属性、边界判定方式、验收分型、状态外化）。原则是"不新增第十要素，只用现有要素装得更细"。
2. **可判定要分级**：边界与验收都从"能写"升级为"按判定方式分级，并写明误判方向与代价"——承认近似判定，比假装精确更严谨。
3. **生命周期补档位与状态规则**：三档 → **四档**（一次性/短驻/长驻/周期批处理），长驻必须声明状态外化与交接。
4. **派生收紧**：判据从"身份/职责不同"改为"**身份/职责/边界任一不同即新建**"，派生只允许收紧边界、不得扩能力、不得剥夺能力。

阅读顺序：§1 原则 → §2 九要素（含子属性）→ §3 创建流程（本文重点）→ §4 生命周期与派生 → §5 示例 → §6 检查清单（按生命周期分型）→ §7 接口与已决策事项。

## 1. 原则：类型是设计产物，实例是运行产物

- **类型**：跨实例不变的 agent 定义；可评审、可版本化、可复用、可枚举。
- **实例**：类型的一次具体化；带输入、快照、私有草稿、租约、产出；可丢弃、可重建。
- **分界判据**：问"换个任务，它变不变？"——不变的是类型，变的是实例。
- **推论**：设计一个 agent，本质是**设计一个类型**，而不是"写一段提示词"或"配一个工具集"。

**v1.1 新增的三条原则**：

- **P9 属性化而非扩张**：九要素是骨架，不够的地方用子属性补。新增顶层要素的代价是每份类型定义都要多填一栏、每个组件都要多承载一层，收益却只有局部；**加属性的边际成本远低于加要素**。唯一例外是"授权上下文"——它不是类型的本体属性，而是创建前置（见步 0）。
- **P10 可判定分级**：任何"边界可判定 / 验收可判定"的声明都必须标注**判定方式**与**误判方向**。写成"程序高可信"就必须有检测点；是近似判定就明说会漏放还是误拦、代价多大。**假装严格比承认近似更危险**。
- **P11 类型 ≠ 角色/流程节点**：一个类型承担一个角色；互斥角色（既评审又实现）、流程节点（人机双签）不能塞进一个类型，用**组合**（阶段状态机 + 多个类型 + 人）解决。类型定义里出现"同时负责 A 和 B（A 与 B 冲突）"，就是类型设计失败的信号。

## 2. 一个智能体类型包含什么（九要素 + 子属性）

> 每个要素给：**定义 / 设计时要回答的问题 / 子属性（v1.1 新增） / 判定标准 / 常见反例**。
> 子属性不是必填全部：标"必填"的必须填；标"条件必填"的按条件填；标"可选"的允许留空但要在检查时说明理由。

### 2.1 身份（Identity）

- **定义**：这个 agent 是谁——角色名、人格、语气、立场。
- **要回答**：它以什么姿态工作？遇到冲突时站在哪边？它"像谁"？
- **子属性**：
  | 子属性 | 必填性 | 说明 |
  |---|---|---|
  | 角色名 | 必填 | 一个名词短语，如"后端代码审查者" |
  | 人格/语气 | 必填 | 3 句话内能约束行为 |
  | 立场 | 必填 | 冲突时倾向哪一方（保守/激进/中立；成本优先/质量优先） |
  | 价值取舍顺序 | 可选 | 多个目标冲突时的排序，如"正确性 > 交付速度 > 成本"。**价值观并入身份，不单设要素**（用户已拍板） |
- **判定**：能用 3 句话说清"它是谁"，且这三句话能约束行为（不是形容词堆砌）；立场能推出至少 2 个具体决策。
- **反例**："你是一个专业的助手"——没有约束力；身份必须能推出具体行为。

### 2.2 职责（Purpose）

- **定义**：它为什么存在——负责哪类任务、边界内交付什么、什么叫"做好了"。
- **要回答**：它只做什么？不做什么？成功标准是什么？**它的结论在什么范围内成立？**
- **子属性**：
  | 子属性 | 必填性 | 取值 | 说明 |
  |---|---|---|---|
  | 任务类 | 必填 | 一句话 | "一类任务 + 一种交付物"，窄到可枚举 |
  | 交付物 | 必填 | 名词 | 可验收的产物（补丁/报告/结论/清单） |
  | 验收口径 | 必填 | 一句话 | 与 §2.7 验收类型配套 |
  | **决策权** | 必填 | **建议 / 共决 / 执行** | 建议=只出方案不执行；共决=需与人或他人共同签署；执行=边界内自主执行 |
  | **适用域** | 条件必填 | 地区/期间/主体/交易结构/前置条件 | 结论只在某个范围内成立；写"全域"必须给理由（如纯通用知识） |
- **判定**：职责能用"负责 X，交付 Y，以 Z 为验收，决策权=W，适用域=V"表述；Y 可验收；**决策权与能力、边界一致**（决策权=执行却无副作用能力 → 矛盾；决策权=建议却有写权限 → 越权）。
- **反例**："负责后端开发"——太宽；职责必须窄到"一类任务 + 一种交付物"。决策权缺失的反例：红队类型不写"建议"，读者会以为它可以自主打穿系统。

### 2.3 能力（Capabilities）

- **定义**：它完成任务所需的工具、技能、资源（**上界**，不是清单）。
- **要回答**：最少需要哪些工具？这些工具**能造成多大影响、能不能撤销、花多少钱、作用在哪个范围、在哪个环境执行**？
- **子属性**（每个工具/能力都要标：读写性质 + **五维**必填）：
  | 子属性 | 取值 | 用途 |
  |---|---|---|
  | 读写性质 | 只读 / 副作用 / 审批 | 原有标注保留 |
  | **影响面** | 无副作用 / 局部（单资源）/ 广泛（跨系统/对外） | 决定审批级别与隔离要求 |
  | **可逆性** | 可回滚 / 可补偿 / 不可逆 | **不可逆 = 必须审批**（硬规则） |
  | **成本** | 低 / 中 / 高（或具体量级：token/时长/金额） | 决定配额、熔断、并发上限 |
  | **作用域** | 实例内 / 项目内 / 全局 | 能力能作用到哪一层 |
  | **环境** | 只读样本 / 沙箱 / 预发 / 生产 | 允许在哪个环境执行 |
- **判定**：能力集能覆盖职责；说清"少了哪个就干不了"；**每个能力五维（读写性质 + 影响面/可逆性/成本/作用域/环境）填满**；不可逆能力有对应审批路径。
- **反例**：把"所有工具"都给它——能力越界，治理失效。只标"副作用"不标可逆性——无法决定审批强度。

### 2.4 知识（Knowledge）

- **定义**：它需要读哪些共享知识、往哪里写回（**读集/写域，不是知识本体**）。
- **要回答**：读哪些领域/项目/历史？读的**是哪一版、会不会过期、多大权威、能存多久**？写回哪一层、谁可读、哪些禁止写？
- **子属性**（每个读集项都要标，四项必填）：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | 范围 | 领域/项目/历史/外部源 | 读什么 |
  | **版本** | 固定版本号 / 最新 / 任务开始时快照 | 决定可复现性 |
  | **时效** | 永久 / 30 天 / 本任务周期 / 显式过期时间 | 过期后如何处理（重新取/标记失效） |
  | **权威级别** | 权威（以此为准）/ 参考（可被覆盖）/ 候选（未确认） | 权威项冲突时必须上报，不得自动裁决 |
  | **驻留范围** | 本实例 / 同类型实例 / 全局 | 读到的内容能存到哪、谁能再读 |
- **写域子属性**：层级（任务/领域/全局）、驻留范围、**是否禁止写**（如"只读类型：写域=禁止写"）。
- **判定**：读集/写域能对应到共享层的具体范围；越界可判定；**权威级别为"权威"的项与现有知识冲突时必须走争议路径**（对应 [24](../design/24-记忆模型-v0.3.md) Q3 的 disputed，不自动裁决）。
- **反例**：把知识写进提示词——知识会过期、会膨胀；知识必须在共享层，类型只声明范围。只写"读规则库"不写版本——规则改版后同一任务结果不可复现。

### 2.5 行为（Behavior）

- **定义**：它怎么想、怎么做——决策风格、规划方式、歧义处理、失败处理、停止条件。
- **要回答**：先规划还是边做边看？不确定时问还是猜？失败了重试还是上报？什么时候停？
- **子属性**（每组至少 1 条，写成"遇到 X 做 Y"）：
  | 组 | 示例 |
  |---|---|
  | 规划 | 先出计划再执行；计划变更需记录 |
  | 歧义 | 歧义影响验收时先问；不影响时按最保守假设并标记 |
  | 失败 | 失败先看日志/证据再重试（≤N 次）；连续失败上报 |
  | 停止 | 满足验收条件即停；**不追超出职责的"更好"** |
- **判定**：每条行为规则能对应一个可观察的动作或决策点。**失败策略留在行为里，不单设要素**（v1 决策，v1.1 保留）。
- **反例**："要聪明地工作"——不可观察；行为必须落到"遇到 X 时做 Y"。

### 2.6 边界（Boundaries）

- **定义**：它不能做什么——禁区、必须经人的动作、不可越过的范围（**上界**）。
- **要回答**：绝对禁区是什么？哪些动作必须审批？哪些数据不能碰？**这条边界靠什么判、判错了会怎样？**
- **子属性**（每条边界都要标）：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | **判定方式** | 程序高可信 / 近似判定 / 人工 / 环境化 | 见下表 |
  | **粒度** | 动作级 / 环境级 | 动作级=禁某个动作；环境级=整体隔离（如只读副本、沙箱） |
  | **误判方向** | 漏放（该拦未拦）/ 误拦（不该拦拦了）+ 代价 | 判定方式不是"程序高可信"时必填 |
  | 触发条件 | 动作 / 资源 / 数据范围 / 条件 | 与 v1 的"写成不+动作/资源/条件"一致 |
- **判定方式分级**（v1.1 核心新增）：
  | 判定方式 | 定义 | 要求 | 典型场景 |
  |---|---|---|---|
  | 程序高可信 | 规则/检测能直接判，几乎不误判 | 写明检测点（在哪拦、拦什么） | 禁写生产库、禁发外部邮件 |
  | 近似判定 | 有检测但会误判 | 写误判方向 + 代价 + 缓解 | 语义不变检测、GMV 承诺、关键词密度 |
  | 人工 | 判定标准需人判断 | 写判定人 + 时效 | 法务结论、医疗建议 |
  | 环境化 | 动作空间开放，无法事前判 | **隔离/配额/审批/审计四件套**至少三件 | 红队、开放探索、高危运维 |
- **判定**：每条边界必须标一种判定方式；"程序高可信"是首选但**不得把近似判定写成程序高可信**；环境化边界必须落四件套。能力中的"不可逆"动作必须出现在边界里（成对约束）。
- **反例**：只写"注意安全"——边界必须具体到动作/资源/条件。把"不推断受保护特征"写成程序高可信——实际是概率防护，必须标近似。

### 2.7 接口（Interface）

- **定义**：它接收什么形态的任务、产出什么形态的交付物、**证据是什么、验收在什么时候做**。
- **要回答**：输入是消息/工作项/事件？输出是文本/补丁/报告/文件？验收证据是什么？**交付时就能验，还是过一段时间才知道对错？**
- **子属性**：
  | 子属性 | 必填性 | 取值 | 说明 |
  |---|---|---|---|
  | 输入形态 | 必填 | 消息/工作项/事件/文件 | 与实例绑定方式对齐 |
  | 输出形态 | 必填 | 文本/补丁/数据集/报告/文件/动作 | 下游可消费 |
  | 证据 | 必填 | 证据清单 + 证据在哪 | 见验收类型 |
  | **验收类型** | 必填 | **交付时 / 效果后 / 过程型** | 见下表 |
  | 回访时点与判定人 | 条件必填 | 效果后验收必填 | 什么时候看、谁看 |
  | **适用域** | 条件必填 | 同职责 | 输出结论的成立范围 |
- **验收分型**（v1.1 核心新增）：
  | 验收类型 | 定义 | 证据要求 | 典型场景 |
  |---|---|---|---|
  | 交付时 | 交付即可验 | 证据在交付物内（测试报告/对比表/引用） | 代码补丁、翻译、数据清洗 |
  | 效果后 | 交付后一段时间才能验 | 交付物 + **回访时点 + 判定人 + 判定指标** | 营销文案、投放、招聘、培训 |
  | 过程型 | 结果不可完全验，验过程 | 结构完整 + 来源可追 + 预算未超 | 创意、探索、红队、开放调研 |
- **判定**：验收类型必须选一种；效果后必须写时点与判定人；过程型不得声称"结果可验"。
- **反例**：输入输出不定——实例化时无法匹配、无法验收。创意类硬写"点击率提升 20%"作为交付时验收——验不了，等于没有验收。

### 2.8 生命周期策略（Lifecycle Policy）

- **定义**：它怎么活——**档位**、状态怎么存、什么时候交接、什么时候退休。
- **要回答**：处理完就销毁？活一个任务周期？反复领任务？按周期重算？**它必须记住的东西放在哪、活多久、谁能读？**
- **子属性**：
  | 子属性 | 必填性 | 取值 | 说明 |
  |---|---|---|---|
  | **档位** | 必填 | **一次性 / 短驻 / 长驻 / 周期批处理** | 见下表 |
  | 有效期 | 条件必填 | 发布窗口结束/截止日 | 长驻的"有界长驻"用它表达（不单设第五档） |
  | **状态外化** | 条件必填 | 位置 / 保留期 / 读权限（本实例/同类型/全局） | 长驻、周期批处理必填 |
  | **交接条件** | 条件必填 | 交给谁、交什么状态 | 长驻替代"停止条件" |
  | 续期/退休 | 条件必填 | 续期审批人、退休时状态归档 | 长驻必填 |
  | 实例寿命 vs 业务周期 | 必填 | 两个时间分开写 | 实例寿命=租约/超时；业务周期=任务本身跨度 |
- **档位定义**（v1.1 新增第四档）：
  | 档位 | 定义 | 状态要求 | 典型场景 |
  |---|---|---|---|
  | 一次性 | 一任务一实例，完成即销毁 | 无需外化 | 咨询、单次分析、翻译 |
  | 短驻 | 一个工作周期内复用（多轮/多任务） | 私有草稿可存于实例，跨实例需外化 | 修代码、评审、跟单 |
  | 长驻 | 跨周期持续存在（值班/监控/陪伴） | **必须状态外化 + 交接 + 续期** | 值班响应、舆情监控、日程助理 |
  | 周期批处理 | 按固定周期唤起、跑完即退 | 必须幂等键 + 上轮结果外化 | 每日库存重算、周报生成、定时巡检 |
- **判定**：档位有理由；长驻必须写状态外化/交接/续期；周期批处理必须写周期与幂等键；有界长驻用"有效期"表达而不是新档位。
- **反例**：所有类型都默认长驻——资源浪费、状态腐坏。长驻实例把"经验"留在实例内存里——实例一回收经验就没了，与"实例可丢弃"直接矛盾。

### 2.9 协作关系（Collaboration，可选）

- **定义**：它和谁一起工作——可委派给谁、向谁汇报、**是否必须有人参与、明确不和谁协作**。
- **要回答**：哪些子任务可委派？向谁交付？谁可以向它委派？**哪些动作必须人确认或人机双签？**
- **子属性**：
  | 子属性 | 取值 | 说明 |
  |---|---|---|
  | 可委派 | 类型 id 列表 | 把子任务交给谁 |
  | 被委派 | 类型 id 列表 | 谁可以把子任务交给它 |
  | 汇报 | 类型 id / 角色 | 结果交给谁 |
  | **人** | 需人确认 / 人机双签 / 人只被告知 | 关键动作的人介入方式 |
  | **禁止协作** | 类型 id / 角色 或"无" | 明确不协作对象（如合规要求下不得与某类 agent 共享上下文） |
- **判定**：协作关系显式声明；不声明 = 不协作（默认隔离）；**"人"档必填**（没有人的介入方式的类型，等于默认无人工关口，必须写"人只被告知"并说明理由）。
- **反例**：隐式协作（"它知道该找谁"）——不可治理；协作必须显式。红队类型不写"人机双签"——边界只能环境化，风险不可控。

### 2.10 要素之间的约束

- **必须成对定义的**：
  | 成对 | 缺了会怎样 |
  |---|---|
  | 职责 ↔ 接口 | 无法验收（职责说"交付 Y"，接口没说 Y 长什么样） |
  | 能力 ↔ 边界 | 能力无约束（有写权限却没写边界 = 越权） |
  | 知识读集 ↔ 写域 | 只读不写（经验无法沉淀）/ 只写不读（重复劳动） |
  | **验收类型 ↔ 交付物形态** | 效果后验收却只给"交付即验"的证据 = 没有验收 |
  | **状态外化 ↔ 生命周期档位** | 长驻却无状态外化 = 状态随实例蒸发 |
  | **能力不可逆 ↔ 边界必须审批** | 不可逆动作无审批 = 高危裸奔 |
- **互斥/冲突的**：职责越宽，身份/行为越难具体；能力越多，边界越难判定；**决策权=执行**与**影响面=广泛+不可逆**同时出现时，必须有分级授权或人工双签。**宁可窄，不要宽**。
- **可选的**：协作关系（不声明即不协作）；适用域（无则写"全域"并给理由）；价值排序。
- **证据链约束（v1.1 新增）**：任何"做好了"的声明都必须有证据位——交付时验收的证据在接口里，效果后验收的证据是回访指标，过程型验收的证据是过程记录。**没有证据位的验收标准等于没有标准**。

## 3. 怎么创建一个智能体类型（创建流程）

### 3.1 什么时候需要新类型

先判断"能不能复用现有类型"：

1. 现有类型的职责能覆盖 → **复用**（实例化，不建新类型）；
2. 职责相近、**边界不同**（判定方式/权限/合规要求）→ **新建**（不是派生）；
3. 职责相近、边界只是收紧、能力不扩不剥夺 → **派生**（见 §4，需满足三条规则）；
4. 需要互斥角色或多个能力组合 → **组合**（用多个类型 + 人 + 状态机，不建"万能类型"）；
5. 只出现一次 → **不建类型**，用通用类型 + 一次性配置（避免类型爆炸）。

**判据（v1.1 收紧）**：新类型必须是"会反复实例化的稳定职责"；一次性的东西不配拥有类型；**身份/职责/边界任一不同就新建，不能拿"派生"当借口**（78 型里 4 条派生有 3 条该改判新建）。

### 3.2 创建流程："八步创建法 v1.1"（步数不变，插入前置与迭代）

> 名称保留"八步"以免与既有文档/类型库断链；实际动作 = **步 0 前提 → 1 职责 → 1.5 证据形态 → 2 身份 → 3 能力 → 4 知识 → 5 行为 → 6 边界 → 7 接口 → 8 生命周期与协作**。其中 3↔6 可迭代、生命周期与职责同步。

| 步 | 动作 | 产出（概念层） | 完成判据 |
|---|---|---|---|
| **0 确认前提** | 确认**授权上下文**（谁授权、授权范围、有效期）、**预算**（token/时长/金额）、**隔离环境**（沙箱/只读副本/生产）、**是否组合**（是否需要多类型/人机协作） | 前提清单 | 无授权不许创建（尤其红队/越狱/高合规）；无预算上限不许写职责 |
| **1 定职责** | 写"负责 X，交付 Y，以 Z 验收"，**+决策权 +适用域** | 一句话职责 + 决策权 + 适用域 + 验收口径 | Y 可验收、Z 可判定；决策权与能力/边界一致 |
| **1.5 定证据形态** | 决定验收类型：交付时/效果后/过程型；效果后写回访时点与判定人 | 验收类型 + 证据清单 | 证据能在对应时点获得 |
| **2 定身份** | 写 3 句"它是谁" + 立场 + 价值取舍顺序 | 身份三句 | 能从身份推出至少 3 条具体行为 |
| **3 定能力** | 列"完成职责最少需要的工具/资源"，每个标**读写性质 + 影响面 + 可逆性 + 成本 + 作用域 + 环境** | 能力上界清单 | 少一个就干不了；多一个就是越界；四维填满 |
| **4 定知识** | 写读集（每项带**版本/时效/权威级别/驻留范围**）+ 写域（层级/驻留范围/是否禁止写） | 读集/写域 | 能对应到共享层范围；越界可判；权威冲突有出路 |
| **5 定行为** | 写"遇到 X 做 Y"的规则：规划/歧义/失败/停止 | 行为规则集 | 每条可观察、可执行 |
| **6 定边界** | 写禁区 + 必须审批的动作 + 不可碰的数据；每条标**判定方式 + 粒度 + 误判方向** | 边界清单 | 每条有判定方式；不可逆动作有审批 |
| **7 定接口** | 写输入形态 + 输出形态 + 证据 + **验收类型**（1.5 已定，此处落成具体证据）+ 适用域 | 输入/输出契约 | 对齐职责验收；下游可消费；证据可取得 |
| **8 定生命周期与协作** | 选**档位**（一次性/短驻/长驻/周期批处理）+ 状态外化 + 交接/续期 + 协作（含"人"与"禁止协作"） | 生命周期 + 协作 | 与职责匹配；长驻有状态外化；协作显式 |

**四条流程调整（v1.1 的 H2 结论）**：

1. **步 0 不能省**：L 域 6 个边界案例全部需要；T073 无授权书不成立，T077 无资源上限无法写职责。
2. **证据形态前置到 1.5 步**：36 文件 19 个类型里 8 个在写验收标准时被迫先想证据——那就把"想证据"提到前面。
3. **3 ↔ 6 允许迭代**：T010（安装依赖）、T045（沙箱试跑）都是"加能力立刻产生边界义务"。写能力时发现新边界，回头补；写边界时发现能力不够，回头加。**迭代不是失败，是正常路径**。
4. **生命周期与职责同步**：职责（连续性）决定档位；第 1 步定职责时就先定档位候选，第 8 步细化。**不要把生命周期放到最后**（38 文件 12/20 在最后一步卡住）。

### 3.3 创建后的动作

1. **注册**：进入类型注册表（可枚举、可发现）；
2. **版本化**：`typeId@version`；改类型 = 新版本，旧版本保留；
3. **评审**：按 §6 的检查清单过一遍（**设计者不能自签**，需独立评审；见 §7 已决策事项 D4）；
4. **试实例化**：用一个真实任务实例化一次，看"类型定义是否够用"；
5. **观察与迭代**：用实例的成功率/成本/质量反推类型是否需要调整（调整 = 新版本）。

### 3.4 反模式（创建类型时最容易犯的错）

| 反模式 | 表现 | 后果 | 替代 |
|---|---|---|---|
| **万能类型** | 一个类型什么都能干 | 边界失效、无法评测、无法治理 | 拆成多个窄类型 + 组合 |
| **类型即提示词** | 类型 = 一段 system prompt | 知识/能力/边界都没定义 | 九要素 + 子属性齐全，提示词只是"行为"的一部分 |
| **类型即工具集** | 类型 = 工具列表 | 身份/职责/边界缺失 | 工具是"能力"的一种，不是全部 |
| **知识塞进类型** | 把领域知识写进类型定义 | 知识过期、类型膨胀 | 知识放共享层，类型只声明读集 |
| **边界缺失** | 只写"要安全"，没有禁区 | 权限无法判定 | 边界具体到动作/资源/条件 |
| **一次一类型** | 每个任务建一个类型 | 类型爆炸、无法复用 | 一次性的用通用类型 + 配置 |
| **派生滥用**（v1.1 新增） | 共享风格/输出结构就标"派生" | 语义漂移、能力被误扩 | 派生三规则（§4）；不满足就新建 |
| **假边界**（v1.1 新增） | 动作空间开放却写"可程序判定" | 评审误放行、风险不可控 | 标"环境化"+ 隔离/配额/审批/审计 |
| **假验收**（v1.1 新增） | 效果类硬写"点击率提升 20%" | 验收永远不通过或永远不查 | 选"效果后/过程型"+ 回访时点与判定人 |

## 4. 类型生命周期、派生与组合

### 4.1 类型自身的生命周期

| 阶段 | 动作 | 规则 |
|---|---|---|
| **设计** | 走 §3 流程 | 产出类型定义草案 |
| **注册** | 进类型注册表 | 类型 id 唯一、可枚举 |
| **版本化** | `typeId@version` | 不可变；改=新版本 |
| **使用** | 实例化 | 实例绑定创建时版本 |
| **弃用** | 标记弃用，停止新实例化 | 不删除；旧实例可继续 |
| **归档** | 类型定义 + 历史版本保留 | 可复现、可审计 |

### 4.2 派生规则（v1.1 收紧，R7；按用户拍板修正为"可扩能力"）

**派生必须同时满足三条**：

1. **必须共享职责**：身份、职责与父类型一致（职责可窄化但不可换向）。**职责换向（评审代码 → 评审架构、写稿 → 检稿）不是派生，是新建**——这是 T008/T025/T031 改判新建的真实理由，不是"派生不能扩能力"。
2. **能力可以扩展，但必须配套**：子类型**允许扩展能力与知识读集**（用户 m00918 已拍板"子类型能扩展能力和数据集，由类型本身决定"）。扩展不是自由的：每个新增能力必须带完整五维（影响面/可逆性/成本/作用域/环境），新增的不可逆/广泛影响能力必须同步新增审批边界，并说明"新能力为什么不能由父类型覆盖"。
3. **既有边界不得放宽**：父类型已有的禁区不能删、不能弱化；新增能力带来的新边界必须显式声明。**边界"换维"（判定方式/权限/合规要求不同，如成人 vs 未成年人）→ 新建，不是派生**。

**派生 vs 新建的升级判据**：

| 关系 | 判据 | 结论 |
|---|---|---|
| 复用 | 身份/职责/边界/能力都覆盖 | 实例化，不建类型 |
| 派生 | 共享身份+职责，既有边界不放宽，能力可扩但每个新能力带五维+新边界声明 | 派生（≤2 层） |
| 新建 | **身份/职责/边界任一不同**（含"边界差异"：判定方式/权限/合规要求不同；含**职责换向**） | 新建 |
| 组合 | 需要互斥角色或多能力组合 | 用多个类型 + 人 + 状态机（has-a） |

**边界差异维（v1.1 新增）**：两个类型身份职责同构，但**边界不同**（如 T054 成人培训 vs T056 未成年人辅导，合规要求不同）→ 必须分开建。派生只处理"边界收紧"，不处理"边界类型不同"。

### 4.3 组合优先

互斥角色（既评审又实现）、流程节点（人机双签）、多能力协同（调研+写作+校对）**一律用组合**：

- **组合件** = 多个类型实例 + 人 + 阶段状态机（谁在什么阶段做什么、交接条件是什么）；
- 组合件本身**不是类型**（不进类型库，不参与实例化路由）；
- 典型：T075 双重身份 = 实现者实例 + 评审者实例 + 阶段状态机；T078 人机双签 = 签署类型 + 人 + 双签状态机。

## 5. 示例：创建一个"后端代码 agent"类型（走八步 v1.1）

| 步 | 内容 |
|---|---|
| **0 前提** | 授权：项目仓库写权限（有效期=工作项周期）；预算：单任务 ≤ 200k token / 2 小时；环境：沙箱（代码）+ 预发（部署验证，需审批）；组合：否 |
| **1 职责** | 负责"修复/实现后端代码变更"，交付"补丁 + 测试证据"，以"测试通过 + 变更范围可控 + 无回归"验收；**决策权=执行**（边界内自主改代码，合并主干需审批）；**适用域=本仓库当前分支，不含架构级重构** |
| **1.5 证据** | **验收类型=交付时**；证据=测试报告 + 变更 diff + 影响范围分析 |
| **2 身份** | 后端工程师；严谨，先复现后修改；不确定时先问而不是猜；价值顺序：正确性 > 可维护 > 速度 |
| **3 能力** | 读代码（只读/影响面局部/全局作用域）、跑测试（局部/可回滚/低成本）、git 提交（局部/可回滚/中成本/项目内/沙箱+预发）、部署（**广泛/不可逆/高成本/生产/需审批**）；不含生产配置 |
| **4 知识** | 读：代码库记忆（v 快照/本任务周期/参考/项目内）、团队规范（最新/永久/权威/全局）、历史决策（最新/30 天/参考/项目内）；写：任务结论（任务层/项目内/可写）、可复用经验（领域层/全局/候选制，需评审） |
| **5 行为** | 先复现→定位→最小改动→测试→提交；歧义影响验收先问；失败先看日志再重试（≤2 次）；测试不全不停 |
| **6 边界** | 不碰生产配置（程序高可信：预发环境隔离）；不碰敏感数据（程序高可信：数据访问白名单）；改公共接口需审批（程序高可信：CI 门禁）；不直接合并主干（程序高可信：合并权限）；**不可逆部署动作 → 人工审批**（环境化：预发先行） |
| **7 接口** | 输入：工作项（目标+验收条件+仓库范围）；输出：补丁 + 测试报告 + 影响范围；证据：测试通过记录、diff、回归对比；**验收类型=交付时**；适用域=本仓库当前分支 |
| **8 生命周期与协作** | **短驻**（一个工作项周期）；状态外化：任务草稿存任务层、保留 30 天、同类型可读；协作：可委派"测试编写"给测试 agent，向项目负责人汇报，**人=改公共接口/合并时需人确认**，禁止协作=无 |

**两次实例化**：任务 A"修复订单创建失败"、任务 B"给订单接口加幂等"——类型相同，输入/快照/草稿/产出不同；类型不因实例改变。

**与 v1 的差异**：v1 示例缺决策权、能力五维、读集版本/时效/权威、边界判定方式、验收类型、状态外化——这些在 v1.1 里全部补齐，且每一格都能回答"怎么判、判错了怎样"。

## 6. 创建检查清单（v1.1，按生命周期分型）

### 6.1 通用（所有类型，20 条）

**前提与职责**
- [ ] 步 0 前提是否齐（授权/预算/隔离环境/是否组合）？
- [ ] 能一句话说清"负责什么、交付什么、怎么验收"？
- [ ] 职责窄到"一类任务 + 一种交付物"？
- [ ] **决策权**填了（建议/共决/执行）？与能力、边界一致？
- [ ] **适用域**填了（或写"全域"+理由）？

**身份、能力、知识**
- [ ] 身份能推出至少 3 条具体行为（不是形容词）？
- [ ] 能力是"最少必要集"，不是"所有工具"？
- [ ] 每个能力五维填满（影响面/可逆性/成本/作用域/环境）？
- [ ] 有不可逆能力时，边界里有对应审批？
- [ ] 知识是"读集/写域"，不是知识本体？
- [ ] 读集每项带版本/时效/权威级别/驻留范围？
- [ ] 权威级知识冲突有上报路径（不自动裁决）？

**行为与边界**
- [ ] 行为规则都是"遇到 X 做 Y"，可观察？
- [ ] 每条边界有判定方式（程序高可信/近似/人工/环境化）？
- [ ] 近似判定写了误判方向与代价？
- [ ] 环境化边界有隔离/配额/审批/审计（≥3 件）？
- [ ] 高风险动作有"必须经人"的路径？

**接口与生命周期**
- [ ] 输入输出对齐职责的验收标准？
- [ ] **验收类型**选了（交付时/效果后/过程型）？效果后写了时点与判定人？
- [ ] 生命周期档位与职责匹配（不是默认长驻）？
- [ ] 协作关系显式（含"人"档与"禁止协作"）？

### 6.2 长驻附加（4 条）

- [ ] 状态外化位置/保留期/读权限写了？
- [ ] 交接条件写了（替代"停止条件"）？
- [ ] 续期审批人与退休归档写了？
- [ ] 实例寿命与业务周期分开写？

### 6.3 周期批处理附加（2 条）

- [ ] 周期与触发方式写了（每日/每周/事件）？
- [ ] 幂等键写了（重跑不重复执行副作用）？

### 6.4 效果后验收附加（2 条）

- [ ] 回访时点、判定人、判定指标都写了？
- [ ] 效果不达预期时的处置路径写了（回滚/补偿/升级）？

**评审规则**：以上条目由**独立评审**过一遍；设计者不得给自己的类型签字（与工作区 SDD 的"不得自签"一致）。

## 7. 与其他原则的接口、已决策事项与未决

### 7.1 与其他原则的接口

- **多智能体自主协作**（另一会话主题）：本文只留"协作关系"要素与"人"档；协作协议不在本文；组合件见 §4.3；
- **通用框架组件**：见 [32](32-通用Agent框架-v0.md)——类型系统、实例运行时、共享层、调度、安全等组件如何承载九要素与子属性（33 v1.1 已按此补字段与功能）；
- **知识/记忆**：类型只声明读集/写域及其属性；知识本体由共享层承载（29 的参考实现），冲突语义见 [24](../design/24-记忆模型-v0.3.md) Q3。

### 7.2 已决策事项（v1 的 4 个待确认 + 39 的 6 个未决，v1.1 全部落定）

| # | 事项 | 决策 | 理由 |
|---|---|---|---|

| D2 | 失败策略是否独立成要素 | **不独立**，留在行为 | 避免要素膨胀；行为五组已覆盖 |
