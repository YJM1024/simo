# 类型库 · 验证结论 v1

> **性质**：第二步"模拟验证"的汇总结论。证据来自四份类型库（[35 研发与算法](35-类型库-研发与算法.md) 18 型、[36 产品与内容](36-类型库-产品与内容.md) 19 型、[37 业务与服务](37-类型库-业务与服务.md) 21 型、[38 专业与边界案例](38-类型库-专业与边界案例.md) 20 型），合计 **78 个类型**，全部按 [34](archive/34-类型库-模板与总览.md) §2 标准格式、[31](archive/31-核心设计原则-智能体类型-v1.md) 八步法写出。
> **用途**：回答"九要素与八步法到底成不成立、哪里要修"；为 31/33/34 的修订提供证据。
> **一个前置原则（用户已拍板）**：**不新增第十要素**。所有缺口优先用"现有要素的子字段/属性"承载；确实无法归属的（授权上下文）作为**创建前置输入**，不进要素表。

---

## 0. 摘要（先结论）

**总判定**：**九要素与八步法成立**——78/78 能填满、能评审、能区分；但有 **4 类系统性问题**必须在 31 里补属性，否则"填满"不等于"装得下"：

1. **可判定被混为一谈**：边界"能判定"不等于"判得准"；验收"能写"不等于"交付时能验"。需分级（程序高可信/近似/人工；交付时/效果后/过程型）。
2. **缺 5 个必要属性位**：决策权、适用域、生命周期状态外化、能力影响面（可逆性/成本）、边界判定方式。
3. **派生判据过松**：4 条标了"派生"的类型里，**3 条应改判新建**（T025/T031/T008）；判据需改为"身份/职责/边界任一不同即新建"，且派生不得剥夺能力。
4. **长驻类型与"实例可丢弃"冲突**：长驻实例的状态必须外化；生命周期三档不够，需第四档"周期批处理/有界长驻"，并补续期/退休与轮换。

**H1–H6 速览**：H1 部分成立（填满≠装下）｜H2 基本成立（需加步 0、证据前置、3↔6 迭代）｜H3 成立但打折（需分级）｜H4 **不成立**（派生判据要改）｜H5 **不够**（缺一档+状态规则）｜H6 基本成立（相邻运维类型偏弱）。

## 2. H1–H6 逐条判定（附证据）

### H1 九要素对任何领域都够用 —— **部分成立：够填，不够装**

- **证据**：78/78 无空要素；但有 31 个类型出现"要素外补丁"。
- **补丁类型（按出现频次）**：
  | 缺口 | 表现 | 典型类型 |
  |---|---|---|
  | 成本/配额 | 算力预算、观察窗、调用额度无处写 | T015、T009、T028 |
  | 验收方法 | "怎么证明 Z"只能塞进接口证据 | T003、T013 |
  | 环境/权限域 | 影子库 vs 生产、灰度 vs 全量 | T006、T009 |
  | 适用域 | 结论只在"地区/期间/主体/交易结构"内成立 | T049、T050、T052、T057 |
  | 状态外化 | 长驻的状态放哪、谁可读 | T064、T065、T076 |
  | 分级授权 | 限额内自动 vs 超限审批 | T037、T073 |
  | 版本/时效 | 术语表、规则集、情报的版本与过期 | T026、T029、T023 |
  | 判定方式 | 边界"能判但判不准" | T030、T032、T035、T037 |
  | 驻留范围 | "仅实例内可见、不写共享层" | T072 |
  | 授权上下文 | 红队/靶场的授权书决定类型成立 | T073、T074 |
- **结论**：九要素是**骨架**成立，是**表达力**不足；修法不是加要素，是给要素加子属性（见 §4）。

### H2 八步顺序可行 —— **基本成立，需 3 处调整**

- **证据**：78 个中约 60 个按序一次走完；18 个需要回头。
- **调整**：
  1. **加"步 0：确认前提"**（授权、预算、隔离环境、是否组合）——L 域 6 个类型全部需要；T073 无授权书不成立，T077 无资源上限无法写职责。
  2. **证据形态前置为"第 1.5 步"**——36 文件 19 个里有 8 个在写 Z 时被迫先想证据；证据形态是 Z 可判定的前提。
  3. **第 3 步能力 ↔ 第 6 步边界允许迭代**——T010（安装依赖）、T045（沙箱试跑）都是"加能力立刻产生边界义务"。
  4. **生命周期不能放在最后**——它与职责（连续性）耦合；38 文件 12/20 在最后一步卡住。

### H3 边界/验收/能力可判定 —— **成立但打折：可判定 ≠ 判得准**

- **边界**：约 60/78 能写成"程序可直接判定"；其余三类：
  - **近似判定**（能跑检测但判不准）：T030 语义不变、T032 GMV 承诺、T035 关键词密度、T037 承诺 vs 预估；
  - **概率防护**：T053 不推断受保护特征；
  - **环境化判定**（动作空间开放，只能靠隔离/配额/审批/审计事后判）：T073、T074、T077。
- **验收**：约 55/78 交付时即可验（此计数是下限，示例非穷举）；其余：
  - **效果后验收**（交付时验不了）：T035、T037、T061、T062、T065、T068、T071（7 个，36/37 源码实测；v1 草稿只列 4 个是漏列，不是口径）；
  - **过程型验收**（只能验结构完整+来源可追+预算未超）：T077，以及创意类 T021/T023/T027 的 Z 退化。
- **结论**：31 的"可程序判定"要求要**分两级 + 承认残余风险**，否则评审会把近似判定当严格判定放过。

### H4 类型可派生/组合而不失语义 —— **不成立（本批 4 条派生 3 条应改判）**

| 派生 | 实际关系 | 判定 |
|---|---|---|
| T005 重构 ← T001 后端代码 | 能力/知识几乎原样复用，只换职责与验收；边界是收紧 | **成立** |
| T008 架构评审 ← T004 代码评审 | 复用输出结构，但**职责换向**（评审对象从代码变为架构） | **应改判新建**（共享的是输出结构，不是职责；"派生不能扩能力"**不是**理由——用户已拍板子类型可扩能力） |
| T025 长文写作 ← T024 文案 | 只共享"品牌语气"一条读集，职责不同 | **应改判新建** |
| T031 品牌语气守护 ← T024 文案 | 身份相近、**职责相反**（写 vs 检），还**剥夺**了写稿能力 | **应改判新建** |

- **派生规则要改三条**：① **必须共享职责**（不能只共享身份/风格/输出结构）；② **能力可扩但须配套**——用户已拍板"子类型能扩展能力和数据集，由类型本身决定"，所以"不扩能力"不是派生约束，扩能力必须带完整五维并新增对应边界/审批；③ **既有边界不得放宽**（可收紧、可新增，不可删减弱化）。另加判据维：**边界差异**（T054 培训 vs T056 辅导：身份职责同构，但未成年人合规不同 → 必须分开）。
- **组合优先**：T075 双重身份证明互斥角色不能塞进一个类型，必须用组合（阶段状态机）；T073/T074 需要"授权上下文 + 隔离环境"作为组合件。

### H5 生命周期三策略覆盖需求 —— **不够：缺一档 + 缺状态规则**

- **证据**：一次性 48、短驻 21、长驻 9——三档都用上，**但**：
  - T009 发布守护是"发布期长驻"= **有界长驻**（第四档）；
  - T061 库存优化需要"周期批处理"（每日重算）；
  - T064/T065/T076 长驻状态**必须外化**，否则与"实例可丢弃"矛盾；
  - T076 需要**续期/退休**；
  - T034/T036 长驻不应有"停止条件"，应改为"交接条件"；
  - 一次性 vs 短驻界线模糊（T025 多轮修订、T030 返工轮次）。
- **修法**：生命周期 = 档位（一次性/短驻/长驻/周期批处理）+ 状态外化位置 + 保留期 + 续期/退休 + 交接条件；实例寿命 vs 业务周期分开写。

### H6 类型差异能被九要素区分 —— **基本成立，相邻运维类型偏弱**

- **成立证据**：同域抽查 T001/T005/T010（验收/能力/边界/写域均不同）、T024/T025/T031（写短/写长/只检）、T032/T033/T037（方案/实验/执行）——不是换皮。
- **偏弱证据**：T064 故障响应 vs T067 日志分析，差异落在"处置权"（能力）而非职责——说明"处置权是否属于职责"要写进切分判据。

| R7 | 派生三规则：**必须共享职责**、**能力可扩但须配套五维+新边界**、**既有边界不得放宽**；判据加"**边界差异**"维；**组合优先** | §4 | P0 | T008/T025/T031/T054/T056/T075 |

| R12 | 明确"**类型 ≠ 角色/流程节点**"；流程节点型 agent 是否入库要单独说明 | §2.10/§4 | P1 | T075/T078 |

**不采纳的建议**（记录取舍）：

- **不加"价值观/偏好"要素**（用户已拍板并入身份）——本批未出现需要独立价值观位的类型；
- **不把"授权上下文"做成第十要素**——它是创建前置，做成要素会污染九要素的"类型本体"语义；
- **不追求"边界 100% 程序判定"**——近似判定是物理现实（语义类），承认它比假装不存在更严谨。

## 6. 对 34（类型库清单）的修订

1. §3 清单加三列：**决策权**（建议/共决/执行）、**验收类型**（交付时/效果后/过程型）、**适用域**（有/无/范围）。
2. **删除"域级生命周期预设"**——实测与预设不符（如 H 域 10 个里 7 个是一次性，而预设写"短驻"）。改为逐类型标注。
3. 校验规则加两条：① 边界须写"判定方式 + 误判方向"；② 长驻类型不要求"停止条件"，改要求"交接条件 + 状态外化"。
4. **L 域（T073–T078）建议单列为"压力测试集"**，不作为可实例化类型——它们依赖类型外前提，直接照抄会漏掉授权/隔离/组合。

## 8. 未决问题（已收口 5 条，保留 2 条）

**已由 31 v1.1 §7.2 D5–D9 落定（不再未决）**：

1. 授权上下文谁维护 → D5：类型所有者签发、创建时校验、到期失效；
2. 过程型验收由谁判定 → D6：验收门判，设计者不得自签；
3. 长驻记忆读权限 → D7：状态外化声明三档（**本实例 / 同类型 / 全局**），T072 类禁止写共享层；
