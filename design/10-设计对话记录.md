## 4. 你开始讲设计了：四条基本要点

**你的原话（语音识别噪声已按语义校正，"绘画"=会话）**
> 就说这个 Agent 跟人的交互啊，要求以流畅为准。用户随时可以给这个 Agent 发消息，千万不要是一问一答形式，或者消息在队列里面那种方式，这样是不行的。用户可以随时发消息，Agent 可以随时实时应答各类消息。
>
> 这个 Agent 的定位是秘书助理形式：跟我对接的只有一个 Agent，统一的一个 Agent。这个 Agent 在理解我需求之后，可以下发给不同的实际执行任务的 Agent，可能是专家类型的去做执行。跟我对接的这个 Agent 要求响应非常快、非常聪明，当然它不需要掌握所有知识，可以派发给对应的领域 Agent 去执行。
>
> 我这个 Agent 是以树形会话形式的组织方式。一个会话里面可能会有子会话，子会话里面还可能再有子会话，是一个树状结构。为什么会有树状结构？不同会话之间可能需要共享上下文，而且是部分共享上下文。因为一个任务可能非常复杂，会拆成一个树或 DAG 形式的。完成任务之后需要汇总；如果拆成单独的会话，人工整理工作量太大，所以希望用 Agent 去整理。比如在一个会话里，我可以跟 Agent 同时讨论三个子任务，Agent 能清楚分清不同子任务对应的记忆、状态；执行完之后，在同一个会话窗口里把三个子任务的结果都汇聚，进行下一步处理。

**我的解读**
- 主线不是"聊天机器人"，而是**以会话树为组织单元、以人为中心的实时多 agent 协作**；
- 秘书是唯一人机接口，专家是执行体；
- 上下文共享是树的核心动机（部分共享），不是附带功能；
- 汇总必须在会话内自动完成（否则人工整理成本爆炸）。

**我的建议**
- 参见 [`11-设计方案v0.md`](11-设计方案v0.md)：四条主线各自的硬问题 + 6 个待拍板问题 + 讨论顺序。
- 与 Super-agent 划清概念：可借机制（秘书不下场、上下文引用、并发），不套概念（ticket/事件驱动）。

**待确认（按优先级）**
1. 打断语义：agent 输出中来了新消息，立刻停 / 说完再处理 / 先确认再纳入？
2. "不排队"= 必须立刻有反应，还是允许多条合并理解？（我理解两者都要，内部队列不可见）
3. 会话树的共享规则：父→子继承什么？子→父何时可见？兄弟共享吗？快照还是实时？
4. 专家执行是"子会话"还是"任务+结果"？
5. 同窗口三子任务怎么呈现（分栏/卡片/缩进线程）？
6. 汇总由秘书做，还是专门汇总 agent？

## 5. 最底层的一条：基于记忆，而不是基于大模型

**你的原话（语音识别噪声已按语义校正，"代理/A 卷"=Agent）**
> 我希望设计这个 Agent 是基于记忆的，而不是基于大模型的。一个 Agent 可能就是一个实体，就是一个思考的过程，再加上对应的记忆，记忆其实是 Agent 的一部分。但我想把这个关系换过来。
>
> 举个例子：前端/后端这种产品设计里，后端它的整个记忆——当前任务、需求、项目开发进展——可能保存在一个公共的地方，叫公共记忆。每当前端、产品、测试等其他 Agent 有一个需求过来的时候，后端的这个 Agent 可以自动 Fork 或 Spawn 出一个对应的 Agent 出来。相当于并发：比如有 10 个并发请求，就有 10 个对应的 Agent 出来。这 10 个 Agent 都共用一套记忆，就是后端的这种记忆。但它们具体执行的时候，可以有自己独有的短期记忆；执行完之后总结一下，回写到对应的长期记忆里面去。
>
> 再比如客服：100 个客服每天跟客户聊天、解决问题，每个客服其实共享了相同的知识库。每个客服跟客户聊完天，把聊天过程中重要的问题、经验总结沉淀下来，就变成通用的知识。虽然每个客服跟不同客户聊天，但内容是相通的，就可以总结沉淀。而且不是只有一个客服，可以按需求并发新建任意多个客服，它们共享相同的记忆，用相同记忆响应不同的处理。

**我的解读**
- 这是整份设计的**地基**：不是"给 agent 加记忆"，而是**记忆是主体，agent 实例是记忆的临时视图**。
- 大模型是**可替换的推理算力**；连续性、身份、知识沉淀都在记忆里。
- Agent 实体 = **一个记忆作用域 + 一套行为策略**；实例 = 按需 spawn、并发、有私有短期记忆、结束后回写。
- 这会让前面四条重新落位：秘书是根作用域上的长驻实例；专家是领域作用域；会话树很可能是**记忆作用域树的视图**；"汇总"本质是**向上蒸馏写回**。

**我的建议**
- 参见 [`11-设计方案v0.md`](11-设计方案v0.md) 第 7 节：记忆优先的模型、并发语义（快照隔离 + 乐观合并）、写回流程、以及头号风险"记忆污染"。
- 这条一旦定死，前面 1–4 条的问题清单要重写一遍——建议先定记忆模型，再回头收口交互与会话树。

**待确认**
1. 记忆的最小单位：结构化条目（事实/决策/需求/进展/经验）还是自由文本块？
2. 写回方式：实例直接写，还是提交"候选记忆"由记忆管理器合并（高风险变更要人审）？
3. 层级：全局 → 领域/角色 → 任务 → 实例私有，这个分层对不对？会话树和记忆树是同一个东西，还是两个视图？

## 7. 交互语义与上下文可见性：你的拍板

**你的原话**
> 打断语义：我的要求是你要出一个智能调整的方案。比如什么设计最好，你要给我一个方案。不一定是立刻停，也不一定是说完再处理。比如我可能会持续给你发消息，你也需要持续处理。千万不要等我发完了，你再处理，这样其实是浪费时间。你这里要给一个比较优化的方案。
>
> 不排队：我发数据之后，你要有反应，千万不能说你做完手头事情之后再有反应。当然，我也不是说你马上就要有反应，但必须比较快。
>
> 上下文共享：父子之间要继承父会话的上下文，兄弟之间其实也是共享的，应该说是可以实时共享。相当于我引用另外一个会话的时候，你要能够知道去拉取对应的上下文信息。
>
> 树状结构：默认情况下是一种树状结构。当然，我预期的理想情况是，你可以访问任意会话的消息。树状结构就是说，默认情况下，假设我不告诉你，你只访问祖先会话的上下文就可以了。
>
> 会话上下文要求是实时的上下文，而不是产生子任务那一刻父会话上下文的快照。最新的消息你也要能够知道。

**我的解读（已按此设计候选方案）**
- **交互**：不要"轮"，要"连续步进"——用户消息随时进入当前步；agent 按语义段流式输出；每段之间是抢占检查点；消息按类型智能处理（补充/修正/新任务/确认），不是一刀切"打断"或"说完再处理"。
- **反应速度**：有可测 SLA（首反应很快、首实质内容较快、永不无响应）；系统内部可以有队列，但**用户不可感知**。
- **上下文可见性**：默认树形——只能看祖先链；**引用任何会话**即可拉取其上下文；兄弟之间可**实时共享**；引用后应能持续获取**最新**消息。
- **实时而非快照**：子会话运行期间，父会话的新消息也要可见（读最新），不是 spawn 那一刻的快照。
- **由此推出的一致性原则**：**读实时、写版本化**——上下文读取永远拿最新视图；记忆写入仍走候选/版本合并（避免并发写冲突）。

**方案落点**
- 交互协议候选方案 → 待讨论确认后由子智能体固化为 `design/13-交互协议-候选方案.md`（本文件先记录结论，方案细节在对话中给）。

**我建议的数据模型（待确认）**

## 32. Spec 不可见原则：所有 Spec 操作投影成对话

| Spec 内部动作 | 用户侧表现 |
|---|---|
| Spec 建立/更新 | 通常不说；需要时一句"好的，我记下了/我按这个理解做" |
| Spec 拆分 | "我把它拆成两条线：一条 X、一条 Y，可以吗？"（仅需要确认时） |

| Plan 需确认（风险门） | 展示方案摘要 + "确认这么执行吗？" |

| 风险动作前 | "这一步会改线上/删数据/花钱，确认吗？" |
| Spec 归档 | 不说；除非你问"这事完了吗" |

**语言规范（禁用 → 替换）**
- "Spec / 规格 / 需求文档 / 验收标准 / 基线 / 增量" → 不出现；
- "方案 / 这件事 / 结果 / 需要你确认" → 正常使用。

## 38. 消息不打断后台工作：对话回路与执行回路分离

**你的原话**
> 我在给这个智能体发消息的时候，其实不会打断智能体当前的工作。智能体的工作是在后台，我们可以持续在前端跟它做持续交互。不是说我发一条消息，就会打断它当前的工作；也不是它回完之后就忘了继续做之前的事情、还要我接着说。
>
> 例子：智能体现在在做一件事，我连续发三条消息交代三件不同任务。智能体分别回复这三条消息，同时开启三个同时进行的任务（三个子智能体），完成以后又向我汇报，整个交互非常流畅。

**确认的规则**
1. **默认不打断**：用户发消息 → 秘书即时回复 + 视需要派发新任务；**正在进行的任务继续跑**，不取消、不暂停。
2. **两条回路分离**：
   - **对话回路**：接收消息、回复、澄清、汇报——始终可用，不等后台任务；
   - **执行回路**：后台任务/子智能体/长任务——独立推进，完成后以事件回流到对话。
3. **只有显式修正/停止才影响正在做的事**：用户说"别做 X / 停掉 / 改成 Y"是明确的 steer/cancel；其余一律视为新增或补充，并行处理。
4. **三件事 = 三条并行线**：三条消息 → 三次回复 + 三个子智能体并行；互不阻塞；完成后各自汇报，秘书汇总。
5. **"撤回"只作用于对话回复**（流式未完成的那条），不作用于后台任务。
6. 资源约束靠**并发上限/预算**，不靠"等上一个做完"。

**对实现的要求（M2 落地）**
- E1 Loop 保持 `Acting + Speaking` 并存；消息处理路径不得 await 任务完成；
- 子任务派发即返回（异步结算），对话继续；
- UI 侧：回复流与任务列表独立更新，任务不锁输入框。

## 44. 会话即工作区 + 会话内任务编排（多任务自动推进）

**你的原话（要点）**
> 我们并不需要工作区，会话树就是工作区的概念。一个会话可以包含一个或者多个任务，需要对任务进行管理：任务执行要有状态；右侧需要任务列表视图/选项卡，列出已完成、执行中、还没开始的任务。任务在后台执行，不影响会话内交互；完成后在会话里给我发消息。甚至任务可以自动拆分成多个，执行完一个自动创建下一个——相当于工作流，触发由智能体自行进行，不需要我人工确认下一步。多智能体先做到这种程度，后面再设计智能体团队。

**确认的模型**
1. **会话 = 工作区**：不引入独立 workspace；会话树承担工作区职责。
2. **会话 1→N 任务**：一个会话可同时/先后有多个任务；任务有状态（待开始/执行中/已完成/失败/已取消/阻塞）。
3. **后台执行、不阻塞对话**：任务跑在后台，用户随时可以继续聊；任务完成由秘书在会话里发一条消息。
4. **任务面板**：右侧任务列表/选项卡，按状态分组（执行中/待开始/已完成/失败），显示进度、阶段、耗时、产物；可取消/重试/查看详情。
5. **智能体自主编排（工作流）**：用户提需求 → 秘书拆成任务链/DAG → 完成一个自动创建/启动下一个 → 直到全部完成/失败/预算耗尽/用户中止；**不需要用户逐条"确认下一步"**。
6. **用户干预**：默认不打断；用户说"停/改成…"才调整；可随时插话问进度。
7. **多智能体**：本阶段先做"单秘书 + 任务编排"；智能体团队后续讨论。

**设计要点**
- 任务链用显式依赖（depends_on）表达；无依赖可并行，有依赖串行；
- 自动推进要有边界：并发上限、步数/任务数上限、token 预算、失败重试上限、危险操作需审批；
- **汇报按任务粒度（你的补充）**：**每个任务完成都要在会话里发一条汇报消息**，不要等工作流全部完成才统一汇报；工作流结束时再发一条总结（可选）；
- 中间进展也可汇报：任务开始/进入关键阶段/产出中间产物时可发简短进展（可配置频率，避免刷屏）；
- 汇报用自然语言、讲要点、附产物/文件链接，详情可折叠；
- 任务状态、阶段、产物全部持久化；重启恢复 running→interrupted/可重试。

## 45. 定时任务与自动化（对齐 DSH schedule/automation）

**你的问题**：DSH 有定时任务、自动化任务，有没有考虑到？

**DSH 的做法（已确认）**
- 定时任务支持：延时（after）、绝对时间（at）、固定间隔（every）、每天/每周固定时刻、cron 表达式；时区感知；
- 到点后向会话投递一条 prompt（提醒/任务），由 agent 执行；
- 停机错过只补发最近一次；重复投递可能发生（崩溃恢复）；
- 自动化 = 定时任务 + 目标（goal）+ 工作流（workflow）的组合；插件/触发器生态另算。

**司墨的设计（P1，M13）**
1. **定时任务**：一次性/周期（每天、每周、cron、间隔）；绑定到某个会话或新建会话；内容 = 一句话任务或模板；
2. **执行**：到点由调度器创建任务/消息，走正常任务编排与权限；结果按"逐任务汇报"回到会话；
3. **管理 UI**：定时任务列表（启用/暂停/下次运行/最近结果）、创建向导（时间、内容、目标会话、权限）；
4. **自动化**：任务完成/文件变化/条件触发 → 启动工作流（先做时间触发，事件触发放 P2）；
5. **可靠性**：停机补偿最近一次、失败重试、错过提示；时区按本地；
6. **权限**：定时任务执行沿用会话权限；涉及写/执行/联网仍走审批；无法审批时 fail-closed（可配置为"暂停并通知"）。

**暂不做**：插件触发器、外部 webhook 生态（P2）。
