## D-01 形态与宿主：内核跑在哪？

**问题**：这个 agent 的"身体"放在哪——直接做成当前 DSH Harness 的 agent preset，还是独立内核 + 多个宿主适配？

**我的建议**：**独立内核（零依赖）+ 宿主可换**。第一宿主用本机 CLI demo，第二宿主再接 DSH preset 桥接。

**理由**：
- 你的设计自由度最重要。DSH preset 的能力边界是硬的：模型不能由 preset 绑定（Host 的 `agent-default-model` + 会话级 `/model` 决定）、team/ralph/terminal 在 Host 层关不掉、config 整体替换不深合并。
- 内核独立后，事件源、执行器、模型都能换；"场景可插拔"才真的成立。
- 代价是两套集成要做，第一版感知不到 GUI 的便利。

**代价**：不能直接在这个聊天界面里"切过去用"；要自己跑进程。

**什么时候该反过来**：如果你要的只是「一个更好用的聊天 agent」，且接受 3 个月内不碰架构级改动，那直接做 preset 更划算。

**落点**：`../skeleton/`（内核）｜后续 `bridge/dsh-preset/`（适配）

**你的决定**：待定

## D-02 分层与角色：几层？Router/Worker 照抄吗？

**问题**：是"单 agent + 工具"，还是"Lead 深介入的 Agent Team"，还是"Router/Worker 双层"？

**我的建议**：**四层 + 一横切**——
- 事件层（Source / Trigger / Thread）
- 决策层（研判 + 分派 = Router）
- 执行层（Worker，隔离上下文）
- 状态层（Store / Effects / 订阅）
- 横切：人机界面与验收门

**关键判据**：决策层**不准下场干活**（不配或少配执行工具）。这是双层与团队的分水岭，也是能否承载"多任务"的结构原因。

**理由**：团队式编排的 Lead 负载极重（理解细节、拆子任务、高频协调），随任务数线性劣化；双层把"任务之间的排队/归属"与"任务内部怎么做"彻底切开，Router 只做长输入短输出，可批处理摊薄。

**代价**：Router 是单点。任务量上去后必然要分片，而分片会牺牲全局连续性——这个矛盾官方也没解决。

**什么时候该反过来**：如果你 90% 的场景是"一次一个复杂任务"，那单 agent 更简单，双层是负资产。

**落点**：`skeleton/src/kernel/scheduler.mjs` + `policy.mjs` + `agent.mjs`

**你的决定**：待定

## D-03 一等公民：Session 还是 Ticket？

**问题**：系统的基本单位是什么？会话（Session）还是工单（Ticket）？

**我的建议**：**Ticket 是一等公民，Session 可丢弃**。Ticket 自持状态（做到哪、等谁、证据是什么），Session/执行器只是可替换的耗材。

**理由**：执行体会换、会崩、会被重启。如果"这件事做到哪了"挂在 Session 上，一切恢复都是灾难。原文明确：Ticket 定义自己的状态，**不跟随执行体**。

**代价**：要写状态机（open→ended、stage 优先级），比"一个对话数组"复杂。

**什么时候该反过来**：个人一次性助手、无需恢复的场景。

**落点**：`skeleton/src/kernel/tasks.mjs`

**你的决定**：待定

## D-04 驱动模型：提示词驱动还是事件驱动？

**问题**：agent 什么时候动？人说话时，还是环境有事件时？

**我的建议**：**统一事件总线，人消息也是一条事件**；两级过滤（程序 Gate 先筛，模型再研判）；**永远不用模型当权限边界**。

**理由**：人消息驱动是"每次都得 @ 它"；纯模型看消息决定要不要动，是提示词注入最容易被攻破的地方。程序层决定"谁能触发"，模型只在"已准入"的候选里做语义判断。

**代价**：要维护 Source 适配器、幂等键、读取游标；比"一个 chat 循环"重。

**什么时候该反过来**：只做单人对话助手 → 事件层是过度设计。

**落点**：`skeleton/src/kernel/bus.mjs` + `policy.mjs`

**你的决定**：待定

## D-05 授权模型：主动 agent 凭什么不闯祸？

**问题**：一条群消息就能让它改代码，怎么防？

**我的建议**：**Mandate（授权凭证）+ 带版本 Policy + 默认 observe 影子模式**。授权与上下文严格分离：订阅 Thread 让上下文自由流动，但不带来任何权限；权限只由 accept 创建、人 stop 撤回、恢复前对当前 Policy 重校验。

**理由**：这是主动型 agent 能安全上线的唯一现实路径。影子模式先跑一周"它本来会做什么"，人审过历史决策再放开 auto。

**代价**：多一层对象（Policy/Mandate/Decision），实现复杂度明显上升。

**什么时候该反过来**：只读、无外部副作用的场景 → 授权层可简化成白名单。

**落点**：`skeleton/src/kernel/policy.mjs`

**你的决定**：待定

## D-06 上下文与记忆：怎么长跑不丢？

**问题**：跨天、跨渠道、几十个任务之后，怎么找回上下文？

**我的建议**：**Inline & Spill + 对象 ID 引用图（链式召回）**，不用向量库当主记忆。

**理由**：窗口是 cache 不是仓库。给每个对象唯一 ID，注入时内联紧密关联对象的 ID，工具召回也内联下一跳 → 模型可逐跳展开。比"向量检索 + 摘要压缩"更工程化、更可测（跳数、召回成功率）。

**代价**：要求第一天就把领域对象建模成图，事后补很痛；没有强一致的"记忆"语义。

**什么时候该反过来**：非结构化海量文本检索（如知识库问答）→ 向量检索仍是主力。

**落点**：`skeleton/src/kernel/context.mjs`

**你的决定**：待定

## D-07 状态与一致性：崩了怎么办？

**问题**：进程挂了，活会不会丢？外部动作会不会重复？

**我的建议**：**单写者 Store（先 JSONL append-only，量大再 SQLite）+ Effects 先落库后执行 + 恢复注记**。

**理由**："授权已创建但派工丢了""消息已发但记录没写"这类不一致会立刻摧毁信任。先存储后执行、幂等收据、指数退避，把系统从"一个幸运的进程"变成"可恢复的状态机"。

**代价**：所有外部副作用都要走队列，写起来比直接 await 麻烦。

**什么时候该反过来**：一次性任务、失败可整体重跑 → 不需要。

**落点**：`skeleton/src/kernel/store.mjs`

**你的决定**：待定

## D-08 并发与资源：多任务怎么不饿死人？

**问题**：并发上限怎么定？人会不会被机器任务饿死？

**我的建议**：**slot 信号量 + 人优先 +1 额外 slot**；长任务异步化（前台命令转后台）；后台有工作时限（turn 结束后 30 分钟，subagent 可继续）；handoff 给人立即释放 slot。

**理由**：这条是"体验分水岭"——并发打满时人发消息仍能立刻响应，人才敢把工作交给它。

**代价**：调度逻辑变复杂；slot 泄漏很难查。

**什么时候该反过来**：单任务串行场景。

**落点**：`skeleton/src/kernel/scheduler.mjs`

**你的决定**：待定

## D-09 验收门：把"人做验收"变成机制

**问题**："做完了"到底是什么？原文这块是缺的。

**我的建议**：**验收门升为一等原语**。Ticket 从 `ready` → 进人工 review 前必须满足场景定义的一组合格证据（如 bugfix：复现失败的测试/脚本、测试通过证据、改动范围与影响、回滚方式）；缺任一项**退回 working 并列出缺什么**，不许进 `person/review`。等待人的提问只走结构化字段。

**理由**：原文的"人做验收"落到实现只是 ready Report + 人肉看 PR，没有契约。把验收约束显式化，才真正减少人的注意力消耗。

**代价**：每个场景都要写证据契约；太严会让 agent 卡在补证据上。

**什么时候该反过来**：创意/探索型任务（无客观证据）→ 验收门退化为"人确认"。

**落点**：`skeleton/src/kernel/acceptance.mjs`

**你的决定**：待定

## D-10 场景可插拔：通用底座怎么适配不同场景？

**问题**：一套内核，怎么同时服务研发、调研、个人助理？

**我的建议**：**Scenario Pack** = 一个目录/文件，声明：准入规则、证据契约、Worker 策略与提示词、工具集、输出规范（按信道）、指标。换场景只换包，内核零改动。

**理由**："通用底座"如果没有明确扩展点，最后会变成一坨 if-else。

**代价**：要预留足够稳定的端口；过早抽象会抽象错。

**什么时候该反过来**：确定只做一个场景 → 直接写死，别抽象。

**落点**：`skeleton/src/scenarios/bugfix.mjs`（示范包）

**你的决定**：待定

## D-11 进化机制：真的能自我升级吗？

**问题**：你说的"发展、演进、升级、进化"具体到机制是什么？

**我的建议**：**分三级，逐级放权**——
- **L1 参数级**（安全）：提示词、阈值、准入规则、证据契约的自动调优；必须留 diff + 可回滚 + 指标对比。
- **L2 场景级**（需影子模式）：根据失败案例自动生成新场景包/新规则草案，observe 跑一周，人批后生效。
- **L3 内核级**（不做自动化）：改内核代码/架构，走"人设计 → 我实现 → 测试"的显式流程。

**理由**：agent 自改代码是目前风险最高、收益最不确定的一环；但 L1/L2 已经能产生真实的进化闭环。关键是**先有指标**，否则"进化"无法判定好坏。

**代价**：需要观测基建；没有评测集时 L1 调优容易过拟合噪音。

**什么时候该反过来**：如果你要的就是"能自己写自己的 agent"，那 L3 也得设计，但要配套沙箱 + 评审门 + 回滚。

**落点**：`design/` 里另起 `05-进化机制.md`（待你确认方向后建）

**你的决定**：待定

## D-12 打扰预算：主动 agent 怎么不变成噪音？

**问题**：主动性的度量在哪？

**我的建议**：**量化**：每 Ticket 消息数、人均日被通知次数、`ready` 后被推翻的返工率、人 stop 的比率、静默弃单率。目标函数 = 价值 / 注意力，写进面板首页。

**理由**：原文哲学是"注意力成本"，落到机制只有 observe 和 100 词限制，没有指标。没有数字，"主动"会单调滑向"噪音"，而你没证据。

**代价**：要埋点、要定义"价值"（可先用"被人接受的交付物数量"代理）。

**什么时候该反过来**：内部试用期 → 先把指标跑出来再说。

**落点**：`design/06-观测与指标.md`（待建）

**你的决定**：待定

## D-14 模型接入：Router 与 Worker 用同一个模型吗？

**问题**：怎么把模型接进来？不同角色要不要用不同模型？

**我的建议**：**端口化 + 按角色分模型**。Router/Assessor 用轻量模型（长输入、短输出、只做研判分派），Worker 用最强模型；模型在会话创建时定格，不中途换。内核不 import 任何厂商 SDK，只依赖 `llm.ask({role, context, task})` 契约。

**理由**：两个角色的性价比曲线完全不同——Router 每天可能研判上千条事件，Worker 才产出实际价值。混用一个模型，要么 Router 贵得离谱，要么 Worker 质量不够。端口化还让"换模型/加回退/注入失败模式"都不动内核。

**代价**：要维护两套提示词与两套评测；小模型研判质量要用数据验证。

**什么时候该反过来**：任务量小、预算宽裕 → 全用最强模型，少一层配置。

**落点**：`skeleton/src/llm/mock.mjs`（参考实现，D-14）｜真模型只替换端口

**你的决定**：待定

## D-15 装配与宿主：内核怎么被"装起来"？

**问题**：内核跑在什么上下文里？CLI / Web / DSH GUI / 服务，怎么接才不把内核写死？

**我的建议**：**唯一装配根（composition root）+ 宿主适配器**。内核只暴露"装好的一组对象"；宿主（CLI、未来 DSH preset 桥、HTTP 服务）只负责把外部事件喂进 `ingest()`、把内核事件渲染出去。任何模块都不反向依赖宿主。

**理由**：这是"场景可插拔 + 宿主可换"的最后一环。若不隔离，换宿主会牵动内核，之前的抽象全白做。

**代价**：多一层装配代码；调试要顺着适配器看。

**什么时候该反过来**：只做一个 CLI 工具 → 直接写在入口里也行。

**落点**：`skeleton/src/kernel/runtime.mjs` + `demo.mjs` + `src/adapters/cli.mjs`

**你的决定**：待定
