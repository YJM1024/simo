## v0.3 变更摘要（相对 v0.2.3，10 条）

1. **从"作用域分层"升级为"实体图 + 唯一库"**：不再有"每个会话/作用域一套记忆"的概念；一个库内用**实体（域/项目/会话/任务/智能体）+ 关系 + 记忆条目**组织，作用域退化为"实体绑定 + 可见性 + 写域"（§2、§6）。
2. **记忆类型从 8 个 kind 收敛为 5 类**：场景 / 语义 / 规范 / 程序 / 工作；旧 kind 全部给映射（§3）。
3. **事实唯一 + 观点归属**：客观事实有 `factKey`，同一事实槽位只允许一个 active；观点/判断必须带归属实体；冲突**不合并、不覆盖**，标 `disputed`（§4）。
4. **金字塔**：按实体抽象层级（L0 原始 → L4 全局）组织与压缩，支持多视角投影；压缩是派生视图、可重建、失效可传播（§5）。
5. **智能体 = 实体 + 记忆域 + 记忆视图**：智能体通用记忆从它负责的会话中提炼、带来源，**不与会话记忆混淆**（§6）。
6. **写入改为三段管道**：原文（raw，不可变）→ canonical（意图识别 + 指代消解 + 归一化，唯一处理入口）→ 记忆条目；三者双向溯源（§7）。
7. **跨智能体默认只读、写域隔离、人格防混乱**：身份锁定、他者内容打标、只能写自己的记忆域、行为校验（§6.4）。
8. **召回升级为"实体/关系召回 + RRF + 关系下钻 + 金字塔下钻 + agentic 多步"**，预算/打分/cite 沿用 design/22（§8）。
9. **迁移建议**：与已实现 M3 表结构兼容的增量迁移（扩列 + 新表 + 回填 + 双写期 + 回滚），不推倒重建（§9）。
10. **差异与已定结论**：明确与 v0.2 的 8 处差异（其中"事实冲突不再按权威自动裁决"是关键变化）；10 个问题已由 Lead 拍板定稿（§10、§12）。

## 1. 一句话模型 + 不变式

**一句话**：全局唯一记忆库 = **实体图（含智能体）+ 关系 + 记忆条目 + 金字塔**；**原文（raw）永久不可变，canonical 是唯一处理与检索入口**；智能体是带人格与记忆域/记忆视图的实体，**只能写自己的记忆域，跨智能体只读**；**事实唯一、观点归属、冲突保留**。

```
┌──────────────────────────────────────────────────────────────────┐
│ 全局唯一记忆库（单库，不分库；视图过滤）                            │
│                                                                  │
│  原始流 raw ──canonical 化──> canonical unit ──抽取──> 记忆条目     │
│  (不可变)      (意图/指代/归一)      (唯一处理入口)     (实体绑定)   │
│       │                              │                     │      │
│       └──────────── 溯源链 ──────────┴─────────────────────┘      │
│                                                                  │
│  实体图：域 / 项目(映射) / 会话 / 任务 / 智能体                     │
│    └─ 关系：父子 / 归属 / 关于 / 负责 / 产出 / 依赖 / 引用 / 冲突    │
│                                                                  │
│  金字塔：L0 原始 → L1 会话 → L2 任务/项目 → L3 领域 → L4 全局        │
│    └─ 派生视图：可压缩、多视角、失效传播、可重建                     │
│                                                                  │
│  智能体：人格 + 工具 + 模型 + 记忆域(写) + 记忆视图(读)              │
└──────────────────────────────────────────────────────────────────┘
```

### 1.1 不变式（违反即作废）

- **I1 唯一库**：物理只有一个记忆库；"按会话/智能体看记忆"是视图过滤，不是分库。
- **I2 原文不可变**：用户消息的 raw 永久保存、只追加、不可改写；仅合规流程可走"标记删除"（不物理删、需审计，§12 Q2 已定）；raw 是最终证据。
- **I3 canonical 唯一入口**：检索、抽取、写记忆都只消费 canonical；**不允许从 raw 直接写记忆**；每段 canonical 必须能回指 raw。
- **I4 事实唯一**：同一 `factKey` 只允许一个 `active` 的语义事实；更新走"旧值闭合 + 新值"；不一致断言进入 `disputed`（§4.1）。
- **I5 观点归属**：观点/判断/立场必须带 `attributed_to`（哪个智能体/用户/外部来源）；**无归属的判断不得入语义事实**，只能作观点或推断。
- **I6 写域隔离**：智能体只能写自己的记忆域；跨智能体默认**只读**；秘书/主智能体也不得替其他智能体直写（只能转呈候选，§6.2）。
- **I7 冲突是正常数据**：矛盾不合并、不覆盖，标 `disputed` 成对保留；可询问、可延迟、可保持（§4.3）。
- **I8 金字塔是派生**：压缩节点不是真相；源条目/原文才是；压缩节点可失效、可重建，不因压缩丢事实。

## 2. 全局唯一记忆库的四件套

### 2.1 实体（Entity）

实体是记忆的**挂载点**，也是"视图"的过滤维度。最小实体类型（【本稿】可扩展）：

| kind | 说明 | 例子 | 备注 |
|---|---|---|---|
| `domain` 域 | 长期领域，承载领域级规范/程序/语义 | 后端、前端、客服、生活、财务 | 长期记忆的主要归属 |
| `project` 项目 | **映射概念**（design-core §1）：一组会话/任务的视图锚点 | "Atlas 迁移项目" | 不拥有独立记忆域；靠关系映射会话，§2.2 |
| `conversation` 会话 | 会话树节点（主会话根 + 会话）；消息归属地 | 主会话、某需求会话 | 负责人 = 智能体；Spec 挂这里 |
| `task` 任务 | 会话内执行单元（M5 长任务/工作流） | "排查支付回调 bug" | 短生命周期，工作记忆主要归属 |
| `agent` 智能体 | 身份定义（人格/工具/模型/记忆域/记忆视图） | 司墨（默认）、某专家角色 | 本身也是记忆中的实体，§6 |

**字段（建议）**：`id`（`ent-…`）、`kind`、`name`（显示名）、`canonical_name`（规范名，别名归一）、`aliases[]`、`parent_id`（仅会话树/域层级用；项目不用父子归属）、`attrs`（结构化属性，如项目状态）、`owner_agent`（会话/任务的负责人）、`status`（active/archived/marked）、`version`、`created_at`/`updated_at`、`sensitivity`。

规则：
- **实体合并**：同名/同义的实体要能合并（合并记录进关系，不物理删）；否则图会碎。
- **项目是虚拟锚点**：项目不拥有记忆（记忆挂在会话/域），项目视图 = 关系映射 + 聚合；不建"项目作用域"。
- **会话树传事不传人**：会话可继承祖先的**任务/需求/背景**（通过实体关系），**不继承人格**（人格只来自 agent 实体）。

### 2.2 关系（Relation）

关系是实体之间的有向、带类型、带来源的边。存储为独立表（不塞进实体 JSON），因为召回要按关系下钻。

| rel_type | 语义 | 例子 |
|---|---|---|
| `parent_of` | 层级（会话树/域层级） | 主会话 → 需求会话 |
| `belongs_to` | 归属（会话→域；任务→会话） | 会话 → 域:后端 |
| `about` | 记忆/任务关于哪个实体 | 任务 → 支付服务 |
| `owned_by` | 负责人 | 会话 → 智能体:司墨 |
| `mapped_to` | **项目映射**（项目→会话/任务） | 项目 → 会话 |
| `produced` | 产出 | 任务 → 产物/文件 |
| `depends_on` | 依赖 | 任务 A → 任务 B |
| `references` | 引用 | 规范条目 → 领域条目 |
| `supersedes` | 取代（版本/新旧条目） | 新规范 → 旧规范 |
| `conflicts_with` | 冲突（双向） | 两条 disputed 条目 |

**字段（建议）**：`id`、`from_entity`、`to_entity`、`rel_type`、`attrs`（JSON，如权重/条件）、`source`（user/tool/inferred）、`confidence`、`valid_from`/`valid_to`（双时态）、`created_at`。

规则：`parent_of` 必须防环（数据库层或写入校验）；关系也是"可被推断的"——推断出的关系标 `source=inferred`，不覆盖已确认关系。

### 2.3 记忆条目（MemoryItem）

在已实现 M3 `memory_items` 基础上扩展（字段级见 §9.3）。核心字段：

| 字段 | 说明 |
|---|---|
| `id` / `version` | 稳定 id + 版本号（ADD-only，旧版本进 history） |
| `type` / `sub_type` | 五种类型 + 子类型（§3） |
| `content` | **canonical 文本**（不是 raw 原文；raw 用 `raw_refs` 溯源） |
| `canonical_refs[]` | 指向 canonical unit（1..n） |
| `entity_refs[]` | 绑定的实体（主实体 + 关联实体），多对多 |
| `fact_key` | 语义事实的槽位键（`subject|predicate|qualifier` 归一后），用于事实唯一 |
| `assertion` | `fact`（客观）/ `opinion`（观点）/ `instruction`（指令/规范） |
| `attributed_to` | 观点/判断的归属实体（智能体/用户/外部来源）；客观事实为 null |
| `owner_agent` | **写域**：属于哪个智能体的记忆域（§6.2） |
| `source` / `authority` / `confidence` | 来源（user/conversation/tool/inferred）、权威（user_confirmed/system_verified/inferred）、置信度（沿用 v0.2 上限） |
| `status` | `active` / `disputed` / `superseded` / `retracted` / `archived` |
| `valid_from` / `valid_until` | 双时态：这条记忆对外成立的区间（失效优于删除） |
| `layer` | 金字塔层级（L0–L4，§5.1） |
| `importance` / `strength` / `last_used_at` | 打分与使用强度（沿用 M3/22） |
| `refs` | 关联 `session:` / `task:` / `spec:` / `artifact:`（遗留兼容） |
| `conflict_with[]` | 冲突条目（双向） |
| `sensitivity` | `normal` / `sensitive` |
| `created_at` / `updated_at` | 系统时间 |

### 2.4 原始流（Raw）

**用户消息原文永久保存、不可变**（design-core §3、【用户已定】）：

- `raw_messages`：`id`、`conversation_entity_id`、`sender_kind`（user/agent/tool）、`sender_id`、`content`（原文）、`attachments`、`content_hash`、`created_at`。**只 INSERT，无 UPDATE/DELETE**；仅合规流程可"标记删除"（不物理删、需审计；§12 Q2 已定）。
- `raw_events`：工具调用/结果、任务事件、审批、系统事件；同样 append-only。
- raw 只用于：溯源、审计、重放、canonical 重建；**不直接进检索、不直接写记忆**。

### 2.5 Canonical 单元

canonical = **意图识别 + 指代消解 + 归一化**后的"可处理版本"（design-core §3、【用户已定】）：

| 字段 | 说明 |
|---|---|
| `id` | `can-…` |
| `raw_refs[]` | 来源原文（1..n；一段 canonical 可来自多条消息，如连续补充） |
| `conversation_entity_id` / `turn_id` | 归属会话与轮次 |
| `actor` | 谁说的（user / agent:<id> / tool） |
| `intent` | statement / question / instruction / preference / correction / smalltalk / task |
| `canonical_text` | 改写后的规范文本（保留语义，不新增主张） |
| `frame` | 结构化：`entities[]`、`relations[]`、`modality`（must/should/may）、`polarity`（否定）、`time`、`conditions`、`speaker` |
| `ops` | 改写操作清单：`resolve(它→ent-…)、normalize(今天→2026-11-08)、expand(简称→全称)` |
| `canonicalizer_version` / `model` | 可重放、可评测 |
| `status` | `ok` / `unresolved`（指代无法消解）/ `failed` |
| `content_hash` / `created_at` | 防篡改与溯源 |

**canonical 是唯一处理入口**：检索、抽取、写记忆都读 canonical；raw 只作证据。**不允许**"从 raw 直接写一条记忆"（绕过意图/指代/归一化，等于绕过质量闸）。

### 2.6 金字塔节点（PyramidNode）

| 字段 | 说明 |
|---|---|
| `id` / `version` | 节点版本 |
| `entity_id` | 挂在哪个实体（会话/任务/项目/域/全局） |
| `level` | L0–L4（§5.1） |
| `view_id` | 属于哪个视角（§5.5） |
| `kind` | summary / cluster / abstract |
| `source_item_ids[]` / `source_node_ids[]` | 压缩来源（必须可追溯） |
| `text` | 压缩文本（只压缩，不新增事实） |
| `coverage` | 覆盖度（被覆盖源条目/全部源条目） |
| `status` | `active` / `stale`（源变更后）/ `archived` |
| `built_by` / `built_at` / `invalid_at` | 构建者、时间、失效时间 |

### 2.7 四件套怎么协作（一个小例子）

用户在主会话说："以后后端项目都用 Go，别用 Java。"（raw）→ canonical：`instruction / modality=must / time=from-now`，实体解析为 `域:后端`（`ops: resolve("后端项目")`）→ 记忆条目：`type=norm / sub_type=constraint / owner_agent=司墨 / entity_refs=[域:后端] / attributed_to=用户` → 关系：`域:后端 about 这条规范`（由实体绑定自动生成）→ 金字塔：L3 领域视图出现这条规范，L1 会话摘要引用它；召回时"后端 + 技术选型"意图先命中领域规范。

## 3. 五种记忆类型

### 3.1 类型定义

| type | 定义 | 回答的问题 | 典型子类型 | 例子 | 生命周期 | 事实唯一适用 |
|---|---|---|---|---|---|---|
| **scene 场景** | 一次具体经历/案例（发生了什么、怎么处理的、结果） | "上次类似的事是怎么发生的？" | `experience`（经验案例）、`incident`（事故）、`case`（客服案例） | "11-03 订单故障：连接池耗尽，先调参后扩容" | 长期（可衰减），随会话归档提炼 | 否（场景可重复/相似） |
| **semantic 语义** | 客观事实/概念/知识 | "是什么？" | `fact`、`concept`、`entity_attr` | "订单主库 = PostgreSQL 14" | 长期；失效不删 | **是**（§4.1） |
| **norm 规范** | 目标/约束/决定/规则/偏好（应该怎样） | "该怎么做/不该做什么？" | `goal`、`constraint`、`decision`、`rule`、`preference` | "对外接口只用 REST"、"发布窗口外禁改线上配置" | 长期；变更需人审/高权威 | 否（但**同槽位规范冲突 → disputed**） |
| **procedural 程序** | 怎么做：流程/SOP/工具用法/技巧 | "怎么做？" | `sop`、`playbook`、`tool_usage`、`heuristic` | "中文短查询（<3 字）走 LIKE 兜底，≥3 走 FTS trigram" | 长期；越用越稳（strength） | 否（同 signature 聚合） |
| **working 工作** | 当前状态：进行中/待办/阻塞/中间结论 | "现在做到哪了？" | `state`、`todo`、`blocked`、`open_question` | "任务 T7 进行到第 3 阶段，卡在等待 DBA 确认" | **短**（任务结束闭合、可重建） | 否 |

**类型边界（容易混的）**：
- **场景 vs 程序**：场景是"发生过的事"（带时间/结果），程序是"以后可复用的做法"（去情境化）。同一次经历往往生成两条：场景（原始案例）+ 程序（提炼做法），前者可衰减、后者可复用。
- **语义 vs 规范**：语义是"是什么"（可被验证），规范是"应该怎样"（可被采纳/否决）；同一句话可能两者都有（"我们用 PG"是事实，"以后都用 PG"是规范）。
- **工作 vs 其他**：工作记忆是**可重建的运行时状态**，不做长期知识，不参与事实唯一；任务结束后闭合 `valid_until` 并归档，避免"过时进度压过事实"。
- **偏好备注**：显式偏好（用户说"以后这种直接做"）作为 `norm/preference` 存；**自动推断偏好仍暂缓**（design/10 §14 的边界不变）。

### 3.2 旧 kind → 新 type/sub_type 映射

| v0.2 kind | v0.3 type/sub_type | 迁移说明 |
|---|---|---|
| `fact` | `semantic/fact` | 附带 `fact_key` 回填 |
| `decision` | `norm/decision` | 结论/取舍；冲突 → disputed |
| `requirement` | `norm/goal` | 目标/需求条目；完成状态走 working |
| `constraint` | `norm/constraint` | 红线；修改需人审 |
| `preference` | `norm/preference` | 只收显式偏好（暂缓自动推断） |
| `progress` | `working/state` | 短生命周期，任务结束闭合 |
| `experience` | `scene/experience`（有步骤的另生成 `procedural`） | 迁移默认场景；整理者后续重分类 |
| `open_question` | `working/open_question` | 未决问题；解决后落 `norm/decision` |
| `spec`（22 曾作为记忆 kind） | **移出记忆类型**：Spec 属于会话（design-core §2） | 迁移到现有 `specs` 表或标 `archived`；记忆只引用 `spec:` |

### 3.3 类型与写域/召回的默认关系

| type | 默认写域 | 默认层级 | 默认召回优先级 |
|---|---|---|---|
| scene | agent:<id> / 会话实体 | L1–L2 | 中（相似场景） |
| semantic | team / agent:<id> | L1–L3 | 高（事实先于观点） |
| norm | team / 域实体 | L2–L3 | **最高**（红线必进，沿用"块/pin 必进"） |
| procedural | agent:<id> / 域实体 | L2–L3 | 中高（任务类型匹配） |
| working | 会话/任务实体 | L0–L1 | 高（当前相关），短寿命 |

## 4. 事实唯一、观点归属、冲突保留

### 4.1 事实唯一：`factKey`

**定义**：`factKey = normalize(subject_entity) + "|" + normalize(predicate) + "|" + normalize(qualifier)`。

- `subject_entity`：实体 id（不是字符串），先从 canonical frame 的实体解析拿到；
- `predicate`：受控词表（如 `is_a` / `has_property` / `depends_on` / `located_at` / `owned_by`），先用规则+词典映射，映射不了标 `open_question`，不硬猜；
- `qualifier`：条件/时间/范围（如 `env=prod`），无则空。

**唯一性规则**：
1. 同一 `factKey` 只允许一个 `status=active` 的 `semantic/fact`（SQLite 用**部分唯一索引**实现，既有 M3 的 `key` 列可复用为 `fact_key`）。
2. 新断言与 active 值**一致** → 不新建事实，合并来源/证据（strength++，记录 `sources[]`，版本不升）。
3. 新断言与 active 值**不一致** → **不覆盖**：新条目 `status=disputed`，旧条目保持 active，生成冲突记录（§4.3）。**禁止按来源层级自动替换**（这是与 v0.2 的关键差异；Lead 已拍板确认，见 §10 D3、§12 Q3）。
4. 旧事实失效（环境变化/被验证为错）→ 闭合 `valid_until` + `status=superseded`；新事实 active。这是"同一个事实的演进"，不是冲突。
5. 事实可被**用户确认**为真/假：用户说"不对，现在是 X"→ 记用户确认的新事实 + 旧条目 superseded；用户确认也是"新断言"，仍走候选与版本（不原地改）。

**归一化风险**：合并/拆分错会让"事实唯一"误判。缓解：实体解析先于键计算（用实体 id 不用名字）、predicate 受控词表、`factKey` 生成记录 `ops` 可审计、冲突不删（误合并可回滚）。

### 4.2 观点归属

- `assertion=opinion` 的条目**必须**有 `attributed_to`（智能体/用户/外部来源实体）。
- 同一事实/话题的不同观点**允许并存**，**不触发 disputed**（它们不是矛盾的事实，是不同立场）；召回时按归属分组展示。
- 观点可以：
  - 被用户**采纳** → 生成 `norm/decision`（attributed_to=用户），观点条目保留为来源；
  - 被验证 → 提升为 `semantic/fact`（需 `system_verified` 证据）；
  - 无归属的观点（模型自说自话）**不能入库**，只能作为推断候选并标 `agent_inferred`。
- 智能体读取其他智能体的观点时，必须带"谁认为"的标注（§6.4 他者内容打标），不能当成自己的判断。

### 4.3 冲突保留（disputed）与询问策略

**冲突类型**：

| 类型 | 触发 | 处理 |
|---|---|---|
| `fact_contradiction` | 同 `factKey` 不同值 | 新条目 `disputed`，成对保留；询问/延迟 |
| `norm_conflict` | 同槽位规范互斥（如"只用 REST" vs "关键链路用 gRPC"） | 两条都保留（都 `disputed` 或新条目 disputed），询问/延迟 |
| `opinion_disagreement` | 同话题不同立场 | **不算冲突**，按归属并列（§4.2） |
| `scene_divergence` | 同场景不同结论 | 标"结论不一致"，保留两条，交整理者复核 |

**冲突记录字段**：`id`、`item_a`、`item_b`、`type`、`severity`、`status`（open / asking / deferred / resolved）、`ask_policy`、`ask_count`、`last_asked_at`、`resolved_by`、`resolution`（用户选择 → 生成新规范/事实）。

**询问/延迟策略**（对应 design-core "可询问用户，也可保留待后处理"）：
- **ask_now**：冲突影响当前决策/高风险动作/用户当场在讨论该话题 → 在回复里问（一两个选项，不展开）。
- **defer**：其余情况 → 保留 disputed，记入"待确认"，在合适时机（会话概览/相关话题下次出现/整理者复盘）问一次。
- **不重复打扰**：同一冲突默认最多问 1 次（`ask_count`），未答保持 disputed，不升级、不猜。
- **不阻塞**：冲突不影响系统继续工作；检索到冲突条目时成对带出 + 冲突横幅（沿用 v0.2 的"冲突可见"）。

**解决动作**：用户选 A/B/都不是 → 生成 `norm/decision`（attributed=用户）→ 被否决方 `valid_until` 闭合、`status=superseded`；冲突记录 `resolved`；历史全保留。

## 5. 金字塔：抽象层级、压缩、多视角

### 5.1 层级定义

| 层 | 内容 | 典型载体 | 例子 |
|---|---|---|---|
| **L0** 原始 | 消息、工具结果、任务步骤、working 状态 | raw_messages / raw_events / working 条目 | "10:13 执行的 SQL 返回 PG 14.9" |
| **L1** 会话 | 一次会话发生了什么、决定了什么、产出什么 | scene 条目 + 会话级 summary 节点 | "11-03 会话：定位连接池问题并修复" |
| **L2** 任务/项目 | 一个任务/项目层面的结论、复用做法 | scene/procedural/norm 条目 + 项目视图节点 | "Atlas 迁移项目的技术栈是 Go + SQLite" |
| **L3** 领域 | 领域级规范/程序/语义 | norm/procedural/semantic 条目 + 领域 summary | "后端：对外接口只用 REST" |
| **L4** 全局 | 用户长期目标/原则/偏好（显式） | norm/preference、goal 条目 | "我要求对话不阻塞、随时可打断" |

**注意**：层级不是存储分区，是**条目的抽象层级标记 + 视图组织方式**；同一条目通常只属于一个层（working 在 L0/L1，规范多在 L2–L3）。

### 5.2 存储 vs 视图（关键区分）

- **存储是扁平的**：所有条目在 `memory_items`，所有压缩节点在 `pyramid_nodes`；没有"每层一个表/一个库"。
- **视图是金字塔**：给定实体（如"项目 Atlas"或"域:后端"），按关系聚合其下条目 → 按层组织 → 向上压缩、向下下钻。
- **压缩节点是派生数据**：可随时删掉重建，不影响条目；检索命中压缩节点时，必须能展开到源条目（cite 链）。

### 5.3 压缩规则

**触发**：会话归档、任务完成、某实体下条目数超阈值、整理者后台定时/空闲。

**输入**：实体的子条目（必须带 `id@version` + cite）。

**输出**：`pyramid_nodes` 一条（`level=L+1`，`source_item_ids[]`，`text`，`coverage`）。

**硬规则**：
1. **只压缩、不新增**：压缩文本不得出现源条目里没有的事实/数字/结论（faithfulness；生成后做规则/模型校验）。
2. **必保留**：约束/否定（"不/禁止/必须"）、数字、日期、风险、未完成/失败项、未决问题。丢了即压缩失败。
3. **必须带 cite**：摘要的每句都能回指源条目（至少段落级 cite）。
4. **覆盖度门槛**：`coverage < 0.8` 不生成（或生成但标 `partial`），避免"只看了一半就总结"。
5. **版本化**：压缩节点有 `version`；源条目更新 → 节点 `stale`（§5.4）。
6. **不删除源**：压缩后源条目保留，只降低检索权重/标记已覆盖（detail 可下钻）。

**压缩比默认值**（【推断】，可调）：L1 ≤ 源文本 1/3；L2 ≤ 1/5；L3 ≤ 1/10；L4 只放极少量原则（字数上限）。

### 5.4 失效传播与重建

```
源条目 version++ / 失效 / retracted
   → 引用它的 pyramid_nodes 标 stale（invalid_at=now，status=stale）
   → 检索默认不返回 stale（除非 asOf 历史查询/显式展开）
   → 异步重建（从当前条目重新压缩；不依赖旧压缩结果）
   → 重建后 version++，status=active
```

- **传播链**：节点依赖节点时，沿 `source_node_ids` 向上传播一趟（L1 stale → L2 也 stale）。
- **重建可重放**：同一组源条目 + 同一压缩配置 → 应产出可比较的结果；压缩模型/提示词版本化，便于评测。
- **重建成本**：只重建受影响子树；全量重建仅在模型/策略升级时做（与索引重建同纪律）。

### 5.5 多视角投影

同一实体可以有多个"视角"，每个视角是一个 `pyramid_views` 记录（= 过滤条件 + 组织方式 + 视角目的）：

| 视角 | 过滤 | 回答 | 用途 |
|---|---|---|---|
| **事件视角**（what happened） | scene + working，按时间 | 这个会话/任务经历了什么 | 会话概览、复盘 |
| **认知视角**（what is） | semantic，按实体 | 关于这个实体我们知道什么事实 | 查询/回答 |
| **规范视角**（what should） | norm，按适用范围 | 对这个实体有哪些约束/决定 | 决策/风险门 |
| **程序视角**（how to） | procedural | 这类事该怎么做 | 执行/规划 |
| **状态视角**（current） | working，未失效 | 现在到哪了、卡在哪 | 任务面板/汇报 |

- 视角是**检索/展示参数**，不改变数据；新增视角 = 加一条 `pyramid_views`，不改表结构。
- 与"会话是视图"一致：会话实体是金字塔的一层挂载点；项目视图 = `mapped_to` 关系的聚合视角。

## 6. 智能体与记忆

### 6.1 智能体实体

| 字段 | 说明 |
|---|---|
| `id` / `name` | `agent:simo`（司墨，默认）、`agent:<role>` |
| `persona` / `persona_version` | 人格定义（风格、原则、行为模式）；**版本化**，防"人格漂移不可追溯" |
| `tools[]` / `model` / `reasoning_effort` | 能力与算力（模型可替换，沿用） |
| `memory_domain` | 写域（§6.2） |
| `memory_view` | 默认读视图（实体范围 + 类型 + 视角，§5.5） |
| `status` / `created_at` | 生命周期 |

**智能体是记忆中的实体**（design-core §4、【用户已定】）：它的身份、人格、记忆域都是可被引用的数据；"换模型/换进程"不改变它是谁。

### 6.2 记忆域：写域 vs 读集（两个正交维度）

- **写域（成员资格）**：`owner_agent`。谁产生/负责这条记忆，只有该智能体可写；其他智能体只能读或提交候选（由单写者决定是否收）。
- **读集（可见性）**：由 `entity_refs`（挂哪些实体）+ `owner_agent` + `sensitivity` 决定。

| 域 | 归属 | 谁能写 | 谁能读 | 例子 |
|---|---|---|---|---|
| `team` | 团队共享 | 司墨直写；专家提交候选 | 所有智能体 | "对外接口只用 REST" |
| `agent:<id>` | 智能体私有/通用 | 仅该智能体 | 所有智能体**只读**（design-core：不隔离） | 某专家"这类 bug 先复现再改"的经验 |
| 实体绑定（会话/任务/域） | 挂在实体上 | 该实体负责人（写域内） | 按实体可见性（会话参与者、项目成员） | 某会话的过程/决定 |

> **写域隔离是"防人格混乱"的机制之一**：智能体不能往别人的记忆域写，避免"我的经验变成你的"。

### 6.3 智能体通用记忆 vs 会话记忆（**不要混**）

| 维度 | 会话记忆 | 智能体通用记忆 |
|---|---|---|
| 归属 | 会话实体（`entity_refs` 含该会话） | `agent:<id>` 写域 |
| 生命周期 | 跟随会话（可归档，长期挂起） | 跨会话长期 |
| 内容 | 这次发生了什么/决定了什么/产出了什么 | 跨会话可复用的经验/程序/风格/教训 |
| 类型 | scene / working / 少量 norm/semantic | procedural / scene（提炼后）/ norm（工作方式） |
| 写入时机 | 任务完成/会话收尾 | **会话归档 + 周期复盘（整理者后台）** |
| 召回 | 按会话/项目/聚合视图 | 按智能体人格 + 当前任务类型 |
| 可见性 | 会话参与者/项目视图 | 其他智能体只读（design-core 不隔离） |
| 来源 | 会话 raw/canonical | **必须带 `source_conversations[]` + canonical/raw 引用**（从哪次会话提炼的） |

**提炼规则**：
1. **只从它负责的会话提炼**（`owner_agent` 匹配）；跨智能体的会话内容不得被提炼进自己的通用记忆。
2. **提炼必须有来源**：每条通用记忆的 `raw_refs`/`canonical_refs` 指向被提炼的会话；无来源不入库。
3. **提炼走候选 + 单写者**（与所有写入一致），可被用户查看/否决（记忆页只读，改走对话）。
4. **不得把会话私有信息带出**：`sensitivity=sensitive` 的会话内容不进入通用记忆（除非用户显式要求）。
5. **通用记忆的分层**：经验类先 `scene`（案例）→ 攒够独立会话佐证 → 提炼为 `procedural`（SOP）或 `norm`（工作方式）；门槛沿用 v0.2（默认 ≥3 独立会话；Q6 已定）。

### 6.4 人格防混乱（design-core §4 的四件事）

| 机制 | 设计 |
|---|---|
| **身份锁定** | 每个 turn 注入的 persona = 当前 agent 的 `persona@persona_version`；**上级会话只继承任务/需求/背景，不继承人格**（design-core §1）；换模型不换人格。 |
| **他者内容打标** | 读到的其他智能体记忆/观点，在上下文里标 `[agent:<id> 的观点]`（`attributed_to`），**不得**被当成自己的判断；注入时分区（自己的记忆 / 他人的只读记忆）。 |
| **只能写自己的记忆域** | 写入时校验 `owner_agent == 当前 agent`；跨域写一律拒（候选也不行，只能"转呈"给该域负责人/单写者）。 |
| **行为校验** | ① 角色断言：请求里带 role/agent id，输出契约禁止冒充他人；② 轻量 persona 校验（风格/禁用词/身份声明）在 L1 评测里做，不靠模型自觉；③ 越权工具（不在该 agent `tools[]` 内）由权限层拒。 |

**边界**：跨智能体"只读彼此人格/记忆"不等于"可以扮演对方"；读取他人内容必须带归属（§4.2），执行任务只能用自己的人格。

### 6.5 跨智能体只读的边界（需要拍板的灰度）

design-core 说"不隔离：智能体之间可只读彼此的人格/记忆"（【用户已定】）。但历史设计里 `sensitivity=sensitive` 不跨域（12 Q13）。**Lead 已拍板（v0.3.1，§12 Q4）**：默认只读共享，敏感例外不跨域。

- **默认**：所有智能体可读 `team` + 任意 `agent:<id>` 的记忆（只读）、可读彼此人格定义；
- **例外**：标 `sensitivity=sensitive` 的条目（PII/凭证/隐私）**不进入跨智能体读集**，仅来源智能体 + 用户可见；
- **其他例外**：用户显式说"这条只给我" → `private_to=user`；
- 例外清单要少（否则"不隔离"名存实亡），但必须有（否则隐私/安全无法兜底）。

## 7. 写入：原文不可变 + canonical 唯一入口

### 7.1 三层管道

```
用户消息 / 工具结果 / 事件
        │ ① 落库（同步、append-only）
        ▼
   raw_messages / raw_events          ← 永久、不可变、不直接检索/不直接写记忆
        │ ② canonical 化（意图识别 + 指代消解 + 归一化）
        ▼
   canonical_units                    ← 唯一处理入口；带 ops 与 raw_refs
        │ ③ 抽取/判定（候选）
        ▼
   memory_candidates                  ← 类型/实体绑定/事实键/归属/置信度
        │ ④ 单写者合并（结构冲突规则裁决；语义冲突 → disputed）
        ▼
   memory_items + 关系 + 金字塔       ← 真相层
```

**硬约束**：
- ①→②→③ 不可跳过；从 raw 直接写记忆 = 绕过质量闸，禁止（I3）。
- raw 与 canonical 都是**只追加**：canonical 版本化（`canonicalizer_version`），不原地改；raw 永不改。
- 记忆条目的 `content` 必须是 canonical 文本（或其压缩），**不是 raw 原文**。

### 7.2 canonical 化 8 步（设计稿，不写实现）

1. **采集**：raw 消息（含附件引用）+ 当轮工具结果。
2. **分段**：按语义段/轮次切分（与交互协议的"语义段"对齐）；一段可跨多条消息（连续补充）。
3. **意图识别**：陈述/提问/指令/偏好/纠正/闲聊/任务；为后续抽取定策略。
4. **指代消解**：把"它/那个/上次/刚才/我的项目"解析为实体 id；**高置信才改**，低置信保留原短语 + `status=unresolved`。
5. **归一化**：时间（相对→绝对 + 时区）、数值/单位、实体别名→规范名、否定/条件/情态保留。
6. **生成 frame**：`entities[]`、`relations[]`、`modality`、`polarity`、`time`、`conditions`、`speaker`。
7. **忠实性校验**：canonical 不得引入 raw 没有的主张；对比原文（规则 + 可选模型）通过才 `ok`。
8. **入库**：写 `canonical_units`（带 `ops` 与版本）；`unresolved/failed` 只留 raw，不进入记忆抽取（宁可不记，不写错）。

### 7.3 canonical 的质量规则

- **忠实优先**：改写 = 重述 + 消解 + 归一，**不是总结**；不丢限定词（"只有/除非/暂时"）。
- **幂等可重放**：同一 raw + 同一 canonicalizer 版本 → 同 canonical（用于评测与重建）。
- **可解释**：每条改写记 `ops`（消解了什么、归一了什么），用户/审计能看 diff。
- **版本化**：canonicalizer 升级 → **重放重建 + 可疑记忆标"待复核"**（不冻结旧版；Q1 已定）；记忆条目仍绑定旧 canonical，重建后需对照。
- **失败可见**：`unresolved` 不能被静默丢弃，应进"待澄清"（可在合适时机问用户，或保留原词不猜测）。

### 7.4 溯源链（raw ↔ canonical ↔ memory）

- 正向：`memory_item.canonical_refs[]` → `canonical.raw_refs[]` → `raw_messages`（原文可看）。
- 反向：从一条 raw 消息可查"它被 canonical 成了什么、被写进了哪些记忆、被谁用过"。
- 完整性：raw 与 canonical 存 `content_hash`；记忆条目存 `canonical_refs` + `content_hash`，防篡改与错配。
- UI/审计：记忆页每条可"查看原文与改写"（用户侧只读，符合"记忆可见、Spec 不可见"）。

### 7.5 二次污染防线（canonical 本身也是模型产物）

- canonical 化只允许**重述/消解/归一**，不允许"总结成事实"；事实抽取必须能回指 canonical 原句。
- 抽取分两类：**显式**（用户说"记住/以后都…"→ 高权威）与**推断**（agent 归纳 → `authority=inferred`，置信上限沿用 v0.2）。
- 错误止损：canonical 可重放修复 → 重新抽取；已写入的记忆走 `retracted`/版本回退，并沿金字塔标 stale。
- 写入仍走候选 + 单写者（不变），canonical 不绕过冲突检测。

### 7.6 写触发点（沿用 22 的 W1–W3，新增 W0/W4/W5）

| # | 触发 | 写什么 | 前置 |
|---|---|---|---|
| **W0** | 每条用户消息/工具结果 | raw + canonical（不写记忆） | 只追加；不阻塞对话回路（异步 canonical 化，失败重试） |
| **W1** | Task done（双裁决后） | scene/procedural/working 收尾 | 沿用 22 §3.2；`boundary.writeScope` |
| **W2** | Spec verified | norm/semantic 结论 | **`canArchive(specId)==true` 前置**（18 v0.3，沿用） |
| **W3** | 用户说"记住/改成/忘掉" | norm/semantic/working | 用户权威最高，但仍走候选与冲突检测 |
| **W4** | 会话归档 / 周期复盘 | 智能体通用记忆（§6.3） | 只从自己负责的会话提炼；带来源 |
| **W5** | 后台整理 | 金字塔压缩/失效重建/实体合并 | 派生数据；可重放；不写记忆真相 |

**写入频率与噪声控制**：同一实例同一任务候选批次 ≤3（沿用 22）；W4 低频（每日/归档时）；W5 后台且可配置。

## 8. 召回：实体/关系召回 + 金字塔下钻（与 design/22 融合）

### 8.1 召回七步（v0.3 版）

```
Step 0  输入：意图帧 + 当前会话/任务/智能体 + 查询
Step 1  查询理解：抽实体、关系、意图类型（事实/做法/现状/规范/经历）
Step 2  实体解析：别名/上下文 → 实体 id；可能的实体列表（歧义则带候选）
Step 3  多路召回：
          A 关键词（FTS5，V1 已有）
          B 实体邻域（关系 1–2 跳，按 rel_type 过滤）
          C 向量（P1，本地 ONNX；V1 不做）
          D 结构化过滤（type/layer/status/valid_until/authority/sensitivity）
Step 4  融合：RRF（k=60）融合多路排名 → 归一化为 rel
Step 5  关系下钻：沿 depends_on/part_of/about 下钻（预算内；标注"可展开"）
Step 6  金字塔定位：按意图选层（概览→L1–L2 + cite 下钻；精确→L0/L1；做法→procedural；现状→working）
Step 7  打包：cite + 8% 预算 + K=8 + 单条 ≤400 token + 冲突成对 + untrusted 封装
Step 8（可选 agentic）：追问/多步（≤3 步，每步有预算）
```

### 8.2 多路召回与 RRF（与 22 §4.5/§5 对齐）

- V1 实际可用：A（FTS5）+ B（实体邻域）+ D（结构化过滤）；C 留 P1。
- 融合用 RRF 而不是把不同分数硬加：`rrf(d) = Σ 1/(60 + rank_i(d))`，再归一化；**硬过滤先于融合**。
- 总分沿用 22 §5.4：`score = 0.50·rel + 0.25·imp + 0.15·rec + 0.10·str`；v0.3 不新增加权项，**实体距离只作 tie-break**（近实体优先）。
- `disputed` 成对：**不许拆开**、不许因分数低裁掉一方。
- 同 `factKey` 去重：只返回 active 事实（disputed 例外成对返回）。

### 8.3 金字塔定位（层级选择）

| 意图 | 默认层 | 注入形态 |
|---|---|---|
| "以前发生过什么/复盘" | L1 会话 → 下钻 L0 | 摘要 + cite 可展开 |
| "是什么/事实" | L2–L3 → 命中条目 | 条目原文（canonical） |
| "该怎么做/怎么做" | L3 规范/程序 | 规范/程序条目 |
| "现在到哪了" | L0–L1 working | 状态条目（短、最新） |
| "整体介绍/汇报" | L2–L3 摘要 | 压缩节点 + 下钻入口 |

**Inline & Spill**：高层摘要进上下文，细节只给 cite/指针；用户追问再下钻（控制 token）。

### 8.4 预算、cite、信任（沿用 design/22，不重复定义）

- 检索 ≤8% A、top-K 8、单条 ≤400 token；块/规范必进不裁；超限按 22 §2.5 降级。
- cite 硬要求：`[mem:id@ver]` / `[entity:…]` / `[pyramid:…]` / `[spec:…]` / `[episode:…]`；集外 cite 视为失败。
- 检索内容一律是数据不是指令；v0.3 新增 `[agent:<id> 的观点]` 归属标签与"他者记忆"分区。

### 8.5 agentic 检索（design-core 要求"全程 agentic"）

- 工具化：`memory_search(query, entities?, types?, layer?)`、`memory_drill(entity|relation)`、`memory_timeline(entity|session)`。
- 允许追问/多步（默认 ≤3 步），每步受同一预算约束，**不无限自检索**（沿用 22 §9.3 对 agentic RAG 的限制：V1 只做有限步）。
- 检索失败降级：空结果优于编造；索引不可用走"结构化过滤 + 最近 N 条"（沿用 22 §2.7）。

### 9.5 迁移步骤（memory 模块 v1 → v2）与回滚

2. **回填实体**：

   - `scope='task:ID'` → 建 `task:ID` 实体 + `belongs_to` 对应会话（从 `tasks.session_id` 取）；
   - `scope='instance:<id>'`（若有遗留）→ 映射到所属任务/会话；否则保留 legacy scope、`owner_agent` 记实例、可见性 private；
   - `refs` 里的 `session:/task:/spec:` → 关系/绑定。
3. **回填类型**：按 §3.2 映射写 `type/sub_type`；`kind` 与 `scope` 保留（投影）。
4. **回填 `fact_key`**：对 `semantic/fact` 条目离线计算（实体解析 + predicate 词表 + qualifier）；无法解析的置空（唯一索引只约束非空）；生成报告供人工抽查。
5. **迁 Spec 条目**：`kind='spec'` → 转入 `specs` 表（已存在）或标 `archived`；记忆只保留 `refs` 引用。
6. **重建 FTS**：建 `memory_fts_v3` 并全量导入；校验条数与抽样；切换读路径到新表；旧 `memory_fts` 保留一个版本后删除。
7. **双写期（1 个版本）**：新写入同时维护 legacy `kind/scope` 列，保证既有 API/前端/评测不破；读路径优先新字段、回退旧字段。
8. **校验与放量**：`count` 对账 + 抽样审计（`fact_key` 准确性、实体绑定正确性）+ 跑 M3 既有评测子集；全绿后才切换默认读路径。

**回滚**：保留迁移前备份；迁移失败 → 事务回滚；上线后发现问题 → 回滚二进制 + 从备份恢复（迁移不可逆，因此**必须**有备份）；双写期内旧列始终可读，降低回滚成本。

### 9.6 兼容与评测影响

- **API**：`GET /api/memory/items` 增加 `type/entityId/layer/includeChildren` 等参数；响应保留 `kind/scope`（legacy）；新增 `GET /api/memory/entities`、`/api/memory/graph`、`/api/memory/views`；**仍无写接口**（沿用 v0.2 纪律，修改走对话）。
- **评测**：M3 的 5 类 case（写入/作用域/冲突/检索/只读）必须继续通过（双写期保证）；新增 v0.3 case：事实唯一、观点归属、冲突保留与询问、canonical 溯源、实体召回、金字塔压缩与失效、智能体通用记忆隔离、跨智能体只读。
- **性能**：1 万条量级下多路召回 + 实体 join 预计毫秒级（【待核实】需实测）；金字塔压缩在后台，不阻塞读。

## 11. 风险与未知

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **canonical 改写失真**：模型消解错指代/丢条件 → 记忆从源头就错 | 污染且难发现 | 忠实性校验、`ops` 可审计、低置信保留原词、`unresolved` 不写记忆、可重放修复 |

| R3 | **金字塔压缩失真/过期** | 摘要层给出错误结论 | 只压缩不新增、必保留项、coverage 门槛、失效传播、stale 不返回、可重建 |
| R4 | **实体图噪声/膨胀** | 关系召回变差、成本上升 | 实体合并、关系来源分级、1–2 跳限制、定期整理 |
| R5 | **跨智能体只读 vs 隐私/安全** | 敏感信息扩散或人格串味 | 已定：默认只读共享 + sensitive 例外（Q4）、他者内容打标、写域隔离 |
| R6 | **迁移风险**（大数据量、回填错） | 数据/评测回归 | 备份、事务、双写期、抽样审计、评测门槛、回滚方案 |
| R7 | **多路 + agentic 检索成本/延迟** | 首 token 变慢 | 硬过滤先行、预算不变（8%/K=8）、agentic ≤3 步、V1 不做向量 |

## 12. 已定结论（Lead 拍板，v0.3.1）

> **状态：已定**。以下 10 条由 **Lead 于 2026-11-08 拍板**：Q1–Q4 为 Lead 的明确决定，Q5–Q10 按初稿建议的默认值。如用户后续否决，按 `Qx 改成 …` 回退并在版本记录追加。

**Q1. canonical 重建策略（canonicalizer / 模型升级后）**
- A. 重放重建，记忆条目自动重新对照、可疑的标"待复核"；B. 冻结旧 canonical，只对新消息生效；C. 逐条人工审
- **已定：A**（Lead 拍板）。决定 = **重放重建 + 可疑记忆标"待复核"**，不冻结旧版。影响：保持一致性，重建会触及历史记忆。

**Q2. 原文不可变的删除例外**
- A. 只做 tombstone（内容脱敏、保留 id 与哈希）；B. 用户明确要求 + 二次确认后才物理删除；C. 一律不删
- **已定：A（更严格版）**（Lead 拍板）：**raw 永久不可变**；**仅合规流程**可走"标记删除"（内容脱敏、保留 id 与哈希，**不物理删除**），且必须**审计留痕**。影响：可追溯性优先；本设计不提供物理删除路径。

**Q3. 事实冲突是否允许"按权威自动裁决"**
- A. 不自动裁决，一律 `disputed`（design-core 语义）；B. 允许 `user_confirmed/system_verified` 自动覆盖 `inferred`；C. 全部人审
- **已定：A**（Lead 拍板，遵循 design-core）。**事实冲突一律 `disputed`，不允许按权威自动裁决**；可询问、可延迟。影响：最稳，但会积累 disputed。

**Q4. 跨智能体只读的边界**
- A. 全部只读共享（人格+记忆，含 sensitive）；B. 默认只读共享，`sensitivity=sensitive` 例外不跨域；C. 只共享 team 域
- **已定：B**（Lead 拍板）。**默认只读共享；`sensitivity=sensitive` 例外不跨域**。影响：兼顾"不隔离"与隐私兜底。

**Q5. 智能体通用记忆的提炼时机**
- A. 会话归档时 + 每日复盘（低频后台）；B. 仅会话归档；C. 每个任务结束都提炼
- **已定：A**（按初稿默认）。影响：低频后台，噪声与成本可控。

**Q6. 金字塔层级与压缩触发**
- A. 五层 L0–L4；触发 = 会话归档/任务完成/条目阈值；B. 简化三层（会话/任务/领域）；C. 暂不做自动压缩，先手工视图
- **已定：A**（按初稿默认）。影响：层级完整，压缩实现复杂度较高。

**Q7. Spec 是否保留为记忆类型**
- A. 不保留（design-core：Spec 属于会话，记忆只引用）；B. 保留 `kind=spec` 仅内部
- **已定：A**（按初稿默认）。影响：需迁移现有 Spec 条目；与 design-core 定位一致。

**Q8. 旧 kind/scope 兼容策略**
- A. 保留 legacy 投影 + 双写一个版本，之后清理；B. 一次迁移，不做兼容
- **已定：A**（按初稿默认）。影响：迁移安全、双写期多写一列。

**Q9. 观点归属的粒度**
- A. 每条观点必须带 `attributed_to`（实体级），同话题多观点并列展示；B. 允许"未归属观点"作为推断；C. 观点并入规范，不单独建模
- **已定：A**（按初稿默认）。影响：观点可追溯到"谁说的"。

**Q10. 智能体写团队记忆的权限**
- A. 仅司墨直写 team，专家提候选由单写者合并；B. 所有智能体可直写 team；C. 团队记忆只读，全部走候选
- **已定：A**（按初稿默认）。影响：与"只写自己记忆域"一致，专家经验经候选沉淀。
