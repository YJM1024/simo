### 0.4 一句话速览（先看这个）

1. **A. DSH 的强项在"运行时底座"**：事件溯源日志、三屏障检查点、token 计量闭环、压缩/裁剪、工具管线、委派 seam——恰好补我们 10 §27 列出的内核缺口。
2. **B. Codex CLI 的强项在"安全模型 + 产品面"**：沙箱与审批正交、受保护路径、AGENTS.md、goal 三要素、记忆 generate/use 分离。
3. **C. Claude Agent SDK 的强项在"权限求值顺序 + 评测框架 + 持久规则/压缩解耦 + 信任边界"**：六步权限求值（hooks→deny→ask→mode→allow→canUseTool）、plan 模式对子代理同样生效、`WITH/W/OUT/Δ` 三列 eval 与六种 grader、CLAUDE.md 每轮重注入且与压缩解耦、子代理输出指令形态中和。**但其"一 session 一 claude 子进程"的形态，Go 不抄——用 goroutine 做一进程多会话。**
4. **我们的强项不在这些报告里**：记忆语义（主体/作用域/候选单写者/权威分轴/失效优于删除）与交互语义（连续步进/三速/撤回/中断点/歧义先确认）是我们独有的设计；不要把三家的"记忆"直接套过来。
5. **最大缺口**（10 §27 已自陈）：**RAG、上下文工程、提示词工程、评测**四项"没有设计"；三家恰好在这四项上各有可借零件（DSH 压缩/提示词注册表、Codex AGENTS.md/goal、Claude eval/持久规则/工具检索）。

## 2. 详细对照（21 个维度）

> 说明：标 **【同核】** 只用于 Codex CLI 与其 SDK 封装（附录 A），不用于 C 列。C 列证据以 `research/claude-agent-sdk-mechanisms.md` 章节 + 官方文档短路径标注。

### D1 系统定位与形态

| 维度 | A. DSH | B. Codex CLI | C. Claude Agent SDK | 我们的选择/借鉴（引用 design/10） |
|---|---|---|---|---|
| **D1 定位与形态** | **做法**：本机 Desktop（Electron/Node）通用 agent 运行时；Super-agent 另有"常驻双层 Router/Worker"的设计主张。〔码-R〕dsh-mechanisms §0；〔A〕super-agent-report §1–2。**借**：本地优先、单机可跑、Router/Worker 职责分离思想。**不适用**：双层+事件驱动是 Super-agent 的形态，不是我们要的。 | **做法**：终端交互式编码 agent（TUI + `codex exec` 非交互），Rust 内核，开源 `openai/codex`；官方文档〔A〕Non-interactive；〔B〕仓库结构 codex-rs/、codex-cli/、sdk/。**借**：交互面与批处理面分离。**不适用**：TUI 形态（我们交付是 Web）。 | **做法**：**不是库，是子进程监管器**——`query()` spawn 一个 `claude` CLI 子进程（stdio 通信），一 session 一子进程，子进程拥有 shell/cwd/JSONL transcript；SDK 内 bundle native CLI，版本钉在 SDK 包上。〔A〕docs: agent-sdk/hosting、overview；报告 §0.3。**借**：进程级隔离/监管语义、二进制版本绑定。**不适用**：**Go 不抄这个形态，用 goroutine 做一进程多会话**（报告 §8.3/§9.4；Go 资源效率高一个量级）。许可/品牌限制也决定它不能当产品内核（报告 §0.6〔A〕）。 | **本地 Web 单机单人，一个秘书**（10 §2：本地 Web + React/Go 单体；10 §4：唯一秘书）。**不引入 DSH 运行时、不套双层/事件驱动**（10 §4、§28；12 §12）。DSH 只作机制参考，不作运行时（10 §27）。 |

### D2 驱动源与入口

| 维度 | A. DSH | B. Codex CLI | C. Claude Agent SDK | 我们的选择/借鉴 |
|---|---|---|---|---|
| **D2 驱动源与入口** | **做法**：Super-agent 以环境事件为主输入（Source→Trigger→Gate/Assessment→Worker）；DSH 实现里人消息与 steer/followup 也是入口。〔A〕super-agent-report §3；〔码-R〕dsh-mechanisms §1.5。**借**：两级过滤（先程序后模型）、Trigger 幂等。**不适用**：我们没有 IM/CI/邮件等环境事件源；V1 人是唯一驱动。 | **做法**：人在 turn 里输入；`turn/steer`（并入当前轮）与 Queue（下一轮）分离；`thread/inject_items` 只注入不开启 turn。〔A〕App Server / Prompting。**借**：steer/queue 二分、注入与唤醒分离。**不适用**：键盘快捷键形态。 | **做法**：两种输入模式——**Streaming Input**（`prompt` 传异步生成器；持久交互、可排队、可实时打断、可中途 `setModel`/`setPermissionMode`）与 **Single Message Input**（一次性 `query()`；不支持图像/排队/打断/自然多轮）。官方推荐 streaming。〔A〕docs: agent-sdk/streaming-vs-single-mode；报告 §1.1。**借**：双入口"一次性 vs 流式"、streaming 独有的控制能力。**不适用**：single 模式的能力缺口（Go 默认流式 channel，需要时再一次性）。 | **人始终在场的连续对话**（10 §4/§7：不要一问一答、不要可感知队列）；**不做事件驱动领域模型**（10 §4、§28；12 §12）。**借** steer/queue 与 streaming 双入口语义，落进 13 的"连续步进 + 四类消息"（10 §7；13 §5）。**【已采纳·用户 2026-11-06：steer/queue 分离】** |

### D3 Agent Loop 结构

| 维度 | A. DSH | B. Codex CLI | C. Claude Agent SDK | 我们的选择/借鉴 |
|---|---|---|---|---|
| **D3 Agent Loop** | **做法**：turn/step 显式状态机，inbox 认领（纯删除）、每步从日志派生历史；工具并行安全/独占屏障；五段工具管线；取消三态；**无内建 turn 预算**。〔码-R〕dsh-mechanisms §1.1–§1.6。**借**：turn/step 两层、失败三态、每流一个终止事件。**不适用**：无预算（我们要有 SLA/兜底）。 | **做法**：Thread→Turn→Item 三层；7 个动作（start/resume/fork/turn start/steer/interrupt/读事件）；停止条件 4 类；中断是"请求"而非杀进程。〔A〕App Server；〔B〕codex-rs/core/src/codex_thread.rs。**借**：三层命名、steer 独立原语、中断请求式、`turn.completed` 带 usage。**不适用**：Item 类型绑产品面。 | **做法**：Session→Turn→Message；流里五类消息 `System/Assistant/User/Stream/Result`；主循环五步；**Result 五态**（success / error_max_turns / error_max_budget_usd / error_during_execution / error_max_structured_output_retries）；`maxTurns` 计数=有工具调用的 turn + 1 个纯文本收尾；单发模式在 error result 后还会 raise、streaming 模式存活；**turn 在 SDK 内部完成，不交还控制权**；只读工具并发、写工具串行、自定义工具默认串行（需 `readOnlyHint`）。〔A〕docs: agent-sdk/agent-loop；报告 §1.1。**借**：五分类消息、Result 五态、`maxTurns` 口径、"迭代到流结束再 break"、只读并发/写串行默认。**不适用**：turn 内部完成导致无法中途插手（只能 hooks）；一 AssistantMessage 一 content block 需消费方聚合；工具名 `Task`→`Agent` 漂移。 | **连续步进 + 三速响应 + 语义段抢占**（10 §7；13 §3–§8）；**四类消息**（13 §5）；**撤回未完成回复**（10 §13；13 §3.2/§8.5）。借五分类/Result 五态/`maxTurns` 口径/流结束语义；改造为"人随时插入 + 撤回重答"（比 Claude 的 turn 内不可插手更细，见 13 §8.3）。 |

| D1 定位与形态 | 官方 TS/Python 库；Python 文档明确"controls the local Codex app-server over JSON-RPC"，TS 底层同依赖本地运行时的推断标 [D]。 | 不是独立架构；与 CLI 共用内核，只换接口面。 |
| D2 驱动源与入口 | 宿主程序发起 `startThread → run(prompt)`（批处理）；事件流需订阅 app-server 通知；宿主可循环调用实现多轮。〔A〕Codex SDK；〔D〕文档未展示流式（待核实）。 | CLI 的键盘 steer/queue 在 SDK 面退化为程序调用/事件订阅。 |
| D3 Agent Loop | SDK 面只暴露 `run()`（一次拿最终结果）与 `resumeThread`，流式/工具事件要看 app-server 通知；TS 文档未见流式（待核实）。 | 同一 turn/step 内核；SDK 无"实时打断键"，需用事件面/取消 API。 |
| D4 会话模型 | `startThread()` / `resumeThread(id)` / `run()`；`include_turns=False` 可"有上下文但不回灌历史"；无 TUI 的 cwd 选择交互。 | 与 CLI 共用 thread 持久化；SDK 少了交互式恢复选择。 |
| D5 消息/事件模型 | 通常只把 final response 暴露给调用方（批），完整事件流走 app-server 通知；是否内置事件订阅待核实。 | 与 CLI 的 `--json` 事件流同源。 |
| D6 上下文工程 | 压缩发生在 app-server 内核，SDK 通过配置/宿主间接影响，SDK 文档未细述压缩 API。〔D〕待核实。 | 压缩实现与 CLI 相同；SDK 无专用压缩入口。 |
| D7 提示词工程 | SDK 在 `turn/start` 里传覆盖项（model/cwd/sandbox），系统提示/指令文件由内核对接受控；未提供"按角色拼 prompt"的公开面（待核实）。 | 与 CLI 共用 AGENTS.md/指令系统。 |
| D8 记忆 | SDK 面没有公开的 memories 管理 API（〔D〕待核实）；宿主可读配置开关。 | 记忆仍在 CLI/内核侧配置。 |
| D9 RAG/检索 | SDK 侧没有检索 API；检索仍由 agent 工具完成（待核实）。 | 与 CLI 相同。 |
| D10 工具模型 | SDK 可注入 dynamicTools（`item/tool/call`，实验）〔A〕；未提供工具注册公共面〔D〕待核实。 | 内核工具集相同；SDK 可注入实验性动态工具。 |
| D11 沙箱 | 可在 `turn/start` 覆盖 sandbox policy（per-turn override）〔A〕；SDK 不改变实现。 | 内核沙箱相同；SDK 把 policy 作为调用参数。 |
| D12 权限与审批 | SDK 面通过 app-server 接收 approval 请求，但 SDK 文档未详述调用侧交互〔D〕待核实。 | CLI 有交互式审批 UI；SDK 需宿主自行实现应答。 |
| D13 规划 | goal 通过 `thread/goal/set|get|clear` 暴露给 SDK（可程序化）；`/plan` 属 CLI 交互概念，SDK 无同名面〔A〕+〔D〕。 | SDK 可读写 goal，但没有 slash 命令。 |
| D14 长任务 | `resumeThread` 续跑、`run()` 批处理；长任务流式续跑需 app-server 事件面〔D〕。 | 续跑语义与 CLI 相同；SDK 无 TUI 恢复交互。 |
| D15 多 agent | SDK 侧多 agent 暴露面有限〔D〕待核实。 | 多 agent 主要在内核/配置侧。 |
| D16 评测 | SDK 适合在 CI 里批处理跑任务（`run()`），可作为评测驱动面〔A〕/〔D〕。 | CLI 有 `/review` 等交互式检查；SDK 批处理适合回归。 |
| D17 可观测性 | SDK 宿主是否透传 OTel 取决于调用方〔D〕待核实。 | 指标在内核/宿主层；CLI 有默认输出。 |
| D18 扩展性 | SDK 两种面——批处理（`run`）与事件面（app-server 通知）；TS/Python 库；服务端嵌入。〔A〕Codex SDK。 | 双接口面是 SDK 封装的价值；CLI 只有交互面 + exec。 |
| D19 部署/数据/离线 | SDK 需要本地 Codex runtime；部署形态=宿主进程 + 本地 app-server；离线取决于宿主。（〔A〕Python 文档 / 〔D〕待核实） | 与 CLI 共用本地存储；SDK 无独立数据库。 |
| D20 成本/性能 | 批处理适合 CI/离线批量（一次 run），事件面适合交互；成本由宿主 runtime 计量。〔A〕/〔D〕。 | CLI 的 `turn.completed` usage 同样可用于 SDK。 |
| D21 注入防护 | SDK 宿主需自行保证不可信输入策略（SDK 文档未提供防护 API）〔D〕。 | CLI 侧有 web_search cached 等默认；SDK 需宿主对齐。 |

## 7. 附：Codex CLI 的"同核不同面"对照（CLI vs SDK 封装，避免重复结论）

| 能力 | 同核（app-server 内核） | CLI 面（B 列） | SDK 封装面（附录 A） |
|---|---|---|---|
| 会话 | thread/turn/item 模型、SQLite+rollout 持久化 | TUI 恢复、`codex exec resume` | `startThread/resumeThread`、`run()` |
| 输入 | turn/steer/queue | 键盘 Enter=steer、Tab=queue；`--json` | 程序调用；事件订阅 |
| 审批 | approval policy / 五态 | 交互式弹窗/`on-request` | 宿主接收 approval 请求（文档未详述） |
| 上下文 | 压缩/裁剪/预算 | 配置项 + `/compact` | 经配置/宿主间接 |
| 记忆 | local memories + 开关 | Settings/AGENTS.md | 未见公开管理 API |
| 沙箱 | 三模式 + OS 实现 | 启动探测、`codex sandbox` | `turn/start` override |
| 规划 | plan item / goal 状态 | `/plan`、`/goal` | `thread/goal/*` |
| 评测 | ——（无内建） | `/review`、goldens 自建 | CI 批处理入口 |

> 结论：**Codex CLI 与它的 SDK 封装不是两套架构**；对照时应把"接口面"当变量、内核当常量。我们的借鉴对象是**内核机制**，不是 CLI 键位或 SDK 封装。**C 列（Claude Agent SDK）是另一个独立架构**（子进程模型 + 六步权限 + eval 框架），已在本表 §2 单独讨论。
