## 0. 一分钟读法

1. **六层 + 二分**：上下文按"钉住前缀（pinned prefix）/ 动态尾部（dynamic tail）"二分；前缀只放**稳定且高权威**的东西（系统不变量、持久规则、人格风格、工具定义），尾部放**每步变化**的东西（Spec 视图、Frame、记忆命中、对话窗口、上一步工具结果、检索注入、环境事实）。
2. **预算四件套**：`W` 窗口、`O` 输出预留、`T` 工具定义预留、`S` 安全边界；可用预算 `A = W − O − T − S`，按配额分给各层，超配额先走 **Inline→Spill** 而不是压缩。
3. **压缩三段式（一笔可回放的事务）**：① 剪工具输出（纯函数、无模型调用、被 `read` 读取的结果豁免）→ ② 结构化摘要（一次辅助请求，**逐字重放 system+tools+被压区间**以命中 provider warm prefix）→ ③ `compaction/start → summary → replace → end` + `compact_boundary` 事件；**未闭合的 start 就是锁**。
4. **压缩后重注入**：钉住前缀（规则/门禁/输出契约）+ 一段 ≤20 行的"当前阶段 + 下一步该做什么 + 不可丢项"短段；重注入与压缩**解耦**（每步都注入，压缩只是"额外的必须重注入时机"）。
5. **检索按需、结果带引用**：记忆条目/Spec 片段/文档/episode 四类检索源；结果一律 `[cite]` + 截断 + 来源标签 + 去重；检索失败**不阻塞**，只记 `budgetReport`。
6. **父子不灌入**：父 Spec 看子 Spec 只拿"摘要 + handle + 指针"，子对话默认不进父上下文；跨会话取用只读、不复制。
7. **缓存友好**：前缀版本化（`prefixHash`），**只有前缀变化才允许重建**；对话/结果/检索只追加在尾部，保证 warm prefix 命中；每步记录 `cache_read_input_tokens`。
8. **失败降级五条**：超窗口→压缩→仍超→摘要+指针；压缩失败→降级 compactor→仍失败→摘要+指针并可见说明；检索失败→空结果；**规则缺失/超预算→拒绝编译 + 报错**（不降级、不截断）；计量不可用→估算 + 标注 `estimated`。
9. **V1 只做**：前缀/尾部装配（含 L1 角色槽位）、配额与计量、主动+被动压缩三段式、重注入、常驻块 + 条目检索 top-K、Inline/Spill、父→子摘要聚合、结构断言与 11 个上下文判定点（P-C1..C11）；其余进 P1。
10. **本稿交付**：装配流水线、预算模型、压缩策略、检索接口、Inline&Spill、父子聚合、缓存友好、失败降级、指标/判定点、V1/P1；**拍板结论见 §12.3**（Q1/Q2/Q5 已由用户 2026-11-06 授权 lead 定案，Q3/Q4 按默认推进）。

## 1. 定位、边界与契约

### 1.1 E2 是什么 / 不是什么

| 维度 | 结论 |
|---|---|
| **是什么** | Loop 每次 `assembling` 阶段调用的**纯函数式装配器**：输入一个"上下文状态快照"，输出一个 `InjectionPlan`（请求消息 + 工具 schema + 预算与来源报告 + 是否需压缩）；外加**预算/压缩/检索/ spilled 引用**的规则集。 |
| **不是什么** | 不是提示词文本（E3 拥有 section 文本与措辞）；不是检索实现（E4 拥有索引与召回，E2 定接口与预算）；不是规划器（E5）；不是记忆写入（12 的单写者）；不是 Loop 状态机（19）。 |
| **交付形态** | 文档 + 不变量 + 判定点；实现落 M2（组装/预算/压缩/重注入）+ M4（检索接口）+ M6/P1（父子聚合、增量优化）。 |
| **成功标准** | ① 每一步的请求**可重建、可解释**（每个注入项有事件 id、有预算归属）；② 长会话**不因上下文丢失而返工**；③ 压缩**不抖动**、可回放；④ warm prefix 命中可度量。 |

**输出**（写回 `step/assembled` 事件，19 §4.1 ①）：

```text
InjectionPlan {
  request: { system: Section[], messages: Msg[], tools: ToolSchema[] },
  canonicalHash,                 // 全 envelope 的规范哈希（供 E1 回放对账，D8 吸收 21 增量）
  prefixHash,                    // 钉住前缀的版本哈希 = H(L0 段, L1 角色段)

  tokenEstimate { total, breakdown{system,rules,persona,tools,spec,memory,dialogue,results,retrieval,contract,env} },
  budgetReport { A, used, perLayer[], overQuota[], actions[] },   // 让"没生效"可诊断（12 §4.3）

  untrustedBlocks[] { id, kind, cite, escaped, neutralized },     // 不可信内容统一登记；neutralized 表示 E3 已做输出中和
  inline[] / spillRefs[],        // 内联 / 溢出引用
  needsCompaction { needed, scope, reason },                      // Loop 决定是否先压（19 §9.2）
  warnings[]                     // 截断/降级/估算标注（注意：S2 超预算不是 warning，而是编译失败）
}
```

**对齐约束**：E2 的所有输出必须保持 19 §9.1 的六条不变量：① 每项可追溯；② 记忆条目不可静默丢（**硬断言**）；③ 持久规则每步重注入；④ 被撤回文本不得重新进入上下文；⑤ 不可信内容统一封装；⑥ 同一状态组装结果**确定**（顺序稳定、可 hash 对账）。

**与 19 v0.1 的字段差异（标「待对齐」）**：19 v0.1 §4.1 的 `step/assembled` 记录 `envelope 哈希、token 估算、breakdown、注入来源`，§9.1 输出字段为 `request/tokenEstimate/breakdown/provenance[]/untrustedBlocks[]/needsCompaction`。本稿输出是它的**超集**，额外含 `prefixHash`、`budgetReport`、`inline[]/spillRefs[]`、`warnings[]`；**语义一致、字段扩展**，建议 19 下次修订并入。**当前标「待对齐（扩展字段）」**，不视为设计冲突。

### 1.4 角色槽位（L1）与 L0 稳定前缀的关系（【对齐 design/21 v0.1 · 差异 D3】）

**背景**：21 §4 定义四类角色（秘书/专家/评审/摘要），各有独立的目标/权限/禁止事项/输出契约；其差异 D3 指出本稿 v0.1 只有 S3 人格/风格，**没有角色槽位**——若不修，专家与评审会继承秘书的身份与 Iron Law。

**设计：前缀拆成 L0（公共）+ L1（角色）两段**

| 段 | 内容 | 变化频率 | 缓存 |
|---|---|---|---|
| **L0 公共前缀** | `S1a` 角色无关的通用硬约束（不可信内容、诚实与证据、安全边界、"提示词不做门禁"声明）+ `S2` 持久规则 + `S1.contractSchema`（`DecisionEnvelope` schema 说明） | 跨角色/跨会话稳定 | 可缓存（`l0Hash`） |
| **L1 角色前缀** | 角色槽位：`identity.<role>@v`、`ironLaw.<role>@v`、`persona.<role>@v`（可空）、`toolWhitelist.<role>@v`、`roleProhibitions.<role>@v`、`outputFocus.<role>@v` | 换角色才变（agent 生命周期内固定） | 同角色可缓存（`roleHash`） |
| **完整前缀** | `L0 + L1`；`prefixHash = H(L0 段, L1 段)`，另记 `l0Hash` / `roleHash` | — | — |

**不继承规则（硬，可测）**：

1. 秘书的 **Iron Law 与人格只存在于 `secretary` 的 L1**；`expert`/`reviewer` 的 L1 使用各自版本（或显式空），**不得引用 `secretary` 段**。
2. **编译期校验**：`roleProfile.role` 必须与所有角色段 id 的角色维度一致（如 `identity.expert@v` 只能配 `role=expert`），不一致 → **拒绝编译**（错误码 `ROLE_SECTION_MISMATCH`）。
3. `summarizer` 的 L1 = 压缩专用（不可丢项清单 + 摘要模板 + 输出限制），**不含**秘书身份/铁律/人格。
4. L1 同时决定**可见层集合**：秘书=全部；专家=L0 精简 + brief + 必要工具（**看不到父对话与 Spec 全文**）；评审=L0 精简 + review-package（**无工具**）；摘要=L0 精简 + 被压区间。E2 在装配期按角色裁剪尾部各层（见 §3.4 角色可见性）。

**与 L0 稳定前缀的关系（缓存语义）**：

- L1 位于 L0 **之后**、动态尾部之前，符合 21 §1.1 的"稳定性升序"；L1 变化只影响 `roleHash`，**L0 字节不变**。
- 因此：**同角色**的跨会话/跨实例请求可完全命中前缀缓存；**不同角色**的请求仍能复用 L0 的共同前缀（provider 按最长公共前缀命中，首个不同 token 起失效），`l0Hash` 用于单独度量这部分复用率（E2-M02 分桶）。
- 角色在 agent 生命周期内固定（换角色 = 新 agent/新实例，19 §8），所以 L1 稳定，**不会每步重建前缀**。

| S1 配额 | 8% A | **S1a ≤4% A、S1b ≤4% A**（合计不变） | 提议，需联调 |
| S3 配额 | 3% A | 3% A 仅秘书；**专家/评审/摘要 = 0** | 提议，需联调 |

| T3/T4/T5 | 固定配额 | 专家/评审按可见性收缩（专家 T4=0、评审 T3/T4/T5≈0），**释放的预算回到 T2/T5** | **待 E1/21 联调确认** |

## 2. 术语与四个基础量

| 术语 | 定义 | 备注 |
|---|---|---|
| **钉住前缀**（pinned prefix） | 一段**长期不变或变化极慢**的 system 段序列：`L0 公共前缀`（S1a 通用硬约束 + S2 持久规则 + 契约 schema）+ `L1 角色前缀`（identity/ironLaw/persona/工具白名单；见 §1.4） | 变化即 `prefixHash` 变；**L0 跨角色共享**（`l0Hash`），**L1 同角色稳定**（`roleHash`）；不得包含会话内容 |
| **L1 角色槽位** | 秘书/专家/评审/摘要四选一的角色前缀（身份/铁律/禁止事项/输出侧重/工具白名单）；**专家与评审不继承秘书人格与 Iron Law** | 【对齐 design/21 v0.1 · D3】见 §1.4 |
| **契约空位**（`contract.slot`） | "本次要输出什么"的空位声明（结构固定、内容每步变） | 【对齐 21 · D5】**并入 T1 尾段**，不动 `prefixHash` |
| **动态尾部**（dynamic tail） | 每步重算的消息序列：任务帧 → 记忆 → 对话窗口 → 上一步结果 → 检索注入 → 环境事实 | 只追加/替换，不重写头部 |
| **常驻块 block** | 12 §2.0 ①：每轮必带、不受检索预算裁剪的短文本段（约束/偏好/当前目标/作用域说明） | E2 给**配额上限**（见 §3.4） |
| **条目 record / episode** | 12 §2.0 ②/③：可检索结构化条目 / 不可变原始流（只作证据，注入只带指针） | E2 只接受"条目摘要"与"episode 指针"，**不接受 episode 全文** |
| **W / O / T / S** | 窗口 / 输出预留 / 工具定义预留 / 安全边界 | 见 §3.1 |
| **生效预算 A** | `A = W − O − T − S` | 所有层配额按 A 的比例算 |
| **压缩窗口前缀**（compaction-window prefix） | 压缩后保留的"锚"（钉住前缀 + checkpoint + 最近 K 条逐字对话）；之后阈值只算**前缀之后的增量** | 【借鉴 Codex `body_after_prefix`】防"刚压完又立刻超"的抖动 |
| **重注入短段**（re-inject digest） | 压缩后强制重放的 ≤20 行短段：阶段 + 下一步 + 不可丢项指针 | 与"持久规则每步注入"解耦（规则本来每步都在） |

## 3. 装配流水线（每步做什么、按什么顺序）

### 3.1 总体流程（进入 Loop 的 `assembling` 阶段）

```text
┌ 0 取快照：specView/frame/brief/memoryView/surface/results/rules/env/budget
│
├ 1 计算预算：A = W−O−T−S；按模型/阶段取配额；读 meter（provider usage 优先）
│
├ 2 决定是否先压缩 → needsCompaction（19 §9.2 的四种触发）
│     若需要：执行压缩事务（§5）→ 成功后重取 surface/rules digest，回到 1
│
├ 3 选择角色槽位（L1）：按 roleProfile.role 取 identity/ironLaw/persona/工具白名单/禁止事项
│     校验 role 与段 id 一致（不一致 → ROLE_SECTION_MISMATCH，**拒绝编译**）
│     专家/评审不得引用 secretary 段（§1.4 不继承规则）
│
├ 4 构建钉住前缀（稳定优先，命中缓存）：
│     L0 公共段：S1a 通用硬约束 + S2 持久规则（全文；**超预算即拒绝编译**）+ S1.contractSchema
│     L1 角色段：S1b 角色身份/铁律 + S3 角色人格（仅秘书；专家/评审为空或专属）+ S4 角色工具白名单
│     → l0Hash = H(S1a,S2,S1.contractSchema)；roleHash = H(L1 段)；prefixHash = H(l0Hash,roleHash)
│
├ 5 构建动态尾部：
│     T1 任务帧：goal/constraints/acceptance/specBinding/stopPolicy + **尾段 `contract.slot`（本次空位）**
│     T2 当前 Task：brief 摘要 + writeScope + requiredEvidence（全文走 handle）
│     T3 记忆：常驻块（必进）+ 检索条目（top-K，带 cite/截断）+ 冲突提示
│     T4 对话窗口：保留最近逐字对话 + 更早的 checkpoint 摘要（+ compact_boundary 标记）
│     T5 上一步结果：工具结果/子代理结算（Inline 或 Spill 指针，见 §7）
│     T6 检索注入（若 T3 未覆盖或多源检索，见 §6）
│     T7 环境事实：时间/工作目录/模型/阶段（user-role 快照，不改前缀）
│
├ 6 配额校验与压级：任一超配额 → 先 Inline→Spill（§7）→ 再"摘要+指针"→ 才报 needsCompaction
│     （S2 超预算例外：**直接拒绝编译**，不走降级；见 §3.4 / D4）
│
├ 7 确定性排序与渲染：层内按固定键排序（id/时间），层间按 L0→L1→T1..T7；计算 tokenEstimate/breakdown
│
├ 8 产出 InjectionPlan（含 canonicalHash/prefixHash/provenance/untrustedBlocks/warnings/budgetReport）
│
└ 9 Loop 写 `step/assembled`（canonicalHash、promptSetVersion、breakdown、来源）→ B1 请求前检查点 → 发请求
```

### 3.2 层表：来源、顺序、频率、预算、缓存影响

| # | 层 | 内容 | 来源 | 变化频率 | 默认预算 | 缓存影响 | 允许截断/降级 |
|---|---|---|---|---|---|---|---|
| **S1a** | 通用硬约束（L0） | 角色无关：不可信内容规则、诚实与证据、安全边界、"提示词不做门禁"声明 | E3 + 18 阶段表（角色无关部分） | 极低 | ≤4% A | **在 L0**（`l0Hash`） | 否（必须完整；超限是配置错误） |
| **S2** | 持久规则（L0） | 项目规则（AGENTS.md 式）**全文** + 版本号 + `rulesHash` | 规则文件 | 文件内容 hash 变化 | ≤10% A | **在 L0** | **禁止截断/丢弃**：超预算 → **拒绝编译 + 报错**（D4） |
| **S1b** | 角色段（L1） | 角色身份/铁律/禁止事项/输出侧重（`identity.<role>@v` 等） | E3（按角色） | 换角色才变 | ≤4% A | **在 L1**（`roleHash`） | 否；role 与段 id 不一致 → 拒绝编译（`ROLE_SECTION_MISMATCH`） |

| **T5** | 上一步结果 | 工具结果/子代理结算（Inline 或 Spill 指针） | 事件日志 | 每步 | ≤10% A（inline） | 尾部 | 超限 spill，只留指针 |

> **为什么前缀里只放这些**：它们"稳定且高权威"。**L0 跨角色稳定、L1 仅在换角色时变化**；任何**会随对话变化**的内容（包括"当前进度"、本次契约空位）都放尾部——否则每步都改前缀，缓存全废（Claude：稳定前缀 = system + tools + 规则文件；DSH：prompt 是 surface 节点，但请求头/工具集稳定）。**专家/评审的 L1 不引用秘书段**（§1.4）。

### 3.3 顺序的硬约束（可测）

1. **L0→L1→尾部顺序固定**（S1a → S2 → 契约 schema → S1b/S3/S4 → T1..T7），且层内排序键固定（工具按 toolId 字典序；section 按显式 order 常量表）→ 同一状态 `prefixHash` 必须一致（19 §9.1 ⑥）。
2. **T1..T7 顺序固定**；同一层内按"时间升序 + id 升序"。
3. **不进前缀的四类内容**：当前时间、当前进度、检索结果、工具结果——它们放尾部（T5/T6/T7）。
4. **被撤回文本永不进入**（19 §9.1 ④）；surface 视图只取未撤内容。
5. **不可信内容一律走统一封装**（来源标签 + 框架标签 + `<` 转义 + 字节预算），并在 `untrustedBlocks[]` 登记（含 `neutralized`，D8）；**不可信内容不得直接触发写记忆/写文件/改策略**（19 §6；16 §3.1）。
6. **角色一致（L1）**：一次请求内 `roleProfile.role` 固定；所有角色段必须同角色维度（`identity.<role>@v`），否则**拒绝编译**（`ROLE_SECTION_MISMATCH`）；**专家/评审不得引用秘书段**（§1.4 不继承规则）。
7. **契约空位在尾部**：`contract.slot` 只进 T1 尾段，**不得进前缀**（否则每步 `prefixHash` 变化、缓存全废；D5）。
8. **前缀两段式**：L0（跨角色稳定）→ L1（角色稳定）→ 尾部；`l0Hash` 变化才算"公共段重建"，`roleHash` 变化只算"角色段重建"（§1.4）。

## 4. 预算模型

### 4.1 四个基础量与触发线

```text
W = 模型窗口（provider 声明；未知则用保守默认 128K 并标 estimated）
O = 输出预留 = max(配置 maxTokens, 4096)，默认 8192
T = 工具定义预留 = 实测 schema token × 1.1（V1 工具少：经验 3–6K）
S = 安全边界 = min(16K, 12.5% × W)          // 吸收估算误差与协议开销
A = W − O − T − S                            // 生效预算
高水位 P_high = floor(min(W × 0.75, W − O − T − S))
低水位 P_low  = floor(P_high × 0.55)         // 压缩目标：压到低水位以下，留出增量空间
```

- **触发主动压缩**：`measured(canonical envelope) ≥ P_high`（或 `needsCompaction` 由配额校验置位）。
- **触发被动压缩**：provider 返回 `CONTEXT_WINDOW_EXCEEDED`（19 §9.2）。
- **压缩目标**：压到 `≤ P_low`；否则视为压缩失败（见 §5.5）。
- **收尾后压缩**（P1，Codex 借鉴）：Turn 关闭时若活跃占比 > `postTurnPercent`（默认 70%），关闭后补一次压缩，避免下一 Turn 开局即超——**在用户等待结束后做昂贵操作**。

> 【待核实】`0.75 / 0.55 / S=16K` 是工程默认，需 M2 基线后按模型校准；CJK 下估算误差更大（见 §4.3）。17 §6.2：目标值先采基线。

### 4.2 计量：provider usage 优先，估算兜底（INV-10）

| 优先级 | 来源 | 何时可用 | 精度 | 用途 |
|---|---|---|---|---|
| 1 | provider 上报 usage（含 cache_read/cache_write） | 每次模型结算后 | 真值（同一 canonical envelope） | 累计/预算/指标/压缩判定的**锚点** |
| 2 | 未命中锚点时的估算 | 每次组装 | ±10–30%（CJK 更差） | 组装前的**预判**（只用于决定是否压，不用于结算） |
| 3 | 工具/上下文层的结构化估算 | 每层 | 粗 | 配额分配与 `breakdown` |

规则：
1. **锚点复用条件**：provider/model/工具集/参数与上次成功请求的 canonical envelope **完全一致**；否则整体重新估算（DSH 的做法）。
2. **判定用锚点、决策用估算**：是否触发压缩用"最近锚点 + 增量估算"，结算与指标用真实 usage。
3. **估算标注**：`InjectionPlan.tokenEstimate.estimated=true` 时必须出现在 `budgetReport` 与指标里；不得假装精确。
4. **单一计量**：压缩/预算/UI/评测都读同一个计量服务（19 INV-10），E2 不自己维护第二套账。

### 4.3 估算口径（V1 建议）

- 文本：**UTF-8 感知**——ASCII 约 4 字符/token，CJK 约 1.2–1.5 字符/token，按字符类别加权（DSH 的 4 字符/token 在中文下严重低估，明确不照搬）。
- 结构开销：每条消息 +4 token、每个 section +2 token、工具 schema 按 JSON 字符数/3 估算。
- 图片/附件：按路由声明的视觉 token；未声明则按固定占位（V1 不做多模态预算，标 P1）。
- **校准**：M2 用 20 条真实会话做"估算 vs usage"回归，目标平均误差 ≤15%（【待核实】此目标需实测确认）。

### 4.4 动态调整（按阶段与任务类型）

| 场景 | 调整 | 理由 |
|---|---|---|
| `draft/confirmed`（只读、讨论） | T3 记忆配额 ↑、T4 对话 ↓ | 需要背景，不需要长执行历史 |
| `executing` | T5 结果 ↑、T4 ↓ | 刚发生的事实最重要 |
| `verifying` | T2 Task/Evidence 指针 ↑、T3 ↓ | 判据优先 |
| 子代理派发回合 | T2 brief ↑、T4 ↓（父对话与子无关） | 19 §8：父不传全文，但 brief 必须够用 |
| 长任务（>20 Step） | 更早启用 `body_after_prefix` 作用域 | 防抖动（§5.2） |
| 用户明确要求"看细节" | T4/T5 ↑、T3 ↓ | 意图优先于默认配额 |

调整硬约束：**块与 pin 条目永不被配额挤掉**（12 §4.3 必进项）；**S1a/S1b/S3 超限是配置错误**，不是运行时降级（S2 超限是拒绝编译，见 §3.4）。

## 5. 压缩策略（三段式 + 事务 + 重注入）

### 5.1 触发（四种，对齐 19 §9.2）

| 触发 | 条件 | 动作 |
|---|---|---|
| 主动 | `measured ≥ P_high` 或配额校验置 `needsCompaction` | 三段式完整流程 |
| 被动 | provider `CONTEXT_WINDOW_EXCEEDED` | 绕过阈值做"最大平衡头部缩减"→ 成功后**只重试一次** → 仍失败降级 |
| 收尾后（P1） | Turn 关闭且活跃占比 > 70% | 关闭后台压缩 |
| 手动（P1） | 用户要求"整理上下文" | 同主动 |

### 5.2 作用域：`total` vs `body_after_prefix`（**防抖动关键**）【借鉴 Codex】

| 作用域 | 定义 | 何时用 |
|---|---|---|
| `total` | 按完整活跃上下文计（含钉住前缀与压缩窗口前缀） | **首次压缩前**（还没有压缩窗口前缀） |
| `body_after_prefix` | 只算"压缩窗口前缀之后的增量" | **第一次压缩成功后自动切换**；长任务强制 |

- **压缩窗口前缀** = `钉住前缀（L0 + L1） + 最近一次 checkpoint 摘要 + 最近 K 条逐字对话`；它作为"锚"被保留且**不参与阈值计算**。
- 效果：刚压完的会话不会因"前缀本身很大"而立刻再次触发（抖动）；压缩频率成为真实压力的信号（指标 E2-M04）。
- **【拍板 Q2·用户 2026-11-06 授权 lead 拍板】** 接受**隐式切换**：首次压缩前用 `total`（此时还没有压缩窗口前缀），**首次压缩成功后自动切 `body_after_prefix`**，无需用户配置；切换事件记 `compaction_scope_switched{from,to,reason}`，此后该会话固定使用 `body_after_prefix`（除非显式重置）。不采用"全程 `total`"（长任务必然抖动）。

### 5.3 三段式（顺序不可换）

| 段 | 动作 | 是否调模型 | 阈值/参数（V1 默认） | 配额/限制 |
|---|---|---|---|---|
| **① 剪工具输出** | 纯函数：超长结果替换为"头 + 中间标记 + 尾"；只改文本，图片/结构块保序；**被 `read` 工具读取的结果豁免**（防自噬） | 否 | `thresholdChars=8192`、`head=4096`、`tail=1024`（code point 计数；DSH 参数） | 一次通过即收敛（head+marker+tail ≤ threshold，保证不增长） |
| **② 结构化摘要** | 一次辅助请求：把 `system+tools+被压区间` 逐字重放，末尾追加固定指令；只取返回**文本**（丢弃 reasoning/tool calls） | 是（1 次） | 8 段模板（见 §5.4）；`maxTokens=headroom`；`retries=1` | 摘要必须**严格小于**源区间（shrink 校验），否则拒绝 |
| **③ 替换 + 边界** | `compaction/start`（同步落盘、取锁）→ `compaction/summary`（log-only）→ 一条 `replace{startSeq,endSeq}` 的 user 消息 → `compaction/end` → 记 `compact_boundary` | 否 | 替换而非追加；原事件保留（INV-4） | **未闭合的 start 就是锁**：宁可 busy 不可重入 |

- **摘要请求复用 warm prefix**：重放的前缀若与上一次成功请求逐字相同，provider 只需计算尾部指令与输出——成本极低（DSH 做法）。
- **选区规则**：从"第一个非 system 节点"开始，**钉住前缀永不被遮蔽**；压缩边界保证"没有未回答的 tool call 跨边界"（tool pairing 平衡）。
- **摘要模型**：默认与主模型同族的小/便宜模型；可配置；失败回退见 §8。
- **可回放**：替换事件引用被替换区间；`deriveMessages` 从日志重建，压缩前后都可重放；评测可断言"压缩前后可见语义不变"（除摘要信息损失）。

### 5.4 摘要模板（8 段，V1 固定）

```text
## Primary Request and Intent      （用户原始与演进的意图；关键原话逐字保留）
## Key Technical Concepts          （技术/协议/约束）
## Files and Code                  （精确路径: 为何重要、关键改动）
## Errors and Fixes                （错误原串: 如何解决、相关反馈）
## Pending Jobs                    （明确要求但未完成的工作）
## Current Work                    （检查点时刻正在做什么）
## Next Step                       （下一步唯一动作，或 (none)）
## Critical Context                （决策与理由、约束、用户偏好、未决问题）
```

规则（沿用 DSH + 我们的约束）：
1. 空节写 `(none)`，**不许删节**。
2. 保留精确路径、命令、错误串、标识符、数值、函数签名。
3. **不得提及"这是摘要/压缩"**（模型不应把检查点当对话事件）。
4. 若区间内已有更早 checkpoint：**合并仍为真的事实、丢弃过时的**，不照抄。
5. 替换消息用 `<compacted-summary>` 包裹 + 一段前言："这是自动生成的检查点，当作既定背景，直接从后续消息继续，不要确认它。"

### 5.5 压缩后必须重注入的清单（**硬要求**，≤20 行 / ≤600 token 默认）

| # | 重注入项 | 为什么必须 |
|---|---|---|
| 1 | 系统不变量（身份 + 阶段允许/禁止 + 输出契约 + 不可信规则） | 压缩会吃掉早期 system 消息；规则不能丢（Claude："持久规则放规则文件而非首条 prompt"） |
| 2 | 持久规则**全文**（版本号 + `rulesHash`；**不截断**——超预算在编译期拒绝，见 §3.4 / D4） | 与压缩解耦：每步注入，压缩后额外强调 |
| 3 | 当前 Spec 阶段 + 下一步门禁（一句话） | 防止压缩后"忘了自己在哪个阶段、能做什么" |
| 4 | 未完成 Task 的 brief 摘要 + `writeScope` + `requiredEvidence` 指针 | 19 §9.3 不可丢项 |
| 5 | Frame 核心：`goal/constraints/acceptance/selfDecisions/mustAsk` | 19 §9.3 不可丢项 |
| 6 | 未结算工具/子代理的 handle + 三态状态 | 防止恢复后重复副作用 / 丢等待 |
| 7 | Evidence 与交付物指针（不展开明细） | 验收需要"凭什么说完成" |
| 8 | 不可信来源标签规则（哪些块不可信） | 重放后仍需标注 |
| 9 | 预算与停止策略（当前用量/软硬限） | 防止压缩后继续烧预算 |
| 10 | 输出契约（本轮至少要输出什么形态） | 防格式漂移 |

- **放置**：1/2/3 进**钉住前缀**（S1/S2）；4–10 进**动态尾部开头**（T1 之前或合并进 T1）。
- **去重**：重注入内容与已有上下文重复时只保留一份（按 `sourceId+hash` 去重），避免"压缩后反而更长"。
- **【按默认推进 Q3】** 规则/门禁/输出契约（1–3 项）进前缀，其余（4–10 项）进尾部开头；代价是每次压缩让 `prefixHash` 变一次（压缩本就低频，可接受）。

### 5.6 失败与抖动

| 情况 | 处理 |
|---|---|
| 摘要请求失败/超时 | 重试 1 次；仍失败 → 换 fallback compactor（更便宜/更稳的模型）→ 仍失败 → **降级为"摘要+指针"**（不丢原文，指针指向日志），画一句可见说明（19 F5） |
| 摘要不比源区间小 | 拒绝该次压缩（不写替换），记 `compaction_rejected`，本次改用"仅剪工具输出"路径 |
| 压缩期间 surface 被改（steer/撤回） | 重新校验选区稳定性；不稳定就放弃本次压缩（不做部分替换） |
| 中断/崩溃 | 未闭合 `compaction/start` = 锁；恢复时判 `busy` 并跳过（宁可少压一次） |
| 抖动（连续 2 次压缩间隔 < 3 步） | 记 `compaction_thrash` 指标告警；自动把作用域切到 `body_after_prefix`；仍抖 → 提高 `P_high`（+5%）并标注 |
| 压缩后仍超窗口 | 被动路径：最大平衡头部缩减一次；仍超 → 只读降级（保留最后可读状态，禁止继续写，19 F18/§11.1） |

### 5.7 压缩的边界：只改"模型可见"，不改"用户可见"（【拍板 Q5·用户 2026-11-06 授权 lead 拍板】）

- **适用范围**：压缩/裁剪/替换**只作用于"模型可见上下文"**（即从事件日志派生出的 `deriveMessages()` 视图与发给模型的 envelope）。
- **用户可见历史不丢**：对话原文、消息历史、工具调用与结果、`compact_boundary` 前后的原始事件，在 **SQLite 事件日志与 UI（会话/审计视图）中仍完整可查**；压缩产生的"替换"是 surface 视图的区间替换（19 INV-4），**底层事件只增不删**。
- **可回放**：任何时候都能从日志重建"压缩前"的完整历史（审计/评测/复盘用），也能重建"压缩后"的模型视图；两者由同一份日志派生，不产生第二套真相。
- **用户问"我们之前说过什么"**：走"回放/检索原始历史"而不是"从摘要里回忆"；UI 的对话历史是原文，摘要只影响模型。
- **推论**：压缩的"信息损失"只影响**模型判断**，不影响**人类可读记录**；因此 §12.3 Q5 的"永不丢清单"是**模型可见上下文**的硬约束，而不是数据保存的硬约束（数据保存由 19 INV-4/INV-2 保证）。

## 6. 检索式注入（RAG 接口）

> E2 定接口与预算，E4 实现索引/召回/打分。**默认不预取、不后台灌入**：检索是"这一步需要"的显式动作。

### 6.1 哪些内容按需检索（而不是常驻）

| 内容 | 默认 | 触发检索的时机 | 结果形态 |
|---|---|---|---|
| 记忆条目（`fact/decision/experience/progress…`） | 常驻块与 `pin` 条目**已常驻**；其余按需 | 每步（意图相关时） | 摘要 + `[mem:id@rev]` |
| Spec 片段（Requirement/Acceptance/Plan） | 只带"受影响片段"；全文走 handle | 阶段切换、验收、争议 | 引用 + 指针 |
| 文档（仓库/知识库） | **不常驻** | 用户提到、工具失败需查文档、P1 文档检索 | 摘要 + `[doc:path#anchor]` |
| 历史 episode（原始交互） | **不常驻**，只作证据 | 需要追溯"凭什么"、复现问题 | 只给指针 `[episode:id]`，**不注入全文**（12 §2.5） |
| 子 Spec 摘要 | 不常驻 | 父需要汇总/验收时（§6.3） | 摘要 + `[spec:child@v]` |

### 6.2 接口契约

```text
RetrievalRequest {
  purpose: "step_context" | "evidence_lookup" | "doc_lookup" | "child_summary",
  query:   string,                 // 由 Loop/E2 从当前目标派生（不是用户原话直传）
  kinds:   []string,               // 记忆 kind / "spec" / "doc" / "episode"
  scopeChain: []ScopeId,           // 12 §4.3：instance→task→domain→global（+显式 refs）
  filters: { time, status, sensitivity, specId? },
  topK:    int,                    // 默认 8，上限 20
  tokenBudget: int,                // 默认 ≤8% A（与 T3 检索桶共享）
  requireCite: true
}

RetrievalResult {
  items: [{ id, kind, rev, score, snippet, tokens, cite, trust: trusted|untrusted }],
  truncated: bool, budgetReport: { requested, returned, dropped, reason },
  warnings: []
}
```

### 6.3 结果如何带引用与截断（注入格式）

1. **每条都必须带 cite**：`[mem:<id>@<rev>]`、`[spec:<specId>@<ver>#<key>]`、`[doc:<path>#<anchor>]`、`[episode:<id>]`；无 cite 的条目**不得注入**（12 §2.5 证据纪律）。
2. **每条截断**：默认单条 ≤ 400 token；超出则保留"首句 + 关键句 + …[+N tokens，展开见 cite]"，**不静默丢**。
3. **去重**：按 `(id, rev)`；同一条目跨源命中只注入一次（取最高分来源）。
4. **信任标签**：外部/用户提供的 claim 标 `untrusted` 并走统一封装（来源 + 框架标签 + `<` 转义）；**不可信内容不得触发写入/策略变更**（19 §6）。
5. **排序**：`score = w1·rel + w2·imp + w3·rec + w4·strength`（12 §4.6 骨架）；**常驻块与 pin 直接必进、不参与排序**（12 §4.3）。
6. **预算超限**：先提阈值（只留高分）→ 再减 K → 最后只留 cite；三次降级都记 `budgetReport`。
7. **检索失败**：返回空结果 + `warnings`，**不阻塞主流程**；若本轮依赖检索（如证据核对），降级为"问人/换工具"，不编造。

### 6.4 何时不该检索

- 上下文已含高相关且未过期内容（避免重复注入、避免撑爆尾部）。
- 阶段是 `executing` 且当前 Task 的 brief 已覆盖（检索只用于补充冲突/证据）。
- 预算已用 >90% A（除非被动压缩后重试）。
- 用户明确"别查记忆，按我说的做"（意图优先）。

## 7. Inline & Spill（内联与溢出）

### 7.1 阈值与归属（V1 默认）

| 对象 | 内联阈值 | 超出处理 | 指针形态 |
|---|---|---|---|
| 单条工具结果 | ≤6K token（≈24K ASCII 字符） | 落 spill 文件 + 头尾预览 | `[spill:<id>] <首行摘要>…（完整：read tool offset/limit 或 grep）` |
| 单 Step 全部结果 | ≤10% A | 逐条按"信息密度"排序后 spill 低密度项 | 同上 |
| 工具调用参数 | 记录但**不回显**（除错误需要） | — | `[tool:<callId>]` |
| episode | 永不内联全文 | 只给指针 | `[episode:<id>]` |
| 文档检索结果 | 每条 ≤400 token | 截断 + cite | `[doc:path#anchor]` |
| 子代理 report | 摘要 + handle；report 全文 ≤3K token 才内联 | 超限只给 `[report:<id>]` | handle |

### 7.2 Spill 存储与续读入口

- 存储：`<workspace>/.ctx-spill/<sessionId>/<step>-<id>.txt`（会话级、单写者、git-ignored；与 12 的 episode 不同层：spill 是"上下文缓冲"，episode 是不可变证据）。
- **续读入口**（必须给模型可执行路径）：提示行固定格式 + 约定工具 `read(offset,limit)` / `grep`；不得只说"内容太大"。
- 清理：会话归档时清理；P1 加 TTL（默认 7 天）与容量上限（默认 200MB），超限按最旧优先删并记事件。
- 安全：spill 内容沿用原信任标签；spill 文件**不得**被当作可信输入（读回时仍以 `untrusted` 标注，除非原来源可信）。

### 7.3 选择策略（Inline 优先级）

1. 本 Step 刚产生的、与当前 Task 直接相关的工具结果 → 内联；
2. 更早的结果 → spill；
3. 已被模型引用过的结果 → 优先保留指针（可重复读）；
4. 大而低密度的结果（日志、全文件 dump）→ 直接 spill，只留"头 20 行 + 错误/关键行"。

## 8. 对话与子会话聚合（父子 Spec）

### 8.1 原则：父只读摘要与指针，不灌入子对话

| 关系 | 父能看到什么 | 默认不进父上下文 | 取用方式 |
|---|---|---|---|
| 父 Spec → 子 Spec | 子 Spec 的**摘要**（goal/现状/verdict/未决项）+ `[spec:child@v]` + `[report:id]`/`[evidence:id]` 指针 | 子会话的完整对话、子工具结果全文、子 episode 全文 | 按需 `child_summary(specId, depth=1)`；需要细节时用指针展开 |
| 父会话 → 子会话 | 同上（子会话是子 Spec 的 UI 视图，19 §1.2） | 同上 | 同上 |
| 兄弟 Spec | 默认不可见 | 全部 | 不提供接口（除非显式 `refs`） |

### 8.2 聚合接口

```text
ChildSummaryRequest { specIds[], depth: 1, fields: [goal,state,verdict,blockers,evidenceRefs,artifacts], tokenBudget }
ChildSummaryResult { items[{specId, version, goal, state, verdicts, evidenceRefs[], artifacts[], tokens, cite}], truncated }
```

- `depth=1` 默认只取直接子；`depth>1` 需显式（P1），且每层预算减半。
- **聚合预算**：≤10% A；超限按"未完成/阻塞优先"保留（进度与风险优先于已完成）。
- **不重复灌入**：父已持有的子摘要按 `(specId, version)` 去重；子 Spec 版本变化才替换（引用而非复制，12 §8）。
- **只读**：父子聚合只读；跨会话取用不复制数据（10 §25）。
- **子 Spec 的上下文由子自己装配**：父不为子组装上下文，只传 brief（19 §8：父不传全文）。

### 8.3 与"会话 = 视图"的一致（12 §8）

- 会话/子会话只是 UI 视图，**不是上下文单位**；E2 的聚合对象是 **Spec 树**，不是会话树。
- 因此"父看子"= "父 Spec 读子 Spec 的摘要"，与用户看到的会话界面无关；同一份对话不会因为视图切换而被二次注入。

## 9. 缓存友好（warm prefix）

### 9.1 前缀结构（顺序固定、版本化）

```text
[ L0 公共段：S1a 通用硬约束 | S2 持久规则 | 契约 schema ]        ← l0Hash（跨角色共享）
[ L1 角色段：identity.<role> | ironLaw.<role> | persona.<role>? | toolWhitelist.<role> ]  ← roleHash（同角色稳定）
[ T1 帧+contract.slot ][ T2 Task ][ T3 记忆 ][ T4 对话 ][ T5 结果 ][ T6 检索 ][ T7 环境 ]  ← dynamic tail
```

> `prefixHash = H(l0Hash, roleHash)`；**L0 与 L1 都只在"稳定性"允许时才重建**（见 §9.2/§9.3）。角色切换 = 新 agent/新实例（19 §8），**同一 agent 内 `roleHash` 不变**。

### 9.2 变化频率与缓存影响（允许变化 / 不允许变化）

| 层 | 允许变化 | 频率 | 缓存影响 | 处理 |
|---|---|---|---|---|
| L0（S1a/S2/契约 schema） | 规则内容 hash、schema 版本变化 | 低 | `l0Hash` 变 → **公共段重建**（所有角色） | 记 `prefix_rebuilt{l0,reason}` |
| L1（S1b/S3/S4） | 换角色（= 新 agent/新实例）；角色段版本 | 极低（agent 内固定） | `roleHash` 变 → **该角色前缀**重建 | 记 `prefix_rebuilt{role}`；**同一 agent 内禁止换角色** |
| T1–T7（含 `contract.slot`） | 每步可变 | 高 | **不影响前缀**（只追加/替换尾部） | 追加优先；`contract.slot` 只进 T1 尾段（D5） |
| T1–T7 | 每步可变 | 高 | **不影响前缀**（只追加/替换尾部） | 保持尾部追加优先，少做替换 |

### 9.3 硬规则

1. **不许把"每步都会变"的东西放进前缀**（时间、进度、检索结果、工具结果）。
2. **前缀只在必要时重建**；重建必须记录原因（阶段切换/压缩重注入/规则更新/工具集变更）。
   - **【拍板 Q1·用户 2026-11-06 授权 lead 拍板】** 持久规则（AGENTS.md 式）**放钉住前缀的 system 段（S2）**；缓存代价用"**内容 hash 变化才重建**"控制——`rulesHash = H(规范化文本)`，仅当 `rulesHash` 变化（或版本号变化）才更新 S2 并重建前缀；mtime 变化但内容 hash 不变**不重建**。
3. **尾部优先"追加"而不是"替换"**：撤回与压缩才用替换（19 INV-4）。
4. **记录缓存指标**：每步从 usage 取 `cache_read_input_tokens`/`cache_write_input_tokens`；`cache_read / (cache_read + cache_write + uncached)` = warm 命中率（E2-M02）。
5. **provider 差异**：不支持前缀缓存/不报告 usage 的模型，warm 命中率记 `unavailable`，不假装 0 也不假装命中。
6. **【待核实】** provider 是否支持"system 消息可出现在历史中"（DSH 的 `in-history` 能力）：支持则压缩后可把重注入短段追加到尾部而不是重建前缀；不支持则每步重建前缀并接受缓存代价。

### 12.3 拍板结论（**用户 2026-11-06 授权 lead 拍板**；Q3/Q4 按默认推进）

> 结论已写回正文落点：Q1→§9.3；Q2→§5.2；Q5→§5.7（含用户可见历史不丢的边界）；Q3→§5.5；Q4→§6。

#### Q1【拍板】持久规则（AGENTS.md 式）放"钉住前缀的 system 段"还是"每步注入的 user 消息"？
- **结论**：**放钉住前缀的 system 段（S2）**。
- **理由**：规则是硬约束，权威应高于对话；且我们本就有"每步重注入"机制（S2 每步都在），不必借 user 轮次实现（Claude 把 CLAUDE.md 当 user message 是其历史选择，不默认继承）。
- **缓存代价与控制**：规则文件变化会导致 `prefixHash` 失效——用**内容 hash 变化才重建**（`rulesHash`），mtime 变而内容不变不重建；每次重建记 `prefix_rebuilt{rules}`。
- **对齐 design/21 v0.1 · D4**：S2 超预算改为**拒绝编译 + 报错"规则超预算，请拆分/精简"**；不截断、不整份丢弃、不静默 warning（与 21 拍板 Q2=A 一致；§3.4 / §10 G4）。

#### Q2【拍板】压缩作用域是否 V1 就默认 `body_after_prefix`？
- **结论**：**接受隐式切换**：首次压缩前 `total`（尚无压缩窗口前缀），**首次成功压缩后自动切 `body_after_prefix`**；切换记 `compaction_scope_switched{from,to,reason}`，此后该会话固定 `body_after_prefix`（除非显式重置）。
- **理由**：首次 `body_after_prefix` 无定义；不切则长任务必然抖动。全程 `total` 被否。

#### Q3【默认推进】压缩后的"重注入短段"进前缀还是进尾部？
- **结论**：**规则/门禁/输出契约（1–3 项）进前缀；其余（4–10 项）进尾部开头**。
- **代价**：每次压缩让 `prefixHash` 变一次（压缩低频，可接受）。

#### Q4【默认推进】V1 的检索默认开多大？（top-K / 预算 / 是否默认开文档检索）
- **结论**：**只对"记忆条目 + Spec 片段"开启，`topK=8`、检索预算 ≤8% A；文档检索与 episode 全文检索留 P1**（episode 只给指针）。

#### Q5【拍板】超窗口降级时，"丢什么"的优先级
- **结论**：同意以下顺序：**① 先 Inline→Spill；② 再只留指针+摘要；③ 再压缩最早非 checkpoint 对话；④ 最后丢弃最老的、非不可丢清单的工具结果文本（保留其指针）**。
- **永不丢（模型可见上下文的硬约束）**：常驻块/pin 条目、未完成 Task 的 brief 摘要/writeScope/requiredEvidence、当前 Frame 核心、未结算工具/子代理句柄与三态、Evidence/交付物指针、不可信来源标签、持久规则。
- **补充边界（用户 2026-11-06 授权 lead 拍板时明确）**：压缩只影响**模型可见上下文**；对话原文/消息历史在 **DB 与 UI 中仍完整可查**（用户可见历史不丢）——详见 §5.7。因此上述"永不丢"是**模型视图**的硬约束，数据保存由 19 INV-2/INV-4 保证。
