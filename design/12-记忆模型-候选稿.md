## 1. 一句话模型 + 六条不变式

**一句话**：记忆是一份**三层、带版本、可溯源、只追加（ADD-only）**的结构（常驻块 + 可检索条目 + 不可变原始流）；实例是它的**只读快照 + 私有草稿本 + 一次性提交权**；整个 Agent 只有**一个秘书、一段对话**，会话只是这段对话的 **UI 视图**，不承载状态。

```
┌──────────────────────────────────────────────────────────┐
│ 记忆层（唯一真相，长期存在）= 三层单元                   │
│   ① 常驻块 block：约束/偏好/目标 + 作用域说明（常驻注入）│
│   ② 可检索条目 record（fact/decision/经验…，带来源+版本）│
│   ③ 不可变原始流 episode：消息/工具/产物（仅作证据）     │
│   作用域树：global → domain:后端/客服 → task → 实例私有  │
│     └ 跨域只读引用（前端任务读后端接口约定）             │
└──────────────────────────────────────────────────────────┘
      ▲  读：快照视图（版本向量）+ 检索 + 白名单实时订阅
      │
┌──────────────────────────────────────────────────────────┐
│ 实例（模型 + 工具 + 私有工作集） ← 临时、可丢弃、可换模型│
└──────────────────────────────────────────────────────────┘
      │  写：只写私有；结束时提交 handoff / 候选记忆
      ▼
┌──────────────────────────────────────────────────────────┐
│ 记忆管理器（单写者：校验→合并→冲突标记→发版本）          │
│ 后台整理者（独立模型）：去重/失效/提升候选，仍走管理器   │
│ 语义冲突 → 裁决者（人/秘书）：不自动合并，只交裁决       │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│ 对话视图（UI 侧，不在 Agent 状态里）                     │
│ = 同一段对话 + 同一棵会话树（会话/子会话）的过滤/跳转；V1 固定  │
│ 删/拆/并/改名都不丢状态；只决定人看到哪一段              │
└──────────────────────────────────────────────────────────┘
```

### 1.1 不变式（建议当"违反即作废"来用）

- **I1 记忆是唯一真相**：实例可随时被杀；杀掉重建不丢连续性、不改变"这个 agent 是谁"。身份 = 记忆 + 作用域，不是进程，也**不是会话**（会话只是视图，见第 8 节）。
- **I2 单写通道**：公共/领域/任务层只由记忆管理器单写者写入（后台整理者也只能经它落库）；执行实例只能自由写自己的私有作用域 + 提交候选，且**上下文里不挂记忆编辑工具**（见 5.7）。
- **I3 只追加（ADD-only）**：任何修改/撤销都产生新版本，不原地覆盖；失效 = 闭合 `validUntil`（见 2.7）；不物理删除（用户要求删除时，写一条 `retracted` 并清空内容，保留"曾经存在过"这一事实 + 审计记录）。
- **I4 全量溯源**：任何一条记忆都能回答：谁（哪个实例、哪个模型）、基于什么（哪条 episode）、什么时候写的、为什么改。
- **I5 默认不外溢**：实例私有工作集不进入检索、不被兄弟实例读到；只有结论/经验/决策允许上升，且必须过闸。
- **I6 冲突显式**：两条矛盾记忆不静默覆盖，而是并存 + 标注 + 报给秘书/人（结构冲突按规则裁决，语义冲突标 `disputed` 并存，见 5.9）。

> 「推断」I2 与 I3 是本稿最关键的两条；如果这两条被推翻，第 5、7 节要重写。v0.2 起，I2 有了先行方案的反面证据（5.7），I3 有了工业趋势背书（mem0 ADD-only、Graphiti 失效不删，2.7）。

## 2. 记忆单元：三层结构与条目 schema

### 2.0 三层单元：常驻块 / 可检索条目 / 不可变原始流（v0.2 新增）

先行方案收敛出的共同形状是**三层**，因为它们回答三个不同问题（`research/memory-first-prior-art.md` §2、§9 的 M1）：

| 层 | 回答的问题 | 形态 | 本稿的载体 | 关键约束 |
|---|---|---|---|---|
| **① 常驻块 block**（always-visible） | "实例一启动就必须知道什么？" | 带 `label` + `description` 的短文本段，直接拼进上下文 | 本节的块 schema；替代 v0.1 只靠 `injection.pin` 的近似做法 | 有字符上限；红线/政策类设 `readOnly`，只能人/中台改 |
| **② 可检索条目 record / claim** | "这次任务相关的事实/经验是什么？" | 结构化条目 + 自由文本附件 | 2.1–2.4 的 schema（本稿主体） | 带来源 + 置信度 + 版本；写入必须可追溯 |
| **③ 不可变原始流 episode** | "这条结论凭什么成立？" | 一次交互的原始片段（消息、工具结果、文件产物、测试输出） | 2.5（原 v0.1 的 trace，本节升格为正式一层） | 不可变；只增不改；不注入，只作证据指针 |

**三层缺一不可**：
- 只有 ①②：丢掉"这句话是谁、在什么时候、基于什么说的"——回滚与追责没有落点；
- 只有 ③：每次都要从原始流重算，延迟与成本不可接受；
- 只有 ①③ 或 ②③：要么没有可检索面，要么每次启动都要重新检索全部历史。

> **用户已定（Q1，2026-11-03）**：记忆的**最小单位 = 结构化条目 + 自由文本附件**。块与原始流是系统层面的另外两层（渲染载体 / 证据层），不改变"最小单位"的定义——三层结构与本条决定不冲突；条目之外的块/流不另立"最小单位"。

**与"可追溯 / 回滚"的关系（v0.2 的重点）**：
- 回滚的**最小单位是条目**（②）：把一条错误条目 `retracted` 或写新 rev；
- 追溯的**最小单位是 episode**（③）：每条条目的 `provenance.evidence[]`（本稿亦称 `episodeIds[]`）必须能指回去，指不回去的写入只能算 `agent_inferred`，进不了高权威位；
- 回滚的**证据面**是三层的交集：谁（作者 / 模型）、基于什么（episode）、什么时候写（`recordedAt`）、为什么改（提交 message / `Sources`，见 5.8）；
- 所以"可回滚"不是一句承诺，而是"②有版本 + ③不可变 + 两者硬链接"这条结构决定的。v0.1 缺的正是第③层——它把 trace 当"旁路"，于是"回滚"只能停在条目层，指不回原始证据。

**① 常驻块的字段（新增）**：

| 字段 | 说明 |
|---|---|
| `label` | 唯一标识，如 `constraints.online-release` / `profile.user` / `domain.backend.brief` |
| `description` | **用自然语言告诉模型"这块该放什么"**——检索不靠它，**写入靠它**，是被先行方案低估的字段（Letta 的 `description`，M2） |
| `value` | 内容；有字符上限 |
| `scope` | 属于哪个作用域 |
| `readOnly` | 红线 / 政策类块只能人 / 中台改（对应 Letta 的 read-only block，M3；也是污染防线的第一道） |
| `limit` | 字符上限，防止块膨胀排挤检索预算 |
| `rev` | 块也版本化（同 2.3），改块同样产生新版本 |

**块的准入规则（防止"什么都塞块"）**：块只放"每次都必须知道、且条目检索不可靠"的少量内容——硬约束、已确认决策、用户偏好、当前目标、作用域 `description`。其余一律走条目检索（②）。块的默认预算建议 ≤ 上下文的 15%（占用太多会把检索预算挤没）。

### 2.1 字段表（条目层）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|

### 2.2 类型表（kind 决定"怎么写回、怎么注入、怎么衰减"）

| kind | 语义 | 典型 `content.data` | 默认写入者 | 默认注入/衰减 | 依据 |
|---|---|---|---|---|---|
| `fact` | 可验证的现状 | `subject` / `relation` / `value` | 系统验证、用户 | 按需检索，decay slow | 推断 |
| `decision` | 已定的取舍 | `question` / `decision` / `alternatives` / `rationale` / `reversible` | 用户确认、秘书汇总 | pin 常驻，不衰减 | 推断 |
| `requirement` | 要做的事与验收 | `item` / `acceptance` / `status` | 用户、秘书 | 按需 + 未完成项常驻 | 推断 |
| `progress` | 做到哪了 | `task` / `pct` / `blockers` / `updatedAt` | 执行实例（允许执行中提交） | 实时共享，decay fast | 推断 |
| `experience` | 可复用做法 | `trigger` / `condition` / `action` / `outcome` / `signature` / `samples` | 实例总结（候选） | 低优先，decay slow | 【原话·客服"经验沉淀"】 |
| `preference` | 人的偏好 | `topic` / `preference` | 用户 | pin，不衰减 | 推断 |
| `constraint` | 硬约束/红线 | `rule` / `scope` / `source` | 用户、系统 | pin，不衰减，改需人审 | 【原话·"别动线上环境"类】推断 |
| `open_question` | 未决问题/冲突 | `question` / `options` / `blocked_by` | 实例、合并器 | 秘书可见，不衰减 | 推断 |

> `constraint` 和 `open_question` 是我加的两类（推断）。如果嫌多，可以并进 `decision` / `requirement`——但"红线永远常驻"和"冲突要显式可见"这两个需求得有落脚点。
>
> v0.2 补充：表里"pin 常驻"指**渲染方式**——标 `pin` 的条目在视图里以常驻块形式出现（2.0），但**存储仍在条目层**。块是渲染单元，不是存储单元；否则同一条内容会在块和条目里各存一份。
>
> **范围注记（2026-11-03）**：`preference` 行本期保留"可陈述偏好"的原有语义；但**偏好/习惯记忆、每日复盘与偏好页属于人格/偏好层，暂缓**（§2.8，用户明确"跟当前架构不是一回事，先记下来后面再说"）。提议新增的 `habit` kind **不在本表生效**，等后续单开讨论。

### 2.3 状态与版本（先看这张图，再看示例）

```
记忆对象（id 稳定）内部：
  rev1 (superseded)  rev2 (superseded)  rev3 (active)   ← 版本链，全部保留
   │                   │                  │
   └─ 每次写入追加一条版本记录，读的时候取链头

跨对象： 旧对象A --supersedes--> 新对象B   （整条作废、另起炉灶时才用）
冲突：   A <--conflictsWith--> B           （双向，且会派生一条 open_question）
```

- **`rev` 是"这条记忆自己是第几版"**，不是全局版本；全局/作用域版本见 3.5。
- 状态只对**链头**有意义；旧版本自动视为 `superseded`。
- `candidate` 只存在于候选区（未生效），见第 5 节。
- **v0.2 新增两态**：`active → disputed`（结构/语义冲突未裁决，两条并存 + 派生 `open_question`）；`active → archived`（长期未用 + 低重要度，退出检索候选但可召回）。`expired` 只是"`validUntil` 已闭合"的派生显示，**不等于删除**（见 2.7）。
- **改内容 = 新 rev，不原地覆盖**（ADD-only）；"当前值"是版本链的投影，不是一条被反复改写的记录。

### 2.5 第三层：不可变原始流（episode）——不注入，只作证据

对话片段、工具调用、文件产物不塞进记忆条目，单独存为 episode（v0.1 曾叫 trace，v0.2 升格为正式一层）：

```
Episode { episodeId, at, scope, taskId, instanceId, kind(消息/工具/产物/测试), payloadRef, hash }
```

- **不可变**：入库后字段不再改（只增不改）；纠错靠"新 episode + 条目重写"，不靠改历史；
- 记忆条目通过 `provenance.evidence[].ref`（本稿亦称 `episodeIds[]`）指向它；**指不回去的写入只能算 `agent_inferred`**，进不了高权威位（先行方案 M9）；
- 注入上下文时**不带 episode 全文**，只带"可展开指针"（沿用 Inline & Spill 的思路：要细节时再展开）；
- 好处：总结错了，原始证据还在；总结丢了条件，能顺着 episode 回去补。

> 与"可追溯 / 回滚"的关系（v0.2 补）：**回滚的最小单位是条目（②），追溯的最小单位是 episode（③）**；"②有版本 + ③不可变 + 两者硬链接"这条结构，才是"可回滚"能落地而不是一句承诺的原因（见 2.0、5.5）。
>
> 会话视图（UI 侧）是对同一份消息/episode 流做过滤，**不另造一份数据**（第 8 节）。

### 2.7 失效优于删除：双时态 + ADD-only（v0.2 新增）

**原则**：删除是例外动作（隐私/合规/明确纠错），不是常规维护动作；常规维护走"**失效 + 降权 + 归档**"。

| 动作 | 语义 | 数据怎么写 | 检索表现 |
|---|---|---|---|
| **失效 invalidate** | "这条曾为真，但现在不再成立" | 闭合 `validUntil`（= `invalid_at`）；或写新 rev 让旧值带失效窗口；**旧条目保留** | 默认只取 `validUntil=null`；`asOf` 查询可取历史（M19） |
| **降权 decay** | "仍然成立，但价值/时近性在下降" | 只影响 `lifecycle.decay` / `importance` / `accessCount`，**不改内容** | 排序降低，仍可被检索到 |
| **归档 archive** | "长期未用且低重要度" | `status=archived` | 退出默认检索候选，可显式召回 |
| **纠错重写** | "当时写错了" | 新 rev（ADD-only，旧 rev 留痕）+ 下游标 `needs_review` | 取新值；旧值可审计 |
| **删除 delete** | 隐私 / 合规要求 | 写 `retracted` 并清空正文，保留"曾存在"这一事实 + 审计记录 | 不可检索；审计可查 |

**两条硬规则**：
1. **ADD-only**：内容层不原地 UPDATE/DELETE，只追加新版本；"当前值"是投影结果。这是先行方案的趋势（mem0 2026 版明确转向 ADD-only、Graphiti 失效不删，见 research §5、M7/M8）。
2. **双时态**：`validFrom/validUntil` 记"世界时间"（这条事实何时为真），`recordedAt` 记"系统时间"（何时写进来）。两者分离，才能回答"当时为真的事实是什么"。

**默认参数（占位，非结论，见 Q7）**：
- 有保质期的事实（当前分支、发布窗口、临时开关）：默认 7–30 天闭合 `validUntil`；
- 普通 `fact`：不设硬过期；90 天未验证 → 降权 + 提示复核；
- `progress`：任务结束后 7 天归档；
- `preference` / `constraint` / 已验证 `decision`：不衰减、不自动失效；
- `experience`：不失效，但试用期 30 天（7.5）。

> **为什么不能只用 TTL**：TTL 分不清"过时"与"重要但久未使用"，会把"三个月前定下的架构决策"一起杀掉；而且 TTL 到期不会留下任何事实痕迹，事后无法回答"它当时为什么失效"（先行方案 P5）。

### 2.8 偏好 / 习惯记忆 + 每日复盘（【人格/偏好层 · 暂缓】）

> **范围调整（用户 2026-11-03）**：偏好复盘 / 习惯积累**本质上是 Agent 人格设计，跟当前做的 Agent 架构不是一回事**；用户要求"**先记下来，后面再说**"。
> **处置**：① **不计入本期架构范围与 schema**；② 本节只保留需求与候选分析，供后续单开讨论；③ 架构里只留**接口占位**（"决策时可查询偏好"），不展开实现；④ 不删除这里的分析，保持可追溯。原话见 [`10-设计对话记录.md`](10-设计对话记录.md) §14。

**需求原话要点**：Agent 要对用户的工作习惯产生积累/判断经验，每天持续沉淀、复盘并记下来；有些事情用户更希望先确认，有些事情更希望 agent 直接开始做。

**候选分析（记下来，待后续单开讨论；不是本期结论）**：

| 视角 | 候选内容【推断】 |
|---|---|
| 记忆类型 | `preference`（可陈述的偏好）/ `habit`（从重复行为归纳的习惯）；scope = global（用户级），跨任务 |

| 消费 | 决策时按"动作 + 领域"查偏好 → `ask` / `act`；**任务显式指令覆盖长期偏好** |
| 控制 | 偏好页可看/改/删/暂停；"忘记这条"写 `retracted`（不物理删除，同 2.7） |
| 边界 | 不推断隐私/情绪；证据不足不成条；偏好不能越过红线、授权与不可逆确认 |

**接口占位（本期不实现，只留语义）**：

## 3. 记忆分层与作用域

### 3.1 四层

| 层 | 例子 | 生命周期 | 谁能读 | 谁能写 |
|---|---|---|---|---|
| **global** 全局 | 你的偏好、长期目标、跨域硬约束 | 永久 | 所有实例 | 秘书候选写；你可直接改 |
| **domain** 领域 | 后端/前端/客服各自的现状、决策、经验、SOP | 长期 | 本域实例 + 被引用方只读 | 本域实例候选写；秘书可转呈 |
| **task** 任务 | 一次复杂任务的进展、结论、中间决策 | 任务期 + 归档 | 参与该任务的实例 | 参与实例候选写 |
| **instance** 实例私有 | 草稿、试错、中间推理、原始观察 | 实例期 + 保留 7 天 | 仅本实例 | 自由写，不上报 |

> 「推断」`task` 层是我补的：没有它，"一次任务的临时结论"只能塞进领域层（污染）或私有层（兄弟实例看不见）。如果你觉得四层太多，可以把它并进领域层 + 细分类型（标签属 P1 候选，V1 不引入），但"部分共享"就必须靠作用域约定。
>
> **v0.2 边界补充（重要）**：这四层是**记忆作用域**，不是"会话的层级"。会话 / 子会话**不在**这一层里——它是 UI 视图（第 8 节），不拥有记忆、也不是写入单位。任务（task）是 Agent 侧结构，会话只是任务的 UI 投影（见 [`10-设计对话记录.md`](10-设计对话记录.md) 第 9、10 节）。

### 3.2 作用域对象

| 字段 | 说明 |
|---|---|
| `id` | `global` / `domain:后端` / `task:订单故障排查-20261103` / `instance:inst-be-a3f1` |
| `kind` | `global` / `domain` / `task` / `instance` |
| `parentId` | 层级父（task 可挂在 domain 下，也可挂 task 下） |
| `refs[]` | 跨域**只读引用**（例：前端任务引用 `domain:后端` 的接口约定） |
| `blocks[]` | 该作用域挂的常驻块 label（块内容另存，见 2.0） |
| `description` | 一句话说明"这个作用域放什么"——块与条目的写入质量入口（M2） |
| `rv` | 作用域版本号，单调递增；快照单位（见 3.5） |
| `readPolicy` | 默认读策略：`inherit`（派发时快照）/ `live`（白名单实时） |
| `writePolicy` | 谁能往这里提交候选、哪些 kind 需要人审 |
| `status` | `active` / `archived`（任务结束后归档，不删） |

### 3.3 三态：继承 / 实时共享 / 隔离

这三种状态是"部分共享"的全部答案，必须显式挂在**任务作用域或实例视图**上，不能靠默认值模糊处理（推断）。会话视图只决定人看到哪一段，不参与这里的判定。

| 态 | 读行为 | 写行为 | 机制 | 例子 |
|---|---|---|---|---|
| **继承**（inherit） | spawn 时把父作用域条目**按快照**注入；运行中不随源变化 | 只读 | 视图钉住 `(scopeId, rv)` | 派发子任务时注入目标/约束/已定决策 |
| **实时共享**（live） | 订阅白名单条目；变更到达时以**"更新提示"**注入（不重写已有上下文） | 仍只读，写要候选 | 订阅 `(entryId / kind / scope)`，收到 `rev + diff` | 后端接口约定变更，同步给并行前端实例；客服新知识即时上架 |
| **隔离**（isolated） | 默认不可见 | 可自由写 | 独立作用域，不参与检索与继承 | 实例草稿、试错、中间推理 |

- **默认是继承**（简单、可复现、可审计）；
- **live 只给白名单**：`progress`（进展）、`decision`（已定决策变更）、`constraint`（红线变更）、带 `tag=interface-contract` 的条目——否则实时共享会退化成"上下文被不断重写"，模型反而更乱（推断）；
- **隔离是兜底**：私有工作集永远隔离，实例结束才允许"申请上升"。

### 3.4 写权限矩阵（谁能往哪层提交候选）

| 作用域 | 秘书实例 | 领域实例 | 任务实例 | 用户 |
|---|---|---|---|---|
| global | 读 ✓ / 候选 ✓ | 读 ✓（检索）/ 候选 ✗ | 读 ✓ / 候选 ✗ | 读 ✓ / **直接写** ✓ |
| domain:X | 读 ✓ / 候选（转呈）✓ | 读 ✓ / 候选 ✓（本域） | 读 ✓ / 候选 ✓（任务内） | 读 ✓ / 直接写 ✓ |
| task:Y | 读 ✓ / 候选 ✓ | 读 ✓（被引用）/ 候选 ✓ | 读 ✓ / 候选 ✓ | 读 ✓ / 直接写 ✓ |
| instance:Z | 读 ✗（除非审计授权） | 读 ✗ | 读 ✗ | 读 ✓（审计/回溯） |

> 秘书不能直接写领域层（它不下场干活），只能"转呈"——真正的合并由后台整理者执行（见 5.1、5.7）。这条限制是为了让领域记忆只由懂它的人写（推断）。

### 3.5 版本向量（快照的单位）

一个实例视图跨多个作用域，所以快照是**版本向量**：

```
view.baseVersion = { "domain:后端": 41, "global": 7, "task:订单故障排查": 3 }
```

- 作用域 `rv` 每次批量提交 +1；
- **快照不是锁**：提交晚了不会被拒；`baseVersion` 只用于**冲突检测与审计**（"你当时读到的是哪一版"）；
- **`baseVersion` 过期是常态，不是异常**（10 并发 + 长任务）：过期不失败，走三方合并（见 5.9）；
- 冲突只发生在**条目级**（同一 id/同一 dedupeKey）或**规则级**（越权、跨域提升），不发生在"版本号落后"上。

## 4. spawn / fork 语义

### 4.1 先把你原话里的两个词分开

【原话·第5节】"后端的这个 Agent 可以自动 Fork 或 Spawn 出一个对应的 Agent 出来"——我按下面区分（推断，需你确认，见 Q9）：

| 动作 | 含义 | 私有工作集 | 典型用途 |
|---|---|---|---|
| **spawn** | 在某个作用域上新建实例；私有工作集为空；读视图 = 快照 + 检索 | 新建 | 10 个并发请求各起一个后端实例；客服按需起实例 |
| **fork** | 从"进行中的实例/任务"分叉：**复制其私有工作集 + 任务上下文**再继续 | 复制 | 同一问题试两条路；人接手后开新方向；失败重试但保留试错记录 |

两者共同点：**都不复制记忆本身**——记忆是共享的，复制的是"视图 + 私有草稿"。

### 4.2 实例视图对象

| 字段 | 说明 |
|---|---|
| `instanceId` | 一次性实例 id |
| `role` | `secretary` / `expert` / `cs-agent` / `summarizer` |
| `model` | 本次使用的模型（可替换算力的记录；换模型不改变"是谁"） |
| `scopes[]` | `{scopeId, rv, mode: inherit\|live\|isolated}` |
| `pinned[]` | 必注入条目 id（由视图组装决定） |
| `retrievalBudget` | 检索条数/字符预算（见 Q12） |
| `privateScopeId` | 私有作用域 id |
| `spawnedBy` | 谁 spawn 的（秘书 / 领域实例 / 客服池） |
| `taskId` | 绑定的任务（可选；纯后台实例可以没有）。会话视图不绑在实例上——它只是 UI 侧过滤 |
| `blocks[]` | 本次视图要渲染的常驻块 label（见 2.0） |
| `startedAt` / `expiresAt` | 生命周期；防止实例泄漏 |

### 4.3 视图组装（读侧）5 步

1. **解析作用域链**：instance → task → domain → global（+ 显式 `refs` 只读引用）。
2. **必进项（常驻块 + pin 条目）**：该作用域链上的常驻块（约束/偏好/当前目标/作用域说明，见 2.0）与所有 `pin=true` 且 `status=active` 的条目——不受检索预算裁剪。
3. **检索项**：按当前意图检索 top-K（相关性 + 重要度 + 时近性 + 使用强度，打分骨架见 4.6），去重后占剩余预算。
4. **展开一跳**：沿 `links` 带出直接关联条目（引用图思路），标"可展开"。
5. **冲突横幅**：所有 `status=disputed` 的条目附冲突标记（"存在相反记忆，见 X"），**不允许静默选一个**。

输出：`{blocks[], entries[], snapshotVersion, budgetReport}`。`budgetReport` 让"记忆没生效"可诊断（是被裁剪了还是没检索到）。

> v0.2：切换**当前子会话**只改变**视图起点与展示顺序**（例如"现在只看 task:订单故障排查"），不改变 Agent 侧的记忆权限——秘书始终拥有全部记忆的读权（第 8 节）。

### 4.4 私有工作集

- 结构同 schema，`scope=instance:<id>`，可以直接 `active`（但仅本实例可见）；
- **物理隔离**：私有区与公共区不同存储，回写必须显式 `promote`（候选），不存在"顺手写回"的路径（先行方案 P16）；
- 不参与检索、不被继承、不进 episode 之外的任何地方；
- 实例结束时**冻结归档 7 天**（只审计），之后清理；
- 只有经 handoff 提交、且被记忆管理器合并的候选，才进入公共层。

### 4.5 生命周期

```
spawn → running ──(检查点：可提交 progress)──> running → summarizing（生成 handoff）
   → submitted → ended → archived(7 天) → 清理
   └─ crash ──> 私有工作集保留；无 handoff → 秘书决定：重 spawn（同作用域）/ 人工看私有
```

**换模型 = 新实例**：同一个作用域挂一个新实例，`model` 记在实例上，记忆不受影响——这就是"模型是可替换算力"的落地。

### 4.6 检索打分骨架（v0.2 新增）

先行方案收敛的公式（Generative Agents 三因子 + LangMem 的 strength，见 research §4、M12）：

**score = w1·rel + w2·imp + w3·rec + w4·str**

| 项 | 含义 | 何时算 | 数据来源 | 默认 |
|---|---|---|---|---|
| `rel` | 相关性：语义相似度，可叠加 BM25 / 图距离（M13） | 检索时 | 向量 / 词法索引 | 先只做"向量 + 作用域过滤 + 时间过滤"，BM25/图后补 |
| `imp` | 重要度：这条记忆有多重要 | **写入时**打分 | `importance` 1–10 归一化 | 缺省按 kind 给（`decision`/`constraint` 高，`progress` 低） |
| `rec` | 时近性：多久前被验证/写入 | 检索时 | `lastVerifiedAt` / `recordedAt` + `lifecycle.halfLifeDays` | 指数衰减；`decay=none` 不衰减；半衰期缺省 90 天 |
| `str` | 使用强度：最近/最频繁被用过 | **读取时**更新 | `accessCount` / `lastAccessedAt`（派生索引，可重建） | 越常用越容易被再次召回（LangMem） |

- **默认权重（占位，非结论）**：w1=0.50、w2=0.25、w3=0.15、w4=0.10；后续按真实回放校准，不"拍一个常数就上线"。
- **不走公式的东西**：常驻块与 `pin` 条目直接必进（4.3 第 2 步），不参与排序竞争。
- **过滤先于打分**：默认只取 `validUntil=null` 且 `status=active`；`asOf` 参数可查"当时为真"，`includeDisputed` 决定是否带出 `disputed` 条目（M19）。
- **两处成本要认**：`imp` 要在写入时多一次 LLM 打分（写入路径本来就有整理者，成本可摊）；`str` 要在读取时写回一次计数（高频读会放大写压力，可批量/异步）。
- **评估**：权重与半衰期必须可调，并用真实任务回放做 A/B；否则检索退化时无法归因（"是没检索到"还是"排序错了"）。

## 5. 写回流程：候选制 + 记忆管理器单写者 + 版本

### 5.1 五个角色

| 角色 | 职责 | 关键约束 |
|---|---|---|
| **实例**（执行者） | 干活；产生 handoff / 候选；写私有 | **永不直接写公共层，上下文里也不挂记忆编辑工具**（理由见 5.7） |
| **记忆管理器**（提交闸 / 单写者） | 校验 → 落库（append-only）→ 冲突分类 → 发版本 | **提交路径不调模型**（纯规则，快）；崩溃可重放；是唯一直接触碰公共存储的进程 |
| **后台整理者**（consolidator） | 周期性把候选去重、合并、闭合失效、提升为试用/正式；把"越写越乱"的增量记忆整理干净 | 可用**独立模型**（通常更强/更慢）；产出仍是候选，经管理器落库；不绕开单写者 |
| **裁决者** | 处理需要判断的合并与语义冲突（人 / 秘书实例） | 裁决结果也是候选，仍经管理器落库，记 `decidedBy` |
| **用户** | 最高权威：可直接改写/撤销 | 直接写也产生版本，保留旧版 |

> 「推断」把"管理器"和"裁决者 / 整理者"分开很重要：管理器若调 LLM，10 并发下立刻变瓶颈；纯规则合并是毫秒级，判断类与整理类慢慢来，不挡提交队列。先行方案的对应物：Letta 的 sleep-time agent、LangMem 的 background 写入（见 5.7）。

### 5.2 状态机

```
        ┌────────────────────────── 私有草稿（实例内）
        │  提交 handoff（幂等键 = instanceId + seq；带 baseVersion + Sources）
        ▼
   candidate ──校验失败──> rejected（带原因，回执给实例）
        │
        ├──baseVersion 恰好 == head ──> fast-forward ──> merged（新 rev，active）
        │
        ├──baseVersion 过期 ──> 三方合并（base/ours/theirs）
        │        ├─结论仍成立 ──> rebase 落地 ──> merged
        │        ├─结论部分成立 ──> 降级 ──> disputed
        │        └─结论已被推翻 ──> rejected（回执说明）
        │
        ├──校验通过 + 低风险 ──> merging ──> merged（新 rev，active）
        ├──校验通过 + 高风险 ──> pending_review ──人批──> merged
        │                              └──人否──> rejected
        └──结构/语义冲突 ──> disputed_open（两条并存 + open_question）
                        │
                        └──裁决（人/秘书）──> merged / rejected / retracted
```

条目本身的状态（v0.2）：`active → superseded`（被新版本取代）、`active → disputed`（冲突未裁决，两条并存）、`active → expired`（`validUntil` 闭合，派生显示）、`active → archived`（归档，退出检索候选）、`active → retracted`（用户纠错/回滚）。**没有常规物理删除路径**（除隐私/合规的显式删除动作，见 2.7）。

### 5.3 伪流程（8 步，文字）

1. 实例结束或到检查点，生成 handoff（2.6 的六样）。
2. 提交候选批次（`baseVersion` = 提交者视图的版本向量；`candidateId` 做幂等；提交体带 `Sources`：谁、何时、哪条 episode、原话摘录——见 5.8）。
3. 管理器逐条校验：
   a. **schema 完整性**（缺 handoff 六样直接拒）；
   b. **权限**（这个实例能否写目标作用域，见 3.4）；
   c. **去重**（`dedupeKey` / 聚类签名：同一条经验不写 10 份）；
   d. **置信度钳制**（按来源等级上限，见 7.3）；
   e. **结构冲突检测**（同 id 的 rev、同 `dedupeKey` / 同 `(scope, key)` 的值是否矛盾——规则可判，见 5.9）；
   f. **敏感检查**（`sensitivity=sensitive` 不得离开实例/任务作用域）；
   g. **baseVersion 检查**（过期 ≠ 失败：走三方合并，结论成立则 rebase 落地，不成立则降级 `disputed`）。
4. 分类：`fast-merge` / `auto-merge` / `pending_review` / `conflict` / `reject`（规则见 5.4）。
5. **合并**：单写者串行提交；批次原子（要么全落，要么全不落）；目标作用域 `rv+1`；旧版本标 `superseded`（旧值不删，见 2.7）。
6. **冲突**：两条都保留（`status=disputed`），双向 `conflictsWith` + 派生一条 `open_question` 条目；秘书下次读记忆时能看到。**语义冲突不自动合并**（判定交 LLM/人，见 5.9）。
7. **派生**（异步、可重放）：更新聚类/统计/索引/`accessCount`；不影响"已生效"的语义。
8. **回执**：候选状态回写（`merged@rv` / `rejected + 原因` / `pending_review` / `disputed`），实例或秘书可查。

### 5.4 合并规则（按 kind × 风险）

| kind | 冲突判定 | 默认合并策略 | 风险 |
|---|---|---|---|
| `fact` | 同 `(subject, relation)` 值不同 | 来源层级高者胜，低者保留为 `disputed`/证据；同级 → 并存 + 上报 | 中 |
| `decision` | 同 `question` 结论互斥 | **永不自动合并**；全部置 `disputed`/候选，交人裁 | 高 |
| `requirement` | 同一需求项被改写 | 需 `user_confirmed` 或人审才能改；否则标"与已确认要求不符" | 高 |
| `progress` | 同任务进度 | `recordedAt` 新者 supersede 旧者；互相矛盾（一成一败）→ 冲突 | 低 |
| `experience` | 同 `signature` | 聚合成一条并累计 `samples`；**不覆盖**，只增强 | 中 |
| `preference` | 同偏好项 | 用户最新表述覆盖；agent 推断的偏好不得覆盖用户表述 | 高 |
| `constraint` | 修改/撤销 | 只允许用户或系统规则；agent 永不自动改 | 极高 |
| `open_question` | 新增/解决 | 追加；解决时写一条 `decision` 并关联 | 低 |

> **v0.2 补**：本表处理的是**结构冲突**（同 key、可判定的矛盾）的默认合并策略；**语义冲突**（跨 key / 跨作用域的自然语言矛盾）本表只给处置动作，判定本身必须交给 LLM/人，或直接标 `disputed` 并存（见 5.9）。

**高风险判定（默认值，见 Q5）**：改/删已有 `decision`/`constraint`/`requirement`、跨作用域提升（task→domain→global）、覆盖用户写过的条目、`sensitivity=sensitive` 离开私有层 → 必审；新增 `fact`/`experience`/`progress` 在**本域内** → 自动合并但标"未确认"。

### 5.5 版本与回滚

- 作用域 `rv` 单调递增；条目 `rev` 随写入递增；**历史全留**（append-only）。
- **回滚 = 写新版本**（`retracted` 或恢复旧值），不是删除。于是"这条错误记忆是谁、在版本几写完的"永远查得到。
- **影响面**：沿 `links.derived_from` 反向查询"哪些条目/经验是从这条派生的"，回滚时把它们一起标 `needs_review`（见 7.4）。
- **批量撤销**（v0.2 补）：污染要么没被发现、要么是"一批"。按 `provenance.authorInstance` + 时间窗整批 `superseded`/`retracted`，并派生一条审计记录（AgentPoison 的教训，见 7.6）。
- **合并本身也要可审计**（v0.2 补）：每次合并记录 `decidedBy`（规则 / 模型 / 人）+ `sources` + `baseVersion`；合并动作产生新版本，可回滚（research P14）。
- 用户直接改写视为最高权威：立即产生新版本，冲突条目自动降级。**V1 不提供记忆直接编辑控件**（用户 2026-11-03 已确认）：用户通过"跟秘书对话"下达修改，秘书按 `user_confirmed` 提交候选，仍走"新版本 + 保留旧版"；记忆页只做**可见只读**（列表/作用域/来源/时间）。

### 5.6 崩溃与幂等

- 候选提交幂等（`candidateId`），重复提交不产生重复版本；
- 合并批次原子（先写日志/事务，后更新索引），管理器崩溃重启后重放未完成批次；
- 提交失败要回执原因——**静默丢弃候选**是最糟的失败模式（实例以为自己写回去了）。

### 5.7 为什么不能由实例自己写公共层（v0.2 新增）

v0.1 只写了"实例永不直接写公共层"这条规则，这里补论证。先行方案给的主要是**反面证据**：

| 证据 | 内容 | 对我们的含义 |
|---|---|---|
| **Letta sleep-time agent**（原文，research §3） | MemGPT 把"记忆管理 + 对话 + 其他任务"塞进同一个 agent，结果**可能更慢**（对话中要调记忆操作）、**可能更不可靠**（同时调记忆工具与普通工具）；而且**增量式记忆形成，时间一长会变乱**。所以新版把记忆编辑工具从 primary 拿掉，只给 sleep-time agent | 执行实例不该同时"干活"和"整理记忆"；**不是不鼓励，是不给工具** |
| **LangMem 的 hot path 代价**（原文） | 让 agent 在对话中自己决定存什么，会给交互加可感知延迟，还多一个干扰它完成任务的障碍 | 我们的 handoff 是"结束 / 检查点提交"，不是"边聊边写公共层" |
| **共享可变块 = last-write-wins**（原文，Letta 文档明文） | 多个 agent 并发改同一块 → 后写覆盖前写，且**静默** | 10 实例共享"后端记忆"如果做成一个可变块，必然丢写；所以公共层必须是 append-only 候选 + 单写者合并 |
| **Cognee 的 accepted lessons**（原文） | 只有"被采纳的经验"才进永久记忆 | 与候选制同构：进公共层要经过一个采纳阶段 |

**结论（落到约束上）**：
1. 执行实例的上下文里**不挂记忆编辑工具**——它只能写私有工作集 + 提交 handoff；
2. 公共层的写权限只属于**记忆管理器（单写者）**；语义整理由**后台整理者**提议、仍经管理器落库；
3. 写回"慢一拍"（秒到分钟级）是可接受代价：记忆生效本来就该滞后于任务完成；
4. 反过来，"让实例顺手写公共层"只省一次提交，代价却是**10 并发下的静默丢写 + 无人可追责**，不成比例。

### 5.8 共享记忆按"版本控制仓库"语义（v0.2 新增）

先行方案里最诚实的工业做法不是 CRDT，而是**把共享记忆当版本控制仓库**（Letta 的 shared memory repo，research §6.3）。本稿直接借它的语义：

| 版本控制概念 | 本稿对应 | 说明 |
|---|---|---|
| 仓库 | 一个作用域（`domain:后端` / `global`）的记忆版本历史 | 归"领域 / 组织"所有，不属于任何实例 |
| checkout | 实例 spawn 时钉住的快照（`baseVersion` 版本向量） | 只读；实例挂载的是视图，不是仓库本体 |
| commit | 一次候选批次落库 | `{scope, rev, message, sources[], author, baseVersion, decidedBy, at}` |
| commit message + `Sources:` | 提交元数据 | 必带：谁（实例 / 模型）、何时、哪条 episode、原话摘录、为什么值得长期保留；**正文只写结论，来源放提交元数据**（M10） |
| 一次学习一个 commit | 一条记忆（或一组强相关条目）一个批次 | 便于审计与精确回滚，不要"一次提交 50 条" |
| push 冲突 → `pull --rebase` | 乐观并发 + 三方合并 | 重试**一次**；仍冲突则**不自动合并**，标 `disputed` + `open_question` 上交 |
| 人工 / agent 处理冲突 | 裁决者（人 / 秘书）｜后台整理者 | 裁决结果仍是候选，经管理器落库 |
| 分支 / tag | 不引入 | 我们不需要分支；"试用知识"用 `status` + 权重表达（7.5） |

**五条提交纪律**（缺一条，审计就不成立）：
1. `Sources` 必填：指不回去的写入只能标 `agent_inferred`，不得占用高权威位（7.3）；
2. `baseVersion` 必填：用于三方合并与"你当时读到哪一版"的审计（3.5）；
3. 批次原子：要么全落、要么全不落（5.6）；
4. 不自动语义合并：语义冲突一定上交（5.9）；
5. 每次合并记 `decidedBy`（规则 / 模型 / 人），且合并本身产生新版本、可回滚（P14）。

### 5.9 冲突检测分两层 + baseVersion 过期是常态（v0.2 新增）

**先分两层**（v0.2 最重要的补充之一，research §6.6 关键补充 1）：

| | 结构冲突 | 语义冲突 |
|---|---|---|
| 定义 | 同一 `(scope, key)` / 同一 `id` / 同一 `dedupeKey` 上的值矛盾（两实例同时改"连接池上限"） | 不同 key、甚至不同作用域的两条事实话对着干（"接口用 REST" vs "API 已改 GraphQL"） |
| 怎么检出 | 规则 / 字段比对，可自动 | 文本 diff 判不出来，必须 LLM / 人判断 |
| 怎么处置 | 按 5.4 的规则裁决（来源权威 + kind 策略），低者留 `disputed`/证据 | 标 `disputed`，**两条并存**，派生 `open_question`，上报秘书 / 人 |
| 风险 | 低（可判） | 高（藏起来最危险） |
| 先行方案对照 | Graphiti 的自动失效；Letta 的 rebase 冲突 | 只有 Graphiti 明确把"矛盾消解"放进摄取管线，其余回避（research §7） |

**再说 `baseVersion` 过期**：
- **过期是常态，不是异常**：10 并发 + 长任务，回写时 `baseVersion` 大概率落后（research P13）；
- 若设计成"过期即失败" → 大量重试与丢弃，最糟；
- 正确做法：**三方合并**（`base` / `ours` / `theirs`）：
  - 结论仍成立 → **rebase 落地**（写新 rev；`declaredBase` 记原 base，`mergedBase` 记当时 head）；
  - 结论部分成立 → 降级为 `disputed` 或候选，不硬写；
  - 结论已被推翻（对方已闭合了这条事实）→ `rejected`，回执说明原因；
- 重试有上限（默认 1 次，对齐 Letta 的 rebase-retry-once），**不设无限重试**。

**最后两条提醒**：
- **合并本身如果调 LLM，也是非确定性写入**：输出必须是结构化决策（合并 / 拒绝 / 降级 + 理由），记录 `decidedBy`，并产生可回滚的新版本（research §6.6 补充 3、P14）；
- **时间不是权威**：新写入不等于更正确（投毒可以很"新"），权威由来源 + 方法决定，时间只影响排序（P7）。

## 6. 并发语义：10 个实例共享一套"后端记忆"

### 6.1 规则

1. **快照隔离**：每个实例 spawn 时钉住版本向量；执行期间不受别人写入影响。
2. **只写私有**：执行期间写的都是自己私有作用域（`progress` 例外，可中途提交，见 Q8）。
3. **乐观并发 + 三方合并**：结束时带 `baseVersion` 提交；恰好命中 → 快进；过期 → 三方合并（base/ours/theirs）；结论成立就 rebase 落地，不成立退 `disputed`（见 5.9）。**`baseVersion` 过期是常态，不是异常。**
4. **不用锁、不用后写覆盖（last-write-wins 禁止）**：快照版本落后不是拒绝理由，结构 / 语义冲突才是。共享层按"版本控制仓库"语义工作（5.8）。
5. **冲突也是记忆**：派生 `open_question` 条目 + `disputed` 条目，秘书下次读就能看见——不靠"事件推送"，靠记忆本身可见（这一点刻意避开事件驱动那套，见第 12 节）。

### 6.2 场景设定

2026-11-03 14:00，订单服务发布后出现 3 类线上问题，秘书同时 spawn **10 个后端实例**（还陆续接了客服转来的 2 个案例）。它们共享：

- `domain:后端 @ rv 41` + `global @ rv 7` + 各自 `task` 作用域。

起始记忆里（节选）：

| `mem-be-000031` | fact | 连接池上限 = 20 | agent_inferred | 读自旧文档，**潜在毒源** |
| `mem-be-000018` | constraint | 发布窗口外禁止改线上配置 | user_confirmed | pin，全体常驻 |

### 6.5 六类冲突逐一怎么处理

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| **同一事实不同值** | I6"上限 20"（旧文档，推断）vs I7"上限 100"（实测） | 来源层级高者胜；低者保留为 `disputed` 并链到胜者；派生"更新旧文档"问题。**不静默覆盖**，因为旧文档本身也要修 |
| **同一决策不同结论** | I4"行锁" vs I5"乐观锁+重试" | 不自动合并；两条并存标冲突；报给用户（同级、无人确认，系统不替人选） |
| **进展互相矛盾** | 一个实例说"已恢复"，另一个说"仍在失败" | 保留两条 + 标冲突；`recordedAt` 新的不自动淘汰旧的——恢复与偶发失败可能同时为真 |
| **跨作用域提升** | 实例想把 task 里的结论直接写进领域层 | 拦截：要么走人审，要么攒够独立佐证（见 Q6）；`sensitivity=sensitive` 直接拒 |
| **语义冲突（跨 key）** | "接口用 REST" vs "API 已改 GraphQL"，两条不在同一 key 上 | 文本 diff 判不出来：标 `disputed`、两条并存、上报；由 LLM / 人判定后写新版本（5.9） |
| **重复经验** | I8、I9 写同一 `signature` | 聚合成一条，累计 `samples`，达到门槛才提升（7.5） |

补充两类（v0.2）：
- **基于过期快照的提交**：实例按 rev 41 判断，期间 43 已改了连接池上限 → `baseVersion` 过期，走三方合并：**结论仍成立就 rebase 落地，不成立就降级 `disputed`**（既不整批拒收，也不静默按旧值写）。
- **语义冲突**：两条不在同一 key 上、但话对着干 → 规则合不了，标 `disputed` 并存 + 派生 `open_question`，判定交 LLM / 人（5.9）。

### 6.6 实时共享下的"过期提示"

`live` 订阅的条目变更时，不重写实例已有上下文，而是追加一条提示：

> 【记忆更新】`mem-be-000031`（连接池上限）在你启动后由 rev1（20）更新为 rev2（100）。你基于 rev1 的判断需要复核。来源：实例 I7（实测）。

理由：模型的上下文是"追加式"的，偷偷改历史会让它自相矛盾；**显式提示过期**比"上下文被悄悄替换"可控（推断）。

## 7. 记忆污染防线

### 7.1 污染是怎么发生的（含量化证据，v0.2 补）

链路：实例总结有误（幻觉/早停验证/丢了条件）→ 写进公共层 → 之后所有实例当成事实 → 基于它再总结 → 扩散、复利。

客服场景的高危变体：**客户说错了**（"我明明付款了"）→ 实例当事实写入 → 知识点被污染。

**这不是理论风险，有两条量化证据**：
- **恶意侧（AgentPoison，NeurIPS 2024）**：针对 agent 长期记忆 / 知识库的后门攻击，**投毒率 <0.1%** 就能把攻击成功率做到 **>80%**，良性性能影响 **<1%**，且**不需要训练或微调**（`research/memory-first-prior-art.md` §7）。低剂量 + 无感，意味着"抽查"几乎不可能发现它。
- **自然侧（Generative Agents 自述）**：LLM 写记忆时会**给记忆编造 embellishments**（美化 / 脑补细节）——**不需要攻击者，写入流程自己就会变脏**。

所以防线不能建立在"内容看起来对不对"上（LLM 判不了自己写的脏内容），只能建立在**结构**上：来源分级、候选制、可逆与可批量撤销（见 7.2、7.6）。

### 7.2 七道防线

| # | 防线 | 机制 | 挡什么 | 代价 |
|---|---|---|---|---|
| 1 | **来源分级** | 每条约带 source + 置信度上限 | 模型总结被当事实 | 要定义分级（7.3） |
| 2 | **候选制 + 单写者** | 实例不能直接写公共层；合并由后台整理者（单写者）做 | 无审核的批量污染 | 写回慢一拍（可接受，见 5.7） |
| 3 | **校验闸** | schema/权限/去重/PII/baseVersion 过期（三方合并） | 越权、重复、过期、泄露 | 规则要写细 |
| 4 | **风险分级审阅** | 高风险必人审 | 改决策/改约束/跨域提升 | 人要有空看 |
| 5 | **失效 + 降权 + 归档** | 双时态失效（`validUntil` 闭合）、decay 只影响排序、`archived` 退出检索 | 过时事实被当现状；也避免 TTL 误杀长期决策 | 要维护复核节奏（见 2.7） |
| 6 | **冲突显式** | 并存 + 冲突边 + 注入横幅 + open_question | 错误覆盖正确 | 上下文变长 |
| 7 | **可逆 + 影响面 + 批量撤销** | append-only 版本、回滚、派生反查、按作者 + 时间窗整批撤销 | 污染无法追责 / 无法止损 | 存储与查询成本 |

可选第八道（推断，建议先不做）：**试用期/影子注入**——新提升的通用知识先低权重注入，观测命中与失败率，异常自动降级。工程量大，等有指标再做。

### 7.3 来源分级与置信度上限

| 等级 | source | 说明 | 置信度上限 | 备注 |
|---|---|---|---|---|
| L0 | `user_confirmed` | 用户明确确认/决定 | 1.0 | 最高权威（意图类） |
| L1 | `system_verified` | 工具/测试/git/监控可验证 | 0.99 | 事实类最高权威 |
| L2 | `user_stated` | 用户随口说的（未确认） | 0.9 | 意图/偏好类仍很权威；事实类可能记错 |
| L3 | `external_claim` | **客户/第三方陈述** | 0.5 | 必须标 `claim`，不得当 fact 写公共层 |
| L4 | `agent_inferred` | 实例推理/推断 | 0.7 | 可写，但明确标"推断" |
| L5 | `agent_summary` | 实例总结/经验 | 0.6 | 走候选 + 佐证门槛 |

**权威顺序与 kind 有关**（**已定，2026-11-03：按类型分轴，见 Q4**）；且必须**落在字段与合并规则里**（`provenance.source` + 5.4 的合并策略），不能只写在文档里：
- **意图类**（preference / constraint / requirement / decision 的"要什么"）：用户 > 系统 > 实例；
- **事实类**（fact / progress 的"是什么"）：系统验证 > 用户陈述 > 实例推断（用户也会记错）；
- 两类冲突时**不静默裁决**，并存上报。

### 7.4 影响面与回滚

- 每条记忆都有 `derived_from` 链；回滚时反查"哪些条目/经验是从这条派生的"。
- 回滚动作 = 写新版本（`retracted` 或恢复旧值）+ 下游标 `needs_review`。
- 审计能回答：这条错误记忆被哪些实例注入过、被谁引用进了总结——这是"污染止损"的关键（推断）。

例子：`mem-be-000031`（连接池=20，错）被 I2、I8 注入过；I8 据此写了经验"先查连接池"。回滚时：事实标 `retracted`；I8 的经验标 `needs_review`；open_question 通知知识维护者。

### 7.5 客服场景：经验 → 通用知识的流水线

```
实例结束总结（候选 experience）
   → 去重/聚类（signature：触发条件 + 适用条件）
   → 佐证门槛（默认 ≥3 个独立交互，且无反向证据；不同客户 / 任务才算，仅切换显示不算）
   → 试用（低权重注入，30 天）
   → 转正（命中率/解决率达标）→ 进入领域知识
   → 失败/被推翻 → 降级或退役（写新版本，不删）
```

配套三条：
1. **客户陈述是 claim**，不是 fact：只能存 task 作用域并标注，需系统核对（订单/支付记录）才能升级为 fact。
2. **知识缺口也记录**：KB 没有答案、客户问题超出范围 → `open_question`，给知识运营的人看；这是产品改进的输入。
3. **反馈闭环**：实例使用经验后，把"解决了/没解决"作为证据回写（samples / success），否则经验只是"看起来对"。

### 7.6 为什么"来源分级 + 候选制 + 可逆"非做不可（v0.2 补证据）

| 防线 | 不做会怎样（证据） | 结论 |
|---|---|---|
| **来源分级** | AgentPoison：**<0.1% 投毒率 → >80% ASR**，良性影响 <1%。被投毒的条目**读起来像正常记忆**，内容层面判不出来 | 唯一可行的判别维度是"来源 + 方法"（用户确认 / 工具实测 / agent 推断 / agent 总结），不是"看起来对不对"（7.3） |
| **候选制** | 投毒只需要"一条能进检索的条目"；LLM 自述的 embellishment 也不需要攻击者——写入流程自己就会脏 | 把"进检索"变成一个需要**合并**的阶段：候选 → 校验 → 单写者落库；多一道闸，同时天然产出审计线索 |
| **可逆 + 影响面 + 批量撤销** | 低剂量 + 良性影响 <1% ⇒ **抽查几乎发现不了**；等发现时已扩散到多个实例的总结里 | 必须能"事后定位 + 按 authorInstance + 时间窗整批撤销 + 反查下游 `needs_review`"，否则止损只剩全库回滚 |
| （附加）**写入路径当特权 API** | Graphiti 的参考 server 自己声明"无鉴权、无授权、无 prompt-injection 防护"（research §7） | 记忆写入通道必须鉴权、schema 校验、限速、审计——不能因为"内网"就不设防（P11） |

一句话：这三道防线不是"最佳实践"，是这个场景的**准入条件**。10 并发 + 公共层 + LLM 写入，三个条件叠加，缺任何一道，"记忆优先"都会退化成"污染优先"。

## 8. 结构定位：记忆作用域树（Agent 侧结构）+ 会话视图（UI 侧过滤/跳转，引用同一份对话与任务）

> **v0.2 重写**：v0.1 这里是"会话树 vs 记忆树"的二选一（方案 A / B）。你在 2026-11-03 的第 9、10 节澄清了会话的定位，所以本节不再做二选一，改为**两侧分工**。

### 8.1 你的澄清（已定，优先级最高）

三条原话的直接落位（[`10-设计对话记录.md`](10-设计对话记录.md) 第 9、10 节）：
1. **整个 Agent = 一个秘书 + 一段对话 + 一套记忆**。你跟一个秘书沟通，把需求都告诉它，它执行完把结果回馈给你。
2. **会话只是 UI 视图**："分成不同会话，本质上是按照 UI 的组织方式，我可以直接跳转到对应的会话里看那 100 条消息……这本质上不是对 Agent 的要求，也不是对 Agent 的优化，而是对人类用户的优化。"
3. **你永远只跟秘书说话**；点击子任务不是换对话对象，而是把**当前子会话**切过去（"现在我们讨论这个子任务"）——只用「会话 / 子会话」这两个词，不用"焦点"。

由此确定（不再是推断）：
- 会话**不是** Agent 的身份 / 状态单位，不能承载记忆，也不能作为写入 / 权限单位；
- Agent 侧的结构是**记忆作用域树**（global → domain → task → instance 私有）+ **会话树（会话 / 子会话）**；
- 人可读的对话只有**一份**；执行轨迹另有一份（默认折叠、按需展开），两者不混在同一份日志里；
- **V1 会话模型（用户 2026-11-03 已定）**：会话结构**固定——不可拆分、不可合并**；**可以改名，改名纯显示、无任何语义影响**；"灵活调整（拆分/合并/重组）"留到 P1。因为状态不在会话里，所以改名只是换显示，Agent 无感。

### 8.1b 会话模型（V1 固定）与标签（P1 候选）

| 项 | V1 结论 | 依据 |
|---|---|---|
| 命名 | 只用「会话 / 子会话」；表达"正在看哪个"用「当前会话 / 当前子会话」；停用"副会话 / 子视图 / 线程 / 焦点"作名词 | 用户 2026-11-03 已定 |
| 结构 | **不可拆分、不可合并**；层级固定（根会话 → 子会话） | 用户 2026-11-03 已定 |
| 改名 | **可以改名，纯显示、无语义影响**（不改记忆、不改结构、不改权限） | 用户 2026-11-03 已定 |
| 灵活调整 | 拆分 / 合并 / 重组 → **P1 再支持** | 用户 2026-11-03 已定 |
| 标签 | **V1 暂不引入**（待最终确认）。定义候选：贴在会话上的分类属性，用于分组/筛选，**不改变结构与可见范围**；只作 **P1 候选**（详见 14 附录） | 用户 2026-11-03 已定（暂不引入） |

### 8.2 两侧各是什么（一张表）

| | Agent 侧（本体） | UI 侧（视图） |
|---|---|---|
| 单位 | 记忆作用域（global / domain / task / instance）+ 条目 + 块 + episode | 会话 / 子会话（对消息流的过滤与分组）+ 会话树导航 |
| 寿命 | 长期 / 永久（作用域可归档，不删） | 随显示变化；改名/换视图只影响"好不好看"（V1 不可拆分/合并） |
| 谁写 | 记忆管理器（单写者）+ 后台整理者（候选制） | 用户只改"看哪一段"或改名，不改数据 |
| 权限挂在哪 | 挂在作用域 / 条目 / 消息上 | 不参与权限判定 |
| 坏了怎么办 | 记忆丢失 / 污染（严重） | 视图重建即可（可恢复） |

### 8.3 数据模型（沿用第 9、10 节，v0.2 落定；v0.2.2 术语对齐）

- **一份消息流**（= 第三层 episode，见 2.5）：`{id, at, author(用户/秘书/实例), taskId, sessionId, type(对话/工具/摘要/handoff), visibility}`；
- **任务**：Agent 侧结构，挂在 `task:…` 记忆作用域上（任务有层级）；
- **会话 / 子会话**：消息的子集视图（可多个会话引用同一消息，不复制）；`sessionId` 是纯 UI 字段；**V1 固定层级、不可拆分/合并，可改名（纯显示）**；
- **实例视图**：`{scopes[]（作用域 + 模式）, blocks[], taskId, retrievalBudget}`——决定"这个实例能读到什么"，与会话无关（见 4.2）；
- 约束：消息 id / 任务 id 必须稳定，视图才能稳定重建；**权限挂在数据上，不挂在会话上**（第 9 节）。

### 8.4 为什么"让会话拥有记忆"仍然是错的（保留 v0.1 的论证，改它的地位）

v0.1 的方案 A 是"会话节点 = 记忆作用域（1:1）"。现在它不是"没被选中的方案"，而是**被用户澄清排除的做法**。理由沿用 v0.1，逐条都是"会话拥有记忆会付出什么"：

- **会话短命 vs 记忆长久**：会话删了，记忆跟着死吗？不死就得开例外；
- **跨领域任务**：一个任务同时要后端 + 前端的记忆，会话树里没有"同一节点的多个父"；
- **同一领域多个会话**：两个会话各有一份"后端记忆"→ 记忆碎片化，共享失效；
- **客服 100 并发**：要共享知识库，就得让 100 个会话挂同一个祖先；要么所有客户共用一个作用域（隔离性崩了），要么在树外再建"领域根"——那就是现在的记忆作用域树；
- **删除会话 = 删记忆**，风险最高；也与"会话只是显示、V1 只允许改名（纯显示）"的定位冲突。

### 8.5 "部分共享"的答案（原 3.3 三态，位置不变）

- 继承 / 实时共享 / 隔离挂在**实例视图 + 任务作用域**上；
- **会话视图只决定人看到哪一段**，不参与"能不能读 / 能不能写"的判定；
- 因此：同一个人在会话 A 和会话 B 里看到的秘书，拥有**完全相同**的记忆权限，只是**当前子会话**不同（当前子会话影响"展示什么、优先加载什么"，不影响记忆权限）。

### 8.6 复杂度怎么藏（原 8.4 推荐的改写）

- 默认体验仍是"一棵树"：一个任务自动对应一个 `task` 作用域，UI 默认按会话树（会话 / 子会话）切显示；
- 只有跨域引用与领域共享时，才露出"作用域树 + 只读引用"的形状；
- 因为状态不在会话里，所以**改名只是换显示**（V1 允许）、**拆分/合并留到 P1**；这些都不影响 Agent 侧数据。

### 8.7 客服场景（保留原 8.5）

- 100 个客户对话 = 100 个 `task:对话-xxxx`（隔离，含客户信息）的视图 + 共享 `domain:客服`（知识库 / 经验）；
- 人看到的是"100 个会话视图"，Agent 侧看到的是"1 个共享领域 + 100 个任务作用域 + 各自的私有工作集"——**共享与隔离各自有明确的作用域，不靠规则特判**。

## 11. 本稿最可能被推翻的地方（我的不确定性）

1. **三层的维护成本**：块 + 条目 + episode 都要人维护 schema；如果条目层维护成本高于收益，会退化成"文本块 + 人审"。判断依据是并发共享必须有机器可判的冲突检测——仍是推断。
2. **两侧模型的真实代价**：会话视图 + 记忆作用域在纸面上能压住复杂度，实现时 UI 的"当前子会话 / 过滤"与"作用域绑定解析"可能比预期重。
3. **单写者吞吐**：纯规则合并在单机够用；若每次提交都要全文扫描 / 聚类，10 并发还行，100 客服会紧。可能要把聚类拆成异步；**后台整理者的 LLM 成本也要算进预算**（research §6.6 补充 3）。
4. **经验佐证门槛（≥3）**：数值是拍的；客服场景可能 2 就够，研发场景可能要 5+，甚至应按 kind 分场景定。
5. **失效 / 降权参数**：7/30/90 天与半衰期都是占位，需要真实使用数据校准；"90 天未验证就降权"可能对低频高价值事实不公平。
6. **实时共享是否值得**：如果"过期提示"让实例频繁犹豫，可能退化成"只在 spawn 时快照 + 结束时汇总"。
7. **语义冲突检测的成本**：判定要靠 LLM / 人，本身就是新的非确定性与延迟；如果冲突太频繁，`disputed` 会变成噪声（可能要靠"只在高重要度条目上做语义检测"来限流）。
8. **检索权重**：w1–w4 与 importance 打分都没有真实数据；不调参会退化成"看起来有记忆"。
