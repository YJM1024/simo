# 27 · 万级消息吞吐 + 一致性分析备忘

> **定位**：分析备忘，不是设计方案；不改 `design/26` 及其它文件。
> **证据分级**：`[文档]`＝官方文档/论文可查并给 URL；`[推断]`＝本文推导；`[估算]`＝带假设的数字，不是实测。
> **抓取时间**：2026-11-16（CST，会话时钟）。价格与配额会变，引用前请复核。
> **一句话**：1 万 msg/s 全量调 LLM，在配额与成本上不可行；"没有一致性"是伪命题——可以放弃全局串行，不能放弃**每 key 定序、幂等、原子状态迁移**。

## 0. 结论先行

1. **量纲**：1 万 msg/s ≠ 1 万 agent ≠ 1 万 LLM 调用/s ≠ 1 万写入/s。用 Little's law：`在飞数 = 到达率 × 停留时间`。
2. **全量语义**：每条 1k in/200 out，需 **12M token/s = 720M TPM**；最便宜档也要 **$23.3 万/天**（off-peak）[估算]。
3. **可行形态**：L0 全量 + L1 5% + L2 0.2% + L3 0.01%，约 **24M TPM、$7.3k/天**；再叠加抽样/聚合可到 **$23/天** 量级。
4. **一致性**：至少 6 类位置必须定序/幂等/原子；正确做法是**按数据域给一致性预算**，不是全系统一个级别。
5. **吞吐**：1 万/s 对消息队列很小（3 节点 Kafka 基准可到百万级）[第三方基准]；真正的瓶颈是 **LLM 配额、每 key 串行度、写放大、成本**。

## 1. 量纲拆解

```
λ_msg  = 10^4 /s
N_inst = λ_msg × W_inst / c_inst          # W=平均处理时长(含排队), c=每实例并发度
λ_LLM  = λ_msg × Σ_d (f_d × s_d / B_d)    # f=档位占比, s=每条调用次数, B=批大小
N_LLM  = λ_LLM × T_LLM                    # Little's law
λ_write= λ_msg × w / B_w                  # w=每条写事件数
N_write= λ_write × T_write
```

| 量 | 假设 | 结果 |
|---|---|---|
| 活跃实例 | 每条一个实例，处理 1s / 10s / 30s | **1 万 / 10 万 / 30 万** |
| 活跃实例 | 每实例并发 10 条，处理 10s | 1 万 |
| LLM 在飞 | 1 次/条，3s，不批 | **3 万**（单账号 flash 上限 2500 的 12 倍） |
| LLM 在飞 | 同上，批 20 条/次 | 1500（在 2500 内） |
| 写入 | 3 事件/条，单次 2ms | **3 万 写/s，60 个在飞写事务** |

**"1 万 agent"有三种读法**：每条一个、活 1s → 1 万；长驻 1 万个、每个吃 1 条/s → 正好 1 万/s；每条一个、活 30s → 30 万。只有前两种与 1 万 msg/s 对齐，第三种差 30 倍。**实例数是被停留时间放大的，不是被需求数决定的**（延续 [26 §2](../26-记忆中心并发Harness-v0.md) 的"逻辑/物理并发"区分，但把"工作项"换成"消息速率"）。批处理只适用于可独立拆分的短任务；把 20 条完整对话塞进一次调用会改变语义，不能拿来绕过配额。

## 2. 分级处理与成本

> 以下占比、token 数、延迟均为 `[估算]` 假设，用于算账，不是实测；换业务要重算。

| 档 | 占比（假设） | 处理 | 单条 token | 延迟 | 触发条件 |
|---|---|---|---|---|---|
| **L0** 规则/索引 | 100% | 去重、路由、抽取、FTS/向量索引 | 0 | <5ms | 全部消息，确定性 |
| **L1** 小模型 | 5% | 分类/抽取/打标，批 4 | 400 in + 60 out | 50–300ms | 规则置信低、缺语义字段 |
| **L2** 单 agent | 0.2% | 3 次调用，带工具 | 3×(2k+300)=6.9k | 3–15s | 需多步推理/外部动作 |
| **L3** 多 agent | 0.01% | 15 次调用，分工/复核 | 15×(2k+400)=36k | 30–300s | 高价值、高风险、可拆 |

> L0 若含向量化，embedding 是另一类模型调用（不占生成式 token，但同样吃 GPU/配额）；10k/s 全量 embedding 本身就是独立容量问题，下面的账未含它。

**全量语义的账**（每条都调一次 LLM）：

```
10^4 × (1000+200) = 1.2×10^7 token/s = 7.2×10^8 TPM
日 token：1.0368×10^12（in 8.64×10^11，out 1.728×10^11）
deepseek-flash：off-peak $0.15/$0.60 每 M → $233,280/天；peak → $466,560/天
deepseek-v4-pro：off-peak $912,384/天；peak → $1,824,768/天
```

**分级的账**（L1 500/s、L2 20/s、L3 1/s）：

```
in  = 500×400 + 20×3×2000 + 1×15×2000 = 3.5×10^5 /s
out = 500×60  + 20×3×300  + 1×15×400  = 5.4×10^4 /s
合计 4.04×10^5 token/s = 2.42×10^7 TPM
flash：off-peak $7,335/天；peak $14,671/天（约为全量的 1/32）
```

**抽样 + 聚合**（1% 抽样、100 条/批、消息较短）：`1 次/s × 1200 token = 7.2×10^4 TPM`，flash off-peak 约 **$23/天**。这是"全量确定性处理 + 语义抽样"的成本杠杆：**语义覆盖率每降一个数量级，成本降一个数量级；但覆盖率不能凭空定，要由业务召回率倒推**。

**物理可行性**：10M in-token/s 的 prefill 约 `2×8G×10^7 = 1.6×10^17 FLOP/s`；H100 FP16 稠密 989 TFLOPS、按 35% MFU 约需 **460 张**（仅 prefill，不含 decode、网络、冗余）[估算]。30k 在飞 × 1.2k token × 128KiB/token（8B GQA 假设）≈ **4.7TB KV**，仅 KV 就要 ~59 张 80GB H100 [估算]。结论：**不是物理定律不允许，而是配额/成本/延迟三条同时不允许**；只有自建 400+ GPU、大批处理、放弃秒级端到端，才谈得上"全量语义"。对单一团队，"每条都调一次 LLM"没有可行前提。

## 3. 一致性现实核查

"这个系统没有一致性"混淆了"不需要全局串行"与"不需要任何定序"。以下六类位置必须有保证。**记忆越"透明"，越不能把一致性推给 agent**：agent 看不到版本冲突，运行时必须替它做定序、去重与冲突升级。

| 位置 | 出错形态 | 必须的保证 |
|---|---|---|
| 同一实体并发写 | 丢失更新、后写覆盖先写 | 每 key 串行，或 CAS/版本条件更新 |
| 状态机迁移 | 非法跳转、重复完成、卡死 | 迁移原子 + 版本 + 幂等 |
| 计数器/额度 | 超发、少扣、重复扣 | 原子增量或单写者 |
| 外部副作用 | 重复发消息/付款/写文件 | 幂等键 + outbox + 外部回执 |
| 唯一性约束 | 重复用户/订单/幂等键 | 数据库唯一索引，不是 check-then-act |
| 记忆合并 | 矛盾事实并存、静默覆盖 | OCC + 三方合并 + 冲突显式（[26 §5.3](../26-记忆中心并发Harness-v0.md)） |

**一致性预算**（按数据域选最弱但够用的模型）：

| 模型 | 适用 | 代价 | 例子 |
|---|---|---|---|
| 强一致单写者 | 金额、库存、额度 | 每 key 吞吐上限；故障切换要停顿 | 账本、扣款 |
| 每 key 串行 actor | 订单、会话、任务 | 热 key、队头阻塞、actor 生命周期 | 订单状态机 |
| 乐观并发 + 三方合并 | 记忆条目、文档 | 重试、冲突率、人审带宽 | MemoryItem |
| append-only + CRDT | 计数、在线状态、标签集合 | 元数据膨胀；无全局不变量 | PN-counter、OR-Set |
| 最终一致读模型 | 搜索、向量、看板 | 陈旧读；read-your-writes 要额外处理 | 索引/物化视图 |

规则：**全局强一致不必要，per-key 强一致不可省**。CAP 只在网络分区时逼你选；多数业务可用"单写者 + 幂等 + 补偿"避开分布式事务。真正不能省的是：同一实体上的写必须可定序，外部副作用必须可去重。

## 4. 写入路径

```
ingress → 幂等去重(key) → append-only log(partition=entity|thread)
        → 每 key 串行器 → 状态表(CAS/version)
        → outbox → 外部副作用(幂等收据)
        → CDC → 读模型(搜索/向量/OLAP)
```

1. **事件日志是事实源**，状态表是物化视图；日志按 `entity_id` 或 `thread_id` 分区，分区内有序，跨分区不承诺顺序。
2. **幂等键**用 `(source, event_id)` 或 `(entity_id, seq)`，唯一索引 + 7 天去重表；重复提交返回首次结果，不重复写。
3. **每 key 单写者**：actor 或"分区消费者 + 单在飞"；不同 key 可并行。热 key 是并发度的硬上限，不是加机器能解决的。**存储层有效并发 ≈ 活跃 key 数，不是 agent 数**；1 万 agent 打 1 个 key，串行度就是 1。
4. **批量提交**：30k 事件/s × 512B ≈ 15MB/s、约 1.3TB/天；按 5–20ms 或 100–500 条 group commit，把 fsync 摊薄。逐条 fsync 在单盘上不可行。
5. **读模型异步**，记录 `version/offset`；需要 read-your-writes 时用会话版本等待，不能假设"写完立刻搜到"。
6. **向量索引**：pgvector 与主数据同库同事务，天然 ACID + WAL 复制[文档]；独立向量库则走 outbox + 版本号，查询时按主库版本过滤，删除用 tombstone。ANN 是近似检索，**索引命中不等于数据一致**。
7. **存储分层**：事件日志用追加/LSM（写优化），实体状态用 B-tree 行存（点查/事务），分析走列存/OLAP；write-behind 只用于可重建的读模型，事实源必须同步落日志，不能靠缓存回写。

| 指标 | 单机可跑 | 触发分布式 |
|---|---|---|
| 入口速率 | ≤10k msg/s | 持续 >10k/s，或多租户 |
| 日志追加 | ≤50k 事件/s（顺序写） | >50k/s，或需跨机复制 |
| 状态写入 | ≤20k 写/s（批量提交） | >20k/s，或单 key >5k/s |
| 热状态 | ≤50GB | >50GB，或总量 >1TB |
| 并发 agent | ≤128 | >128，或需跨机故障转移 |
| 保留期 | ≤7 天本地 | 合规/回放要求更长 |
| 可用性 | RPO 分钟级 | RPO≈0、多 AZ |

**1 万/s 本身不构成分布式理由**；触发点是 HA、租户隔离、保留期和写放大。

## 5. 反压与失控防护

反压的基本算式：`积压增长 = λ - μ`，`排空时间 = 积压 / (μ - λ)`。阈值要按"秒"和"钱"设，不按消息条数设。

| 指标 | 阈值（建议） | 动作 |
|---|---|---|
| 消费 lag（按秒，不按条数） | >30s 或 >5× 基线 | 先降 L3，再降 L2 抽样 |
| 单分区队列深度 | >1 万且连续 5min 增长 | 重分区/限流 |
| LLM 429 比例 | >1%/min | 发放速率减半，扩配额 |
| token 花费 | >80% 小时预算告警；>100% 熔断 | 停 L2/L3，只留 L0/L1 |
| agent 放大系数 | 均值 >3 或单根 >50 | 阻断 spawn，查触发环 |
| 重试率 / 同错误 | >5% / 同错误 >1%/min | 熔断 30s，进 DLQ |
| 热点 key | >3× 均值 | 本地预聚合/拆 key |
| 写冲突率 | >5% | 降并发/拆写域（不是加重试） |
| 租约过期率 | >1% | 查心跳、GC、超时 |
| 端到端 p99 | >2× SLO | 降级，保 L0 审计 |

**Agent 触发风暴**（agent 之间互相触发）三道闸：① 因果链 `root_id` + `depth ≤5`；② 单根 `spawn ≤50`、fan-out ≤3；③ 按 `(root_id, step)` 去重，禁止实例间直接消息（沿用 [26 D-H9](../26-记忆中心并发Harness-v0.md)），所有触发必须落到日志再消费。**重试风暴**用"重试预算"（如请求量的 5%）+ 指数退避 + 抖动 + 熔断；**租约**分两类：消息级 5–30s 或无租约（无状态），agent 任务 60s TTL/15s 心跳（[26 §4.3](../26-记忆中心并发Harness-v0.md)）。降级顺序固定：L3 → L2 抽样 → L1 → 只做 L0；**永不丢 L0 审计日志**。

## 6. 技术选型对照

**单机最小形态（P0，10k msg/s 以内）**

| 层 | 选择 | 理由 / 不该用 |
|---|---|---|
| 入口/队列 | 单进程 + NATS JetStream 或 Redis Streams | 10k/s 足够；不必上 Kafka |
| 状态 | Postgres 18 单节点（或 SQLite 原型）+ 分区表 | 事务/唯一约束/SQL 成熟；别用 Redis 当事实源 |
| 向量 | pgvector（同库同事务） | <500 万向量够用；别双写独立向量库 |
| 调度 | 进程内 worker pool + 租约表 | 128 并发以内；别上 Temporal |
| 模型 | 单一 provider + 信号量 32–128 | 别自建 vLLM |
| 观测 | Prometheus + 结构化日志 | 先有 lag/成本/冲突三组指标 |

**万级形态（10k msg/s 持续）**

| 组件 | 何时合适 | 何时不该用 |
|---|---|---|
| Kafka / Redpanda | 需回放、多消费组、7 天+保留；3 节点起步 | 只有 1 个消费者、<1k/s：Postgres/Redis 更简单 |
| Flink | 窗口聚合、去重、状态化 ETL；checkpoint 提供故障无差别恢复[文档] | 只做逐条过滤/转发：普通 consumer 就够 |
| Temporal | L2/L3 长流程、审批、补偿；durable execution[文档] | 每条消息一个 workflow：history 开销不划算 |
| Ray | 离线批推理、agent fan-out 调度 | 低延迟有状态服务：调度开销大 |
| Postgres | OLTP 事实源、按 entity 分区 | 大宽表分析：上列存/OLAP |
| Redis | 热计数、限流、锁、会话 | 系统 of record：内存成本 + 持久化边界 |
| 向量库（Milvus 等） | >5–10M 向量、需分片/多租户；一致性级别可选[文档] | 小规模：pgvector 的 ACID 更省心 |
| vLLM | 自建 L1/L2、连续批处理拉高吞吐[文档] | 流量尖峰/低利用率：API 更便宜 |

> 选型表中"何时不该用"是 `[推断]`（基于语义匹配与运维复杂度），不是基准结论；具体规模阈值需用真实流量压测校准。
