## 1. 四条设计要点（原话整理）

**① 交互以流畅为准**
用户随时可以发消息，agent 随时实时应答各类消息；**不要一问一答**，**不要用户可感知的消息队列**。

**② 单一秘书 + 专家执行**
跟我对接的只有**一个统一 agent**（秘书/助理）。它理解我的需求后，把任务**下发给不同的专家型 agent 执行**。秘书要**响应非常快、非常聪明**，但**不需要掌握所有知识**——靠派发给对应领域 agent 来补。

**③ 树形会话组织 + 部分上下文共享**
会话可以有**子会话**，子会话还可以再有子会话——树状结构。原因：复杂任务要拆成树/DAG；不同会话之间**需要共享上下文**，而且是**部分共享**。

**④ 在同一会话窗口内汇总**
一个窗口里可以**同时讨论三个子任务**；agent 要能分清每个子任务对应的**记忆、状态**；子任务执行完后，在**同一个会话窗口**里把三份结果**汇聚**，进入下一步处理——不用人工整理。

## 2. 这套设计和 Super-agent 的区别（先划清，免得概念误套）

| 维度 | Super-agent（参考素材） | 你的设计 v0 |
|---|---|---|
| 驱动源 | 环境事件（群聊/CI/邮件），人不一定在场 | **人在对话里持续输入**，人始终在场 |
| 组织单位 | Ticket（工单）+ Thread（事件流） | **会话树**（会话 → 子会话 → …） |
| 人机关系 | 人上移到"决策与验收层"，平时静默 | 人随手说，秘书实时接话、随时分派 |
| 并发单位 | Worker Session（一 Ticket 一 Session） | 子会话（可并行，也可同窗口讨论） |
| 汇总 | 报告 + 人肉验收 | **系统内汇总**，回灌到同一窗口继续下一步 |

**结论**：可以参考它的机制（Router 不下场干活、上下文引用而非全量、并发 slot），但**概念不要硬套**——你的主线是"以会话树为组织单元、以人为中心的实时协作"，不是"事件驱动的调度系统"。

## 3. 四条主线各自的硬问题

### 3.1 交互流畅：什么是"不排队"？

"随时发消息 + 实时应答"听起来简单，实际要先定三件事：

- **打断语义**：agent 正在输出时，用户又发一条——立刻停？说完这句再处理？还是先确认"收到"再把新消息纳入后续？
- **合并窗口**：用户连发三条（"帮我做个 X" / "要快" / "别动线上环境"），是三次独立应答，还是合并理解一次回答？我倾向后者：**内部允许合并，用户不可感知**。
- **两段式应答**（我的建议）：秘书先给**低延迟的即时反应**（"收到，我拆分一下" / 直接开始），专家结果**流式补充**进来；这样"快"和"准"不冲突。

关键区分：**系统内部可以有队列/背压，但"用户可感知的排队"不能有**。物理上完全无队列不现实（模型推理有时间），可承诺的是：永不无响应、消息不丢、可随时打断。

### 3.2 秘书 + 专家：边界与延迟

- **职责边界**：秘书持有全局意图、约束、进度、我的偏好；专家只拿"任务简报 + 所需上下文"，不直接对我说话（或只在被指派时说话）。**秘书不下场干活**——否则它会被拖慢，这是从 Super-agent 借的判据。
- **延迟预算**：秘书要快 → 小模型/短上下文/首 token 低延迟；专家要强 → 大模型/深上下文。两者用不同模型、不同工具集。
- **派发时机**：是等我"说完"再派，还是**边听边预判、投机派发**？后者更快，但会白干。建议：先"理解后派"，跑稳后加"预判派发"。

### 3.3 会话树：上下文怎么"部分共享"（最难的一块）

必须把"共享"拆成三种状态，否则会乱：

| 状态 | 含义 | 例子 |
|---|---|---|
| **继承**（父→子，一次性） | 派发时把父节点的目标/约束/已定决策注入子会话 | 子任务知道"要快、别动线上" |
| **发布/订阅**（实时） | 父节点把某些结论实时广播给相关子节点 | 子任务 A 定了接口，B 立刻知道 |
| **隔离**（默认） | 子会话的草稿、试错、中间推理不往上传 | 免得污染其他分支 |

需要你拍板的点：

- **方向**：父→子继承哪些？子→父是全程可见还是只在结束时提交？**兄弟之间**直接共享，还是必须经父节点中转？
- **方式**：共享用"派发时快照"（简单、可复现）还是"实时可见"（更灵活、更难一致）？
- **冲突**：两个子会话改了同一个共享结论，谁赢？需要版本号/合并策略吗？
- **树 vs DAG**：你说"树或 DAG"。树是组织形式，DAG 是依赖关系——建议：**会话树 + 显式依赖边**，不要为了 DAG 把树改成图。

### 3.4 汇总：谁来汇总、汇总什么

- **谁汇总**：秘书自己做，还是专门起一个"汇总专家"？建议先秘书做（它本来就有全局视角）。
- **汇总什么**：子会话全文？还是每个子会话结束时产出**结构化 handoff**（做了什么 / 结论 / 产物 / 未决问题 / 证据）？我强烈建议后者——否则汇总就是二次阅读全文，成本爆炸。
- **细节保留**：汇总会丢信息。建议：handoff 只带摘要 + 引用（指向子会话/产物），需要细节时再展开（这就是 Inline & Spill 的思路）。

## 4. 待你拍板的问题（按优先级）

1. **打断语义**：你说"随时发消息、实时应答"——当 agent 正在输出时又来新消息，期望它：立刻停？说完再处理？还是先确认再纳入？
2. **"不排队"的定义**：是"我发出去必须马上有反应"，还是"多条消息可合并理解、不要求逐条回"？（我理解是两者都要，内部队列不可见）
3. **会话树的共享规则**：父→子继承什么？子→父何时可见？兄弟之间共享吗？快照还是实时？
4. **专家执行是什么形态**：专家也形成**子会话**（有完整对话记录），还是只是"任务 + 结果"？
5. **同窗口多子任务的呈现**：三个子任务在一个窗口里，用分栏、卡片流、还是缩进子线程？
6. **汇总由谁做**：秘书，还是专门的汇总 agent？

## 7. 第五个要点（地基）：记忆优先，而不是模型优先

> 原话见 [`10-设计对话记录.md`](10-设计对话记录.md) 第 5 节。

### 7.1 命题：记忆是主体，实例是视图

传统写法：`Agent = 思考过程 + 记忆（记忆是 Agent 的一部分）`。
你要的反转：**`记忆 = 主体`，`Agent 实例 = 记忆的临时视图 + 私有工作集`**。

- 大模型 = 可替换的推理算力（换模型不影响"这个 agent 是谁"）；
- 记忆 = 身份、知识、连续性、沉淀；
- 实例 = 按需 spawn、可并发、有短期私有记忆、结束后回写。

一个精确的类比（我建议拿它当架构语言）：**记忆像数据库，实例像会话/事务**。
- 多个实例并发读同一份记忆 → **快照隔离**（各自读一个固定版本）；
- 写回 → **提交**，需要合并/冲突处理（乐观并发）；
- 这样可以同时拥并发与一致性，不必发明新协议。

### 7.2 这会让前面四条重新落位

| 前四条 | 在记忆优先下变成 |
|---|---|
| ① 流畅交互 | 秘书是根记忆作用域上的**长驻实例**；对话是它的读写视图 |
| ② 秘书 + 专家 | 专家 = **领域记忆作用域**（后端/前端/测试）；派发 = 在该作用域上 **spawn 实例** |
| ③ 会话树 + 部分共享 | 很可能是**记忆作用域树**的 UI 视图：父作用域 → 子作用域，共享=作用域继承，隔离=私有工作集 |
| ④ 同窗汇总 | 汇总 = 把子实例的 handoff **蒸馏写回**到父作用域，而不是"在聊天窗口里拼一段话" |

**需要你确认的关键判断**：会话树和记忆树，是同一棵树，还是两个视图（会话可以引用/组合多个记忆作用域）？这决定数据模型是"一个树"还是"树 + 引用图"。

### 7.3 记忆分层（我的建议，待你改）

```
全局记忆        （我的偏好、长期目标、跨领域约束）
  └─ 领域记忆    （后端/前端/产品/测试…，各自一套）
       └─ 任务记忆（一次复杂任务，可跨领域）
            └─ 实例私有工作集（草稿、试错、中间推理，默认不上传）
```

- **读**：实例 spawn 时拿到"作用域快照 + 按需检索"，不是全量灌入（否则上下文爆炸）。
- **写**：实例结束时提交 handoff / 候选记忆；由记忆管理器合并成新版本。
- **隔离**：私有工作集默认不写回；只有"结论/经验/决策"才允许上升。

### 7.4 10 个并发实例怎么共享记忆（并发语义）

1. 每个实例 spawn 时**钉住一个记忆版本**（快照）；
2. 执行期间只写自己的私有工作集；
3. 结束后提交 handoff，带 `baseVersion`；
4. 记忆管理器做**乐观合并**：无冲突 → 直接产生新版本；有冲突 → 标记冲突、由秘书/人或专门合并者裁决；
5. 永不原地覆盖——记忆是 append-only 的版本历史，可回滚、可追溯。

### 7.5 头号风险：记忆污染（这一条必须设计进去）

LLM 生成的"总结"一旦写进公共记忆，就会成为之后所有实例的"事实"。错误记忆会像病毒一样扩散。

必须有的防线：
- **来源分级**：用户亲口确认 > 系统记录（工具/代码事实）> agent 推断/总结；
- **候选制**：实例不能直接改公共记忆，只能提交候选；
- **可回滚**：每次写回产生新版本，能定位"这条错误记忆是哪个实例写的、基于什么"；
- **衰减与遗忘**：旧事实要 TTL / 降权；"过时"本身要能被记录；
- **冲突可见**：两条矛盾记忆不静默覆盖，而是显式并存、标注冲突。

### 7.6 待你拍板（按优先级）

1. **记忆的最小单位**：结构化条目（事实/决策/需求/进展/经验，带作用域+来源+版本）还是自由文本块？我建议结构化条目 + 自由文本附件。
2. **写回方式**：直接写 vs 候选 + 合并（我建议后者；高风险写入要人审）。
3. **会话树 = 记忆树？** 同一棵树，还是会话可以组合多个作用域？
4. **并发语义**：快照隔离 + 乐观合并，可以吗？
5. **权威顺序**：用户 > 系统 > 推断，对吗？旧记忆要不要 TTL？
6. **spawn 权限**：秘书 spawn，还是领域作用域自己按负载 spawn？

### 7.7 和 Super-agent 的关系（一句话）

Super-agent 是"事件 → 工单 → 执行"；你是"**记忆 → 实例 → 执行 → 沉淀**"。前者以任务为中心，后者以记忆为中心。**可以参考它的并发/隔离机制（一实例一目录、slot、恢复注记），但领域模型要重新设计。**
