# Super-agent 三条主线详解：双层架构 / 事件驱动 / 存算分离

> 参考素材，非方案。详细证据见 [`../archive/research/super-agent-report.md`](../archive/research/super-agent-report.md)。
> 标注：〔A〕官方文章明确 · 〔B〕官方原型代码/文档 · 〔D〕调研者推断。

## 先讲三者为啥是一件事

它们不是三个并列特性，而是**同一个判断的三个推论**。

那个判断是：**瓶颈已经从"模型能不能做"变成"人的注意力够不够用"**。团队观察：一个人通常只能同时跟进 3–5 个活跃会话〔A〕。而单个 ReAct 循环（一问一答、同步工具调用、一个会话）有三个结构性限制：串行、绑单机、必须被人推进。

所以团队说了一句很关键的话：这些约束和传统计算机系统长期面对的问题**同构**，因此**调度、缓存、存算分离、看门狗这些经典系统思想可以直接迁移**〔A〕。这句话把这件事从"提示词工程"重新定义成"系统设计"——这也是理解三条主线的钥匙。

一个统一的类比〔A〕：Agent 系统 ≈ 操作系统。Worker ≈ 进程，Router ≈ 调度器，Subscription ≈ 文件描述符，Mandate ≈ capability，Ticket ≈ job，Effects ≈ WAL，Inline & Spill ≈ page cache，链式召回 ≈ inode 引用跳转。

## 一、双层架构：把"连续性"和"并发"拆开

### 要解决的矛盾

- **跨渠道连续交互** 要求：全局上下文、同一件事在 IM 和 PR 里被认成同一件 → 天然倾向**一个会话全接**；
- **多任务高并发** 要求：上下文隔离、互不阻塞 → 天然倾向**每个任务一个会话**。

全塞一个会话：串行、吞吐低、细节混杂；全开独立会话：没有全局上下文、结果割裂、多个会话各自回复人。这是**根本权衡**，靠调提示词解决不了。

解法：把「维护全局连续性」与「高并发执行」拆成两层。核心一句：**"Session 应该成为系统实现细节，而不是用户认知负担。"**〔A〕

### 两层职责

| 维度 | **Router 层** | **Worker 层** |
|---|---|---|
| 角色 | 常驻全局路由：全局序点、协调、记忆 | 具体执行：上下文隔离的并发执行体 |
| 承接 | **所有人类交互**；跨任务信息与决策汇总 | 单一任务；完整工具 |
| 亲自干活 | **否**（原型里甚至可以不配 Bash）〔A〕 | **是** |
| 对外说话 | **唯一出口**，统一回复人 | 否，只向 Router 汇报状态 |
| 上下文 | 全局、连续、跨渠道 | 局部、隔离、单任务 |
| 建议模型 | **轻量模型**（长输入短输出，只需分派） | **最强模型**（直接决定结果质量） |
| 任务内部拆解 | **不介入**（只处理任务之间的关联与分派） | 自己决定 |
| 自由度 | 不必是单会话，部分逻辑可不调 LLM | 内部可再开 subagent，甚至本身是个团队 |

### 最容易抄错的地方：双层 ≠ Agent Team

| | 常见多 Agent 编排 | Super-agent 双层 |
|---|---|---|
| 解决什么 | **一个复杂任务内部**怎么拆步骤、分角色 | **任务之间**怎么排队、归属、分派、恢复 |
| 子任务耦合 | 紧耦合 | 松耦合、彼此独立 |
| Lead 负载 | **极重**（理解细节、规划、高频协调） | **极轻**（高层关联与分派） |
| 类比 | 技术负责人 + 团队 | **调度器 + 工作进程** |

**判据：主会话有没有下场干活。** 主会话只研判分派、不亲自执行 = 双层；既规划又执行 = 只是团队。〔A〕
官方甚至给了反向等价：用提示词约束一个团队的主会话"不执行、只对外交互并分派"，它就已经是双层架构了。

### Router 为什么不是瓶颈：批处理

表面看 Router 是全局单点，必然卡。实际不必然〔A〕：

1. 上一轮推理期间到达的事件**积压**，下一轮**一并注入**，自然形成 batch；
2. Router 每步是**长输入、短输出**（只做轻量交互与分派）；
3. 批量的多条 Trigger 合并进**一次** LLM 调用，在 **Prefill 阶段并行**计算 —— 单次请求耗时增长远慢于 batch 大小。

实测：Trigger 到达 1→40 条/分钟，平均 batch 1.0→2.8，单次请求 2.5s→3.9s，**单个决定分摊的推理时间 6.4s→1.6s**〔A〕。

代价：**Router 单点 vs 分片的内在矛盾**。任务量上去必须分片，而切分越细、分片间记忆与上下文连续性越低——官方明确承认"在全局记忆问题解决前，这个权衡始终存在"〔A〕。

## 二、事件驱动：驱动源从"人打字"换成"环境事件"

### 变化本身

驱动 agent 的主要输入，从"人在会话里逐条键入的提示词"，变成环境中源源不断的**半结构化事件**，叫 **Trigger**：群聊消息、邮件、日程提醒、代码评审评论、CI 结果……〔A〕
同一条事件流（同一个 PR / IM 话题 / 邮件串）下的 Trigger 构成 **Thread**，是有序序列。

Trigger 的完整生命周期有四步，对应四个模块边界：

```
Source ──Trigger──> ①两级过滤 ──> ②订阅直通路由 ──> ③上下文组织 ──> Worker Session
                        │                                          │
                        └──> Router 研判 → Ticket ─────────────────┘
                                                     └─> ④投机执行（提前开工）
```

### 三个 Fast / Slow Path

这是"程序 vs 模型"的分工在三个环节上的重复〔A〕：

| 环节 | Fast Path（程序，确定性） | Slow Path（模型，语义） | 解决什么 |
|---|---|---|---|
| **过滤** | 来源、群组范围、白名单、是否 @、是否 bot | 用提示词策略判断"这条值不值得介入" | 真实事件流是**高噪音、低触发率**，逐条调模型又慢又贵 |
| **路由** | 已归属事件由程序**直投**给订阅该 Thread 的 Worker | Router 只研判**尚未归属**的新事件 | 让全局节点不承受"每条后续消息都转发"的负载 |
| **上下文** | 对象 ID + 摘要；按局部性逐步内联 | 需要时按 ID 展开完整内容 | 窗口是 cache，不是仓库 |

实测直通效果〔A〕：完成时间基本不变（**直通不提速**），但 Router 决定数 ↓约 30%，读缓存 token 3177 万 → 2323 万（**↓约 37%**）。

**过滤这一层真正的价值不是性能，是信任边界**〔D〕：**永远不要用模型当权限边界**。谁能触发 agent 由代码判定（白名单、来源、身份），模型只在"已准入"的候选里做语义研判。反过来做（让模型看消息自己决定动不动），是这类系统最容易被提示词注入攻破的地方。

### 订阅直通：一个很精妙的设计

- Worker 创建后**订阅**它负责的 Thread，后续同 Thread 事件由程序直投，**不需要 Router 每次调工具转发**；
- 订阅是**多对多**：一个 Worker 可订阅多个 Thread，一个 Thread 可被多个 Worker 订阅；
- 多个 Worker 在同一工作环境（如同一个 PR）发生交集时，新事件**同时扇出**给所有订阅者 → 它们**无需点对点通信**，也能看到彼此操作、自行发现和解决冲突；
- 越界处理：Worker 可取消订阅或交回 Router 重新分派。

这等价于把并发控制从「消息传递 + 锁」换成了「**共享观察 + 自主避让**」〔D〕。代价：没有强一致性（两个 Worker 可能同时改同一处），收益：不需要写一整套 Agent 间通信协议。对代码场景够用（git 本身就是乐观并发），对强一致场景不够。

### 上下文：Inline & Spill + 链式召回

原话：**"浪费上下文窗口，就是浪费模型的智能。"**〔A〕
两个基本操作：**Inline**（近期高相关直接塞进窗口，省工具往返）、**Spill**（超预算/低频内容留在窗口外，只留引用）。

一条可照抄的注入阶梯〔A〕：
1. 从最少信息开始：只给对象 ID 和摘要；
2. 利用局部性逐步内联：先附紧密关联对象 ID，再附时空相邻内容（内容前 50 字、IM 前后相邻消息与所回复消息、评审讨论相邻评论）；
3. 超上限就截断，并**保留续读入口**，模型需要时再调工具读。

**链式召回**：给 Trigger、Thread、Worker Session 都编唯一 ID；注入时内联紧密关联对象的 ID，使对象在底层构成一张**引用图**；工具召回返回的对象**同样遵循 Inline & Spill**，于是每一跳又带出下一跳的 ID。模型不是"在记忆里找"，而是**在引用图里跳**〔A〕。

这缓解了 Router 的长程问题：既不能把所有历史塞进窗口，又要在用户跨渠道提起旧任务时找回上下文。

### 投机执行：允许它偷偷干活

借自计算机系统的**投机执行**〔A〕：不确定结果会不会被采用时，**根据环境信号在后台提前尝试**，用额外后台算力换人的等待与介入成本；**有价值就交付，没价值就丢弃**。

最典型的例子：团队在内部群配了"**静默复现并修复**"策略——有人反馈问题或讨论方案时，agent 先在隔离目录里尝试复现、找修复；**只有"确认了问题"且"找到简单修复方案"两个条件同时满足**，才把结果交付（通常是直接提 PR），否则全程安静〔A〕。

硬币的另一面：**允许它白干，就必须允许执行廉价、可丢弃、无外部副作用**——投机阶段只能在隔离目录/沙箱里做，不能去 push、不能改线上〔D〕。

## 三、存算分离：把"跑循环 / 存状态 / 执行环境"拆开

### 问题

现有本地 agent 默认把三件事**绑在同一台设备**〔A〕：推进 Agent Loop 的**计算**、需要持久保存的**会话状态**、代码仓库与本地工具链等**执行环境**。后果：设备休眠/离线 agent 就停，且无法访问其他设备上的环境。

### 两步解耦

| 步骤 | 解耦 | 效果 |
|---|---|---|
| 第一步 | Agent Loop **计算** ↔ **持久化会话状态** | 摆脱单机生命周期，云端持久在线 |
| 第二步 | 云端 Agent Loop ↔ **重状态执行环境** | 真实工作环境留在原地，只部署"负责执行命令、返回结果"的轻量 daemon |

由此支持〔A〕：
- **BYOM（Bring Your Own Machine）**：把用户日常开发机接入云端 agent；
- 云端托管机器或按需创建的计算环境；
- **间歇在线设备**：某台个人设备重新上线后，云端 agent 自动触发并完成需要在该设备执行的任务。

### 与 Anthropic「脑手分离」的同与异

相同〔A〕：harness 保持**无状态**；会话日志存放在 harness **之外**；通过**统一接口**按需接入执行环境。
差异〔A〕：Anthropic 描述的是托管服务（按需创建的沙箱、客户 VPC）；DeepSeek 首先要接入的是**用户日常使用、可能间歇在线的个人机器**——上面有未提交修改和本地凭据。

这个差异不是措辞，是**威胁模型**的差异〔D〕：托管沙箱是"干净、可弃、无凭据"；个人开发机是"脏、不可弃、满是凭据"。同一套架构在两个场景下安全含义完全不同。

### 原型实际落地的"单机降级版"

原型的存算分离**没有实现**（它是单进程 + 本地 SQLite）〔B〕，但在单机范围内做到了逻辑分离，这是可直接抄的最小版本〔B〕：

- **状态**：单一 SQLite 文件，**只有 Store 能打开**；启动先取**目录锁**，防第二个进程；
- **计算**：Router/Worker 都是会话，可替换、可中断、可重启，**崩溃不影响状态**；
- **环境**：一 Ticket 一目录（默认在 state 目录下），首次派工前跑一次 **prepare 命令**（10 分钟超时，典型 `git worktree`）；
- **恢复**：重启后运行中的 assignment 以 "host restarted" 结束，新 assignment 带**恢复注记**——"先核对目录、git 历史、远端状态，再重复任何外部动作"。

一句话总结这个降级版：**计算体是牲口，状态是宠物，环境可重建**。

## 三条怎么咬合

- **事件驱动** 决定"什么值得动、动谁"（过滤 / 路由 / 上下文）；
- **双层架构** 决定"谁来动、怎么并发"（Router 研判分派 / Worker 隔离执行）；
- **存算分离** 决定"在哪动、崩了怎么继续"（状态外置 / 环境原地 / 恢复注记）。

三者共同的前提：**会话降级为实现细节，人上移到决策与验收层**。

## 两条现实提醒（设计前必须知道）

1. **文章 ≠ 原型**〔B〕：双层、事件驱动、授权已落地；**存算分离/BYOM 与 Watchdog 在原型中未见实现**，是纯设计主张；异步 ReAct Loop 官方明说"已在 DSH 实现但未默认开启"〔A〕。
2. **实验数字不可外推**〔A〕：合成负载、约 300 条消息、编码工作用"只耗时工具"替身，**只评调度效率，不评执行质量**；p50 12.4 分钟不能被理解成"修一个 bug 要 12 分钟"。
3. **两个空白**〔D〕：验收门没被做成一等原语（`ready` Report + 人肉看 PR）；打扰成本没有量化指标（没有"主动"变成"噪音"的判据）。—— 这两块如果在你自己的设计里做，是真正的差异化空间。
