## 0. 一分钟读法

**先看七条结论，细节在后文。**

1. **这套系统的本质不是"一群 Agent 聊天"，而是一个以记忆为数据库的运行时**：记忆是唯一真相；Agent 类型是"模式（schema）"；实例是"事务（transaction）"；协作是"多个事务之间的协议"；自主是"系统自己给自己发事务请求"。
2. **你说的两个核心，正好对应两张表**：
   - **数据绑定** = `AgentType × DataSelector → Binding`：一个类型可以覆盖多个存储/实体类型的任意子集，一个存储也可以被多个类型覆盖；**不需要一对一，允许部分覆盖、重叠、漂移**；
   - **动态派生** = `Type Forge`：运行时按任务/数据模式生成新的 Agent 类型（草案 → 注册 → 灰度 → 实例化），**派生的是"类型"，不是"记忆本体"**。
3. **多智能体协作模式不需要 N 套协议**：**8 个协作原语 + 4 类拓扑 + 共享范围 + 预算**就能表达绝大多数模式；模式 = 编排模板，引擎只执行模板，不为每种模式写死代码。**但要把"任务内协作"和"任务间并发"分成两层**——后者（26 的 1 万工作项）实例之间没有消息流，混进来会把系统做坏。
4. **自主不是"随机乱动"**：自主 = **自产信号 + 自定目标 + 自排优先级 + 自评结果**，且必须挂到"触发源 + 目标 + 授权 + 预算"四要素上才允许执行。自主分 L0–L4，本期做到 L3（边界内自主规划），L4（自改类型/策略）只做受控的类型派生，**不做内核自改**。
5. **每秒 1 万条消息，全量"处理"可以，全量"LLM 推理"不可能**：1 万条/秒 × 一次 4k token 调用 ≈ 每秒 4,500 万 token ≈ 每天 3.9 万亿 token，成本与配额都差 3–4 个数量级。正确形态是**分级处理**：L0 规则/索引吸收 95%+，L1 小模型/本地模型吸收大部分剩余，L2 LLM 只处理"值得想"的 0.1%–1%，L3 多 Agent 协作更少。
6. **"没有一致性"只对了一半**：跨消息不需要全局事务，但**同一实体的定序、副作用幂等、记忆合并冲突**三处必须有机制；否则高并发下会出现丢更新、重复发消息、记忆互相矛盾。本方案给"**一致性预算**"：按数据域购买一致性，不买全局强一致。
7. **落地顺序不能反**：先证明"记忆 + 类型/绑定 + 委派/评审 + 目标监控"的语义闭环（单机、100 msg/s），再上协作模式库，最后才是万级吞吐。**先做 1 万并发会失败**（与 [26 §11](26-记忆中心并发Harness-v0.md) 同一判断）。

**一句话方案**：

> **一个记忆库 + 一个类型/绑定注册表 + 一条信号总线 + 一个实例运行时 + 一层协作编排 + 一层自治内驱**；万级吞吐靠分区与分级，不靠"起 1 万个进程"。

## 1. 我对你想法的理解（逐条对齐）

> 这一节先确保"我理解对了"，再谈设计。**如果某条理解错了，后面整篇都要改。**

### 1.1 你的原话 → 我的理解 → 设计落点

| # | 你的原话（语义校正后） | 我的理解 | 设计落点 |
|---|---|---|---|
| 1 | "这个系统支持自主行动、自主规划、自主思考，就像真人一样，不需要外界触发后才被动响应" | 主动性不是"更快的被动响应"，而是**系统内部能生成"下一步做什么"**：目标检查、定时、异常、反思、好奇/机会都能产生事件 | §6 自治层：**内驱（Drive）也是事件源**；L0–L4 分级；目标/计划/反思是一等对象 |
| 2 | "每秒 1 万条消息进来，每条都要处理" | 这是**流处理问题**，不是"1 万次聊天"；"处理"必须允许**分级处理深度**，否则物理上不成立 | §7 分级处理 L0–L3 + 分区 + 批处理 + 反压 |
| 3 | "派送 1 万个 Agent 实例去处理，本质上处理的都是同一个透明的记忆" | 逻辑上可以"一条消息一个执行体"，但**活跃实例数由处理时长决定**（Little's law）；"透明记忆"= 同一记忆库的**快照读 + 候选写**，不是并发直写 | §3/§7：事件总线按 key 分区；实例短生命周期；记忆读写沿用 12/24 的快照隔离 + 候选制 |
| 4 | "这个系统反正也没有一致性的地方" | **对一半**：消息之间不需要跨实体事务；但同一实体并发写、外部副作用、记忆合并**必须有定序/幂等/冲突处理** | §7.4 一致性预算表；§7.5 反压与风暴控制 |
| 5 | "让一种类型对应一种存储类型，或者对应一个数据实体类型的范围；不要求完全匹配，粒度可任意组合" | **Agent 类型 ↔ 数据不是外键，是"覆盖映射"**：选择器 + 投影 + 触发 + 写域，支持 N:M、部分覆盖、重叠 | §4 数据绑定：`Binding = (AgentType, DataSelector, Projection, TriggerPolicy, WriteScope)` |
| 6 | "10 个存储里，一个'物类型'可以对应某些类型的部分数据" | **物理存储、逻辑实体类型、数据实例**要分三层；绑定落在"逻辑实体类型 + 字段/标签/关系"上，不直接绑物理表 | §4.1 三层数据模型；§4.3 绑定编译与倒排索引 |
| 7 | "Agent 可以动态创建新的 Agent 类型，这种类型有对应的数据处理方式" | **类型是第一等、可运行时生成的对象**；派生要经过注册、校验、灰度，不能绕过 | §4.4 Type Forge：草案 → 注册 → 影子/灰度 → 激活 → 回滚 |
| 8 | "核心两点：动态的派生部分 + 跟数据绑定" | 这两点决定系统的**扩展方式**：加数据/加任务 → 派生类型/绑定，而不是改内核代码 | §4 全章；§5.5 模式也是"协作模板的派生" |
| 9 | "自我进化先不说，等发现了后面再说" | 本文**不做** L4 自改内核；只保留"类型派生"这个受控接口，并明确边界 | §4.4 边界；§13 D-M8 |

### 1.2 一个必须说清的纠偏：两种"多 Agent"不是一回事

这是本方案与很多"多 Agent 框架"最大的区别，也是 [26 §1.2](26-记忆中心并发Harness-v0.md) 已经指出过的：

| | **层 A：任务内协作（Intra-task）** | **层 B：任务间并发（Inter-task）** |
|---|---|---|
| 解决什么 | **一个复杂任务内部**怎么拆、分工、评审、汇总 | **很多任务之间**怎么并行、归属、恢复、合并 |
| 实例之间 | **有消息流**（请求/回复/辩论/投票） | **没有消息流**，只共享记忆 + 候选合并 |
| 协调靠什么 | 协作协议 + 角色 + 会话/线程 | 租约 + 版本 + 合并规则 + 反压 |
| 失败模式 | 无限对话、成本爆炸、责任稀释 | 冲突、重复执行、假吞吐、人审积压 |
| 典型例子 | 需求 → 设计 → 实现 → 评审 → 测试 | 1 万条客服消息各自处理，共享知识库 |
| 本方案 | §5 协作层 | 沿用 [26](26-记忆中心并发Harness-v0.md) 的 harness |

**判据**：两个执行体之间是否存在"必须实时交换语义才能继续"的依赖。有 → 层 A；没有 → 层 B；混合 → 在层 A 的某个子任务内部再走层 B。

**为什么必须先分开**：如果把层 B 也做成"1 万个 Agent 互相聊天"，就同时背上了协作协议的开销和消息风暴的风险；如果层 A 也只靠共享记忆，就表达不了"辩论/评审/投票"这类需要**同步语义**的模式。**两层各自优化，接口只保留"任务/记忆/预算"三样。**

## 2. 设计判据与不变量

### 2.1 五条设计判据（违反任一条，方案就要重做）

| # | 判据 | 为什么 |
|---|---|---|
| J1 | **记忆是唯一真相，实例可丢弃** | 崩溃恢复、弹性扩缩、换模型都不影响"这个 Agent 是谁"〔沿用 12 I1/I2、24 I1–I8〕 |
| J2 | **任何自主行动可归因**：触发源 + 目标 + 授权 + 预算 | 否则无法审计、无法止损、无法判断"该不该做" |
| J3 | **扩展靠加类型/绑定/模板，不改内核** | 否则"动态派生"只是口号，系统会退化成 if-else |
| J4 | **全量处理 ≠ 全量推理**：分级是架构，不是优化 | 万级吞吐下，LLM 配额与成本是硬约束 |
| J5 | **一致性按域购买**：不为不需要的强一致付全局代价 | 全局强一致会杀死吞吐；完全不管会杀死正确性 |

### 2.2 本文新增的三条不变量

在 [12 §1.1](12-记忆模型-候选稿.md)（I1–I6）与 [24 §1.1](24-记忆模型-v0.3.md)（I1–I8）、[26 §7](26-记忆中心并发Harness-v0.md)（C1–C8）之上，本文补：

| # | 不变量 | 怎么测 |
|---|---|---|
| **M1** | **类型/绑定变更必须版本化、可回滚、可灰度**；运行时派生不得绕过注册表 | 注册表审计日志；构造"绕过注册直接 spawn"应被拒绝 |
| **M2** | **自主行动四要素齐全才允许执行**：`trigger + goal + mandate + budget`；缺一即拒绝（不是排队） | 构造缺 goal/mandate 的自主任务，应 100% 被拒 |
| **M3** | **协作会话有界**：轮数、消息数、token、时长、扇出深度任一超限即终止并留下中间结论 | 构造"两个 Agent 无限互问"，应在阈值处停止 |

### 2.3 本文不做什么（防止范围膨胀）

- **不做**自我进化 L4（自改内核代码/架构）；只做受控的**类型派生**与**模板派生**，边界见 §4.4；
- **不做**分布式实现细节（多机一致性、跨机房、多租户计费）；只给迁移阈值（§7.7）；
- **不做** UI/交互设计；沿用 [13](13-交互协议-候选方案.md)/[14](14-总体设计-v1.md) 的"用户只跟秘书说话"；
- **不做**模型训练/微调；模型是可替换算力〔沿用〕；
- **不重定义**记忆 schema、单实例循环、Planner 细节；分别引用 12/24、19、23。

## 4. 核心一：数据绑定（数据 → Agent 类型）

> **一句话**：Agent 类型不是"某个存储的 owner"，而是"**对某组数据的一个行为契约**"——它声明"我看哪些数据、看到什么投影、什么变化会唤醒我、我能写哪里"。多个类型可以看同一份数据；一个类型可以跨多个存储。

### 4.1 三层数据模型（先分清"存储 / 实体类型 / 数据实例"）

| 层 | 是什么 | 例子 | 谁定义 |
|---|---|---|---|
| **物理存储 Store** | 真实存放数据的地方 | PostgreSQL 表、SQLite 表、对象存储桶、文件目录、Kafka topic、向量索引、外部 API | 工程/运维 |
| **逻辑实体类型 EntityType** | 带 schema 的"物类型"；是绑定的**主锚点** | `Order`、`Ticket`、`DesignDoc`、`Component`、`Customer` | 领域建模（schema registry） |
| **数据实例 Entity** | 一条具体数据 | 订单 #123、工单 #456、某个设计稿 | 运行时写入 |

**为什么要分三层**：你说的"10 个存储，一个物类型对应其中某些类型的部分数据"——只有把"物理存储"和"逻辑实体类型"分开，绑定才能表达"跨 3 个存储、只取 `Order` 的 5 个字段、外加 `Ticket` 的标签"这种组合；否则绑定就被物理表结构锁死。

**字段级建模的最小要求**（不要求一开始就完美）：

```yaml
entity_type: Order
version: 7
keys: [order_id]
fields:
  order_id:   {type: string, pii: false}
  status:     {type: enum, values: [created, paid, shipped, refunded, closed]}
  amount:     {type: decimal, pii: false}
  customer:   {type: ref, target: Customer}
  timeline:   {type: event_stream, source: store:order_events}
tags: [payments, high_value]
relations:
  - {type: belongs_to, target: Customer}
  - {type: has_many, target: Refund}
```

> 实体类型是**契约**，不是物理表；一个 EntityType 可以投影自多个 Store（如 `Order` 来自 PG 的 `orders` + 对象存储的合同 PDF + 事件流的 `order_events`）。这是"任意组合"的落点。

### 4.2 AgentType：行为 DNA（第一等对象）

```yaml
agent_type: refund-anomaly-analyst
version: 3
status: active            # draft | canary | active | deprecated
role: "退款异常分析专家"
persona: "谨慎、先证据后结论、不臆测金额"
capabilities:             # 能力声明（不是代码）
  tools: [sql_query, read_file, http_get, memory_search]
  models: {default: reasoning-model, fallback: cheap-model}
memory:
  read_set: [domain:payments, task:*, entity:Order, entity:Refund]
  write_domain: domain:payments      # 只能写自己的记忆域（24 I6）
  projection: "只读金额/状态/时间线；客户 PII 脱敏"
triggers:                 # 什么信号会唤醒我（与 Binding 配合）
  - signal: order.refunded
  - signal: anomaly.detected
  - schedule: "0 9 * * *"
bindings:                 # 数据绑定（下一节展开）
  - ...
collaboration:            # 我能扮演的协作角色
  roles: [analyst, reviewer]
  patterns: [delegation, review]
autonomy: L2              # 自主等级（§6）
budget:
  per_task: {tokens: 200k, wall: 30m, cost_usd: 2}
  per_day:  {tokens: 5m, cost_usd: 50}
policy:
  approval: "写外部系统需人审；只读分析自动"
evaluation:
  suite: evals/refund-anomaly@1   # 类型上线前必须过评测
```

**要点**：

- **类型是声明式的**：能力、工具、模型、记忆视图、触发、预算、审批策略都在类型里；实例只是"按类型 + 数据 + 任务"装配出来的执行体。
- **类型本身也是可检索对象**：建议在注册表为真相、在记忆库留一条 `procedural` 条目做引用与审计（**不双写语义**，只存引用，避免两套真相）。
- **类型有版本**：`refund-anomaly-analyst@3`；实例永远绑定一个确定版本，升级走新版本 + 灰度。

### 4.3 Binding：本文最关键的一张表

> **Binding 不是外键，是五元组**。它回答："这个类型，对哪些数据，看到什么，什么时候被唤醒，能写哪里。"

```
Binding = (
  agent_type_ref,     # 哪个 Agent 类型（含版本范围）
  data_selector,      # 选中哪些实体/字段/标签/关系/流（支持并/交/差、部分覆盖）
  projection,         # 看到什么（字段裁剪、脱敏、聚合、采样、时间窗）
  trigger_policy,     # 什么变化唤醒（创建/更新/删除/阈值/定时/异常/关系变化）
  write_scope         # 允许提交候选的范围（实体/字段/记忆域），默认只读
)
```

#### 4.3.1 选择器（DataSelector）：支持"任意组合 + 部分覆盖"

选择器是**对逻辑实体类型的谓词**，不是对物理表的引用：

```yaml
data_selector:
  any_of:
    - entity: Order
      where: "status in ['paid','refunded'] and amount > 1000"
      fields: [order_id, status, amount, customer, timeline]
    - entity: Ticket
      where: "tags contains 'refund' and created_at > now()-30d"
      fields: [ticket_id, title, tags, status]
    - store: store:refund_events        # 也可以直接绑流
      where: "event_type in ['refund.requested','refund.failed']"
  exclude:
    - entity: Order
      where: "test_account = true"       # 排除测试数据
  coverage: partial                      # 明确允许"只覆盖一部分"
```

**语义规则**：

1. **N:M 是常态**：一个类型可 `any_of` 多个实体类型/存储；一个实体类型可被多个类型覆盖。**不要求一对一**。
2. **部分覆盖是一等语义**：未覆盖的数据不是"错误"，而是"未知区"——它会产生 `coverage.gap` 信号，驱动 §4.4 的类型派生或人工建模（这正是"自主发现该建什么类型"的来源）。
3. **重叠允许，但要定序**：多个类型同时命中同一数据时，用 `specificity（选择器越具体越优先）→ priority → lease` 决定谁处理；不静默双写。
4. **选择器必须可编译**：注册时静态校验实体/字段/关系是否存在、权限是否允许；运行时编译成**倒排索引**（`entity_type/field/tag/event_type → binding[]`），保证 1 万 msg/s 下匹配是 O(命中候选数)，不是全表扫描。

#### 4.3.2 投影（Projection）：看到什么，比"能不能看"更重要

| 投影能力 | 作用 | 例子 |
|---|---|---|
| 字段裁剪 | 只给需要的字段 | 分析 Agent 不看客户手机号 |
| 脱敏 | PII/敏感字段替换 | `customer.phone → ***` |
| 聚合 | 行级 → 指标 | 只给"近 24h 退款失败率" |
| 采样 | 高频流降采样 | 1% 采样 + 异常全量 |
| 时间窗 | 只给最近 N 天 | 最近 30 天订单 |
| 视图拼接 | 跨存储组合 | 订单 + 合同 PDF 摘要 + 事件流 |

> 投影是**读侧的最小权限**：默认只读、默认最小字段、默认脱敏。**写权限永远单独声明**（`write_scope`），不因为"能读"就"能写"。

#### 4.3.3 触发（TriggerPolicy）：绑定不只是"归属"，还是"唤醒条件"

| 触发类型 | 语义 | 例子 |
|---|---|---|
| `on_create` / `on_update` / `on_delete` | 数据变化 | 新订单、退款状态变化 |
| `on_threshold` | 指标越界 | 退款失败率 > 5% 持续 10 分钟 |
| `on_relation` | 关系变化 | 订单关联到高风险客户 |
| `on_schedule` | 定时/周期 | 每天 9 点复盘 |
| `on_anomaly` | 异常检测输出 | 金额分布突变 |
| `on_goal` | 目标状态变化 | 目标 G 连续 3 天无进展 |
| `manual` | 人或 Agent 显式派发 | 秘书派工 |

**触发不是"每条变化都起一个实例"**：它先进入 S2 的注意力/准入（去重、合并、预算、优先级），再由调度决定"直通动作 / 建工作项 / 合并进已有协作会话"。这是 §7 分级处理的入口。

#### 4.3.4 写域（WriteScope）：绑定必须能回答"它能改什么"

| 写域 | 说明 | 强制 |
|---|---|---|
| `memory` | 只能提交候选记忆到指定记忆域 | 默认；跨域只读（24 I6） |
| `entity` | 可对指定实体/字段提交变更候选 | 需显式声明 + 审批 |
| `artifact` | 可写文件/产物（工作区/worktree 内） | 需写域租约（26 §5.4） |
| `external` | 可调外部副作用（发消息/付款/改线上） | **最高风险**：审批 + 幂等 + 审计 |
| `none` | 纯只读分析 | 最安全，默认 |

### 4.4 动态派生（Type Forge）：类型从哪来

> 你说的"Agent 可以动态创建新的 Agent 类型"——本文把它做成一个**受控流水线**，而不是让任意实例随手 `new AgentType()`。

#### 4.4.1 什么时候派生

| 触发 | 例子 |
|---|---|
| **覆盖缺口** | 连续出现 `coverage.gap`：某类数据没人覆盖 |
| **反复出现的任务模式** | 同类任务被人工/秘书拆了 10 次，模式稳定 |
| **协作模式沉淀** | 某种评审/辩论组合反复成功，值得模板化 |
| **人工指令** | 用户/管理员明确要求"建一个 XX 专家" |
| **性能/成本异常** | 某类型任务量过大，需要派生专职子类型分流 |

#### 4.4.2 派生流水线（六步，每步可回滚）

```
观察（数据/任务/失败样本）
  → 生成类型草案（Type Forge Agent：role/persona/tools/memory view/bindings/budget/eval）
  → 静态校验（schema 存在？权限允许？预算合理？与现有类型重复？）
  → 影子试跑（shadow：只读、不产生外部副作用，跑历史样本）
  → 灰度（canary：小流量、可回滚、与旧路径对比指标）
  → 激活（active：注册版本、绑定生效、写入审计）
  → 复盘（eval + 成本 + 打扰率；不达标回滚/废弃）
```

#### 4.4.3 派生边界（防止"类型爆炸"与"自我进化失控"）

| 风险 | 机制 |
|---|---|
| 类型爆炸（一天生成 1000 个类型） | 类型总数上限 + 去重（相似度）+ 派生深度上限（派生类型不能再无限派生） |
| 权限提升 | 新类型的能力/写域**不能超过派生者的授权**（capability 不放大） |
| 评测缺失 | 无 eval suite 的类型只能 `draft`，不能 `active` |
| 数据污染 | 派生过程只读；类型注册不写业务记忆；草案落独立审计表 |
| 自我进化越界 | **本期只允许"类型级派生"（L1/L2）；内核代码/架构自改（L3）不做**〔对齐 00 D-11 的分级〕 |
| 回滚困难 | 类型/绑定版本化；回滚 = 切回旧版本 + 重绑；实例永远绑确定版本 |

**与"自我进化"的关系**：类型派生是"进化"的最小可行形态，但它进化的对象是**行为配置**，不是**内核代码**。真正的自我进化（改内核、改架构）需要独立的沙箱、评审门、回滚机制，本文明确留到后面〔用户已定：先不说〕。

### 4.5 一个具体例子（把"10 个存储 / 任意组合"讲透）

**场景**：设计域（本工作群就是设计 Agent）。

```
物理存储（10 个）：
  S1 需求库(PG)  S2 设计稿(Figma API)  S3 组件库(JSON)  S4 评审记录(PG)
  S5 用户反馈(流) S6 竞品截图(对象存储) S7 设计规范(Wiki)  S8 埋点(ClickHouse)
  S9 工单(Jira)  S10 聊天记录(IM)

逻辑实体类型：
  Requirement, DesignDoc, Component, Review, Feedback, Metric, Ticket, Message

Agent 类型（只覆盖部分）：
  design-lead       ← Requirement(全部) + DesignDoc(全部) + Review(全部)
  ux-researcher     ← Feedback(抽样 10%) + Metric(聚合) + Message(标签=体验)
  component-curator ← Component(全部) + DesignDoc(引用到组件的片段)
  accessibility-reviewer ← DesignDoc(只读视觉/交互字段) + Review(标签=a11y)

绑定示例（component-curator）：
  selector: entity:Component (all) ∪ entity:DesignDoc where "references any Component"
  projection: 组件 API/变体/使用位置；不含用户 PII
  triggers: component.created/updated, design_doc.published
  write_scope: memory:domain/design + entity:Component(候选)
```

**结论**：10 个存储、任意实体类型、部分覆盖、重叠覆盖、跨存储组合——全部由绑定表达；**加一个新专家 = 加一个类型 + 几条绑定**，不改内核。这就是"动态派生 + 数据绑定"的价值。

### 4.6 反模式（这一段用于 review 时对照）

| 反模式 | 症状 | 正确做法 |
|---|---|---|
| 一个类型绑死一个存储 | 加存储就要改代码 | 绑逻辑实体类型，物理存储可替换 |
| 一个类型看全部数据 | 上下文爆炸、越权、成本高 | 最小投影 + 按需检索（22） |
| 一条数据一个类型 | 类型爆炸、维护灾难 | 用选择器覆盖一批；只对"行为不同"的数据分类型 |
| 隐式绑定 | 代码里 `if entity.type == ...` | 绑定必须声明在注册表，可审计 |
| 绑定不写 `write_scope` | 实例越界改数据 | 默认只读；写必须显式 + 审批 |
| 派生不评测 | 新类型上线即事故 | draft → shadow → canary → active；无 eval 不激活 |
