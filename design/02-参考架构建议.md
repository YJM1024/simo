# 参考架构建议（建议稿，不是定稿）

> 这是**我的建议**，供你推翻/修改/部分采纳。每块都标了对应的决策号（D-xx）和骨架落点文件，方便你"只改你想改的地方"。

## 0. 一句话

**一个事件进、一个 Ticket 出、一份证据交付**的常驻调度系统；人只出现在"决定"与"验收"两个时刻。

## 1. 分层图

```
┌─────────────────────────────── 人机界面（横切）───────────────────────────────┐
│  决策队列（只列 person/*）  ·  验收面板  ·  通知（按信道定制）  ·  打扰预算   │
└───────────────────────────────────▲─────────────────────────────────────────┘
                                    │ 结构化提问 / 审批 / stop
┌───────────────────────────────────┴─────────────────────────────────────────┐
│ 决策层（Router）  研判 + 分派 + 全局记忆 ｜ 不执行、不直接回复具体工作         │
│   Gate(Fast 程序) → Assessment(Slow 模型) → Decision(accept/stop/ignore/…)  │
└──────────────▲───────────────────────────────┬──────────────────────────────┘
               │ Trigger / 报告                 │ Ticket + Mandate
┌──────────────┴──────────────┐   ┌────────────▼──────────────────────────────┐
│ 事件层                      │   │ 执行层（Worker）                           │
│  Source 适配器              │   │  隔离上下文 · 完整工具 · 强模型             │
│  → Trigger（不可变，幂等键）│   │  一 Ticket 一目录 · 可丢弃                  │
│  → Thread（流）· 订阅/扇出  │   └────────────┬──────────────────────────────┘
└──────────────┬──────────────┘                │ Report（六态）+ evidence
               │                               ▼
┌──────────────┴───────────────────────────────────────────────────────────────┐
│ 状态层（唯一写者）                                                            │
│  Store（append-only，事件溯源）· Effects 队列（先落库后执行）· 恢复注记        │
│  验收门：证据契约 → 缺证据退回 working                                        │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 2. 一次完整事件的生命周期

```
Source.read()
  → Trigger（不可变，幂等键 = source 侧 id）
  → Gate：确定性判定 → notAdmitted / explicit / inferred
  → Thread 归属
  → 已订阅？ 是 → 程序直通，投递给订阅它的 Ticket（不调模型）
             否 → Assessment（模型，带 Inline&Spill 上下文）→ Decision
  → Decision=accept 且 acceptMode≠off
      → 新 Ticket + Mandate（记录 Policy 版本、范围、强度）
      → Scheduler 分配 slot → Worker 执行（隔离目录）
      → Report + evidence
      → 验收门检查证据契约
          缺项 → 退回 working（附缺失清单）
          齐备 → person/review（进人工决策队列）
                → 人确认 → ended
                → 人拒绝 → 退回 / 新 Ticket
```

## 3. 核心对象与关系

```
Source 1─n Trigger n─n Thread 1─n Ticket 1─n Assignment
                  │              │
                  └─n Decision   └─n Report / Evidence / Input
                                  └─1 Mandate（不可变，可撤回）
Policy 1─n Mandate（版本化）
```

两条不变量（违反任何一条，整套设计作废）：

1. **授权 ≠ 上下文**：订阅 Thread 只流上下文，不流权限；权限只由 accept 创建、人 stop 撤回。
2. **先落库再执行**：任何外部副作用（发消息、开 PR、派工）必须先作为 effect 落库，commit 后才执行。

## 5. 运行面

- **计算**：Router 与 Worker 都是可丢弃的执行体；Worker 一 Ticket 一目录（`git worktree` 或临时副本），投机执行可整目录丢弃。
- **状态**：单写者 Store；目录锁防第二进程；迁移只升版，新版数据库拒绝旧版启动。
- **环境**：`prepare` 命令首次派工前执行一次（10 分钟超时），典型 `git worktree add`；重启后新 Assignment 带**恢复注记**："先核对目录、git 历史、远端状态，再重复任何外部动作"。

## 6. 人的界面（这是最容易被低估的一层）

- **单出口**：只有 Router 对人说话；Worker 的推理与工具调用不外泄。
- **决策队列**：首屏只列 `person/*`（delivery / answer / review / blocked / failed），健康状态不占空间。
- **结构化提问**：一次只问一个具体问题，字段化，禁止从自由文本推断"在等人"。
- **按信道定制**：IM ≤100 词、只问直接问题；PR/邮件/文档走结构化高密度。
- **静默默认 + 双条件交付门**：主动工作必须满足"确认问题"且"找到简单修复"才开口。

## 7. 我建议的进化路径（与决策 D-11 对齐）

| 阶段 | 干什么 | 判定做完了 |
|---|---|---|
| S0 | 内核跑通 demo（事件→票→验收门→人确认） | `node demo.mjs` 五条剧情全过 |
| S1 | 接真 LLM（Router 轻模型 / Worker 强模型） | 同一个 bug 场景真人可用 |
| S2 | 接一个真实事件源（IM / GitHub / 本地文件监听） | 无人 @ 也能发现一次真实问题并交付 |
| S3 | 上指标 + 影子模式跑一周 | 拿到 would-accept 记录与打扰数据 |
| S4 | L1 进化：提示词/阈值/规则自动调优（留 diff + 回滚） | 一轮调优有指标增益 |
| S5 | 接 DSH 作为第二宿主 | 同一内核在 GUI 里可切换使用 |
| S6 | L2 进化：场景包草案自动生成（observe 审批） | 新场景由系统提出、人批准 |

## 8. 我不建议现在做的

- **多实例 / A2A**（D-13）：官方未解，先别替它趟坑。
- **全自动改内核代码**（D-11 L3）：风险 >> 收益，等你有了评测集再说。
- **一上来就上向量库**（D-06）：引用图 + ID 足够，向量是补充不是主干。
- **先做订阅直通和异步工具**：它们是优化不是地基（原文 §9.9 的反直觉结论）。

## 9. 你的设计可以在哪些地方推翻我

我把"最可能被你有不同想法"的点列出来，方便你直接说"这条我不同意"：

1. **层数**：你可能想要更少/更多层，或把"验收"并进决策层。
2. **Router 形态**：你可能想让 Router 也参与执行（牺牲吞吐换灵活）。
3. **授权粒度**：你可能想按任务类型而非来源授权。
4. **上下文**：你可能偏好"记忆优先"（向量+摘要）而非"引用图优先"。
5. **验收定义**：你可能认为验收该是"人主观判断"而不是证据契约。
6. **进化**：你可能真的想做自改代码（L3），那我们得重新设计沙箱与评审门。
