# 基线：DeepSeek Super-agent 到底设计了什么

> 提炼版。完整证据链（含官方原型仓库 docs/000–007 的代码级细节、实验数据、12 条"被明确拒绝的概念"）见 [`../research/super-agent-report.md`](../research/super-agent-report.md)。
> 证据分级：〔A〕官方文章明确 · 〔B〕官方原型代码/文档 · 〔C〕媒体转述 · 〔D〕调研者推断。

## 一句话

常驻在线、**以环境事件（Trigger）而非人类提示词为输入**、用**双层调度**把"跨渠道连续性"与"多任务并发"解耦的系统形态；会话管理收归系统，人上移到**决策与验收层**。〔A〕

设计哲学（原型第一原则）：**尽可能少占用人注意力，尽可能多给出价值。**〔B〕
这条不是口号，而是可判决的架构裁判准则——任何消息/通知/提问/面板元素，成本 > 价值就删。

## 五个模块〔A〕

1. **双层架构**：Router（全局路由/记忆/分派，不干活，轻模型）+ Worker（隔离执行，完整工具，强模型）
2. **事件驱动**：Source → Trigger（不可变）→ Thread（事件流）→ 两级过滤 → 分派/订阅直通
3. **面向人的交互**：单出口（只有 Router 对人说话）、按信道定制（IM ≤100 词）、静默默认
4. **计算 / 状态 / 环境分离**：云端算+存，执行环境留在原地（BYOM），单机降级=一 Ticket 一目录 + prepare 命令
5. **Watchdog**：主系统之外的独立会话，定时驱动，既查基础设施也**判断工作是否有实质进展**

## 三个最硬的结构性设计

**① 双层 ≠ Agent Team。** 常见多 Agent 编排解决"一个任务内怎么拆"，Super-agent 解决"任务流之间怎么排队、归属、授权、恢复"。Router 的自我阉割是关键：不执行、可不配 Bash、用轻模型、不介入单任务内部拆解。〔A〕
判据：**主会话有没有下场干活**。有提示词把团队主会话约束成"只分派不执行"，那它已是双层。

**② 上下文当 Cache 管，而不是当记忆管。** Inline & Spill（近期/高相关内联，低频/超预算留引用）+ 对象唯一 ID 内联下一跳 ID 构成**引用图**，模型逐跳展开（链式召回），而不是向量检索。〔A〕
原话：**"浪费上下文窗口，就是浪费模型的智能。"**

**③ 授权与上下文分离。** Subscription 让上下文自由流动（订阅 Thread 即收），Mandate 让授权流动（只有 accept 能创建、人 stop 能撤回、恢复前必须对当前 Policy 重校验）。〔B〕
没有这条，主动型 Agent = 一条群消息就能指挥它改代码。

## 事件路由：三个 Fast / Slow Path〔A〕

| 环节 | Fast（程序） | Slow（模型） | 为什么 |
|---|---|---|---|
| 过滤 | 来源/群组/白名单/@ 的确定性判定 | 语义研判"是否需要行动" | 高噪音低触发率；**绝不能用模型当权限边界** |
| 路由 | 已归属事件由程序直通订阅它的 Worker | Router 只研判尚未归属的新事件 | 省 Router 调用（实测 Router 决定数↓30%、读缓存 token↓37%） |
| 上下文 | 对象 ID + 摘要，按局部性逐步内联 | 需要时按 ID 展开 | 窗口是 cache，不是仓库 |

配套：**投机执行**——不确定会被采用时后台先干，有价值就交付、没价值就丢弃；对应"静默复现并修复"策略（双条件交付门：确认问题 + 找到简单修复才开口）。〔A〕

## 人的角色怎么被机制保证〔A〕〔B〕

- Ticket 阶段机里 `person/*` 前缀 = **没有人工输入就无法继续**，把"卡在等人"变成可查询、可排序的状态；
- 等待必须走**结构化字段**，领域模型明确**拒绝从 report 自由文本推断"在等人"**；
- `accept mode` 三档：`off` / **`observe`（默认，影子运行：只记录 would-accept，什么都不接受）** / `auto`；
- 人 stop 是**权限级否决**（撤回 Mandate，Ticket 不再收任何消息）；
- 默认不自动合并；IM 单次回复硬限 100 词；面板首屏只列待人工决定的事项。

## 最小骨架顺序（如果自己造）〔D〕

0. 写下两条不变量：① 授权 ≠ 上下文；② 一切外部副作用**先落库再执行**
1. 单写者 Store + 目录锁
2. Source → Trigger 幂等入库 + 读取游标
3. Thread + 两级过滤 → Decision
4. Ticket + Mandate + observe
5. Executor + 一 Ticket 一目录 + prepare
6. Effects 持久队列 + Outbox
7. Subscription 直通
8. slot + 人优先 +1 + 异步工具
9. Inline & Spill + 链式召回
10. Watchdog + 恢复注记
11. 存算分离 / BYOM

反直觉但重要：**7、8 是优化不是地基**。很多团队先做直通和异步工具（demo 效果明显），结果状态管理一片混乱。

## 两个原文缺口（我们的机会）〔D〕

- **验收门没被做成一等原语**：原文"人做验收"落到实现只是 `ready` Report + 人肉看 PR + 点合并，没有验收契约。→ 建议：证据契约（缺证据不许进 review）。
- **打扰成本没有量化**：只有 observe 和 100 词限制，没有指标。→ 建议：消息数、人均日打扰、返工率、stop 率、静默弃单率。

## 三个必须记住的风险〔D〕

- Router 单点 vs 分片的矛盾**官方未解**（切越细连续性越低）——别把"跨月连续记忆"写进承诺；
- 性能数字（p50 12.4min）**不可外推**：合成负载 + 编码用"只耗时工具"替身，只评调度不评执行；
- 安全边界：原型 worker 以 operator 的 OS 用户无审批执行命令，`blocked commands` 只是默认值**不是安全边界**。
