# 派单模板

派发单元叫**任务**，粒度是一个功能分类，对应产品功能树里的一个 L2 组。一个分类按角色派四张单：设计、前端、后端、测试；四张单共享同一份功能点清单与验收标准，前后端拿到的是同一批 AC。子智能体开工时读整份 spec 与长测试日志会消耗大量 token，读到的多数内容与本任务无关，所以模板要把「读哪一段、交什么、怎么验」写死。spec 用 `scripts/spec-slice.mjs` 按节或按 PRD 取，日志用 `scripts/test-summary.mjs` 压成 40 行以内的摘要。node 不在 PATH 时用 `E:\dsh_home\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe`。行号以当前文件为准，文件改了要重新核对。

## 复制即用的模板

```
角色：<设计 | 前端 | 后端 | 测试>
功能分类：<分类名，例：多标签与同步>
包含功能点：<PRD-ID 列表 + AC-ID 列表，这是本任务的完整范围，做完才算交付>
目标：<一句话，交付物 + 用途>
scope：只写 <文件路径或目录>；越界即返工
只读范围：
  node scripts/spec-slice.mjs <spec 路径> --prd <PRD-ID>
  node scripts/spec-slice.mjs <spec 路径> --section <编号>
  node scripts/test-summary.mjs --kind <go|vitest> --log <日志路径>
依赖与顺序：
  设计先出契约与判据 → 前端与后端并行 → 各自自测 → 测试独立验收 → 更新 spec 与状态
  上游产物：<设计契约路径 / 接口形状>
验收标准（覆盖上面每一个 AC，逐条写可观察结果）：
  <命令> 退出码 0，且 <可观察结果>
自测要求：提交前必须自己跑通本分类的定向用例；不通过不交
证据形式：<命令输出 / diff / 摘要 / 截图路径>
推理档位：<max | high | low | off>，缺省 high
禁止项：不 commit、不删移文件、不改 scope 外文件、不新增依赖、实现者不自签
交付行数上限：报告 <=12 行；代码改动 <=<N> 行
```

分类级派单与单点派单的差别在「包含功能点」这一行：它必须是完整的 PRD 与 AC 清单，而不是「修一下那个 bug」。只有清单里的每一条都有可观察结果，任务才算交付。`scope` 写可写文件的精确路径，只读文件另列在「只读范围」。验收标准写成可执行命令加可观察结果，不写「功能正常」这类判断。证据形式写清提交什么，命令输出贴原文，diff 给路径或贴关键段。禁止项至少保留不 commit、不删移、不越界三条。交付行数上限分别限制报告与代码。

## 反例与正例

| 反例 | 正例 |
|---|---|
| 你读一下前端 spec，按里面要求实现 | 读 `specs/frontend/P1-CONV/spec.md` 第 120–260 行；需要别的节用 `node scripts/spec-slice.mjs specs/frontend/P1-CONV/spec.md --section 7` |
| 看一下后端测试日志，把失败的修了 | 跑 `node scripts/test-summary.mjs --kind go --log backend/.tmp/full-after.log`，按摘要里的失败用例定位；摘要标了「另有 N 行」时再读原日志对应段 |
| 把时间轴那个 44 像素的问题修一下 | 分类「消息与渲染」，包含 AC-CONV-007-02、AC-CONV-004-01；改 `frontend/src/components/components.css:1069`；验收：细指针下 `.tl-bar::after` 实测 ≥44×44，点四角都在条上 |

反例的问题在于范围没有边界，子智能体会读完整份文件并按自己的理解取舍。正例给出文件与行号，或给出能直接执行的切片命令，读到的内容与任务一一对应。日志摘要默认最多 40 行，失败明细优先，被截断时摘要会注明剩余行数与原始日志路径。

## 常见组合

- 整个分类的前端实现：`--prd` 依次取该分类下每个 PRD，一次读全；AC 清单直接抄功能树与产品 spec。
- 只改某个交互细节：`--section 4.4` 取单节；需要上游产品口径时再跑 `--lines 94-108`。
- 先看目录再决定：`--list` 只输出标题与行号，据此挑节。
- 日志只关心失败：直接跑 `test-summary.mjs`，全通过时输出两三行汇总。
