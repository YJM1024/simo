## 依据 2026-11-22 请求级扫描的修正

本轮扫描覆盖 99 个会话文件、9,898 条请求，整线支出 ¥75.63。三个支出大头是工具结果回灌 ¥24.50（32.4%）、上下文命中重读 ¥19.27（25.5%）与 reasoning 输出 ¥17.13（22.7%），合计占 80.5%。下面的修正只改判断，不改前面表格里的条目编号。

被数据否定的第一条判断是子会话起手成本高。98 个子会话的首个请求合计只有 ¥0.81，占整线 1.07%；把起手放宽到前 3 个请求也只有 ¥2.69（3.56%），首请求未命中最大 7,832 token，超过 3 万的会话为 0 个。把 98 个子会话并成 20 个的反事实只省 ¥4.18，说明为了省钱合并子会话没有收益。

被数据否定的第二条判断是压缩是漏点。322 次压缩自身花费 ¥17.52（23.2%），但压缩把平均入参从 130,328 降到 88,770，取消压缩后命中桶的支出涨得更多，压缩整体是净收益。关闭自动压缩因此不列为改进项。

被数据强化的第一条判断是验收轮次。验收审计 18 个会话 ¥15.97、缺陷修复 16 个会话 ¥13.38，两类合计 ¥29.35（38.8%），最贵十个会话里验收占四席、修复占三席。把验收从 3–5 轮压到 1 轮可省 ¥19.57–23.48，但「修复随轮次线性缩放」是强假设，下限口径只有 ¥10.6–12.8；可行的落地方式是脚本跑加抽查，不逐条人工核。

被数据强化的第二条判断是工具往返。工具结果回灌 ¥24.50（32.4%）是最大的单项支出，其中 compress ¥10.45、read ¥6.26、pwsh ¥5.03；全线 read 2,878 次、结果 15.09M 字符，pwsh 4,598 次、结果 10.96M 字符。合并同类命令、先 `grep` 取行号再 `read` 区间、用现成脚本切片，能直接减少这部分回灌。

不要做的三条：

- 不为了省钱合并子会话，实测只省 ¥4.18。
- 不在每条 prompt 前加项目摘要，实测只省 ¥3.21。
- 不关闭自动压缩，取消后命中桶涨得更多。
