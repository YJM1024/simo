## 1. 工作规范（长期有效，允许更新）

### 1.1 两种 Spec（用户 2026-11-21 定案）

**长期 Spec（长期产品 spec）**：常驻、写进仓库，相当于这个项目的设计文档。所有功能从产品出发；产品侧提供**产品功能树**（域 → 场景分类 → 功能点）。**每个功能点**都要有对应的设计 Spec、前端 Spec、后端 Spec、测试 Spec。

**变更 Spec（Change Spec）**：只跟一次需求挂钩，需求做完后**归档**，也写进仓库，形成项目的开发迭代史。变更 Spec 说明"怎么改长期 Spec"，要写清整个流程：①怎么对应产品、怎么对齐产品方案；②怎么设计前端、前后端怎么写代码；③怎么做测试与验收。它可以内含**局部视角的长期 Spec 片段**，因此与长期 Spec 有交集是正常的。

**类比（用户原话）**：长期 Spec = Git 仓库里的一个文件；变更 Spec = 这个文件的 changelog / commit history。

### 1.1.1 SDD 五条（用户 2026-11-21 口述）
1. 采用 Spec 驱动（SDD）设计与开发；
2. 文档体系 = 产品 spec + 前端 spec + 后端 spec + 测试 spec（+ 设计 spec / 组件 spec）；
3. 所有功能从产品出发：产品功能树描述全部场景与功能点；每个功能点有对应设计/前端/后端/测试 spec；
4. 测试必须完整、详细、彻底：后端测试 + 前端测试（无头浏览器/浏览器内）都做；**测试通过才算开发完成**；
5. 每个需求/修复都是一个 SDD 过程，都要有 Change Spec（变更包），并落实成文件。

### 1.2 六类产物与门禁（`$DSH_HOME/rules/spec-workflow.md`）
- 六类：产品 spec / 前端 spec / 后端 spec / 组件 spec / 任务卡 / 测试 spec；缺一类写 `N/A：理由`。
- 门禁 G0–G6 为 Blocking：产品门禁 / 开发门禁 / 组件门禁 / 任务门禁 / 测试门禁 / 追溯门禁 / 证据门禁。
- 状态词：`draft → ready → in-progress → implemented → verified → accepted`；`done` 不得混用。
- 实现者不得自签；验收人独立。

### 1.3 智能体团队模式（核心原则，不得违反）
| 角色 | 职责 |
|---|---|
| 产品 | 问题、场景、行为、AC、非目标、产品域 spec |
| 设计 | 交互/视觉方案、tokens、组件方向、验收截图口径 |
| 前端 | 页面组件实现、状态、响应式、可访问性、前端测试 |
| 后端 | 接口契约、数据、权限、迁移、后端测试 |
| 测试 | 用例设计、自动化、证据归档、覆盖审计 |
| 验收 | 独立核验 AC/证据/回归并签字（不得参与实现） |

- Lead（我）只做：交互、规划、拆卡、派单、**关键点快速验收**、裁决、记录、汇报。
- Lead **不做**：写 spec 正文、写代码、写测试、修构建、装环境、git 操作。
- 前端、后端视工作量各可开 2–3 个 Agent 并行；同一文件同时只有一个 owner。

### 1.4 变更包粒度
- 一个 CHG 按**需求提出视角**聚合：一次需求可覆盖多个功能点、多个场景、多个分类。
- **不按单个功能点拆包**。`Implements:` 可列多个 PRD；跨域用主域编号 + `Domains:` 列全。
- ID 格式仍按 `docs/product/ID-SPEC.md`：`CHG-<主域>-<NNN>`。

### 1.5 Lead 响应 SLA（用户 2026-11-21 定调）
- **短回合优先**：每轮只推进一小步，思考 10–30 秒就回话，让用户能马上接着说下一条；不要攒一大堆再一次性回。
- 回复目标 ≤ 60 秒；任何可能超时的操作一律后台 job + 日志，不阻塞对话。
- 长任务跑着的时候，先给用户一个"已派出去、回来报"的短回复，不干等。
- 验收只做关键点抽查（核心断言/截图/输出），不做全量复核。

### 1.6 阶段出口的部署验证（用户 2026-11-21 定案，全局适用）
- **所有人（产品/设计/前端/后端/测试/验收）都要过 8787 真实部署验证**，不是只看测试报告。
- 验证内容 **= 功能缺陷 + 视觉返工**；视觉必须与设计稿对齐，这属于整体设计流程的一部分，不是可选项。
- 落地方式：每个阶段出口先重建 `simo.exe` 并起 `127.0.0.1:8787`，用真机（真浏览器）逐条走 AC，产出截图证据；不通过就返工到通过为止。

### 1.7 长期 Spec 的粒度与目录（用户 2026-11-21 定案）
- **粒度：按域（功能分类）一个文件，绝不按功能点拆文件。** 一个域（如 P1-CONV）一个文件，文件内按功能点 ID 分节（`#### PRD-CONV-001 · …`）；文件大一点没关系。功能点用 ID 区分，一个文件可含多个功能点。
- 目录（用户已确认"没有问题"）：
```text
docs/product/TREE.md                  产品功能树：域 → 场景分类 → 功能点(ID/一句话/状态/优先级)
specs/product/<域>/spec.md            产品 Spec（已有，71 PRD，按功能点分节）
specs/design/<域>/spec.md             设计 Spec（交互/视觉/tokens/组件方向）
specs/frontend/<域>/spec.md           前端 Spec（组件/状态/数据流/边界/错误态）
specs/backend/<域>/spec.md            后端 Spec（API/存储/并发/错误/迁移）
specs/test/<域>/test-plan.md          测试 Spec（TC↔AC/断言/证据/未覆盖；沿用现名）
specs/changes/CHG-<域>-<NNN>/         变更 Spec（七件套，归档后仍留在仓库）
```
- 现状：产品列有；测试列有骨架（10 个域）；**设计/前端/后端三列全缺**。
- 变更 Spec 必须显式列出「本次改了哪些长期 Spec 文件、改了哪一节、对应哪个功能点」，这就是 changelog 语义，也是 check-trace 的输入。
