## 4. 预估效果

时间模型是 `T = 开卡与读料 + 实现 + 轮次 × 单轮验收 + 构建次数 × 单次构建 + 等待`。本轮代入实测值：开卡与读料 2.0 小时（总账 20.2 减去其余各项：20.2 − 8.6 − 4.5 − 3.0 − 1.9 − 0.2 = 2.0），实现记 0（混在构建段里，没有单独计时，这是公式的已知缺口），5 轮 × 0.6 小时 = 3.0 小时，9 次 × 0.5 小时 = 4.5 小时，等待 8.6 小时，合计 18.1 小时；加上公式外的越权 1.9 小时与沟通 0.2 小时，正好回到 20.2 小时。

优化后按同一公式取值：开卡与读料 0.4–0.6 小时（已有实现时按 `DECISIONS.md:52` 的 30–40 分钟反推契约），实现 0.5–0.8 小时（估算），2 轮 × 0.25–0.3 小时，1 次 × 0.3–0.4 小时，等待 0–0.3 小时，下限 0.4 + 0.5 + 0.5 + 0.3 + 0 = 1.7，上限 0.6 + 0.8 + 0.6 + 0.4 + 0.3 = 2.7，合计 1.7–2.7 小时，中位约 2.2 小时。这个区间成立要同时满足：判据已脚本化、只验变化项、只构建一次、真机依赖在派单前探过。

用户期望的 0.5–1 小时，只在一种情形下成立：只补 1–2 条 AC、改动不跨前后端、不新增依赖、不需要真机证据、用 dev server 热更不重建。按公式代入是 0.3 + 0.3 + 1 × 0.2 + 0 + 0 = 0.8 小时。缺任何一条就回到 1.7–2.7 的区间，"在既有基础上补一个域"这个量级压不到 1 小时。

成本模型是 `C ≈ 请求数 × 平均输入 × 单价 × 命中率折扣`。实测 754 × 154.8K = 116.71M（154.8K = 116.71M ÷ 754），命中 98.2%，未命中 2.12M（新内容 664.9K + 压缩重付 1.03M + 上游 TTL 与重写 427.2K，三项相加 2122.1K，即 2.12M）。把单价与折扣合并成混合单价 0.514 元/百万 token（60 元 ÷ 116.71M），代入得 116.71 × 0.514 ≈ 60 元；这个单价是从总价反算的估算，不是官方价目表。

优化后取请求数 250–320、平均输入 90–110K，总量 22.5–35.2M，成本 11.6–18.1 元，取 12–18 元，是现在的 20%–30%，低于"三分之一以内"那条线（20 元）。请求数的估法按降幅折算：验收轮次从 10 降到 2、构建从 9 降到 1，请求数取本轮的 1/3 到 2/5（754 × 1/3 ≈ 251，754 × 0.42 ≈ 317），这个折算没有考虑并行派单带来的会话数增加，属于估算。

折叠本身也要花钱。按未命中全价 p、命中价 0.1p 反算，p ≈ 60 ÷ (2.12 + 114.59 × 0.1) ≈ 4.42 元/百万 token（估算），本轮 1.03M 的折叠重付折合约 4.5 元。折叠净省的 302.05M 按混合单价折约 155 元（估算），账单上的 60 元是折叠之后的价格。

这两个预估在下面几种情况下失效。判据没脚本化、轮次回到 4–5 轮，时间加 0.6–1.2 小时；CDP 这类外部依赖不可用又没有降级判据，等待一项直接回到 8 小时量级；改动跨 3 个以上能力域或要动数据库结构，实现项翻倍；用户中途改口径，每改一次加一轮 0.3 小时。成本侧，命中率跌到 95% 时混合单价按 (0.05 + 0.95 × 0.1) ÷ (0.018 + 0.982 × 0.1) ≈ 1.25 倍计，12–18 元涨到 15–23 元；平均输入没压下来仍是 155K，250 次就是 38.8M，约 20 元，刚好卡线；请求数没降仍是 754，即使每次 90K 也有 67.9M，约 35 元；模型或供应商调价则整张账单作废，只能重算。
