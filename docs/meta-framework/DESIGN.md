# 墨斗：通用元框架设计记录

状态：草稿
日期：2026-11-26

本文记录一轮讨论形成的结论，供后续设计与评审引用，不作为可执行规范。

本记录描述的通用元框架定名为墨斗。名字取自木工弹线工具，斗里装墨与线，一弹成线，对应它产出下级领域框架的职责。家族三级读作思墨（产品）、墨斗（元框架）、墨线（领域框架）。

## 一、背景与目标

元框架可以抽出，做法是把讨论中提出的两个方向合并成一套架构：方向一作内核，方向二作交付形态。背景是墨线在本项目开发思墨智能体系统的过程中形成，覆盖需求受理、契约、拆卡、实现、测试、验收、收口与复盘的全部环节。要回答的问题是，能否在墨线之上再抽出一层不绑定软件开发的框架，它能产出面向任意行业、学科与专业方向的 SDD 框架（SDD 指规格驱动开发），并且这种产出关系可以递归到下一层。

两个方向在讨论中先后提出。方向一是元框架直接适用于任何领域，任何需求都用它执行。方向二是元框架不直接执行具体需求，它经过多级具体化生成一套面向该需求的框架，再由那套框架执行。两者的差别在于具体化发生在什么时候、由谁承担，通用性本身不构成分界。

具体化的成本不会因为选方向一而消失。方向一把成本分散到每一次使用上，每个需求都要现场补齐判据、证据形式与角色，补得对不对没有统一检查。方向二把成本集中在一次领域绑定上，绑一次，该领域后续需求复用，绑定质量可以单独验收。同一个领域重复使用多次时，方向二的单位成本更低。

可验性是选择方向二的第二个理由。方向二的主张可以检验：给一个领域生成一套框架，拿一个真实需求跑完，按墨线自证标准的四道检查（判据可判定、任务类型全覆盖、门禁有样例、历史回放）验收。方向一的主张“适用于任何领域”没有对应的检查动作，按墨线自证标准里判据可判定的一条，这条主张无法成立。

墨线的版本记录可以看作单层框架退化的样本。v1.4 补契约表十一类与合规处置，v1.5 补发布与插件门禁，v1.6 补插件市场审核，新增规则大多落在具体领域上。这些内容继续写在总册里，总册会成为各领域补丁的合集；写进 domains/ 下的分册，就已经是具体化，缺的是一套生成规则。方向一在规模上会长成方向二，区别在于长出来的分层是手工的。

## 二、术语表

术语按下表统一，正文只用这些词。词汇表只收最终定稿的词，讨论中出现过的其他说法不再保留。同一件事不在别处另起叫法，改动时只改这一处。

| 词 | 定义 |
|---|---|
| 元框架 | 对下级而言的生成者与抽象；根节点是这个角色的顶层实例，也是唯一不含应用领域知识的框架 |
| 领域框架 | 对上级而言的具体化版本；也用作领域内框架的通称 |
| 上级领域框架 | 一个领域节点相对其下级的叫法 |
| 下级领域框架 | 一个领域节点相对其上级的叫法 |
| 领域 | 参与者角色、交付物类型、判据来源、约束条件组成的四元组；学科、行业、专业方向都是它的通俗叫法 |
| 流程 | 领域内把输入变成交付物的一组有序活动，每个活动有进入与退出条件；流程是类型，可跨领域复用 |
| 任务 | 流程的一次具体化，绑定具体需求、执行者与验收取值 |
| 交付物 | 流程的产出，能命名、能判合格、能留证 |
| 框架 | 单元、判据、证据、角色、门禁、状态机（单元从起草到关闭的状态与允许的转移）六件组成的规则集，使一类流程可重复执行、可判定；这里的角色指执行者角色 |
| 领域知识 | 对某领域内多个任务都成立的陈述 |
| 需求知识 | 只对某一次任务成立的陈述 |
| 上提 | 把重复出现的需求知识抽象为领域知识，挂到覆盖样本的最深领域节点 |
| 下放 | 把被误固化为领域知识的内容退回项目层或需求层 |
| 固化 | 把知识写成框架规则 |
| 运行时补料 | 执行任务时由执行者现场补充框架未覆盖的领域知识 |
| 留给判断 | 不固化也不补料，由执行者按专业判断处置，判断须留证 |

原框架、零框架、语言框架这三个词作废，都是语音输入的误识，不采用，正文其余位置不再出现。

## 三、世界模型

世界模型由六个名词组成：领域、流程、任务、交付物、框架、元框架。前五个是实体，元框架是框架在特定位置上的角色，不是第六种实体。它们之间的关系有六类，见下表。

| 关系 | 说明 |
|---|---|
| 领域之间 is-a | 上下级关系，允许多父 |
| 领域拥有流程 | 一对多，同一流程可以跨领域复用 |
| 流程被框架制度化 | 多对多，一个框架覆盖多条流程，一条流程可以由多套框架组合 |
| 流程具体化为任务 | 任务绑定具体需求、执行者与验收取值 |
| 任务产出交付物 | 交付物能命名、能判合格、能留证 |
| 框架之间继承与组合 | 继承走单调增强，组合走裁决规则 |

框架的坐标是领域节点与流程类型的交点。同一交点上出现多套框架，是同一流程的多个实现变体；同一流程类型被多个领域复用，一套框架就覆盖多个领域。框架的直接宿主是流程，领域通过流程传导约束；把框架直接挂在领域上，会回到一个领域一个大框架的粒度问题。

元框架作为角色，对下级是生成者与抽象，对上级是具体化版本。根节点是元框架角色的顶层实例，也是唯一不含应用领域知识的框架；中间节点对上是领域框架，对下是元框架，自身带着该领域的知识。角色由位置决定，同一个节点可以同时演两个角色。

## 四、知识模型

判断一条知识属于哪一类，一个动作就够：换一个任务，看这条陈述是否仍然成立。成立的是领域知识，不成立的是需求知识。同一句话在不同层会有不同身份：本项目用中文对整个项目成立，属于项目层的领域知识；这次需求必须兼容旧接口只对本次成立，属于需求知识。

注入按作用域对齐，每一层只固化作用域覆盖该层全部任务的知识。领域层固化对该领域所有任务成立的内容，子领域层固化更窄的内容，项目层固化只对本项目成立的约定，需求知识留给任务。上层已固化的知识对下层自动生效，下层只写增量。一条知识的作用域比它所在层窄，说明放错了层，要么下沉，要么留给判断。

框架对两类知识的作用不同。它把领域知识固化成规则，把需求知识收成表格：变更包模板规定这次需求必须声明目标、范围、验收取值与约束，具体取值由任务填写。框架保存的是需求知识的格式，内容留在任务里。缺了这张表，执行者不知道该问什么，验收也无法判断输入是否完整。

具体化可以按部分求值理解：把一部分输入提前固定，生成一个专用版本，剩下的输入运行时再给。注入领域知识相当于固定掉领域这一维，得到专用框架；专用框架再吃需求知识，产出任务与交付物。每一层都能执行，因为没固定的输入可以在运行时补上。判断余地在这个视角下有准确的位置，它是运行时还没固定的那部分输入；具体化让这部分输入单调收缩。

具体化的末端是任务，由知识种类决定，与具体程度无关。只要注入的是领域知识，逐层具体化就能继续，哪怕作用域窄到单个项目；注入需求知识之后，对象类型变成任务，不再派生框架。所以最后一级框架是项目框架，任务接在它之后。

需求知识积累到一定程度，公共部分上提成领域知识。上提的落点是覆盖全部样本的最深节点：某个现有节点的子树装得下这些样本，就挂在那里；所有现有节点都太宽，就新建一个下级节点。上提的触发条件有两个，次数与多样性都要满足，同一陈述在三个以上任务里重复出现，并且这些任务来自不同的子领域或不同项目。上提是一次版本事件，动作落盘时要重验已有任务的证据，因为新规则可能推翻旧结论。

反方向也要有一条下放路径。原本当成领域知识固化的内容，后来发现只对一个项目成立，或者本身写错了，要能退回项目层或需求层；只有上提没有下放的框架，会一层层积累错误的通则，越往上越难改。上提做得太早也会出错，样本不够多样时抽出来的是偶然共性，用三个同源任务归纳出的通则并不可靠。

## 五、框架的结构

继承契约规定子框架相对父框架能改什么，它的内容是单调增强：子框架只能收紧判据、增加证据要求，不能放宽或删除父框架的机制。代码里子类覆盖父类方法有编译器与测试保证，框架里没有这层保证；一旦允许放宽，父节点的证据不能复用，多态（同一个调用接口，不同实现）的结果也不可信。语义不一致时，得到的是改写，具体化不成立。

框架之间还有组合边，用来挂载跨领域的知识，合规、安全这类横向要求走这条边。组合要配裁决规则，两套知识冲突时谁优先、证据怎么合并，都要明文规定。没有裁决规则，组合边就不是可执行的边，多个来源的知识混在一起会得出不确定的结论。

领域图先按多根树做，每个根是一个顶层领域。多根树的好处是冲突少、继承链唯一、验收简单；代价是跨域知识不能靠继承表达，只能走组合边，组合的裁决规则要额外维护。多父继承留作扩展点，等组合边不够用时再升级成有向无环图，届时边的类型与节点的父列表要能扩展，不用改模型。菱形冲突（两条继承路径对同一事项给出不同规则）因此在起步阶段被规避，代价是升级时要做一次迁移。

## 六、执行模型

执行前先看框架的作用域与任务所在领域是否对齐，三种情况对应三种模式。作用域精确覆盖时直接执行，不需要补料。作用域是上级领域时，执行者当场补下级领域的知识，补完继续。作用域不覆盖时，应当换框架或组合框架，强行补料会把两套不相容的规则混在一起。

补料必须留痕：补了哪份规范、哪个版本、为什么判断它适用，这些写进任务的证据，否则验收时无法复算，同一处缺口也无法被发现。留痕的粒度按证据字段来，不必把整份规范贴进任务。补料的记录同时是上提的输入，没有记录就没有归纳的样本。

补料不能放宽框架的机制。框架要求留证，某领域惯例不留证，运行时按框架执行，补料只能在框架之内细化。越过这条边界，继承契约失效，上层框架的证据也不能再用。

同一处缺口被反复补，说明它应当固化：补过三次以上的知识，下移一层写进下级领域框架，之后的任务不再重查。框架越抽象，执行者的工作越偏向研究，需要找知识、验知识；框架越具体，这份工作越偏向判断，只需要在选项里选。

## 七、规则集

规则集有六条，每条一句定义。六条规则约束三件事：框架之间的改动、知识与框架之间的流动、具体化在哪里停下。停止与卫生两条另有判据，写在表后。

| 规则 | 定义 |
|---|---|
| 单调增强 | 子框架只能收紧判据、增加证据要求，语义必须与父框架一致 |
| 组合裁决 | 两套知识冲突时写明优先级与证据合并方式 |
| 上提 | 重复出现的需求知识抽象为领域知识，挂到覆盖样本的最深节点 |
| 下放 | 误固化的知识退回其适用层 |
| 停止 | 具体化到剩余运行时输入可由执行者现场给出为止 |
| 卫生 | 每层只固化作用域覆盖该层全部任务的知识 |

停止规则的判据是剩余的运行时输入小到执行者能现场给出，并且给出之后判断可留证；两条有一条不满足，就还要继续具体化。卫生规则的判据有两条：这条知识的适用样本全部落在该层子树内，并且该层是从根到样本所经路径上覆盖全部样本的最深节点。第一条不满足说明节点太窄，知识要上移；第二条不满足说明节点太宽，知识要下移。

## 八、边界

元框架不生产领域知识。它把已有流程写成可执行制度，发现不了还没被写下来的流程，也替代不了领域专家判断交付物是否合格。每个领域的四元组由领域专家提供，元框架负责组织与生成，不负责编写内容。

覆盖范围是已被描述、有交付物、判据写得出来的流程。隐性知识与纯审美判断不在覆盖内，它们的判据无法外化，只能由人当场判断。这条边界决定了元框架能加速制度化，不能取代任何一个行业的专业判断。

## 九、墨线作为样本

墨线现在的分层正好是知识分层的样本。总册固化跨领域的机制，domains/ 下四份规范固化产品与设计、前端、后端、测试与验收四个专业方向，AGENTS.md 固化本项目约束，变更包承接需求知识。四层各自只包含作用域内的知识，没有一层包含全部。

按这轮讨论的判断，domains/ 四份是运行时补料驱动具体化的产物。总册先立机制，具体方向的知识在执行中反复补，补到稳定就抽成域规范。这条路径对元框架的生成程序有直接参考价值：新领域先按上级框架跑，缺口稳定后再固化成下级框架。

## 十、未决项与下一步

下一步按四步走，顺序不变。第一步出一页元模型，写清世界模型与知识模型。第二步用它逐条回放墨线现有 284 条规则，解释不了的部分记成残差清单。第三步选一个外部领域做实例，证明残差不是软件特有。第四步做生成程序。

外部领域还没选，候选有三个：临床试验的方案偏离管理、建筑施工图审查、科研论文的同行评审。生成程序的形态也没定，框架文件包与可调用生成程序两者都要，先后顺序待排。六部件的取法已经定为正文版（单元、判据、证据、角色、门禁、状态机），与按输入归的六件只保留一套。

任务与墨线任务卡的粒度冲突待对齐。墨线里的任务是派单单元，覆盖一个功能分类下的多个需求点，比流程的一次执行大；这轮定义的任务是流程的一次具体化，接近一个需求点，两者同名不同粒度，落地前要把其中一个改名。术语一处定义、全篇沿用的规则在这里会被触发，不能两套并存。

本轮只落盘这份记录，不启动四步中的任何一步，不改墨线与既有流程。这份记录本身是草稿，不进入门禁，也不作为派单依据；等四步里的第一步做完，再决定是否把它升成规范。
