## 组织方式：金字塔

```
L0 产品目标（司墨：本地桌面 AI 秘书）
└─ L1 能力域（会话 / 交互 / 执行 / 记忆 / 团队 / 界面 / 质量）
   └─ L2 史诗（一个可独立验收的能力块）
      └─ L3 功能点（一条可测试的规则）
         └─ L4 任务（一个可分配、可验收、可回滚的工作单元）
```

- 叶子任务必须有：ID、owner、写作用域、验收标准、证据（命令/截图/测试）。
- 同一层节点不重复；跨域依赖写在任务的 `依赖` 字段。
- 需求变化先改文档，再改任务，再派发。

## 角色与写作用域

| 角色 | 负责 | 写作用域 |
|---|---|---|
| 产品 | 需求、契约、验收标准 | `docs/`、`DESIGN.md` |
| 前端 | 设计原型、组件、页面 | `frontend/` |
| 后端 | Go 服务、API、存储 | `backend/` |
| 验收 | 只读检查、截图、结论 | `docs/tasks/acceptance.md` 与 `frontend/review/` |
| Lead | 拆解、派发、跟踪、最终验收 | 只写任务/状态文档，不改业务代码 |

## 工作流

1. 需求进入 `product.md`，落到功能点（L3）；
2. Lead 拆成任务（L4），写清 owner/scope/验收；
3. 派给对应 Agent；任务状态改 `进行中`；
4. Agent 交付证据；验收 Agent 或 Lead 检查；
5. 通过 → `已完成`；不通过 → 打回并记录原因；
6. 每次状态变化同步 `STATUS.md`。

## 状态定义

- `待办`：已定义，未派发
- `进行中`：已派发，正在做
- `待验收`：已交付，等待检查
- `已完成`：验收通过，有证据
- `阻塞`：有明确外部条件，写清原因
- `取消`：不再做，写清原因
