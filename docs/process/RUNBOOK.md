# 变更执行手册（RUNBOOK）

> 状态：`superseded`（由 docs/framework/MOXIAN.md 第 5、10、11、13 章取代，历史内容供追溯），2026-11-24。适用范围：本工作区每一个变更包（`CHG-<主域>-<NNN>`）从立项到关闭的全过程。
> 用法：按七个阶段顺序走。每个阶段只做四件事，读入口条件、按编号步骤做、交产出物、过门禁，过了门禁才进下一阶段。
> 本文件不判断流程好坏，六维基线见全局 `AGENTS.md`；状态与异常出口的定义在 [`MOXIAN.md`](../framework/MOXIAN.md) 第 5 章与第 12 章。
> 步骤编号 `R-<阶段序号>.<步骤序号>`，引用时写全号。门禁未实现的脚本在每阶段标注"待补"，当前按人工核对并留证据。

## 1 主线与阶段

一条线走完一个变更包，依次是立项与范围、产品 spec、设计 spec、前端/后端 spec、实现、测试与验收、复盘与关闭。七个阶段与变更包七个状态的对应关系如下，状态定义见 [`MOXIAN.md`](../framework/MOXIAN.md) 表 5-3。

| 阶段 | 步骤号段 | 进入时状态 | 退出时状态 | 谁推进 |
|---|---|---|---|---|
| 1 立项与范围 | `R-1.1`–`R-1.5` | `草稿` | `进行中` | 产品，Lead 批范围 |
| 2 产品 spec | `R-2.1`–`R-2.6` | `进行中` | `进行中` | 产品 |
| 3 设计 spec | `R-3.1`–`R-3.6` | `进行中` | `进行中` | 前端、后端 |
| 4 前端/后端 spec | `R-4.1`–`R-4.6` | `进行中` | `进行中` | 前端、后端 |
| 5 实现 | `R-5.1`–`R-5.6` | `进行中` | `进行中` | 前端、后端 |
| 6 测试与验收 | `R-6.1`–`R-6.7` | `待验收` | `已验收` 或 `异常` | 实现者提交，验收、用户签字 |
| 7 复盘与关闭 | `R-7.1`–`R-7.6` | `已验收` 或 `已回滚` | `已关闭` | owner、验收核，Lead 关闭 |

任一阶段门禁红了，按 [`MOXIAN.md`](../framework/MOXIAN.md) 第 12 章登记异常，处理好回到被卡的那一步继续，不回到阶段 1 重来。

## 2 阶段 1 · 立项与范围

入口条件：

- 用户要求已记下，含时间、渠道与完整表述；
- 能一句话说出目标用户与场景；
- 能一句话说出本次不做什么。

步骤：

1. `R-1.1` 建 `specs/changes/<CHG-ID>/proposal.md`，首段抄用户原话，写接收时间与渠道。
2. `R-1.2` 写问题与场景各一句，写本次不做什么一句。
3. `R-1.3` 在 `docs/product/TREE.md` 查对应能力域与需求点；没有节点就补节点，补完再往下走。
4. `R-1.4` 按 [`ID-SPEC.md`](../product/ID-SPEC.md) 第 3 节分配变更号，在 proposal 写 `Implements` 与 `Domains`。
5. `R-1.5` 列待确认项与假设，未确认的标 `未确认`；范围冻结后把状态从 `草稿` 改为 `进行中`，写冻结时间与批准人。

产出物：

- `specs/changes/<CHG-ID>/proposal.md`，字段为问题、场景、范围、非目标、依赖、假设、待确认项、影响的能力域；
- `docs/product/TREE.md` 的节点补登记（有缺节点时）；
- 变更号登记，含 `Implements`、`Domains`、owner。

门禁：

- 自动：`node scripts/check-change-package.mjs` 检查目录与必填字段（**待补**，当前人工按字段清单核）；
- 签字：Lead 批范围冻结，签名与时间写在 proposal 末行。

## 3 阶段 2 · 产品 spec

入口条件：

- 范围已冻结，proposal 的六项字段齐全；
- 变更号已分配；
- 该域长期 spec 已读过，知道本次写增量还是建列。

步骤：

1. `R-2.1` 打开 `specs/product/<P*-*>/spec.md`，判断本次是改已有列还是建四列，结论写进 proposal。
2. `R-2.2` 按 `REQ-x.y` 分需求点，每点写触发、前置、动作、可见结果四段。
3. `R-2.3` 每条 AC 写编号与判据，判据取 `scripts/ac/<AC-ID>.mjs` 或 `人工:<动作>`；没有判据的标 `判据待补`，补完再往下走。
4. `R-2.4` 按 [`SPEC-STANDARD.md`](SPEC-STANDARD.md) 第 2.3 节填产品列。
5. `R-2.5` 写非目标与依赖，每条非目标能读出一条不该出现的行为。
6. `R-2.6` 自我检查后交 Lead 冻结 AC，冻结时间与签字写进 spec 首段。

产出物：

- `specs/changes/<CHG-ID>/spec.md`：目标、非目标、需求点清单、AC 清单、依赖与假设、待确认项；
- 长期 spec 的增量段或四列骨架；
- AC 清单表：编号、判据、断言落点、判定人、判定环境。

门禁：

- 自动：`node scripts/check-spec-language.mjs`（已实现 R1 至 R7，R7 为重复 AC 编号检查）；
- 签字：Lead 冻结 AC，冻结前 AC 不得进入实现。

## 4 阶段 3 · 设计 spec

入口条件：

- AC 已冻结，编号与判据固定；
- 组件清单、接口清单、数据改动范围各有一份初稿；
- 组件登记表与画廊已查过。

步骤：

1. `R-3.1` 列出可复用的组件与接口，写进 `design.md` 的复用清单。
2. `R-3.2` 写方案与至少两个候选，每个候选写代价，写被否理由。
3. `R-3.3` 按 `SPEC-STANDARD.md` 第 2.3 节填设计列：选择器、属性、数值、档位、容差、token、状态矩阵。
4. `R-3.4` 写接口草案：method 与 path、鉴权、请求与响应字段、错误码、并发与幂等。
5. `R-3.5` 写数据改动与回滚：dry-run、行数与 hash 对账、回滚脚本；本次无数据改动写 `N/A：<理由>`。
6. `R-3.6` 提设计评审，参加人前端、后端、验收；开放问题列清单，每条指派裁决人与期限。

产出物：

- `specs/changes/<CHG-ID>/design.md`：方案、复用清单、取舍记录、接口草案、数据与回滚、风险、开放问题；
- `specs/COMP-<kebab>/spec.md`（新增或改动组件）：变体、状态、props、DOM 锚点、截图基线；
- 评审意见写在 `design.md` 末节。

门禁：

- 自动：`check:gallery` 查组件登记与截图是否存在（**待补**）；
- 签字：验收在 `design.md` 末节签评审通过。

## 5 阶段 4 · 前端/后端 spec

入口条件：

- 设计评审已通过；
- 接口草案与组件清单已冻结；
- 测试计划已能按 AC 编号列出用例骨架。

步骤：

1. `R-4.1` 按 `SPEC-STANDARD.md` 第 2.3 节填前端列：组件与 props、状态转移、事件到状态、DOM 锚点、错误态、无障碍。
2. `R-4.2` 填后端列：method 与 path、鉴权、请求与响应字段、错误码、并发与幂等、存储不变量。
3. `R-4.3` 填测试列：AC ID、前置、步骤、断言、证据文件、判定人、环境。
4. `R-4.4` 两份 spec 首部写 `Change`、`Implements`、`Scope`、`N/A + 理由`，`Scope` 写明不碰哪些文件。
5. `R-4.5` 拆任务卡，每张卡写 owner、scope、验收标准、证据、禁止项五项，并按「步骤与汇报点」把卡拆成步骤，每步预计不超过 20 分钟，写清每步的产出与汇报对象；检查点落点统一为 `.tmp/<task-id>/checkpoint.md`。
6. `R-4.6` 做两次交接签收：后端交前端（契约）、前端交测试（build），接收方在交接文件上签字。

产出物：

- `specs/changes/<CHG-ID>/frontend.md` 与 `backend.md`；
- `tasks.md` 的任务卡，每卡五要素齐全；
- 交接签收记录（契约交接、build 交接）。

门禁：

- 自动：spec lint 与锚点唯一性检查（**待补**）；
- 签字：接收方签收，契约交接由前端签，build 交接由测试签。

## 6 阶段 5 · 实现

入口条件：

- 两份 spec 已签收，AC 判据冻结；
- 组件、接口、测试数据与账号可用，或写了降级方式；
- 任务卡已派发，步骤拆分与每步汇报点已填。

步骤：

1. `R-5.1` 按任务卡改代码，改动文件不超出 `Scope`。
2. `R-5.2` 每完成一条 AC 就运行对应断言与相关测试，命令与输出贴进 `evidence.md`。
3. `R-5.3` 前端在 dev server 上过一遍状态矩阵并截图；后端只跑改动包及其直接依赖包测试。
4. `R-5.4` 同步更新 OpenAPI 与组件登记；现状与 spec 不符时先停工记录，按 [`MOXIAN.md`](../framework/MOXIAN.md) 第 12 章登记。
5. `R-5.5` 自验结论写 `pass`、`partial`、`fail` 并附证据，不写"应该没问题"。
6. `R-5.6` 每完成一步按 3 行向派单方汇报，派单方按批汇总对外汇报；检查点在每步完成与停下时更新，写已完成、未完成、下一步；交付时同步提交自验结论。

分步汇报与检查点格式：

- 派单卡上的「步骤与汇报点」逐行写步骤号、内容、预计分钟、产出、汇报对象，预计分钟不得超过 20，超过就拆成两步。
- 实现方每完成一步向该步的汇报对象发一次汇报，不超过 3 行：第一行写完做了什么，第二行写证据在哪（文件路径、命令与输出摘要），第三行写下一步做什么。
- 某一步超过 20 分钟仍无进展，实现方立即停下并报告卡点：卡在哪一步、已试过什么、需要什么；派单方据此重新拆分，拆完再继续，不允许原样续跑。
- 检查点文件 `.tmp/<task-id>/checkpoint.md` 在每步完成与停下时更新，字段为步骤号、状态、已完成、未完成、证据路径、下一步、更新时间；换人时以该文件续做，不靠对话记忆。

产出物：

- 代码改动与对应 spec 更新（同一次提交）；
- `evidence.md` 增量条目：命令、参数、输出摘要、时间；
- 截图与组件登记、OpenAPI 文件、迁移脚本与对账结果；
- 分步汇报记录与检查点文件（`.tmp/<task-id>/checkpoint.md`）。

门禁：

- 自动：改动包测试、`tsc` 与 build、断言脚本；
- 签字：实现者自验（不算验收签字），每步汇报与检查点回报派单方。

## 7 阶段 6 · 测试与验收

入口条件：

- 点级用例全绿，`evidence.md` 条目齐全；
- 变更复盘七节已有草稿；
- 独立验收人已指派，与实现者不是同一人。

步骤：

1. `R-6.1` 把测试列的用例写进 `specs/test/<域>/test-plan.md`，一条用例只覆盖一条 AC。
2. `R-6.2` 跑点级增量用例，全绿后把状态从 `进行中` 改为 `待验收`，写提交时间。
3. `R-6.3` 变更级跑一次全量回归与一次重建，数字写进证据簿；跑两次以上时说明原因。
4. `R-6.4` 验收做变更级验收，抽查 3 至 5 条关键 AC，其余沿用上一轮证据并注明轮次。
5. `R-6.5` 不通过按两种处理：点级不过，打回原实现者走查修验循环；变更级或出口级不过，按 [`MOXIAN.md`](../framework/MOXIAN.md) 第 12 章登记异常。
6. `R-6.6` 签字：验收签后端契约、迁移与流程门禁；用户签前端效果。签字写日期与证据链接。
7. `R-6.7` 状态改 `已验收`，未跑项与豁免在验收报告单列，写明批准人与批准时间。

产出物：

- `specs/test/<域>/test-plan.md` 的用例与执行记录；
- `docs/testing/ACCEPT-*.md`：通过、失败、未跑三张清单；
- 签字记录与状态迁移时间。

门禁：

- 自动：`node scripts/ac-coverage.mjs`、全量回归、重建、汇总 runner（`scripts/run-ac.mjs` 已有，`check-gates` 尚未调度断言执行）；
- 签字：验收与用户各签一张，缺一张不得转 `已验收`。

## 8 阶段 7 · 复盘与关闭

入口条件：

- 状态为 `已验收` 或 `已回滚`；
- 证据文件齐全，命令与读数可复算；
- 成本数据能从 `acp_cache` 取到。

步骤：

1. `R-7.1` 写 `docs/plan/RETRO-<YYYYMMDD>-<需求点ID>.md` 或 `RETRO-CHG-<CHG-ID>.md`，七节齐全；变更复盘 60–120 行，单点复盘 20–40 行。
2. `R-7.2` 成本账取 `acp_cache`，写请求数、总输入、平均每次输入、估算金额与除式。
3. `R-7.3` 回写长期 spec，补丁 10 至 20 行；更新 `docs/product/TRACEABILITY.md`。
4. `R-7.4` 需要新口径的写进 `docs/plan/DECISIONS.md`，新条不改旧条。
5. `R-7.5` 验收核复盘七节；本次有流程改动时，在 [`MOXIAN.md`](../framework/MOXIAN.md) 附录 D.2 写一行版本记录。
6. `R-7.6` 状态改 `已关闭`，写关闭时间与复盘链接；有异常登记时与登记文件互相链接。

产出物：

- 复盘文件（七节齐全）；
- 长期 spec 补丁与追溯矩阵更新；
- `DECISIONS.md` 新条（如有）、[`MOXIAN.md`](../framework/MOXIAN.md) 附录 D.2 版本记录行（如有流程改动）。

门禁：

- 自动：复盘存在性与七节齐全检查（**待补**）；
- 签字：验收核复盘，Lead 关闭；七节不全不得关闭。

## 9 异常接入

任一阶段门禁红、验收不通过或超时未交付，停在被卡的那一步，按 [`MOXIAN.md`](../framework/MOXIAN.md) 第 12 章在 24 小时内建 `docs/plan/FAIL-<CHG-ID>-<NN>.md`，用 [`templates/FAILURE.md`](templates/FAILURE.md) 填字段。裁决后按选定的出口执行：回滚到绿回阶段 5 重做，前向修契约回阶段 3 改设计再往下，缩范围回阶段 1 重定范围。执行完回到被卡的步骤继续，状态按 [`MOXIAN.md`](../framework/MOXIAN.md) 表 5-3 的合法迁移推进。
