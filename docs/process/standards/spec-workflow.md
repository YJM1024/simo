# 规格驱动工作流（Spec-Driven Workflow）

> 本文件是全局通用规则，适用于本机所有工作区与项目，不绑定任何具体产品、需求、技术栈或路径。
> 项目可在工作区文档中定义自己的能力域、ID 前缀、目录映射与验收口径；但本文件的六类产物、门禁与追溯原则不得省略。
> `AGENTS.md` 只保留索引，不重复本文件细节。

## 零、原则

1. **规格是事实来源**：代码、界面、测试和验收以已确认的 spec 为准；口头结论必须落成文字，否则视为未确认。
2. **先产品后设计，先设计后实现**：没有产品 spec 不进入设计；没有开发 spec 不写代码；没有测试 spec 不进入验收。
3. **按能力域聚合，按变更交付**：长期规格按能力域维护，不按功能点一人一文件；每次新增、迭代、修复都用一个变更包承载。
4. **六类证据齐全**：产品、前端开发、后端开发、组件、任务卡、测试六类产物，缺一类必须显式写 `N/A` 与理由。
5. **分层不缺席**：轻量变更可以合并文件，但不能合并掉字段、门禁与证据。
6. **不虚构**：未实现、未执行、未验证必须原样标注；不得用“预计通过”“应该没问题”替代证据。

## 一、分层模型

| 层 | 产物 | 回答的问题 | 生命周期 | 主要 owner |
|---|---|---|---|---|
| L0 | 产品域 spec | 这个能力域为谁解决什么问题，包含哪些功能点、场景、行为和 AC | 长期，随能力演进 | 产品/设计 |
| L1 | 变更包 | 这一次新增/迭代/修复改什么、为什么改、如何验证 | 一次变更，完成后归档 | 变更发起人 |
| L2 | 前端/后端开发 spec | 具体组件、状态、交互、接口、数据、错误、权限、迁移怎么做 | 跟随变更 | 前端/后端 |
| L3 | 组件 spec | 可复用组件的契约、变体、状态、可访问性与视觉规则 | 长期，随组件演进 | 前端/设计 |
| L4 | 测试 spec | 每个 AC 用什么用例、数据、断言和证据证明 | 长期按域维护，随变更追加 | 测试/验收 |
| L5 | 任务卡与证据 | 谁在什么范围内做、完成标准是什么、做完拿什么证明 | 一次任务 | 任务 owner |

### 1.1 目录模式（逻辑位置）

项目可映射到等价目录，但必须保持“域 / 变更 / 测试 / 组件”四类边界：

```text
<项目>/specs/product/<域>/spec.md              # L0，一域一份
<项目>/specs/changes/<变更ID>/                  # L1，一次变更一个目录
  proposal.md                                  # 可选：背景、方案对比、取舍
  spec.md                                      # 必需：变更范围、行为、AC、影响
  design.md                                    # 按需：交互/视觉/架构设计
  frontend.md                                  # 涉及 UI 时必需
  backend.md                                   # 涉及 API/数据/权限/迁移时必需
  tasks.md                                     # 必需：任务卡与依赖
  test-plan.md                                 # 必需：用例映射 AC
  evidence.md                                  # 验收时必需：命令、截图、日志、结果
<项目>/specs/test/<域>/test-plan.md            # L4，一域一份
<项目>/specs/test/e2e/test-plan.md             # 跨域端到端
<项目>/specs/COMP-<组件>/spec.md               # L3，一组件/组件组一份
<项目>/specs/templates/                        # 模板，不参与产品实现
```

约束：
- `specs/product/` 下只放长期产品规格，不放某次变更的临时方案。
- `specs/changes/` 下只放一次变更；完成后移入归档区或在索引中标记 `archived`。
- `specs/test/` 下按域放长期测试计划；单次变更的用例先写入变更 `test-plan.md`，验收后合并回域测试计划。
- 组件 spec 只描述组件契约，不承载产品目标；产品目标留在 L0/L1。

## 二、六类必备产物

| # | 产物 | 何时必须 | 最小内容 | 允许 N/A 的条件 |
|---|---|---|---|---|
| 1 | 产品 spec | 任何新增/迭代/修复 | 背景、目标、非目标、场景、行为、AC、状态 | 不允许。纯内部重构也必须说明“行为不变”的边界 |
| 2 | 前端开发 spec | 涉及界面、交互、前端状态或前端接口调用 | 页面/组件清单、状态机、交互、接口、异常、响应式、可访问性、验收点 | 不涉及任何前端改动时写 `N/A：原因` |
| 3 | 后端开发 spec | 涉及 API、数据模型、存储、权限、任务执行或迁移 | 接口契约、数据变化、错误码、权限、幂等/事务、迁移与回滚、观测 | 不涉及任何后端改动时写 `N/A：原因` |
| 4 | 组件 spec | 新增组件、修改组件公共 API/视觉/状态 | 组件名、用途、props/事件、变体、状态、尺寸/间距、可访问性、禁用条件 | 不新增也不修改组件时写 `N/A：原因` |
| 5 | 任务卡 | 任何要分配给人或 Agent 的工作 | owner、scope、依赖、AC、证据、回滚、截止条件 | 不允许。即使一人完成也要有卡 |
| 6 | 测试 spec | 任何要验收的变更 | 用例 ID、对应 AC、前置数据、步骤、断言、证据、自动化层级 | 不允许。确实无法自动化时写手工用例与理由 |

### 2.1 `N/A` 写法

```text
N/A：本次仅修改文档中的术语，不涉及前端代码、组件、接口或数据结构。
```

禁止：
- 空着不写；
- 只写 `N/A` 不写理由；
- 用“暂不涉及”代替具体边界；
- 把应该有的一类写成 N/A 来绕过门禁。

## 三、变更包

### 3.1 完整变更（full）

满足任一条件即按完整变更处理：
- 跨两个及以上能力域；
- 新增或修改公共接口、数据模型、迁移、权限；
- 新增或修改可复用组件、设计 token、全局交互；
- 影响已验收行为或需要分阶段上线；
- 风险高、回滚成本高、需要多方确认。

完整变更至少包含：
`proposal.md`（可选但推荐）、`spec.md`、`design.md`（按需）、`frontend.md`、`backend.md`、`tasks.md`、`test-plan.md`、`evidence.md`。

### 3.2 轻量变更（lightweight）

同时满足以下条件才可轻量：
- 单域、单一边界；
- 不改公共接口、数据结构、权限与迁移；
- 不新增组件、不改组件公共契约与设计 token；
- 可在一次任务内完成并回滚；
- 不改变已验收行为，或只做等价修正。

轻量变更允许合并文件，但字段不能缺：
- `spec.md` 内至少含：背景/目标/非目标/场景/行为/AC/影响/风险；
- `tasks.md` 保留任务卡；
- `test-plan.md` 保留用例与 AC 映射；
- `evidence.md` 保留执行证据；
- 前端/后端/组件不涉及则写 `N/A：理由`。

### 3.3 升级规则

轻量变更在执行中发现以下任一情况，立即停止并升级为完整变更：
- 需要改接口、数据、权限或迁移；
- 需要新增/修改组件公共契约；
- 影响范围超出原定域；
- 出现无法在一次任务内回滚的副作用；
- AC 需要变更。

## 四、流程

```text
需求进入
  → 判断是否已有产品域 spec
  → 无：先补产品 spec（或明确本次只改行为不变的部分）
  → 建立变更包，写 spec/AC/影响
  → 判断 full / lightweight
  → 写前端/后端开发 spec（不涉及则 N/A）
  → 写/改组件 spec（不涉及则 N/A）
  → 拆任务卡（owner/scope/AC/证据）
  → 实现
  → 写测试用例并执行
  → 采集证据
  → 验收（实现者不自签）
  → 合并回产品域 spec / 域测试计划
  → 更新追溯矩阵
  → 归档变更包
```

每一步的产出必须能被下一步直接使用；不得用“后面再补”跳过前一步。

## 五、门禁

| 门禁 | 时点 | 必须存在 | 不通过的处理 |
|---|---|---|---|
| G0 产品门禁 | 进入设计/实现前 | 产品 spec 或“行为不变”的明确边界 | 停止，先补产品 spec |
| G1 开发门禁 | 写代码前 | 对应前端/后端开发 spec，或带理由的 N/A | 停止，先补开发 spec |
| G2 组件门禁 | 写组件代码前 | 新增/修改组件的 COMP spec，或带理由的 N/A | 停止，先补组件 spec |
| G3 任务门禁 | 分配任务前 | 任务卡：owner/scope/依赖/AC/证据/回滚 | 停止，先补任务卡 |
| G4 测试门禁 | 进入验收前 | 测试 spec + 用例映射 AC + 可执行数据 | 停止，先补测试 |
| G5 追溯门禁 | 标记完成前 | PRD/变更/开发/组件/测试/任务六类链接齐全 | 停止，先补追溯 |
| G6 证据门禁 | 验收签字前 | 命令输出、截图/录屏、日志、测试结果、已知限制 | 停止，先补证据 |

门禁判定为 Blocking；不得用“先上线再补”“时间紧”作为豁免理由。确需例外时，必须由项目负责人书面记录例外范围、风险、补交时间和责任人。

## 六、状态与追溯

### 6.1 状态词

项目可本地化，但语义必须一致：

| 状态 | 含义 |
|---|---|
| `draft` | 草稿，未评审，不可开工 |
| `ready` | 已评审，可开工 |
| `in-progress` | 正在实现 |
| `implemented` | 代码完成，未验证 |
| `verified` | 测试通过，待验收 |
| `accepted` | 已验收并签字 |
| `blocked` | 有明确阻塞条件与责任人 |
| `superseded` | 被新版本替代，保留历史 |
| `archived` | 已完成并归档 |

禁止用 `done` 同时表示“代码写完”“测试通过”“已验收”三种不同状态。

### 6.2 追溯规则

每条功能点至少要有：
1. 产品 spec 中的稳定 ID 与章节；
2. 至少一个变更包，且写明 `Implements: <产品ID>`；
3. 前端或后端开发 spec（不涉及的一侧写 N/A 与理由）；
4. 若有组件改动，对应 COMP spec；
5. 任务卡，写明 `Change: <变更ID>` 与 `AC: <AC ID>`；
6. 测试用例，写明 `Covers: <AC ID>` 与执行证据。

追溯矩阵至少包含：
`功能点 ID | 产品 spec | 变更 ID | 前端 spec | 后端 spec | 组件 spec | 任务卡 | 测试用例 | 覆盖状态 | 缺口`

覆盖状态只允许：
- `covered`：六类齐全且有证据；
- `partial`：有 spec 但缺测试/证据/某侧开发 spec；
- `gap`：无产品 spec 或无测试；
- `n/a`：该类确实不适用，且理由已写。

任何 `gap` 必须在同一份追溯文档中列出补课计划与 owner；不得用 `partial` 掩盖 `gap`。

## 七、完成定义（DoD）

一个变更只有同时满足以下条件才算完成：

- [ ] 产品 spec 已更新，行为、非目标、AC 与状态一致；
- [ ] 变更包 `spec.md` 写明范围、影响、风险、回滚；
- [ ] 前端/后端开发 spec 齐全，或 N/A 理由成立；
- [ ] 新增/修改组件有 COMP spec；
- [ ] 任务卡有 owner、scope、依赖、AC、证据；
- [ ] 测试用例覆盖正常、边界、错误、空、加载、权限/并发等适用场景；
- [ ] 无跳过用例；若有，逐条记录原因、风险、补测时间；
- [ ] 证据可复现，包含命令/环境/数据/结果；
- [ ] 实现者未自签；验收人独立；
- [ ] 追溯矩阵无未解释的 `gap`；
- [ ] 变更包已归档，域 spec 与域测试计划已合并。

## 八、反模式

- 先写代码，后补 spec；
- 一功能一 spec 文件，导致目录爆炸、跨功能关系断裂；
- 产品 spec 只写“支持 X”，没有场景、行为、AC；
- 开发 spec 只贴代码或只写“按设计实现”；
- 组件 spec 只写 props，不写状态、可访问性、禁用条件；
- 测试 spec 只写“测试通过”，没有用例 ID、数据、断言、证据；
- 任务卡没有 scope，导致跨模块改动无人负责；
- 追溯矩阵用 `partial` 掩盖 `gap`；
- 轻量变更偷偷改接口/数据/权限；
- 验收由实现者自己签字；
- 用“时间紧”“先上线”绕过门禁。

## 九、检查清单

开工前：
- [ ] 是否已有对应产品 spec？没有则先补。
- [ ] 本次是 full 还是 lightweight？判定依据是否写清？
- [ ] 六类产物是否都有落点？N/A 是否写了理由？
- [ ] 任务卡是否有 owner/scope/AC/证据/回滚？
- [ ] 测试是否已能映射到 AC？

验收前：
- [ ] 开发 spec 与实现是否一致？
- [ ] 组件 spec 是否覆盖新增变体/状态？
- [ ] 测试是否覆盖正常、边界、错误、空、加载？
- [ ] 是否有跳过用例？原因和补测计划是否记录？
- [ ] 证据是否可复现？
- [ ] 追溯矩阵是否无未解释的 `gap`？
- [ ] 实现者是否回避了自签？
