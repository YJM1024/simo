# SKILL · product-discovery

## 何时使用

- 用户/Lead 提出一个新方向，但目标、价值、边界不清；
- 需要判断“值不值得做/先做什么”；
- 新功能立项前，或已有需求反复返工时。

不用于：已批准 spec 的实现；纯 bugfix；纯组件 API 调整。

## 输入

- 用户原话/使用场景/约束/不接受的代价；
- 现有产品现状（`docs/tasks/product.md`、`DESIGN.md`、已有场景）；
- 可验证的一个假设或信号（先不追求完整调研）。

## 步骤

1. **JTBD 一句话**：谁在什么场景下，想完成什么，当前替代方案是什么；
2. **四风险**：价值（有人要吗）、可用（会用吗）、可行（做得出吗）、商业/维护（值得长期养吗）；
3. **机会排序**：影响 × 确定性 / 成本；只保留一个主张；
4. **边界**：明确非目标、不做什么、失败会怎样；
5. **验证信号**：一个可观察指标/用户动作/原型反馈；
6. **决策**：继续发现 / 写 pitch / 暂缓 / 放弃，记录理由。

## 产物

- `templates/product/opportunity.md`（待建）或等价机会卡：JTBD、四风险、非目标、信号；
- 决策记录：继续/暂缓/放弃 + 依据；
- 若进入立项：交给 `pitch-writing`。

## 检查表

- [ ] JTBD 不是“做一个 XX 功能”的换皮；
- [ ] 四风险都有结论，不是只写价值；
- [ ] 至少一个非目标；
- [ ] 验证信号可观察、不是“用户会喜欢”；
- [ ] 明确不做的替代方案。

## 反模式

- 先有方案再补问题；把功能清单当发现；
- 只讲价值不讲可行性/维护成本；
- 用“用户说想要”代替场景证据；
- 发现阶段就锁死 UI/实现。

## 示例

> JTBD：用户在多会话推进中，想一眼看出当前时间轴属于哪个会话，避免点错。
> 四风险：价值高（频繁切换）、可用中（需要可读）、可行高（纯前端）、维护低。
> 非目标：不做跨项目全局时间轴。
> 信号：原型走查中 5 位用户能正确指认会话；否则回退设计。
> 决策：进入 `pitch-writing`。
