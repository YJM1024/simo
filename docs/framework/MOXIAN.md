## 前置定义

本册正文之前先固定三件事：全册只用这十个术语、只认这一组状态值、只认这七个角色。第 1 章至第 9 章的规则直接使用这些词，不再重新定义；术语出现第二个叫法、状态出现第二个写法、角色出现第八个名字时，按本节改写。

### 术语十条

| 术语 | 定义 |
|---|---|
| 流程点 | 一次工作里承载一类产物的最小单元，按链顺序排列并单独编号 |
| 需求点 | 流程点链的起点，写清要解决什么，其余点由它派生 |
| 来源点 | 记录需求依据的流程点，一条需求对应一个来源点 |
| 判定点 | 把需求转成可判定命题的流程点，一条来源点对应一个判定点 |
| 规则点 | 由判定点派生、按规则格式写成的条文单元，一条判定点可派生多条 |
| 验收点 | 检验一条规则是否满足的流程点，一条规则对应一个验收点 |
| 冻结 | 把点的范围与判据固定下来、之后修改必须登记的动作 |
| 打回 | 验收不通过时把点退回草稿并记录期望与实测差异的动作 |
| 解冻 | 冻结后因范围或判据变化撤销冻结、回到草稿的动作 |
| 变更包 | 一次需求从需求点到验收点的全部载体，关闭后归档不复用 |

### 状态四值

点、变更包与任务卡的状态只取四个值：`草稿`、`已冻结`、`实现中`、`通过`。`冻结`、`开工`、`通过`、`打回`、`解冻`、`关闭` 是动作，不是状态值；状态迁移的起点、终点与前置条件写在表 2-4，本节不重复。冻结按点生效，一个变更包里可以同时存在已冻结的点、草稿的点与实现中的点。AC 判定值与覆盖判定值是判定结果，不属于状态四值，见第 2 章。

### 七个角色与可写范围

七个角色各有一段可写范围，任意两份范围没有交集，一个文件只有一个角色可写；签字关系与越界处理由第 3 章的规则约束。

需求方写 `proposal.md`、需求点文件与冻结确认，不写规则条文与验收记录。签字权只有冻结确认与交付范围确认两项，技术验收不得签。

调研员写来源点文件与 `sources/` 下的依据摘录，不写判定点与规则条文。没有签字权，任何验收都不得签。

判定员写判定点文件，不写规则条文与验收记录。签字权限于判定点自检，基于自己判定点得出的验收结论不得签。

架构师写 `DESIGN.md`、点链与章节结构、差异清单，不写规则条文与验收记录。签字权限于结构自检，任何验收不得签。

撰写员写规则点文件与框架章正文，不写判定点、验收记录与 `DESIGN.md`。没有签字权，自己写的规则点不得验收。

验收员写验收点文件与 `docs/testing/ACCEPT-*.md`，不写规则条文与判定点。签字权是点级与变更级验收，自己参与编写或判定的点不得签。

发布员写 `VERSION`、`CHANGELOG.md` 与发布记录，不写规则条文与验收记录。签字权是发布放行，任何验收不得签。

## 第 1 章 目的、范围与自证

本章决定一项工作是否进入本册，以及本册与其它流程文件冲突时按哪一份执行。范围判定发生在受理之前，判为不适用的工作不建变更包，判为适用而没有变更记录的工作不计入交付。本章的规则对所有后续章节生效，后续章节不另立适用范围。

### MXV2-1-01 纳入范围的工作必须建立变更包

- 规则：在本仓库内产生受版本管理的文件改动、用户可观察的行为变化、存量数据结构变化，或结论需要他人复算的工作，按本册执行并建立变更包。
- 判据：改动所在的提交能指到一个 `specs/changes/<CHG-ID>/` 目录，目录内有 `proposal.md` 与 `spec.md`；四项纳入条件在 `proposal.md` 首节逐条写明并给出结论。
- 执行：`script:scripts/check-mapping.mjs --rule MXV2-1-01` 期望退出码 0
- 层级：L1
- 依据：MX-1-01、MX-1-02
- 适用：任何改动落盘之前与合入之前各查一次。

### MXV2-1-02 五类工作不纳入本册

- 规则：调研、只读排查、一次性命令、环境安装与清理、纯对话讨论五类工作不纳入本册，判定时逐条对照表 1-1，不按工作量或耗时推断。
- 判据：五类工作各能在表 1-1 找到一行，行的判定依据写明为什么没有仓库文件改动、没有行为变化或没有人需要复算。
- 执行：`ai-review:五类排除逐条对照表 1-1，排除理由指向具体工作`；谁判：验收员；误放行：该建包的工作被当作调研跳过，改动落地后没有依据；误拦截：只读排查被判为纳入，为一次查证建包。
- 层级：L1
- 依据：MX-1-03
- 适用：受理时；同一项工作后来产生文件改动时重判一次。

表 1-1 适用范围

| 工作 | 是否纳入 | 判定依据 | 落地方式 |
|---|---|---|---|
| 新增或修改用户可观察的能力、页面、接口与字段 | 纳入 | 交付后行为变化可被他人复算 | 变更包、任务卡、证据 |
| 只改文档且文档进入仓库被引用 | 纳入 | 产生受版本管理的文件改动 | 轻量变更包、文档校验门 |
| 改存量数据或迁移结构 | 纳入 | 需要迁移、回填、双写或回滚 | 变更包、迁移演练 |
| 随变更包发生的发布与部署动作 | 纳入 | 改变运行环境且随本次交付发生 | 变更包、发布检查单 |
| 调研与只读排查 | 不纳入 | 不产生仓库文件改动 | 结论写入现有记录或旁路清单 |
| 一次性脚本与命令 | 不纳入 | 用完即弃且不入仓 | 执行记录留在会话 |
| 环境安装、清理、进程启停 | 不纳入 | 不改变仓库内容 | 运维日志 |
| 纯对话讨论与口头答复 | 不纳入 | 没有落盘产物 | 无 |

### MXV2-1-03 判为不纳入的工作不建包，产生改动时补包

- 规则：判为不纳入的工作不建变更包、不写 spec、不占编号；同一项工作后来产生仓库文件改动时，在改动落盘前补建变更包，并按事故登记补记。

## 第 3 章 角色与授权

本章只规定角色怎么引用、签字怎么分、越界怎么处理，不复制角色卡正文。角色名称、可写范围与禁止项以前置定义那一节和 `docs/framework/ROLES.md` 为准，本章引用而不重述。签字分离是本章的核心约束：写的人不判自己写的东西，判的人不签自己判过的东西。

### MXV2-3-01 每个产出物只有一个 owner

- 规则：七个角色按前置定义那一节取值，每个产出物只有一个 owner 角色，owner 写在文件首部或任务卡上；两个角色同时署名时以任务卡登记的 owner 为准，其余署名者按评审记。
- 判据：每个产出物文件首部或所属任务卡有唯一的 owner 角色名；同一产出物不出现两行 owner；评审记录另列，不写成第二 owner。
- 执行：`script:scripts/check-points.mjs --rule MXV2-3-01` 期望退出码 0
- 层级：L1
- 依据：MX-2-01、MX-2-02
- 适用：任何产出物建立与移交时。

### MXV2-3-02 写的人不签自己写的东西

- 规则：实现者不签自己实现的验收，用例作者不判自己用例通过，规则撰写员不验收自己写的规则；验收角色的 owner 不得同时是实现 owner 或用例作者。
- 判据：每份验收记录的签字人与实现 owner、用例作者三列不重合；同一变更内出现重合时有一条 `FAIL-<CHG-ID>-<NN>` 登记。
- 执行：`ai-review:每份验收记录的签字人与实现 owner、用例作者三列不重合，同一变更内出现重合时有一条 FAIL-<CHG-ID>-…`；谁判：判定员；误放行：失守的判定被当成通过；误拦截：合规判定被退回补证；说明：check-evidence.mjs 为批处理入口，不支持单跑。
- 层级：L1
- 依据：MX-2-03
- 适用：派单时、验收签字前各查一次。

### MXV2-3-03 用户只签前端效果与异常出口

- 规则：用户只签前端效果与异常出口裁决，不占七个角色中的任何一个；用户签字不能由其它角色代签，用户意见由需求方落盘后才算记录。
- 判据：用户签字栏只出现在前端效果验收与异常出口裁决两类记录里；落盘记录有需求方的转写行与用户确认时间。
- 执行：`ai-review:用户签字栏位置正确，意见有落盘转写`；谁判：验收员；误放行：把用户口头意见当作签字，交付依据无法复现；误拦截：把需求方按用户确认落盘的记录判为代签。
- 层级：L1
- 依据：MX-2-04
- 适用：涉及用户签字的验收与出口裁决时。

### MXV2-3-04 一人多角色取更窄的可写范围

- 规则：一人兼多角色时以更窄的可写范围为准，同一份文件的连续修订只由同一角色完成；判定权与执行权落在同一人时，判定交给独立角色。
- 判据：兼任记录写明取哪个角色的可写范围；同一文件的多轮修订记录指向同一角色；判定记录的执行人不等于判定人。
- 执行：`ai-review:兼任取窄有记录，判定权与执行权分离`；谁判：验收员；误放行：兼任者用宽角色的范围改窄角色的文件，越界不被发现；误拦截：把同一角色的连续修订判为跨角色。
- 层级：L1
- 依据：MX-2-05
- 适用：一人承担两个及以上角色时。

### MXV2-3-05 缺席时指派代理并写范围与期限

- 规则：角色缺席时由需求方指派代理，代理范围与期限写进任务卡；代理不得突破签字分离，代理自己实现的产物仍不得由自己签。
- 判据：任务卡有代理角色名、代理范围与到期日三项；代理期间的签字记录里，签字人不等于实现 owner。
- 执行：`ai-review:代理三项齐全，签字仍分离`；谁判：验收员；误放行：代理顺手把自己的实现签掉，验收变成自签；误拦截：把同一角色内部的临时顶班判为代理。
- 层级：L2

## 第 4 章 流程点链与流转

本章把一次工作从受理到收口写成一条可对照的链：先有变更包，再有五个点，再有任务卡，最后有交付物。每一步的输入是上一步的产物，判据是上一步已冻结。链条断在任何一处，后一步不开始；补登记只能补记录，不能补判据。

### MXV2-4-01 变更包是唯一入口

- 规则：任何需求先建 `specs/changes/<CHG-ID>/proposal.md`，契约索引与 AC 判据写同一变更包的 `spec.md`，两份文件同批建立；从零建域也走变更包，不另开入口。
- 判据：`proposal.md` 与 `spec.md` 的建立时间在同一批次；变更包首部有 CHG 编号；从代码或对话里能追到的需求都能指到一个变更包。
- 执行：`script:scripts/check-mapping.mjs --rule MXV2-4-01` 期望退出码 0
- 层级：L1
- 依据：MX-5-01
- 适用：受理任何需求时；补包时。

### MXV2-4-02 受理六项全成立才受理

- 判据：六项在 `proposal.md` 首节逐条有结论；退回记录有理由、回复时间与提出人；受理时间晚于六项写全时间。

## 第 6 章 规则格式与判定

本章规定一条规则长什么样、怎么判、写不出判据时怎么处理。规则是可执行条款，不是口号：每条规则一个编号、一句陈述、一个可观察的判据，判据与执行手段分开写，判定点挂到门禁上。本章的规则卡格式适用于全书，包括附录 D 的未判定条目。

- 判据：规则卡字段数等于六；编号与标题行一致；判据行不是“见上文”“按规范执行”这类空指向；来源出处可解析到 SOURCES.md 或旧规则号。
- 执行：`script:scripts/check-rule-fields.mjs --rule MXV2-6-01` 期望退出码 0
- 层级：L1
- 依据：S-025、S-026

### MXV2-6-02 规则编号三段式，域内连续不复用

### MXV2-6-04 一条规则只做一件事

- 规则：一条规则只约束一个可独立判定的对象，陈述写一句祈使句；同一对象的方法、例外与后果写在同一句里用分号隔开，不把两件事并进一条规则。
- 判据：陈述行只有一句且以动词开头；规则内出现的对象不超过一个；判断需要两个互不相关的检查时已拆成两条。
- 执行：`ai-review:逐条读陈述，检查是否一句话一件事、是否以动词开头、是否夹带第二件事`；谁判：判定员；误放行：把“门禁失败要停工并登记”这类两件事写成一条，判定点分散；误拦截：把带条件从句的一句话判成两件事。

### MXV2-6-05 判据写可观察条件

- 执行：`ai-review:判据行含比较符、数值或路径至少一项，不含形容词式判断，同一判据两次执行结论一致`；谁判：撰写员；误放行：缺项内容进入评审或入库；误拦截：合规写法被要求重写；说明：check-spec-language.mjs 为批处理入口，不支持单跑。

### MXV2-9-01 Git 回滚四类触发，命令按情形区分
