本文件把产品与设计域的做法写成可判定的规则。产品侧负责需求是否成立、范围是否清楚、AC 是否可判，设计侧负责界面几何、交互状态、组件复用与视觉判据是否可验收。产品侧产物先交给设计侧，设计侧产物再交给前端、后端与测试，验收以冻结的判据为准。

本文只写方法与产物，不写实现代码、测试用例与接口实现。总册、任务矩阵与语言标准已有规定的部分只引用编号，不复制原文。本文与上位文件冲突时停在当前步骤并升级裁决，规则见第 1 节。

## 1 适用范围与流程位置

本域覆盖八类任务中会产生或修改产品行为、界面与交互的任务。纯文档任务按任务矩阵的取值写 `N/A：<理由>`，重构按该表的契约与设计必做项写行为等价判据，其余步骤按变更范围裁剪。判级在受理阶段一次完成，本域不重新判级；确需改判时回受理阶段重判，见第 2.1 节。

流程位置在受理与判级门之后、契约与设计阶段之内。上游输入是变更包草稿、判级结论与既有长期 spec，下游输出是 PRD 增量、AC 与判据、设计 spec 增量、契约表的产品列与设计列。设计侧在本域内部完成，前端、后端与测试从本域取契约。

| 位置 | 输入 | 动作 | 输出 | 下游 |
|---|---|---|---|---|
| 受理与判级之后 | 用户原话、工单或事故记录、变更包草稿、判级结论 | 查重、挂点、写目标与范围 | proposal、需求点、非目标 | 本域第 2 节 |
| 契约与设计阶段 | proposal、既有产品与设计 spec、token 与组件清单 | 写 AC、写设计契约、评审冻结 | PRD 增量、设计增量、契约表 | 设计、前端、后端、测试 |

- **MX-PD-01** 本域适用于八类任务中产生或修改产品行为、界面与交互的任务；纯文档任务按任务矩阵的取值写 `N/A：<理由>`，重构须写行为等价判据并保留 AC 回归项，不因内部结构改动而省略契约。
- **MX-PD-02** 本域起点是受理与判级门的通过结论，终点是契约门的冻结结论；未过判级门的任务不写本域产物，未过契约门的点不进入拆分与派单。
- **MX-PD-03** 产品侧产物落在 `specs/changes/<CHG-ID>/spec.md` 与 `specs/product/<域>/spec.md`，设计侧产物落在 `specs/changes/<CHG-ID>/design.md` 与 `specs/design/<域>/spec.md`；变更包只写增量，长期 spec 保存合并后的完整事实。
- **MX-PD-04** 本域不写实现代码、测试用例、接口实现与迁移脚本；设计契约写到选择器、几何、状态与 token 为止。
- **MX-PD-05** 产品与设计由对应 owner 起草，前端、后端与测试承担评审，验收在契约门签字；起草人与实现者不得给自己的产物签字。
- **MX-PD-06** 本域与总册、任务矩阵或语言标准冲突时，冲突写入变更包待确认项并升级 Lead，裁决记录进总册附录 D；裁决前停在当前步骤，不自行改写上位文件。

## 2 阶段步骤

六个步骤按顺序执行，前一步的产出是后一步的输入。每一步写清输入、动作、产出与判定人，判定人未签字时下一步不开始。素材收集可以提前准备，产物签字按顺序进行。

### 2.1 需求受理

| 项 | 内容 |
|---|---|
| 输入 | 用户原话、工单或事故记录、TREE 与 TRACEABILITY 的现状、变更包草稿、判级结论 |
| 动作 | 复述场景与触发事件；查重并挂到需求点；写问题三行；列待确认项；确认判级 |
| 产出 | proposal 的受理节、判级行、需求点编号、待确认项清单 |
| 判定人 | 产品 owner 起草，Lead 在判级门确认 |

受理阶段把一句需求变成可讨论的问题。查重先看 TREE 与既有 PRD，能复用就不新建；新增功能点按 ID-SPEC 分配 `PRD-<域>-<NNN>`，并挂到需求点 `REQ-x.y`。问题三行固定写期望结果、受影响角色与当前替代方案，期望结果带度量指标。待确认项一次最多五条，每条一问一句，写清谁决定与截止时点。

- **MX-PD-07** 受理澄清一次最多五问，每问一句，写明决定人与截止时点；判据冻结前待确认项清零，未清零的条目不进入目标阶段。
- **MX-PD-08** 需求先查 TREE 与既有 PRD，已有功能点复用原编号；新增功能点按 ID-SPEC 分配 PRD 编号并挂到需求点，不重复建点。
- **MX-PD-09** 问题三行的期望结果、受影响角色与当前替代方案必须齐备，期望结果必须带度量指标；缺度量的问题退回提出方补充，不进入目标阶段。
- **MX-PD-10** 判级结论写入变更包开头的类型行，包含主类型、附加类型与一句理由；类型行缺失或与任务矩阵的判级顺序不符时，判级门不通过。

### 2.2 目标与机会

| 项 | 内容 |
|---|---|
| 输入 | 受理节、问题三行、用户场景与当前替代方案 |
| 动作 | 写用户可观察的目标；把机会压成四行；定一条成功信号 |
| 产出 | 目标节、机会四行、成功信号 |
| 判定人 | 产品 owner 起草，Lead 批范围，前端与后端评可行性 |

目标写用户在界面上能看到的结果，例如某个入口出现、某个状态可恢复、某个数字与来源一致。机会四行固定写目标、行为变化、度量与假设，每行一句话并且带一个可测指标。成功信号只保留一条主信号，其余指标进测试计划的观测项。

- **MX-PD-11** 目标条目写用户可观察的结果，写清触发场景与完成后的可见状态；以内部结构、接口数量或代码位置作为目标表述的条目退回重写。
- **MX-PD-12** 机会四行逐行写目标、行为变化、度量与假设，每行必须有一个带单位的度量；任一行缺度量时，目标不进入范围步骤。
- **MX-PD-13** 成功信号只写一条，写清比较基准、数值与采样时点；多目标并列时只保留一条主信号，其余改写为测试计划的观测项。

### 2.3 范围与非目标

| 项 | 内容 |
|---|---|
| 输入 | 目标节、机会四行、影响面初判 |
| 动作 | 写 IN 与 OUT；写影响面五项；标出不做的页面与组件 |
| 产出 | 范围表、非目标清单、影响面表 |
| 判定人 | 产品 owner 起草，Lead 批范围，前端与后端评可行性 |

范围用编号列出本轮要改的功能点与页面，每条带 PRD 或 REQ 编号。非目标逐条写不做什么、为什么不做与什么条件下重开，至少一条。影响面按页面、接口、数据、组件、权限五项逐项写值或 `N/A：<理由>`。

- **MX-PD-14** 非目标至少一条，每条写不做的对象、理由与重开条件；只写“本轮不做”而不写重开条件的条目不通过评审。
- **MX-PD-15** 范围条目必须带 PRD 或 REQ 编号；无编号的条目不得进入契约表与派单。
- **MX-PD-16** 影响面五项逐项写值或 `N/A：<理由>`，留空按缺失计；N/A 的理由少于 8 个字按缺失计。
- **MX-PD-17** 范围冻结后新增条目回受理阶段重新判级，见第 2.1 节；在实现阶段直接扩范围的改动不计入本轮交付。
- **MX-PD-58** 范围节写用户活动主干，主干写在 proposal 第 3 节范围表之前，只列用户活动、活动内步骤与可交付点三列；活动按用户实际操作发生的先后排列，每个活动至少一个可交付点，每个可交付点挂 REQ 编号；派单顺序取主干的活动先后，同一活动内按依赖关系排，主干未出现的活动不进入本轮范围，故事卡与发布切片不引入。（对应候选 2.2）
- **MX-PD-59** 同一待办池内的先后顺序用 RICE 计算，Reach 写受影响角色或场景的条数并带单位，Impact 取 3、2、1、0.5 四档，Confidence 取 100%、80%、50% 三档且无依据时取 50%，Effort 写人日，分值按 Reach 乘 Impact 乘 Confidence 再除以 Effort 计算并保留两位小数。任一因子缺失、单位缺失或 Confidence 不在三档内时拒绝计算并列出缺项，不填默认值；排序结果按 `docs/process/templates/priority.md` 逐条登记编号、池名、四因子、分值与位次，算分由 `scripts/rice.mjs` 执行，模板与脚本未建时由产品 owner 按同一算式手算并把四因子与算式写进登记行；分值只用于同一池内的相对排序，跨池不比较，TREE 的优先级列仍按原档位填写。（对应候选 2.5）

### 2.4 AC 写法与冻结

| 项 | 内容 |
|---|---|
| 输入 | 目标、范围、设计草案、既有 AC 定义行 |
| 动作 | 按第 4 节句式逐条写 AC；编号；配脚本或人工判据；映射到需求点 |
| 产出 | AC 定义行、判据、脚本路径或人工判据、AC 与点的映射 |
| 判定人 | 产品 owner 起草，测试复核可测性，验收在契约门确认冻结 |

每条 AC 只回答一个可观察判据，复合条件拆成多条并在编号末两位顺延。定义行沿用 `AC-<域>-<PRD 三位序号>-<两位序号>`，存量五段式编号保留原样。冻结的含义是判据、判定人与脚本入口在契约表里写成固定值，之后改判据按变更处理。

- **MX-PD-18** 一条 AC 只写一个用户可观察结果；同一结果下的多个测量点可同列，测量点超过三个或定义超过两行时拆分编号。
- **MX-PD-19** 每条 AC 必须有判定人，并写脚本路径或人工判据；判定人写 `自动` 或 `人工:<动作>`，脚本写 `scripts/ac/<AC-ID>.mjs`，人工项脚本写 `N/A：<理由>`。
- **MX-PD-20** 判据冻结前写入契约表，并把条目状态从草稿改为冻结；未冻结的点不得拆卡，也不得开始实现。
- **MX-PD-21** AC 编号在冻结后不改；判据要改时开变更记录，写原判据、新判据、影响点与重验范围，旧证据保留。
- **MX-PD-22** 一个需求点至少有一条 AC，一条 AC 只属于一个需求点；点内 AC 逐行登记在契约表的产品列。
- **MX-PD-23** 存量 AC 改写不重编号，只改定义行内容；新增 AC 按第 2.4 节的编号格式顺延，不重用已删除编号。

### 2.5 设计契约

| 项 | 内容 |
|---|---|
| 输入 | 冻结的 AC、DESIGN.md、tokens.css、组件 manifest、既有设计 spec |
| 动作 | 写区域与几何、状态矩阵与转移、四档视口、组件复用结论、可访问性检查项 |
| 产出 | 设计 spec 增量、设计列条目、截图基线路径、组件登记结论 |
| 判定人 | 设计 owner 起草，前端评可实现性，验收确认可判 |

设计契约把 AC 的可见结果翻成界面上的几何、状态与组件选择。每条设计判据带私有编号 `V-<域>-<PRD 序号>-<序号>`，并注明它支撑哪条产品 AC。几何表写选择器、属性、数值、档位、容差与 token，状态矩阵按元素与状态交叉逐格写值。组件先查 manifest，能复用的写复用结论，新增或改动的给 COMP 编号。

- **MX-PD-24** 设计条目只引 token 名，不写裸色值、裸字号与裸间距；取值在 tokens.css 找不到时先裁决 token，再写入契约。
- **MX-PD-25** 状态矩阵覆盖 default、hover、focus、active、disabled、loading、empty、error 八态与元素的交叉，每格写值或 `N/A：<理由>`；有状态切换的组件同时写事件与起止状态。八态是唯一集合，其他文件只引用本条，不另立四态或五态；状态矩阵缺态时按缺失计，不得以「界面无该状态」为由删态，确无该状态时逐格写 `N/A` 与理由。
- **MX-PD-26** 选择器优先 `data-*` 锚点，不使用 `nth-child`、位置序号或可见文本作为唯一锚点。
- **MX-PD-27** 新增或变更的组件必须有 COMP 编号与截图基线；复用既有组件时写“复用 COMP-<kebab>”，不复用也不新增时写 `N/A：<理由>`。
- **MX-PD-28** 设计契约按 375、768、1180、1600 四档写布局与可见性，每档给断言或 `N/A：<理由>`，并把截图基线路径写进设计 spec。
- **MX-PD-29** 可访问性七项的项名、检查方式与判定人在本条定义：键盘操作、焦点可见、可访问名称、对比度、错误识别、reduced-motion 与目标尺寸。七项为唯一集合，`TASK-MATRIX.md` 第 2 节可访问性门、`MOXIAN.md` 的 MX-2-18 与附录 B 表 B-3、`domains/frontend.md` 的 MX-FE-53 只引用本条，不另列清单。表单标签与按钮名称归入可访问名称，页面语言的 `lang` 属性归入可访问名称的检查动作。可自动测的项写脚本入口，脚本未实现时写人工动作与证据路径；七项任一项没有检查方式或结论时契约门判不通过。WCAG 2.2 AA 的映射、数值阈值与豁免按 MX-PD-67 至 MX-PD-69 执行，三条规则不新增检查项名，只给七项补附加检查动作与判定数值。

WCAG 2.2 AA 与七项的映射见下表。映射不改变七项集合，五项补充条目作为对应项的附加检查动作执行，结论并入该项；2.4.11 的焦点不被遮挡并入焦点可见项，2.5.7 的拖动替代并入键盘操作项，3.2.6 的帮助一致性、3.3.7 的冗余输入与 3.3.8 的无障碍认证并入错误识别项。

| WCAG 条目 | 等级 | 归入项 | 附加检查动作 |
|---|---|---|---|
| 2.4.11 焦点不被遮挡（最低） | AA | 焦点可见 | 页面滚动到中部与底部各一次，断言聚焦元素可见面积不少于 90%，不被固定页头、页脚或浮层完全遮挡 |
| 2.5.7 拖动动作 | AA | 键盘操作 | 所有拖动排序与拖动调整必须有单击、键盘或数值输入替代路径，替代路径完成同一结果 |
| 3.2.6 一致的帮助 | A | 错误识别 | 同类页面的帮助入口在相同相对位置出现，顺序一致，错误提示附近有帮助入口 |
| 3.3.7 冗余输入 | AA | 错误识别 | 同一信息在一次流程内只要求输入一次，已提供的信息自动填充或提供选择，不要求重复键入 |
| 3.3.8 无障碍认证（最低） | AA | 错误识别 | 登录与验证环节提供非视觉替代，允许粘贴密码，不要求记忆类认知测试 |

七项中的 reduced-motion 对应 WCAG 2.3.3，该条属 AAA 级，本规范按项目增强项执行，等级差异写进设计说明的可访问性节，不因等级高于 AA 而省略检查。映射表缺条目、条目等级写错或附加检查动作没有结论时，契约门判不通过。

七项的数值阈值按下表判定，阈值是本规范唯一取值处，其他文件引用本条，不另写一套数值。

| 项 | 阈值 | 测量方法 |
|---|---|---|
| 正文对比度 | 前景与背景的相对亮度比不低于 4.5:1 | 取计算样式的颜色值，按 sRGB 相对亮度公式计算 |
| 大字号对比度 | 相对亮度比不低于 3:1；大字号指 18pt 常规字重或 14pt 粗体及以上 | 同正文对比度 |
| 非文本对比度 | 界面组件边界、图标与状态指示的相邻颜色对比不低于 3:1 | 取相邻两色的计算值计算比值 |
| 焦点轮廓 | 轮廓宽度不低于 2px，轮廓与元素边缘的偏移不低于 2px，轮廓与相邻颜色对比不低于 3:1 | 聚焦后读 `outline-width`、`outline-offset` 与颜色值 |
| 目标尺寸 | 可点击目标最小 24×24 CSS 像素，主操作按钮与触控目标最小 44×44 CSS 像素 | 读 `getBoundingClientRect()` 的宽高 |
| 焦点不被遮挡 | 聚焦元素可见面积不少于 90% | 聚焦元素矩形与视口、固定层的交集面积比 |
| reduced-motion | 非必要动画与过渡的时长为 0s | `matchMedia('(prefers-reduced-motion: reduce)')` 命中后读计算样式 |

- **MX-PD-67** WCAG 2.2 AA 映射按上表执行，五个补充条目全部有结论，映射表的条目编号、等级与归入项三列不得空缺；七项中任一 `N/A：<理由>` 必须先经 MX-PD-69 豁免，未豁免的 N/A 按缺失计。映射表写进设计 spec 的可访问性节与 a11y 检查表，两处条目编号一致，验收在契约门逐条核对，检查表按 `docs/framework/templates/a11y-checklist.md` 填写。
- **MX-PD-68** 七项阈值按上表判定，对比度、焦点轮廓、目标尺寸与焦点不被遮挡四项必须给数值结论，只写“符合 AA”而不给比值的按缺失计。测量脚本未建立时人工用取色器与浏览器计算样式测量，命令、颜色值与比值写进证据文件；自动扫描工具的报告只作补充，扫描通过不替代逐项数值。
- **MX-PD-69** 豁免只适用于第三方提供且无法修改的内容、技术不可行且有替代方案、界面处于废弃期并写定移除日期三种情形，键盘操作、可访问名称、对比度、错误识别四项不得豁免。豁免登记固定写八项：条目编号、WCAG 条目、页面与组件、豁免理由、用户影响、替代方案、到期日、批准人。批准人取产品 owner 与验收双签，涉及 AA 条目时另写 Lead 批准与 `DEC-<序号>` 裁决编号；单次变更豁免不超过 3 条，超过时回到范围步骤重定范围。豁免记录写进设计 spec 与变更包 evidence，到期未消除的豁免按缺陷登记并阻断收口。
- **MX-PD-70** 令牌变更的验收按四项判定：受影响组件清单与 manifest 引用一致、旧令牌引用计数为 0、受影响组件截图基线全部更新、回滚演练通过。四项全过记 `pass`；清单或基线缺项记 `partial` 并回到前端应用步骤；旧令牌仍有引用或回滚未通过记 `failed`，不得收口。判定人按 MX-PD-66 分工，证据落 `templates/token-change.md` 第 7 节，验收结论写进该文件第 7 节的判定表与变更包 evidence。
- **MX-PD-60** 每个登记的 COMP 组件在应用内样例页有可访问的地址，地址按组件、变体、状态与视口四个参数定位，格式为 `/#gallery?component=<name>&variant=<variant>&state=<state>&viewport=<375|768|1180|1600>`，四个参数的取值只从 `frontend/src/components/manifest.json` 的 name、variants、states 读，样例页不另维护第二份组件清单，也不引入 Storybook；入口沿用 manifest 的 `gallery` 字段 `/#gallery`，manifest 未登记的组件或状态在样例页显示缺项并按缺失计；截图基线按地址逐状态取图，文件名含组件名、状态与视口宽度，取图走 `scripts/probe-cdp.mjs` 的四档截图扩展。（对应候选 3.7）
- **MX-PD-61** 设计评审按十项启发式逐项给结论，十项为系统状态可见、系统与真实世界匹配、用户控制与自由、一致性与标准、错误预防、识别优于回忆、灵活高效、美观简洁、帮助用户识别与修复错误、帮助与文档；每项写检查动作、判定人与证据路径，其中系统状态可见、帮助用户识别与修复错误、一致性与标准三项写成可执行判据，焦点可见并入系统状态可见的检查动作，其余项写人工动作与截图；十项任一未写结论时契约门不通过，可测项在 `scripts/check-a11y.mjs` 落地后由脚本承担。（对应候选 3.4）

### 2.6 评审

| 项 | 内容 |
|---|---|
| 输入 | proposal、PRD 增量、AC、设计 spec 增量、契约表 |
| 动作 | 三角色逐条核对可判定性；冲突登记；签字冻结 |
| 产出 | 评审记录、契约表冻结标记、未决项清单 |
| 判定人 | 前端、后端、测试评审，验收签契约门，Lead 批范围 |

评审只判两件事，判据能否被执行，产物是否齐全。前端核对选择器、几何、状态与组件是否可实现，后端核对接口行为与错误语义是否写清，测试核对每条 AC 能否落成脚本或人工动作。冲突不现场改需求，登记后回到对应步骤重写。

- **MX-PD-30** 评审至少覆盖前端、后端与测试三个角色；角色缺席时写明代理人与缺席理由，代理签字视为有效。
- **MX-PD-31** 评审只判可判定性与完整性，不在评审现场改需求；确需改动的条目退回范围或 AC 步骤，改完重新评审。
- **MX-PD-32** 评审未通过的点保持草稿状态，不拆卡、不派单；通过的点把契约表状态改为冻结并记录签字人。
- **MX-PD-33** 评审记录写入变更包 `spec.md` 的评审节，字段为日期、参与角色、结论、未决项与签字；缺任一项的记录不计入契约门。
- **MX-PD-34** 实现者不得给自己起草或实现的产物签字；同一人兼任评审与实现时只保留评审签字，实现签字另找独立角色。

## 3 必产出的文件与字段

本域在每次变更里至少产出五类内容，每类有固定落点与字段。变更包只写本次改动的增量，长期 spec 保存合并后的完整事实。字段留空按缺失计，不适用写 `N/A：<理由>`。

### 3.1 变更包 proposal

落点 `specs/changes/<CHG-ID>/proposal.md`，由产品 owner 维护。字段与模板八节的对应关系见下表。

| 字段 | 必填 | 落点与写法 |
|---|---|---|
| 类型行 | 是 | 标题下第一行，写主类型、附加类型与判级理由 |
| 问题三行 | 是 | 第 1 节，写期望结果、受影响角色、当前替代方案，期望结果带度量 |
| 目标与成功信号 | 是 | 第 2 节，目标写用户可观察结果，成功信号一条并带采样时点 |
| 机会四行 | 是 | 第 1 节或第 2 节，写目标、行为变化、度量、假设 |
| 范围与非目标 | 是 | 第 3 节，IN 条目带编号，OUT 至少一条并写重开条件 |
| 影响面 | 是 | 第 4 节，页面、接口、数据、组件、权限五项 |
| 待确认项 | 是 | 第 7 节，最多五条，写决定人与截止时点，冻结前清零 |
| 链接 | 是 | 第 8 节，写 spec、design、tasks 与 test-plan 路径 |

模板现有八节不含类型行与机会四行，落地时写在标题下与第 1 节，模板修订另开一张任务卡。模板修订前，这两项由人工评审核对，见第 8 节的未决点。

- **MX-PD-35** 五类产出缺任一类且未写 `N/A：<理由>` 的变更不得过契约门；缺类的理由少于 8 个字按缺失计。
- **MX-PD-36** 变更包只写本次增量，不复制长期 spec 全文；引用写 PRD、AC 或 REQ 编号，重复口径按引用失效处理。
- **MX-PD-37** PRD 增量按 `ADDED`、`MODIFIED`、`REMOVED` 三段标记，每段写基线版本或基线行号；基线冲突未解决时不得归档。
- **MX-PD-38** AC 编号在全部 spec 内唯一，冻结后不重用；重复编号由语言门禁阻断，拆分后的旧编号保留并标注去向。
- **MX-PD-39** 设计增量按功能点分节，修改节写基线版本与改动行，新增节整节写入；不按页面或文件重新组织章节。
- **MX-PD-40** 契约表是本次变更唯一的契约定义载体，其他文件引用条目编号，不复制条目正文。
- **MX-PD-41** 契约表条目逐项填写，字段见第 3.5 节；缺字段的条目按未通过计，不进入冻结。
- **MX-PD-42** 契约表条目冻结后改动记“已变更”，保留原行并追加新行，同时回到评审步骤重新签字。
- **MX-PD-62** 影响设计契约、token 或组件边界的决定写决策记录，五节固定为标题、状态、背景、决策与后果，追加在 `docs/plan/DECISIONS.md` 末尾并带日期与依据，不新建第二份决策库；编号沿用该文件的 `DEC-<序号>`，一条一号且不复用；状态取提议、接受、作废、被替代四值，被替代时写替代它的编号；缺任一节或状态不在四值内的记录不计入契约门，存量单句条目保留原样，新增条目按五节写。（对应候选 3.3）

### 3.2 PRD 增量

变更侧写在 `specs/changes/<CHG-ID>/spec.md` 的需求与验收节，长期侧合并进 `specs/product/<域>/spec.md`。一个功能点长期只占一个章节，增量不新开文件。

| 字段 | 必填 | 写法 |
|---|---|---|
| 功能点编号与锚点 | 是 | `PRD-<域>-<NNN>`，锚点写 `<a id="prd-...">` |
| 目标行为 | 是 | 编号条目，每条写一个用户可见行为 |
| AC 定义行 | 是 | 见第 3.3 节，编号唯一，不复制正文到其他列 |
| 非目标 | 是 | 与本功能点相关的排除项与重开条件 |
| 优先级 | 是 | 取值沿用 TREE 的优先级列，不自行新造档位 |
| 状态与关联域 | 是 | 状态词取自 ID-SPEC，关联域写跨域归属 |

### 3.3 AC 编号与判据

编号格式为 `AC-<域>-<PRD 三位序号>-<两位序号>`，域码取 ID-SPEC 第 2 节的 12 个技术域码。存量五段式编号保留原样，新增编号按四段式分配，差异交总册裁决，见第 8 节。

| 字段 | 必填 | 写法 |
|---|---|---|
| 触发 | 是 | 事件与对象，例 `pointerup` on `.menu-item` |
| 观测 | 是 | 可测量对象与取值，例 `.dialog` 的 `getBoundingClientRect().width` |
| 判据 | 是 | 比较符、数值、单位与容差，例 `等于 335px`、`±1px` |
| 采样点 | 是 | 时点或元素，例“响应后 500ms”或“弹窗首帧” |
| 脚本 | 是 | `scripts/ac/<AC-ID>.mjs`，人工项写 `N/A：<理由>` |
| 判定人 | 是 | `自动` 或 `人工:<动作>` |
| 证据落点 | 是 | `.tmp/ac/<AC-ID>.json` 或 test-plan 的用例行 |
| 环境 | 是 | base URL、浏览器版本、构建号 |

### 3.4 设计 spec 增量

设计侧变化写在 `specs/changes/<CHG-ID>/design.md`，长期侧合并进 `specs/design/<域>/spec.md`，按功能点编号分节。设计增量与产品增量使用同一批功能点编号，不另建编号体系；组件 spec 作为设计列的子产物随列提交，不单独占契约列。

| 字段 | 必填 | 写法 |
|---|---|---|
| 区域与几何 | 是 | 区域名、选择器、属性、数值、档位、容差、token |
| 状态矩阵与转移 | 是 | 八态与元素交叉逐格写值，事件与起止状态逐条列出 |
| 档位 | 是 | 375、768、1180、1600 四档，逐档写布局断言 |
| 组件 | 是 | COMP 编号或“复用 COMP-<kebab>”，并写截图基线路径 |
| 可访问性 | 是 | 七项的检查方式、判定人与证据路径，项名按 MX-PD-29 |
| 设计判据 | 是 | `V-<域>-<PRD 序号>-<序号>`，注明支撑的产品 AC |
| 冲突与缺口 | 是 | 产品与设计的冲突条目、缺口条目与责任人 |

架构边界随设计增量一起提交，图与契约表在同一轮冻结。

- **MX-PD-63** 接入外部服务、新增进程或新增存储时在设计增量写系统上下文图与容器图两级，上下文图列本系统、外部参与者、外部系统与信任边界，容器图列前端、后端、数据库与外部依赖及其协议；两级图的元素名称与 `manifest.json`、契约表、`openapi.yaml` 的对应名称一致，一个元素一个名称，不画组件级与代码级图；图写在 `specs/changes/<CHG-ID>/design.md` 的架构边界节，长期侧并入 `specs/design/<域>/spec.md`，外部服务未接入时两张图写 `N/A：<理由>` 并写重开条件。（对应候选 3.2）
- **MX-PD-64** 设计令牌作为契约表的设计令牌类登记，一类一行，登记字段为令牌名、作用域、旧值、新值、替代关系与废弃时间六项。令牌名按语义命名，不按色值命名；作用域写引用的组件编号与页面路径，全局令牌写 `global` 并列出全部引用方；旧值与新值成对出现，只改一项时另一项写当前值并注明未变；替代关系写被替代的旧令牌名或 `N/A：<新增>`；废弃时间写日期或 `N/A：<理由>`，写了废弃时间的令牌在到期前按 `templates/token-change.md` 第 6 节执行删除，删除 `frontend/` 下的令牌文件时按 `ROLES.md` 第 5 节 MX-R-31 的写作用域执行。六项缺一不得冻结，令牌取值在 `tokens.css` 找不到时按 MX-PD-24 先裁决再登记。
- **MX-PD-65** 令牌变更写旧值与新值对照表，一行一个令牌，逐项写旧值、新值、影响组件、影响页面与是否需要视觉基线更新。影响组件从 `frontend/src/components/manifest.json` 的引用关系取全，逐组件列编号；影响页面列出路由或页面路径；需要更新视觉基线的组件逐组件重取截图，基线未更新的组件在 375、768、1180、1600 四档视口下各留一张截图作对比证据，页面在 1280 有独立断点时加该档，档位口径按 `MOXIAN.md` 第 9 章 MX-9-11。对照表缺行、影响组件清单与 manifest 引用不一致或基线未更新时，契约门与证据门判不通过。令牌的废弃与迁移按 MX-PD-64 的废弃时间执行，迁移期内的旧令牌保留读取别名，别名清单写进对照表并在迁移完成后删除。
- **MX-PD-66** 令牌变更的验收判定人按对象分工：令牌取值、作用域、替代关系与废弃时间由设计评审人签，令牌在界面上的应用结果与回滚方案由验收签，设计方向由用户确认；设计作者、前端应用者不得在本人参与的对象上签字。判定人写进设计说明的验收节与签字文件，缺判定人或判定人与实现者重合时收口门判不通过。设计交付附加类型的六个阶段必做项与门禁按 `TASK-MATRIX.md` 第 8 节执行，本规范只补令牌对象的判定分工。

## 4 判据写法

判据只写事实、约束、契约与断言，背景说明留在 PRD。每条 AC 按同一句式写全六段，读者只凭这一句能写出脚本或执行一次人工判定。样例使用 `CONV` 域与 901、902 两个不存在的 PRD 序号，只展示格式。

```text
主语=<ID 或选择器>；条件=<可构造的前置>；动作=<一次操作或一条请求>；判据=<观测> <比较符> <数值><单位>，采样=<时点或元素>，容差=<±数值或 0>；判定=<自动|人工:动作>；脚本=<scripts/ac/<AC-ID>.mjs 或 N/A：理由>。
```

- **MX-PD-43** 每条 AC 按句式写全六段，段与段用中文分号隔开；缺任一段的 AC 判不合格并退回重写。
- **MX-PD-44** 主语写 ID 或稳定选择器并写清测量对象；以“该按钮”“这个列表”“相关模块”开头的 AC 判不合格。
- **MX-PD-45** 数字带比较符与单位，几何量带采样点与容差；只写“合适”“足够”而不给数值的 AC 判不合格。
- **MX-PD-46** 时间类判据写起始事件、结束事件与阈值，例“消息落库到 DOM 更新完成”；只写“及时”的 AC 判不合格。
- **MX-PD-47** 判定人只写 `自动` 或 `人工:<动作>` 两种取值；人工项在脚本段写 `N/A：<理由>`，理由写清人工动作与证据落点。
- **MX-PD-48** 一条 AC 对应一个脚本入口 `scripts/ac/<AC-ID>.mjs`；脚本未实现时标 `待建`，脚本落地前该 AC 不得判 `pass`。
- **MX-PD-49** 单条 AC 定义不超过两行；超过两行或测量点超过三个时拆分编号，原编号保留并标注拆分去向。

- 正例一（交互）：`AC-CONV-901-01` 主语=会话行 `.session-item[data-session-id]` 的归档菜单项；条件=`main` 之外的未归档会话 1 个且 `archived=0`；动作=在菜单项上触发 `pointerup`；判据=归档请求发出 1 次、菜单关闭、该行 `data-archived` 变为 `1`（采样=响应完成后 500ms，容差 0）；判定=`自动`；脚本=`scripts/ac/AC-CONV-901-01.mjs`。
- 正例二（几何）：`AC-CONV-901-02` 主语=弹窗 `.dialog`；条件=视口宽度 375px 且页面无横向滚动；动作=打开弹窗；判据=`.dialog` 的 `getBoundingClientRect().width` 等于 335px、左右外边距各 20px（采样=弹窗首帧，容差 `±1px`）；判定=`自动`；脚本=`scripts/ac/AC-CONV-901-02.mjs`。
- 正例三（错误态）：`AC-CONV-901-03` 主语=表单错误区 `[role="alert"]` 与提交按钮 `button[type="submit"]`；条件=提交返回 `422` 且 `code=invalid_email`；动作=点击提交；判据=错误节点 1 个、文案包含“邮箱”、提交按钮 `disabled=false`（采样=响应后 300ms，容差 0）；判定=`自动`；脚本=`scripts/ac/AC-CONV-901-03.mjs`。
- 反例一：`AC-CONV-902-01` 点击后尽量快速显示结果，用户体验要好。
  不合格项：主语未写 ID 或选择器，缺少比较符、数值、采样点、判定人与脚本路径，命中禁用词“尽量”。
- 反例二：`AC-CONV-902-02` 侧栏宽度合适，间距适当，在小屏上自动适配。
  不合格项：没有数值与单位，没有档位、容差与采样点，命中禁用词“适当”，“自动适配”没有触发条件与阈值。
- 反例三：`AC-CONV-902-03` 接口返回成功后列表刷新，失败时给出提示。
  不合格项：主语写成了行为描述，缺少 ID 或选择器，两个判据写在一行，缺少错误码、采样时点、判定人与脚本路径，“成功”与“提示”没有可测定义。

## 6 常见错误与拦截点

## 7 与其它域的接口

本域通过文件交接，聊天记录与口头说明不作为接口。前端、后端与测试各取一部分，取用范围与格式如下。

### 7.1 给前端
交付设计 spec 增量、设计列条目、AC 的前端可判部分与组件结论。
格式为 `点 | AC | 选择器 | 属性 | 数值 | 档位 | 容差 | token | 状态矩阵 | 组件 | 截图基线`，一行一个条目。
接收判据：选择器可在 DOM 定位、每态有值、组件有结论、四档有断言、无裸值；缺一项退回补写。

### 7.2 给后端
交付产品 AC 中的接口行为、错误码、幂等语义、存储不变量与相关非目标。
格式为 `点 | AC | method 与 path | 鉴权 | 请求字段 | 响应字段 | 错误码 | 幂等 | 存储不变量`，一行一个条目。
接收判据：错误码成对、边界值明确、幂等语义可复算、不含界面细节；缺一项退回补写。

### 7.3 给测试
交付 AC 定义行、判定人、脚本入口或人工判据、前置与证据落点。
格式为 `AC 定义行六段 + TEST-<域>-<NNN> | Covers: AC-<ID> | 层级 | 状态`，每条 AC 在 test-plan 占一行。
接收判据：每条 AC 有唯一入口、前置可构造可清理、采样点与容差明确、待建脚本已标注；缺一项不纳入用例。

- **MX-PD-54** 本域对下游的交接以文件为准，聊天记录、口头说明与截图说明不作为接口；下游按字段接收，缺字段退回本域补写。
- **MX-PD-55** 给前端的交付缺选择器、四档、状态矩阵或组件结论时，前端不进入实现。
- **MX-PD-56** 给后端的交付缺方法路径、错误码、幂等语义或存储不变量时，后端不进入实现。
- **MX-PD-57** 给测试的交付缺 AC 定义行、判定人、脚本入口或证据落点时，测试不纳入用例。
