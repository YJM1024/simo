六个门禁是检查动作，挂接到 `docs/framework/TASK-MATRIX.md` 第 2 节的阶段出口门禁上，不新增阶段，也不替换判级门、契约门、派单门、自验门、证据门与收口门。检查对象是 `specs/changes/<CHG-ID>/` 下的变更包、`specs/{product,design,frontend,backend,test}/` 下的五列 spec、`scripts/ac/` 下的断言脚本、`specs/test/<域>/fixtures/manifest.json` 下的夹具清单与 `docs/testing/` 下的证据索引。字段定义沿用 `docs/process/SPEC-STANDARD.md` 第 2 节与 `docs/process/templates/`，本文件只写检查方法与判定条件。

统一输出采用一行一条的文本格式：`[GATE-<NAME>] <path>:<line> <MX-G-NN> <事实>；<修复动作>`。末行输出 `PASS (gate: <name>, checks: <n>, warnings: <m>)` 或 `FAILED: <e> error(s), <w> warning(s)`。`--json` 模式输出对象数组，每项含 `gate`、`rule`、`severity`、`path`、`line`、`ac`、`hint` 七个字段。退出码 0 表示通过，1 表示存在 error，2 表示参数或环境错误。`待补` 用退出码 2 表达，不用 0。

与历史文档的关系。`docs/process/RUNBOOK.md` 的七个阶段与 `R-1` 至 `R-7` 是 v0.9 之前的旧划分，已被本文件的六道检查门禁、矩阵覆盖率门与十五道特有门禁取代；RUNBOOK 只作历史记录，门禁判定与执行以本文件为准，`R-1` 至 `R-7` 不再作为门禁编号引用。

## 1 分级与默认阻断
门禁结果取 `通过`、`不通过`、`待补` 三值，三值的判定条件与后续动作固定下来，避免同一结果在不同人手里解释成不同状态。

- `MX-G-01` 门禁结果取 `通过`、`不通过`、`待补` 三值；error 命中数大于 0 记 `不通过`，退出码 1，停在本阶段；error 为 0 且全部检查已执行记 `通过`；脚本未落地、环境不可达或缺少运行前置记 `待补`，退出码 2。第 4 节标为人工判据的规则由责任人按第 3.2 节与第 3.3 节的判据核对，门禁记录写清判据、核对人与时间时按已执行计，不记 `待补`。`待补` 不计入通过，变更级与出口级出现 `待补` 时按 `不通过` 处理。
- `MX-G-02` warn 只提示不阻断，退出码仍为 0；每条 warn 写入门禁记录的原因与到期日；同一 warn 连续两轮未消除时升为 error，升级由 Lead 在门禁记录中登记。
- `MX-G-03` 默认阻断五道：结构、追溯、语言、契约、证据。增量覆盖率默认告警，其中改动源文件没有任何测试映射按 error 阻断，行覆盖率与分支覆盖率低于阈值按 warn。纯文档变更跳过契约门禁，追溯门禁只查产品列与证据索引，结构门禁的 test-plan 可写 `N/A：<理由>`；跳过与降级须在变更包首部写理由与批准人。
## 2 运行时机
四个时机的范围与门禁组合固定，开工前看输入是否齐全，提交前看本次改动，变更级看全量，出口级看签字前的最终状态。

- `MX-G-04` 开工前跑结构、语言、契约三道；结构门禁确认变更包首部、任务卡、`spec.md` 与 `tasks.md` 齐全，`test-plan.md` 与 `evidence.md` 缺失按 warn 记；语言门禁确认 AC 定义可判定，契约门禁确认契约表已冻结；追溯门禁只跑基线，核对 `Covers` 与五列 spec 的 AC 集是否一致，结果按 warn 记录。
- `MX-G-05` 提交前跑语言与增量覆盖率两道，范围限本次改动文件；改动涉及变更包元数据时加跑结构，涉及证据文件时加跑证据；提交前门禁不替代变更级全量。
- `MX-G-06` 变更级在测试与证据阶段结束时跑全部六道，使用变更全量范围；六道 error 全为 0 才进入验收。
- `MX-G-07` 出口级在签字前再跑全部六道，使用出口范围；证据门禁用当前提交与 buildId 重算有效期，追溯门禁核对长期 spec 回写后的 AC 集；出口级 `待补` 一律按 `不通过`。

| 时机 | 结构 | 追溯 | 语言 | 契约 | 增量覆盖 | 证据 | 范围 |
|---|---|---|---|---|---|---|---|
| 开工前 | 必跑 | 跑基线 | 必跑 | 必跑 | 不跑 | 不跑 | 本变更全部 AC 与任务卡 |
| 提交前 | 按改动 | 不跑 | 按改动 | 不跑 | 按改动 | 按改动 | 本次改动文件 |

## 3 检查门禁与特有门禁
### 3.1 结构门禁
目的：拦截字段不全的变更包与任务卡，避免实现者按残缺信息开工。本门禁只核对模板必填项是否存在、取值是否合法，不评价内容质量。

检查对象与路径：变更包的 `specs/changes/<CHG-ID>/spec.md`、`proposal.md`、`tasks.md`、`test-plan.md`、`evidence.md`，可选的 `frontend.md` 与 `backend.md`，任务卡所在的 `tasks.md` 任务表行，`spec.md` 的评审节或其中登记的独立评审记录，以及 `docs/process/templates/{spec,proposal,tasks,task-card,test-plan,evidence}.md` 与 `docs/framework/templates/{review,evidence-index}.md` 的必填项。

检查项清单：

- `MX-G-08`（error）检查必需文件是否存在；开工前模式只要求 `spec.md` 与 `tasks.md`，`test-plan.md` 与 `evidence.md` 缺失记 warn，变更级要求四个文件；`frontend.md`、`backend.md` 缺失时要求 `N/A：<理由>`，纯文档包的 `test-plan.md` 可用 `N/A：<理由>` 代替；判定按文件存在性与理由长度是否不少于 8 个字符；输出缺失文件路径与缺失理由，一条缺失一行。
- `MX-G-09`（error）检查 `spec.md` 首部字段 `状态`、`Implements`、`Covers`、`Change`、`变更类型`、`Owner`；判定六个字段是否非空，状态是否落在 `SDD-STANDARD.md` 第 3.3 节的七值或 `draft`、`partial`、`blocked`、`accepted` 四个迁移值内，变更类型是否落在 `TASK-MATRIX.md` 第 1 节的八类内；输出缺失字段名或非法取值，一条一行。`SDD-STANDARD.md` 已停用，条款以墨线为准。Covers 编号按三段式 `AC-<域>-<子域>-<序号>` 判定，`CHG-LEGACY-*` 与归档包同时接受两段式 `AC-<域>-<序号>`；历史包的验收项编号随冻结文本固定，改名等于改冻结 AC，补编号等于伪造，因此放宽只对历史包生效，新包仍按三段式判定，避免放宽后掩盖新包的编号缺段。历史包判定沿用本节存量包口径，即包目录名以 `CHG-LEGACY-` 开头或首部状态含 historical、archived、归档；该放宽自 v1.7 起生效。
- `MX-G-10`（error）检查目标、非目标、验收标准三处是否存在，以及验收标准内每条 AC 是否有脚本路径或人工判据；判定按标题是否含 `目标`、`非目标` 或 `未覆盖与明确不做`、`验收` 或 `AC`，以及 AC 定义行是否含 `scripts/ac/` 或 `人工:`；输出缺失位置名或缺少判据的 AC 编号。需求编号表、状态与错误边界、接口与数据、待确认、链接五处按模板为必填，新包缺失记 error，`CHG-LEGACY-*` 与归档包记 warn。
- `MX-G-11`（error）检查 `tasks.md` 任务表的列 `卡`、`任务`、`owner`、`scope`、`依赖`、`AC`、`证据`、`状态` 是否齐全，以及每个数据行八列是否非空，状态列是否落在 `MOXIAN.md` 表 3-3 的任务卡状态五值内；判定按表头列名、单元格内容与状态取值；输出缺列名、空单元格所在行号或非法状态值。
- `MX-G-12`（error）检查每张任务卡是否按 `MOXIAN.md` 表 7-4 写全十八项字段；判定卡号、所属变更、owner 角色、执行人、Change、REQ、AC、CT、scope 允许段与禁止段、验收标准、证据、推理档位、步骤、并行或串行、省略项三列、状态与验收签字人是否非空，owner 是否落在八个角色内，REQ 是否为 `REQ-x.y` 或其多值写法、`REQ-DOC-x.y`、`REQ-TOOL-x.y`、`N/A：` 加不少于 8 个字符的理由之一，CT 是否为空或以 `N/A：` 开头并带不少于 8 个字符的理由，状态是否落在 `MOXIAN.md` 表 3-3 的任务卡状态五值内，验收签字人是否与执行人不同；输出缺项卡号、缺项名与非法取值，签字人重合时按 error 记。
- `MX-G-13`（warn）检查 `test-plan.md` 的 `Covers:` 与 AC 映射表列、`evidence.md` 的结论与 AC 证据表列；判定按模板列名与是否存在数据行；输出缺失列名。
- `MX-G-48`（error）检查立项文件 `proposal.md` 是否存在以及表 5-2 二十五项字段是否按载体填齐；判定按 `MOXIAN.md` 表 5-2 的二十五个字段名逐项查找，载体取 `templates/change.md` 第 1.1 节的映射：proposal 的字段在 `proposal.md` 的八节查，变更包头部的字段在 `templates/change.md` 第 1 节查，契约表的字段在 `templates/change.md` 第 5 节与 `specs/contract/<域>/contract.md` 查，受控节的字段在 `templates/change.md` 受控节查。点级、变更级与建域级共用同一字段集，每项须有内容或 `N/A：<理由>` 且理由不少于 8 个字符；`spec.md` 首部字段齐备不能替代本条，`templates/change.md` 十节填齐也不能替代本条。提案文件缺失、映射载体缺失或任一项为空时记 error，输出缺失文件路径、载体路径与缺失字段名，一行报一项。
- `MX-G-49`（error）检查评审记录是否存在以及四块内容是否填全；判定按 `docs/framework/templates/review.md` 的表 1 基本信息八字段（评审对象、评审人、评审时间、评审类型、所属变更与任务卡、评审依据、评审档位、记录落点）、表 3 逐条结论（序号、条目、依据、通过与否）、表 5 结论（通过、有条件通过、不通过三值之一）与表 6 签字（评审人、日期、签字范围）；记录落在变更包 `spec.md` 的评审节，或落在该节登记的独立文件路径。评审类型只取契约、设计、实现、验收四值，评审档位只取 `high`、`max` 两值：契约、设计、实现与日常验收评审取 `high`，变更级整线签发、P0 级根因裁定、框架版本冻结与独立验收、跨变更架构裁决取 `max`，与场合不符时记 warn 并在评审记录写明原因；签字人与本次实现 owner 不同。缺记录、缺表、缺字段、结论落在三值之外或签字人与实现者重合时记 error，输出记录路径、缺失表号与字段名。本条在契约门与收口门各执行一次，变更包没有任何评审记录时按 error 处理。
- `MX-G-53`（error）检查表 5-2 三个新增字段的内容。`涉及契约项` 字段须写核对人、核对时间、记录位置与契约项编号和状态清单，或写「无」并写核对人；数据迁移的 `数据语义处置` 字段须写处置方式、该处置方式对应的可交付物、决定人与证据路径，处置方式取 `MOXIAN.md` MX-5-23 的四种之一；采用保留一条并附删除清单时核对删除清单的主键范围、行数与对账口径，采用迁移到新字段时核对字段映射、回填范围与回填前后对账数字，采用拒绝写入并登记例外时核对例外对象清单、有效期与批准人，采用按归属判定规则回填并附判定清单时核对归属判定规则的来源字段、优先级与兜底值，以及判定清单的记录主键范围、判定结果与行数、归属判定决定人；性能优化的 `目标指标与测量口径` 字段须写目标值、单位、并发条件、测量命令、样本量与基线来源六项，测量命令须与证据索引中的命令逐字一致。非数据迁移与非性能优化任务的对应字段写 `N/A：<理由>` 且理由不少于 8 个字符。缺项、理由不足、处置方式落在四种之外、处置方式与可交付物不对应或目标值与证据命令不一致时记 error，输出字段所在载体的路径、字段名与缺项或非法取值。

错误级别：`MX-G-08` 至 `MX-G-12`、`MX-G-48`、`MX-G-49` 与 `MX-G-53` 为 error，`MX-G-13` 的模板列缺失为 warn。存量包 `CHG-LEGACY-*` 与归档包的 error 降为 warn，其余包按 error 执行；存量包由 owner 在重开时补齐字段。

通过标准：error 命中数为 0，warn 命中逐条登记原因与到期日，门禁结果记 `通过`。

### 3.4.1 不适用声明

契约表字段与状态全集比对，列文件可以对其中一类提示声明有意不适用。声明只能压低提示级判定，不能改变 error，也不能改变契约表的状态与冻结要求。

语法为一行文本，写在声明文件正文的任意位置。

```
N/A：<类别>：<理由>
```

关键字固定为 `N/A` 三个字符；两个分隔符写全角冒号或半角冒号均可，分隔符前后允许空白。类别取下表登记的一值，按字面精确匹配，不折叠大小写，不接受近义词或自造类别。理由取第二个分隔符到行尾的文本，去掉行内代码、粗体与链接标记、多余空白后不少于 8 个字符。

| 类别 | 适用门禁 | 声明所在文件 | 被跳过的提示 | 仍按原级别输出的判定 |
|---|---|---|---|---|
| `前端字段` | MX-G-27 | 前端 spec | 契约表来源列没有任何前端 props 字段行时的 warn | 前端 spec 缺字段 |
| `设计状态` | MX-G-28 | 设计 spec | 设计 spec 出现契约表状态全集之外状态名时的 warn | 缺失状态、缺失迁移、未知 UI 状态名 |
| `前端状态` | MX-G-28 | 前端 spec | 前端 spec 出现契约表状态全集之外状态名时的 warn | 缺失状态、缺失迁移、未知 UI 状态名 |

当前生效的声明只有设计 spec 的 `N/A：设计状态`（`specs/design/P1-CONV/spec.md:20`）：组件渲染态与交互态不属于契约表类 2 的任务状态机，声明按设计状态类别跳过该类 warn。前端 spec 已删除原有的 `N/A：前端字段` 与 `N/A：前端状态` 两条声明（原第 36 至 38 行、第 90 至 92 行），字段在 §1.8 登记、展示态在 §17.9.4 登记，前端维度有真实比对对象，MX-G-27 与 MX-G-28 对前端 spec 按字段集合、状态集合与迁移记录比对，不再按声明整类跳过。设计侧渲染态声明仍在，N/A 机制保留。

判定按被检查文件全文执行。脚本逐行匹配，取第一条类别与当前判定一致的声明；有效声明跳过该文件这一类的提示，理由不足 8 个字符时记 error 并指出声明行，没有声明或类别不匹配时按未声明处理并保留原提示。同一文件同一类别写多条时只有第一条生效。

声明写在正文、引用块或行内注释里同样识别，判定只按行匹配，不要求行首对齐。类别拼错、写成近义词或省略类别都不构成有效声明，原提示照旧输出且不记 error；这种写法不会让门禁失败，也不会减少提示，修正方式是对照上表改成登记过的类别。未声明时提示逐条输出，没有默认跳过；声明了但理由不足时按 error 失败关闭，不能用空理由把提示压掉。

MX-G-26 允许纯文档包写 `N/A：<理由>` 跳过九条契约规则，那是整包跳过；本节声明带类别，只压 MX-G-27 与 MX-G-28 中登记的提示，两种写法不互相替代。

生效范围是文件级。一条有效声明覆盖该文件这一类的全部提示，不区分字段、状态、行段或提示来源行；当前前端 spec 已无 `前端字段` 与 `前端状态` 声明，MX-G-27 按字段集合与类型比对，MX-G-28 按状态集合与迁移记录比对，不存在整类跳过。设计 spec 的 `N/A：设计状态` 只作用于组件渲染态与类 2 任务状态机维度不同这一处，任务状态缺失、迁移缺失与前端字段、前端状态仍按原级别输出。声明行必须写清被跳过的是哪一类对象与为什么不适用，验收复核时对照声明行、契约表与列文件逐项确认，不能只看 warning 是否归零。单个 spec 同时描述多个组件时，同一类别声明仍会覆盖该类全部提示，这类文件应按组件分节写明理由，或改用补契约表的方式消除提示；新增声明时按组件分节，避免一条声明压掉同文件第二处需要比对的提示。判定不区分正文、引用块与代码块，文件里用登记的类别举示例时会真的压掉提示，示例应写占位符或放在被检查文件之外。

本节由 `scripts/check-contract.mjs` 实现，规则号沿用 MX-G-27 与 MX-G-28，不新增门禁规则编号，现行 69 条规则与编号范围不变。字段类型一致性在契约表「类型」列与列文件同名字段之间比对，字段列识别与类型归一在第 554 至 626 行，类型不一致判定在第 1318 行，error 记录在 1321 至 1331 行（第 1330 行为消息模板）；契约表固定列的缺格扫描在 983 至 1073 行；契约表中文状态按第 89 至 98 行的对照表映射为存储态与展示态，后端比存储态、前端比展示态，比对在 1337 至 1540 行（任务状态机分支，设计分支在 1521 至 1539 行，分支返回在 1540 行）。上述检查均已实现并纳入 `--self-test`，不再列为已知缺口。前端 spec 现有真实字段与展示态，MX-G-27 与 MX-G-28 在前端维度按本节与第 3.4.1 节比对。证据记录写声明文件、声明行号、类别与理由，验收报告登记实际生效的声明；声明不进入契约表，也不改变 `Covers:` 与 AC 的对应关系。

### 3.5 增量覆盖率门禁
目的：确认本次改动的每个源文件都有对应测试，改动行与改动分支的覆盖情况可见。阈值只决定告警，阻断项是映射缺失与未运行，依据 `docs/framework/domains/testing.md` 第 6 节与 `docs/framework/MOXIAN.md` 第 9.4 节的 MX-9-21 与 MX-9-22。

### 3.11 可观测性门

判定值：三条 SLI 齐全，采样率达标，告警触发记录五项字段完整。

失败处置：不得收口；补登记与告警演练后重跑。责任人：后端（值班）发起，验收签字。

### 3.12 外部依赖门

判定值：登记字段齐全，四类注入各至少一次，降级后用户可见结果与契约一致。

失败处置：不得进入验收；补注入验证后重跑。责任人：后端发起，测试复核注入，验收签字。

### 3.13 合规门

检查项：`MX-G-68`（error）核法规依据、数据范围、保留例外、完成时限、第三方回执五项（MX-6-31），另核删除完成证明三项（MX-9-28）与处置记录五类范围、级联顺序（`templates/compliance-disposal-record.md`）。缺项、回执缺失或删除完成证明不足三项记 error。

失败处置：不得收口；由产品（合规判定人）与验收双签后放行。责任人：产品（合规判定人）发起，验收签字。

### 3.14 插件市场审核门

失败处置：不得发布；补记录或换复核人后重跑。责任人：市场审核人发起，复核人独立复核出结论，验收签最终判定。

失败处置：不得发布；补齐后重跑。责任人：后端发起，验收签字。

### 3.16 功能点覆盖门

适用条件：变更级验收前生效，变更包在 `spec.md` 声明功能点覆盖表时逐包检查；点级验收不单独执行，随所属变更包一次执行。

检查项：`MX-G-71`（error）以功能点为单位核对本次变更的覆盖声明。检查对象是变更包 `spec.md` 的“功能点覆盖”节，该节须写明 `覆盖范围：` 与四列表（功能点ID、状态、覆盖它的 AC、备注）。逐行核对五件事：状态只取 `in`、`partial`、`out`；`in` 至少列一个 AC 编号且该编号在 `specs/product/` 或本变更包内能查到；`out` 的备注写明不做理由；`partial` 的备注写明剩余缺口；表中 AC 编号必须已登记。另核必填集合：覆盖范围列出的点、`Implements:` 声明的点与 `TREE.md` 中 CHANGE 指向本变更包的点都须在表中出现，`Implements` 的点不得标 `out`，表外的树点与表内未登记的点各记 error。`partial` 行本身记 error，因为它表示功能点未完成，门禁不得放行。

判定值：覆盖表结构完整，必填集合全部入表，`in` 的 AC 均可登记，`partial` 为 0 行，`out` 均有理由。

失败处置：变更包不得进入变更级验收，已签发的回退到实现阶段；`partial` 行要么补齐缺口改 `in`，要么确认不做改 `out` 并写理由，不得为通过门禁把 `partial` 改标 `in`。责任人：变更包 owner 填表，产品核对功能点范围，验收 Agent 复核并签字。

脚本：`node scripts/check-fp-coverage.mjs`，默认扫描全部含覆盖节的变更包，`--change <CHG-ID>` 检查单包，`--json` 输出逐点明细，`--self-test` 自检 26 条断言。通过样例与失败样例由 `--self-test` 在 `.tmp/fp-coverage-tooling/` 下生成，覆盖 partial、out 缺理由、in 缺 AC、AC 未登记、树外功能点、重复行、缺表头与缺覆盖范围八类失败。真样本取 `CHG-CONV-007`，覆盖表 7 行中 3 行 `partial`，脚本输出 3 条 error、退出码 1，其余 4 行通过。

本节新登记的专项门禁为本地化门、弱网与离线门、可观测性门、外部依赖门、合规门、插件市场审核门、独立工具发布门与功能点覆盖门八道，检查规则见第 3.9 至 3.16 节，编号接续 `MX-G-64` 至 `MX-G-71`。本文件现行规则合计 69 条，编号范围为 `MX-G-01` 至 `MX-G-71`；`MX-G-55` 与 `MX-G-56` 仍为预留编号。
