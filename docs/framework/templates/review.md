# 评审记录模板（review）

版本：v0.2，2026-11-24。状态：active，随第二批压测补缺冻结。
定位：本文件记录一次评审的对象、依据、逐条结论、问题与签字，缺字段或未签字的记录不计入对应门禁。
依据：`docs/framework/ROLES.md` 第 13 节的签字关系、`docs/framework/domains/product-design.md` 第 2.6 节（MX-PD-30 至 MX-PD-34）与 MX-PD-64 至 MX-PD-66、`docs/framework/TASK-MATRIX.md` 的门禁表与第 2.1 节验收对象表、`docs/framework/domains/testing.md` 的证据字段。

## 1 基本信息

基本信息表由评审组织者在评审开始前填写，评审结束后补结论与签字，记录缺字段时不计入门禁。

表 1 基本信息字段

| 字段 | 填写内容 | 填写要求 |
|---|---|---|
| 评审对象 | 文件路径与版本 | 逐行列文件、版本或行数；文档写行数与快照时间，代码写提交号或工作树快照。 |
| 评审人 | 姓名或子智能体名 | 至少覆盖前端、后端与测试三个角色；角色缺席时写代理人与缺席理由。 |
| 评审时间 | 日期与起止时刻 | 写时区，精确到分钟，跨日评审分行记录。 |
| 评审类型 | 契约、设计、设计验收、实现、验收之一 | 一次记录只写一种类型，混合评审拆成多条记录。 |
| 所属变更与任务卡 | `CHG-<域>-<NN>` 与卡号 | 写变更包编号与任务卡号；无法引用时写 `N/A` 与理由。 |
| 评审依据 | 判据与规则编号 | 写 AC 编号、契约项编号或规则编号，不写“按规范”这类泛指。 |
| 评审档位 | `high` 或 `max` | 评审段按 `ROLES.md` 表 4 取 `high`，变更级整线签发取 `max`，契约门与日常验收取 `high`，不降到 `low` 以下。 |
| 记录落点 | `spec.md` 评审节或独立文件 | 按 MX-PD-33 写进变更包 `spec.md` 的评审节；独立成文时路径写进任务卡 scope。 |

填写说明：

- 评审对象写清版本，只写路径而没有版本的记录按缺字段处理；文件在评审后又有改动时另开一条记录，不覆盖旧记录。
- 评审人一栏逐人写角色，同一人兼任多个角色时写全，签字关系按第 6 节处理。
- 评审依据必须能定位到具体条目，引用规则时写规则编号，引用证据时写文件路径与行号。
- 记录字段覆盖日期、参与角色、结论、未决项与签字五项，缺任一项的记录不计入契约门（MX-PD-33）。

## 2 评审类型与判定口径

五种评审类型对应不同的门禁与签字人，评审开始前先按本节确定当前类型，避免用验收的宽松口径处理契约。设计交付附加类型的交付物另走设计验收类型，评的是设计说明与令牌 diff，不评前端实现。

表 2 类型、通过与签字

| 类型 | 评审对象与时机 | 通过条件 | 签字人 |
|---|---|---|---|
| 契约 | 五列契约表与 AC 判据，契约冻结前 | 五列齐全，每条 AC 有判据与判定人，待确认项清零，组件 spec 已登记或写 `N/A` 与理由 | 验收签契约门，Lead 批范围 |
| 设计 | 设计 spec、组件 spec、状态矩阵与截图基线，设计列冻结前 | 判据为可观察量，状态矩阵覆盖八态或有 `N/A` 理由，四档布局写清 | 前端、后端与测试评审，验收签字 |
| 设计验收 | 设计说明、令牌旧值与新值对照表、受影响组件清单与令牌 diff，出口级验收前 | 设计说明章节齐全并逐章有判定人；令牌六项字段齐全；受影响组件与 manifest 引用一致；diff 与实际改动的令牌文件一致 | 验收签交付物，用户确认设计方向；设计作者与评审人不得签本人参与的对象 |
| 实现 | 实现 diff、构建输出与自验记录，提交证据前 | 改动在 scope 内，增量测试通过，未跑项写原因，构建与类型检查通过 | 实现者不得自签，由验收或独立评审人签 |
| 验收 | 证据索引与验收报告，收口前 | 每条必做 AC 有证据与结论，抽查 3 至 5 条可复跑，未验证项列明 | 验收签技术部分，用户签前端效果 |

设计验收逐条核对的字段固定为五项：设计说明章节清单、令牌名与作用域、旧值与新值、受影响组件与页面清单、令牌 diff 路径。五项缺一按不通过计，令牌取值由设计评审人签，界面应用结果由验收签，设计方向由用户确认，分工按 `MX-PD-66` 执行。

签字关系按 `ROLES.md` 第 13 节执行：实现者、用例作者与本轮执行者不得签本交付的验收，用户只签前端效果，同一人兼任时签字栏只保留评审签字。

## 3 逐条结论

逐条结论表覆盖本次评审的每个条目，一条一行；留空的条目按不通过计，不按默认通过处理。

表 3 逐条结论

| 序号 | 条目 | 依据 | 通过与否 |
|---|---|---|---|
| R1 | AC-CONV-001-01 的判据 | `specs/product/<域>/spec.md` 第 3 节 | 通过 |
| R2 | 契约项 CT-CONV-014 的字段与错误码 | `spec.md` 契约表第 2 行 | 不通过 |
| R3 | 页面在 375 档的布局 | 本轮无界面改动，设计列写 `N/A` 与理由 | 不适用 |

- 条目写被评审的具体项，用 AC 编号、契约项编号、文件路径加行号定位，不写“相关章节”。
- 依据写判据、规则编号或证据路径，依据为空时该条按不通过计；通过与否取通过、不通过、不适用三值，不适用必须附理由。

## 4 问题清单

问题清单承接逐条结论里的不通过项与有条件通过的条件，每条给可执行的修法。

表 4 问题清单

| 编号 | 严重度 | 位置 | 问题描述 | 建议 |
|---|---|---|---|---|
| P-01 | 高 | `specs/product/<域>/spec.md:42` | 判据写“正常显示”，无法判定 | 改为可观察量、阈值与判定动作 |
| P-02 | 中 | `spec.md` 契约表第 2 行 | 错误码只写 400，未区分字段与权限 | 补两条错误码与触发条件 |

- 编号在同一变更内连续排，与变更包的问题清单共用一套编号，收口时按编号核对闭合情况。
- 严重度取高、中、低三档，与 `docs/framework/accept/ACCEPT-BATCH1.md` 的写法一致；位置写文件路径加行号或 AC 编号。
- 建议写成可直接执行的一步，不写“加强检查”这类无法验收的话。

## 5 结论

结论只取通过、有条件通过与不通过三个值，有高严重度问题时不写通过；未决项逐条写决定人、截止时点与关闭判据，有条件通过的条件全部写进问题清单。

表 5 结论与后续动作

| 结论 | 成立条件 | 后续动作 |
|---|---|---|
| 通过 | 逐条结论无“不通过”，问题清单为空或只剩低严重度建议 | 契约项改为冻结并记录签字人，其余类型归档记录并回写对应节 |
| 有条件通过 | 无高严重度问题，条件写清 owner 与截止时点 | 条件闭合前不进入下一道门，闭合后由同一评审人复核 |
| 不通过 | 存在任一条高严重度问题或核心条目未通过 | 退回对应阶段重写，改完重新评审，不在现场改需求 |

## 6 签字

签字在结论与问题清单写定后进行，签字人与日期落文件后评审才结束，口头结论不构成评审结果。

表 6 签字栏

| 签字角色 | 签字人 | 日期 | 签字范围 |
|---|---|---|---|
| 评审人 | | | 逐条结论与问题清单 |
| 验收 | | | 契约门、设计交付物或技术验收结论 |
| 用户 | | | 前端效果，含视觉、交互与可用性；设计交付时另确认设计方向 |
| 设计评审人 | | | 令牌取值、作用域、替代关系与废弃时间 |
| 设计作者 | | | 设计说明版本与令牌 diff 的提交，不签本条 |
| 读者 | | | 文档可读性与正确性，仅文档交付与纯文档使用 |
| 缺席代理 | | | 代理角色、缺席理由与被代理人 |

- 设计作者行只登记提交与版本，不作通过签字；设计作者与设计评审人重合时设计验收按自签处理。
- 读者行由目标读者中至少一名实际使用者签，签字人不得为文档作者或合稿人，签字范围写文档路径与生效日期。

- 实现者、用例作者与本轮执行者不得出现在验收签字行，出现时该签字按无效处理；同一人兼任评审与实现时只保留评审签字。
- 签字栏缺签字人或日期时，记录按未完成处理，对应门禁不通过。

## 7 专项验收判定

以下六类专项对象在本表登记判定人、不可兼任关系与结论取值，判定口径与 `TASK-MATRIX.md` 第 2.1 节一致。专项结论与总表结论同表签字，专项未通过时总结论不得写通过。

| 专项对象 | 判定人 | 不可兼任 | 结论取值与依据 |
|---|---|---|---|
| 离线收敛 | 测试判结论，前端复核测量 | 离线功能实现者、用例作者 | 通过、不通过；依据网络五档与收敛条数（MX-9-30） |
| 可观测性接入 | 后端（值班）判口径与采样率，测试核告警 | 指标埋点实现者、发布执行人 | 通过、有条件通过、不通过；依据三条 SLI 与告警触发记录（MX-9-31） |
| 外部依赖策略 | 后端判配额与降级，测试复核注入 | 依赖接入实现者、发布执行人 | 通过、不通过；依据四类注入证据（MX-9-32） |
| 市场审核结论 | 市场审核人签审核结论，复核人签复核决定，验收签放行 | 插件开发者、审核执行人、申诉受理人 | 通过、驳回、可申诉；依据五类事件记录（MX-9-34） |
| 灰度发布结论 | 验收判每档结论 | 发布执行人 | 通过、暂停、回滚；依据档位观察窗口与回滚阈值 |
| 灾备演练结论 | 验收判演练结论 | 执行切换的实现者 | 通过、不通过；依据 RTO、RPO 实测与切换一致性（`templates/drill-report.md`） |

审核人与复核人不得为同一人，申诉受理人不得为出具驳回决定的人；签名栏按第 6 节填写，专项判定人签字写在对应专项行。

## 8 归档与未决点

- 评审记录按 MX-PD-33 写进 `specs/changes/<CHG-ID>/spec.md` 的评审节；独立成文时由派单方在任务卡 scope 内指定路径，文件名沿用 `<对象>-REVIEW-<YYYYMMDD>.md`。
- 评审通过的契约项把状态改为冻结并记录签字人，未通过的点保持草稿，不拆卡、不派单。
- 五种评审类型的门禁细则以 `MOXIAN.md` 第 10 章与 `TASK-MATRIX.md` 第 2 节为准，设计验收另按第 2 节与 MX-PD-66 核对判定人；独立评审记录的命名与目录尚未登记在附录 A，待回写时补登记。
