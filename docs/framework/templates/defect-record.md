# 缺陷记录模板（defect-record）

版本：v0.2，2026-11-24。状态：active，随第二批压测补缺建立；v0.2 于同日补复现人字段与第 9 节受控与披露记录。
定位：本文件按缺陷编号记录一条缺陷从受理到关闭的事实，含根因四行、修复范围、验证结论与复发记录，关闭后按编号可查；根因四行是唯一记录位置，任务卡只引用本节。
依据：`docs/framework/TASK-MATRIX.md` 第 1 节缺陷严重级别表与第 3 节缺陷修复行，`docs/framework/MOXIAN.md` MX-4-17、MX-5-21、MX-6-17、MX-8-06，`docs/framework/domains/testing.md` 第 4 节判据写法。
落点：`docs/plan/DEFECT-<CHG-ID>-<NN>.md`，与 FAIL 文件分开，普通缺陷不进 FAIL。

## 1 缺陷基本信息

| 字段 | 填写内容 | 要求 |
|---|---|---|
| 缺陷编号 | `DEF-<YYYYMMDD>-<NN>` | 同一日期内连续编，不重用 |
| 所属变更 | `CHG-<主域>-<NNN>` | 与变更包首部一致 |
| 发现人 | 角色名与子智能体名 | 发现人与修复人可为同一人，与验收人不得重合 |
| 发现时间 | `YYYY-MM-DD HH:MM` | 带时区 |
| 发现渠道 | 用户报告、探索性测试、监控告警、回归失败四值之一 | 不写「测试时发现」 |
| 影响面 | 受影响功能、页面、接口与数据 | 写实体与数量，不写「部分用户」 |
| 严重级别 | 致命、严重、一般、轻微四值之一 | 取 `TASK-MATRIX.md` 第 1 节判定信号的原句作依据 |
| 级别依据 | 引用判定信号的原句并写命中项 | 写不出依据时不得进入修复 |

## 2 复现与期望

复现记录按 MX-5-21 六项写，六项缺一按未复现处理。环境写构建号、系统、浏览器与视口；版本写提交号或 buildId；复现步骤逐步写操作与输入；期望结果写已写明的预期与出处；实际结果写观察到的值与截图路径；严重级别与第 1 节一致。复现人写角色名与子智能体名，并写与修复卡 owner 的关系；安全修复的复现人按 `TASK-MATRIX.md` 第 1 节取测试角色，测试角色未到位时取未参与修复的另一域实现者，复现人不得为修复卡 owner，独立性结论写进本节。

## 3 根因四行

根因四行在契约阶段确认，由验收复核，复核人不得为实现者。四行写不出时停在根因确认门，不得派发修复卡。

| 行 | 填写内容 |
|---|---|
| 直接原因 | 触发缺陷的具体代码路径、数据状态或配置值 |
| 机制 | 直接原因如何导致观察到的结果，一句写清链路 |
| 复现命令 | 可在本机重跑的失败用例命令与修复前的失败输出路径 |
| 影响面 | 同机制可能波及的其他入口、数据与调用方 |

## 4 修复范围

修复范围写四个清单：改动文件、改动接口或数据、新增用例、回归范围。四个清单逐条写路径或编号，修复不得超出清单；确需扩大时回契约阶段补范围并重过派单门。

## 5 验证与回归

验证写失败用例在修复前后的两次输出、相邻路径回归结果与缺陷发生档位的截图。判定结论取 `pass`、`partial`、`missing`、`blocked` 四值，非 `pass` 写原因码与解除条件。修复未引入新暴露面的检查按安全修复规则执行，普通缺陷写 `N/A：<理由>`。

## 6 复发记录

缺陷复发时保留原记录，新增一行，不覆盖历史。

| 字段 | 填写内容 |
|---|---|
| 复发次数 | 第几次复发，从 1 起计 |
| 上次修复编号 | 上一次的变更号与本记录编号 |
| 复发原因 | 修复不完整、新代码引入、数据残留三类之一 |
| 本次处理 | 重新修复、扩大范围或回滚，写选择依据 |
| 复盘链接 | 单点复盘或变更复盘的路径 |

## 7 台账行

关闭时在缺陷台账补一行，八列齐全。台账文件为 `docs/plan/DEFECT-LEDGER.md`，一行一条缺陷，按编号排序。

| 缺陷编号 | 所属变更 | 级别 | 发现日期 | 根因类别 | 修复范围 | 复发次数 | 关闭日期 |
|---|---|---|---|---|---|---|---|
| `DEF-YYYYMMDD-NN` | `CHG-<域>-<NNN>` | 四值之一 | 日期 | 写代码、数据、配置、依赖或文档 | 文件数与接口数 | 数字或 0 | 日期 |

## 8 关闭检查

- [ ] 复现六项齐全，修复前失败输出已保存。
- [ ] 根因四行齐全，复核人不是实现者。
- [ ] 修复范围四个清单齐全，改动未超范围。
- [ ] 失败用例在修复后通过，相邻路径回归通过。
- [ ] 缺陷发生档位有截图或命令输出。
- [ ] 复发记录与台账行已更新，关闭日期已写。

## 9 受控与披露记录（安全修复关联缺陷时填写）

安全修复关联的缺陷记录另填本节，字段与变更包受控节同名，两处不一致时以变更包受控节为准。非安全修复缺陷写 `N/A：<理由>`，理由写明不涉及披露与受控信息。

| 字段 | 填什么 | 要求 |
|---|---|---|
| 复现人 | 角色名、子智能体名与独立性结论 | 按第 2 节填写，复现人不得为修复卡 owner |
| 受控节路径 | 变更包受控节的节号与版本，模板见 `templates/change.md` | 写节号与版本，不复制知情人名单 |
| 通知对象 | 受影响方名称 | 与变更包受控节逐项一致 |
| 通知方式 | 邮件、站内信、电话或会议四值之一 | 与变更包受控节逐项一致 |
| 通知时点 | `YYYY-MM-DD HH:MM` 带时区 | 不得晚于披露时限 |
| 接收确认 | 接收人角色名、确认时点与确认方式 | 缺确认的条目按未通知处理 |
| 凭证路径 | 受控证据文件路径或消息编号 | 路径可打开，消息编号可回查 |
