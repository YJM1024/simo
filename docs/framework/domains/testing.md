## 1 适用范围与位置

本规范适用于八类任务中进入测试与证据阶段的全部工作，包括新功能、界面调整、缺陷修复、重构、数据迁移、性能优化、安全修复与纯文档。缺陷修复的复现用例、纯文档的示例命令复跑、变更级的全量回归与重建也按本规范执行。框架自身的规则评审、一次性调研脚本与环境维护在不产生交付物时不在适用范围内，这类工作的结论按 `docs/process` 的流程文件处理（MX-QA-01）。

本规范的位置是契约之后、验收之前。上游输入是契约表的测试列与已经冻结的判据，测试列只引用其他列的编号与判据，不复制它们的字段。下游输出给验收的证据索引与四值状态，复盘阶段按同一份状态统计通过率、返工原因与不稳定用例数量。契约表的列数以 [`TASK-MATRIX.md`](../TASK-MATRIX.md) 第 0 节的裁决为准，该节当前写五列并将四列写法废止，[`SPEC-STANDARD.md`](../../process/SPEC-STANDARD.md) 第 4.1 节仍写四列；本文只接测试列，不依赖其他列的数量，两处口径的差异由 lead 裁决后同步（MX-QA-02）。

本阶段的完成标志是三件产物齐备。测试计划增量写清每条 TC 的编号、通道、判据、脚本、证据与状态，夹具清单写清每条用例依赖的输入与生成方式，证据索引写清每份证据的位置、命令与可复跑性。三件产物缺一件即按未完成计，验收不得以代码已读或功能已手动确认替代（MX-QA-03）。

本规范不裁决产品口径。测试中发现产品 spec 与实现不一致时，登记到 test-plan 的待裁项，交产品与验收裁决，测试不改写 AC 迁就实现，也不在证据里写“按现状通过”（MX-QA-04）。本阶段的结论只使用 `pass`、`partial`、`missing`、`blocked` 四个值，四个值之外的说法一律按非法状态处理；`pass` 表示该 AC 的主路径与已声明负路径都有可复跑证据且本轮通过，`partial` 表示部分分支没有断言，`missing` 表示没有自动化用例或实现不存在，`blocked` 表示外部条件未满足（MX-QA-05）。

下游按用途取用本阶段产物。验收取证据索引与四值状态做签字，复盘取四值计数、多次运行一致率、门禁失败次数与覆盖率趋势做度量。验收的入口条件是三件产物齐备且阻断门禁全过，未过门禁的变更不进入验收。下游不得改写证据内容，需要补验时新建轮次并保留旧证据（MX-QA-06）。

## 2 阶段步骤

测试阶段按判据接收、用例设计、脚本实现、执行、留证、回填状态六步推进，六步顺序固定，每一步写清输入、动作、产出与判定人。每一步都有检查点，检查点写已完成部分、未完成项与下一步，供换人或续做时无歧义接手。下表给出六步的最小形态，步骤内的具体测试方法在第 4 节与第 5 节展开。

| 步骤 | 输入 | 动作 | 产出 | 判定人 |
|---|---|---|---|---|
| 判据接收 | 契约表测试列、AC 六项、非目标与风险清单 | 逐条核对六项是否可判定，标出缺项与口径冲突，缺项退回契约阶段补齐 | 判据接收记录，写在测试计划增量首部 | 测试 owner 提出，验收确认 |
| 用例设计 | 判据接收记录、风险级别、等价类与边界值 | 一条 TC 对一条 AC，列正常、边界、错误、权限四类分支，选判定层与通道，写前置与夹具 | 测试计划增量的 TC 行 | 测试 owner 写，契约门复核 |
| 脚本实现 | TC 行、夹具、断言脚本契约 | 先写能因目标行为缺失而失败的断言，再实现或修实现，脚本输出一行 JSON 并写证据文件 | `scripts/ac/<AC-ID>.mjs`、夹具文件 | 实现者自验，测试 owner 复核 |
| 执行 | 已构建版本、环境参数、脚本 | 固定 buildId、端口、`SIMO_HOME`、浏览器与视口，按组运行，记录命令、开始时间与结束时间 | 运行日志、`.tmp/ac/<AC-ID>.json` | 执行者记录，验收抽跑 |
| 留证 | 运行日志、截图、测量 JSON、失败输出 | 每条 TC 至少一份证据，写命令、参数、时间、退出码与原始输出摘要，路径回填证据索引 | 证据索引 | 测试 owner 编，验收核 |
| 回填状态 | 证据索引、四值定义、原因码 | 写四值状态与原因码，更新 test-plan 矩阵、变更包 `evidence.md` 与复盘输入 | 更新后的 test-plan 与证据索引 | 测试 owner 写，验收签 |

判据接收发现六项缺失、判据只写到“正常”“合理”“尽快”这类无法测量的词、或 AC 与产品非目标冲突时，停在接收步骤，把问题退回契约阶段，不在测试阶段替产品补判据（MX-QA-07）。用例设计必须覆盖正常、边界、错误、权限四类分支，任一类不适用时写 `N/A：<理由>` 与批准人。缺少的分支使该 AC 最多记 `partial`，原因码按第 8 节填写，不得把只测主路径的用例记 `pass`（MX-QA-08）。脚本实现遵循先失败后通过的顺序，缺陷修复与高风险路径（核心纯逻辑、迁移、权限）先运行失败用例并保留失败输出，再改实现；其他路径至少在脚本首次运行时确认断言能因目标缺失而失败，禁止只写恒真断言（MX-QA-09）。

执行环境在运行前写定并写入证据。环境项包括被测构建的 buildId 或提交号、服务地址与端口、`SIMO_HOME`、浏览器版本与视口、操作系统与依赖运行时版本；换环境后必须重跑，不用旧环境的结果解释新环境（MX-QA-10）。证据在运行同轮生成，证据里的时间取运行真实开始与结束时间，事后补写的记录按缺失计；跨轮沿用旧证据时在状态列注明轮次与“未重跑”，并保留旧证据文件（MX-QA-11）。状态回填在当轮完成，矩阵行、脚本文件、证据文件与变更包状态四处必须一致，任何一处缺失按 `missing` 计，回填后跑一次覆盖统计确认没有孤立 TC（MX-QA-12）。

每一步的预计时长不超过 20 分钟，到点没有产出时停在检查点并报卡点，不以继续运行代替判断（MX-QA-13）。用例作者与判定人分离，实现者可以跑自验并把输出写进证据，验收独立抽跑并签字，同一人不得既写用例又给自己的用例签通过（MX-QA-14）。检查点与状态回填同时更新，派单方按检查点判断是否可以进入下一步，跨会话交接以检查点文件为准。

重构的等价性证据分前后两组运行，两组在同一用例集版本上产生。基线组在契约冻结后、实现开始前运行，运行前记录重构前提交号、运行命令、环境与用例集版本；对照组在实现完成后用同一命令与同一用例集运行，环境按 MX-QA-10 重新写定并写进证据。两组证据编号在同一变更内连续编，基线组用 `E-<AC-ID>-B<NN>`，对照组用 `E-<AC-ID>-A<NN>`，同一行为清单项的两组编号写进同一行，证据索引的轮次列分别写 `B` 与 `A`。基线组由测试 owner 执行、验收复核，对照组由实现者执行、测试 owner 复核，两组执行人不得为同一人；某行为项只有一组证据或两组不在同一用例集版本上时按 `missing` 计，等价结论不成立（MX-QA-57）。

## 3 必产出文件与字段

测试阶段的三件产物是测试计划增量、夹具清单与证据索引。三件产物都落在文件里，字段留空按缺失计，写 `N/A` 时必须带理由与批准人。本节给出每个字段的写法与缺失后果，字段名与既有 [`specs/test/P1-CONV/test-plan.md`](../../../specs/test/P1-CONV/test-plan.md) 的矩阵列保持兼容。对应关系是通道取既有类型列的判定层，自动化位置拆成脚本路径与证据路径，证据列指向证据索引。

测试计划增量接在 `specs/test/<域>/test-plan.md` 的既有矩阵之后，不另开“每功能一测试 spec”。矩阵之前保留风险清单，清单至少列可能性与影响两列并按高、中、低三档打分，矩阵的风险级别字段从清单取值，高风险点增加测试深度与回归频率。每条 TC 至少写以下字段。

| 字段 | 必填 | 写法 | 缺失后果 |
|---|---|---|---|
| TC 编号 | 是 | `TC-<域前缀>-<三位序号>`，例如 `TC-P1-CONV-055`；负路径用 `-N` 后缀，不改主编号 | 无法定位用例，按 missing 计 |
| AC 编号 | 是 | 一条 TC 只写一条 AC，编号与产品 spec 一致 | 覆盖统计无法归集 |
| 通道 | 是 | 组件、接口、集成、端到端、人工，可多选；判定层只写一层 | 层归属不明，证据不成立 |
| 判据 | 是 | 引用 AC 的 Trigger、Observe、Criterion、Script、Owner、环境六项，不另写一套 | 判据不可判定 |
| 脚本路径 | 是 | `scripts/ac/<AC-ID>.mjs`，或 `N/A：<理由>` 加人工动作 | 无脚本且无人工判据，按 missing 计 |
| 证据路径 | 是 | 脚本证据写 `.tmp/ac/<AC-ID>.json`；验收级证据写 `docs/testing/<文件>` | 无法复算，不得 pass |
| 四值状态 | 是 | `pass`、`partial`、`missing`、`blocked` 四选一 | 非法状态词按缺失计 |
| 判定人 | 是 | `自动` 或 `人工:<动作>`，写到执行判定的角色，与用例作者分离 | 无法确认谁判定 |
| 环境 | 是 | 本轮运行的 buildId、地址、浏览器、视口、`SIMO_HOME`，跨轮重跑时更新 | 证据不可复算 |
| 原因码 | 条件必填 | 非 `pass` 时按第 8 节写七码之一与解除条件 | 原因不明，按缺失计 |
| 运行记录 | 是 | 命令、buildId 或提交号、开始与结束时间、结果摘要 | 证据不可复跑 |
| 风险级别 | 是 | 高、中、低三档，可能性与影响各按三档打分，取两者中较高的一档 | 无法确定回归频率 |
| 夹具引用 | 条件必填 | 集成与端到端用例写夹具 ID，单元与组件用例可写 `N/A：<理由>` | 输入不可重建 |
| 去重键 | 条件必填 | 重复消息类用例写会话 ID、后端消息 ID 与序号三元组，三项与当时的消息表行数、WS 帧序号、界面节点数一起记录；其他用例写 `N/A：<理由>` | 无法判断哪条判据有效 |
| 缺口登记 | 条件必填 | 未覆盖分支、原因码、解除条件与到期日，接在矩阵后的缺口表 | 复盘无法统计缺口 |

夹具清单单独成表，可以写在 test-plan 的夹具节，也可以写在 `specs/test/<域>/fixtures/` 的说明文件里。夹具清单与 TC 行同轮更新，避免夹具版本与断言版本错位。每条夹具写清以下字段。

| 字段 | 必填 | 写法 |
|---|---|---|
| 夹具 ID | 是 | `FX-<域前缀>-<序号>`，与 TC 行互相引用 |
| 路径 | 是 | 仓库相对路径，例如 `specs/test/P1-CONV/fixtures/task/batch-10.json` |
| 覆盖 TC | 是 | 列出使用该夹具的 TC 编号，空夹具也要写覆盖关系 |
| 生成命令 | 是 | 可重复执行的命令与参数，生成结果确定 |
| 校验命令 | 是 | 比对文件名、字节数、校验和或字段的检查命令 |
| 关键字段 | 是 | 决定断言结果的字段清单，例如条数、状态、时间戳基准 |
| owner | 是 | 维护夹具的角色或姓名，变更时由 owner 复核 |
| 失效条件 | 是 | 产品口径、字段结构或构建版本变化时触发重做 |

证据索引登记每份证据的来源与可复跑性，写在 test-plan 的证据节，验收轮次可另建 `docs/testing/EVIDENCE-<域>-<日期>.md`，变更包 `evidence.md` 引用该索引。证据索引按轮次追加，不覆盖上一轮的行。索引中的路径必须能在仓库里直接打开。

证据索引的字段、类型与判定值以 `MOXIAN.md` 表 9-2 为唯一来源，本节不另列表。十五个字段依次为证据编号、AC 编号、证据类型、路径、生成命令、生成时间、判定人、判定结果、未验证原因码、关联任务卡、轮次、可复跑、构建版本、失效标记与备注；证据类型取断言脚本、单元测试日志、接口响应、集成日志、端到端截图、人工记录六类；判定结果取 `pass`、`partial`、`missing`、`blocked` 四值。填写示例与路径规范见 `docs/framework/templates/evidence-index.md`。

TC 编号按域连续分配，新增编号接在该域最大号之后，删除或撤销的编号保留不复用，重排编号按违规处理（MX-QA-15）。一个 TC 只覆盖一条 AC，一条 AC 可以有多条 TC，负路径的 TC 用 `-N` 后缀与主编号关联；矩阵里出现重复 TC 或同一 TC 挂两条 AC 时，覆盖统计按无效处理（MX-QA-16）。编号与 AC 的对应关系写进矩阵列，覆盖统计按该列归集。

夹具必须可确定重建。夹具不读正式数据目录、不依赖当前时间与随机数、不访问外部网络，时间类字段以固定基准写入，需要相对当前时间时写基准与偏移量，由脚本在运行时重算并记录实际值，随机输入使用固定种子并记录种子值（MX-QA-17）。夹具与用例必须对得上，TC 行引用的夹具 ID 在夹具清单中存在，夹具覆盖的条数、状态与断言读取的字段一致，夹具变更后重跑受影响的 TC 并更新证据（MX-QA-18）。夹具的校验命令与结果写进证据索引，重跑时先校验夹具再跑断言。

证据文件按固定位置命名。断言脚本证据写 `.tmp/ac/<AC-ID>.json`，由脚本或 `run-ac.mjs` 生成；截图、测量 JSON 与人工记录写 `docs/testing/` 下带日期的文件，文件名含 TC 或 AC 编号（MX-QA-19）。证据只追加不覆盖，修正证据时保留旧文件并在新文件或索引里注明替代关系，删除证据按违规处理，历史记录供复盘与事故回查（MX-QA-20）。同名证据以索引的轮次列区分，落盘前检查目标路径是否已存在。

三件产物必须互相引用成闭环。test-plan 行指向脚本与证据，脚本产出证据，证据索引回指 AC 与 TC，状态列与证据结果一致，闭环断开的位置按 `missing` 计（MX-QA-21）。核对顺序是先看 test-plan 行，再看脚本与证据文件，最后看状态列与缺口登记。任一处断开时先在证据索引备注列登记，再回填状态并重跑覆盖统计。

金额计算、解析与状态机三类核心纯逻辑在功能用例之外另写属性用例，属性用例跑在第 5 节的单元层。输入生成用固定种子的随机循环加表驱动，不引入第三方生成器库，种子值与输入组数作为脚本参数写进 TC 行的运行记录，实际种子回填证据索引；每条属性至少生成 100 组输入，属性写成对任意输入恒成立的不变量，例如金额合计等于分项之和、序列化后再解析的结果与原值相等、任意事件序列执行后状态仍属于合法集合。失败时执行收缩，逐次删除字段、缩短列表或缩小数值，直到输入仍失败而任意再删一项即通过为止，收缩后的最小反例写进证据并固化为一条回归 TC，没有失败时不写收缩记录（MX-QA-55；对应候选 1.4）。

自动化用例稳定后按章程补探索性测试，一次章程一个时间盒，时长不超过 60 分钟。章程写任务、时间盒、关注区域、风险假设与执行人五项，关注区域从第 3 节风险清单的高风险项取；会话记录逐条写时间、操作、观察、判定与缺陷编号，章程与记录落 `docs/testing/EXPLOR-<YYYYMMDD>-<域>.md`，模板 `docs/process/templates/exploratory.md` 未建时按本节字段手写。会话中发现的问题登记到 test-plan 的缺口表与缺口登记列，缺陷按缺陷流程建 TC，已冻结的 TC 状态不因探索结果改动；章程不设覆盖率指标，不产生 `pass` 状态（MX-QA-56；对应候选 2.5）。

数据迁移与批量导入的对账抽样统一按 `MOXIAN.md` MX-9-25 执行，本文件不另定总体阈值、样本量、抽样方法、随机种子与失败判定。抽样记录写进 test-plan 的抽样节与证据索引，字段名按 MX-9-25 的八项，命中行数、不一致行数与不一致字段清单的填写口径也按该条。任一样本出现差异时按 MX-9-25 扩到全量并按回滚触发条件处理，缺记录或只写「已抽样核对」时证据门判不通过（MX-QA-58）。

## 4 判据写法

一条可判定的判据由 Trigger、Observe、Criterion、Script、Owner、环境六项组成，六项缺一项不得冻结。前五项沿用 [`SPEC-STANDARD.md`](../../process/SPEC-STANDARD.md) 第 2.3 节的五段式，环境项是本规范补的第六项，用来回答在什么构建、什么机器、什么数据上判。判据写在产品 spec 的 AC 字段与 test-plan 的 TC 行里，两处内容一致，test-plan 不另立一套标准。Owner 写判定方式，判定人是执行判定的角色，两个字段分开写，不合并。

| 项 | 必填内容 | 写法 | 反例 |
|---|---|---|---|
| Trigger | 触发事件或请求，加前置数据与视口 | `pointerup` 落在 `.tl-track` 任意纵向位置；前置为 `main` 会话加 2 个子会话 | “点击时间轴时” |
| Observe | 可测量的对象与取值来源 | `.session-count` 的文本、HTTP 状态码与 `error.code`、数据库行的字段值、日志中的帧序号 | “界面显示正常” |
| Criterion | 比较符、数值、单位、容差与时间窗口 | 18 个采样点偏差为 `0`，列外 `1px` 不触发，点击后 `900ms` 内完成定位 | “响应要及时” |
| Script | 可执行脚本路径，或带理由的人工动作 | `scripts/ac/AC-CONV-007-02.mjs`；无脚本时写 `N/A：<理由>` 与 `人工:<动作>` | “已有测试覆盖” |
| Owner | 自动或人工加动作 | `自动`；`人工:目视对齐与底色` | “测试同学” |
| 环境 | 构建、地址、系统、浏览器、视口、数据根 | 8787、buildId `mwrpos0p-d8dkh`、Chrome 120、1600×1000、`SIMO_HOME=data` | “本机环境” |

判据六项必须能由第三方照写复算，Trigger 要能由脚本构造，Observe 要落到稳定锚点（优先 `data-*`，禁止 `nth-child`），Criterion 要带比较符、数值、单位与容差，Script 要指向真实文件或写明人工动作，Owner 要写到人或角色，环境要写到可重建（MX-QA-22）。判据里出现“正常”“合理”“较快”“友好”“基本可用”这类无法测量的词时不得冻结，无法给出数值的观感类判据改写为人工判据，写清判定动作、判定人与可对照的基线图（MX-QA-23）。判据冻结后只允许改脚本实现，不允许在测试阶段放宽 Criterion 或更换 Observe；确需改判据时回契约门重新冻结，写明原因、影响范围与已产生证据的处置方式（MX-QA-24）。

Given、When、Then 只作验收用例的书写格式，执行落到 Playwright、Go 测试、Vitest 或 `scripts/ac/` 脚本，不引入 Cucumber 与 feature 文件层；GWT 句子里的 When 对应 Trigger，Then 对应 Observe 与 Criterion（MX-QA-25）。实例化需求里的关键例子经业务确认后才能进判据，智能体生成的例子先标“待确认”，确认前只作设计参考，不写进 AC，也不作为 `pass` 的依据（MX-QA-26）。示例里出现新的产品口径时回产品裁决，不在判据里用实现现状反推业务规则。

以下三条正例的六项齐全，可以直接冻结。

- 正例一：`Trigger` 为 `pointerup` 落在 `.tl-track` 任意纵向位置，`Observe` 为点击后 `900ms` 采样目标消息是否进入视口且 active 等于最近刻度，`Criterion` 为 18 个采样点偏差 `0`、列外 `1px` 不触发，`Script` 为 `scripts/ac/AC-CONV-007-02.mjs`，`Owner` 为 `自动`，环境为 8787、buildId `mwrpos0p-d8dkh`、Chrome 120、1600×1000、`SIMO_HOME=data`。
- 正例二：`Trigger` 为对话流式输出中按下停止，`Observe` 为上游 SSE 的 `context` 取消时间、停止后 `reply.delta` 与 `message.delta` 的帧数、数据库消息状态，`Criterion` 为停止帧后 `10ms` 内取消、之后 delta 为 `0`、状态为 `retracted`，`Script` 为 `scripts/ac/AC-CONV-005-02.mjs`，`Owner` 为 `自动`，环境为假上游 `127.0.0.1:8790`、隔离 `SIMO_HOME`、后端 8789。
- 正例三：`Trigger` 为携带 `If-None-Match` 请求 `/api/sessions/main/spec-projection?taskLimit=3`，`Observe` 为响应状态、响应体字节数、`ETag` 与 `Cache-Control`，`Criterion` 为首次 `200` 且 `ETag` 形如 `"spec-<16 位十六进制>"`、条件请求回 `304`、响应体 `0` 字节、`ETag` 与 `Cache-Control: no-cache` 保持，`Script` 为 `scripts/ac/AC-CONV-008-04.mjs`，`Owner` 为 `自动`，环境为 8787 与 buildId `mwrpos0p-d8dkh`。

以下三条反例的缺陷各不相同，按表可判为不可冻结。

- 反例一：“时间轴点击要灵敏，用户点了就能跳过去。”这句话缺 Observe 与 Criterion，没有可测量的对象、数值与时间窗口，也没有写环境，换一个人、换一档视口会得到不同结论。
- 反例二：“前端已有单测，逻辑上应该通过。”这句话缺 Script、Owner 与证据，已有测试覆盖的是别的行为，没有运行记录与退出码，“应该通过”不能作为状态。
- 反例三：`Criterion` 写“三次运行中任意一次通过即算通过”。这条判据把多次运行的最好结果当标准，掩盖了时序与数据依赖，正确写法是三次结果一致才算通过，不一致按不稳定用例隔离。

重复消息类问题的判定对象取三项：后端消息表行数、WS 事件帧序列与界面消息节点数。三项在同一操作序列下观测，操作序列写断线点、重连时点与等待窗口，三项读数同时记录，不许分轮补测。去重键取后端消息 ID，前端本地 ID 只作发送关联，不作去重依据；同一屏幕内同一后端消息 ID 出现两次即为重复，判定按三项中任意一项超限成立，三项同时通过才算通过。前后端使用同一元组（会话 ID、后端消息 ID、序号），任一侧改用自己的计数口径时证据门判不通过。用例覆盖重连一次、重连两次与补拉窗口边界三种情形，每种情形断言界面消息节点数与数据库行数相等，并核对 WS 帧序列中没有同一消息 ID 的两帧（MX-QA-59）。

### 4.1 时间类判据与测试时间预算

凡判据依赖时间流逝，包括超时、时限提醒、到期、退避、窗口与长任务存活，判定方式取时间推进，不使用真实等待。用例写清推进量、推进方式、期望发生什么与不期望发生什么四项，推进方式取可注入时钟、时间推进开关或等价的可控时间源，脚本在推进后读取状态与界面；禁止用“跑够 N 分钟”“等半小时再看”这类真实时长代替判定。单元、接口、集成与端到端四层都按本条执行，端到端层先推进时钟，再断言界面与数据（MX-QA-70）。真实等待只在没有注入办法时允许，用例须写明为什么不能注入、等待多久、由谁批准三项，缺一项按未验证处理，默认不允许真实等待。

时间源在实现里显式可替换，替换方式取接口注入或构建标签，测试时钟与生产时钟走同一接口。生产二进制不得包含测试时钟代码，测试构建与生产构建的差异写进构建说明与证据的环境项；只在测试代码里改写系统时间、实现仍直接读系统时钟的，不算可替换（MX-QA-71）。本条与 MX-QA-17 分工不同：MX-QA-17 管夹具不依赖当前时间、时间字段以固定基准加偏移重算，本条管判据如何证明时间流逝；两条同时适用，夹具用固定基准，判据用推进时钟。

测试即核对，真机求关键路径，复盘独立计。测试与脚本验收对既有实现做核对，不产生新设计，默认做成自动化，用一次构建、一次起服务、批量与并行执行完成，不在测试阶段补设计。真机实测必须做，只挑关键路径，用真实模型与真实安装路径跑一次，其余路径由脚本覆盖，不为凑数量重复真机。复盘是写作与判断，与测试分开，测试跑得快不缩短复盘，复盘也不占测试的时间预算；自动化测试、真机实测与复盘三者的耗时分别记录，不互相摊派（MX-QA-72）。

## 5 测试层选择

测试层按改动路径选择，原则是先选能判定该行为的最低层，低层判不了才升层。层与层之间是补充关系，一条 TC 只写一个判定层，其他层的观察写进证据但不改变判定。测试金字塔只作数量形状的参考，不设固定比例；前端取组件与集成优先的取向，具体配比按风险清单决定。六个机器层之外保留人工层，人工层只在机器不可替代时使用。

| 层 | 运行对象与命令 | 适用条件 | 成本 | 必须上的条件 | 不判定什么 |
|---|---|---|---|---|---|
| 单元 | Vitest 单文件、`go test ./<包>` | 纯函数、状态机、解析、金额与校验逻辑 | 秒级 | 改动落在纯逻辑、共享工具或状态转移上 | DOM 结构、真实网络、像素 |
| 组件 | Vitest 加 jsdom、Testing Library、MSW | DOM 结构、文案、`aria`、焦点顺序、入口计数、错误态 | 十秒级 | 改动落在界面、组件、交互反馈上 | 像素尺寸、真实滚动落点、真实网络 |
| 接口 | `scripts/ac/<AC-ID>.mjs` 或 `httptest` 直打真 handler | 状态码、错误码、字段形状、分页、权限、数据库不变量 | 秒级到十秒级，含服务启动 | 改动落在 HTTP 契约、错误码、权限或存储不变量上 | UI 呈现、端到端时序 |
| 集成 | 真后端加隔离 `SIMO_HOME` 加假上游 | 多进程、持久化、重启、流式、断线重连、迁移与对账 | 分钟级 | 行为跨进程、跨模块或依赖真实时序 | 像素几何、真实浏览器事件 |
| 端到端 | Playwright 或 CDP 加真浏览器 | 用户路径、像素几何、命中区、遮挡、刷新保持、真实点击 | 分钟级，需浏览器与后端 | 判据涉及像素、触控命中、遮挡或真实渲染 | 后端字段全量、所有错误码 |
| 命令行与产物 | `go build -trimpath ./tools/<工具名>` 后实跑子命令，产物校验比对 `--version`、文件哈希、页面数、字体与元数据 | 命令行程序、独立工具与 PDF 等交付产物的生成与校验 | 秒到分钟级 | 改动落在命令行入口、产物生成或产物校验上 | 界面呈现、后端字段全量 |
| 人工 | 人眼走查、真机、UAT 记录 | 观感对齐、真实输入法、真实设备与部署形态 | 分钟到小时 | 机器不可替代的观感、真机与外部设备行为 | 可重复的数值断言 |

纯逻辑与共享工具改动必须上单元层，单元层缺失时不得用集成或端到端替代，集成层通过只说明链路通，不说明分支覆盖（MX-QA-27）。界面、组件与交互反馈改动必须上组件层，判 DOM 结构、文案、`aria`、焦点顺序、按钮计数与四态（正常、空、加载、错误），组件层判不了的像素与滚动落点升到端到端（MX-QA-28）。HTTP 契约、错误码、权限与存储不变量必须上接口层，用真 handler 执行，前端 mock 只作组件层输入；接口层至少覆盖一条正常请求与一条负例，负例按错误码逐条落位（MX-QA-29）。

跨进程、持久化、重启、流式时序、断线重连、迁移与对账必须上集成层，用隔离数据根与假上游，不读写正式数据；集成层记录耗时、帧序号与数据库行，供对账与复盘（MX-QA-30）。像素几何、触控命中、遮挡、真实点击与刷新保持必须上端到端层，用真浏览器与真后端；端到端层不承担后端字段全量核对，字段核对回接口层（MX-QA-31）。端到端用 `page.route()` 或页面内 fetch 桩注入的失败只证明前端错误态，不能当作真实后端 413、403 或 500 的证据，真实后端状态由接口层或集成层证明，证据类型列必须写明注入方式（MX-QA-32）。

一条 TC 的判定层写定后，其他层的观察只作补充，补充层通过不改变判定层结果，补充层失败时按缺陷登记，不直接改状态（MX-QA-33）。契约层在 OpenAPI 唯一契约源落地前由接口层与前后端共享样例承担，契约源落地后增加提供者侧校验；序列化、渲染与命令行输出用 testdata 下的 golden 文件比对，更新 golden 单独执行并审查 diff（MX-QA-34）。新增测试工具与契约机制先过选型，当前不引入 Cypress、整树快照与 Pact，出现第二个消费者或现有工具无法覆盖的判据时重开选型并登记理由（MX-QA-35）。

性能优化与安全修复的测量层单独约定，性能按同一条件前后各不少于三次并取中位数，安全按攻击用例失效与相邻入口扫描判定。两类测量都写环境与样本量，不与其他层的通过混算，也不把一次测量写成稳定结论。层与层的成本按运行对象估算，单元与组件为秒到十秒级，接口为秒到十秒级，集成与端到端为分钟级，命令行与产物为秒到分钟级，人工为分钟到小时（MX-QA-36）。命令行与产物层的最小证据为命令全文、退出码、产物路径与版本或哈希输出四项，四项缺一按未验证处理，产物校验项按 `MOXIAN.md` 表 9-1 命令行与产物行执行（MX-9-04）。

断线与重连类用例在集成层与端到端层用固定夹具注入，不靠手工断网或关闭标签页。夹具固定断线点、重连次数与观测窗口三项：断线点在指定序号的消息帧之后注入一次，重连次数取一次与两次两组，观测窗口取重连完成后 5 秒，窗口内收到的帧全部记录。夹具按进程内代理或假上游实现，断线时关闭连接并丢弃后续帧，重连时重建连接并从续传水位补拉；每次注入记录断线时刻、重连时刻、补拉条数与首末帧序号四项，四项写进集成日志证据。夹具自身行为由脚本自检固定，三种注入各有一个通过样例，缺少样例的夹具按未验证处理，连接不稳定造成的失败不计入被测缺陷（MX-QA-60）。

### 5.1 授权与隔离矩阵

授权与隔离的用例按矩阵组织，矩阵维度取主体、租户、资源、动作与环境五维。主体写角色名与属性集合，租户写主体所属租户，资源写归属租户与资源状态，动作取读取、创建、修改、删除、导出五值，环境写请求时间、网络区域与设备标识三项。矩阵字段固定为用例号、主体角色、主体租户、资源归属租户、资源状态、动作、环境条件、期望结果、实际结果与证据路径十项，缺任一项的用例不计入矩阵。

用例数按端点与变更两级判定。每个涉及权限的端点至少 4 条：本租户内允许、本租户内拒绝、跨租户同标识拒绝、跨租户不同标识拒绝。每次变更的矩阵用例不少于 12 条，跨租户读取、写入、删除、导出四类各至少 1 条，每个角色对每个动作至少 1 条允许与 1 条拒绝。属性组合用两两组合裁剪，主体角色、动作与资源归属三者的两两组合必须全覆盖，裁剪掉的组合写进缺口表并写理由；跨租户四类为必做行，不参与裁剪。

跨租户用例按固定构造执行：建两个租户 A 与 B，用同一业务编号在 B 建一条资源，用 A 的凭据按该编号发起请求，断言返回 404 与 `not_found`，响应不含资源标题与归属信息，断言 B 的数据行数与内容未变。构造数据用测试夹具直接写入 B 的隔离数据根，不通过接口提前创建，避免把创建路径的缺陷带进权限用例。负例按错误码逐条落位，不只断言 403 或 404 的状态码，越权写入另断言数据库无新增行（MX-QA-61）。矩阵由测试 owner 起草、验收判定，鉴权与授权相关变更另由安全评审人复核，安全评审人按 `ROLES.md` MX-R-39 指派，复核结论写通过、有条件通过与不通过三值之一；矩阵缺必做行、跨租户构造缺一侧或判定人缺签字时证据门判不通过。矩阵记录按 `docs/framework/templates/tenant-isolation-checklist.md` 与 `docs/framework/templates/permission-policy-matrix.md` 填写。

### 5.2 弱网档位与冲突合并

弱网用例固定三档参数，参数写进 test-plan 与集成日志，不按执行者手感临时调整。第一档 RTT 取 400 毫秒、带宽取 1 Mbps、丢包率取 2%；第二档 RTT 取 1000 毫秒、带宽取 200 kbps、丢包率取 10%；第三档为离线，丢包率 100%，持续 30 秒后恢复。三档参数按 `MOXIAN.md` 表 5-2 的五档网络条件取值：可用与 4G 两档取第一档；3G 取第二档；2G 取第二档参数，并在用例末段叠加第三档的离线 30 秒与恢复动作；断网取第三档。档位名与所用参数组写进用例标题与 test-plan 的运行条件字段，同一用例跨两档时按两段分别记录。注入用进程内代理或可控假上游实现，按固定参数延迟、限速与丢包，不用手工断网、关闭标签页与系统级限速工具。

实测统一由 `scripts/measure-net.mjs` 产出，档位对应的模式、参数与判定值见下表。脚本退出码 0 表示达标，2 表示超阈值，1 表示连接失败，3 表示参数或环境错误；1 与 3 先修注入代理或测量目标再重跑，不得改判定值迁就结果。实测值与设定值偏差超过 20% 时该档作废重跑。

| 档位 | 模式与参数 | 判定值 |
|---|---|---|
| 可用、4G | `latency --count 20 --timeout 3000`；`loss --count 50 --timeout 3000` | `--threshold p95=480`（400 毫秒加 20% 容差）；`--threshold loss=8`（设定 2%，50 次允许 4 次失败） |
| 3G | `latency --count 20 --timeout 3000`；`loss --count 50 --timeout 3000` | `--threshold p95=1200`（1000 毫秒加 20% 容差）；`--threshold loss=20`（设定 10%，50 次允许 10 次失败） |
| 2G | 前段同 3G；末段 `loss --count 10 --timeout 2000`，注入切到丢包 100% | 前段 `--threshold p95=1200` 与 `--threshold loss=20` 同时成立；末段 `--threshold loss>=99`（注入 100%，丢包不低于 99% 才算断网生效） |
| 断网 | `loss --count 10 --timeout 2000`，丢包 100% | `--threshold loss>=99`，且失败原因只出现 `timeout` 或 `refused`；出现 `dns` 判注入未生效 |

2G 末段与断网档的 10 次超时合计约 20 秒，须落在 30 秒离线窗口内；超时参数不得放大到窗口之外，否则恢复后的成功连接会稀释丢包率，`loss>=99` 不再成立。

外部依赖的吞吐另跑 `bandwidth` 模式，目标须为可回显的 TCP 端点，命令为 `bandwidth --size 65536 --timeout 15000 --threshold mbps>=<约定值>`，约定值取依赖方承诺带宽的 80%。目标不接受写入或不回显时脚本退 3 并输出“该模式需要可写目标”，该次只登记延迟与丢包证据，不把吞吐记为通过。

每次测量落一份 JSON，命令写 `--out docs/testing/measure-net-<TC 或 AC 编号>-<4g、3g、2g 或 offline>-<模式>-<YYYYMMDD-HHmm>.json`，目录不存在时脚本自动创建，重复测量另起文件名且不覆盖旧文件（MX-QA-20）。弱网测量证据固定六项：执行机器、网络档位与注入参数、脚本模式与样本量、测得的 p50 与 p95（`loss` 模式为丢包百分比与失败原因分布）、判定值对照与退出码、输出文件路径与生成时间。这六项连同离线时长、收敛结果与合并记录，满足 MX-9-30 的四项证据要求，缺一项按证据不完整处理。

设备清单最低覆盖两种网络形态与一种低性能设备：网络形态取 Wi-Fi 与移动网络，低性能设备取内存不超过 2 GB 或 CPU 核心数不超过 2 的设备；清单缺任一类时证据门按证据不完整判不通过，清单字段与记录口径按 `MOXIAN.md` MX-10-04 的真机五项执行。

离线与缓存断言四项：断网后已缓存列表在 100 毫秒内渲染出旧值并显示离线标识，刷新页面后队列从 IndexedDB 恢复且 `inflight` 行回到 `pending`，恢复网络后按 1 秒、2 秒、4 秒、8 秒的间隔重试且最多 4 次，队列清空后界面数据与服务端一致。缓存版本升级用例把结构版本从 1 改到 2，断言旧键迁移成功或该键被清空后重新拉取，迁移失败不影响其他键。

冲突合并的判定对象取实体版本号、字段级取值、队列顺序与重复条数四项，去重键取 `opId` 与后端消息 ID 的组合。用例覆盖双方改同一字段、双方改不同字段、一方删除另一方修改三种情形。通过条件为本地草稿不丢失、服务端数据不被静默覆盖、服务端版本号只递增一次、重新加载后界面与服务端一致；任一项不满足即判失败，按缺陷修复流程处理（MX-QA-62）。

### 5.3 运行时阈值、故障注入与放量判据

运行时可观测断言按三组执行。指标组从 `GET /metrics` 取文本格式输出，逐条断言指标名、单位、标签与数值，指标名与单位取 `domains/backend.md` MX-BE-71 与契约表可观测性列，缺标签或单位不一致按失败计。追踪组断言同一请求的 `trace_id` 为 32 位小写十六进制、span 名称形如 `<服务>.<操作>`、采样率与导出方式与契约一致，导出文件含 span 起止时间与父 span 标识。告警组注入一次阈值越界，断言告警在 60 秒内到达指定通知渠道，记录规则名、级别、当前值、窗口与抑制条件五项。

告警判定窗口取 1 分钟，连续 3 个窗口越界才算触发，单窗口越界只登记不告警；抑制条件命中时不重复通知，抑制原因写进告警记录。阈值取请求成功率 99.5%、首帧延迟 p95 3000 毫秒、写请求延迟 p95 800 毫秒，三项与 MX-BE-71 一致，测试不另设一套数值（MX-QA-63）。

指标异常注入用假监控源或测试端点构造，注入序列固定为正常 3 个窗口、越界 3 个窗口、恢复 1 个窗口，每个窗口写开始时间、指标值与判定。自动回滚的判定条件为越界后 2 个观测窗口内触发回滚，记录决策时间、回滚命令、回滚后健康检查与数据对账四项；超过 2 个窗口未触发即判失败。灰度放量按 1%、10%、50%、100% 四档执行，每档观察窗口不少于 5 分钟，回滚阈值取错误率超过 1% 或 p95 超过基线 2 倍并连续命中 3 个窗口，放量记录写档位、起止时间、观察窗口、指标值、回滚次数与最终状态六项，结束状态只取全量生效或已回滚两值（MX-QA-64）。

外部依赖故障按注入点与失败序列执行。注入点取请求发出前、响应头返回后与流式响应中途三处，失败序列取 429 带 `Retry-After`、连续 500 三次、超时、连接重置四组。假上游提供控制端点 `POST /__admin/failures`，请求体写失败序列、生效次数与恢复时间，测试按序列逐组执行。断言重试次数与退避时刻落在 200 毫秒、400 毫秒、800 毫秒附近，抖动偏差不超过 20%；连续 5 次失败后熔断打开，30 秒后进入半开并允许 3 次探测，探测成功才关闭；降级动作按 MX-BE-82 的字段返回缓存值、503 或排队。观测窗口取 60 秒，窗口内的请求数、失败数、重试数、熔断状态与降级次数写进证据（MX-QA-65）。

### 5.4 恢复演练判据

恢复演练固定四个目标与四项验证。目标取 RTO 不超过 30 分钟、RPO 不超过 5 分钟、恢复后数据一致、回退到原主库可执行。验证一为备份可恢复，从最近一次全量备份与增量日志恢复到隔离目录，记录备份时间、恢复开始与结束时间、恢复耗时；验证二为数据一致，比对关键表行数、主键范围、校验和与引用完整性四项，四项全过才算一致；验证三为业务可用，启动恢复实例后跑健康检查与一次关键业务命令，两项退出码为 0；验证四为回退条件，写清切换后数据分叉、复制延迟超过 5 分钟与完整性校验失败三种情形，任一出现时停止切换并回退原主库。

演练由后端 owner 执行、验收判定，产品确认 RTO 与 RPO 目标；四项验证缺一项或耗时超过目标时演练判失败，登记 `R-DRILL` 与原因，修复后重跑整轮，不引用上一轮数字。证据写恢复命令、起止时间、行数与校验和、业务命令输出、回退判据五组，数字与目标放在同一张表里对照（MX-QA-66）。

### 5.5 第三方扩展夹具与插件隔离

插件夹具按宿主版本、插件版本与接口版本三列矩阵组织，矩阵至少覆盖 3 个宿主版本、2 个插件版本与 2 个接口版本，共 12 个组合。宿主版本取当前版本、上一小版本与下一大版本预览，插件版本取声明的最低兼容版本与最新版本，接口版本取当前版本与上一个仍受支持的版本。每个组合记录宿主版本号、插件版本号、接口版本号、加载结果、清单一致性与重建哈希六项，清单一致指插件 manifest 的入口、权限与版本字段与实际加载一致，重建哈希指同一组合连续构建两次得到同一哈希。夹具放 `testdata/plugins/`，构造方式写进测试说明，缺少任一组合时矩阵按不完整计（MX-QA-67）。

插件隔离与恶意样本用例覆盖崩溃、超时、资源超限与越权四类。崩溃用例让插件在初始化与调用两个时点各抛一次异常，断言宿主进程存活、插件被卸载、错误帧返回且宿主可继续处理下一请求。超时用例让插件阻塞 2 秒，断言宿主在 2 秒内终止调用并返回超时错误。资源超限用例把插件内存推到 256 MB、CPU 占用推到 80% 持续 5 秒，断言宿主按限额终止插件且不拖垮主进程。越权用例取路径穿越 `../../`、读取宿主数据根外的文件、发起外部网络请求与创建子进程四类，断言全部被拒绝且宿主无文件写出。安全评审按恶意样本清单逐条核对，清单至少 8 条，扫描权限声明与实际调用的一致性，结论写进证据与安全评审记录（MX-QA-68）。

### 5.6 大数据量核对抽样

大数据量核对按分层抽样执行，层取分片、租户与表三类，层内按主键哈希均匀抽取。样本量取 385 条作为 95% 置信水平与 5% 误差下的最小样本，总体不足 3850 条时按总体的 10% 抽取且不少于 200 条；删除验证的样本量同样取 385 条，从删除清单中按主键哈希抽取。抽样用固定随机种子与 SQL 哈希条件实现，例如 `WHERE hash(key) % 100 < 10`，不使用 `ORDER BY RANDOM()`，种子值写进 test-plan 与证据。

核对项写源端与目标端的行数、主键范围、字段分布与校验和四类，行数按分片与租户分组求和后与源端总数比对，不只比对全表总数。任一样本出现字段差异时把样本扩到该层全量并重跑，层内仍有差异时停止放量并按回滚条件处理。抽样记录写总体、层、样本量、抽样方法、随机种子、命中行数、不一致行数与不一致字段清单八项，字段口径按 `MOXIAN.md` MX-9-25 执行，本文件只补分层与分组求和两项（MX-QA-69）。抽样与删除验证记录按 `docs/framework/templates/compliance-disposal-record.md` 填写。

## 6 门禁

测试阶段的阻断门禁按顺序执行，前一道不过不进下一道。门禁分阻断、告警、夜间三档，阻断档只收 `error` 级规则与人工阻断检查，告警档登记后放行，夜间档跑覆盖率趋势与视觉基线，不参与单次交付判定。判据门与全过门由测试 owner 执行、验收复核，证据门、回填门与签字门由验收判定，语言门与治理门由派单方执行，不稳定门与覆盖率门由测试 owner 执行。

| 门禁 | 档位 | 检查动作 | 通过标准 | 不通过后果 |
|---|---|---|---|---|
| 判据门 | 阻断 | 人工核对 AC 六项与脚本或人工判据 | 六项齐全，每条 AC 有脚本或人工判据 | 不得进入测试执行 |
| 脚本自检门 | 阻断 | `run-ac.mjs --self-test` | 末行 `SELF-TEST PASS`，退出码 `0` | 脚本框架不可信，停止执行 |
| 全过门 | 阻断 | `run-ac.mjs --json` | 运行集合 `total` 大于 `0`，`pass` 等于 `total`，`fail`、`timeout`、`error` 均为 `0`，退出码 `0` | 不得进入验收 |
| 证据门 | 阻断 | 核对证据索引与文件 | 每条 `pass` 的 TC 有非空证据，非 `pass` 的 TC 有原因码与缺口登记，命令可复跑 | 缺证据的条目不得写 `pass` |
| 不稳定门 | 阻断 | 同环境同参数复跑三次 | 三次结果一致，退出码一致 | 不一致的用例隔离，不参与发布判定 |
| 覆盖率门 | 夜间 | `test:coverage` 与 `go test -cover` | 生成行、分支、函数三类统计与未覆盖清单 | 只登记趋势，不阻断交付 |
| 回填门 | 阻断 | 矩阵、脚本、证据、变更包四处核对 | 四处一致，矩阵无孤立行，证据无孤立记录 | 状态回填不完整，退回测试阶段 |
| 语言门 | 阻断 | `check-spec-language.mjs` | error 为 `0`，warning 逐条登记原因 | 不得交付 |
| 治理门 | 阻断 | `check-sdd.mjs` 与 `check-trace.mjs` | 末行 `PASS`，退出码 `0` | 变更包与追溯不完整，不得收口 |
| 签字门 | 阻断 | 核对用例作者与验收签字人 | 两者不重合，判定人符合 AC 的 Owner | 自签的 AC 退回验收 |

阻断门禁按以下命令执行，工作目录为仓库根，前端与后端命令先切换到对应目录。代码块里的 `$AC_LIST` 是本轮范围的 AC 编号逗号列表，例如 `AC-CONV-007-02,AC-CONV-008-04`。运行前先按本轮矩阵列生成该列表，不把全库脚本当成本轮范围。

```powershell
$NODE = 'E:\dsh_home\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe'
$AC_LIST = 'AC-CONV-007-02,AC-CONV-008-04'
& $NODE scripts/run-ac.mjs --self-test
& $NODE scripts/run-ac.mjs --only $AC_LIST --json
& $NODE scripts/ac/AC-CONV-007-02.mjs --base-url http://127.0.0.1:8787
& $NODE scripts/check-spec-language.mjs
& $NODE scripts/check-sdd.mjs
& $NODE scripts/check-trace.mjs
```

```powershell
cd frontend
& $NODE node_modules/vitest/vitest.mjs run --pool=threads
& $NODE node_modules/vitest/vitest.mjs run --coverage
cd ..\backend
..\toolchain\go.ps1 test ./... -count=1 -timeout 300s
..\toolchain\go.ps1 test ./... -count=1 -cover
```

脚本全过的定义是总数大于零且每条都通过。`run-ac.mjs` 在没有匹配脚本时输出“没有匹配的 AC 断言脚本”并返回 `0`，这个 `0` 不算通过，执行前用 `--only` 限定本轮范围并核对 `total` 与计划条数相等。全过门只检查本轮运行集合，运行集合由本轮必做 TC 中已有脚本的条目组成，`missing` 与 `blocked` 条目不在集合内，但必须在证据门登记原因码并经验收确认（MX-QA-37）。

`skipped`、`SKIP`、`blocked`、`partial` 都不计入 `pass`。新增跳过用例必须在 test-plan 登记原因码与解除条件，存量跳过项逐条列入基线清单，新出现的跳过项按门禁失败处理（MX-QA-38）。存量跳过项在清单里注明既有原因，不作为新门禁失败的豁免依据。

覆盖率只做趋势，不设阻断阈值；前端用 `test:coverage` 取行、分支、函数三类统计，后端用 `go test -cover` 取包级覆盖，未覆盖清单写进证据。增量覆盖率脚本尚未建立，当前按告警运行，升为阻断前先改 `FRAMEWORK.md` 第 3.4 节。该文件已停用，条款以墨线为准。变异抽检只对关键模块做人工抽检，存活体清单进复盘，不作门禁。覆盖率报告与用例通过记录分开存放，数字不替代断言（MX-QA-39）。

不稳定用例按三次复跑判定，命令为 `1..3 | ForEach-Object { & $NODE scripts/run-ac.mjs --only AC-CONV-007-02 --json | Tee-Object ".tmp/ac-flaky-$_.json" }`，每次保存一份输出。三次的 `counts` 与每条结果必须一致，不一致即标记为不稳定并移入隔离清单，写责任人与到期日。重试次数保持 `0`，不得用重试掩盖失败，隔离用例不参与发布判定（MX-QA-40）。

缺证据不得写 `pass`，截图、口头确认、日志片段与别人跑过的结果单独出现时不构成证据，证据必须能定位到 AC、命令、时间与输出（MX-QA-41）。`ac-coverage.mjs` 只检查脚本是否存在或是否写了人工判据，不检查脚本是否运行与证据是否落盘，因此它用于缺口盘点，不用于证据门禁的通过判定；盘点命令为 `& $NODE scripts/ac-coverage.mjs --json`，它有 `missing` 时退出 `1`，该退出码按缺口登记处理（MX-QA-42）。门禁结果写进变更包与本轮验收记录，按本轮范围与存量基线比对，存量基线逐条写进证据索引并带到期日，只有本轮新增失败阻断；阻断门禁失败时停在测试阶段，修完重跑全部门禁，不跳过失败项只跑其余项，告警项登记原因与到期日（MX-QA-43）。

退出码按统一口径解释，`0` 表示通过，`1` 表示失败或存在 error，`2` 表示参数或环境错误，`probe-cdp.mjs` 的 `3` 表示 CDP 环境不可用。非 `0` 一律不得写 `pass`，参数或环境错误按第 8 节原因码登记，失败按第 7 节拦截点定位。脚本自检失败时先修脚本，不把脚本错误记成被测缺陷（MX-QA-44）。

## 7 常见错误与拦截点

下表列出测试阶段反复出现的错误，每条给出典型表现、拦截点与检查动作。拦截点不过时按未完成计，不因为“已经解释过”放行；同一变更里同一错误出现两次以上，记入复盘并补脚本检查。错误按出现频次排列，新增错误先补表再改流程。

| 错误 | 典型表现 | 拦截点 | 检查动作 |
|---|---|---|---|
| 把 SKIP 当通过 | 汇总写“全部通过”，实际有一组 skipped | 全过门 | 读 `run-ac.mjs --json` 的 `counts` 与 Vitest 的 skipped 行，非零即拦 |
| 夹具与用例对不上 | 断言读的字段在夹具里不存在，或条数不一致 | 判据门 | 核对夹具覆盖表与断言字段，跑夹具校验命令 |
| 只测正例 | 只有成功路径，没有边界与错误分支 | 判据门 | 检查 TC 行的四类分支，缺类降为 `partial` |
| 证据不落文件 | 证据只写在对话或提交说明里 | 证据门 | 按索引逐条检查文件存在、非空、AC 匹配 |
| 复跑到绿 | 第一次失败，重复运行直到通过再记录 | 不稳定门 | 同环境三次一致才算通过，失败记录保留 |
| 用桩数据冒充真实后端 | 页面注入 500 后写“后端 500 已验证” | 证据门 | 看证据类型与注入方式，真实后端状态回接口或集成层 |
| 旧证据跨版本复用 | 引用上一构建的日志证明本构建 | 证据门 | 核对 buildId、提交号与时间，不一致要求重跑 |
| 空跑返回 0 判通过 | 没有匹配脚本也返回 0 | 全过门 | 要求 `total` 大于 `0` 且等于计划条数 |
| 覆盖率数字代替用例 | 覆盖率上升就写功能通过 | 覆盖率门 | 覆盖率只进夜间趋势，不看作用例通过 |
| 状态与证据不一致 | 矩阵写 `pass`，证据是 `fail` 或缺失 | 回填门 | 逐行比对矩阵状态与证据结果 |
| TC 编号复用或重排 | 删除旧 TC 后把号给新用例 | 回填门 | 编号唯一且只增，撤销号保留 |
| 判定人自签 | 实现者给自己的用例签通过 | 签字门 | 核对用例作者与签字人是否同一人 |

错误表之外的新错误按缺陷登记，不自行新增拦截规则；拦截规则需要新增时先改本文件并同步脚本，不在执行现场临时加判据（MX-QA-45）。拦截记录写进证据索引的备注列，写明拦在哪一道门、触发条件、处理人与处理结果，拦截记录不替代失败证据，修复后仍需按第 6 节重跑门禁（MX-QA-46）。同一错误连续两轮重复出现时，升级为流程问题并在复盘里给整改项。

## 8 未验证的原因码

未验证的条目只能写七种原因码之一，原因码解释状态，不改变状态。写法统一为“状态（原因码：事实；解除：条件）”，事实写可核对的一句话，解除条件写可验证的动作与验证人，不写“后续处理”这类没有动作的短语。事实部分写观察到的现象与数值，不写推测原因。

| 原因码 | 含义 | 适用状态 | 写法 | 解除条件 |
|---|---|---|---|---|
| `R-ENV` | 环境不可用，包括 CDP 端口无监听、浏览器无法启动、系统权限或沙箱限制 | `blocked` | `blocked（R-ENV：CDP 9223 无监听；解除：启动 headless Chrome 后复跑 AC-CONV-007-02）` | 环境恢复并留下启动日志 |
| `R-BUILD` | 被测构建未生成、未部署或启动失败 | `blocked` | `blocked（R-BUILD：目标构建未部署，当前实例 buildId 不符；解除：部署指定 buildId 后重跑）` | 部署完成且健康检查通过 |
| `R-SCRIPT` | 断言脚本或夹具未落盘、未通过自检、只占位未实现 | `missing` | `missing（R-SCRIPT：断言脚本与夹具待建；解除：脚本落盘并通过 run-ac 自检后复跑）` | 脚本存在且自检通过 |
| `R-EXT` | 外部服务不可达、凭据失效或第三方接口拒绝 | `blocked` | `blocked（R-EXT：厂商接口返回 403，凭据失效；解除：恢复凭据或按机制判据重写并获裁）` | 外部条件恢复或替代判据获裁 |
| `R-MANUAL` | 只能人工或真机判定，本轮没有执行人与记录 | `blocked` | `blocked（R-MANUAL：真实输入法未覆盖，需真机人工；解除：指定判定人执行并留截图与记录）` | 人工记录与截图落盘 |
| `R-SPEC` | 判据未冻结、未裁决，或两份文件对同一事实取值冲突 | `blocked` | `blocked（R-SPEC：判据与产品非目标冲突；解除：产品裁决后更新 AC 与 test-plan）` | 裁决结论写入文件 |
| `R-DRILL` | 恢复演练未通过：恢复目标未达标、备份不可恢复、切换后数据不一致或回退条件不成立 | `blocked` | `blocked（R-DRILL：RTO 实测 42 分钟超出 30 分钟目标；解除：修复后重跑整轮演练并留新证据）` | 演练通过并留恢复命令、起止时间、行数与校验和、业务命令输出与回退判据五组证据 |

原因码在 test-plan 的 TC 行、证据索引与变更包 `evidence.md` 三处保持一致，同一 AC 有多条未验证分支时写主原因码，其余分支在备注里逐条写事实，不写两个以上状态（MX-QA-47）。`R-SCRIPT` 对应 `missing`，其余六码对应 `blocked`；已经完成一部分分支的写 `partial`，并在备注里写未完成分支的原因码，状态与原因码不匹配时按非法状态处理（MX-QA-48）。解除条件必须可验证，解除后按原命令复跑，旧证据保留，新证据写新轮次，原因码连续两轮没有解除时上报派单方，按异常流程处理（MX-QA-49）。

能修的失败不得标 `blocked`。断言失败先定位是实现缺陷、脚本缺陷还是判据缺陷，属于实现或脚本缺陷的回原实现者修复，只有外部条件确实不满足时才使用原因码（MX-QA-50）。原因码变更时同步回填三处记录，并在复盘里统计各码出现次数与平均解除轮次；原因码不是免检通道，七码之外的写法按违规处理（MX-QA-51）。复盘统计原因码时区分首次出现与复发，复发次数单独列出。
