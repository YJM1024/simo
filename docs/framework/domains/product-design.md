增量覆盖率没有基线时，`scripts/check-incremental-coverage.mjs` 退出码 2 属待补，不算失败；先补 `frontend/coverage/coverage-final.json` 与 `backend/coverage.out` 基线，补出后按退出码 0 判，补基线路径见 `docs/framework/v2/BACKLOG.md` 的 B-16。

## 1 适用范围与位置

本文件规定产品列与设计列在墨线框架内怎么受理、怎么写需求、怎么写验收场景、怎么定设计契约、怎么定可访问性阈值，以及这些产出由谁判。前端实现、后端接口与测试执行按各自域文件判定，本文件只写它们要接住的输入。

本文件处在受理与契约之间。输入是用户请求、`docs/product/TREE.md` 的功能点与 `SOURCES.md` 的来源判定；输出是可冻结的判据、可核对的场景与可执行设计契约。判定单位是需求点：一个点的判据齐全才允许开工，缺一件按未冻结处理。

## 2 受理与立项

受理阶段把用户请求变成可判级的变更包，立项阶段把目标、范围与非目标写死。两阶段的产出不合格时后续所有判据都会失真，因此本节规则全部前移到开工之前执行，冻结后只允许按 MXV2-4-08 迁移状态。

本节对应 SOURCES 的 S-037 与 S-038 两条改造后采纳来源：故事地图给骨架与切片，INVEST 给需求点拆分自检。S-039 Job Stories 与 S-041 WSJF 不采纳，理由分别是与立项三句重复且无可核对判据、公开材料缺评分推导，两条只在文末承接表登记。

- 规则：写需求之前先登记变更包，受理记录写清六项结论，六项全成立后才允许写契约与拆卡；六项缺一的通知按未受理处理，不得进入契约阶段。
- 判据：受理记录六项各有结论行；变更包编号写在首部；需求先写、变更包后建的记录条数为 0。
- 执行：`script:node scripts/check-mapping.mjs --rule MXV2-4-01` 期望退出码 0
- 层级：L1
- 依据：MXV2-4-01、MXV2-4-02；S-032

### MXV2-PD-06 目标三句、非目标可判定、假设带后果

- 规则：目标写不超过三句，非目标写成能被判真假的句子，每条假设后面写一句后果；三类内容缺一类或缺后果时范围段不算写完。

## 3 需求句写法

需求句按 EARS 五句式分槽写，前置条件、触发与响应各占一槽。分槽的目的是让句子能被判真假：同一句话里出现两个响应、一个实现手段或一个没有数值的形容词，判据就无法冻结。

本节引用 S-035 EARS（采纳）与 S-025 29148 的九条需求特性（改造后采纳，只取清单作评审项）。两份来源共用的判据是句子可判，不引入第二套句式。

### MXV2-PD-13 需求句按 EARS 五句式分槽写

- 规则：每条需求句写成五种句式之一：普遍式写系统做什么，事件式写当某个触发发生时系统如何响应，状态式写处于某状态期间系统如何表现，可选式写带某特性时如何表现，不期望式写出现某情况时系统如何拒绝；前置条件、触发与响应三槽各出现一次。
- 判据：每条需求句能归入五句式之一；三槽各出现一次；归不进的句子数为 0。
- 执行：`ai-review:每条需求句能归入五句式之一`；谁判：判定员；误放行：未逐项核对“需求句按 EARS 五句式分槽写”即判通过；误拦截：证据已齐仍判不通过
- 层级：L1
- 依据：MXV2-6-05；S-035
- 适用：写需求句时；契约门评审需求句时。

### MXV2-PD-14 一条需求句只写一个响应

- 规则：一条需求句只描述系统的一个响应，出现两个独立响应时拆成两条并各自编号；同一响应附带的条件与例外写在同一句里，用分句承载。
- 判据：句内由“并且”“同时”连接出的独立响应数为 0；复合需求已拆成多条独立编号。
- 执行：`ai-review:逐句拆主干，确认一句话只有一个可观察响应`；谁判：撰写员；误放行：一句写“保存并通知”，实现只做保存也判通过；误拦截：把同一响应的两个观察点判为两个响应。
- 层级：L2
- 依据：MXV2-6-04；S-035
- 适用：写需求句与拆分需求时。

### MXV2-PD-15 需求句不写实现手段

- 规则：需求句只写用户可观察的行为与结果，不写组件名、库名、表名、接口路径与内部状态字段；实现手段写进设计列或技术方案，不写进产品需求。
- 判据：句内出现组件名、库名、表名或接口路径的条数为 0。
- 执行：`ai-review:逐句检索技术名词，确认只剩可观察行为`；谁判：撰写员；误放行：需求写成“用对话框组件弹出”，换实现即失效；误拦截：把用户可见的“下载文件”判为实现手段。
- 层级：L2
- 依据：MXV2-6-05；S-025
- 适用：写需求句与评审时。

### MXV2-PD-16 需求句的量化项带数值、单位与来源

- 规则：每个量化项写出数值、单位与阈值来源，阈值来源写清测量条件与批准人；没有来源的阈值不得写进需求句，只写成待确认项。
- 判据：每个量化项后跟数值与单位；每个阈值有来源与批准人；缺来源的量化项数为 0。
- 执行：`ai-review:每个量化项后跟数值与单位`；谁判：判定员；误放行：未逐项核对“需求句的量化项带数值、单位与来源”即判通过；误拦截：证据已齐仍判不通过
- 层级：L2
- 依据：MXV2-6-05、MXV2-7-02；S-036
- 适用：写含量化的需求句时。

### MXV2-PD-17 五个禁用词出现即按未判定

- 规则：需求句、判据与验收结论里不得出现“基本完成”“差不多通过”“应该可以”“暂时通过”“原则通过”五类说法，出现任一即按未判定处理，判定值回到 `missing` 或 `blocked`。

- 执行：`ai-review:全文检索五个词命中数为 0`；谁判：判定员；误放行：未逐项核对“五个禁用词出现即按未判定”即判通过；误拦截：证据已齐仍判不通过
- 层级：L3
- 依据：MXV2-2-13；S-025
- 适用：写判定结论时；证据门自检时。

### MXV2-PD-18 同一概念全篇一个词

- 规则：同一概念在需求、设计、契约与测试文件里只用一个词，同义词与英文别称按总册术语表改写；术语表里没有的新词先提案再使用。
- 判据：同一概念两种写法命中数为 0；同义词只出现在术语表登记行。

## 4 验收场景写法

场景用给定、当、那么三段写，那么段只放可观察结果。场景是 AC 的可执行形态：一条 AC 至少一个场景，一个场景只挂一条 AC，场景之间互不依赖。

本节引用 S-036 Gherkin 6（采纳，声明式场景与可观察结果）。判定五段与 Criterion 六项由总册 MXV2-7-02 定义，本节只写场景这一层，不重复定义判据字段。

### MXV2-PD-20 场景按给定、当、那么三段写

### MXV2-PD-43 可访问性七项为唯一集合

- 规则：可访问性检查只认键盘操作、焦点可见、可访问名称、对比度、错误识别、减少动效、目标尺寸七项，各项结论按四值写并附证据行；整块不适用时写 `N/A` 加理由并由验收确认。
- 判据：七项各有结论与证据行；出现第八项时已登记并改齐；缺项数为 0。
- 执行：`ai-review:七项各有结论与证据行`；谁判：判定员；误放行：未逐项核对“可访问性七项为唯一集合”即判通过；误拦截：证据已齐仍判不通过
- 层级：L3
- 依据：MXV2-7-14；S-048、S-049
- 适用：界面调整与新功能含界面时；出口抽检时。

### MXV2-PD-44 对比度按 4.5:1 与 3:1 分档（WCAG 1.4.3、1.4.11）

- 规则：正文文本与背景的对比度不低于 4.5:1，大字号（18pt 常规或 14pt 粗体）不低于 3:1，图标与边框等非文本元素不低于 3:1；三项按计算值判定，不按目视判定。

### MXV2-PD-45 焦点可见且不被遮挡（WCAG 2.4.7、2.4.11）

- 规则：键盘聚焦的元素必须有可见焦点指示，轮廓宽度不小于 2px、偏移不小于 2px、与相邻颜色对比不低于 3:1；焦点元素被其它元素遮挡时可见面积不低于 90%。

- 层级：L3

### MXV2-PD-46 键盘可达，无焦点陷阱（WCAG 2.1.1、2.1.2）

- 规则：主路径只用 Tab、Shift+Tab、Enter、Space、Esc 即可完成，浮层打开后焦点进入浮层、Esc 可退出并把焦点还给触发元素；不得出现焦点被困在区域内的情形。

- 执行：`ai-review:只用键盘走一遍主路径，记录焦点序列与退出动作`；谁判：验收员；误放行：浮层只能点关闭按钮，键盘用户出不去；误拦截：把需要按住修饰键的快捷键缺失判为键盘不可达。

### MXV2-PD-47 目标尺寸不小于 24×24，主操作不小于 44×44（WCAG 2.5.8）

- 规则：可点击元素的宽高各不小于 24×24 CSS px，主操作按钮与触控目标不小于 44×44；相邻目标之间的间距使误触不会命中另一个目标。

### MXV2-PD-48 交互元素有角色与非空可访问名称（WCAG 4.1.2）

### MXV2-PD-49 错误识别给出原因与改法（WCAG 3.3.1、3.3.3）

- 规则：错误提示写清出错原因与改正方法，错误不只靠颜色表达，错误文本与对应字段建立关联（`role="alert"` 或 `aria-describedby`），校验失败时保留用户已填内容。
- 判据：错误文本给出原因与改法；错误不只靠颜色；错误有 `role="alert"` 或 `aria-describedby` 关联；缺项数为 0。

## 8 评审与门禁

评审把前七节的产物收成一次结论：谁提、谁复核、谁判、证据在哪。设计交付物的判定人与设计作者分离，视觉方向由用户确认，交付物由验收签发。

### MXV2-PD-55 评审三人分工，判定人不兼作者

- 规则：设计评审记录写提出人、复核人与判定人三列，判定人不得是该产物的设计作者；判定冲突时按职责归属裁决，不按资历裁决。
- 判据：评审记录三列都有值；判定人与设计作者重合的条数为 0；冲突有裁决记录。
- 执行：`ai-review:逐份评审记录核对三列与作者身份，确认分离`；谁判：验收员；误放行：设计作者给自己签评审结论，缺陷直接进交付；误拦截：同一人在另一份不相关产物上兼两个角色被判为自签。
- 层级：L1
- 依据：MXV2-8-05、MXV2-3-02、MXV2-3-07
- 适用：设计评审与签字时。

### MXV2-PD-56 设计交付物由验收签、用户确认方向

- 规则：设计交付物由验收签交付物结论，用户确认设计方向；两行都在才算签过，缺一行时变更包不得标 `通过`。
- 判据：验收签交付物、用户确认方向两行都在；设计作者自签的条数为 0。
- 执行：`ai-review:验收签交付物、用户确认方向两行都在`；谁判：判定员；误放行：未逐项核对“设计交付物由验收签、用户确认方向”即判通过；误拦截：证据已齐仍判不通过
- 层级：L2
- 依据：MXV2-8-05、MXV2-3-03
- 适用：界面类交付物验收时。
