# DeepSeek Harness 适配

位置：`docs/framework/adapters/deepseek.md`。本文件是「墨线」适配层在 DeepSeek Harness 上的分支，版本绑定 `main v1.2 + ds.1`，基于总册 v1.2（2026-11-24），生效日期 2026-11-24。六个环境节之后附覆盖表、补充项与未决点，覆盖表逐条对照 main，main 的规则条文在本文件里原样保留。

## 一、版本与适用范围

适用环境为 DeepSeek Harness，当前 profile 为 `desktop`，模型 `deepseek-flash`。路由提供 `off`、`low`、`high`、`max` 四档推理，默认 `high`，档位名称与语义以 `list_subagent_models` 的实测返回为准。profile 配置在 `E:\dsh_home\profiles\desktop\cordis.patch.yml`，其中 `agentOptions` 到不了 preset 内的派单工具，档位只能按次在派单调用上写。

适用任务为本工作区内通过子智能体完成的实现、评审、验收、取数与复盘，以及主会话的拆分与汇总。其他模型、其他命令行工具与其他工作区不适用本文件，换环境时按适配层 README 新开分支。档位集合、工具参数或 main 版本发生变化时，先改本文件并递增分支序号 `ds.N`，再按新参数派单。

本文件与总册冲突时以总册为准，冲突登记在文末的未决点。main 的章节、规则编号与条文在本文件里原样保留，本文件只新增或覆盖执行参数。覆盖的条目全部列在覆盖表；main 已有对应规则的写法按原样继承，main 没有对应规则的写法列在补充项。

## 二、推理档位映射

派单卡的「推理档位」字段取 `off`、`low`、`high`、`max` 之一，对应总册第 7 章的派单字段。DeepSeek Harness 没有 `medium` 档，写 `medium` 会在路由校验阶段被拒绝，派单模板只列这四个值。以下四行给出每档的任务形态、判定依据与例外。

| 档位 | 任务形态 | 判定依据 | 例外与要求 |
|---|---|---|---|
| off | 按行号截取、字段抄录、格式转换、跑一条命令并回报 | 输出可逐字校验，不需要推理 | 需要判断截取边界或字段归属时升到 low，回报附原始片段 |
| low | 闭集核对、按模板填值、单文件小改、照脚本逐条跑验收 | 答案集合封闭，错误可由脚本或模板发现 | 脚本失败需要定位原因时升到 high，每条结论带行号证据 |
| high | 实现、评审、验收、跨文件一致性检查、需求点新建与派生判定 | 需要开放式发现与多文件推断，漏判代价高 | 工作区默认档，漏标按此档执行，分层交付并报卡点与未验证项 |
| max | 变更级整线签发、P0 根因裁定、框架版本冻结与独立验收、跨变更架构裁决 | 错误代价高且没有第二次机会，错则整批结论作废 | 一次只用于一个判断，写明一次做对的理由，低频使用 |

1. 子会话派单同时写 `provider`、`model`、`reasoning_effort` 三个字段。缺 `provider` 或 `model` 时 `reasoning_effort` 被拒绝，按 `high` 执行；实测写在 profile `agentOptions` 里的档位不生效。三字段成组出现，缺一项即视为漏标。
2. 漏标按 `high` 执行。低档回报遇到材料不足、两种以上可能或与上游事实冲突时，报「需要升档」并写明缺什么，由派单方重派，不允许猜测。升档后在派单记录里写明原因与新增材料。
3. 验收与评审用 `high`，整线签发与 P0 根因裁定用 `max`，照脚本逐条执行并回报的段落用 `low`。本工作区按项目裁决 DEC-19（照脚本执行段不取高档）执行，判断段回到 `high`，整线签发仍取 `max`。覆盖表按新口径同步，本分支只放宽机械执行段。
4. 降档后按同一 prompt 跑十组闭集核对或三组开放发现，观测通过率与平均步数。两项任一变差超过两成时回到 `high`，并把结论记入任务目录的决策记录。没有对照样本时不降档。
5. 推理档位只影响输出费用，对缓存命中占比较高的输入费用没有作用。把机械段降档的收益按个位数百分比预估，不承诺数量级。对外汇报成本变化时同时给请求数与三个桶的 token，不只报费用。

## 三、上下文与压缩

当前上下文窗口为 1,048,576 token。生效的压缩闸门是 billion-context 插件的 `compress.maxContextLimit`，取窗口的 75%，触发点为 786,432。DeepSeek Harness 原生闸门的触发点 727,040 与保留量 126,812 只在卸载该插件或关闭它的闸门后生效，本环境当前不压上限。

压缩后保留当前任务的目标与可写范围、已改文件与状态、未完成项与下一步动作、关键决策与证据路径、派单禁止项。已被写入文件的正文、重复的命令输出与已经核对过的日志摘要不再保留，需要时按路径与行号回读。保留项按优先级排序，证据路径与未完成项优先于过程描述。

压缩前把上述内容写入检查点 `.tmp/<task-id>/checkpoint.md`，每完成一步或停下时更新，写已完成部分、未完成项与下一步。压缩后的第一个动作读检查点与 `HANDOFF.md`，再决定是否重读源文件。同一事实需要细节时用 `grep` 取行号，再用 `read` 的 `offset` 与 `limit` 读区间。

跨会话或换人时写 `HANDOFF.md`，整份不超过 6,000 token，只放目标与验收标准、已定决策与理由、已改文件与当前状态，另加一份「不要再读」清单。压缩摘要的 `maxTokens` 取 6,000，摘要写长会把刚腾出的空间重新填满。超长工具结果按落盘策略（`spill-policy`）的 `maxInlineTokens` 12,500 写入文件，正文用路径引用，不整段贴回上下文。压缩次数与压缩后首个请求的未命中 token 记入复盘，调整触发点时同时改保留量，只改一项会同时改变可增长空间与每次压缩的重灌量。

## 四、工具与派单

可用工具包括 `subagent`（新会话子智能体）、`subagent_fork`（继承父会话）、`send_message`（续派与追问）、后台 job（长构建与批量渲染）与 `workflow`（仅在用户明确要求多智能体编排时使用）。子智能体开工前先读派单 prompt 与工作区基线，不整篇读 spec 与长日志。需要并行的独立调用合并在一条消息里发出。

同一能力域同时最多 2 至 3 个子智能体，改同一文件的两个子智能体不得同时运行。跨域可以并行，数据库迁移串行，同一批并行工具调用只算一个步骤。派单前先核对可写范围是否重叠，重叠时拆成串行两批。

派单 prompt 内嵌派单五要素（owner、scope、验收标准、证据与禁止项），并显式写 `provider`、`model`、`reasoning_effort` 三个字段。新会话子智能体不继承父会话上下文，派单时把已确认的事实与禁止读取的路径一并写入。需要继承时才用 `subagent_fork`，并在 prompt 里写明沿用的结论。

每步预计不超过 20 分钟，完成一步向派单方回报 3 行，写做完什么、证据在哪个文件或命令、下一步做什么。单步超过 20 分钟仍无进展时停下，报告卡在哪、已试过什么、需要什么，重新拆分后再继续。单次验证超过 10 分钟拿不到证据，记「未取到」并落盘。任务被中断时先读检查点，按未完成项续做，不重跑已完成步骤。构建、测试与批量渲染放后台 job，日志写到 `.tmp/<task-id>/` 下的文件，需要时按摘要与行号读取。这些要求属于执行参数，不新增门禁，门禁仍以总册附录 B 与 `scripts/ac/` 为准。

## 五、成本计量

请求数按实际发出的模型请求逐次计数，同一批并行工具调用只算一个步骤，但每次请求各计一次。按日总数从 `E:\dsh_home\storages\token_stats.json` 的 `global.days[].requests` 读取。请求级明细从会话日志逐条扫描每次请求的 token 用量得到，按会话与时间戳对齐。

输入 token 分两列：`input` 是未命中缓存的输入，`cacheRead` 是命中缓存的输入，输入总量取两者之和。`output` 单列，不并入输入。缓存命中率等于 `cacheRead` 除以 `input` 与 `cacheRead` 之和，复盘同时写分子与分母，避免只报百分比。

费用按三个桶折算：未命中输入、缓存命中、输出，各桶 token 乘对应单价后相加。单价取 DeepSeek 官方价目表，高峰时段为周一至周五 9:00 至 12:00 与 14:00 至 18:00，高峰单价是低谷的两倍，法定节假日除外。费用按请求发生时的时段与档位折算，不把高峰请求按低谷价计。

按日聚合时读 `token_stats.json`，按请求核对档位时读会话日志的 `request/header` 中的 `reasoningEffort`。复盘写请求数、总输入、前三项支出及各自占比，数据取按日聚合值与请求级扫描。分档预估下一轮成本时用实测三个桶的比例校准，按桶分别乘单价。改口径先改本节，再改复盘模板，并在 `docs/plan/DECISIONS.md` 追加一条记录。

## 六、已知失败模式与绕行

| 失败模式 | 识别方式 | 绕行做法 | 上报条件 |
|---|---|---|---|
| 长上下文截断 | 压缩后引用已被压缩掉的内容，行号错位，重复读同一文件 | 压缩前把目标、已改文件与证据路径写进检查点，大输出落盘后用路径与行号引用，压缩后先读检查点再回读源文件区间 | 同一事实两次压缩后仍取不到，停下报告触发点与保留量 |
| 工具调用参数不合规 | 返回 `reasoning_effort` 被拒绝、`medium` 不被识别、JSON 参数类型错误 | 按 `list_subagent_models` 的返回重写参数，三字段成组传，派单模板只列合法档位，失败后读错误原文再改 | 同一调用连续两次失败即停，贴错误原文与参数，不原地重试 |
| 子智能体上下文不继承父会话 | 子会话重复问范围、引用父会话里没有的结论、产出偏离派单范围 | 派单 prompt 内嵌五要素与已确认事实，需要继承时用 `subagent_fork` 并写明沿用的结论，跨日写 `HANDOFF.md` | 子会话报材料不足或与上游事实冲突时，补发结论或重派，不要求它猜测 |
| 沙箱限制导致命令失败 | 出现 `[sandbox: file access denied]`、工作区外路径写入失败、审批被自动拒绝 | 读写限定在工作区与 `.tmp/`，输出落文件，越界需求上报派单方；被拒绝的操作不换写法重试，记录提示原文与目标路径 | 任务必须写到工作区外时，由派单方处理权限，不自行提权 |

四条失败模式都按识别、绕行、上报三步处理，绕行只在当前任务内生效。跨任务复用的做法先写进本文件再执行，不靠对话记忆传递。上报时附现象原文、命令与目标路径，便于派单方复现。

## 覆盖表

本表逐条对照分支对 main 的覆盖，main 列引用总册章节或规则编号，分支列写本文件的写法。总册规则正文按现行 v1.2 引用，章号与规则编号变化时按新版复核。覆盖只放宽或细化 main 的做法，不删除、不改写 main 的任何规则。

| main 原文 | 分支写法 | 覆盖理由 | 影响范围 |
|---|---|---|---|
| 验收与评审用 high，整线签发与 P0 裁定用 max，不降到 low 以下（总册第 7 章派单与第 10 章验收的档位要求，规则正文见 `MOXIAN.md` 第 7 章、第 10 章与项目基线 `AGENTS.md` 的成本纪律条款） | 照脚本逐条执行并回报的段落取 low，需要判断、归因与日常验收的段落取 high，整线签发与 P0 裁定取 max，验收签字权不变 | 本工作区复盘测得验收会话的主要成本在长上下文逐条核对，机械执行段取 low 不改变判定结果（项目裁决 DEC-19，见 `docs/plan/DECISIONS.md`） | 只影响照脚本执行段；证据要求、签字流程、门禁与总册第 10 章的验收判据不变 |
| 汇报按批进行，派单方在一批任务全部完成后汇总一次；批内单个任务卡或子智能体完成时不逐卡转述进度（总册第 8 章，MX-8-01） | 子智能体每完成一步向派单方回报 3 行；派单方对用户仍按批汇总，不逐卡转述 | 单步可达 20 分钟，批末才发现方向错误会造成整批返工 | 增加派单方内部消息条数，不增加用户侧汇报，MX-8-01 对用户侧的约束保留 |

以下条目在 main 中没有对应规则，属于分支新增的执行参数，不构成门禁。

1. 四档推理的名称与语义，默认 `high`，`medium` 不存在。
2. 子会话派单的 `provider`、`model`、`reasoning_effort` 三字段与漏标落 `high`。
3. 上下文窗口、压缩触发点 786,432、保留量 126,812 与摘要上限 6,000。
4. 检查点 `.tmp/<task-id>/checkpoint.md` 的更新时机与 `HANDOFF.md` 的 6,000 token 上限。
5. 请求数、输入 token、缓存命中与输出 token 的取数口径与缓存命中率算法。
6. 四条失败模式的识别方式与绕行做法。

main 中关于派单五要素、每步 20 分钟、同一域并行 2 至 3 个、验收独立签字与门禁清单的规则原样继承，本分支不做定制。这些规则与本文件冲突时以 main 为准。main 升版后按覆盖表逐条复核，失效的覆盖删除并在未决点登记理由。

未决点有三项。第一项是压缩闸门由 billion-context 插件接管时 DeepSeek Harness 原生阈值不生效，换环境后需要重新实测触发点与保留量。第二项是峰谷单价未在仓库内固化，费用折算依赖外部价目表，价目表变更时本节需要同步。第三项是档位实际生效值只能从请求头核验，派单后需要抽查 `request/header` 的 `reasoningEffort` 是否等于派单值。
