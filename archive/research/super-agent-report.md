## 1. 一句话定义

> Super-agent 是一个**常驻在线、以环境事件（而非人类提示词）为输入、用双层调度把"跨渠道连续性"与"多任务并发"解耦**的 Agent 系统形态；它把会话管理与上下文同步从人手里收归系统，把人上移到"决策与验收层"。〔A〕

如果只允许留一句设计哲学，是原型仓库的第一行原则〔B〕：

> **"尽可能少占用人注意力，尽可能多给出价值。"**
> （Take as little human attention as possible, and give as much value as possible.）

它之所以重要，是因为这句话不是口号，而是**可判决的架构裁判准则**——原型文档明确说：一条消息、一个通知、一个提问、一个设置、一个面板元素、一段文档，都在消耗某人的注意力，都必须产出高于成本的价値，否则删掉。这条准则直接导出了后面所有机制（静默、100 词限制、observe 模式、面板只显示待人工决定）。

**问题起点**〔A〕：模型完成单个任务已越来越不需要人介入，瓶颈从"模型能力"转向"人的注意力"。团队观察：**一个人通常只能同时跟进 3–5 个活跃 Session**；现有 Agent 以单一 Session 为单位、Session 间相互独立，用户并行推进多项工作时得手动切换并搬运上下文；即使通过 CLI/MCP/外部连接器扩展，仍受**单会话同步阻塞、多任务上下文混乱、本地设备离线即停**三重制约。
（注：3–5 这个数字是团队的经验观察，文中未给出统计口径，属**未溯源的实证断言**。）

**四项基础特征**〔A〕：

| 特征 | 含义 | 反例（不满足时的表现） |
|---|---|---|
| **连续** | 在 IM、GitHub 评论等不同渠道与同一个 Agent 交互，感觉始终只存在一个 Agent | 用户在 IM 定了方案 A，到 GitHub PR 评论改方案 B，Agent 不理解这是同一件事 |
| **高效** | 不需等上一个命令/任务完成就能接新指令，多复杂任务并行 | 长命令把会话阻塞，人在干等 |
| **主动** | 持续观察环境事件并自行推进值得处理的事项；不需介入时保持安静 | 必须每次 @ 它才动；或者反过来，噪音刷屏 |
| **持久** | 始终在线、直连真实工作环境、长期运行遇异常自动恢复 | 合上笔记本任务就死；跑一天卡死无人知 |

〔A〕文章的核心方法论主张：**单个 ReAct Loop 无法同时支持这四点**；而"相似的约束会导出相似的架构选择"，上述问题与传统计算机系统长期探讨的问题高度同构，因此**调度、缓存、存算分离、看门狗等经典系统思想可直接迁移**。这是全文最锋利的一句——它把这件事从"提示词工程"重新定义为"系统设计"。

**五大模块**〔A〕：双层架构、事件驱动、面向人的交互、计算与状态及环境分离、Watchdog。

## 2. 双层架构：职责边界

### 2.1 为什么必须分两层〔A〕

"跨信道连续交互"与"多任务高效并发"存在**根本权衡**：

- 全部交给一个 Session → 上下文最连续，但单 ReAct Loop **串行**、吞吐低、细节混杂；
- 全部开独立 Session → 吞吐最高，但**缺全局上下文**、结果割裂、交互混乱（多个会话各自回复人）。

解法：把「维护全局连续性」与「高并发执行」拆成两层。**"Session 应成为系统实现细节，而非用户认知负担。"**〔A〕

### 2.2 职责边界表

| 维度 | **Router 层** | **Worker 层** |
|---|---|---|
| 角色 | 常驻全局路由层；全局序点、协调点、记忆 | 具体执行层；上下文隔离的并发执行体 |
| 承接 | **所有入口的人类交互**；跨任务的信息与决策在此汇总 | 单一任务；完整执行工具 |
| 是否亲自干活 | **否**。只负责人类交互与任务分派，**甚至可以不配 Bash 工具** | **是**。专注完成单一任务 |
| 对外说话 | **是**，唯一对外出口，统一向用户回复 | **否**。推理过程与工具调用不输出到外部信道，只向 Router 汇报状态 |
| 上下文 | 全局、连续、跨渠道、跨任务 | 隔离、局部、单任务 |
| 建议模型 | **较轻量模型即可**（任务常不复杂，兼顾速度与效果） | **能力最强的模型**（直接决定结果质量与代码质量） |
| 是否介入任务内部拆解 | **否**。只处理任务之间的**高层关联与分派** | 是。任务内部怎么拆由它自己决定 |
| 内部结构自由度 | 不必是单 Session；部分逻辑甚至不必调 LLM；可多层过滤或水平切分 | 内部可再创建 Subagent，也可**本身就是一个 Agent Team**——对 Router 透明 |
| 原型实现〔B〕 | 主 Session，代码/提示词中称 `orchestrator`，preset 为 `dsh-superagent-router` | 执行器 Session，`worker-<ticketId>`，preset 为 `dsh-superagent-worker`，**一 Ticket 一 Session 一目录** |

### 2.3 一个极易被误读的对比：Router/Worker ≠ 常见 Agent Team〔A〕

文章专门澄清了这点，因为它决定了你抄错方向：

| | 常见 Agent Team / 多 Agent 编排 | Super-agent 双层架构 |
|---|---|---|
| 解决什么 | **单个复杂任务内部**的步骤拆解与角色协作 | **任务之间**的排队、归属、分派与连续性 |
| 子任务耦合 | 紧耦合 | 松耦合、彼此独立 |
| Lead 的负载 | **极重**：需深入理解任务细节、规划子任务、高频协调 | **极轻**：只处理高层关联与分派，不介入单任务内部 |
| 类比 | 技术负责人 + 团队 | **调度器 + 工作进程** |

〔A〕文章甚至给出了反向等价：**用提示词约束一个 Agent Team 的主会话"不亲自执行、只对外交互并把不同任务分派给各成员独立推进"，这个形态也可视为双层架构**。（言下之意：架构由约束决定，不必新造名词。）

### 2.4 Router 的批处理：为什么单 Session 不是瓶颈〔A〕

这是全篇最反直觉、也最值得抄的一段工程洞察。

表面看，Router 作为全局单点必然成为吞吐瓶颈。但团队发现**不必然**，因为：

1. 上一轮推理期间到达的环境事件会**积压**下来，在下一轮**一并注入**，自然形成 batch；
2. Router 每步是典型的**长输入、短输出**（只做轻量交互与分派）；
3. 把积压的多条 Trigger 合并进**一次** LLM API 调用，在 **Prefill 阶段并行计算**，单次请求耗时增长远慢于 batch 大小。

因此在一定范围内**"积压越多，单个决定分摊的推理时间越低"**。上限取决于上下文长度，以及模型在一轮中能准确处理多少条 Trigger。

实验数据佐证〔A〕：Trigger 到达速率 1→40 条/分钟时，平均 batch 1.0→2.8，单次请求耗时仅 2.5s→3.9s，**单个决定分摊的推理时间 6.4s→1.6s**。

结论：团队规模下，**一个常驻 Router Session 加上订阅直通与链式召回，已经够用**，无需过早水平切分而牺牲全局连续性。规模再大时，Router 层内部可做多层过滤或水平切分为多会话——但〔A〕明确承认：**切分粒度越细，Router 吞吐越高，分片间记忆与上下文连续性越低；"在全局记忆问题被解决前，这一权衡始终存在"**。

> 〔D〕批处理摊薄的是 **token / 推理成本**，不是**上下文长度**。Router 的上下文规模是 O(任务数) 的全局索引，任务量上去后必然要分片——而分片直接摧毁"连续性"这一核心卖点。这是架构内在最硬的自相矛盾，文章自己也只承认、未解决。

## 3. 事件驱动模型

**驱动源的根本改变**〔A〕：驱动 Agent 的主要输入不再是人类在 Session 中逐条键入的提示词，而是环境中源源不断的**半结构化事件**。这些事件被称为 **Trigger**：群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果等。

一条 Trigger 的完整生命周期，按文章的四步递进问题组织（这也是实现时的四个模块边界）：

```
Source ──Trigger──> ① 两级过滤 ──> ② 订阅直通路由 ──> ③ 上下文组织 ──> Worker Session
                        │                                              │
                        └──> Router 研判(Decision) ──> Ticket ────────┘
                                                                    └─> ④ 投机执行（提前开工）
```

### 3.1 第一级问题：高噪音、低触发率 → Fast Path / Slow Path 两级过滤〔A〕

接入真实群聊与代码平台后，事件流呈现**"高噪音、低触发率"**：绝大多数日常消息并不需要 Agent 介入。对每个事件都调大模型判断，延迟与算力都不可承受。

借自计算机系统的 **Fast Path / Slow Path** 思想：**程序 = 快速但僵硬；模型 = 灵活但昂贵**。

| 层 | 定位 | 判据 | 作用 |
|---|---|---|---|
| **程序层策略（Fast Path）** | 确定性代码 | 事件来源、群组范围、用户/机器人白名单等确定性条件 | 在调用模型前**滤除大部分无关消息**。对不同来源分别设"仅响应明确请求 / 作为候选事件 / 直接忽略" |
| **语义层策略（Slow Path）** | LLM 判断 | 用提示词编写的策略 + 上下文 | 判断"是否需要行动"；同时**充当面向人类的自然语言扩展点**，可随时用提示词开关或新增策略 |

> 〔D〕这一层的真正价值不是性能，而是**信任边界**：**永远不要用模型当权限边界**。谁能触发 Agent 是代码判定的，模型只在"已准入"的候选里做语义研判。把这一条反过来做（让模型自己看消息决定要不要动），是这类系统最容易被提示词注入攻破的地方。

### 3.2 第二个问题：事件路由 → 订阅 + 直通〔A〕

若已分配任务的每条后续事件都要经 Router 转发，这个全局节点依然会承受大量负载。因此 Fast/Slow Path **同样适用于路由**：

- **概念**：同一个 GitHub PR、同一个 IM 话题、同一封往来邮件串下的连续事件构成一条事件流，称为 **Thread**。
- **Slow Path（未订阅）**：Router 层创建 Worker Session 后，**仍可观测所有事件以掌握全局状态**，但只负责判断和分派**尚未被订阅的新事件**（新任务冷启动 + 跨任务协调）。
- **Fast Path（已订阅）**：Worker 直接**订阅**该 Thread，后续同 Thread 事件由**程序直接投递**给它，**无需 Router 再调用工具转发**。
- **越界处理**：若新事件超出当前任务范围，Worker 可**取消订阅**或**交回 Router** 重新分派。
- **订阅是多对多关系**：一个 Worker 可同时订阅多个 Thread；同一个 Thread 也可被多个 Worker 订阅。

**多对多订阅是这套架构里最精妙的一个设计**〔A〕：当多个 Worker 在同一个工作环境（如同一个 PR）发生交集时，该 Thread 下的新事件会**同时直通给所有订阅它的 Worker**，使它们**无需点对点通信**，也能看到彼此的操作并**自行发现和解决冲突**。少数跨任务协同才由 Router 中转。

> 〔D〕这等价于把并发控制从"消息传递 + 锁"换成了**"共享观察 + 自主避让"**。代价是没有强一致保证（两个 Worker 可能同时改同一处），收益是不需要写任何 Agent 间通信协议。对代码场景够用（git 本身就是乐观并发 + 冲突暴露）；对强一致场景不够。这是**用一致性换掉一整套 A2A 协议栈**的取舍。

### 3.3 第三个问题：向上下文注入多少 → Inline & Spill + 链式召回〔A〕

系统输入从"有限人类提示词"变成"环境持续产生的半结构化事件"后，注入过多会挤占窗口、稀释注意力；注入过少会迫使模型反复调工具读取、增加执行步数。文章原话：

> **"浪费上下文窗口，就是浪费模型的智能。"**

做法：**把有限上下文窗口当 Cache 管理**，两个基本操作：

- **Inline**：把近期很可能用到的信息**直接内联**进当前窗口，省去额外工具调用往返；
- **Spill**：把超出窗口预算或低频使用的完整信息**留在窗口之外**，窗口内只保留引用或摘要，供模型按需读取。

结合**局部性**思想，逐步优化（这是一条可直接照抄的注入策略阶梯）：

1. **从最少信息开始**：只提供当前对象 ID 和内容摘要；
2. **利用局部性逐步 Inline 关联信息**：先附紧密关联对象 ID，再附时空相邻内容——内容前 50 字、IM 消息前后相邻消息与所回复消息、代码评论所在评审讨论中的相邻评论；
3. **超出上限则 Spill**：对长内容设较小长度上限，超出部分截断并**保留续读入口**，模型需要完整内容时再调用工具读取。

**链式召回（Chain of Recall）**：把 Inline & Spill 一致应用到系统各类对象后，自然得到一种**按需展开的多跳检索机制**。

- 机制：给 Trigger、Thread、Worker Session 等对象**唯一 ID**，注入时**内联紧密关联对象的 ID**，使这些对象在底层构成**一张引用图**；
- 因为每次工具召回返回的对象**同样遵循 Inline & Spill**，结果中又会内联**下一跳**的摘要与 ID；
- 于是模型可以**从当前事件出发，顺引用关系逐跳展开**：一条当前消息 → 所在 Thread → 该 Thread 内联的 Worker Session ID → 该 Worker 关联的另一个代码评审 Thread。
- 目的〔A〕：缓解 Router 层在长程中丢失先前信息的问题——Router 既不能把所有历史任务全量放进窗口，又要在用户跨渠道提起旧任务时找回上下文。

> 〔D〕这是**"上下文 = 带外键的数据库视图"**的思维方式：模型不是在"记忆"里找，而是在**引用图里跳**。它隐含一个强假设——**所有值得回忆的东西都有 ID 且建立了外键**。这一点比 99% 的 Agent 记忆方案（向量检索/摘要压缩）都更工程化，也更可测（跳数、召回成功率）。但它要求你从第一天就把领域对象建模成图，事后补会非常痛。

### 3.4 第四个问题：如何提前行动 → 投机执行〔A〕

借自计算机系统的**投机执行（speculative execution）**：Agent 在还不确定结果是否会被采用时，**根据环境信号在后台提前尝试**，用额外后台算力换人的等待与介入成本。**结果有价值就交付，没有价值就丢弃。**

两个具体例子〔A〕：

- 个人助手：收到会议邀约邮件或待办消息 → 后台**核对日程冲突、搜集相关背景资料、备好回复草稿** → 用户过目后直接确认发出；
- 研发协作：团队在内部用户群配置了一条 **"静默复现并修复"** 策略 → 有人反馈问题或讨论改动方案时，Agent **先在后台尝试复现并寻找修复方案**，**只有在确认问题且找到简单修复方案后，才把结果交付**，否则**全程保持安静**。

> 〔D〕"投机执行"和"静默"是一枚硬币的两面：**允许它偷偷干活，就必须允许它白干**。这要求执行必须廉价、可丢弃、无外部副作用——所以投机阶段只能在隔离目录/沙箱里做（原型的 `git worktree` + 一 Ticket 一目录正是为此）。**不能让投机执行去 push、发消息、改线上。**

## 4. 存算分离与上下文同步

### 4.1 问题〔A〕

现有本地 Agent 默认把三件事**绑定在同一台设备**：推进 Agent Loop 的**计算**、需持久保存的**会话状态**、代码仓库与本地工具链等**执行环境**。一旦设备休眠/离线，Agent 停止运行，且无法访问其他设备上的环境。

### 4.2 两步解耦〔A〕

| 步骤 | 解耦对象 | 效果 |
|---|---|---|
| 第一步 | **Agent Loop 计算** ↔ **持久化会话状态** | Agent 摆脱单机生命周期限制，实现**云端持久在线** |
| 第二步 | **云端 Agent Loop** ↔ **重状态执行环境** | 真实工作环境**留在原地**，支持跨设备访问 |

落形态〔A〕：计算与持久化状态放**云端**；执行环境可留在**用户本地设备**，仅部署**负责执行命令、返回结果的轻量 daemon**。由此支持：

- **BYOM（Bring Your Own Machine）**：把用户日常使用的开发机/个人电脑接入云端 Agent；
- 云端托管机器，或按需创建的计算环境；
- **间歇在线设备**：某台个人设备重新上线后，由云端 Agent **自动触发并完成**需要在该设备执行的任务。

### 4.3 与 Anthropic "脑手分离" 的同与异〔A〕

文章主动对标 Anthropic 的"脑手分离"：

| | 相同点 | 差异 |
|---|---|---|
| Anthropic | **harness 保持无状态**；**会话日志存放在 harness 之外**；通过**统一接口按需接入执行环境** | 描述的是**托管服务**，主要讨论按需创建的**沙箱**与客户 VPC 内资源 |
| DeepSeek Super-agent | 同上 | 首先要接入的是**用户日常使用、可能间歇在线的个人机器**，上面有**未提交修改和本地凭据** |

> 〔D〕这个差异不是措辞差异，是**威胁模型的差异**。托管沙箱是"干净、可弃、无凭据"；个人开发机是"脏、不可弃、满是凭据"。同一套"harness 无状态 + 外置日志 + 统一执行接口"在两个场景下的安全含义完全不同——这直接解释了为什么 DeepSeek 把"安全与隐私"列为未解问题（见 §8.2）。

### 4.4 上下文同步怎么落地（原型视角）〔B〕
〔B〕原型**没有实现存算分离**（它是单进程 DSH 插件 + 本地 SQLite），但它在**单机范围内**实现了"计算/状态/环境"的逻辑分离，这是你可以直接抄的最小版本：

- **状态**：单一 SQLite 文件 `<stateDir>/orchestrator.sqlite`，**只有 Store 能打开**；Runtime 启动时**先取目录锁**，防止第二个进程迁移或写入同一状态。
- **计算**：Router/Worker 都是 DSH Session，是**可替换、可中断、可重启**的执行体；Session 崩溃不影响状态。
- **环境**：每 Ticket 一个目录（在 execution root 下，默认 `<stateDir>/work`），由一个**prepare 命令**在首次派工前执行一次（`sh`，**10 分钟超时**，典型用 `git worktree` 建 checkout）。目录与 Session 都可通过 `DSH_SUPERAGENT_*` 环境变量传给执行体。
- **恢复**：重启后 Assignments 以 "host restarted" 结束，新 Assignment 带一条**恢复注记**，要求 Executor **先核对目录、git 历史、GitHub 再重复任何外部动作**（"oldest Ticket first"）。

> 〔D〕`prepare 命令 + 一 Ticket 一目录 + 恢复注记`这三件套，是**"存算分离"在单机上的可行降级**：不搞云端 daemon，但保证"计算体是牲口、状态是宠物、环境是可重建的"。如果你短期上不了 BYOM，就照这个做，收益的 80% 已经拿到。

## 5. 多任务 / 团队协作扩展

### 5.1 编码层面的"多任务"到底是什么〔B〕

文章讲的是"多任务"，原型把它落成了一个**领域模型**，这是最可复用的一层。核心对象与其不变量：

| 对象 | 是什么 | 关键规则（不变量） |
|---|---|---|
| **Source** | 一条事件流；kind 是可复用实现，instance 是一次配置 | 持有**自己的读取游标**和自己的**机器人身份**；在进入领域前就丢掉 bot 自己的消息与不监听范围外的事件；**重启不得重放事件** |
| **Trigger** | 一条**不可变**事件 + Source 侧元数据（如 actor） | 属于一个或多个 Thread；**同一 Trigger 接受两次只产生一个 Ticket**（幂等单位） |
| **Thread** | 按时间排序的 Trigger 序列；由 Source 定义哪些 Trigger 构成一条 Thread | **同一时刻最多一个 Eval 在其上运行**；可挂多个 Ticket；持有其 Subscription、运行中的 Eval 与 Decision 历史 |
| **Correlation** | 一条 Trigger 所跨多个 Thread 之间的关系 | **只增加上下文，永不参与路由** |
| **Channel** | Thread 的**写侧**；Source 定义其地址 | 一个 Thread 可有多个 Channel；一个 Ticket 持有一组 |
| **Policy** | **带版本**的准入与研判规则 + 各 Source 的部分（谁能通过该 Source 发起工作、白名单如何同步、哪些 bot 可产生候选） | Policy 版本覆盖规则、accept mode、Source 各部分；**变更只投递给受影响的活动 Ticket，不撤销 Mandate**；不同 Source 上的身份**永不互相映射** |
| **Eval** | 对一批 Trigger 的研判，**两层：Gate（准入，确定性）+ Assessment（研判，模型）** | 输入：Trigger 批次、Thread 快照、该 Thread 上**全部** Ticket（含已结束）、当前 Policy。输出：一个 Decision。**自身无状态** |
| **Mandate** | 一次 accept 授予的东西：Policy 版本、scope、strength、命中的规则、发送者在该 Source 的身份、Source 如何收到该 Trigger | **不可变**；scope 变宽=新 Ticket；Ticket 结束不结束 Mandate（只有人 stop 才撤回，Policy 不再支持才吊销）；结束的 Ticket 恢复前**必须对当前 Policy 重新校验** |
| **Ticket** | 一个**已授权工作的单位** | **只有 Eval 能创建**；持有 Channels、Inputs；`open → ended`，被人消息恢复则回 `open`；**自己定义状态，不跟随 Executor 的状态** |
| **Assignment** | Ticket 到**一个 Executor 实例**的绑定 | 一个 Ticket 先后可有多个；`pending → running → ended`，**独立于 Ticket**；只有其最终 Report 可在 Executor 侧结束 Ticket |
| **Subscription** | Ticket 与 Thread 的**多对多**关系（由 Thread 持有） | 匹配的 Trigger **扇出**给所有活动订阅 Ticket，**不检查发送者**；人经此到达的消息**不产生 Eval**；结束的 Ticket **保留** Subscription（人再发言可凭原 Mandate 直接恢复，无需 Eval）；被人 stop 的 Ticket **收不到任何东西** |

**最核心的一条不变量**〔B〕：

> **Subscription 让"上下文"流动，Mandate 让"授权"流动；两者严格分离。**

原文表述为："Mandate separates authorization from context"（Mandate 把授权与上下文分开）。这条不变量是所有安全性的根：一条 PR 讨论里的任何消息都能进 Worker 的上下文，但**不因此获得任何新权限**——权限只由创建时的 Mandate 决定，并在恢复时被重新校验。

### 5.2 并发与资源调度〔B〕

原型给了一套非常具体、可直接照抄的并发规则：

- **worker slot**：一个 Ticket 从 launch（含 prepare）或从"唤醒空闲 Executor 的投递"开始占用一个 slot，并贯穿整个活跃 turn；受配置的并发上限约束。
- **+1 个额外 slot 专供人**：人的消息或状态请求可**使用这个额外 slot**，并在新 launch 之前**优先拿下一个空出的普通 slot**。→ **保证"新工作永远无法阻止一个人继续已有 Ticket"**，人永远不会被机器任务饿死。
- **排队语义**：CI 结果等其他 Input 只能等普通 slot；launch 在 `working / queued` 等待；**launch 之间并发**，所以一个慢 prepare 只延迟它自己的 Ticket。
- **后台工作与 slot**：turn 结束时若有 shell job 或 subagent 在跑，Ticket **保留 slot 并保持 working**（不报 waiting），完成后再用**同一个 slot** 唤醒 Executor。turn 结束时无后台工作，才正常报 waiting。
- **30 分钟上限**：每 turn 结束后后台工作最多 30 分钟；到点**杀掉 shell job** 并报 waiting，报告里附 Executor 最后的话与被杀/残留清单；**subagent 允许继续**。
- **handoff 释放 slot**：把控制权交还给人（`ready` 报告或提了问题，或 `blocked`/`failed`）时**立即释放 slot**；此时 subagent 停止，shell job（如供评审的 server）可继续且**不占 slot、不受 30 分钟限制**。
- **Executor 预设把前台命令 5 秒后转后台 job**，使 worker 能在下一个 step 收到新消息，而不是被长命令卡死。

### 5.3 团队协作的扩展路径〔A〕

| 层级 | 扩展方式 |
|---|---|
| 单 Worker | 内部可创建 Subagent，或本身是一个 Agent Team（对 Router 透明） |
| 多 Worker | 上下文隔离并行；同层**默认不直接通信**，冲突靠**订阅同一 Thread 共享观察**自行避让；跨任务协同由 Router 中转 |
| Router | 初期单个常驻 Session 够用；不够时**多层过滤**或**水平切分为多个会话**（代价：牺牲分片间连续性） |
| 组织 | 〔A〕未解：组织扩大后**如何划分上下文边界**、多个隔离实例之间**A2A 通信与协作**（见 §8.2） |

## 6. 人的角色上移：从"操作者"到"决策与验收层"

### 6.1 上移的具体含义〔A〕

系统在**底层接管会话管理与上下文同步**，于是人不必再关心"Session X 的上下文中是否有 Y 信息"；人的工作被压缩为两件事：**设定目标/做决定**、**验收结果**。

### 6.2 上移是靠哪些机制保证的（这是本节真正的干货）

不是靠一句"让人做决策"，而是靠一串**强制人工介入点**与**强制静默规则**：

| 机制 | 原型实现〔B〕 | 解决什么 |
|---|---|---|
| **Ticket 阶段机** | `person / delivery`（输入投递失败）、`person / answer`（有待人工回答）、`person / review`（最新 Report 是 `ready`）、`person / blocked`、`person / failed`、`working / queued`、`idle`、`working`。**`person` 前缀 = 没有人工输入就无法继续** | 把"卡在等人"变成一个**显式、可查询、可排序**的状态，而不是一个沉默的会话 |
| **Attention（结构化提问）** | 待人工决定 = Ticket 上一个**等待回答的问题**。人的消息到达后 `blocked`/`failed` 的 Ticket 被释放回执行 | 防止"问题淹没在长报告里"——必须**一次只问一个具体问题，且用结构化字段** |
| **显式拒绝从自由文本推断"在等人"** | 领域模型"被拒绝的概念"里明确写着：**不得从 report 的自由文本推断"waiting on a person"，必须用结构化字段提问** | 机器可判定的状态机，不能靠 NLP 猜 |
| **面板只显示待人工** | 面板**首先列出等人处理的事项**；健康状态**不占空间** | 注意力预算原则的直接体现 |
| **Report 状态集** | `progress / waiting / ready / blocked / failed / dropped` | 让"进展、等待、就绪、受阻、失败、无需处理"六态可区分，而不是一句"我做完了" |
| **accept mode 三级** | `off`（推断类一律不成候选）/ `observe`（**默认**：正常研判，但正判定只记为 "would accept"，**什么都不接受**）/ `auto`（正判定的推断类候选真的接受）。**明确请求在所有模式下都生效** | **影子运行**：先让系统"只记录它本来会做什么"，人审过历史决策后再放开。这是把 Agent 上线风险降到最低的关键机制 |
| **强度区分** | `explicit`（白名单上的人明确请求 / 已有 Ticket 的 Thread 上的跟进 / 准入表某格设为 explicit）vs `inferred`（名单外的人在已有 Ticket 的 Thread 上跟进 / 准入表设为推断候选 / 名单内 bot 的消息） | "谁说的"决定"能做多少"，而不是"说了什么" |
| **人永远可 stop** | 人的 stop **撤回 Mandate**；被 stop 的 Ticket 保持结束、不再收任何消息 | 人的否决权是**权限级**的，不是建议级的 |
| **默认不自动合并** | auto-merge 需另一个账号的 CLI（因为 GitHub 把合并归因于开启者）；无则人合并。默认指令仅允许：自家开的 PR、已 ready、必需 approvals 覆盖 head commit、**增删合计 < 200 行**；推下一版前必须撤回 auto-merge | 把"最后一步不可逆动作"默认留给人 |
| **交付规范按信道** | IM/即时通讯：**单次回复不超过 100 词**（团队验证过的硬性规定）、只问直接问题、给简短结论、像人类同事一样只在需要决策或验收时发通知；GitHub/邮件/文档：结构化、高信息密度（完整问题背景、改动说明、验证结果） | 不同信道带宽不同，输出必须匹配；把推理过程与工具调用**隔离在 Worker 内部**，不外泄 |

> 〔D〕这一节最值得抄的不是任何单点，而是**"验收"在原文里其实没有被做成一等原语**。文章反复说"人做决策与验收"，但原型的验收手段只有 `ready` Report + PR review + 人肉点合并——**没有验收契约**（比如"必须附复现脚本""必须附测试通过证据""必须附回滚方案"才允许从 `ready` 走到 `ended`）。这是我造的时候会补的第一个洞（见 §9.11）。

## 7. 内部实例的真实行为

### 7.1 已持续运行的内部实例〔A〕

基于 DeepSeek Harness 构建的**内部 Super-agent 实例已持续运行**，参与：**问题复现与修复、代码审查响应、以及 DeepSeek Harness 自身的迭代**。

### 7.2 "无人 @" 的行为链条（这是最值得拆解的一段）

〔A〕描述：团队在 Harness 内部用户群配置了 **"静默复现并修复"（observe/reproduce silently）** 策略。当群里有人反馈问题或讨论改动方案时：

1. **程序层先筛**：该群在监听范围内、消息来自允许的来源 → 成为候选；
2. **语义层研判**：按提示词策略判断"这条讨论是否值得介入"——不需要人 @ 它；
3. **后台投机执行**：在该 Ticket 的隔离目录（`git worktree`）里**尝试复现故障、寻找修复方案**；
4. **交付门（关键）**：**只有在"确认了问题"且"找到了简单修复方案"两个条件都满足时**，才把结果交付给人；**否则全程保持安静**；
5. 满足条件时的交付形态：**提交修复 Pull Request**（而不是在群里长篇解释）；
6. 交完后：群聊 Channel 收到**一条**最终通知（PR 结果）；GitHub 上 PR 自身已展示结果，无需重复。

〔A〕配图描述的正是："群内还在讨论解决方案时，Super-agent 已在后台提交了修复 Pull Request"——即**它的输出比人的讨论更快产生了一个可验收物**。

> 〔D〕这条链条的真正门槛不在"能不能修"，而在**第 4 步的交付门**。要有"确认问题"的能力，意味着它必须**先写一个能复现失败的断言/脚本**（可判定），而不是"我觉得这是 bug"。所以"静默复现"策略的隐含前提是：**复现是可自动判定真假的**。这条策略在代码仓库里成立，在"这个功能设计得好不好"上不成立。抄的时候别把"静默"抄成"乱猜"。

### 7.3 实验：它到底快多少、贵多少〔A〕

实验设置：用群聊 + GitHub CI 消息流驱动四种方案；单次约 **300 条消息**、其中约 **20 条工作请求**；编码工作用**只耗时的工具**代替；每种方案**重复 5 次**。

| 方案 | p50 | p95 | 备注 |
|---|---|---|---|
| **Super-agent**（双层 + 订阅直通） | **12.4 min** | **15.7 min** | 基准成绩 |
| 单 Session + Subagent 工具（中性提示） | — | **29.5 min** | **5 次运行一次都没调用 Subagent**，全在主 Session 里干、不断被新消息打断 |
| 单 Session + Subagent（优先委派提示） | — | 仍慢于 Super-agent | 5 次有 4 次委派；剩下 1 次模型判断"工作很小"自己执行，形成**长尾** |

**订阅直通消融**〔A〕：

| 指标 | 有直通 | 无直通 | 变化 |
|---|---|---|---|
| 完成时间 | 基本一致 | 基本一致 | 直通**不提速** |
| Router 决定数 | — | **+约 30%** | 直通省 Router 负载 |
| 读缓存 token | **2,323 万** | **3,177 万** | **+约 37%** |

→ 结论：**直通不提速，但为 Router 省下可观的 token 与推理开销**。

**Router 批处理压测**〔A〕（Router 调真实模型、Worker 用 Mock）：1→40 Trigger/分钟，batch 1.0→2.8，单次请求 2.5s→3.9s，**单决定分摊推理 6.4s→1.6s**。→ 解释"去掉直通后峰值负载增加仍未触及瓶颈"，也是**不做过早水平切分**的依据。

**实验局限（团队自陈，必须一并转述）**〔A〕：基于**合成负载与简化环境**；主要评估**系统调度与协作能力**，**不衡量单个任务的实际执行能力**；部分设置还可更严谨，**仅作初步参考**。

> 〔D〕两句必须点出来的话：
> 1. **12.4 分钟不能外推**。编码工作是"只耗时工具"替身，真实编码任务是小时级；这个实验度量的是**排队与调度效率**，不是"修一个 bug 要多久"。
> 2. **经济性未被论证**。多会话本身就比单会话读缓存 token 高；直通省的 37% 是在一个**已经很贵的基线**上省的。文章没说"用更多 token 换更短更稳的时间"是否划算——智东西的转述把这句点破了，是中肯的。

## 8. 与现有 Agent 范式的差异

### 8.1 差异矩阵

| 维度 | **ReAct（单循环）** | **多 Agent 编排 / Agent Team** | **Claude Code / Codex 类** | **Super-agent** |
|---|---|---|---|---|
| 基本单位 | 一个同步循环 | 一个有向任务图/角色分工 | **一个 Session** | **一条事件流 + 一个 Ticket** |
| 驱动源 | 人类提示词 | 人类提示词（任务描述） | 人在终端/IDE 键入 | **环境事件（Trigger）** |
| 生命周期 | 一问一答，结束即止 | 一次性任务，有明确起止 | 会话开→关 | **常驻在线，永不停机** |
| 工具调用 | **同步阻塞**（`run()` 等到返回） | 通常同步或有限并发 | 同步（长命令阻塞会话） | **异步 `start()`/`stop()`**，结果作为新事件回流 |
| 谁开会话 | 人 | 框架 | 人 | **系统自己开（Session 是实现细节）** |
| 谁对外说话 | 该会话 | Lead | 该会话 | **只有 Router** |
| 并发粒度 | 无 | 任务内子步骤（紧耦合） | 单会话串行 | **任务间并行（松耦合、上下文隔离）** |
| 冲突处理 | — | 显式消息传递/协议 | — | **共享观察 + 自主避让**（订阅同一 Thread，无 P2P 协议） |
| 人的位置 | 每一步的输入者 | 任务描述者 + 结果接收者 | 操作者（盯着终端） | **决策与验收层**（只在关键点出现） |
| 上下文管理 | 全塞窗口 | 手工/摘要压缩 | 手工 + 自动压缩 | **当 Cache 管：Inline & Spill + 链式召回（引用图跳转）** |
| 异常恢复 | 无（重开） | 有限重试 | 无（重开会话） | **外部 Watchdog + 恢复注记 + 持久效果队列** |
| 状态与计算 | 绑定 | 框架进程内 | **绑定在本机** | **解耦**（云端计算/状态 + 本地执行环境 daemon，BYOM） |
| 失败模式 | 上下文溢出、跑偏 | Lead 推理过载、协调开销爆炸 | 长命令阻塞、关笔记本即死 | **Router 单点/分片矛盾、成本、安全边界** |

### 8.2 逐条展开的差异要点

**① vs ReAct：把"一个循环"劈成"两个循环"，且循环内部也非阻塞**
ReAct 的结构性缺陷是**同步工具调用**：模型发起 `run()` 后循环阻塞到工具返回，期间会话无法响应任何新输入。Super-agent 两处动手：**纵向**把"决策循环"（Router）与"执行循环"（Worker）分开；**横向**把耗时命令与子任务工具调用改成异步 `start()`/`stop()`——调用后立即收到"已启动"返回，循环不再等待；后台完成后系统把**最终结果作为一条新事件消息投递进会话**；模型也可调 `stop()` 主动终止执行过长的后台命令。于是**前台对话响应与后台任务执行解耦**，新输入在当前推理步结束后即被处理。〔A〕
〔A〕重要补充：**该异步任务机制已在 DeepSeek Harness 中实现，但尚未默认开启。**（这类"已实现未默认开"的功能，通常是踩过坑的——见 §10 风险。）

**② vs 多 Agent 编排：它是调度器，不是技术负责人**
这是最容易被抄错的地方。多 Agent 框架（LangGraph/AutoGen/CrewAI 式）回答的是"**一个任务怎么拆给多个角色**"；Super-agent 回答的是"**源源不断的任务流怎么排队、归属、授权、恢复**"。证据是 Router 的自我阉割：**不直接执行具体任务、甚至可以不配 Bash 工具、用轻量模型、不介入单任务内部拆解**。〔A〕
〔A〕文章给了反向判据：如果你用提示词把一个 Agent Team 的主会话约束成"不亲自执行、只对外交互并分派"，那它就已经是双层架构了。→ **判据是"主会话有没有下场干活"，不是"有没有多个 agent"。**

**③ vs Claude Code / Codex：会话从"交互单元"降级为"资源"**
Claude Code / Codex 里，Session 是**人和 AI 交互的基本单元**：人开一个会话，人盯着它，人关掉它。Super-agent 里 Session 是**系统内部的执行资源**：系统按 Ticket 自动创建、隔离、回收，用户**感知不到 Session 的存在**（"用户感觉始终只存在一个 Agent"）〔A〕。〔B〕原型的落地方式是 `worker-<ticketId>` 一 Ticket 一 Session 一目录，Ticket 结束后工具调用被拒绝、subagent 释放、shell job 被杀。
另一处硬差异：**多渠道**。Claude Code/Codex 的入口是终端/IDE；Super-agent 的入口是 IM 群、GitHub PR 评论、Issue、邮件——**人不用离开自己的工作界面**。

**④ vs Anthropic 脑手分离**：见 §4.3。相同的是架构原则（无状态 harness、外置日志、统一执行接口），不同的是威胁模型（托管沙箱 vs 用户间歇在线个人机 + 未提交修改 + 本地凭据）。

**⑤ 一个统一的类比（〔A〕作者自陈，本报告整理）：Agent 系统 ≈ 操作系统**

| OS 概念 | Super-agent 对应物 |
|---|---|
| 进程 / 线程 | Worker Session（`worker-<ticketId>`） |
| 进程隔离 / 地址空间 | 上下文隔离 + 一 Ticket 一目录 |
| 调度器 | Router 层（批处理 = 合并中断） |
| 调度优先级 / 防饿死 | worker slot + 1 个**人优先**额外 slot |
| 文件描述符 / 订阅 | Subscription（多对多） |
| capability / 权限令牌 | **Mandate**（不可变、带 Policy 版本、可重校验、可撤回） |
| 作业 / job | Ticket（自持状态，独立于执行体） |
| Write-Ahead Log | **Effects 持久队列 + 先存储后执行** |
| Page cache / 局部性 | **Inline & Spill** |
| inode / 硬链接 | 对象唯一 ID + 内联下一跳 ID（**链式召回**） |
| 系统调用边界 | **程序层 Gate（Fast Path）** —— 不让模型当权限边界 |
| watchdog timer | **外部 Watchdog Session** |
| 中断 / 信号 | Trigger |
| 快照恢复 | 恢复注记（先核对目录/git/远端再重做） |
| 影子模式 / dry-run | **accept mode = observe** |

> 〔D〕这个类比不是修辞。它的实用价值是：**当你在设计里卡住时，去 OS 里找对应机制**。团队自己就是这么做出来的（"相似设计约束会导出相似架构选择"）。但它也有个陷阱：**OS 的进程是确定性的，Agent 是概率性的**——所以 OS 里"进程挂了就重启"能成立，Agent 里"重跑一遍"可能得到不同的、更糟的结果。这正是为什么必须加 **Watchdog 判进展**（而不只是判存活）和**恢复注记**（而不是盲目重放）。

## 9. 实现原语清单（核心交付物）

> 用法：这张表是"零件清单"。**"最小实现形态"列是刻意往小里写的**——每条都给出一个能在 1–3 天内做出来的版本，以及它在该版本下的已知局限。这样你可以按 §9.9 的顺序增量搭建，而不是一次性造一个平台。

### 9.1 事件与路由层

| # | 原语 | 要解决什么问题 | 最小实现形态 | 证据 |
|---|---|---|---|---|
| P1 | **Source（事件源适配器）** | 异构渠道（IM/GitHub/邮件/CI）的事件如何归一；如何避免重启重放、如何避免自己回自己 | 每渠道一个 adapter，暴露 `read()` 返回 `{id, at, actor, text, scope, isBot}`；**持久化读取游标**（如 `github-cursor:<n>`）；**在进入领域前丢弃 bot 自己的消息与监听范围外的事件**；定义"什么算一个事件"（含仅随时间成立的条件） | 〔B〕 |
| P2 | **Trigger（不可变事件）** | 幂等与审计的单位是什么 | 一条 DB row：`{id, source, at, actor, raw, disposition}`，**不可变**；`at` 统一为 `Date#toISOString` 一种形式（便于文本比较与分页） | 〔B〕 |
| P3 | **幂等键 = Trigger，不是文本** | 同一条消息被两个渠道/两次轮询重复投递 | 用 Source 侧事件 ID（GitHub comment id / Feishu message id）做主键；**"接受两次只创建一个 Ticket"** 落在 `disposition` 表上，不靠内容哈希 | 〔B〕 |
| P4 | **Thread（事件流）** | 同一 PR / 同一 IM 话题 / 同一邮件串的连续事件要归到一起；同一条流上的研判必须串行 | Thread = 有序 Trigger 序列 + `{subscriptions, runningEval, decisionHistory}`；**同一 Thread 最多一个 Eval 在跑**，运行期间到达的 Trigger **合并进下一批** | 〔B〕 |
| P5 | **两级过滤：Gate(Fast) + Assessment(Slow)** | 高噪音低触发率；**不能用模型当权限边界** | 程序层：来源/群组/白名单/是否 @ 的确定性判定 → `{explicit, inferred, notAdmitted}`；语义层：LLM 按提示词规则研判，输出 Decision。**成本上必须先程序后模型** | 〔A〕〔B〕 |
| P6 | **Subscription + 直通（多对多）** | 后续事件不该绕全局节点；多 Worker 冲突不该需要 P2P 协议 | `thread.subscriptions: Set<ticketId>`；匹配 Trigger **扇出**给所有活动订阅 Ticket；**程序直接投递，不经过 Router 的一次 LLM 调用**；订阅**不检查发送者** | 〔A〕〔B〕 |
| P7 | **Thread ←→ 对象引用图（内联下一跳 ID）** | 长期运行后 Router 无法全量持有历史，又必须能找回 | 每个对象注入时**内联其紧密关联对象的 ID**；工具召回返回的对象同样内联下一跳 → 模型可逐跳展开 | 〔A〕 |
| P8 | **读取游标 / 位点** | 重启不重放、不漏读 | 每 Source 持久化一个位点；失败的读**不推进位点**（"读位置留在原地，下次读取补上漏掉的部分"） | 〔B〕 |

### 9.2 授权与生命周期层（**最关键的一层**）

| # | 原语 | 要解决什么问题 | 最小实现形态 | 证据 |
|---|---|---|---|---|
| P9 | **Policy（带版本）** | 规则会变，进行中的工作该按哪版规则算 | `{version, paused, evalTimeoutMs, rules[], sourceParts{allowList, botList, admissionTable}, acceptMode}`；`version` = 规则+acceptMode+Source 部分的**哈希**；变更**只投递给受影响的活动 Ticket**，不撤销 Mandate | 〔B〕 |
| P10 | **Mandate（授权凭证）** | "凭什么做这件事、能做多远"必须可审计、不可篡改、可撤回 | 不可变记录：`{policyVersion, scope, strength, matchedRules, senderIdentity, source, via}`；**scope 变宽 = 必须新 Ticket**；**只有人能 stop 撤回、Policy 不再支持才吊销**；**结束的 Ticket 恢复前必须 revalidate** | 〔B〕 |
| P11 | **Decision（四态）** | 研判结果要能被机器消费，不能是自由文本 | `accept / stop / ignore / unavailable`，各带 `reason`（`code` + `values` + `triggerId`） | 〔B〕 |
| P12 | **accept mode 三档（含影子模式）** | Agent 上线初期如何不闯祸 | `off` / **`observe`（默认）** / `auto`；observe 下正判定只记为 `ignoredFromCard`/"would accept"，**什么都不接受**；**明确请求在所有模式下都生效** | 〔B〕 |
| P13 | **准入表（Admission Table）** | "谁能通过哪个入口发起工作"是二维的，白名单一维不够 | 行 = 接收范围（各 IM 群 / 各 GitHub 范围 / DM / CI）；列 = 三个格：`名单内未@`、`名单外@`、`名单外未@`；每格取 `explicit / inferred / ignore` | 〔B〕 |
| P14 | **Ticket（工作单位 + 自持状态）** | 执行体会换、会挂、会被重启，但"这件事做到哪了"不能丢 | `open → ended`（`ended` 记录 when/by whom/why/outcome）；**状态自己定义，不跟随 Session**；`latestReport` 反映最近进展；结束时**未读的跟进消息退回 Eval** | 〔B〕 |
| P15 | **Assignment（Ticket↔Executor 绑定）** | 同一件工作可能先后由多个执行实例做 | `pending → running → ended`，**独立于 Ticket 生命周期**；一个 Ticket 先后可有多个；**只有最终 Report 可在 Executor 侧结束 Ticket** | 〔B〕 |
| P16 | **Report（六态）+ Attention（结构化提问）** | "做完了"不够，要区分进展/等待/就绪/受阻/失败/无需处理；"在等人"必须机器可判定 | `progress / waiting / ready / blocked / failed / dropped`；等人的提问走**独立结构化字段**，**禁止从自由文本推断** | 〔B〕 |
| P17 | **Ticket 阶段机（stage）** | 面板与调度需要一个"它现在卡在哪"的统一答案 | 按优先级自上而下取第一个匹配行：`person/delivery → person/answer → person/review → person/blocked 或 failed → working/queued → idle → working`；**`person` 前缀 = 无法自行继续** | 〔B〕 |
| P18 | **人 stop 的权限级否决** | 人的否决不能只是建议 | stop **撤回 Mandate**；被 stop 的 Ticket 保持 ended 且**不再接收任何消息**；同 Thread 后续工作在需要时走**新 accept** | 〔B〕 |

### 9.3 执行与资源层

| # | 原语 | 要解决什么问题 | 最小实现形态 | 证据 |
|---|---|---|---|---|
| P19 | **Executor 端口（Session 工厂）** | 执行体必须可替换、可隔离、可回收 | `open(ticketId) → Session`；一 Ticket 一 Session（`worker-<id>`）+ 一目录；**Ticket 结束后拒绝其工具调用**，释放 subagent | 〔B〕 |
| P20 | **prepare 命令 + 一 Ticket 一目录** | 并行任务不能共享工作区；投机执行必须可丢弃 | 首次派工前跑一次 `sh`（**10 分钟超时**），典型 `git worktree add`；失败则 Ticket 失败并记录输出；重试/人发言可再次尝试准备 | 〔B〕 |
| P21 | **worker slot + 1 个人优先 slot** | 并发有上限，但**人不能被机器任务饿死** | 计数信号量，上限可配；人的消息/状态请求可用 **+1 额外 slot**，并在新 launch 前优先取下一个空出的普通 slot | 〔B〕 |
| P22 | **异步工具：`start()` / `stop()`** | ReAct 的同步阻塞让人干等、且无法接新指令 | 耗时命令/子任务改为 `start()` 立即返回 `Started`；完成时**把结果作为新事件消息投递进会话**；`stop()` 可主动终止过长任务；**新输入在当前推理步结束后即处理** | 〔A〕（**DSH 已实现但未默认开启**） |
| P23 | **前台命令自动转后台 + 短 wait 上限** | 长命令把 worker 卡死，收不到新消息 | 预设层：前台 shell 命令 **5 秒后转后台 job**；`job_output` 等待上限 5 秒；拒绝 `sleep` 与超长 `timeoutMs` | 〔B〕 |
| P24 | **后台工作时限 + handoff 语义** | 后台任务无限拖会占住 slot | turn 结束后后台最多 **30 分钟** → 杀 shell job、报 waiting（附最后的话与被杀清单），**subagent 允许继续**；handoff 给人**立即释放 slot**，shell job（如评审用 server）可继绪且不占 slot | 〔B〕 |
| P25 | **恢复注记（recovery note）** | 崩溃/重启后盲目重放外部动作会造成重复副作用 | 重启时运行中的 Assignment 以 "host restarted" 结束，新 Assignment 携带注记："**先核对目录、git 历史、远端状态，再重复任何外部动作**"；按 oldest Ticket first 处理 | 〔B〕 |
| P26 | **执行环境变量注册表** | 执行体与 prepare 命令需要同一套上下文（仓库、Ticket、账号） | 各方 register `key, value, description`；命令读环境变量，**Executor 在提示词里读其值与描述**；**任何一项都不含凭据** | 〔B〕 |
| P27 | **审批/权限边界（诚实的那个版本）** | 想让 Agent"只能做某些事" | 命令 wrapper + `DSH_SUPERAGENT_BLOCKED_COMMANDS`（按名字拦截）；**文档明说：这只是默认值，不是安全边界——worker 仍可用绝对路径执行程序**。真正的边界要靠独立 OS 账号/容器 | 〔B〕 |

### 9.4 状态与持久化层

| # | 原语 | 要解决什么问题 | 最小实现形态 | 证据 |
|---|---|---|---|---|
| P28 | **单写者 Store + 事务** | 并发写状态会撕裂不变量 | **一个 SQLite 文件**（`<stateDir>/orchestrator.sqlite`），**只有 Store 打开**；启动先取**目录锁**防第二进程；`Engine` 是 Trigger/Thread/Decision/Ticket/Assignment 的**唯一写入者**；**每个命令一个事务**；迁移只升版，新版数据库拒绝启动 | 〔B〕 |
| P29 | **端口在事务内入队、提交后执行** | 状态改了但外部动作没做（或反之）会不一致 | 命令在自己的事务里 `enqueue(kind, key, payload)`；**只有 commit 后才开始执行**；`afterCommit` 钩子；回滚时绝不执行 | 〔B〕 |
| P30 | **Effects：持久副作用队列** | 外部调用会失败、会卡、会重试；进程会挂 | 表 `(kind, key, payload, order, attempts, lastError, dueAt)`，**每 kind/key 一行**（同 key 重复入队 = 替换 payload 并立即到期，不改队列顺序）；按 due 时间 oldest first、受并发上限；**指数退避**；`Later` 异常 = 延迟不计失败（如没空闲 slot）；每种 kind 一个 **health 条目**（连续 3 次失败才报错） | 〔B〕 |
| P31 | **Effect kinds（最小集合）** | 需要异步化的动作有哪些 | `assessment`（把候选卡送进 Router turn）、`launch`（起 Assignment）、`delivery`（投递 Input）、`relay`（把 worker 报告转进 Router）、`notice`（不唤醒 Router 地注入通知）、`reply`（发送消息） | 〔B〕 |
| P32 | **Outbox：幂等收据 + 定向保序** | 消息不能重发、不能乱序；但全局保序会杀掉并发 | 按消息 **id** 存收据（`pending/sent/dropped`），**同一 id 永不重复入队**；**同 Ticket 同会话保序**（前一条未发出则后一条等待，直到前一条连续失败 3 次）；**其他 Ticket、无 Ticket 的消息不等待** | 〔B〕 |
| P33 | **Dropped 的留痕** | 消息被丢弃后不能被重新排队，且要能追责 | 丢弃时记录**何时、为何、属于哪个 Ticket**，作为生成列（便于索引）；"dropped 的 ack 读起来是 dropped，不是 sent" | 〔B〕 |
| P34 | **暂停/恢复（pause）** | 出问题时需要"只停处理、不停记录" | pause 停止：派工、新 Eval、Eval 超时、Input 投递、回复；**Source 继续记录 Trigger**；**运行中的 Executor turn 不被中断**；pause 期间 Eval 不超时，恢复后每个截止时间**顺延 pause 的时长** | 〔B〕 |

### 9.5 上下文与记忆层

| # | 原语 | 要解决什么问题 | 最小实现形态 | 证据 |
|---|---|---|---|---|
| P35 | **Inline & Spill 注入阶梯** | 注入过多稀释注意力，过少迫使反复调工具 | ① 只给对象 ID + 摘要 → ② 内联紧密关联 ID → ③ 内联时空相邻内容（前 50 字、IM 前后消息与回复对象、评审讨论相邻评论）→ ④ 超上限截断，**保留续读入口** | 〔A〕 |
| P36 | **Thread 窗口（结构化注入）** | 研判需要局部上下文，但不能塞满 | 首批 5 条 + 目标消息前后各 5 条；消息以 `{id, from, at, text}` 给出，通常限 400 字、紧邻 2 条限 1,200 字；截断带 `chars`；**其余已加载消息降为 50 字 stub**，可按 id 展开 | 〔B〕 |
| P37 | **链式召回（引用图跳转）** | Router 无法持有全部历史，又要跨渠道找回旧任务 | 见 P7；**关键**：工具返回的对象**自身也遵循 Inline & Spill**，所以每一跳都会带出下一跳 ID | 〔A〕 |
| P38 | **Resource 面（可读资源命名空间）** | 模型需要一个稳定、可寻址的读接口，而不是一堆散装工具 | `tickets/ triggers/ threads/ decisions/` 分页列表（`{items, next_offset}`）；`thread/<key>`、`ticket/<id>` 及子资源（`/assignments`、`/inputs`、`/transcript`、`/report/<id>`）；**默认页 4,000 UTF-16 单位，列表 20 项**；**每个 id 都能从某一页读到**，模型可逐步走图；**没有任何东西靠哈希读**（Eval id、Policy 版本不上页） | 〔B〕 |
| P39 | **按角色裁剪的读权限** | Worker 只能看自己 Ticket 的东西，否则越界+上下文污染 | Executor 只能读自己的 Ticket、它的 Thread、到达它的 Trigger、它工作过的提示词版本与原件；**页面上不出现它读不到的 id**（Decisions、别的 Ticket） | 〔B〕 |
| P40 | **提示词/设置版本化** | 行为变更要可回滚、可归因 | 编号版本（`settings-version:<n>`、`prompt-version:<n>`），保存记录 origin、Policy 版本、受影响 Ticket；支持 `preview: true` 只组合不保存 | 〔B〕 |

### 9.6 交互与人机层

| # | 原语 | 要解决什么问题 | 最小实现形态 | 证据 |
|---|---|---|---|---|
| P41 | **单出口原则** | 多会话各自回复人 = 混乱 | **只有 Router 对外说话**；Worker 的推理与工具调用**不外泄**，只汇报状态 | 〔A〕〔B〕 |
| P42 | **按信道定制输出规范** | IM 与 PR 的信息带宽和习惯完全不同 | IM：**≤100 词**、只问直接问题、只给简短结论、只在需决策/验收时发通知；GitHub/邮件/文档：结构化高密度（问题背景、改动说明、验证结果） | 〔A〕〔B〕 |
| P43 | **静默默认 + 交付门** | 主动型 Agent 最容易变成噪音源 | 默认不说；只在"人必须行动"或"人能用上结果"时开口；主动工作必须有**双条件交付门**（如"确认问题"且"找到简单修复"）才交付 | 〔A〕 |
| P44 | **面板 = 待人工决定队列** | 需要一个"人现在该干什么"的唯一入口 | 首屏只列 `person/*` 阶段的 Ticket 与未解的 `unavailable` Decision；**健康状态不占空间**；每项给一键动作（回答/重试/停止/重新评估） | 〔B〕 |
| P45 | **Watchdog（外部控制回路）** | 长期运行的系统不能靠自身逻辑保证可靠；Agent 的异常常不是崩溃而是**陷入无效循环/跑偏** | **主系统之外**一个独立 Session，用**定时消息驱动**；既查基础设施（接口报错、状态恢复失败），也**用模型判断各 Worker 是否有实质进展、方向是否偏离**；发现异常介入修复，偶发故障持续复查；**本身具备完整工具**，可用自然语言问它故障原因，也可让它在线改主系统行为（增删提示词、调整触发规则） | 〔A〕 |
| P46 | **健康条目（health）** | 部分失败要被看见，但不能刷屏 | 每个部件/每种 effect 一个 health 条目，**由它自己的下一次成功清除**；**连续 3 次失败**才报错 | 〔B〕 |
| P47 | **未解决项升级提醒** | `unavailable` 之类的"没做成"容易被遗忘 | 仅当：Decision < 24 小时、是该 Thread 上最新 Decision、未被 dismiss、Thread 既未排队也未在研判时，才请人注意；可重新评估或 dismiss | 〔B〕 |

### 9.8 一组"被明确拒绝的概念"（省你很多弯路）〔B〕

原型的领域文档专门列了"Rejected concepts"，**这是最省时间的一节**——它告诉你哪些看起来自然的设计是坑：

| 被拒绝的设计 | 拒绝理由（原文意译） |
|---|---|
| 把 Principal / Membership 做成实体，或跨 Source 映射身份 | 人是 Trigger 元数据；白名单是 Policy 的 Source 部分；跨 Source 映射是**提示词文本** |
| 让 Eval 自己调度延迟 Trigger | 需要等待的条件就是一个普通 Source；**Eval 永不反向依赖 Source** |
| Eval 的 `waiting` / `revoked` 状态 | 等待属于 Source；超时的 Eval 把 Trigger 重新排队或记 `unavailable` |
| 一个 Thread 最多一个活动 Ticket | 一条 Thread 可承载多件独立工作；重复由 Ticket 列表在研判时规避 |
| "追加到 Ticket"这种 Decision | 追加 = Subscription 扇出，**不需要 Eval** |
| 在 Subscription 上做准入检查 | Subscription 覆盖整条 Thread；**Mandate 把授权与上下文分开** |
| 让 Correlation 参与路由 | **Subscription 负责路由；Correlation 只加上下文** |
| Ticket 状态跟随 DSH Session | Ticket 可被交接、恢复、由多个 Executor 执行，**必须自持状态** |
| 由 Executor 声明"某人让它停" | **只有 Eval 决定 stop 的强度** |
| Policy 变更时取消运行中的 Ticket | 取消会留下半成品；**记录并投递变更**，不撤销 |
| Executor 失败时锁死它全部工具 | 会连人直接在 Session 里的操作和恢复后的报告一起拒掉；**只暂停自动输入即可** |
| 从 Report 自由文本推断"在等人" | 需要结构化事实；Executor 必须用**结构化字段**提问 |

### 9.9 最小可行骨架：从零到能跑的顺序

如果我自己造，会按这个顺序，**每一步都可以停下来用**：

| 阶段 | 做什么 | 为什么必须在这个位置 | 验收标志 |
|---|---|---|---|
| **0** | **先写下两条不变量**：① 授权 ≠ 上下文（Subscription 流上下文，Mandate 流授权）② 一切外部副作用**先落库再执行** | 这两条事后补会重写全部业务代码 | 代码里找不到"某处顺手调了外部 API 而没入队" |
| **1** | **单 SQLite + Engine 单写者 + 目录锁** | 所有并发正确性的地基 | 两进程同时启动，一个被锁拒绝 |
| **2** | **Source → Trigger 幂等入库 + 读取游标** | 没有幂等，重试与重启都是灾难 | 同一事件重投两次，只产生一行 Trigger |
| **3** | **Thread + 两级过滤 + Eval(Gate→Assessment) → Decision** | 先把"要不要动"做对，再谈"怎么动" | Gate 用纯函数，单测覆盖"名单外 @ 也进不来" |
| **4** | **Ticket + Mandate + accept mode=observe** | 影子运行让你敢上线 | 观察一周"would accept"记录 |
| **5** | **Executor + 一 Ticket 一目录 + prepare** | 并行与可丢弃的前提 | 两个 Ticket 同时跑互不干扰 |
| **6** | **Effects 队列 + Outbox** | 到这里系统才能"崩了不丢活" | 杀进程重启，未发出的消息仍会发出且不重复 |
| **7** | **Subscription 直通 + 扇出** | 这一步才真正省下 Router 的 37% | 去掉直通对比 Router 决定数 |
| **8** | **worker slot + 人优先 +1 slot + 异步工具** | 人机体验的分水岭 | 并发打满时人发消息仍立刻有响应 |
| **9** | **Inline & Spill + 链式召回** | 长跑之后才痛，但设计要早定 | Router 能凭 ID 找回三天前的任务 |
| **10** | **Watchdog + 恢复注记** | 从"demo 能跑"到"能长期跑" | 故意让 worker 空转，Watchdog 能发现 |
| **11** | **存算分离 / BYOM** | 最后才做；§4.4 的单机降级已能拿到 80% 收益 | 合上笔记本，云端任务照常 |

> 〔D〕注意 **7 和 8 的位置**：直通与异步工具不是架构地基，而是**性能与体验优化**。很多团队会先做这两块（因为 demo 效果明显），结果状态管理一片混乱。**先把 0–6 做扎实。**

### 9.10 三个我认为最关键的原语

如果需要向别人解释这套架构，我只讲这三个——它们各自独立地改变了系统性质：

**① Mandate / Policy 授权层（P9 + P10 + P12）——把"权限"和"上下文"彻底切开**
没有它，主动型 Agent 就是"一条群消息就能指挥它去改代码"。有了它：上下文可以自由流动（订阅 Thread 即收），**权限却只能由 accept 创建、由人撤回、恢复前必须对当前 Policy 重校验**。再加 `observe` 影子模式，你获得一条**从"只记录"到"真执行"的渐进放权路径**——这是把主动型 Agent 安全上线的唯一现实办法。

**② Thread + Subscription 直通（P6 + P4）——事件归属的去中心化**
它同时解决三个问题：路由负载（后续事件不绕 Router）、并发冲突（共享观察替代 P2P 协议）、上下文连续性（同 Thread 自动同下文）。**它把"谁该处理这条消息"从每次询问中心节点，变成了第一次回答后就固化的程序路由**——这是 Router 不成为瓶颈的结构性原因，而不是靠模型变快。

**③ 持久 Effect 队列 + Outbox（P29–P33）——让"崩溃"变成可恢复事件**
它把系统从"一个幸运的进程"变成"一个可恢复的状态机"：先存储后执行、幂等收据、定向保序、指数退避、health 条目。**没有它，前两个原语都只是纸面设计**——因为"授权已创建但派工丢了""消息已发但记录没写"这类不一致会立刻摧毁信任。

### 9.11 原文没给、但我会补的两块（〔D〕，明确是推断）

**A. 验收门（Acceptance Gate）应当升为一等原语。**
文章反复说"人上移到决策与验收"，但实现里"验收"= `ready` Report + 人看 PR + 人点合并，**没有验收契约**。我会加：Ticket 从 `ready` → `ended` 必须满足一组**可检查的证据条件**（按工作类型配置），例如——附复现失败的测试/脚本、附测试通过证据、附改动范围与影响说明、附回滚方式；缺任一项则**不许进 `person/review`，而是退回 `working` 并提示缺什么。这把"验收"从人的隐性负担变成系统的显式约束，直接服务于"减少注意力占用"。

**B. 打扰预算（Attention Budget）应当被量化。**
原型的哲学是"注意力成本"，但落到机制只有 observe 模式和 100 词限制，**没有指标**。我会定义并监控：每个 Ticket 的**消息数**、每人每天的**被通知次数**、`ready` 之后被推翻的**返工率**、人 stop 的**比率**、以及"静默弃单率"（投机执行被判无价值而丢弃的比例）。**没有这些数字，"主动"会单调地滑向"噪音"，而你没证据。**

## 10. 未解问题与风险

### 10.1 官方自陈的四个开放问题〔A〕

1. **双层架构如何扩展**：单 Router 承载超限后**何时切分、切多细、Worker 间何时直接通信**均无定论；**跨月乃至更长跨度的长程记忆**也是瓶颈。
2. **脱离 Session 后如何协作**：聊天窗口未必是最终形态，交互可更多发生在 GitHub 等领域界面；还需支持用户**中途介入、接管与实时协同**。
3. **组织扩大后的上下文边界**：多个隔离实例间的 **A2A 通信与协作**待探索。
4. **安全与隐私**：云端 Agent 接入端侧凭据存在**被入侵与提示词注入**风险；还需做到**让 Agent 不接触凭据本身也能使用凭据**。

原型文档另列两条〔B〕：**信任边界**（哪些 Trigger 字段可信——Source 的 actor 与 Thread 成员关系可信；正文与引用不可信）、**部署隔离**（Agent 的 profile 应钉在自己的 DSH 安装上，避免别处升级把它弄坏）。

### 10.2 我认为最该警惕的五点〔D〕

| # | 风险 | 判断依据 | 应对 |
|---|---|---|---|
| R1 | **Router 的"单点 vs 分片"内在矛盾未解** | 文章承认"切分越细连续性越低，在全局记忆解决前这一权衡始终存在" | 别把"跨月连续记忆"当卖点写进产品承诺；先按"单团队/单仓库"设边界 |
| R2 | **性能数字不可外推** | 合成负载、只耗时工具替身、仅评调度不评执行；真实编码任务小时级 | 用自己场景的 p95 重测；把"调度效率"与"任务质量"分开度量 |
| R3 | **经济性未论证** | 多会话读缓存 token 本就更高；37% 是在昂贵基线上省的 | 先测"每完成一件可验收工作的总成本"，再决定要不要多会话 |
| R4 | **信任边界与凭据暴露是最大工程风险** | Worker **以 operator 的 OS 用户、无审批**执行命令；blocked commands **只是默认不是安全边界**（可按绝对路径绕过）；云端接本地机意味着提示词注入直达凭据 | 独立 OS 账号/容器跑 Agent；凭据走代理（Agent 用"能力"而非"秘密"）；默认 accept mode=observe；默认不自动合并 |
| R5 | **主动性的度量缺失** | 只有 observe 与静默原则，无 precision/recall/噪音预算 | 见 §9.11-B，先建指标再放开 auto |

### 10.3 文章架构 vs 原型实现：哪些没落地〔B〕

原型 README 明确："有些文章讨论的设计是未来方向，本原型未实现"。据文档推断（**〔D〕，属"缺席证据"推断**）：

| 文章模块 | 原型状态 | 依据 |
|---|---|---|
| 双层架构（Router/Worker） | **已落地**（主 Session/Executor Session） | 架构文档有 `orchestrator` / `worker` 双角色与两套 preset |
| 事件驱动（两级过滤、订阅直通、链式召回、投机执行） | **大部分落地**（Source/Eval/Subscription/资源分页） | 领域模型与 Engine 命令齐全 |
| 异步 ReAct Loop | **DSH 已实现但未默认开启**（文章明说） | 〔A〕 |
| 面向人的交互（多信道、100 词） | **已落地** | 代码层限制 100 词、按信道提示词 |
| **存算分离 / BYOM** | **未见实现**（原型是单进程 + 本地 SQLite） | 架构文档无 daemon、无云端状态、无 BYOM 相关模块 |
| **Watchdog** | **未见实现**（架构文档无 Watchdog 模块/effect kind） | 同上 |
| **A2A / 多实例协作** | **未实现**（列为开放问题） | 〔A〕 |

> 这条差异极其重要：**你读文章会以为这是一套已跑通的系统，实际跑通的只是"单机双层 + 事件驱动 + 授权"**。存算分离与 Watchdog 是纯设计主张。抄的时候按"哪些有代码"分级投入。
